*Topic: [[../Topicwise_answers_exam_style/T01_DB_Concepts_and_Architecture.md#T01.2 · File system vs DBMS (8 disadvantages of file systems)|T01.2 · File system vs DBMS (8 disadvantages of file systems)]] · Section A* · CLO1
*(Repeated question: Also asked in 2017 | Solved in T01)*

**Question.**
Discuss four significant differences between a file-processing system and a DBMS.

**Answer.**

| Feature | File Processing System | DBMS (Database Management System) |
| :--- | :--- | :--- |
| **Data Redundancy & Inconsistency** | Data is duplicated across multiple separate files. Different copies easily get out of sync. | Centralizes data storage. Normalization avoids duplication and keeps copies consistent. |
| **Data Access & Retrieval** | Programmers must write a new custom program in C or Java for each new query. | Users write declarative queries (like SQL) to retrieve ad-hoc data quickly without new code. |
| **Data Isolation & Independence** | Data structures and application code are tightly coupled. Changing a file structure breaks programs. | Provides data abstraction. Changes to physical storage structures do not affect application programs. |
| **Concurrent Access & Recovery** | Hard to coordinate simultaneous access. Multiple updates cause lost data. Crash recovery is manual. | Built-in concurrency control prevents conflicting updates. Automated logging and recovery preserve ACID properties. |

### Q.1(b) · 03 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T01_DB_Concepts_and_Architecture.md#T01.3 · Functions/roles of the DBA ("five functions"); relation schema|T01.3 · Functions/roles of the DBA ("five functions"); relation schema]] · Section A* · CLO1
*(Repeated question: Also asked in 2020 | Solved in T01)*

**Question.**
What are the five main functions of a database administrator?

**Answer.**

**Five Main Functions of a Database Administrator (DBA):**
1. **Schema definition:** The DBA creates the original database schema by executing DDL statements.
2. **Storage structure and access-method definition:** The DBA defines internal storage structures, indexing methods, and file organizations to optimize data access.
3. **Schema and physical-organization modification:** The DBA modifies database schemas and physical storage layouts to improve performance or adapt to changing business requirements.
4. **Granting of authorization for data access:** The DBA assigns access rights and user roles to regulate who can inspect or modify specific data items.
5. **Routine maintenance:** The DBA performs recurring operational tasks. These include periodically backing up the database, monitoring running jobs, and ensuring sufficient free disk space.

**Relation Schema:**  
A **relation schema** is the formal logical definition or blueprint of a relation (table). It specifies the name of the relation along with its set of attributes (columns) and their corresponding domains (data types).

- Format: $R(A_1, A_2, \dots, A_n)$
- Example: $\text{instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$, where $\underline{\text{ID}}$ serves as the primary key.

### Q.1(c) · 05 Marks · CLO2

*Topic: [[../Topicwise_answers_exam_style/T03_Relational_Model_Keys_and_Integrity.md#T03.3 · Referential integrity & FK syntax (MySQL)|T03.3 · Referential integrity & FK syntax (MySQL)]] · Section A* · CLO2

**Question.**
How do we achieve referential integrity in DBMS? Provide necessary MySQL query with an appropriate example.

**Answer.**

**1. How Referential Integrity is Achieved in DBMS:**  
Referential integrity ensures that relationships between tables remain consistent. It requires that any foreign key value in a referencing table must exist as a primary key value in the referenced table, or be NULL.  
A DBMS achieves referential integrity through three mechanisms:
1. **Constraint Declaration:** The database designer defines foreign keys in the DDL schema using the `FOREIGN KEY ... REFERENCES` clause.
2. **Active Violation Checking:** The DBMS monitors `INSERT`, `UPDATE`, and `DELETE` commands. It blocks any operation that creates orphan child records.
3. **Automated Referential Actions:** The designer specifies rules for parent modifications:
   - `CASCADE`: Deleting or updating a parent row automatically deletes or updates matching child rows.
   - `SET NULL`: Sets child foreign key columns to NULL when the parent row is deleted or updated.
   - `RESTRICT` / `NO ACTION`: Default rule; rejects parent deletion or update if matching child rows exist.

**2. MySQL DDL Query Example:**

```sql
-- Parent table (Referenced relation)
CREATE TABLE Department (
    dept_name VARCHAR(20) PRIMARY KEY,
    building VARCHAR(20),
    budget DECIMAL(12, 2)
);

-- Child table (Referencing relation)
CREATE TABLE Student (
    student_id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    dept_name VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES Department(dept_name)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

**3. Operation and Violation Demonstration:**  
Populate a valid parent department:

```sql
INSERT INTO Department VALUES ('ECE', 'Academic Building 2', 500000.00);
INSERT INTO Student VALUES (101, 'Akib', 'ECE'); -- Allowed
```

Now attempt a violating insert with a nonexistent department:

```sql
INSERT INTO Student VALUES (102, 'Shuvo', 'ME');
```

**MySQL System Response:**  
MySQL rejects the insert and raises an integrity violation error:

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`university`.`Student`, CONSTRAINT `student_ibfk_1` FOREIGN KEY (`dept_name`) REFERENCES `Department` (`dept_name`) ON DELETE CASCADE ON UPDATE CASCADE)
```

If `'ECE'` is deleted from `Department`, `ON DELETE CASCADE` automatically deletes student 101. This keeps the database consistent.

**Question.**
Consider the following relation schema:<br>&emsp;customer (<u>id</u>, name, age, gender)<br>&emsp;order (<u>id</u>, product, price, date)<br><br>Now, give expression in relational algebra to-<br>(i) find name of the customers who are male.<br>(ii) find name of all customers who have purchased car as product.<br>(iii) find the details of all customers who have purchased "phone" as product and the price is less than \$300.

**Answer.**

*Assumption: The attribute `order.id` represents the customer identifier that placed the order.*

**(i) Names of male customers:**

$$
\boxed{\Pi_{\text{name}}(\sigma_{\text{gender} = \text{"male"}}(\text{customer}))}
$$

**(ii) Names of all customers who purchased car as product:**

Join customer and order on `id`, filter for product "car", and project customer names:

$$
\boxed{\Pi_{\text{name}}(\text{customer} \bowtie \sigma_{\text{product} = \text{"car"}}(\text{order}))}
$$

**(iii) Details of all customers who purchased "phone" priced under \$300:**

Filter order records for product "phone" with price below 300, then join with customer:

$$
T_{\text{target\_orders}} \leftarrow \sigma_{\text{product} = \text{"phone"} \land \text{price} < 300}(\text{order})
$$

$$
\boxed{\text{customer} \bowtie T_{\text{target\_orders}}}
$$

To project customer attributes only:

$$
\Pi_{\text{customer.id}, \text{name}, \text{age}, \text{gender}}(\text{customer} \bowtie T_{\text{target\_orders}})
$$

### Q.2(b) · 03 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T03_Relational_Model_Keys_and_Integrity.md#T03.2 · Keys: super / candidate / primary / alternate / composite / foreign|T03.2 · Keys: super / candidate / primary / alternate / composite / foreign]] · Section A* · CLO1
*(Repeated question: Also asked in 2023 | Solved in T03)*

**Question.**
Differentiate among Superkey, Candidate Key and Primary Key with an appropriate example.

**Answer.**

A key is an attribute or set of attributes used to identify rows in a table.

**Distinctions Among Keys:**

| Key Type | Definition | Minimality | NULL Allowed |
| :--- | :--- | :--- | :--- |
| **(i) Primary Key** | The candidate key chosen by the database designer to identify tuples uniquely. | Yes (minimal) | No (never allowed) |
| **(ii) Candidate Key** | A minimal super key. Removing any attribute destroys uniqueness. | Yes (strictly minimal) | Yes (unless constrained `NOT NULL`) |
| **(iii) Super Key** | Any set of attributes that uniquely identifies a row. May contain extra attributes. | No (can have redundant attributes) | No for identifying columns |
| **(iv) Composite Key** | A key that consists of two or more attributes rather than a single attribute. | Can be minimal (candidate) or non-minimal | Depends on whether it is PK or unique |

**Relationship:**
$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

**Running Example:**  
Consider relation $\text{Student}(\underline{\text{student\_id}}, \text{name}, \text{email}, \text{nid}, \text{dept\_name})$:

| student_id | name | email | nid | dept_name |
| :--- | :--- | :--- | :--- | :--- |
| 101 | Akib | akib@gmail.com | 1999123456 | ECE |
| 102 | Shuvo | shuvo@gmail.com | 2000654321 | ECE |
| 103 | Sakib | sakib@gmail.com | 2001987654 | ETE |

- **Super Key:** Any set containing a candidate key. Examples: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{student\_id}, \text{name}\}$, $\{\text{email}, \text{dept\_name}\}$.
- **Candidate Key:** Minimal sets with no extra columns: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{nid}\}$.
- **Primary Key:** The chosen identifier: $\{\text{student\_id}\}$.
- **Composite Key:** In table $\text{Takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{grade})$, the combination $\{\text{student\_id}, \text{course\_id}\}$ forms a composite candidate and primary key. Neither column alone identifies an enrollment record.

*Short version for 2018 Q.2(a) (4 marks):* Omit (iv) Composite key. Keep the definitions, distinctions table, and the Student running example for Super Key, Candidate Key, and Primary Key.  
*Short version for 2021 Q.2(b) (3 marks):* Same as 2018 Q.2(a). Present the 3-row distinction table and the Student relation key classification.

### Q.2(c) · 04 Marks · CLO2

*Topic: [[../Topicwise_answers_exam_style/T04_Relational_Algebra_and_Calculus.md#T04.3 · Explain an RA expression in words|T04.3 · Explain an RA expression in words]] · Section A* · CLO2

**Question.**
For each expression, explain in words what the expression does.<br>Where takes(<u>id</u>, <u>course</u>, <u>sec_id</u>, sem, year, grade)<br>(i) $\sigma_{year \ge 2009}(\text{takes}) \bowtie \text{student}$<br>(ii) $\Pi_{id, name, course\_id}(\text{student} \bowtie \text{takes})$

**Answer.**

**(i) Expression:** $\sigma_{year \ge 2009}(\text{takes}) \bowtie \text{student}$

1. **Selection:** Filters the `takes` relation to keep only enrollment records where `year` is 2009 or later.
2. **Natural Join:** Joins the filtered course enrollments with the `student` relation on their common attribute `id`.
3. **Meaning in words:** Retrieves full student and enrollment records for all students who took a course in 2009 or later.

**(ii) Expression:** $\Pi_{id, name, course\_id}(\text{student} \bowtie \text{takes})$

1. **Natural Join:** Matches each student with the courses they have taken by joining `student` and `takes` on `id`.
2. **Projection:** Keeps only student ID (`id`), name (`name`), and course ID (`course_id`). Discards other attributes and eliminates duplicates.
3. **Meaning in words:** Lists the ID, name, and course taken for every student and each course they enrolled in.

### Q.3(b) · 04 Marks · CLO4

*Topic: [[../Topicwise_answers_exam_style/T02_ER_and_EER_Modeling.md#T02.2 · Attribute types (simple/composite, single/multivalued, derived)|T02.2 · Attribute types (simple/composite, single/multivalued, derived)]] · Section A* · CLO4

**Question.**
Define entity and attribute. Explain the following attributes-<br>(i) Multi-valued<br>(ii) Derived<br>(iii) Composite

**Answer.**

- **Entity:** A "thing" or "object" in the real world that exists and is distinguishable from other objects (e.g., a specific instructor `ID = 22222`, or a student).
- **Attribute:** A descriptive property possessed by all members of an entity set (e.g., `name`, `salary`).

**Explanation of Attribute Types:**

1. **Multi-valued Attribute:**
   - Holds a set of multiple values for a single entity instance.
   - Depicted by a **double ellipse** in Chen notation.
   - *Example:* An instructor may have multiple phone numbers (`phone_numbers` = `{0171..., 0181...}`).

2. **Derived Attribute:**
   - The value is not stored directly. It is computed from stored attributes or system values.
   - Depicted by a **dashed ellipse** in Chen notation.
   - *Example:* `age` derived from current date minus `date_of_birth`.

3. **Composite Attribute:**
   - Can be divided into smaller component attributes with independent meanings.
   - Depicted by an ellipse with attached branches leading to sub-ellipses.
   - *Example:* `name` divided into `first_name`, `middle_initial`, and `last_name`.

### Q.4(a) · 12 Marks · CLO2

*Topic: [[../Topicwise_answers_exam_style/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.7 · Multi-table business-schema query sets (MySQL): Covid, Company, Insurance, E-commerce|T05.7 · Multi-table business-schema query sets (MySQL): Covid, Company, Insurance, E-commerce]] · Section A* · CLO2

**Question.**
Consider the following E-comerce database:<br>&emsp;client (<u>c_no</u>, name, city, state, Baldue)<br>&emsp;product (<u>p_no</u>, description, profit_percent, quantity, sell_price, cost_price)<br>&emsp;salesman (<u>s_no</u>, name, city, state, sal_amount, target, sold_yearly, remarks)<br>&emsp;order (<u>order_no</u>, client_no, order_date, delivery_address, salesman_no, del_type, del_date, order_status)<br>&emsp;order_details (<u>order_no</u>, product_no, quantity_ordered, product_rate)<br><br>(i) Find the total value of each product sold.<br>(ii) Find the products and their quantities for the orders placed by client no "C0001" and "C0002".<br>(iii) Find the product no and description of the products not being sold.<br>(iv) Find if the product "Lyera Top" has been ordered by any client and print the client_no, name to whom it was sold.<br><br>*(Note: "E-comerce" and "Lyera Top" printed verbatim from original question paper)*

**Answer.**

*(i) Total value of each product sold:*

```sql
SELECT od.product_no,
       p.description,
       SUM(od.quantity_ordered * od.product_rate) AS total_value
FROM order_details od
JOIN product p ON od.product_no = p.p_no
GROUP BY od.product_no, p.description;
```

*(ii) Products and quantities ordered by client "C0001" and "C0002":*

```sql
SELECT o.client_no,
       od.product_no,
       p.description,
       od.quantity_ordered
FROM `order` o
JOIN order_details od ON o.order_no = od.order_no
JOIN product p ON od.product_no = p.p_no
WHERE o.client_no IN ('C0001', 'C0002');
```

*(iii) Product number and description of products not sold:*

```sql
SELECT p_no, description
FROM product
WHERE p_no NOT IN (
    SELECT DISTINCT product_no
    FROM order_details
);
```

*(Alternative using `NOT EXISTS`:*
```sql
SELECT p.p_no, p.description
FROM product p
WHERE NOT EXISTS (
    SELECT 1
    FROM order_details od
    WHERE od.product_no = p.p_no
);
```
*)*

*(iv) Check if "Lyera Top" was ordered and display client number and name:*

```sql
SELECT DISTINCT c.c_no, c.name
FROM client c
JOIN `order` o ON c.c_no = o.client_no
JOIN order_details od ON o.order_no = od.order_no
JOIN product p ON od.product_no = p.p_no
WHERE p.description = 'Lyera Top';
```

### Q.5(a) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T02_ER_and_EER_Modeling.md#T02.1 · Entity sets, relationship sets, types of relationships (unary/binary/ternary)|T02.1 · Entity sets, relationship sets, types of relationships (unary/binary/ternary)]] · Section B* · CLO1

**Question.**
What is ER diagram? Illustrate different types of relationship that can be represented in ER diagram.

**Answer.**

An **Entity-Relationship (E-R) diagram** is a graphical tool used in database design. It represents the conceptual schema of an enterprise by depicting entities, their attributes, and the relationships among them.

The **degree** of a relationship set is the number of participating entity sets. Different types of relationships based on degree include:

1. **Unary (Recursive) Relationship (Degree 1):**
   - The same entity set participates more than once in different roles.
   - *Example:* A `course` entity related to another `course` entity via a `prereq` relationship (roles: `course_id` and `prereq_id`).

2. **Binary Relationship (Degree 2):**
   - Involves two distinct entity sets. This is the most common relationship type.
   - *Example:* `instructor` and `student` linked by the `advisor` relationship.

3. **Ternary Relationship (Degree 3):**
   - Involves three distinct entity sets simultaneously.
   - *Example:* `proj_guide` linking `instructor`, `student`, and `project`.

| Relationship Type | Degree | Description | Example |
| :--- | :---: | :--- | :--- |
| **Unary (Recursive)** | 1 | Association among entities of the same entity set | Course $\xrightarrow{\text{prereq}}$ Course |
| **Binary** | 2 | Association between two distinct entity sets | Instructor $\xrightarrow{\text{advisor}}$ Student |
| **Ternary** | 3 | Association among three distinct entity sets | Instructor, Student, Project $\xrightarrow{\text{proj\_guide}}$ |
| **$n$-ary** | $n$ | Association among $n$ entity sets | Rare; usually decomposed into binary |

### Q.5(b) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T08_Normalization_and_Functional_Dependencies.md#T08.4 · Attribute closure $X^+$, $F^+$, finding candidate keys|T08.4 · Attribute closure $X^+$, $F^+$, finding candidate keys]] · Section B* · CLO1

**Question.**
Compute the closure of the following set F of functional dependencies for relational schema r (A, B, C, D, E).<br><br>&emsp;$A \to BC$<br>&emsp;$CD \to E$<br>&emsp;$B \to D$<br>&emsp;$E \to A$<br><br>List the candidate Keys for R.

**Answer.**

#### 1. Closure of Functional Dependencies ($F^+$)

The complete closure $F^+$ contains over one hundred trivial and non-trivial dependencies, which is too large to write out fully.

We compute the attribute closures of each single attribute and pair under $F$:

1. **$A^+$:**
   - Initial: $\{A\}$
   - Using $A \rightarrow BC$: $\{A, B, C\}$
   - Using $B \rightarrow D$: $\{A, B, C, D\}$
   - Using $CD \rightarrow E$: $\{A, B, C, D, E\}$
   - Result: $A^+ = \{A, B, C, D, E\}$

2. **$B^+$:**
   - Initial: $\{B\}$
   - Using $B \rightarrow D$: $\{B, D\}$
   - Result: $B^+ = \{B, D\}$

3. **$C^+$:**
   - No FD has $C$ on the LHS alone.
   - Result: $C^+ = \{C\}$

4. **$D^+$:**
   - No FD has $D$ on the LHS alone.
   - Result: $D^+ = \{D\}$

5. **$E^+$:**
   - Initial: $\{E\}$
   - Using $E \rightarrow A$: $\{E, A\}$
   - Since $A^+ = \{A, B, C, D, E\}$: $\{A, B, C, D, E\}$
   - Result: $E^+ = \{A, B, C, D, E\}$

6. **Key Two-Attribute Closures:**
   - $BC^+$: Using $B \rightarrow D$, we get $\{B, C, D\}$. Using $CD \rightarrow E$, we get $\{B, C, D, E\}$. Using $E \rightarrow A$, we get $\{A, B, C, D, E\}$. So $BC^+ = \{A, B, C, D, E\}$.
   - $CD^+$: Using $CD \rightarrow E$, we get $\{C, D, E\}$. Using $E \rightarrow A$, we get $\{A, C, D, E\}$. Using $A \rightarrow BC$, we get $\{A, B, C, D, E\}$. So $CD^+ = \{A, B, C, D, E\}$.

**Key Non-Trivial Functional Dependencies in $F^+$ (derived using Armstrong's Axioms):**
- $A \rightarrow D$ (by Decomposition of $A \rightarrow BC$ to $A \rightarrow B$, then Transitivity with $B \rightarrow D$).
- $A \rightarrow E$ (by Transitivity from $A \rightarrow CD$ and $CD \rightarrow E$).
- $E \rightarrow B, E \rightarrow C, E \rightarrow D$ (by Transitivity from $E \rightarrow A$ and $A \rightarrow BCDE$).
- $BC \rightarrow E$ (by Augmentation of $B \rightarrow D$ to $BC \rightarrow CD$, then Transitivity with $CD \rightarrow E$).
- $CD \rightarrow A, CD \rightarrow B$ (by Transitivity from $CD \rightarrow E$, $E \rightarrow A$, and $A \rightarrow B$).

#### 2. Candidate Keys for $R$

A candidate key is a minimal set of attributes whose closure contains all attributes $\{A, B, C, D, E\}$.

- $A^+ = \{A, B, C, D, E\} \implies \{A\}$ is a candidate key.
- $E^+ = \{A, B, C, D, E\} \implies \{E\}$ is a candidate key.
- $BC^+ = \{A, B, C, D, E\}$, while neither $B^+$ nor $C^+$ is a superkey $\implies \{BC\}$ is a candidate key.
- $CD^+ = \{A, B, C, D, E\}$, while neither $C^+$ nor $D^+$ is a superkey $\implies \{CD\}$ is a candidate key.

$$
\text{Candidate Keys} = \{A\}, \{E\}, \{BC\}, \{CD\}
$$

### Q.5(c) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T08_Normalization_and_Functional_Dependencies.md#T08.7 · 2NF test from an FD set|T08.7 · 2NF test from an FD set]] · Section B* · CLO1

**Question.**
Given a relation R (A, B, C, D) and functional dependency at FD = { AB $\to$ CD, B $\to$ C }. Determine whether the given R is in 2NF? If not, convert it into 2NF.<br><br>*(Note: "functional dependency at FD" printed verbatim from original question paper)*

**Answer.**

#### 1. Determine Candidate Key and Attribute Types

Given relation $R(A, B, C, D)$ and functional dependencies:
$$
FD = \{AB \rightarrow CD, B \rightarrow C\}
$$

- Attribute $A$ never appears on the right-hand side of any dependency. Thus, every candidate key must contain $A$.
- Compute closure of $AB$:
$$
AB^+ = \{A, B, C, D\}
$$
- Test proper subsets:
  - $A^+ = \{A\}$
  - $B^+ = \{B, C\}$
  Neither subset is a superkey. Therefore, $AB$ is minimal.

$$
\text{Candidate Key} = \{AB\}
$$
$$
\text{Prime Attributes} = \{A, B\}
$$
$$
\text{Non-Prime Attributes} = \{C, D\}
$$

#### 2. Test for Second Normal Form (2NF)

A relation is in 2NF if it is in 1NF and no non-prime attribute depends on a proper subset of any candidate key.

Examine the dependencies:
1. $AB \rightarrow CD$: The determinant $AB$ is the complete candidate key. This is a **full functional dependency**.
2. $B \rightarrow C$: The determinant $B$ is a proper subset of candidate key $AB$, and $C$ is a non-prime attribute. This is a **partial functional dependency**.

Because a partial dependency exists ($B \rightarrow C$), **the relation $R$ is NOT in 2NF**.

#### 3. Conversion to 2NF

To achieve 2NF, we decompose $R$ by isolating the partial dependency into its own relation:

1. Create a relation for the partial dependency:
$$
R_1(B, C) \quad \text{with } FD_1 = \{B \rightarrow C\}
$$
$$
\text{PK of } R_1 = B
$$

2. Remove the determined attribute $C$ from the original relation:
$$
R_2(A, B, D) \quad \text{with } FD_2 = \{AB \rightarrow D\}
$$
$$
\text{PK of } R_2 = AB
$$

**Verification:**
- In $R_1(B, C)$, the candidate key is $B$. The non-prime attribute $C$ depends on the entire key. $R_1$ is in 2NF.
- In $R_2(A, B, D)$, the candidate key is $AB$. The non-prime attribute $D$ depends on the full key $AB$. $R_2$ is in 2NF.
- Lossless join: $R_1 \cap R_2 = \{B\}$, which is the primary key of $R_1$. Thus, the decomposition is lossless.

$$
\boxed{\text{Decomposed 2NF Relations: } R_1(B, C) \text{ and } R_2(A, B, D)}
$$

### Q.6(b) · 05 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T08_Normalization_and_Functional_Dependencies.md#T08.5 · Canonical cover $F_c$ (and how it differs from normalization)|T08.5 · Canonical cover $F_c$ (and how it differs from normalization)]] · Section B* · CLO1

**Question.**
Define Functional dependency. Consider the following functional dependency set:<br><br>&emsp;$\text{FD} = \{$<br>&emsp;&emsp;$A \to BC,$<br>&emsp;&emsp;$CD \to E,$<br>&emsp;&emsp;$B \to D,$<br>&emsp;&emsp;$E \to A$<br>&emsp;$\}$<br><br>Find the canonical form of the FD set.

**Answer.**

#### 1. Definition of Functional Dependency

A **functional dependency** (FD) is a constraint between two sets of attributes in a relation schema $R$.

Let $\alpha \subseteq R$ and $\beta \subseteq R$. The functional dependency:
$$
\alpha \rightarrow \beta
$$
holds on $R$ if, in every legal relation instance $r(R)$, whenever any two tuples $t_1$ and $t_2$ have the same values for attributes in $\alpha$, they must also have the same values for attributes in $\beta$:
$$
\text{If } t_1[\alpha] = t_2[\alpha] \implies t_1[\beta] = t_2[\beta]
$$

We say $\alpha$ functionally determines $\beta$.

#### 2. Finding the Canonical Cover ($F_c$)

A canonical cover $F_c$ satisfies two conditions:
1. No functional dependency contains an extraneous attribute (on the LHS or RHS).
2. Each left-hand side of a functional dependency is unique.

**Step 1: Apply the Union Rule to combine identical LHS**  
In the given set $F = \{A \rightarrow BC, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$, the left-hand sides are $A, CD, B, E$. All left-hand sides are already unique.

**Step 2: Test for Extraneous Attributes**

1. **Check $A \rightarrow BC$:**
   - **Test attribute $B$ (on RHS):**  
     Form $F' = \{A \rightarrow C, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$.  
     Compute $A^+$ under $F'$:  
     $A^+ = \{A, C\}$.  
     $A^+$ does not contain $B$. Therefore, $B$ is **not extraneous**.
   - **Test attribute $C$ (on RHS):**  
     Form $F' = \{A \rightarrow B, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$.  
     Compute $A^+$ under $F'$:  
     $A^+ = \{A, B, D\}$ (via $A \rightarrow B$ and $B \rightarrow D$).  
     $A^+$ does not contain $C$. Therefore, $C$ is **not extraneous**.

2. **Check $CD \rightarrow E$:**
   - **Test attribute $C$ (on LHS):**  
     Check if $D \rightarrow E$ holds under $F$.  
     Compute $D^+$ under $F$: $D^+ = \{D\}$.  
     $D^+$ does not contain $E$. Therefore, $C$ is **not extraneous**.
   - **Test attribute $D$ (on LHS):**  
     Check if $C \rightarrow E$ holds under $F$.  
     Compute $C^+$ under $F$: $C^+ = \{C\}$.  
     $C^+$ does not contain $E$. Therefore, $D$ is **not extraneous**.

3. **Check $B \rightarrow D$:**  
   Both LHS and RHS have a single attribute. Neither can be removed without dropping the dependency entirely.

4. **Check $E \rightarrow A$:**  
   Both LHS and RHS have a single attribute. Neither can be removed.

**Step 3: Resulting Canonical Cover**  
Since there are no extraneous attributes, the canonical cover is:

$$
\boxed{F_c = \{A \rightarrow BC, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}}
$$

*(Note: In minimal cover form with singleton right-hand sides, the equivalent set is $\{A \rightarrow B, A \rightarrow C, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$. Both representations are correct.)*

### Q.7(a) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T09_Transactions_ACID_and_Anomalies.md#T09.1 · ACID properties (with the \$50 transfer example/diagram)|T09.1 · ACID properties (with the \$50 transfer example/diagram)]] · Section B* · CLO1
*(Repeated question: Also asked in 2017 | Solved in T09)*

**Question.**
Explain the ACID properties of transaction.

**Answer.**

A **transaction** is a logical unit of program execution that accesses and updates data items. To preserve data integrity during crashes and concurrent access, the DBMS must ensure the four **ACID** properties:

1. **Atomicity ("All-or-None"):**
   - Either all operations of the transaction are properly reflected in the database, or none are.
   - If a failure happens before the transaction completes, partial modifications are rolled back.
   - **Enforced by:** The **Recovery System** (using undo log records).

2. **Consistency (Preservation of Invariants):**
   - Executing a transaction in isolation preserves database consistency.
   - The database moves from one valid state to another valid state, satisfying all integrity constraints.
   - In a fund transfer, the total balance sum must remain unchanged.
   - **Enforced by:** The **Application Programmer** (correct business logic) and DBMS **Integrity Constraints**.

3. **Isolation (Shielding Concurrent Access):**
   - Each transaction executes as if it were running alone without interference from other concurrent transactions.
   - Intermediate results remain hidden from other concurrent transactions until commit.
   - **Enforced by:** The **Concurrency-Control System** (using locking or timestamp protocols).

4. **Durability (Persistence):**
   - After a transaction completes successfully and commits, its updates persist in the database permanently.
   - The committed data survives subsequent system crashes or power outages.
   - **Enforced by:** The **Recovery System** (using redo logs and non-volatile stable storage).

*Short version for 2024 Q.6(c) (2 marks):*
- **Atomicity:** All operations complete or none do. The recovery system undoes partial writes.
- **Consistency:** Execution in isolation preserves database validity and invariants.
- **Isolation:** Intermediate updates remain hidden from concurrent transactions.
- **Durability:** Committed changes persist permanently on disk despite crashes.

A schedule $S$ is **conflict serializable** if it is conflict equivalent to some serial schedule. Two schedules are conflict equivalent if one can be transformed into the other by swapping non-conflicting adjacent instructions.

- **On item $B$:**
  - $T_1: \text{read}(B)$ precedes $T_2: \text{write}(B) \implies T_1 \to T_2$
  - $T_1: \text{write}(B)$ precedes $T_2: \text{read}(B) \implies T_1 \to T_2$
  - $T_1: \text{write}(B)$ precedes $T_2: \text{write}(B) \implies T_1 \to T_2$

Every conflict directs from $T_1$ to $T_2$. There is no instruction in $T_2$ executed before a conflicting instruction in $T_1$.

The precedence graph has one directed edge: $T_1 \to T_2$. It contains no cycles.

### Q.8(a) · 05 Marks · CLO1

*Topic: [[../Topicwise_answers_exam_style/T11_Concurrency_Control_Protocols.md#T11.4 · Deadlock: conditions, prevention vs detection, wait-for graph, victim selection|T11.4 · Deadlock: conditions, prevention vs detection, wait-for graph, victim selection]] · Section B* · CLO1

**Question.**
What is deadlock? Consider the following wait-for-graph:<br><br>![Wait-for-graph for Q.8(a)](diagrams/2021_p02_fig01.jpg)<br><br>Determine whether the schedule contains any deadlock or not.<br><br>*(Refer to the Wait-for-Graph Diagram and Detailed Text Representation below)*

**Answer.**

**Deadlock:**  
A deadlock is a state where each transaction in a set is waiting for a resource or data lock held by another transaction in that set. None of the transactions can continue execution.

**Analysis of the Wait-For Graph:**  
The given wait-for graph has:
- **Vertices (Transactions):** $V = \{T_1, T_2, T_3, T_4, T_5\}$
- **Directed Edges:** $E = \{(T_1, T_4), (T_1, T_2), (T_1, T_3), (T_4, T_5), (T_5, T_2), (T_2, T_4)\}$

A directed edge $T_i \to T_j$ means transaction $T_i$ is waiting for transaction $T_j$ to release a required lock.

**Cycle Detection:**  
We trace the directed edges among transactions $T_2, T_4,$ and $T_5$:

$$
T_4 \to T_5 \to T_2 \to T_4
$$

1. $T_4$ is waiting for $T_5$.
2. $T_5$ is waiting for $T_2$.
3. $T_2$ is waiting for $T_4$.

This forms a closed directed cycle.

**Verdict:**  
**Yes, the schedule contains a deadlock.**

**Transactions in Deadlock:**  
Transactions $\mathbf{T_2, T_4, \text{ and } T_5}$ are deadlocked. (Note: $T_1$ is waiting on $T_2, T_3, T_4$, but is not part of the cycle. $T_3$ has no outgoing edges and is not blocked).

**Breaking the Deadlock:**  
The DBMS must select one transaction in the cycle ($T_2, T_4$, or $T_5$) as a **victim** based on minimum abort cost, roll it back, and release its locks. This breaks the cycle and allows the remaining transactions to complete.

### Q.8(b) · 05 Marks · CLO4

*Topic: [[../Topicwise_answers_exam_style/T13_Security_Indexing_and_Hashing.md#T13.2 · SQL injection: how it works + prevention|T13.2 · SQL injection: how it works + prevention]] · Section B* · CLO4

**Question.**
What is SQL injection attack? Describe the precautions that should be taken to prevent this attack.

**Answer.**

**1. What is an SQL Injection Attack?**  
An **SQL injection attack** occurs when an attacker inputs malicious SQL commands into an application input field. The application concatenates this untrusted input directly into a dynamic SQL query string. The database parser interprets the malicious input as SQL instructions rather than data. This allows the attacker to bypass authentication, read unauthorized data, or modify and delete tables.

**2. How It Works**  
Consider an application that builds a query using string concatenation:

```python
# Vulnerable query construction
query = "SELECT * FROM instructor WHERE name = '" + user_input + "'"
```

- **Scenario 1: Authentication Bypass / Data Dumping**
  - **Attacker input:** `' OR '1'='1`
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = '' OR '1'='1';
    ```
  - **Mechanism:** The quote closes the name literal. The `'1'='1'` condition is always true. The database returns all records in the `instructor` table.

- **Scenario 2: Destructive Attack (Piggybacked Query)**
  - **Attacker input:** `'; DROP TABLE student; -- `
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = ''; DROP TABLE student; -- ';
    ```
  - **Mechanism:** The semicolon terminates the first query. The database engine executes the injected `DROP TABLE student` statement. The trailing `--` treats the remaining query syntax as a comment.

**3. Precautions to Prevent SQL Injection**  

1. **Use Prepared Statements (Parameterized Queries):**
   This is the primary defense. The application precompiles the SQL query structure with placeholders. User input is bound separately as data parameters. The parser never executes parameter content as SQL commands.
   ```python
   # Secure parameterized query
   cursor.execute("SELECT * FROM instructor WHERE name = %s", (user_input,))
   ```
   In Java/JDBC, use `PreparedStatement` with `?` markers and `setString()`.

2. **Input Validation and Whitelisting:**
   Validate data types, lengths, and patterns before passing them to queries. For dynamic query parts like table or column names that cannot use parameters, check input against an explicit whitelist of allowed identifiers.

3. **Enforce Least Privilege:**
   Configure database user accounts with minimal necessary privileges. A public web application account should only have `SELECT` or `INSERT` access. It must never have administrative permissions like `DROP TABLE` or `GRANT`.

4. **Use Parameterized Stored Procedures:**
   Wrap database operations inside stored procedures with typed parameters. Do not concatenate dynamic SQL inside the stored procedure body.

5. **Suppress Database Error Messages:**
   Hide internal database error details, table names, and stack traces from end users. Display generic error pages instead.

*Short version for 2020 Q.4(a) (4 marks):* Provide the definition, the `' OR '1'='1` exploit example, and the three core precautions: prepared statements, input validation, and least privilege.

*Topic: [[../Topicwise_answers_exam_style/T02_ER_and_EER_Modeling.md#T02.4 · Weak vs strong entity sets (discriminator, identifying relationship)|T02.4 · Weak vs strong entity sets (discriminator, identifying relationship)]] · Section B* · CLO1

**Question.**
Explain weak and strong entity set with appropriate example.

**Answer.**

**Entity Set:**  
An entity set is a collection of entities of the same type that share the same properties or attributes (e.g., the set of all students in a university).

| Feature | Strong Entity Set | Weak Entity Set |
| :--- | :--- | :--- |
| **Primary Key** | Has sufficient attributes to form its own primary key. | Lacks a primary key of its own. Uses a partial key (discriminator). |
| **Existence Dependency** | Independent. Does not depend on another entity set. | Existence-dependent on an identifying (strong) entity set. |
| **E-R Notation** | Single rectangle. | Double rectangle. |
| **Relationship Set** | Connected via regular relationship (single diamond). | Connected via identifying relationship (double diamond). |
| **Discriminator Key** | None (uses full primary key underlined with solid line). | Has a discriminator underlined with a dashed line. |
| **Composite PK** | Its own primary key. | Formed by (Owner Primary Key + Discriminator). |
| **Example** | `course` with primary key `course_id`. | `section` with discriminator `sec_id`, `semester`, `year`. |

![Weak entity set section connected to identifying strong entity set course via sec_course](../LectureSlides/diagrams/L05_p37_fig01.jpg)
*Figure: Expressing Weak Entity Sets in ER Diagram (Deck 05, Slide 37)*

- **Strong Entity Set Example:** `course` has attributes `course_id` (PK), `title`, `credits`. It exists independently.
- **Weak Entity Set Example:** `section` has attributes `sec_id`, `semester`, `year`. A section number like `Sec 1` is meaningless without knowing the course. Its full primary key is `(course_id, sec_id, semester, year)`.
