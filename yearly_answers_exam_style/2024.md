*Topic: [[Topicwise_answers_exam_style/T01_DB_Concepts_and_Architecture.md#T01.2 · File system vs DBMS|T01.2 · File system vs DBMS]] · Section A* · 1

**Question.**
A courier tracking company maintains large files for daily parcel updates. The data grows rapidly and requires fast retrieval. Choose between a file based system and a DBMS and justify the decision.

**Answer.**

**Decision:** Choose a **DBMS (Database Management System)**.

**Justification:**
1. **Rapid Data Growth and Scalability:** As parcel records grow rapidly each day, a DBMS manages storage dynamically with tables and secondary storage. A file system suffers from large unwieldy files, data isolation, and slow sequential processing.
2. **Fast Retrieval via Indexing:** Customers and couriers need instant tracking updates. A DBMS builds B+ tree indexes on tracking numbers (`parcel_id`). This delivers lookup results in milliseconds instead of scanning large files line by line.
3. **Concurrent Multi-User Updates:** Delivery drivers, sorting hubs, and recipients update and read parcel records at the same time. A DBMS provides concurrency control to prevent lost updates and race conditions. A file system would require file locking, which blocks other users.
4. **Data Integrity and Constraints:** A DBMS automatically enforces rules. For example, status codes must be valid, and tracking IDs cannot be null or duplicated. File systems require custom application code to check every update.
5. **Crash Recovery and Backup:** Courier data cannot be lost during system crashes or power failures. A DBMS maintains write-ahead logs (WAL) and automatic transaction rollback to preserve tracking history.

### Q.2(a) · 03 Marks · 2

*Topic: [[Topicwise_answers_exam_style/T07_Triggers_and_Stored_Procedures.md#T07.2 · Triggers for security before and after a breach|T07.2 · Triggers for security before and after a breach]] · Section A* · 2
*(Repeated question: Also asked in 2017 | Solved in T07)*

**Question.**
Discuss how trigger can contribute to the security of database before and after a security breach. Explain with example.

**Answer.**

Triggers protect database security at two stages: proactive prevention before a breach and forensic auditing after a breach.

#### 1. Before a Security Breach: Prevention via BEFORE Triggers

`BEFORE` triggers act as real-time security gatekeepers. They evaluate incoming data modifications before changes reach the database.

- **Security Role:** They validate user identity, verify business timing, and inspect the values being written. If a policy violation appears, the trigger halts the transaction using `SIGNAL SQLSTATE '45000'`.
- **Key Contributions:**
  - Blocks unauthorized operations outside working hours.
  - Prevents illegal privilege escalation or unauthorized salary updates.
  - Validates and sanitizes input data to stop malicious updates.

**Example (Blocking salary changes outside working hours):**

```sql
DELIMITER //

CREATE TRIGGER trg_prevent_unauthorized_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT = 'Security Alert: Salary edits outside office hours are blocked';
        END IF;
    END IF;
END //

DELIMITER ;
```

#### 2. After a Security Breach: Auditing and Forensics via AFTER Triggers

`AFTER` triggers execute immediately after a modification succeeds on a table.

- **Security Role:** If an attacker bypasses application checks, `AFTER` triggers write the unauthorized changes into an independent audit log table.
- **Key Contributions:**
  - Creates a tamper-evident audit trail capturing `USER()`, `NOW()`, the modified table, and both `OLD` and `NEW` column values.
  - Supplies forensic evidence to pinpoint how and when the attacker breached the system.
  - Helps administrators trace unauthorized modifications and restore corrupted data to its original state.

**Example (Logging security role modifications):**

```sql
DELIMITER //

CREATE TRIGGER trg_audit_role_change
AFTER UPDATE ON user_roles
FOR EACH ROW
BEGIN
    IF OLD.role <> NEW.role THEN
        INSERT INTO security_audit_log (
            user_id, old_role, new_role, changed_by, changed_at
        ) VALUES (
            OLD.user_id, OLD.role, NEW.role, USER(), NOW()
        );
    END IF;
END //

DELIMITER ;
```

*Short version for 2024 Q.2(a) (3 marks):* State how `BEFORE` triggers block unauthorized actions with `SIGNAL` and how `AFTER` triggers record tamper-evident audit logs with `USER()` and timestamps. Provide one concise trigger example.

### Q.2(c) · 03 Marks · 1

*Topic: [[Topicwise_answers_exam_style/T09_Transactions_ACID_and_Anomalies.md#T09.2 · Consistency property alone, with example|T09.2 · Consistency property alone, with example]] · Section A* · 1
*(Repeated question: Also asked in 2019 | Solved in T09)*

**Question.**
Explain the consistency property of a database system with a proper example.

**Answer.**

**Definition:**  
The **consistency** property requires that executing a transaction in isolation preserves the consistency of the database. If the database starts in a valid state that satisfies all integrity rules, it must end in a valid state after the transaction completes.

**Categories of Consistency Constraints:**
1. **Explicit Constraints:** Rules enforced automatically by the DBMS, including primary keys, foreign keys, data types, and `CHECK` constraints (such as `balance >= 0`).
2. **Implicit Invariants:** Business rules that cannot easily be expressed in DDL, such as preserving total assets across account transfers.

**Example (Bank Transfer):**  
Let account $A$ have \$1000 and account $B$ have \$2000. The consistency invariant requires total funds to remain constant:

$$
A + B = \$1000 + \$2000 = \$3000
$$

Transaction $T_1$ transfers \$50 from $A$ to $B$:
1. $\text{read}(A)$
2. $A := A - 50$
3. $\text{write}(A) \quad [A = \$950]$
4. $\text{read}(B)$
5. $B := B + 50$
6. $\text{write}(B) \quad [B = \$2050]$

- **Temporary Inconsistency During Execution:** After step 3, $A = \$950$ and $B = \$2000$. The sum is $\$950 + \$2000 = \$2950$. The database enters a temporarily inconsistent state.
- **Restored Consistency at End:** After step 6 completes, $A = \$950$ and $B = \$2050$. The sum is $\$950 + \$2050 = \$3000$. Database consistency is restored.
- **Responsibility:** Ensuring transaction logic is correct is primarily the responsibility of the **application programmer**.

### Q.3(a) · 04 Marks · 2

*Topic: [[Topicwise_answers_exam_style/T08_Normalization_and_Functional_Dependencies.md#T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF|T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF]] · Section A* · 2

**Question.**
A library database stores information about Books, Authors, Publishers and Borrowers. Create a table that contains some data redundancy and partial dependencies. Also, show the procedure to normalize the table.

**Answer.**

#### 1. Unnormalized / 1NF Table with Redundancy and Partial Dependencies

Consider a single table `LIBRARY_LOAN` designed to store all lending records:

| Book_ID | Borrower_ID | Title | Author_ID | Author_Name | Publisher_Name | Borrower_Name | Borrow_Date |
| :---: | :---: | :--- | :---: | :--- | :--- | :--- | :---: |
| B101 | U01 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Akib | 2024-01-10 |
| B101 | U02 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Shuvo | 2024-02-15 |
| B202 | U01 | Operating Systems | A1 | Silberschatz | Wiley | Akib | 2024-03-01 |

**Primary Key:** `(Book_ID, Borrower_ID)`

**Functional Dependencies:**
- `Book_ID -> Title, Author_ID, Publisher_Name` (partial dependency on subset `Book_ID`)
- `Author_ID -> Author_Name` (transitive dependency)
- `Borrower_ID -> Borrower_Name` (partial dependency on subset `Borrower_ID`)
- `(Book_ID, Borrower_ID) -> Borrow_Date` (full dependency)

**Data Redundancy:**
- Book title, author details, and publisher name are duplicated whenever the same book is loaned to another borrower.
- Borrower name is repeated whenever a user borrows multiple books.

---

#### 2. Procedure to Normalize the Table

##### Step 1: Eliminate Partial Dependencies (Convert to 2NF)
Decompose `LIBRARY_LOAN` so non-prime attributes depend only on the full primary key:

1. `BOOK_INFO(Book_ID, Title, Author_ID, Author_Name, Publisher_Name)` with PK `Book_ID`
2. `BORROWER(Borrower_ID, Borrower_Name)` with PK `Borrower_ID`
3. `LOAN(Book_ID, Borrower_ID, Borrow_Date)` with PK `(Book_ID, Borrower_ID)`

This eliminates partial dependencies and achieves 2NF.

##### Step 2: Eliminate Transitive Dependencies (Convert to 3NF)
In `BOOK_INFO`, the dependency `Author_ID -> Author_Name` is transitive because `Author_ID` is a non-prime attribute determining `Author_Name`.

We decompose `BOOK_INFO` into:
1. `BOOK(Book_ID, Title, Author_ID, Publisher_Name)` with PK `Book_ID` and FK `Author_ID`
2. `AUTHOR(Author_ID, Author_Name)` with PK `Author_ID`

#### Final Normalized 3NF Schema:
1. **BOOK** (`Book_ID`, `Title`, `Author_ID`, `Publisher_Name`)  
   PK: `Book_ID` | FK: `Author_ID` references `AUTHOR(Author_ID)`
2. **AUTHOR** (`Author_ID`, `Author_Name`)  
   PK: `Author_ID`
3. **BORROWER** (`Borrower_ID`, `Borrower_Name`)  
   PK: `Borrower_ID`
4. **LOAN** (`Book_ID`, `Borrower_ID`, `Borrow_Date`)  
   PK: `(Book_ID, Borrower_ID)` | FKs: `Book_ID` references `BOOK`, `Borrower_ID` references `BORROWER`

### Q.3(b) · 04 Marks · 1

*Topic: [[Topicwise_answers_exam_style/T12_Recovery_System_and_RAID.md#T12.1 · Failure classification, precautions, recovery methods|T12.1 · Failure classification, precautions, recovery methods]] · Section A* · 1
*(Repeated question: Also asked in 2019 | Solved in T12)*

**Question.**
Discuss the ways of DBMS can be failed. Also, mention the precautions should be taken considering the failure of DBMS and point out the recovery methods.

**Answer.**

#### 1. Ways a DBMS Can Fail
A DBMS can fail in three primary ways:
- **Transaction Failure:** Caused by logical errors (overflow, invalid input) or system errors (deadlock aborts).
- **System Crash:** Loss of volatile main memory from power loss, CPU faults, or operating system crashes.
- **Disk Failure:** Loss of non-volatile disk storage caused by head crashes or bad sectors.
- *(Site / Disaster Failure):* Physical destruction of an entire data center caused by fire, flood, or earthquake.

#### 2. Precautions Against DBMS Failures
- **Write-Ahead Logging (WAL):** Force log records to stable storage before writing modified data pages to disk.
- **Uninterruptible Power Supply (UPS) & NVRAM:** Use battery-backed caches to prevent incomplete writes during sudden power loss.
- **Disk Redundancy (RAID):** Use mirroring (RAID 1) or parity (RAID 5/6) to survive single or double disk failures.
- **Archival Off-Site Backups:** Periodically copy full database dumps and log files to remote tape or cloud storage.

#### 3. Recovery Methods
- **Log-Based Recovery:**
  - *Undo:* Reverses uncommitted updates using old values from the log.
  - *Redo:* Re-applies committed updates using new values from the log.
- **Checkpoints:** Periodically flushes dirty buffer blocks and logs active transactions, bounding the restart log scan.
- **Shadow Paging:** Writes updates to a separate page copy and switches pointers atomically, avoiding undo/redo logs.
- **Archival Restore and Roll-Forward:** Restores the last offline backup and replays subsequent archived log records.

### Q.3(c) · 02 Marks · 1

*Topic: [[Topicwise_answers_exam_style/T06_Joins_and_Views.md#T06.1 · Types of joins|T06.1 · Types of joins]] · Section A* · 1

**Question.**
Differentiate between inner joining and outer joining.

**Answer.**

| Feature | Inner Join | Outer Join |
| :--- | :--- | :--- |
| **Tuple Retention** | Keeps only matching tuples from both relations. Drops non-matching rows. | Preserves matching rows plus unmatched rows from one or both relations. |
| **Missing Values** | Never produces `NULL` values to represent missing relationship data. | Pads missing attributes of unmatched tuples with `NULL`. |
| **Information Loss** | Loses dangling records that fail the join predicate. | Prevents information loss by keeping all records from preserved relations. |
| **Forms / Syntax** | Theta join, equijoin, and natural join (`INNER JOIN`, `JOIN`). | Left outer, right outer, and full outer join (`LEFT JOIN`, `RIGHT JOIN`, `FULL JOIN`). |

The common attribute between Courses and Teacher is `t_code`.

#### i) Natural Join
Matches tuples with equal `t_code` values and retains one copy of `t_code`.

Relational algebra:
$$
\text{Courses} \bowtie \text{Teacher}
$$

MySQL query:
```sql
SELECT Code, Series, t_code, Designation
```

**Outcome Table (4 rows):**

---

#### ii) Left Outer Join
Preserves all tuples from the left relation (**Courses**). Unmatched right-side fields are set to `NULL`.

Relational algebra:
$$
\text{Courses} \mathbin{⟕} \text{Teacher}
$$

MySQL query:
```sql
SELECT Courses.Code, Courses.Series, Courses.t_code, Teacher.Designation
```

---

Preserves all tuples from the right relation (**Teacher**). Unmatched left-side fields are filled with `NULL`.

Relational algebra:
$$
\text{Courses} \mathbin{⟖} \text{Teacher}
$$

MySQL query:
```sql
SELECT Courses.Code, Courses.Series, Teacher.t_code, Teacher.Designation
FROM Courses
RIGHT JOIN Teacher ON Courses.t_code = Teacher.t_code;
```

**Outcome Table (5 rows):**

| Code | Series | t_code | Designation |
| :--- | :--- | :--- | :--- |
| E_2215 | 2020 | T1 | Head |

*Explanation:* Teacher T4 has no matching course row. T4 appears with `NULL` for `Code` and `Series`.

---

Retains all records from both relations. Non-matching fields are filled with `NULL`.

Relational algebra:
$$
\text{Courses} \mathbin{⟗} \text{Teacher}
$$

```sql
SELECT Courses.Code, Courses.Series, Courses.t_code, Teacher.Designation
FROM Courses
LEFT JOIN Teacher ON Courses.t_code = Teacher.t_code
UNION
SELECT Courses.Code, Courses.Series, Teacher.t_code, Teacher.Designation
FROM Courses
RIGHT JOIN Teacher ON Courses.t_code = Teacher.t_code;
```

**Outcome Table (5 rows):**

| Code | Series | t_code | Designation |
| :--- | :--- | :--- | :--- |
| E_2215 | 2020 | T1 | Head |
| E_4127 | 2021 | T2 | AP |
| E_1203 | 2022 | T3 | AP |
| E_2219 | 2021 | T3 | AP |
| `NULL` | `NULL` | T4 | Lecturer |

*Explanation:* All courses find a teacher match. The unmatched teacher T4 is preserved with `NULL` for `Code` and `Series`.

### Q.5(a) · 04 Marks · 2

*Topic: [[Topicwise_answers_exam_style/T04_Relational_Algebra_and_Calculus.md#T04.2 · Write RA queries on a given schema|T04.2 · Write RA queries on a given schema]] · Section B* · 2

**Question.**
Consider the following relation database:<br>Patient (Patient_ID, Patient_Name, Mobile)<br>History (Patient_ID, Symptom, Date)<br>Report (Patient_ID, Corona_center, Test_result)<br>Now, write down the relational algebra (Not SQL) to find out the following queris:<br>i) Find the names of those patients who have fever symptom<br>ii) Find out the mobile numbers of those patients who have provided samples in Rangpur corona center and their results have become positive.<br>*(Note: "relation database" and "queris" printed verbatim in original paper; refers to relational database and queries)*

**Answer.**

*Assumption: In relation `Report`, `Parient_ID` is a typographical misprint for `Patient_ID`.*

**(i) Names of patients who have fever symptom:**

Join patients with their history records filtered for fever, then project the patient names:

$$
\boxed{\Pi_{\text{Patient\_name}}(\text{Patient} \bowtie \sigma_{\text{Symptom} = \text{"fever"}}(\text{History}))}
$$

**(ii) Maximum number of suspected patients (high-fever symptom) on a date:**

Filter records for "high-fever", count patients per date, and take the maximum:

$$
T_1 \leftarrow \sigma_{\text{Symptom} = \text{"high-fever"}}(\text{History})

### Q.6(a) · 04 Marks · 2

*Topic: [[Topicwise_answers_exam_style/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.6 · Subqueries theory ("two examples"): IN, SOME/ALL, EXISTS, scalar, correlated, WITH|T05.6 · Subqueries theory ("two examples"): IN, SOME/ALL, EXISTS, scalar, correlated, WITH]] · Section B* · 2

**Question.**
Explain sub-queries with two suitable examples.

**Answer.**

**Explanation:** A **subquery** (or nested query) is a `SELECT` statement embedded inside another SQL statement (the outer query). It can appear in the `WHERE` clause to filter tuples, in the `FROM` clause as a temporary derived relation, or in the `SELECT` clause as a scalar expression. Subqueries allow multi-step data retrieval in a single query.

**Example 1: Set Membership Subquery (`IN`)**  
Find all courses offered in Fall 2017 that were also offered in Spring 2018:

```sql
SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2017
  AND course_id IN (
      SELECT course_id
      FROM section
      WHERE semester = 'Spring' AND year = 2018
  );
```

The inner subquery generates the set of courses running in Spring 2018. The outer query checks whether Fall 2017 courses belong to that generated set.

**Example 2: Scalar Comparison Subquery (`AVG`)**  
Find instructors whose salary is higher than the average salary of all instructors:

```sql
SELECT name, salary
FROM instructor
WHERE salary > (
    SELECT AVG(salary)
    FROM instructor
);
```

The inner query computes a single numeric value (the overall average salary). The outer query evaluates the `>` predicate against this scalar value for each instructor.

### Q.6(b) · 04 Marks · 3

*Topic: [[Topicwise_answers_exam_style/T07_Triggers_and_Stored_Procedures.md#T07.3 · Implement a trigger or stored procedure|T07.3 · Implement a trigger or stored procedure]] · Section B* · 3

**Question.**
An e-commerce system wants to automate actions when a new order is inserted such as updating stock and sending email. Implement a database trigger that handles this workflow.

**Answer.**

*Assumption: The tables are `orders(order_id, product_id, quantity, customer_email)`, `products(product_id, stock)`, and `email_queue(queue_id, recipient, subject, body, queued_at)`.*

A trigger runs inside the database engine and cannot send external emails directly.
Instead, the trigger updates product stock and inserts a row into an `email_queue` table. An external mailer application reads this queue and sends the email.

```sql
DELIMITER //

CREATE TRIGGER trg_after_order_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    -- 1. Deduct ordered quantity from product stock
    UPDATE products
    SET stock = stock - NEW.quantity
    WHERE product_id = NEW.product_id;

    -- 2. Enqueue email notification for external mailer service
    INSERT INTO email_queue (recipient, subject, body, queued_at)
    VALUES (
        NEW.customer_email,
        'Order Confirmation',
        CONCAT('Your order #', NEW.order_id, ' for product #', NEW.product_id, ' (Qty: ', NEW.quantity, ') has been placed successfully.'),
        NOW()
    );
END //

DELIMITER ;
```

### Q.6(c) · 02 Marks · 3

*Topic: [[Topicwise_answers_exam_style/T09_Transactions_ACID_and_Anomalies.md#T09.1 · ACID properties|T09.1 · ACID properties]] · Section B* · 3
*(Repeated question: Also asked in 2017 | Solved in T09)*

**Question.**
Briefly discuss the ACID properties of transaction.

**Answer.**

A **transaction** is a logical unit of program execution that accesses and updates data items. To preserve data integrity during crashes and concurrent access, the DBMS must ensure the four **ACID** properties:

1. **Atomicity ("All-or-None"):**
   - Either all operations of the transaction are properly reflected in the database, or none are.
   - If a failure happens before the transaction completes, partial modifications are rolled back.
   - **Enforced by:** The **Recovery System** (using undo log records).

2. **Consistency (Preservation of Invariants):**
   - Executing a transaction in isolation preserves database consistency.
   - The database moves from one valid state to another valid state, satisfying all integrity constraints.
   - In a fund transfer, the total balance sum must remain unchanged.
   - **Enforced by:** The **Application Programmer** (correct business logic) and DBMS **Integrity Constraints**.

3. **Isolation (Shielding Concurrent Access):**
   - Each transaction executes as if it were running alone without interference from other concurrent transactions.
   - Intermediate results remain hidden from other concurrent transactions until commit.
   - **Enforced by:** The **Concurrency-Control System** (using locking or timestamp protocols).

4. **Durability (Persistence):**
   - After a transaction completes successfully and commits, its updates persist in the database permanently.
   - The committed data survives subsequent system crashes or power outages.
   - **Enforced by:** The **Recovery System** (using redo logs and non-volatile stable storage).

*Short version for 2024 Q.6(c) (2 marks):*
- **Atomicity:** All operations complete or none do. The recovery system undoes partial writes.
- **Consistency:** Execution in isolation preserves database validity and invariants.
- **Isolation:** Intermediate updates remain hidden from concurrent transactions.
- **Durability:** Committed changes persist permanently on disk despite crashes.

**Question.**
Write short note on the following statements –<br>i) ON CASCADE DELETE<br>ii) Group By<br>iii) Order By<br>iv) As

**Answer.**

**i) ON DELETE CASCADE (printed as "ON CASCADE DELETE"):**  
A foreign key referential integrity action. When a tuple in the parent table is deleted, the DBMS automatically deletes all corresponding referencing tuples in the child table. This maintains referential integrity and prevents orphaned records.

```sql
CREATE TABLE section (
    course_id VARCHAR(8),
    sec_id VARCHAR(8),
    semester VARCHAR(6),
    year NUMERIC(4, 0),
    PRIMARY KEY (course_id, sec_id, semester, year),
    FOREIGN KEY (course_id) REFERENCES course(course_id)
        ON DELETE CASCADE
);
```

**ii) GROUP BY:**  
An SQL clause used to partition table rows into distinct groups having identical values in specified columns. Aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) then compute summary statistics for each individual group.

```sql
SELECT dept_name, AVG(salary) AS avg_sal
FROM instructor
GROUP BY dept_name;
```

**iii) ORDER BY:**  
An SQL clause that sorts query result rows in ascending (`ASC`, default) or descending (`DESC`) order based on one or more attributes. Multiple sort keys break ties sequentially.

```sql
SELECT name, salary
FROM instructor
ORDER BY salary DESC, name ASC;
```

**iv) AS:**  
An SQL keyword used to define an alias (an alternative temporary name). It can rename an attribute or computed expression in the `SELECT` clause for readability, or rename a table in the `FROM` clause to shorten table references and enable self-joins.

```sql
SELECT salary * 1.15 AS revised_salary
FROM employee AS e;
```

### Q.7(c) · 03 Marks · 3

*Topic: [[Topicwise_answers_exam_style/T12_Recovery_System_and_RAID.md#T12.4 · RAID levels, comparison, and recovery role|T12.4 · RAID levels, comparison, and recovery role]] · Section B* · 3

**Question.**
A multimedia archive contains very large image and video files. RAID is recommended for storage. Compare different RAID levels.

**Answer.**

#### Workload Characteristics
Multimedia archives store multi-gigabyte image and video files. The workload consists of high-throughput sequential reads (streaming, downloading), rare updates (write-once, read-many), and very high total capacity demands.

#### Comparison of RAID Levels

| RAID Level | Striping Unit | Redundancy Mechanism | Fault Tolerance | Usable Storage Capacity | Read Speed (Large Files) | Write Speed |
| :--- | :--- | :--- | :---: | :---: | :---: | :--- |
| **RAID 0** | Block | None | 0 disks | 100% | Very Fast | Very Fast |
| **RAID 1** | Block / Drive | Mirroring (copy) | 1 disk per pair | 50% | Fast | Moderate |
| **RAID 5** | Block | Distributed Parity | 1 disk | $\frac{N-1}{N}$ (High) | Very Fast | Fast for sequential |
| **RAID 6** | Block | Distributed P + Q | 2 disks | $\frac{N-2}{N}$ (High) | Very Fast | Moderate |
| **RAID 1+0** | Block | Mirroring + Striping | 1 disk per pair | 50% | Very Fast | Very Fast |

#### Recommendation and Justification
- **Recommended Level:** **RAID 6** (or **RAID 5** for smaller arrays).
- **Justification:** Multimedia archives require high storage efficiency and sequential read throughput, making parity schemes far more economical than mirroring (which wastes 50% capacity). Because archives use massive multi-terabyte drives, rebuild times can take days; RAID 6 tolerates a second drive failure during rebuild, protecting against catastrophic data loss.

### Q.8(a) · 03 Marks · 3

*Topic: [[Topicwise_answers_exam_style/T09_Transactions_ACID_and_Anomalies.md#T09.5 · Concurrency problems|T09.5 · Concurrency problems]] · Section B* · 3
*(Repeated question: Also asked in 2019 | Solved in T09)*

**Question.**
If concurrency-control management is not implemented properly what problem may occur? Explain with example.

**Answer.**

**Definition:**  
The **consistency** property requires that executing a transaction in isolation preserves the consistency of the database. If the database starts in a valid state that satisfies all integrity rules, it must end in a valid state after the transaction completes.

**Categories of Consistency Constraints:**
1. **Explicit Constraints:** Rules enforced automatically by the DBMS, including primary keys, foreign keys, data types, and `CHECK` constraints (such as `balance >= 0`).
2. **Implicit Invariants:** Business rules that cannot easily be expressed in DDL, such as preserving total assets across account transfers.

**Example (Bank Transfer):**  
Let account $A$ have \$1000 and account $B$ have \$2000. The consistency invariant requires total funds to remain constant:

$$
A + B = \$1000 + \$2000 = \$3000
$$

Transaction $T_1$ transfers \$50 from $A$ to $B$:
1. $\text{read}(A)$
2. $A := A - 50$
3. $\text{write}(A) \quad [A = \$950]$
4. $\text{read}(B)$
5. $B := B + 50$
6. $\text{write}(B) \quad [B = \$2050]$

- **Temporary Inconsistency During Execution:** After step 3, $A = \$950$ and $B = \$2000$. The sum is $\$950 + \$2000 = \$2950$. The database enters a temporarily inconsistent state.
- **Restored Consistency at End:** After step 6 completes, $A = \$950$ and $B = \$2050$. The sum is $\$950 + \$2050 = \$3000$. Database consistency is restored.
- **Responsibility:** Ensuring transaction logic is correct is primarily the responsibility of the **application programmer**.

### Q.8(b) · 03 Marks · 3

*Topic: [[Topicwise_answers_exam_style/T11_Concurrency_Control_Protocols.md#T11.6 · Timestamp ordering: R-TS/W-TS rules, trace a schedule; rolled-back transaction gets a NEW timestamp|T11.6 · Timestamp ordering: R-TS/W-TS rules, trace a schedule; rolled-back transaction gets a NEW timestamp]] · Section B* · 3
*(Repeated question: Also asked in 2018 | Solved in T11)*

**Question.**
When a transaction is rolled back under timestamp ordering and it is assigned a new timestamp? Why can it not simply keep its old timestamp?

**Answer.**

**When a Transaction is Rolled Back Under Timestamp Ordering:**  
Under the Timestamp Ordering (TSO) protocol, a transaction $T_i$ is rolled back whenever it attempts an operation that conflicts with a younger transaction:

1. **On Read:** $T_i$ issues $\text{read}(Q)$, but $\text{TS}(T_i) < \text{W-timestamp}(Q)$.  
   $T_i$ is attempting to read an older value of $Q$ that has already been overwritten by a younger transaction. The read is rejected and $T_i$ is rolled back.
2. **On Write:**
   - $T_i$ issues $\text{write}(Q)$, but $\text{TS}(T_i) < \text{R-timestamp}(Q)$.  
     The value of $Q$ that $T_i$ is producing was needed previously by a younger transaction, which already read an older value. The write is rejected and $T_i$ is rolled back.
   - $T_i$ issues $\text{write}(Q)$, but $\text{TS}(T_i) < \text{W-timestamp}(Q)$.  
     $T_i$ is attempting to overwrite $Q$ with an obsolete value after a younger transaction has already written it. The write is rejected and $T_i$ is rolled back.

**Assigning a New Timestamp:**  
When $T_i$ is rolled back, the system aborts it and restarts it. Upon restarting, the system assigns $T_i$ a **new, larger timestamp** using the current system clock or logical counter.

**Why It Cannot Keep Its Old Timestamp:**

1. **Avoids Immediate Re-abort:**  
   If $T_i$ kept its old timestamp, $\text{TS}(T_i)$ would remain smaller than the $\text{R-timestamp}$ or $\text{W-timestamp}$ values already written by the younger transactions. On restarting, when $T_i$ reaches the same step, the exact same timestamp check would fail again.
2. **Prevents Starvation (Livelock):**  
   Keeping the old timestamp traps the transaction in an endless abort and restart loop. It would never finish. A new timestamp breaks this cycle.
3. **Correct Serial Order:**  
   A new timestamp assigns the transaction a fresh position in the logical serialization order, placing it after the conflicting transactions and allowing its operations to execute successfully.

*Short version for 2024 Q.8(b) (3 marks):* Give the read and write rollback conditions concisely. Then explain in 2 points why the old timestamp causes repeated aborts and starvation.

**Answer.**

We extract the sequence of database read and write instructions:
1. $T_1: \text{read}(A)$
2. $T_2: \text{read}(A)$
3. $T_2: \text{write}(A)$
4. $T_2: \text{read}(B)$
5. $T_1: \text{write}(A)$
6. $T_1: \text{read}(B)$
7. $T_1: \text{write}(B)$
8. $T_2: \text{write}(B)$

#### Conflict Analysis

- **On item $A$:**
  - $T_1: \text{read}(A)$ occurs before $T_2: \text{write}(A) \implies T_1 \to T_2$
  - $T_2: \text{read}(A)$ occurs before $T_1: \text{write}(A) \implies T_2 \to T_1$
  - $T_2: \text{write}(A)$ occurs before $T_1: \text{write}(A) \implies T_2 \to T_1$
- **On item $B$:**
  - $T_2: \text{read}(B)$ occurs before $T_1: \text{write}(B) \implies T_2 \to T_1$
  - $T_1: \text{read}(B)$ occurs before $T_2: \text{write}(B) \implies T_1 \to T_2$
