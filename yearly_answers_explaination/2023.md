**Question.**
Draw an ER diagram for RUET Central Library Management System. You have to consider the entities mentioned below:<br>(i) Books (ii) Members (iii) Staff (iv) Borrowing (v) Reservations

**Answer.**

**What the examiner wants.**  
An E-R diagram featuring the exact 5 entity sets specified in the question: Books, Members, Staff, Borrowing, and Reservations (5 marks). All entities must have attributes and primary keys, connected with meaningful relationships and cardinalities.

**Key idea.**  
Borrowing and Reservations are often modeled as relationships in simpler designs. But the prompt explicitly requires them as entities. So we model both as independent entity sets with their own unique IDs and transaction dates.

**Step-by-step solution.**  
*Design Note: Borrowing and Reservations are explicitly specified as entity sets in the prompt; each is modeled with its own unique identifier and transaction attributes.*

**Entity Sets & Attributes:**
1. **BOOKS:** `book_id` (PK), `isbn`, `title`, `author`, `edition`.

3. **STAFF:** `staff_id` (PK), `name`, `designation`.
4. **BORROWING:** `borrow_id` (PK), `borrow_date`, `due_date`, `return_date`.
5. **RESERVATIONS:** `res_id` (PK), `res_date`, `status`.

**Relationships:**
- `Issues` (1:N): A staff member processes multiple borrowings.
- `Borrows` (1:N): A member initiates multiple borrowings.
- `Includes` (N:1): A borrowing record links to the specific book borrowed.
- `Reserves` (1:N): A member makes multiple book reservations.
- `For_Book` (N:1): A reservation is placed for a specific book.

### Q.1(b) · 03 Marks · CLO1

*Topic: [[Topicwise_answers_explaination/T01_DB_Concepts_and_Architecture.md#T01.2 · File system vs DBMS|T01.2 · File system vs DBMS]] · Section A* · CLO1
*(Repeated question: Also asked in 2019 | Solved in T01)*

**Question.**
What are the advantages of DBMS over file processing system?

**Answer.**

**What the examiner wants.**  
A brief statement on why a DBMS is important (~1 mark) and a structured list of at least 4 to 5 key advantages over file systems (~2 marks).

**Key idea.**  
A DBMS provides a central, reliable layer between applications and physical storage. Its advantages directly fix the classic drawbacks of file processing systems: duplicate data, lack of ad-hoc access, and crash vulnerability.

**Step-by-step solution.**  
**Importance of DBMS:**  
A DBMS provides centralized, secure, and coordinated control over an organization's data. It replaces scattered operating system files and ensures that data remains reliable, shared, and recoverable during hardware or software crashes.

**Advantages of DBMS over File Processing Systems:**
1. **Control of Data Redundancy and Inconsistency:** Centralized data storage minimizes duplicate entries and prevents conflicting records.
2. **Data Independence:** Physical storage structures can change without requiring updates to application programs.
3. **Fast and Convenient Data Access:** Declarative query languages (like SQL) retrieve data without custom low-level programming.
4. **Transaction Management (ACID Properties):** Guarantees atomicity during crashes and protects data integrity during concurrent multi-user access.
5. **Data Security and Integrity Constraints:** Restricts unauthorized access through user privileges and enforces business rules automatically.

*Variant for 2023 Q.1(b) (3 marks):* Focus directly on the 5 advantages over file processing systems; omit the general importance statement.

**Check.**  
*Quick self-test:*
- Q: What does data independence mean in practice?  
  A: You can change disk storage layouts or indexes without rewriting application queries.
- Q: Why is atomicity a major advantage of DBMS?  
  A: It guarantees that fund transfers or updates complete fully or roll back completely during a crash.

> [!warning] Common mistakes
> - Listing fewer than 4 points for a 3-mark question.
> - Confusing software features with business benefits without naming technical mechanisms.

**Exam tip.**  
List 5 numbered advantages with bold titles. This guarantees full marks even if an examiner deducts for a brief point.

### Q.1(c) · 02 Marks · CLO1

*Topic: [[Topicwise_answers_explaination/T01_DB_Concepts_and_Architecture.md#T01.5 · DDL vs DML|T01.5 · DDL vs DML]] · Section A* · CLO1

**Question.**
Explain DDL and DML with example.

**Answer.**

**What the examiner wants.**  
A concise definition and a valid SQL example for DDL (1 mark), and a concise definition and a valid SQL example for DML (1 mark).

**Key idea.**  
DDL sets up the schema and tables. DML queries and manipulates the records stored within those tables.

**Step-by-step solution.**  
- **DDL (Data Definition Language):** A specialized set of commands used to define, alter, and delete the database schema and storage structures.
  Example:
  ```sql
  CREATE TABLE instructor (
      ID CHAR(5),
      name VARCHAR(20),
      dept_name VARCHAR(20),
      salary NUMERIC(8,2)
  );
  ```
- **DML (Data Manipulation Language):** A language used to query, insert, update, or delete data stored in the database.
  Example:
  ```sql
  SELECT name FROM instructor WHERE dept_name = 'Comp. Sci.';
  ```

**Check.**  
*Classification check:*
- `DROP TABLE student;` $\rightarrow$ DDL (modifies schema).
- `INSERT INTO instructor VALUES ('10101', 'Srinivasan', 'Comp. Sci.', 65000);` $\rightarrow$ DML (modifies data).

> [!warning] Common mistakes
> - Forgetting to include concrete SQL code examples.
> - Mistaking `SELECT` for DDL. `SELECT` is declarative DML (query language).

**Exam tip.**  
Keep the explanation to 1 sentence per term, followed immediately by a clean 4-line SQL statement.

### Q.2(a) · 06 Marks · CLO4

*Topic: [[Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF|T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF]] · Section A* · CLO4

**Question.**
Consider a university tracking students, their courses and exam scores. A sample table is given below. Step by step convert this to 3NF.<br><br><table border="1" style="border-collapse: collapse; text-align: center;"><thead><tr><th style="padding: 4px 10px;">S_ID</th><th style="padding: 4px 10px;">S-Name</th><th style="padding: 4px 10px;">Courses</th><th style="padding: 4px 10px;">Instructors</th><th style="padding: 4px 10px;">Grades</th></tr></thead><tbody><tr><td style="padding: 4px 10px;">1</td><td style="padding: 4px 10px;">Alice</td><td style="padding: 4px 10px;">Math, Physics</td><td style="padding: 4px 10px;">Dr. Smith, Dr. Brown</td><td style="padding: 4px 10px;">A, B+</td></tr><tr><td style="padding: 4px 10px;">2</td><td style="padding: 4px 10px;">Bob</td><td style="padding: 4px 10px;">Chemistry</td><td style="padding: 4px 10px;">Dr. White</td><td style="padding: 4px 10px;">A-</td></tr><tr><td style="padding: 4px 10px;">3</td><td style="padding: 4px 10px;">Charlie</td><td style="padding: 4px 10px;">Math, Biology, Chemistry</td><td style="padding: 4px 10px;">Dr. Smith, Dr. Gray, Dr. White</td><td style="padding: 4px 10px;">B+, A-, A</td></tr></tbody></table>

**Answer.**

**What the examiner wants.**  
Step-by-step conversion starting from unnormalized table to 1NF (atomic rows, 2 marks), then to 2NF eliminating partial dependencies (2 marks), and checking/verifying 3NF (2 marks).

**Key idea.**  
Flatten the comma-separated lists to get 1NF. Notice that student names depend on student ID, and instructor depends on course. These are partial dependencies on the composite key `(S_ID, Course)`. Splitting into `STUDENT`, `COURSE`, and `ENROLLMENT` achieves 2NF. Since there are no further transitive dependencies, the tables are also in 3NF.

**Step-by-step solution.**

#### Step 1: Convert to First Normal Form (1NF)

The sample table violates 1NF because the attributes `Courses`, `Instructors`, and `Grades` contain multi-valued entries.

To achieve 1NF, we flatten each multi-valued row into individual atomic records:

| S_ID | S-Name | Course | Instructor | Grade |
| :---: | :--- | :--- | :--- | :---: |
| 1 | Alice | Math | Dr. Smith | A |
| 1 | Alice | Physics | Dr. Brown | B+ |
| 2 | Bob | Chemistry | Dr. White | A- |
| 3 | Charlie | Math | Dr. Smith | B+ |
| 3 | Charlie | Biology | Dr. Gray | A- |
| 3 | Charlie | Chemistry | Dr. White | A |

**Primary Key for 1NF:** `(S_ID, Course)`

#### Functional Dependencies Identified:
1. `S_ID -> S-Name` (partial dependency on `S_ID`)
2. `Course -> Instructor` (partial dependency on `Course`)
3. `(S_ID, Course) -> Grade` (full dependency on the composite key)

---

#### Step 2: Convert to Second Normal Form (2NF)

In 1NF, `S-Name` and `Instructor` depend on parts of the composite primary key `(S_ID, Course)`.

To eliminate these partial dependencies, we decompose the table into three relations:

1. **STUDENT**

   | S_ID | S-Name |
   | :---: | :--- |
   | 1 | Alice |
   | 2 | Bob |
   | 3 | Charlie |

   PK: `S_ID`

2. **COURSE**

   | Course | Instructor |
   | :--- | :--- |
   | Math | Dr. Smith |
   | Physics | Dr. Brown |
   | Chemistry | Dr. White |
   | Biology | Dr. Gray |

   PK: `Course`

3. **ENROLLMENT**

   | S_ID | Course | Grade |
   | :---: | :--- | :---: |
   | 1 | Math | A |
   | 1 | Physics | B+ |
   | 2 | Chemistry | A- |
   | 3 | Math | B+ |
   | 3 | Biology | A- |
   | 3 | Chemistry | A |

   PK: `(S_ID, Course)`

All non-prime attributes in these three relations depend fully on their entire candidate keys. Thus, the schema is in 2NF.

---

#### Step 3: Check for Third Normal Form (3NF)

A relation in 2NF is in 3NF if no non-prime attribute transitively depends on a candidate key.

- In `STUDENT(S_ID, S-Name)`, `S_ID` is the candidate key and determines `S-Name`. No transitive dependency exists.
- In `COURSE(Course, Instructor)`, `Course` is the candidate key and determines `Instructor`. No transitive dependency exists.
- In `ENROLLMENT(S_ID, Course, Grade)`, `(S_ID, Course)` is the candidate key and determines `Grade`. No transitive dependency exists.

Since there are no transitive dependencies, the 2NF schema is already in **3NF**.

$$
\boxed{\text{Final 3NF Schema: } \text{STUDENT}(\underline{\text{S\_ID}}, \text{S-Name}), \; \text{COURSE}(\underline{\text{Course}}, \text{Instructor}), \; \text{ENROLLMENT}(\underline{\text{S\_ID}, \text{Course}}, \text{Grade})}
$$

**Check.**  
*Reconstruction check:*
- Query: What did Alice score in Math, and who taught it?  
  Join `STUDENT` on `S_ID = 1`, `ENROLLMENT` on `Course = 'Math'`, and `COURSE` on `Course = 'Math'`. Result: Alice, Math, Dr. Smith, Grade A. Perfectly matches row 1 of the initial table.

> [!warning] Common mistakes
> - Splitting the data incorrectly by pairing the wrong instructor with the wrong course. Follow the exact order in the comma-separated strings!
> - Overcomplicating Step 3: if a relation in 2NF has no transitive dependencies, clearly state that it already satisfies 3NF.

**Exam tip.**  
Underline the primary keys in your final relations to make them stand out clearly.

### Q.2(b) · 04 Marks · CLO4

*Topic: [[Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.1 · Why normalize: redundancy and insert/update/delete anomalies|T08.1 · Why normalize: redundancy and insert/update/delete anomalies]] · Section A* · CLO4

**Question.**
What are the anomalies that normalization aims to eliminate? Provide examples of insertion, deletion and update anomalies.

**Answer.**

**What the examiner wants.**  
Naming the three anomalies (1 mark), followed by clear definitions and concrete examples for each using an employee/department or student/course table (3 marks).

**Key idea.**  
When independent facts share a table, they cannot be modified independently. An insertion requires dummy data, a deletion erases unintended facts, and an update requires touchpoints across many records.

**Step-by-step solution.**

Normalization aims to eliminate three modification anomalies caused by data redundancy and undesirable functional dependencies:

1. **Insertion Anomaly**
2. **Deletion Anomaly**
3. **Update Anomaly**

#### Example Table: `EMP_DEPT`

Consider an unnormalized table where employee and department facts share one relation:

| Emp_ID | Emp_Name | Dept_ID | Dept_Name | Location |
| :--- | :--- | :--- | :--- | :--- |
| E01 | Alice | D10 | IT | Building A |
| E02 | Bob | D20 | HR | Building B |
| E03 | Charlie | D10 | IT | Building A |

**Primary Key:** `Emp_ID`

#### 1. Insertion Anomaly
- **Problem:** We cannot insert information about a new department unless at least one employee is assigned to it.
- **Example:** The company opens a new department `D30` (Finance, Building C). Because `Emp_ID` is the primary key, it cannot be `NULL`. We cannot record department `D30` until an employee is hired.

#### 2. Deletion Anomaly
- **Problem:** Deleting an entity record accidentally deletes an unrelated entity.
- **Example:** Employee `E02` is the only person working in department `D20` (HR). If Bob resigns and we delete his row (`E02`), the fact that department `D20` is HR located in Building B is permanently erased.

#### 3. Update Anomaly
- **Problem:** Changing a single real-world fact requires modifying multiple records.
- **Example:** If the IT department (`D10`) moves to "Building D", we must update both rows E01 and E03. If the system updates E01 but fails on E03, department D10 has two conflicting locations.

**Check.**  
*Quick self-test:*
- Q: Which DBMS rule prevents inserting a department with a null `Emp_ID`?  
  A: The Entity Integrity constraint.
- Q: What is the solution to these anomalies?  
  A: Decompose `EMP_DEPT` into `EMPLOYEE(Emp_ID, Emp_Name, Dept_ID)` and `DEPARTMENT(Dept_ID, Dept_Name, Location)`.

> [!warning] Common mistakes
> - Writing abstract definitions without providing the required examples.
> - Creating three separate unrelated examples when a single small table can illustrate all three anomalies cleanly.

**Exam tip.**  
Stick to the standard `EMP_DEPT` or `STUDENT_COURSE` table. It keeps your answer compact and lets you show all three anomalies on the same data.

### Q.3(a) · 06 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.2 · DDL + DML warm-up: CREATE, INSERT, ALTER ... ADD, UPDATE, DELETE, rename, filter|T05.2 · DDL + DML warm-up: CREATE, INSERT, ALTER ... ADD, UPDATE, DELETE, rename, filter]] · Section A* · CLO2

**Question.**
Write SQL queries for the following:<br>(i) Create a table "Employee" with attributes: EmpID (primary key), Name, Age and Department.<br>(ii) Insert a record into this table: EmpID=1, Name='Nafisa', Age=21, department='HR'.<br>(iii) Find employees whose salary is greater than the average salary of their department.

**Answer.**

**What the examiner wants.**  
Three progressive SQL queries (2 marks each):  
1. DDL `CREATE TABLE` with primary key declaration.  
2. DML `INSERT INTO` statement with literal values.  
3. Advanced query using a correlated subquery to compare individual employee salary against their department average.

**Key idea.**  
Part (iii) requires comparing each employee's salary to an aggregate computed over a specific group (their own department). Because the inner aggregate depends on the department of the current outer tuple (`e1.Department = e2.Department`), the query must be structured as a correlated subquery.

**Step-by-step solution.**  
*(i) Create table Employee:*

```sql
CREATE TABLE Employee (
    EmpID INT PRIMARY KEY,
    Name VARCHAR(50),
    Age INT,
    Department VARCHAR(30)
);
```

*(ii) Insert record into Employee:*

```sql
INSERT INTO Employee (EmpID, Name, Age, Department)
VALUES (1, 'Nafisa', 21, 'HR');
```

*(iii) Find employees earning more than their department's average salary:*

*Assumption: The Employee relation includes an attribute `Salary DECIMAL(10,2)`.*

```sql
SELECT *
FROM Employee e1
WHERE e1.Salary > (
    SELECT AVG(e2.Salary)
    FROM Employee e2
    WHERE e2.Department = e1.Department
);
```

**Check.**  
*Trace of correlated execution:*
- For an employee `e1` in the 'HR' department earning 40,000:
  The inner query computes `AVG(Salary)` for all employees where `Department = 'HR'`.
  If the HR average is 32,000, `40000 > 32000` evaluates to true, and `e1` is included in the output.
- The inner query re-evaluates dynamically for each distinct department encountered in the outer scan.

> [!warning] Common mistakes
> - Writing an uncorrelated subquery `WHERE Salary > (SELECT AVG(Salary) FROM Employee)`. That calculates the company-wide average salary, ignoring departmental differences.
> - Not stating an assumption about the missing `Salary` attribute in the printed schema.

**Exam tip.**  
When an attribute requested by a query is missing from the problem's own schema definition, declare an assumption line immediately.

### Q.3(b) · 04 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T03_Relational_Model_Keys_and_Integrity.md#T03.2 · Keys: super / candidate / primary / alternate / composite / foreign|T03.2 · Keys: super / candidate / primary / alternate / composite / foreign]] · Section A* · CLO2

**Question.**
Explain the distinctions among the terms-<br>(i) Primary key<br>(ii) Candidate key<br>(iii) Super key<br>(iv) Composite key

**Answer.**

**What the examiner wants.**  
Precise definitions and clear distinctions among the four key types. The mark split is 1 mark per key type. The examiner expects minimality rules, nullability constraints, and an illustrative relational table.

**Key idea.**  
Think of a super key as any attribute set that uniquely identifies a row. A candidate key is a minimal super key: removing any attribute ruins uniqueness. The primary key is the single candidate key chosen by the database designer. A composite key is any key consisting of two or more attributes.

**Step-by-step solution.**  
A key is an attribute or set of attributes used to identify rows in a table.

**Distinctions Among Keys:**

| Key Type | Definition | Minimality | NULL Allowed |
| :--- | :--- | :--- | :--- |
| **(i) Primary Key** | The candidate key chosen by the database designer to identify tuples uniquely. | Yes (minimal) | No (never allowed) |
| **(ii) Candidate Key** | A minimal super key. Removing any attribute destroys uniqueness. | Yes (strictly minimal) | Yes (unless constrained `NOT NULL`) |
| **(iii) Super Key** | Any set of attributes that uniquely identifies a row. May contain extra attributes. | No (can have redundant attributes) | No for identifying columns |
| **(iv) Composite Key** | A key that consists of two or more attributes rather than a single attribute. | Can be minimal (candidate) or non-minimal | Depends on whether it is PK or unique |

**Relationship:**
$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

**Running Example:**  
Consider relation $\text{Student}(\underline{\text{student\_id}}, \text{name}, \text{email}, \text{nid}, \text{dept\_name})$:

| student_id | name | email | nid | dept_name |
| :--- | :--- | :--- | :--- | :--- |
| 101 | Akib | akib@gmail.com | 1999123456 | ECE |
| 102 | Shuvo | shuvo@gmail.com | 2000654321 | ECE |
| 103 | Sakib | sakib@gmail.com | 2001987654 | ETE |

- **Super Key:** Any set containing a candidate key. Examples: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{student\_id}, \text{name}\}$, $\{\text{email}, \text{dept\_name}\}$.
- **Candidate Key:** Minimal sets with no extra columns: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{nid}\}$.
- **Primary Key:** The chosen identifier: $\{\text{student\_id}\}$.
- **Composite Key:** In table $\text{Takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{grade})$, the combination $\{\text{student\_id}, \text{course\_id}\}$ forms a composite candidate and primary key. Neither column alone identifies an enrollment record.

*Short version for 2018 Q.2(a) (4 marks):* Omit (iv) Composite key. Keep the definitions, distinctions table, and the Student running example for Super Key, Candidate Key, and Primary Key.  
*Short version for 2021 Q.2(b) (3 marks):* Same as 2018 Q.2(a). Present the 3-row distinction table and the Student relation key classification.

**Check.**  
*Minimality and closure verification:*
- For $\{\text{student\_id}, \text{name}\}$: It uniquely identifies each tuple, so it is a super key. But its subset $\{\text{student\_id}\}$ is also unique. So it has an extraneous attribute (`name`) and cannot be a candidate key.
- For $\{\text{student\_id}\}$: No proper subset exists (except empty set). So it is strictly minimal and qualifies as a candidate key.

> [!warning] Common mistakes
> - Confusing super keys with candidate keys. A candidate key must be minimal; a super key can have extra attributes.
> - Believing a composite key is a separate fourth category. Any super, candidate, or primary key with multiple attributes is a composite key.
> - Forgetting to state that a primary key prohibits NULL values.

**Exam tip.**  
Write down the subset formula $\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}$ right above your example. This gives the examiner an instant visual proof of your grasp.

### Q.4(a) · 04 Marks · CLO1

*Topic: [[Topicwise_answers_explaination/T12_Recovery_System_and_RAID.md#T12.4 · RAID levels, comparison, and recovery role|T12.4 · RAID levels, comparison, and recovery role]] · Section A* · CLO1

**Question.**
Discuss the features of RAID models.

**Answer.**

**What the examiner wants.**  
A discussion of the core architectural capabilities of RAID: parallel striping, redundancy mechanisms, transparent virtualization, hot swapping/rebuilds, and data scrubbing.

**Key idea.**  
RAID is more than disk duplication. It combines parallel bus performance, mathematical error correction, virtualized storage abstractions, and proactive hardware maintenance.

**Step-by-step solution.**  
A Redundant Array of Independent Disks (RAID) provides four major architectural features:

1. **Data Striping (Performance Enhancement):** Data is segmented into blocks or bytes and distributed across multiple physical drives. This enables parallel disk I/O, which boosts transfer rates for large accesses and balances access loads.
2. **Data Redundancy (Fault Tolerance):** Redundancy is achieved through mirroring (duplicate blocks in RAID 1) or parity codes (XOR parity in RAID 5; Reed-Solomon P+Q codes in RAID 6). If a disk fails, data is restored without data loss.
3. **Storage Virtualization:** An array of physical drives appears to the operating system and DBMS as a single, large logical volume.
4. **Online Rebuild and Hot Swapping:** Failed drives can be replaced while the system remains powered on. The controller automatically rebuilds data onto hot-spare disks in the background.
5. **Background Data Scrubbing:** The controller continuously reads idle sectors to detect and repair latent sector corruption (bit rot) before additional drive failures occur.

**Check.**  
*Quick self-test:*
- Q: What is the benefit of data scrubbing in a RAID system?  
  A: It detects unreadable sectors (bit rot) on idle drives and repairs them before another drive crashes.

### Q.4(b) · 04 Marks · CLO3

*Topic: [[Topicwise_answers_explaination/T09_Transactions_ACID_and_Anomalies.md#T09.1 · ACID properties|T09.1 · ACID properties]] · Section A* · CLO3

**Question.**
Briefly explain the importance of ACID properties of transactions with suitable example.

**Answer.**

**What the examiner wants.**  
The technical justification for why each ACID property is critical in a database system. The examiner expects an example (typically fund transfer) and concrete failure scenarios showing what disaster occurs if any single property is missing. Mark split: 1 mark per property.

**Key idea.**  
Do not merely define the terms. Explain the failure consequence of omitting each property: lost money for atomicity, corrupted business rules for consistency, phantom dirty reads for isolation, and wiped transactions for durability.

**Step-by-step solution.**  
Databases must handle two critical challenges: system failures (crashes, power loss) and concurrent user execution. The ACID properties are essential because without them, database data becomes corrupt and untrustworthy.

**Example:** Transaction $T_1$ transfers \$50 from account $A$ (\$1000) to account $B$ (\$2000). The invariant is $A + B = 3000$.

**Importance of Each Property:**

1. **Importance of Atomicity:**
   - *Failure case without atomicity:* The system crashes after deducting \$50 from $A$, before adding \$50 to $B$. The bank loses \$50 of customer money.
   - *Protection:* Atomicity forces the recovery manager to undo the deduction, restoring $A = 1000$ (\$1000).

2. **Importance of Consistency:**
   - *Failure case without consistency:* A flawed program deducts \$50 from $A$ but adds \$100 to $B$.
   - *Protection:* Consistency ensures transaction logic preserves all domain rules. The total sum $A + B = 3000$ remains balanced.

3. **Importance of Isolation:**
   - *Failure case without isolation:* An audit transaction $T_2$ reads balances right after $T_1$ writes $A = 950$, before $T_1$ writes $B$. $T_2$ calculates total assets as $950 + 2000 = 2950$. It issues a false financial warning.
   - *Protection:* Isolation ensures $T_2$ sees either pre-transfer data (\$3000) or post-transfer data (\$3000).

4. **Importance of Durability:**
   - *Failure case without durability:* $T_1$ completes and confirms the transfer. Then a power outage occurs before updates reach disk. The transfer is lost upon reboot.
   - *Protection:* Durability guarantees that committed transactions are logged to stable storage and survive power loss.

**Check.**  
*Quick self-test:*
- Q: What exact harm occurs if isolation is violated during an account transfer?  
  A: Other transactions read partial updates, leading to false reporting or corrupt calculations based on invalid balances.
- Q: What exact harm occurs if durability is violated?  
  A: Customers receive successful transaction receipts, but the database forgets the change after a restart.

> [!warning] Common mistakes
> - Giving purely abstract definitions without showing the practical failure consequence.
> - Using an example without numerical balances, which makes it harder for the examiner to verify the invariant.

**Exam tip.**  
Structure each property as a two-part bullet: *Failure case without property* followed by *Protection provided*. This layout proves you understand the importance of the concept.

**Question.**
What are the benefits of VIEW?

**Answer.**

**What the examiner wants.**  
A concise definition of what a view is, followed by four clear benefits of using views in database systems (about 0.75 marks per benefit).

**Key idea.**  
A view is a saved query that acts like a virtual table. It does not duplicate table data on disk. Instead, it creates a custom window into the database. It improves security by hiding columns, simplifies complex SQL, and gives logical data independence.

**Step-by-step solution.**

A view is a virtual relation defined by an SQL query. The database does not store the view data on disk. Instead, it stores the query definition and executes it when referenced.

**Key Benefits of Views:**
1. **Security and Access Control:** Views hide sensitive columns and rows from unauthorized users. For example, a view can display employee names and departments while hiding salary data.

3. **Logical Data Independence:** If base tables are restructured, split, or renamed, the administrator updates only the view query. Applications using the view continue running without changes.
4. **Consistent and Standardized Data Representation:** Views provide uniform business calculations across multiple users and departments. This avoids duplicate and conflicting query logic.

**Check.**

- Q: Does creating a view duplicate table data on disk?  
  A: No. A standard view stores only the query definition. The query is evaluated when referenced.
- Q: How does a view provide logical data independence?  
  A: When the underlying schema changes, modifying the view definition keeps existing application queries valid.

> [!warning] Common mistakes
> - Confusing standard virtual views with materialized views (standard views do not store physical rows on disk).
> - Stating vague benefits like "makes queries faster" instead of precise database concepts like "logical data independence" and "access security".

**Question.**
Define joining. Discuss different types of joining with suitable example.

**Answer.**

**What the examiner wants.**  
A formal definition of a join operation in relational database systems (1 mark), followed by descriptions and examples of the main join types: Inner join, Left outer join, Right outer join, Full outer join, and Cross join (4 marks, approximately 1 mark per join type).

**Key idea.**  
A join operation combines tuples from two tables into a single result relation. It checks matching values in specified columns. An inner join keeps only matching rows. An outer join retains matching rows plus unmatched rows from one or both tables by padding empty attributes with `NULL`. A cross join pairs every row from the first table with every row from the second table.

**Step-by-step solution.**

**Definition of Joining:**  
A join operation takes two relations and combines them into one relation based on a matching condition. It acts as a Cartesian product followed by a selection predicate and projection.

![Summary of SQL join types and join conditions](../LectureSlides/diagrams/L04_p04_fig01.jpg)
*Figure: Join types and join conditions (Deck 04, Slide 4)*

**Example Base Tables:**

Table `course`:

| course_id | title | dept_name | credits |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | 4 |
| CS-190 | Game Design | Comp. Sci. | 4 |
| CS-315 | Robotics | Comp. Sci. | 3 |

| course_id | prereq_id |
| :--- | :--- |
| BIO-301 | BIO-101 |
| CS-190 | CS-101 |
| CS-347 | CS-101 |

---

#### 1. Inner Join (and Natural Join)
Retains only tuples that satisfy the join condition in both tables. Unmatched rows are dropped.

```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
INNER JOIN prereq ON course.course_id = prereq.course_id;
```

Relational algebra:
$$
\text{course} \bowtie \text{prereq}
$$

**Result:**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |

---

#### 2. Left Outer Join
Preserves every row from the left table (`course`). Fills right-table attributes with `NULL` when no match exists.

```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
LEFT JOIN prereq ON course.course_id = prereq.course_id;
```

Relational algebra:
$$
\text{course} \mathbin{⟕} \text{prereq}
$$

**Result:**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-315 | Robotics | Comp. Sci. | `NULL` |

---

#### 3. Right Outer Join
Preserves every row from the right table (`prereq`). Fills left-table attributes with `NULL` when no match exists.

```sql
SELECT prereq.course_id, title, dept_name, prereq_id
FROM course
RIGHT JOIN prereq ON course.course_id = prereq.course_id;
```

Relational algebra:
$$
\text{course} \mathbin{⟖} \text{prereq}
$$

**Result:**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-347 | `NULL` | `NULL` | CS-101 |

---

#### 4. Full Outer Join
Retains all rows from both tables. It pairs matching rows and fills missing values with `NULL`. MySQL emulates it using `UNION`.

```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
LEFT JOIN prereq ON course.course_id = prereq.course_id
UNION
SELECT prereq.course_id, title, dept_name, prereq_id
FROM course
RIGHT JOIN prereq ON course.course_id = prereq.course_id;
```

$$
\text{course} \mathbin{⟗} \text{prereq}
$$

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-315 | Robotics | Comp. Sci. | `NULL` |
| CS-347 | `NULL` | `NULL` | CS-101 |

---

#### 5. Cross Join (Cartesian Product)
Combines each row of the first table with every row of the second table without any condition.

```sql
SELECT *
FROM course
CROSS JOIN prereq;
```

$$
\text{course} \times \text{prereq}
$$

It returns $3 \times 3 = 9$ rows.

- Q: How does a FULL OUTER JOIN handle tuples present in only one table?  
  A: It retains both tuples and pads the missing columns from the other relation with `NULL`.
- Q: Does MySQL support the SQL standard `FULL OUTER JOIN` syntax directly?  
  A: No. MySQL does not have native `FULL OUTER JOIN` syntax, so we combine `LEFT JOIN` and `RIGHT JOIN` with `UNION`.

### Q.6(a) · 02 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.9 · TRUNCATE vs DELETE|T05.9 · TRUNCATE vs DELETE]] · Section B* · CLO2

**Question.**
What is the difference between 'Truncate' and 'Delete' in SQL?

**Answer.**

**What the examiner wants.**  
Direct architectural and operational comparison between `TRUNCATE` and `DELETE` in SQL (especially in MySQL), addressing command category (DDL vs DML), filtering capability, rollback/transaction semantics, triggers, auto-increment counter handling, and performance.

**Key idea.**  
`DELETE` is a row-level DML statement that individually removes tuples, checks constraints, fires triggers, and writes extensive undo logs for each deleted row. `TRUNCATE` is a table-level DDL statement that drops and recreates the data storage pages directly, bypassing row-level trigger logic and running substantially faster with minimal logging.

**Step-by-step solution.**  
Both `TRUNCATE` and `DELETE` remove rows from a relation, but they operate at different architectural levels:

| Feature | `TRUNCATE TABLE` | `DELETE FROM` |
| :--- | :--- | :--- |
| **Command Category** | **DDL** (Data Definition Language) | **DML** (Data Manipulation Language) |
| **Row Filtering (`WHERE`)** | Not supported; always empties the entire table | Supported; deletes specific filtered rows or all rows |
| **Transaction & Rollback** | Executes an implicit `COMMIT` in MySQL; cannot be rolled back | Logged row-by-row; can be rolled back inside a transaction |
| **Triggers** | Does not fire `DELETE` triggers | Fires `BEFORE DELETE` and `AFTER DELETE` triggers for each row |
| **`AUTO_INCREMENT` Counter** | Resets the auto-increment counter back to its starting value (1) | Preserves the current auto-increment counter sequence |
| **Execution Speed** | Extremely fast; deallocates data pages directly | Slower; scans rows and records individual undo/redo logs |

**Check.**  
*Quick self-test:*
- Q: Can you execute `TRUNCATE TABLE student WHERE dept = 'ECE'`?  
  A: No, `TRUNCATE` has no `WHERE` clause; attempting to provide one causes a syntax error.
- Q: If a table has an auto-increment column at 150 and you execute `DELETE FROM table`, what will the next inserted row's ID be?  
  A: 151. If `TRUNCATE TABLE` were used instead, it would reset to 1.

> [!warning] Common mistakes
> - Stating that `TRUNCATE` is a DML statement. In SQL and MySQL, `TRUNCATE` is classified as DDL.
> - Believing that `TRUNCATE` can be undone with `ROLLBACK` in MySQL; MySQL DDL statements execute an immediate implicit commit.

A concise 6-row comparison table is the fastest, cleanest way to secure full 2/2 marks on this question.

### Q.6(b) · 06 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T07_Triggers_and_Stored_Procedures.md#T07.3 · Implement a trigger or stored procedure|T07.3 · Implement a trigger or stored procedure]] · Section B* · CLO2

**Question.**
Considering the tables (Products, Orders, and Auditlog) answer (i) and (ii).<br>(i) Create a stored procedure to place an order consider stock availability, updates the stock.<br>(ii) Create a trigger to log every stock update in the Auditlog table automatically.

**Answer.**

**What the examiner wants.**  
Implementation of two distinct database routines: a stored procedure that checks stock availability and places an order within a safe transaction (3 marks), and an automatic `AFTER UPDATE` trigger that logs every inventory change into an audit table (3 marks).

**Key idea.**  
The stored procedure coordinates the ordering workflow: it locks the item row, checks whether enough units exist, creates the order record, and reduces inventory. The trigger acts as an automatic observer: whenever product stock changes for any reason, it automatically writes a historical log entry.

**Step-by-step solution.**  

*Assumption: The table schemas are `Products(product_id, name, stock, price)`, `Orders(order_id, product_id, quantity, order_date)`, and `Auditlog(log_id, product_id, old_stock, new_stock, changed_at)`.*

#### (i) Stored Procedure to Place an Order

The stored procedure verifies available stock using row-level locking (`FOR UPDATE`), places the order, and reduces the inventory within a transaction:

```sql
DELIMITER //

CREATE PROCEDURE PlaceOrder (
    IN p_product_id INT,
    IN p_quantity INT
)
BEGIN
    DECLARE v_stock INT;

    START TRANSACTION;

    -- Lock the target product row to prevent concurrent race conditions
    SELECT stock INTO v_stock
    FROM Products
    WHERE product_id = p_product_id
    FOR UPDATE;

    -- Validate product existence and stock sufficiency
    IF v_stock IS NULL THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Product does not exist';
    ELSEIF v_stock < p_quantity THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Insufficient stock available';
    ELSE
        -- Record the new order
        INSERT INTO Orders (product_id, quantity, order_date)
        VALUES (p_product_id, p_quantity, NOW());

        -- Deduct ordered quantity from stock
        UPDATE Products
        SET stock = stock - p_quantity
        WHERE product_id = p_product_id;

        COMMIT;
    END IF;
END //

DELIMITER ;
```

#### (ii) Trigger to Log Stock Updates Automatically

An `AFTER UPDATE` trigger detects when the `stock` column changes and writes an audit record to `Auditlog`:

```sql
DELIMITER //

CREATE TRIGGER trg_log_stock_update
AFTER UPDATE ON Products
FOR EACH ROW
BEGIN
    -- Log only when the stock quantity actually changes
    IF OLD.stock <> NEW.stock THEN
        INSERT INTO Auditlog (product_id, old_stock, new_stock, changed_at)
        VALUES (OLD.product_id, OLD.stock, NEW.stock, NOW());
    END IF;
END //

DELIMITER ;
```

**Check.**  
*Trace with concrete sample tuples:*
- Setup: `Products(101, 'Monitor', 10, 150.00)`.
- *Execution 1:* Client calls `CALL PlaceOrder(101, 3);`.  
  1. The procedure locks row 101. Available stock is $10 \ge 3$.  
  2. Inserts record into `Orders(order_id, 101, 3, NOW())`.  
  3. Updates `Products` setting `stock = 10 - 3 = 7`.  
  4. Commits transaction.  
  5. The update on `Products` automatically fires `trg_log_stock_update`. Since $\text{OLD.stock} (10) \neq \text{NEW.stock} (7)$, it inserts `(101, 10, 7, NOW())` into `Auditlog`.
- *Execution 2:* Client calls `CALL PlaceOrder(101, 20);`.  
  Current stock is 7. Since $7 < 20$, the procedure raises `SIGNAL SQLSTATE '45000'`. No order is inserted and stock stays at 7.

> [!warning] Common mistakes
> - Decrementing inventory without checking whether available stock is sufficient, which causes negative stock values.
> - Missing `FOR UPDATE` on the stock check query. Without locking, concurrent transactions could read the same stock and sell more items than available in the warehouse.
> - Attaching the audit trigger to `Orders` instead of `Products`. Stock can also change through restocking, supplier returns, or inventory audits. The trigger must monitor `Products`.

*(Repeated question: Also asked in 2024 | Solved in T05)*

**Question.**
Write short note on " ON CASCADE DELETE".

**Answer.**

**What the examiner wants.**  
Concise technical descriptions, purpose, and standard SQL syntax/examples for four fundamental SQL clauses and constraint actions (1 mark each).

**Key idea.**  
Each term serves a distinct role in relational data management: `ON DELETE CASCADE` governs referential integrity maintenance; `GROUP BY` partitions data for summary aggregation; `ORDER BY` controls output presentation order; `AS` introduces aliasing for projection expressions and relation names.

**Step-by-step solution.**  
**i) ON DELETE CASCADE (printed as "ON CASCADE DELETE"):**  
A foreign key referential integrity action. When a tuple in the parent table is deleted, the DBMS automatically deletes all corresponding referencing tuples in the child table. This maintains referential integrity and prevents orphaned records.

```sql
CREATE TABLE section (
    course_id VARCHAR(8),
    sec_id VARCHAR(8),
    semester VARCHAR(6),
    year NUMERIC(4, 0),
    PRIMARY KEY (course_id, sec_id, semester, year),
    FOREIGN KEY (course_id) REFERENCES course(course_id)
        ON DELETE CASCADE
);
```

**ii) GROUP BY:**  
An SQL clause used to partition table rows into distinct groups having identical values in specified columns. Aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) then compute summary statistics for each individual group.

```sql
SELECT dept_name, AVG(salary) AS avg_sal
FROM instructor
GROUP BY dept_name;
```

**iii) ORDER BY:**  
An SQL clause that sorts query result rows in ascending (`ASC`, default) or descending (`DESC`) order based on one or more attributes. Multiple sort keys break ties sequentially.

```sql
SELECT name, salary
FROM instructor
ORDER BY salary DESC, name ASC;
```

**iv) AS:**  
An SQL keyword used to define an alias (an alternative temporary name). It can rename an attribute or computed expression in the `SELECT` clause for readability, or rename a table in the `FROM` clause to shorten table references and enable self-joins.

```sql
SELECT salary * 1.15 AS revised_salary
FROM employee AS e;
```

*Short version for 2019 Q.8(c) (4 marks):* Provide parts (i) and (ii).  
*Short version for 2023 Q.6(c) (2 marks):* Provide part (i) with definition, syntax, and effect.

**Check.**  
*Referential trace of `ON DELETE CASCADE`:*
- Department 'Biology' exists in parent table `department`.
- Three courses in child table `course` have `dept_name = 'Biology'`.
- Deleting 'Biology' from `department` via `DELETE FROM department WHERE dept_name = 'Biology'` automatically removes the three referencing courses from `course`.

> [!warning] Common mistakes
> - Confusing `ON DELETE CASCADE` with `ON DELETE SET NULL`; cascading drops the entire referencing row, whereas `SET NULL` updates the referencing foreign key column to `NULL`.
> - Assuming `AS` permanently alters attribute names in physical storage; `AS` renames items only within the output result relation.

### Q.7(a) · 03 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T12_Recovery_System_and_RAID.md#T12.1 · Failure classification, precautions, recovery methods|T12.1 · Failure classification, precautions, recovery methods]] · Section B* · CLO2
*(Repeated question: Also asked in 2017 | Solved in T12)*

**Question.**
Explain the different types of failures that can occur in a database system.

**Answer.**

**What the examiner wants.**  
The three fundamental failure classes in a DBMS: transaction failure, system crash, and disk failure. Examiners look for the affected storage medium and a 1-mark split per class.

**Key idea.**  
Different components fail differently. Main memory is volatile and loses data on power loss. Disk drives are non-volatile and survive power loss, but suffer physical media damage. Transactions can fail internally even when all hardware is operating normally.

**Step-by-step solution.**  
A database management system experiences three main classes of failure based on the affected storage component:

1. **Transaction Failure:** An individual transaction aborts before completing.
   - *Logical Error:* Caused by internal transaction logic or bad data (such as division by zero, arithmetic overflow, or data not found).
   - *System Error:* The system enters an undesirable state (such as a deadlock or timeout) and terminates the transaction.
2. **System Crash:** A hardware failure, power outage, or operating system bug halts the database server.
   - The contents of **volatile storage** (main memory buffers) are lost.
   - The contents of **non-volatile storage** (disk drives) remain uncorrupted (*fail-stop assumption*).
3. **Disk Failure:** Physical damage destroys data blocks on non-volatile media.
   - Causes include head crashes, magnetic surface defects, or transfer errors.
   - Recovery requires redundancy such as RAID arrays or archival backups.

*Variant for 2023 Q.7(a) (CLO2, 3 marks):* The same three-part classification directly answers the question.

**Check.**  
*Quick self-test:*
- Q: What storage contents are lost during a system crash under the fail-stop assumption?  
  A: Volatile storage (main memory and buffer cache) is lost, while non-volatile disk storage survives uncorrupted.
- Q: What is the difference between a logical transaction error and a system error?  
  A: A logical error occurs from invalid data or code (like division by zero). A system error occurs from external database conditions (like deadlock victim selection).

> [!warning] Common mistakes
> - Confusing a system crash (RAM loss) with a disk failure (physical drive damage).
> - Forgetting that logical transaction errors are distinct from concurrency deadlocks.
> - Omitting the fail-stop assumption when defining system crashes.

Structure the answer clearly into three numbered tiers: transaction logic, volatile memory (system crash), and non-volatile disk media.

### Q.7(b) · 04 Marks · CLO2

*Topic: [[Topicwise_answers_explaination/T12_Recovery_System_and_RAID.md#T12.3 · Log-based recovery and shadow paging|T12.3 · Log-based recovery and shadow paging]] · Section B* · CLO2

**Question.**
What is log based recovery? Illustrate with an example of a system crash and recovery process.

**Answer.**

**What the examiner wants.**  
A formal definition of log-based recovery followed by a complete worked crash scenario showing the log state at crash, the classification into redo and undo lists, the recovery actions, and the final data values.

**Key idea.**  
Recovery replays history forward from the log to restore updates of committed transactions, then scans backward to erase updates of active transactions that never completed.

**Step-by-step solution.**  

#### Definition
**Log-based recovery** is a crash recovery technique that records all database update actions on stable storage in a sequential log prior to updating the database on disk. By maintaining both old and new values, the recovery manager can undo incomplete transactions and redo committed transactions after a failure.

#### System Crash Example
Consider three transactions running on data items $A$, $B$, and $C$ with initial values $A = 1000$, $B = 2000$, and $C = 500$:
- $T_1$ transfers \$100 from $A$ to $B$ (commits).
- $T_2$ adds \$200 to $C$ (commits).
- $T_3$ subtracts \$50 from $B$ (active during crash).

**State of Log on Stable Storage at Crash:**
```text
1. <T1 start>
2. <T1, A, 1000, 900>
3. <T1, B, 2000, 2100>
4. <T1 commit>
5. <T2 start>
6. <T2, C, 500, 700>
7. <T3 start>
8. <T2 commit>
9. <T3, B, 2100, 2050>
---- CRASH OCCURS HERE ----
```

#### Recovery Process
1. **Analysis:** The recovery manager scans the log to classify transactions:
   - **Redo-list** = $\{T_1, T_2\}$ (both contain `<start>` and `<commit>` records).
   - **Undo-list** = $\{T_3\}$ (contains `<start>` but no `<commit>` or `<abort>` record).
2. **Redo Phase:** Scans the log forward to re-apply updates for committed transactions:
   - Redo $T_1$: set $A \leftarrow 900$, $B \leftarrow 2100$.
   - Redo $T_2$: set $C \leftarrow 700$.
3. **Undo Phase:** Scans the log backward to rollback uncommitted transactions:
   - Undo $T_3$: restores $B$ to its old value $2100$ using record 9.
   - Writes $\langle T_3\text{ abort}\rangle$ to the log.

**Final Database State:**
$A = 900$, $B = 2100$, $C = 700$. Both atomicity for $T_3$ and durability for $T_1$ and $T_2$ are satisfied.

**Check.**  
*Trace verification:*
- $T_1$ committed successfully: $A$ changed from 1000 to 900, $B$ changed from 2000 to 2100. Sum $A + B = 3000$ is preserved.
- $T_2$ committed successfully: $C$ changed from 500 to 700.
- $T_3$ crashed before commit: its modification to $B$ (subtracting 50 to 2050) was undone back to 2100.
- All values match the exam-style solution.

> [!warning] Common mistakes
> - Putting an uncommitted transaction into the redo list.
> - Forgetting to list the final database values after recovery.
> - Failing to write the `<abort>` log record at the conclusion of the undo pass.

**Exam tip.**  
Write out a clean, numbered log sequence. Then explicitly display the Redo-list and Undo-list before detailing the value changes.

*Topic: [[Topicwise_answers_explaination/T12_Recovery_System_and_RAID.md#T12.4 · RAID levels, comparison, and recovery role|T12.4 · RAID levels, comparison, and recovery role]] · Section B* · CLO2

**Question.**
Briefly describe the RAID model and its significance in database recovery.

**Answer.**

**What the examiner wants.**  
A two-part response: a concise definition of the RAID model, followed by its specific significance in database recovery (realizing stable storage, preventing offline tape restores, protecting transaction logs).

**Key idea.**  
Database recovery algorithms theoretically depend on stable storage. RAID provides the practical hardware foundation that keeps data and write-ahead logs durable against physical media loss.

**Step-by-step solution.**  

#### Description of RAID Model
The RAID (Redundant Array of Independent Disks) model combines multiple physical disk drives into a single logical unit. It uses data striping for parallel speed and data redundancy (mirroring or parity) for reliability.

#### Significance in Database Recovery
1. **Physical Realization of Stable Storage:** Standard database recovery algorithms (such as Write-Ahead Logging) assume the existence of **stable storage** that survives system crashes and media failures. RAID 1, 5, and 6 provide this physical foundation.
2. **Prevents Costly Offline Restores:** A single physical drive failure does not force the database offline. The system avoids hours of downtime spent restoring tape archives and replaying redo logs.
3. **High Availability During Rebuild:** Transactions continue processing queries normally while the controller reconstructs failed data blocks in the background.
4. **Guarantees Transaction Log Durability:** Database transaction logs are typically placed on RAID 1 volumes, ensuring sequential write speed and protection against log loss.

**Check.**

- Q: What theoretical DBMS storage assumption does RAID satisfy in practice?  
  A: Stable storage.

> [!warning] Common mistakes
> - Defining RAID levels without answering how RAID helps database recovery.
> - Assuming RAID replaces DBMS transaction logging (RAID only protects against disk crashes, not power loss or logic aborts).

### Q.8(a) · 02 Marks · CLO1

*Topic: [[Topicwise_answers_explaination/T13_Security_Indexing_and_Hashing.md#T13.3 · Indexing: dense vs sparse index|T13.3 · Indexing: dense vs sparse index]] · Section B* · CLO1

**Question.**
Write short note on dense and sparse index.

**Answer.**

**What the examiner wants.**  
Concise definitions of dense and sparse indices (1 mark) and their key differences in lookup speed, storage overhead, and file ordering requirements (1 mark).

**Key idea.**  
An index speeds up search by mapping search keys to disk block locations. A dense index is like an index at the back of a textbook with an entry for every term. A sparse index is like the header word at the top of a dictionary page, pointing only to the start of each page.

**Step-by-step solution.**  

**1. Definitions**  
- **Dense Index:** An index that contains an index record for **every** search-key value in the data file. To find a record, the system looks up the search key directly in the index and follows its pointer.
- **Sparse Index:** An index that contains index records for only **some** search-key values (typically one entry per disk block). The data file **must be sorted** on the search key. To find a record, the system finds the largest index key less than or equal to the target value, then scans the data block sequentially.

![Dense index on instructor file with search key ID](../Textbook/Chapter_14_Indexing/diagrams/fig_14_02.jpg)
*Figure 13.1: Dense index on instructor file with search key ID (Source: Textbook Ch. 14, Fig. 14.2).*

![Sparse index on instructor file with search key ID](../Textbook/Chapter_14_Indexing/diagrams/fig_14_03.jpg)
*Figure 13.2: Sparse index on instructor file with search key ID (Source: Textbook Ch. 14, Fig. 14.3).*

**2. Comparison**  

| Feature | Dense Index | Sparse Index |
| :--- | :--- | :--- |
| **Index Entries** | One entry for every search-key value in the file. | One entry for only some search-key values (usually one per disk block). |
| **Lookup Speed** | Faster. Locates the exact record or its list of duplicates directly. | Slower. Requires an index lookup followed by a sequential block scan. |
| **Space Overhead** | Large. The index file consumes significant disk or memory space. | Small. The index file is much smaller and often fits in main memory. |
| **File Ordering** | Can be built on sorted (clustering) or unsorted (non-clustering) files. | Requires the data file to be ordered on the search key (clustering only). |
| **Maintenance Cost** | High. Insertions and deletions often require adding or removing index entries. | Low. Records can often be inserted or deleted inside a block without updating the index. |

**Practical Trade-off:** A sparse index with one entry per disk block offers a good compromise between lookup speed and index size.

**Check.**  
*Trace Example (Searching for instructor ID "22222" using Figures 13.1 and 13.2):*
- **Dense index lookup:** The index has a direct entry for `22222`. The pointer goes straight to record `22222` in disk block 1. Cost: 1 index access + 1 data block access.
- **Sparse index lookup:** The index has entries for `10101`, `32343`, and `76543`. The largest key $\le 22222$ is `10101`. The pointer goes to block 1. The DBMS scans block 1 sequentially until it finds `22222`.

*Quick self-test:*
- Q: Can we build a sparse index on an unordered (non-clustering) data file?  
  A: No. If the data file is not sorted on the search key, intermediate values could be in any arbitrary block, so sparse pointers cannot bracket missing keys.
- Q: When is a dense index required?  
  A: A dense index is required for all secondary (non-clustering) indices.

> [!warning] Common mistakes
> - Stating that sparse indices work on unsorted files. Sparse indices strictly require sorted data records.
> - Believing that sparse indices point directly to individual records. They point to the first record of each data block.
> - Leaving out the storage overhead trade-off.

**What the examiner wants.** Complete list of conflicting pairs (1 mark), drawing the 4-node precedence graph (1 mark), acyclic verdict (0.5 marks), and finding **all** valid topological sorts (1.5 marks).

**Key idea.** With 4 transactions, the precedence graph defines a partial order. If the graph has no cycles, it is conflict serializable. Because some transactions have no direct or indirect dependency between them, there may be more than one valid topological sort. The question asks for **all possible serialized schedules**, so we must find every single one.

**Step-by-step solution.**

#### 1. Chronological Operation Trace

Let the rows of schedule $S$ be indexed 1 to 7:
1. $T_4: R(A)$
2. $T_2: R(A)$
3. $T_1: W(B)$
4. $T_3: R(A)$
5. $T_2: W(A)$
6. $T_3: R(B)$
7. $T_2: W(B)$

#### 2. Conflicting Pairs Analysis

- **Item $A$ conflicts:**
  - $T_4: R(A)$ (step 1) occurs before $T_2: W(A)$ (step 5) $\implies T_4 \to T_2$.
  - $T_3: R(A)$ (step 4) occurs before $T_2: W(A)$ (step 5) $\implies T_3 \to T_2$.
  - ($T_2: R(A)$ and $T_2: W(A)$ belong to the same transaction, so they do not produce an edge).
- **Item $B$ conflicts:**
  - $T_1: W(B)$ (step 3) occurs before $T_3: R(B)$ (step 6) $\implies T_1 \to T_3$.
  - $T_1: W(B)$ (step 3) occurs before $T_2: W(B)$ (step 7) $\implies T_1 \to T_2$.
  - $T_3: R(B)$ (step 6) occurs before $T_2: W(B)$ (step 7) $\implies T_3 \to T_2$.

#### 3. Precedence Graph and Cycle Check

![2023 Q.8(b) Precedence Graph DAG with 4 nodes](diagrams/T10_2023_Q8b_precedence_graph.jpg)

The directed edges are:
- $T_1 \to T_3$
- $T_3 \to T_2$
- $T_4 \to T_2$
- $T_1 \to T_2$ (implied transitively by $T_1 \to T_3 \to T_2$)

There are no backward edges, so the precedence graph is **acyclic**.  
**Verdict:** Schedule $S$ is **conflict serializable**.

#### 4. Determine All Possible Serialized Schedules

We perform topological sorting on the directed acyclic graph:
- Constraint 1: $T_1$ must precede $T_3$ ($T_1 \to T_3$).
- Constraint 2: $T_3$ must precede $T_2$ ($T_3 \to T_2$). This establishes the chain:
  $$
  T_1 \longrightarrow T_3 \longrightarrow T_2
  $$
- Constraint 3: $T_4$ must precede $T_2$ ($T_4 \to T_2$).
- Notice that there is no edge between $T_4$ and $T_1$, and no edge between $T_4$ and $T_3$.

Therefore, $T_4$ can be placed in any position as long as it appears before $T_2$:
1. $T_4$ before $T_1$: $\boxed{\langle T_4, T_1, T_3, T_2 \rangle}$
2. $T_4$ between $T_1$ and $T_3$: $\boxed{\langle T_1, T_4, T_3, T_2 \rangle}$
3. $T_4$ between $T_3$ and $T_2$: $\boxed{\langle T_1, T_3, T_4, T_2 \rangle}$

**Result:** There are exactly **3** possible serialized schedules.

**Check.**
- Total permutations of 4 transactions is $4! = 24$.
- The condition $T_1 < T_3 < T_2$ restricts the relative order of $\{T_1, T_2, T_3\}$ to 1 out of 6 possibilities ($24 / 6 = 4$).
- The condition $T_4 < T_2$ eliminates the case where $T_4$ is after $T_2$ ($\langle T_1, T_3, T_2, T_4 \rangle$).
- Exactly $4 - 1 = 3$ valid topological orders remain.

> [!warning] Common mistakes
> - Listing only one topological sort when the question explicitly says "determine **all** the possible serialized schedules".
> - Inventing an artificial dependency between $T_4$ and $T_1$ or $T_3$. $T_4$ only accesses $A$, and neither $T_1$ nor $T_3$ writes $A$.
> - Forgetting that $T_2$ reads $A$ and writes $A$, but operations within the same transaction never create graph edges.

**Exam tip.** When asked for "all possible serialized schedules", state the partial ordering constraints first. Then show each position where the unconstrained transaction can fit.

  $$
  \text{R-TS}(A) = 0, \quad \text{W-TS}(A) = 0
  $$
  $$
  \text{R-TS}(B) = 0, \quad \text{W-TS}(B) = 0
  $$
  $$
  \text{R-TS}(C) = 0, \quad \text{W-TS}(C) = 0
  $$

**2. Step-by-Step Trace Table:**

| Step | Txn | Op | Protocol Rule & Condition Check | Action | Updated Timestamps |
| :---: | :---: | :---: | :--- | :--- | :--- |
| **1** | $T_1$ | $R(A)$ | $\text{TS}(T_1) \ge \text{W-TS}(A) \implies 100 \ge 0$ (Valid) | **Execute** | $\text{R-TS}(A) = \max(0, 100) = 100$ |
| **2** | $T_2$ | $R(B)$ | $\text{TS}(T_2) \ge \text{W-TS}(B) \implies 200 \ge 0$ (Valid) | **Execute** | $\text{R-TS}(B) = \max(0, 200) = 200$ |
| **3** | $T_1$ | $W(C)$ | $\text{TS}(T_1) \ge \text{R-TS}(C)$ and $\text{W-TS}(C) \implies 100 \ge 0$ (Valid) | **Execute** | $\text{W-TS}(C) = 100$ |
| **4** | $T_3$ | $R(B)$ | $\text{TS}(T_3) \ge \text{W-TS}(B) \implies 300 \ge 0$ (Valid) | **Execute** | $\text{R-TS}(B) = \max(200, 300) = 300$ |
| **5** | $T_1$ | $R(C)$ | $\text{TS}(T_1) \ge \text{W-TS}(C) \implies 100 \ge 100$ (Valid) | **Execute** | $\text{R-TS}(C) = \max(0, 100) = 100$ |
| **6** | $T_2$ | $W(B)$ | $\text{TS}(T_2) < \text{R-TS}(B) \implies 200 < 300$ (**Violated!**) | **REJECTED** | **$T_2$ is rolled back** |
| **7** | $T_3$ | $W(A)$ | $\text{TS}(T_3) \ge \text{R-TS}(A)$ and $\text{W-TS}(A) \implies 300 \ge 100$ (Valid) | **Execute** | $\text{W-TS}(A) = 300$ |

**3. Detailed Evaluation:**
- **Step 1 ($T_1: R(A)$):** $\text{TS}(T_1) \ge \text{W-TS}(A)$ holds ($100 \ge 0$). $\text{R-TS}(A)$ updates to 100.
- **Step 2 ($T_2: R(B)$):** $\text{TS}(T_2) \ge \text{W-TS}(B)$ holds ($200 \ge 0$). $\text{R-TS}(B)$ updates to 200.
- **Step 3 ($T_1: W(C)$):** $\text{TS}(T_1)$ is not less than $\text{R-TS}(C)$ or $\text{W-TS}(C)$. Write executes. $\text{W-TS}(C)$ updates to 100.
- **Step 4 ($T_3: R(B)$):** $\text{TS}(T_3) \ge \text{W-TS}(B)$ holds ($300 \ge 0$). $\text{R-TS}(B)$ updates to $\max(200, 300) = 300$.
- **Step 5 ($T_1: R(C)$):** $T_1$ reads the value of $C$ that it wrote at Step 3. $\text{TS}(T_1) \ge \text{W-TS}(C)$ holds ($100 \ge 100$). $\text{R-TS}(C)$ updates to 100.
- **Step 6 ($T_2: W(B)$):** $T_2$ issues a write on $B$. The protocol checks whether $\text{TS}(T_2) < \text{R-TS}(B)$. Here, $\text{TS}(T_2) = 200$ and $\text{R-TS}(B) = 300$. Because $200 < 300$, the check fails. $T_2$ is attempting to produce a value of $B$ that $T_3$ was supposed to read, but $T_3$ already read an older value. The write operation is rejected, and **$T_2$ is rolled back**.
- **Step 7 ($T_3: W(A)$):** $\text{TS}(T_3) = 300 \ge \text{R-TS}(A) = 100$ and $\ge \text{W-TS}(A) = 0$. Write executes. $\text{W-TS}(A)$ updates to 300.

**Conclusion:**  
**The schedule is not accepted without rollback.** At Step 6, transaction $T_2$ violates timestamp ordering and is rolled back. When restarted, $T_2$ must receive a new timestamp greater than 300.

**Check.**  
*Verification of conflict:*
- In timestamp ordering, the serial order must be $T_1 \to T_2 \to T_3$.
- In the schedule, $T_3$ reads $B$ before $T_2$ writes $B$. This enforces an execution order $T_3 \to T_2$ on item $B$.
- This contradicts the timestamp order $T_2 \to T_3$.
- Therefore, $T_2$'s write must fail and trigger a rollback.

> [!warning] Common mistakes
> - Missing the condition at Step 6 and concluding that the entire schedule succeeds.
> - Forgetting that $\text{R-TS}(B)$ became 300 at Step 4, causing $T_2$'s write at Step 6 to fail.
> - Thinking that Step 5 ($T_1: R(C)$) fails. Step 5 succeeds because $T_1$ reads its own previous write ($100 \ge 100$).

**Exam tip.**  
Always draw the step-by-step trace table with columns for Step, Transaction, Operation, Condition Check, Decision, and Updated Timestamps. This structure proves every step to the examiner.
