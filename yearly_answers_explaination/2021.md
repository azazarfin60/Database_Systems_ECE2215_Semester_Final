### Q.1(a) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T01_DB_Concepts_and_Architecture.md#T01.2 · File system vs DBMS (8 disadvantages of file systems)|T01.2 · File system vs DBMS (8 disadvantages of file systems)]] · Section A* · CLO1
*(Repeated question: Also asked in 2017 | Solved in T01)*

**Question.**
Discuss four significant differences between a file-processing system and a DBMS.

**Answer.**

**What the examiner wants.**  
Four distinct architectural differences between an operating system file processing system and a DBMS. The mark split is 1 mark per difference. Examiners expect key technical concepts: redundancy, ad-hoc access, data independence, and concurrency or crash recovery.

**Key idea.**  
An operating system file stores a sequence of bytes. The OS does not understand the internal structure of the data inside the file. In contrast, a DBMS understands data structures, enforces relations and constraints, coordinates concurrent users, and guarantees recovery after system crashes.

**Step-by-step solution.**  

| Feature | File Processing System | DBMS (Database Management System) |
| :--- | :--- | :--- |
| **Data Redundancy & Inconsistency** | Data is duplicated across multiple separate files. Different copies easily get out of sync. | Centralizes data storage. Normalization avoids duplication and keeps copies consistent. |
| **Data Access & Retrieval** | Programmers must write a new custom program in C or Java for each new query. | Users write declarative queries (like SQL) to retrieve ad-hoc data quickly without new code. |
| **Data Isolation & Independence** | Data structures and application code are tightly coupled. Changing a file structure breaks programs. | Provides data abstraction. Changes to physical storage structures do not affect application programs. |
| **Concurrent Access & Recovery** | Hard to coordinate simultaneous access. Multiple updates cause lost data. Crash recovery is manual. | Built-in concurrency control prevents conflicting updates. Automated logging and recovery preserve ACID properties. |

*Variant for 2021 Q.1(a) (4 marks):* The same four differences directly answer the question.

**Check.**  
*Quick self-test:*
- Q: Why does a file system struggle with ad-hoc reporting?  
  A: Because each report requires a programmer to write and compile a new program from scratch.
- Q: How does a DBMS prevent data inconsistency when multiple copies exist?  
  A: It centralizes data and applies normalization so each fact is stored only once.

> [!warning] Common mistakes
> - Writing vague generalities like "file systems are old, DBMS is modern" instead of specific technical differences.
> - Omitting concurrent access anomalies and transaction crash recovery.
> - Writing a long essay instead of a structured comparison table.

**Exam tip.**  
Use a comparison table with clear feature titles. This layout allows the examiner to check off 1 mark per row in seconds.

### Q.1(b) · 03 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T01_DB_Concepts_and_Architecture.md#T01.3 · Functions/roles of the DBA ("five functions"); relation schema|T01.3 · Functions/roles of the DBA ("five functions"); relation schema]] · Section A* · CLO1
*(Repeated question: Also asked in 2020 | Solved in T01)*

**Question.**
What are the five main functions of a database administrator?

**Answer.**

**What the examiner wants.**  
The five official functions of a DBA (3 marks, following the exact terminology from Deck 01 Slide 10) and the definition of a relation schema with a formal example (2 marks).

**Key idea.**  
The Database Administrator (DBA) is the person with centralized control over the database system. The DBA handles both physical storage decisions and user authorization. A relation schema is the logical structural definition of a table (its blueprint).

**Step-by-step solution.**  
**Five Main Functions of a Database Administrator (DBA):**
1. **Schema definition:** The DBA creates the original database schema by executing DDL statements.
2. **Storage structure and access-method definition:** The DBA defines internal storage structures, indexing methods, and file organizations to optimize data access.
3. **Schema and physical-organization modification:** The DBA modifies database schemas and physical storage layouts to improve performance or adapt to changing business requirements.
4. **Granting of authorization for data access:** The DBA assigns access rights and user roles to regulate who can inspect or modify specific data items.
5. **Routine maintenance:** The DBA performs recurring operational tasks. These include periodically backing up the database, monitoring running jobs, and ensuring sufficient free disk space.

**Relation Schema:**  
A **relation schema** is the formal logical definition or blueprint of a relation (table). It specifies the name of the relation along with its set of attributes (columns) and their corresponding domains (data types).

- Format: $R(A_1, A_2, \dots, A_n)$
- Example: $\text{instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$, where $\underline{\text{ID}}$ serves as the primary key.

*Variant for 2021 Q.1(b) (3 marks):* State and explain the five DBA functions above; omit the relation schema.  
*Variant for 2017 Q.1(c) (2 marks):* List only the names: (1) Schema definition, (2) Storage structure and access-method definition, (3) Schema and physical-organization modification, (4) Granting of authorization for data access, (5) Routine maintenance.

**Check.**  
*Quick self-test:*
- Q: What is the difference between a relation schema and a relation instance?  
  A: The schema is the logical definition (table design), while an instance is the actual data populated at a given moment.
- Q: Which DBA function ensures that the system does not run out of storage during operations?  
  A: Routine maintenance (monitoring disk space and upgrading storage).

> [!warning] Common mistakes
> - Inventing informal duties (like "writes SQL queries" or "enters user records") instead of using the five official functions from Deck 01 Slide 10.
> - Forgetting to provide a concrete schema example for the relation schema part.

**Exam tip.**

### Q.1(c) · 05 Marks · CLO2

*Topic: [[../Topicwise_answers_explaination/T03_Relational_Model_Keys_and_Integrity.md#T03.3 · Referential integrity & FK syntax (MySQL)|T03.3 · Referential integrity & FK syntax (MySQL)]] · Section A* · CLO2

**Question.**
How do we achieve referential integrity in DBMS? Provide necessary MySQL query with an appropriate example.

**Answer.**

**What the examiner wants.**  
An explanation of how a DBMS enforces referential integrity (~2 marks) plus valid, executable MySQL DDL and DML queries showing table creation, constraints, violating insert behavior, and cascading options (~3 marks).

**Key idea.**  
Referential integrity prevents orphan child records. In MySQL, you define it using `FOREIGN KEY ... REFERENCES ...`. When someone attempts to insert a child row pointing to a nonexistent parent row, MySQL blocks the command with Error 1452.

**Step-by-step solution.**  
**1. How Referential Integrity is Achieved in DBMS:**  
Referential integrity ensures that relationships between tables remain consistent. It requires that any foreign key value in a referencing table must exist as a primary key value in the referenced table, or be NULL.  
A DBMS achieves referential integrity through three mechanisms:
1. **Constraint Declaration:** The database designer defines foreign keys in the DDL schema using the `FOREIGN KEY ... REFERENCES` clause.
2. **Active Violation Checking:** The DBMS monitors `INSERT`, `UPDATE`, and `DELETE` commands. It blocks any operation that creates orphan child records.
3. **Automated Referential Actions:** The designer specifies rules for parent modifications:
   - `CASCADE`: Deleting or updating a parent row automatically deletes or updates matching child rows.
   - `SET NULL`: Sets child foreign key columns to NULL when the parent row is deleted or updated.
   - `RESTRICT` / `NO ACTION`: Default rule; rejects parent deletion or update if matching child rows exist.

**2. MySQL DDL Query Example:**

```sql
-- Parent table (Referenced relation)
CREATE TABLE Department (
    dept_name VARCHAR(20) PRIMARY KEY,
    building VARCHAR(20),
    budget DECIMAL(12, 2)
);

-- Child table (Referencing relation)
CREATE TABLE Student (
    student_id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    dept_name VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES Department(dept_name)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

**3. Operation and Violation Demonstration:**  
Populate a valid parent department:

```sql
INSERT INTO Department VALUES ('ECE', 'Academic Building 2', 500000.00);
INSERT INTO Student VALUES (101, 'Akib', 'ECE'); -- Allowed
```

Now attempt a violating insert with a nonexistent department:

```sql
INSERT INTO Student VALUES (102, 'Shuvo', 'ME');
```

**MySQL System Response:**  
MySQL rejects the insert and raises an integrity violation error:

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`university`.`Student`, CONSTRAINT `student_ibfk_1` FOREIGN KEY (`dept_name`) REFERENCES `Department` (`dept_name`) ON DELETE CASCADE ON UPDATE CASCADE)
```

If `'ECE'` is deleted from `Department`, `ON DELETE CASCADE` automatically deletes student 101. This keeps the database consistent.

**Check.**  
*MySQL execution trace:*
- `INSERT INTO Department VALUES ('ECE', ...)`: Row added.
- `INSERT INTO Student VALUES (101, 'Akib', 'ECE')`: Check verifies that `'ECE'` exists in `Department.dept_name`. Insertion succeeds.
- `INSERT INTO Student VALUES (102, 'Shuvo', 'ME')`: Check discovers `'ME'` is absent from `Department.dept_name`. Transaction halts with `ERROR 1452`.

> [!warning] Common mistakes
> - Creating the referencing table before the referenced table. The referenced table must be created first.
> - Omitting the column list in `REFERENCES Department(dept_name)`. MySQL requires the explicit referenced column.
> - Forgetting to demonstrate what happens during an integrity violation.

**Exam tip.**  
Write both the `CREATE TABLE` statements and the violating `INSERT` statement. Quoting MySQL Error 1452 shows genuine practical database expertise.

### Q.2(a) · 05 Marks · CLO2

*Topic: [[../Topicwise_answers_explaination/T04_Relational_Algebra_and_Calculus.md#T04.2 · Write RA queries on a given schema (incl. "only" queries → set difference, $\gamma$ count/max, RA modification/update)|T04.2 · Write RA queries on a given schema (incl. "only" queries → set difference, $\gamma$ count/max, RA modification/update)]] · Section A* · CLO2

**Question.**
Consider the following relation schema:<br>&emsp;customer (<u>id</u>, name, age, gender)<br>&emsp;order (<u>id</u>, product, price, date)<br><br>Now, give expression in relational algebra to-<br>(i) find name of the customers who are male.<br>(ii) find name of all customers who have purchased car as product.<br>(iii) find the details of all customers who have purchased "phone" as product and the price is less than \$300.

**Answer.**

**What the examiner wants.**  
Three relational algebra expressions worth approximately 1.5, 1.5, and 2 marks. Evaluates single-table selection, natural join between customer and orders, and compound filtering combining string and numeric inequalities.

**Key idea.**  
The attribute `id` serves as customer primary key and appears as foreign key in `order`. Natural join equates `customer.id = order.id`. Filter on product names and numerical price thresholds.

**Step-by-step solution.**

*Assumption: The attribute `order.id` represents the customer identifier that placed the order.*

**(i) Names of male customers:**

Select tuples from `customer` where gender is "male", then project the customer name:

$$
\boxed{\Pi_{\text{name}}(\sigma_{\text{gender} = \text{"male"}}(\text{customer}))}
$$

**(ii) Names of all customers who purchased car as product:**

1. Select orders where product is "car".
2. Natural join with `customer` on `id`.
3. Project customer names:

$$
\boxed{\Pi_{\text{name}}(\text{customer} \bowtie \sigma_{\text{product} = \text{"car"}}(\text{order}))}
$$

**(iii) Details of all customers who purchased "phone" priced under \$300:**

1. Filter the `order` relation for product "phone" with price strictly below 300:

$$
T_{\text{target\_orders}} \leftarrow \sigma_{\text{product} = \text{"phone"} \land \text{price} < 300}(\text{order})
$$

2. Join the filtered orders with `customer`:

$$
\boxed{\text{customer} \bowtie T_{\text{target\_orders}}}
$$

To project customer attributes only:

$$
\Pi_{\text{customer.id}, \text{name}, \text{age}, \text{gender}}(\text{customer} \bowtie T_{\text{target\_orders}})
$$

**Check.**  
Sample data:
- `customer`: `(101, "Kamal", 30, "male")`, `(102, "Nila", 24, "female")`.
- `order`: `(101, "phone", 250, "2021-05-10")`, `(102, "phone", 400, "2021-06-01")`, `(102, "car", 15000, "2021-07-15")`.

- Part (i): Kamal has gender "male". Output: `{"Kamal"}`.
- Part (ii): Order with product "car" belongs to ID 102. Natural join with customer outputs `{"Nila"}`.
- Part (iii): Kamal's phone costs 250 ($< 300$). Nila's phone costs 400 ($\not< 300$). Result contains Kamal's record.

> [!warning] Common mistakes
> - Omitting the outer projection $\Pi_{\text{name}}$ in parts (i) and (ii). Without projection, all attributes from both tables are returned.
> - Putting quotes around numerical values like `price < "300"`. Price is a numeric attribute.
> - Writing a Cartesian product ($\times$) without specifying the join predicate `customer.id = order.id`.

**Exam tip.**  
When the question asks for "details of all customers", providing the joined relation or projecting the customer relation's attributes is accepted. Always state the join assumption on `id`.

### Q.2(b) · 03 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T03_Relational_Model_Keys_and_Integrity.md#T03.2 · Keys: super / candidate / primary / alternate / composite / foreign|T03.2 · Keys: super / candidate / primary / alternate / composite / foreign]] · Section A* · CLO1
*(Repeated question: Also asked in 2023 | Solved in T03)*

**Question.**
Differentiate among Superkey, Candidate Key and Primary Key with an appropriate example.

**Answer.**

**What the examiner wants.**  
Precise definitions and clear distinctions among the four key types. The mark split is 1 mark per key type. The examiner expects minimality rules, nullability constraints, and an illustrative relational table.

**Key idea.**  
Think of a super key as any attribute set that uniquely identifies a row. A candidate key is a minimal super key: removing any attribute ruins uniqueness. The primary key is the single candidate key chosen by the database designer. A composite key is any key consisting of two or more attributes.

**Step-by-step solution.**  
A key is an attribute or set of attributes used to identify rows in a table.

**Distinctions Among Keys:**

| Key Type | Definition | Minimality | NULL Allowed |
| :--- | :--- | :--- | :--- |
| **(i) Primary Key** | The candidate key chosen by the database designer to identify tuples uniquely. | Yes (minimal) | No (never allowed) |
| **(ii) Candidate Key** | A minimal super key. Removing any attribute destroys uniqueness. | Yes (strictly minimal) | Yes (unless constrained `NOT NULL`) |
| **(iii) Super Key** | Any set of attributes that uniquely identifies a row. May contain extra attributes. | No (can have redundant attributes) | No for identifying columns |
| **(iv) Composite Key** | A key that consists of two or more attributes rather than a single attribute. | Can be minimal (candidate) or non-minimal | Depends on whether it is PK or unique |

**Relationship:**
$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

**Running Example:**  
Consider relation $\text{Student}(\underline{\text{student\_id}}, \text{name}, \text{email}, \text{nid}, \text{dept\_name})$:

| student_id | name | email | nid | dept_name |
| :--- | :--- | :--- | :--- | :--- |
| 101 | Akib | akib@gmail.com | 1999123456 | ECE |
| 102 | Shuvo | shuvo@gmail.com | 2000654321 | ECE |
| 103 | Sakib | sakib@gmail.com | 2001987654 | ETE |

- **Super Key:** Any set containing a candidate key. Examples: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{student\_id}, \text{name}\}$, $\{\text{email}, \text{dept\_name}\}$.
- **Candidate Key:** Minimal sets with no extra columns: $\{\text{student\_id}\}$, $\{\text{email}\}$, $\{\text{nid}\}$.
- **Primary Key:** The chosen identifier: $\{\text{student\_id}\}$.
- **Composite Key:** In table $\text{Takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{grade})$, the combination $\{\text{student\_id}, \text{course\_id}\}$ forms a composite candidate and primary key. Neither column alone identifies an enrollment record.

*Short version for 2018 Q.2(a) (4 marks):* Omit (iv) Composite key. Keep the definitions, distinctions table, and the Student running example for Super Key, Candidate Key, and Primary Key.  
*Short version for 2021 Q.2(b) (3 marks):* Same as 2018 Q.2(a). Present the 3-row distinction table and the Student relation key classification.

**Check.**  
*Minimality and closure verification:*
- For $\{\text{student\_id}, \text{name}\}$: It uniquely identifies each tuple, so it is a super key. But its subset $\{\text{student\_id}\}$ is also unique. So it has an extraneous attribute (`name`) and cannot be a candidate key.
- For $\{\text{student\_id}\}$: No proper subset exists (except empty set). So it is strictly minimal and qualifies as a candidate key.

> [!warning] Common mistakes
> - Confusing super keys with candidate keys. A candidate key must be minimal; a super key can have extra attributes.
> - Believing a composite key is a separate fourth category. Any super, candidate, or primary key with multiple attributes is a composite key.
> - Forgetting to state that a primary key prohibits NULL values.

**Exam tip.**  
Write down the subset formula $\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}$ right above your example. This gives the examiner an instant visual proof of your grasp.

### Q.2(c) · 04 Marks · CLO2

*Topic: [[../Topicwise_answers_explaination/T04_Relational_Algebra_and_Calculus.md#T04.3 · Explain an RA expression in words|T04.3 · Explain an RA expression in words]] · Section A* · CLO2

**Question.**
For each expression, explain in words what the expression does.<br>Where takes(<u>id</u>, <u>course</u>, <u>sec_id</u>, sem, year, grade)<br>(i) $\sigma_{year \ge 2009}(\text{takes}) \bowtie \text{student}$<br>(ii) $\Pi_{id, name, course\_id}(\text{student} \bowtie \text{takes})$

**Answer.**

**What the examiner wants.**  
Accurate plain English descriptions of two relational algebra expressions (2 marks each). Evaluates understanding of selection, natural join semantics, projection, and attribute propagation.

**Key idea.**  
Trace the operation tree from the innermost operators to the outermost operators. Explain what filtering or pairing takes place at each step, and describe what the final relation represents.

**Step-by-step solution.**

**(i) Expression:** $\sigma_{year \ge 2009}(\text{takes}) \bowtie \text{student}$

1. **Selection Operation:** The term $\sigma_{year \ge 2009}(\text{takes})$ scans the `takes` relation and filters it. It keeps only the course enrollment records where the course was taken in the year 2009 or later.
2. **Natural Join Operation:** The join $\bowtie$ matches the filtered course enrollment records with tuples in the `student` relation on their common attribute `id`.
3. **What the join adds:** The join combines all student details (`name`, `dept_name`, `tot_cred`) with all enrollment details (`course`, `sec_id`, `sem`, `year`, `grade`).
4. **Summary in words:** Finds the full records (combining all student and enrollment information) of all students who took at least one course in the year 2009 or later.

**(ii) Expression:** $\Pi_{id, name, course\_id}(\text{student} \bowtie \text{takes})$

1. **Natural Join Operation:** The term $\text{student} \bowtie \text{takes}$ pairs each student with every course enrollment record that shares the same `id`.
2. **What the join adds:** It brings together the student's personal identity (`name`) and their enrolled course details (`course_id` / `course`).
3. **Projection Operation:** The operator $\Pi_{id, name, course\_id}$ selects only three attributes: the student ID (`id`), student name (`name`), and the course identifier (`course_id` / `course`). All other attributes (such as department name, section ID, semester, year, and grade) are discarded. Duplicate rows are removed automatically.
4. **Summary in words:** Displays a list showing the ID, name, and course ID for all students and each course they have taken.

**Check.**  
- Part (i): If student 101 took courses in 2008 and 2010, the selection drops the 2008 record. The join keeps the 2010 record paired with student 101's details. If student 102 took courses only in 2005, student 102 does not appear in the result.
- Part (ii): If student 101 took CS-101 and CS-201, the output contains two tuples: `(101, "Alice", "CS-101")` and `(101, "Alice", "CS-201")`.

> [!warning] Common mistakes
> - Writing a vague summary such as "joins student and takes table" without explaining what the filter condition or projection actually achieves.
> - Forgetting to mention that projection removes duplicates.
> - Overlooking that students who have taken no courses in 2009 or later are excluded from part (i).

**Exam tip.**  
Format your answer in three distinct bullet points: describe the inner operation, explain the outer operation, and give a one-sentence plain English summary of the final output.

### Q.3(a) · 08 Marks · CLO2

*Topic: [[../Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.2 · DDL + DML warm-up: `CREATE`, `INSERT`, `ALTER ... ADD`, `UPDATE`, `DELETE`, rename, filter|T05.2 · DDL + DML warm-up: `CREATE`, `INSERT`, `ALTER ... ADD`, `UPDATE`, `DELETE`, rename, filter]] · Section A* · CLO2

**Question.**
Consider the following E-comerce database:<br>&emsp;client (<u>c_no</u>, name, city, state, baldue)<br>&emsp;product (<u>p_no</u>, description, profit_percent, quantity, sell_price, cost_price)<br>&emsp;salesman (<u>s_no</u>, name, city, state, sal_amount, target, sold_yearly, remarks)<br><br>Now write the appropriate MySql code to execute the following query:<br>(i) Change the city of client no "C0005" to "Barishal".<br>(ii) Delete all salesmen whose salaries are equal to 35000 Tk.<br>(iii) Add a column called "Telephone" of datatype numeric and size = '11' to the client table.<br>(iv) Find products whose selling price is more than 500. Calculate a new selling price as original price*15. Rename the new column in the output as new_price.<br><br>*(Note: "E-comerce" and "MySql" printed verbatim from original question paper)*

**Answer.**

**What the examiner wants.**  
Four distinct MySQL statements (2 marks each):  
1. `UPDATE` statement with `SET` and targeted `WHERE` clause.  
2. `DELETE FROM` statement with numeric equality comparison.  
3. `ALTER TABLE` statement specifying column name and data type `NUMERIC(11)`.  
4. `SELECT` statement performing arithmetic calculation and renaming using `AS`.

**Key idea.**  
MySQL adheres to ANSI SQL DDL and DML standards for row-level modifications (`UPDATE`, `DELETE`), schema evolution (`ALTER TABLE`), and calculated output expressions (`AS`).

**Step-by-step solution.**  
*(i) Change city of client "C0005" to "Barishal":*

```sql
UPDATE client
SET city = 'Barishal'
WHERE c_no = 'C0005';
```

*(ii) Delete salesmen whose salary is 35000 Tk:*

```sql
DELETE FROM salesman
WHERE sal_amount = 35000;
```

*(iii) Add column "Telephone" of numeric type and size 11 to client table:*

```sql
ALTER TABLE client
ADD Telephone NUMERIC(11);
```

*(iv) Find products with sell_price > 500 and calculate new selling price:*

```sql
SELECT p_no,
       description,
       sell_price,
       sell_price * 15 AS new_price
FROM product
WHERE sell_price > 500;
```

**Check.**  
*Statement validation:*
- Part (i): Filters on primary key `c_no = 'C0005'`, ensuring exactly one record is updated.
- Part (ii): Uses attribute `sal_amount` defined in the schema.
- Part (iii): `NUMERIC(11)` matches the requested numeric type with precision 11.
- Part (iv): Arithmetic expression `sell_price * 15` is evaluated row by row and projected under the alias `new_price`.

> [!warning] Common mistakes
> - Writing `UPDATE client SET city = 'Barishal'` without a `WHERE` clause, which overwrites the city for all clients.
> - Writing `DELETE * FROM salesman`, which is invalid SQL syntax (`DELETE FROM` does not take `*`).

**Exam tip.**  
Double check attribute names against the provided schema (`sal_amount`, not `salary`; `sell_price`, not `price`).

### Q.3(b) · 04 Marks · CLO4

*Topic: [[../Topicwise_answers_explaination/T02_ER_and_EER_Modeling.md#T02.2 · Attribute types (simple/composite, single/multivalued, derived)|T02.2 · Attribute types (simple/composite, single/multivalued, derived)]] · Section A* · CLO4

**Question.**
Define entity and attribute. Explain the following attributes-<br>(i) Multi-valued<br>(ii) Derived<br>(iii) Composite

**Answer.**

**What the examiner wants.**  
Definitions of entity and attribute (1 mark total). Explanations of multi-valued, derived, and composite attributes with visual notations and examples (1 mark each, 3 marks total).

**Key idea.**  
An entity is an object that exists in the real world. Attributes are the characteristics that describe it. The E-R model provides special graphical notation for attributes that hold sets of values, values computed on the fly, or values composed of parts.

**Step-by-step solution.**  
- **Entity:** A "thing" or "object" in the real world that exists and is distinguishable from other objects (e.g., a specific instructor `ID = 22222`, or a student).
- **Attribute:** A descriptive property possessed by all members of an entity set (e.g., `name`, `salary`).

**Explanation of Attribute Types:**

1. **Multi-valued Attribute:**
   - Holds a set of multiple values for a single entity instance.
   - Depicted by a **double ellipse** in Chen notation.
   - *Example:* An instructor may have multiple phone numbers (`phone_numbers` = `{0171..., 0181...}`).

2. **Derived Attribute:**
   - The value is not stored directly. It is computed from stored attributes or system values.
   - Depicted by a **dashed ellipse** in Chen notation.
   - *Example:* `age` derived from current date minus `date_of_birth`.

3. **Composite Attribute:**
   - Can be divided into smaller component attributes with independent meanings.
   - Depicted by an ellipse with attached branches leading to sub-ellipses.
   - *Example:* `name` divided into `first_name`, `middle_initial`, and `last_name`.

**Check.**  
*Quick self-test:*
- Q: Why should `age` not be stored directly as a base attribute?  
  A: Because age changes constantly. Storing it leads to stale data unless updated daily. Deriving it from `date_of_birth` is always accurate.
- Q: What symbol marks a derived attribute in Chen notation?  
  A: A dashed ellipse.

> - Writing that derived attributes are stored in the database. They are typically computed at query time or represented by views.
> - Drawing single ellipses for multivalued attributes instead of double concentric ellipses.

**Question.**
Consider the following E-comerce database:<br>&emsp;client (<u>c_no</u>, name, city, state, Baldue)<br>&emsp;product (<u>p_no</u>, description, profit_percent, quantity, sell_price, cost_price)<br>&emsp;salesman (<u>s_no</u>, name, city, state, sal_amount, target, sold_yearly, remarks)<br>&emsp;order (<u>order_no</u>, client_no, order_date, delivery_address, salesman_no, del_type, del_date, order_status)<br>&emsp;order_details (<u>order_no</u>, product_no, quantity_ordered, product_rate)<br><br>(i) Find the total value of each product sold.<br>(ii) Find the products and their quantities for the orders placed by client no "C0001" and "C0002".<br>(iii) Find the product no and description of the products not being sold.<br>(iv) Find if the product "Lyera Top" has been ordered by any client and print the client_no, name to whom it was sold.<br><br>*(Note: "E-comerce" and "Lyera Top" printed verbatim from original question paper)*

**Answer.**

**What the examiner wants.**  
Four comprehensive queries on a five-table sales database (3 marks each):  
1. Grouped total value calculation ($\sum \text{quantity\_ordered} \times \text{product\_rate}$).  
2. Multi-table join filtering by multiple client keys using `IN ('C0001', 'C0002')`.  
3. Unsold product retrieval using set difference / anti-join (`NOT IN` or `NOT EXISTS`).  
4. Multi-table join across four tables (`client`, `order`, `order_details`, `product`) filtering on a specific product description string.

**Key idea.**  
In MySQL, the table name `order` is a reserved SQL keyword and must be escaped with backticks (`` `order` ``). Unsold products exist in `product` but have zero entries in `order_details`, making `NOT IN` or `NOT EXISTS` the appropriate selection mechanism.

**Step-by-step solution.**  
*(i) Total value of each product sold:*

```sql
SELECT od.product_no,
       p.description,
       SUM(od.quantity_ordered * od.product_rate) AS total_value
FROM order_details od
JOIN product p ON od.product_no = p.p_no
GROUP BY od.product_no, p.description;
```

*(ii) Products and quantities ordered by client "C0001" and "C0002":*

```sql
SELECT o.client_no,
       od.product_no,
       p.description,
       od.quantity_ordered
FROM `order` o
JOIN order_details od ON o.order_no = od.order_no
JOIN product p ON od.product_no = p.p_no
WHERE o.client_no IN ('C0001', 'C0002');
```

*(iii) Product number and description of products not sold:*

```sql
SELECT p_no, description
FROM product
WHERE p_no NOT IN (
    SELECT DISTINCT product_no
    FROM order_details
);
```

*(Alternative using `NOT EXISTS`:*
```sql
SELECT p.p_no, p.description
FROM product p
WHERE NOT EXISTS (
    SELECT 1
    FROM order_details od
    WHERE od.product_no = p.p_no
);
```
*)*

*(iv) Check if "Lyera Top" was ordered and display client number and name:*

```sql
SELECT DISTINCT c.c_no, c.name
FROM client c
JOIN `order` o ON c.c_no = o.client_no
JOIN order_details od ON o.order_no = od.order_no
JOIN product p ON od.product_no = p.p_no
WHERE p.description = 'Lyera Top';
```

**Check.**  
*Trace of part (iii) anti-join:*
- Suppose `product` has keys $\{P01, P02, P03\}$.
- Suppose `order_details` records sales for $\{P01, P02\}$.
- The subquery `SELECT DISTINCT product_no FROM order_details` returns $\{P01, P02\}$.
- `WHERE p_no NOT IN ({P01, P02})` evaluates to true only for $P03$. Product $P03$ is correctly reported.

> [!warning] Common mistakes
> - Writing `FROM order` without backticks in MySQL; `ORDER` is a reserved keyword for `ORDER BY` and triggers a parse error.
> - Using an `INNER JOIN` between `product` and `order_details` in part (iii); an inner join only matches sold products and can never find unsold products.
> - Altering the printed spelling "Lyera Top" in part (iv); keep the exact string literal from the question paper.

**Question.**
What is ER diagram? Illustrate different types of relationship that can be represented in ER diagram.

**Answer.**

**What the examiner wants.**  
A concise definition of an Entity-Relationship (E-R) diagram (1 mark). An explanation and illustration of relationship types classified by their degree: unary (recursive), binary, and ternary (3 marks).

**Key idea.**  
An E-R diagram models a business enterprise visually. It maps entities as rectangles, attributes as ellipses, and relationships as diamonds. The degree tells you how many entity sets take part in a relationship. Binary is by far the most common, but unary and ternary also exist.

**Step-by-step solution.**  
An **Entity-Relationship (E-R) diagram** is a graphical tool used in database design. It represents the conceptual schema of an enterprise by depicting entities, their attributes, and the relationships among them.

The **degree** of a relationship set is the number of participating entity sets. Different types of relationships based on degree include:

1. **Unary (Recursive) Relationship (Degree 1):**
   - The same entity set participates more than once in different roles.
   - *Example:* A `course` entity related to another `course` entity via a `prereq` relationship (roles: `course_id` and `prereq_id`).

2. **Binary Relationship (Degree 2):**
   - Involves two distinct entity sets. This is the most common relationship type.
   - *Example:* `instructor` and `student` linked by the `advisor` relationship.

3. **Ternary Relationship (Degree 3):**
   - Involves three distinct entity sets simultaneously.
   - *Example:* `proj_guide` linking `instructor`, `student`, and `project`.

| Relationship Type | Degree | Description | Example |
| :--- | :---: | :--- | :--- |
| **Unary (Recursive)** | 1 | Association among entities of the same entity set | Course $\xrightarrow{\text{prereq}}$ Course |
| **Binary** | 2 | Association between two distinct entity sets | Instructor $\xrightarrow{\text{advisor}}$ Student |
| **Ternary** | 3 | Association among three distinct entity sets | Instructor, Student, Project $\xrightarrow{\text{proj\_guide}}$ |
| **$n$-ary** | $n$ | Association among $n$ entity sets | Rare; usually decomposed into binary |

**Check.**  
*Quick self-test:*
- Q: What is the degree of a recursive relationship?  
  A: It is 1 (unary), because only one entity set participates, even though entities take on distinct roles.
- Q: Can an $n$-ary relationship always be converted to binary relationships?  
  A: Yes. An artificial entity set can replace the $n$-ary diamond by connecting to each entity set via binary relationships.

> [!warning] Common mistakes
> - Confusing relationship types based on degree (unary, binary, ternary) with mapping cardinalities (1:1, 1:N, M:N). If asked for relationship types, degree is the primary classification.
> - Forgetting role indicators in unary relationships. A recursive relationship requires distinct role labels like `prereq_id` and `course_id`.

**Exam tip.**

### Q.5(b) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.4 · Attribute closure $X^+$, $F^+$, finding candidate keys|T08.4 · Attribute closure $X^+$, $F^+$, finding candidate keys]] · Section B* · CLO1

**Question.**
Compute the closure of the following set F of functional dependencies for relational schema r (A, B, C, D, E).<br><br>&emsp;$A \to BC$<br>&emsp;$CD \to E$<br>&emsp;$B \to D$<br>&emsp;$E \to A$<br><br>List the candidate Keys for R.

**Answer.**

**What the examiner wants.**  
Demonstrating the closure computation of functional dependencies (2 marks), followed by finding all candidate keys with proof of minimality (2 marks).

**Key idea.**  
Computing the full set $F^+$ on a 5-attribute schema yields hundreds of dependencies. In an exam, state that $F^+$ is too large to write in its entirety, compute the attribute closures of single attributes and relevant combinations, and derive key non-trivial dependencies using Armstrong's axioms. Then identify all minimal attribute sets whose closure is $\{A, B, C, D, E\}$.

**Step-by-step solution.**

#### 1. Closure of Functional Dependencies ($F^+$)

The complete closure $F^+$ contains over one hundred trivial and non-trivial dependencies, which is too large to write out fully.

We compute the attribute closures of each single attribute and pair under $F$:

1. **$A^+$:**
   - Initial: $\{A\}$
   - Using $A \rightarrow BC$: $\{A, B, C\}$
   - Using $B \rightarrow D$: $\{A, B, C, D\}$
   - Using $CD \rightarrow E$: $\{A, B, C, D, E\}$
   - Result: $A^+ = \{A, B, C, D, E\}$

2. **$B^+$:**
   - Initial: $\{B\}$
   - Using $B \rightarrow D$: $\{B, D\}$
   - Result: $B^+ = \{B, D\}$

3. **$C^+$:**
   - No FD has $C$ on the LHS alone.
   - Result: $C^+ = \{C\}$

4. **$D^+$:**
   - No FD has $D$ on the LHS alone.
   - Result: $D^+ = \{D\}$

5. **$E^+$:**
   - Initial: $\{E\}$
   - Using $E \rightarrow A$: $\{E, A\}$
   - Since $A^+ = \{A, B, C, D, E\}$: $\{A, B, C, D, E\}$
   - Result: $E^+ = \{A, B, C, D, E\}$

6. **Key Two-Attribute Closures:**
   - $BC^+$: Using $B \rightarrow D$, we get $\{B, C, D\}$. Using $CD \rightarrow E$, we get $\{B, C, D, E\}$. Using $E \rightarrow A$, we get $\{A, B, C, D, E\}$. So $BC^+ = \{A, B, C, D, E\}$.
   - $CD^+$: Using $CD \rightarrow E$, we get $\{C, D, E\}$. Using $E \rightarrow A$, we get $\{A, C, D, E\}$. Using $A \rightarrow BC$, we get $\{A, B, C, D, E\}$. So $CD^+ = \{A, B, C, D, E\}$.

**Key Non-Trivial Functional Dependencies in $F^+$ (derived using Armstrong's Axioms):**
- $A \rightarrow D$ (by Decomposition of $A \rightarrow BC$ to $A \rightarrow B$, then Transitivity with $B \rightarrow D$).
- $A \rightarrow E$ (by Transitivity from $A \rightarrow CD$ and $CD \rightarrow E$).
- $E \rightarrow B, E \rightarrow C, E \rightarrow D$ (by Transitivity from $E \rightarrow A$ and $A \rightarrow BCDE$).
- $BC \rightarrow E$ (by Augmentation of $B \rightarrow D$ to $BC \rightarrow CD$, then Transitivity with $CD \rightarrow E$).
- $CD \rightarrow A, CD \rightarrow B$ (by Transitivity from $CD \rightarrow E$, $E \rightarrow A$, and $A \rightarrow B$).

#### 2. Candidate Keys for $R$

A candidate key is a minimal set of attributes whose closure contains all attributes $\{A, B, C, D, E\}$.

- $A^+ = \{A, B, C, D, E\} \implies \{A\}$ is a candidate key.
- $E^+ = \{A, B, C, D, E\} \implies \{E\}$ is a candidate key.
- $BC^+ = \{A, B, C, D, E\}$, while neither $B^+$ nor $C^+$ is a superkey $\implies \{BC\}$ is a candidate key.
- $CD^+ = \{A, B, C, D, E\}$, while neither $C^+$ nor $D^+$ is a superkey $\implies \{CD\}$ is a candidate key.

$$
\text{Candidate Keys} = \{A\}, \{E\}, \{BC\}, \{CD\}
$$

**Check.**  
*Verification of Candidate Keys:*
- Single attribute keys: $A$ and $E$ have closures equal to $R$. They are single attributes, so minimality is trivial.
- Pair keys: $BC^+ = R$, and proper subsets $B^+ = \{B, D\} \neq R$, $C^+ = \{C\} \neq R$. Thus $BC$ is minimal.
- Pair keys: $CD^+ = R$, and proper subsets $C^+ = \{C\} \neq R$, $D^+ = \{D\} \neq R$. Thus $CD$ is minimal.
- Are there other keys? Attributes not determined by anything except keys: $C$ appears on no LHS and is only determined by $A$ and $E$. So any key without $A$ or $E$ must contain $C$. With $C$, we need $B$ or $D$ to derive the rest. Thus exactly four keys exist.

> [!warning] Common mistakes
> - Spending 20 minutes trying to list all FDs in $F^+$. State clearly that $F^+$ is too large, then show the attribute closures and derived non-trivial FDs.
> - Missing $BC$ or $CD$ as candidate keys because they consist of two attributes.
> - Including non-minimal superkeys like $AB$ or $AC$ as candidate keys.

**Exam tip.**  
Compute single-attribute closures first. Once you see that $A^+ = R$ and $E^+ = R$, you already have two candidate keys. Then test pairs containing $C$.

### Q.5(c) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.7 · 2NF test from an FD set|T08.7 · 2NF test from an FD set]] · Section B* · CLO1

**Question.**
Given a relation R (A, B, C, D) and functional dependency at FD = { AB $\to$ CD, B $\to$ C }. Determine whether the given R is in 2NF? If not, convert it into 2NF.<br><br>*(Note: "functional dependency at FD" printed verbatim from original question paper)*

**Answer.**

**What the examiner wants.**  
Candidate key derivation and attribute classification (1 mark), identification of the partial dependency violating 2NF (1.5 marks), and correct decomposition into 2NF relations with candidate keys identified (1.5 marks).

**Key idea.**  
Candidate key is $AB$. The dependency $B \rightarrow C$ has $B$ on its left, which is only part of the key $AB$. Because $C$ is a non-prime attribute depending on half the key, it is a partial dependency. Decompose to isolate $B \rightarrow C$ into its own relation.

**Step-by-step solution.**

#### 1. Determine Candidate Key and Attribute Types

Given relation $R(A, B, C, D)$ and functional dependencies:
$$
FD = \{AB \rightarrow CD, B \rightarrow C\}
$$

- Attribute $A$ never appears on the right-hand side of any dependency. Thus, every candidate key must contain $A$.
- Compute closure of $AB$:
$$
AB^+ = \{A, B, C, D\}
$$
- Test proper subsets:
  - $A^+ = \{A\}$
  - $B^+ = \{B, C\}$
  Neither subset is a superkey. Therefore, $AB$ is minimal.

$$
\text{Candidate Key} = \{AB\}
$$
$$
\text{Prime Attributes} = \{A, B\}
$$
$$
\text{Non-Prime Attributes} = \{C, D\}
$$

#### 2. Test for Second Normal Form (2NF)

A relation is in 2NF if it is in 1NF and no non-prime attribute depends on a proper subset of any candidate key.

Examine the dependencies:
1. $AB \rightarrow CD$: The determinant $AB$ is the complete candidate key. This is a **full functional dependency**.
2. $B \rightarrow C$: The determinant $B$ is a proper subset of candidate key $AB$, and $C$ is a non-prime attribute. This is a **partial functional dependency**.

Because a partial dependency exists ($B \rightarrow C$), **the relation $R$ is NOT in 2NF**.

#### 3. Conversion to 2NF

To achieve 2NF, we decompose $R$ by isolating the partial dependency into its own relation:

1. Create a relation for the partial dependency:
$$
R_1(B, C) \quad \text{with } FD_1 = \{B \rightarrow C\}
$$
$$
\text{PK of } R_1 = B
$$

2. Remove the determined attribute $C$ from the original relation:
$$
R_2(A, B, D) \quad \text{with } FD_2 = \{AB \rightarrow D\}
$$
$$
\text{PK of } R_2 = AB
$$

**Verification:**
- In $R_1(B, C)$, the candidate key is $B$. The non-prime attribute $C$ depends on the entire key. $R_1$ is in 2NF.
- In $R_2(A, B, D)$, the candidate key is $AB$. The non-prime attribute $D$ depends on the full key $AB$. $R_2$ is in 2NF.
- Lossless join: $R_1 \cap R_2 = \{B\}$, which is the primary key of $R_1$. Thus, the decomposition is lossless.

$$
\boxed{\text{Decomposed 2NF Relations: } R_1(B, C) \text{ and } R_2(A, B, D)}
$$

**Check.**  
*Decomposition property check:*
- Attribute union: $R_1 \cup R_2 = \{B, C\} \cup \{A, B, D\} = \{A, B, C, D\} = R$.
- Common attributes: $R_1 \cap R_2 = \{B\}$.
- Since $B$ is the candidate key of $R_1$, the intersection is a superkey of $R_1$. The decomposition is guaranteed to be lossless!

> [!warning] Common mistakes
> - Leaving attribute $C$ inside $R_2$, producing $(A, B, C, D)$ and $(B, C)$, which fails to eliminate the partial dependency from the main relation.
> - Forgetting to state the candidate key of each newly formed relation.

**Exam tip.**  
Always show the intersection $R_1 \cap R_2$ and state that it forms a key for $R_1$. This proves your decomposition is lossless.

### Q.6(b) · 05 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.5 · Canonical cover $F_c$ (and how it differs from normalization)|T08.5 · Canonical cover $F_c$ (and how it differs from normalization)]] · Section B* · CLO1

**Question.**
Define Functional dependency. Consider the following functional dependency set:<br><br>&emsp;$\text{FD} = \{$<br>&emsp;&emsp;$A \to BC,$<br>&emsp;&emsp;$CD \to E,$<br>&emsp;&emsp;$B \to D,$<br>&emsp;&emsp;$E \to A$<br>&emsp;$\}$<br><br>Find the canonical form of the FD set.

**Answer.**

**What the examiner wants.**  
Formal mathematical definition of functional dependency (2 marks), followed by a complete step-by-step canonical cover derivation: union rule check, extraneous attribute testing on LHS and RHS, and the final canonical set (3 marks).

**Key idea.**  
A canonical cover has no redundant attributes and no redundant dependencies, with each LHS combined. To test if an attribute is extraneous on the RHS, remove it and see if you can still derive it using the remaining dependencies. To test an attribute on the LHS, remove it and see if the reduced LHS can derive the RHS under the original dependencies.

**Step-by-step solution.**

#### 1. Definition of Functional Dependency

A **functional dependency** (FD) is a constraint between two sets of attributes in a relation schema $R$.

Let $\alpha \subseteq R$ and $\beta \subseteq R$. The functional dependency:
$$
\alpha \rightarrow \beta
$$
holds on $R$ if, in every legal relation instance $r(R)$, whenever any two tuples $t_1$ and $t_2$ have the same values for attributes in $\alpha$, they must also have the same values for attributes in $\beta$:
$$
\text{If } t_1[\alpha] = t_2[\alpha] \implies t_1[\beta] = t_2[\beta]
$$

We say $\alpha$ functionally determines $\beta$.

#### 2. Finding the Canonical Cover ($F_c$)

A canonical cover $F_c$ satisfies two conditions:
1. No functional dependency contains an extraneous attribute (on the LHS or RHS).
2. Each left-hand side of a functional dependency is unique.

**Step 1: Apply the Union Rule to combine identical LHS**  
In the given set $F = \{A \rightarrow BC, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$, the left-hand sides are $A, CD, B, E$. All left-hand sides are already unique.

**Step 2: Test for Extraneous Attributes**

1. **Check $A \rightarrow BC$:**
   - **Test attribute $B$ (on RHS):**  
     Form $F' = \{A \rightarrow C, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$.  
     Compute $A^+$ under $F'$:  
     $A^+ = \{A, C\}$.  
     $A^+$ does not contain $B$. Therefore, $B$ is **not extraneous**.
   - **Test attribute $C$ (on RHS):**  
     Form $F' = \{A \rightarrow B, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$.  
     Compute $A^+$ under $F'$:  
     $A^+ = \{A, B, D\}$ (via $A \rightarrow B$ and $B \rightarrow D$).  
     $A^+$ does not contain $C$. Therefore, $C$ is **not extraneous**.

2. **Check $CD \rightarrow E$:**
   - **Test attribute $C$ (on LHS):**  
     Check if $D \rightarrow E$ holds under $F$.  
     Compute $D^+$ under $F$: $D^+ = \{D\}$.  
     $D^+$ does not contain $E$. Therefore, $C$ is **not extraneous**.
   - **Test attribute $D$ (on LHS):**  
     Check if $C \rightarrow E$ holds under $F$.  
     Compute $C^+$ under $F$: $C^+ = \{C\}$.  
     $C^+$ does not contain $E$. Therefore, $D$ is **not extraneous**.

3. **Check $B \rightarrow D$:**  
   Both LHS and RHS have a single attribute. Neither can be removed without dropping the dependency entirely.

4. **Check $E \rightarrow A$:**  
   Both LHS and RHS have a single attribute. Neither can be removed.

**Step 3: Resulting Canonical Cover**  
Since there are no extraneous attributes, the canonical cover is:

$$
\boxed{F_c = \{A \rightarrow BC, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}}
$$

*(Note: In minimal cover form with singleton right-hand sides, the equivalent set is $\{A \rightarrow B, A \rightarrow C, CD \rightarrow E, B \rightarrow D, E \rightarrow A\}$. Both representations are correct.)*

**Check.**  
*Equivalence verification:*
- Every FD in $F_c$ is directly present in $F$, so $F \implies F_c$.
- Every FD in $F$ is directly present in $F_c$, so $F_c \implies F$.
- Thus, $F_c \equiv F$, all LHS are unique, and no attribute is extraneous.

> [!warning] Common mistakes
> - Writing a vague definition of FD without mentioning the tuple comparison ($t_1[\alpha] = t_2[\alpha] \implies t_1[\beta] = t_2[\beta]$).
> - Forgetting the formal difference between testing an attribute on the LHS vs testing on the RHS.
> - Splitting $A \rightarrow BC$ into $A \rightarrow B$ and $A \rightarrow C$ and claiming the split is the final canonical cover. In Silberschatz 7e canonical cover, dependencies with identical LHS must be merged using the union rule.

**Exam tip.**  
Show the closure calculation for each extraneous attribute test explicitly. Even if the answer is "no attribute is extraneous", showing the test proves you know the algorithm.

### Q.7(a) · 04 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T09_Transactions_ACID_and_Anomalies.md#T09.1 · ACID properties (with the \$50 transfer example/diagram)|T09.1 · ACID properties (with the \$50 transfer example/diagram)]] · Section B* · CLO1
*(Repeated question: Also asked in 2017 | Solved in T09)*

**Question.**
Explain the ACID properties of transaction.

**Answer.**

**What the examiner wants.**  
A concise definition of each of the four ACID properties. Examiners look for the specific database subsystem responsible for enforcing each property. The mark split is 1 mark per property (or 0.5 marks each in the 2-mark paper).

**Key idea.**  
A transaction is a logical unit of database work. To keep data safe during crashes and concurrent access, the DBMS treats every transaction as an atomic, isolated unit that leaves data consistent and permanently saved.

**Step-by-step solution.**  
A **transaction** is a logical unit of program execution that accesses and updates data items. To preserve data integrity during crashes and concurrent access, the DBMS must ensure the four **ACID** properties:

1. **Atomicity ("All-or-None"):**
   - Either all operations of the transaction are properly reflected in the database, or none are.
   - If a failure happens before the transaction completes, partial modifications are rolled back.
   - **Enforced by:** The **Recovery System** (using undo log records).

2. **Consistency (Preservation of Invariants):**
   - Executing a transaction in isolation preserves database consistency.
   - The database moves from one valid state to another valid state, satisfying all integrity constraints.
   - In a fund transfer, the total balance sum must remain unchanged.
   - **Enforced by:** The **Application Programmer** (correct business logic) and DBMS **Integrity Constraints**.

3. **Isolation (Shielding Concurrent Access):**
   - Each transaction executes as if it were running alone without interference from other concurrent transactions.
   - Intermediate results remain hidden from other concurrent transactions until commit.
   - **Enforced by:** The **Concurrency-Control System** (using locking or timestamp protocols).

4. **Durability (Persistence):**
   - After a transaction completes successfully and commits, its updates persist in the database permanently.
   - The committed data survives subsequent system crashes or power outages.
   - **Enforced by:** The **Recovery System** (using redo logs and non-volatile stable storage).

*Short version for 2024 Q.6(c) (2 marks):*
- **Atomicity:** All operations complete or none do. The recovery system undoes partial writes.
- **Consistency:** Execution in isolation preserves database validity and invariants.
- **Isolation:** Intermediate updates remain hidden from concurrent transactions.
- **Durability:** Committed changes persist permanently on disk despite crashes.

**Check.**  
*Quick self-test:*
- Q: Which DBMS subsystem enforces atomicity?  
  A: The recovery system, using write-ahead undo logs.
- Q: Who is primarily responsible for consistency?  
  A: The application programmer who codes correct business logic, assisted by DBMS integrity constraints.
- Q: Why is durability not handled by volatile main memory?  
  A: Main memory loses data on power failure. Durability requires writing to stable storage or non-volatile disk logs.

> [!warning] Common mistakes
> - Confusing Atomicity with Isolation. Atomicity handles failure and recovery. Isolation handles concurrent transactions.
> - Stating that the DBMS guarantees consistency automatically without programmer logic. Erroneous application code (like adding \$100 instead of \$50) produces valid SQL that still breaks business invariants.
> - Forgetting to name the enforcing subsystem for each property.

**Exam tip.**  
Start each bullet with the letter of the acronym, bold the property name, write a one-sentence definition, and end by naming the enforcing component.

*Topic: [[../Topicwise_answers_explaination/T10_Serializability.md#T10.3 · Precedence-graph test → cycle → serial order(s)|T10.3 · Precedence-graph test → cycle → serial order(s)]] · Section B* · CLO3

**Question.**
Define conflict serializability. Check whether the following schedule is a conflict serializable or not.<br><br><table border="1" style="border-collapse: collapse; text-align: center;"><thead><tr><th style="padding: 4px 20px;">$T_1$</th><th style="padding: 4px 20px;">$T_2$</th></tr></thead><tbody><tr><td style="padding: 4px 20px;">read(A)</td><td style="padding: 4px 20px;"></td></tr><tr><td style="padding: 4px 20px;">write(A)</td><td style="padding: 4px 20px;"></td></tr><tr><td style="padding: 4px 20px;"></td><td style="padding: 4px 20px;">read(A)</td></tr><tr><td style="padding: 4px 20px;"></td><td style="padding: 4px 20px;">write(A)</td></tr><tr><td style="padding: 4px 20px;">read(B)</td><td style="padding: 4px 20px;"></td></tr><tr><td style="padding: 4px 20px;">write(B)</td><td style="padding: 4px 20px;"></td></tr><tr><td style="padding: 4px 20px;"></td><td style="padding: 4px 20px;">read(B)</td></tr><tr><td style="padding: 4px 20px;"></td><td style="padding: 4px 20px;">write(B)</td></tr></tbody></table>

**Answer.**

**What the examiner wants.** Formal definition of conflict serializability (1 mark), conflict pair analysis (1.5 marks), precedence graph and serializability test (1 mark), and the equivalent serial order (0.5 marks).

**Key idea.** In this schedule, $T_1$ finishes all operations on $A$ before $T_2$ touches $A$. Then $T_1$ finishes all operations on $B$ before $T_2$ touches $B$. Because $T_1$ precedes $T_2$ on both items and $T_2$ never executes anything before $T_1$, all directed edges flow strictly from $T_1$ to $T_2$. There can be no cycles.

**Step-by-step solution.**

#### 1. Definition

A schedule $S$ is **conflict serializable** if it is conflict equivalent to some serial schedule. Two schedules are conflict equivalent if one can be transformed into the other by a sequence of non-conflicting adjacent instruction swaps.

#### 2. Detailed Conflict Trace

We examine the 8 operations in order:
- Operations on $A$:
  1. $T_1: \text{read}(A)$
  2. $T_1: \text{write}(A)$
  3. $T_2: \text{read}(A)$
  4. $T_2: \text{write}(A)$
- Operations on $B$:
  5. $T_1: \text{read}(B)$
  6. $T_1: \text{write}(B)$
  7. $T_2: \text{read}(B)$
  8. $T_2: \text{write}(B)$

Conflicting pairs:
- **On item $A$:**
  - $T_1: \text{read}(A)$ before $T_2: \text{write}(A) \implies T_1 \to T_2$
  - $T_1: \text{write}(A)$ before $T_2: \text{read}(A) \implies T_1 \to T_2$
  - $T_1: \text{write}(A)$ before $T_2: \text{write}(A) \implies T_1 \to T_2$
- **On item $B$:**
  - $T_1: \text{read}(B)$ before $T_2: \text{write}(B) \implies T_1 \to T_2$
  - $T_1: \text{write}(B)$ before $T_2: \text{read}(B) \implies T_1 \to T_2$
  - $T_1: \text{write}(B)$ before $T_2: \text{write}(B) \implies T_1 \to T_2$

Every single conflict edge goes from $T_1$ to $T_2$. No operation in $T_2$ precedes any conflicting operation in $T_1$.

#### 3. Precedence Graph

![2021 Q.7(b) Precedence Graph showing single edge T1 to T2](diagrams/T10_2021_Q7b_precedence_graph.jpg)

The graph contains two vertices $\{T_1, T_2\}$ and a single directed edge:
$$
T_1 \longrightarrow T_2
$$

The graph is **acyclic**.

**Result:** The schedule is **conflict serializable**. The unique equivalent serial schedule is:
$$
\boxed{\langle T_1, T_2 \rangle}
$$

**Check.**
- Notice that in this schedule, all $T_1$ operations on $A$ occur first, then $T_2$ on $A$, then $T_1$ on $B$, then $T_2$ on $B$.
- By swapping $T_2$'s operations on $A$ with $T_1$'s operations on $B$ (which do not conflict because $A \neq B$), the schedule becomes strictly $\langle T_1, T_2 \rangle$. This confirms conflict serializability.

> [!warning] Common mistakes
> - Missing the definition part of the question. The question explicitly starts with "Define conflict serializability."
> - Thinking this is already a serial schedule. It is interleaved: $T_2$ operates on $A$ before $T_1$ operates on $B$. It is a concurrent schedule that is serializable.

**Exam tip.** Always explicitly state the equivalent serial order $\langle T_1, T_2 \rangle$ whenever you conclude that a schedule is serializable.

### Q.8(a) · 05 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T11_Concurrency_Control_Protocols.md#T11.4 · Deadlock: conditions, prevention vs detection, wait-for graph, victim selection|T11.4 · Deadlock: conditions, prevention vs detection, wait-for graph, victim selection]] · Section B* · CLO1

**Question.**
What is deadlock? Consider the following wait-for-graph:<br><br>![Wait-for-graph for Q.8(a)](diagrams/2021_p02_fig01.jpg)<br><br>Determine whether the schedule contains any deadlock or not.<br><br>*(Refer to the Wait-for-Graph Diagram and Detailed Text Representation below)*

**Answer.**

**What the examiner wants.**  
The definition of deadlock (1 mark), followed by a graph analysis of the provided wait-for graph: listing vertices and edges (1 mark), detecting the cycle (1.5 marks), giving the verdict and identifying the deadlocked transactions (1 mark), and explaining how to break the deadlock (0.5 marks).

**Key idea.**  
A wait-for graph models who is waiting for whom. An arrow from $T_i$ to $T_j$ means $T_i$ is waiting for $T_j$ to release a lock. If you can follow arrows and return to where you started, you have a directed cycle. A cycle equals a deadlock. In this graph, $T_4 \to T_5 \to T_2 \to T_4$ forms a loop.

**Step-by-step solution.**  
**1. Deadlock Definition:**  
A deadlock is a situation where two or more transactions wait indefinitely for resources or data locks held by one another. None can continue without intervention.

**2. Graph Structure:**  
From the diagram:
- **Vertices (Transactions):** $V = \{T_1, T_2, T_3, T_4, T_5\}$
- **Directed Edges:** $E = \{(T_1, T_4), (T_1, T_2), (T_1, T_3), (T_4, T_5), (T_5, T_2), (T_2, T_4)\}$

A directed edge $T_i \to T_j$ indicates that transaction $T_i$ is waiting for a lock currently held by $T_j$.

**3. Cycle Detection:**  
We examine the paths in the graph:
- $T_4$ waits for $T_5$ (edge $T_4 \to T_5$)
- $T_5$ waits for $T_2$ (edge $T_5 \to T_2$)
- $T_2$ waits for $T_4$ (edge $T_2 \to T_4$)

These three edges form a closed directed cycle:

$$
\mathbf{T_4 \to T_5 \to T_2 \to T_4}
$$

**4. Verdict:**  
**Yes, the schedule contains a deadlock.**

**Deadlocked Transactions:**  
Transactions $\mathbf{T_2, T_4, \text{ and } T_5}$ are deadlocked.  
*Note on remaining transactions:* Transaction $T_1$ has outgoing edges to $T_2, T_3$, and $T_4$. It is blocked waiting for them, but it is not part of the cycle. Transaction $T_3$ has no outgoing edges and is not blocked.

**5. Deadlock Resolution:**  
The DBMS must resolve the deadlock by:
1. **Victim Selection:** Choose one transaction from the cycle ($T_2, T_4$, or $T_5$) that minimizes rollback cost.
2. **Rollback:** Abort or partially roll back the victim transaction to release its locks.
3. Breaking any single edge in the cycle breaks the loop, allowing the remaining transactions to finish.

**Check.**  
*Cycle verification:*
- $T_4 \to T_5 \implies T_4$ blocked on $T_5$.
- $T_5 \to T_2 \implies T_5$ blocked on $T_2$.
- $T_2 \to T_4 \implies T_2$ blocked on $T_4$.
- Returning to $T_4$ proves circular wait. Cycle length is 3. Deadlock is confirmed.

> [!warning] Common mistakes
> - Listing $T_1$ or $T_3$ as part of the deadlock cycle. $T_1$ points into the cycle, but no edge returns to $T_1$. $T_3$ has no outgoing edges. Only $T_2, T_4, T_5$ form the cycle.
> - Saying "no deadlock" because $T_3$ can finish. If any subset forms a cycle, the system contains a deadlock.
> - Forgetting to state how the deadlock is broken.

**Exam tip.**  
Explicitly write out the cycle $T_4 \to T_5 \to T_2 \to T_4$ and state the three specific transactions involved.

### Q.8(b) · 05 Marks · CLO4

*Topic: [[../Topicwise_answers_explaination/T13_Security_Indexing_and_Hashing.md#T13.2 · SQL injection: how it works + prevention|T13.2 · SQL injection: how it works + prevention]] · Section B* · CLO4

**Question.**
What is SQL injection attack? Describe the precautions that should be taken to prevent this attack.

**Answer.**

**What the examiner wants.**  
Definition of SQL injection (1 mark), a concrete example of how the attack operates (1.5 to 2 marks), and comprehensive technical precautions for prevention (2 marks).

**Key idea.**  
SQL injection happens because the database cannot tell code apart from data when strings are glued together. Prepared statements separate the code structure (precompiled query plan) from the data (parameters). Even if a parameter contains SQL keywords or quotes, the database treats it only as a literal string.

**Step-by-step solution.**  

**1. What is an SQL Injection Attack?**  
An **SQL injection attack** occurs when an attacker inputs malicious SQL commands into an application input field. The application concatenates this untrusted input directly into a dynamic SQL query string. The database parser interprets the malicious input as SQL instructions rather than data. This allows the attacker to bypass authentication, read unauthorized data, or modify and delete tables.

**2. How It Works**  
Consider an application that builds a query using string concatenation:

```python
# Vulnerable query construction
query = "SELECT * FROM instructor WHERE name = '" + user_input + "'"
```

- **Scenario 1: Authentication Bypass / Data Dumping**
  - **Attacker input:** `' OR '1'='1`
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = '' OR '1'='1';
    ```
  - **Mechanism:** The quote closes the name literal. The `'1'='1'` condition is always true. The database returns all records in the `instructor` table.

- **Scenario 2: Destructive Attack (Piggybacked Query)**
  - **Attacker input:** `'; DROP TABLE student; -- `
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = ''; DROP TABLE student; -- ';
    ```
  - **Mechanism:** The semicolon terminates the first query. The database engine executes the injected `DROP TABLE student` statement. The trailing `--` treats the remaining query syntax as a comment.

**3. Precautions to Prevent SQL Injection**  

1. **Use Prepared Statements (Parameterized Queries):**
   This is the primary defense. The application precompiles the SQL query structure with placeholders. User input is bound separately as data parameters. The parser never executes parameter content as SQL commands.
   ```python
   # Secure parameterized query
   cursor.execute("SELECT * FROM instructor WHERE name = %s", (user_input,))
   ```
   In Java/JDBC, use `PreparedStatement` with `?` markers and `setString()`.

2. **Input Validation and Whitelisting:**
   Validate data types, lengths, and patterns before passing them to queries. For dynamic query parts like table or column names that cannot use parameters, check input against an explicit whitelist of allowed identifiers.

3. **Enforce Least Privilege:**
   Configure database user accounts with minimal necessary privileges. A public web application account should only have `SELECT` or `INSERT` access. It must never have administrative permissions like `DROP TABLE` or `GRANT`.

4. **Use Parameterized Stored Procedures:**
   Wrap database operations inside stored procedures with typed parameters. Do not concatenate dynamic SQL inside the stored procedure body.

5. **Suppress Database Error Messages:**
   Hide internal database error details, table names, and stack traces from end users. Display generic error pages instead.

*Short version for 2020 Q.4(a) (4 marks):* Provide the definition, the `' OR '1'='1` exploit example, and the three core precautions: prepared statements, input validation, and least privilege.

**Check.**  
*Replaying the attack in a prepared statement:*
- If an attacker submits `' OR '1'='1` into `cursor.execute("SELECT * FROM instructor WHERE name = %s", (user_input,))`, the database searches for an instructor whose literal name is the exact 10-character string `' OR '1'='1`.
- Because no instructor has that literal name, the query safely returns 0 rows.

*Quick self-test:*
- Q: Why is escaping quotes less reliable than prepared statements?  
  A: Hand-crafted escaping functions often miss edge cases, like second-order injection or multibyte character encodings.
- Q: Can prepared statements parameterize table names or `ORDER BY` columns?  
  A: No. SQL parameters only work for data literals. Table and column names must be validated against a strict whitelist.

> [!warning] Common mistakes
> - Confusing SQL injection with cross-site scripting (XSS). XSS executes scripts in the user browser; SQL injection executes queries in the database engine.
> - Claiming that client-side validation (like HTML5 form attributes) prevents SQL injection. Attackers bypass browsers completely using tools like `curl`.
> - Forgetting to show both the input string and the resulting modified SQL statement.

**Exam tip.**  
Always show the input `' OR '1'='1` and the resulting query where `'1'='1'` makes the `WHERE` clause tautological. This guarantees full marks on "how it works".

### Q.8(c) · 02 Marks · CLO1

*Topic: [[../Topicwise_answers_explaination/T02_ER_and_EER_Modeling.md#T02.4 · Weak vs strong entity sets (discriminator, identifying relationship)|T02.4 · Weak vs strong entity sets (discriminator, identifying relationship)]] · Section B* · CLO1
*(Repeated question: Also asked in 2018 | Solved in T02)*

**Question.**
Explain weak and strong entity set with appropriate example.

**Answer.**

**What the examiner wants.**  
Definition of an entity set (1 mark). Comprehensive comparison and explanation of strong vs weak entity sets (2 marks). Concrete examples showing the identifying relationship, discriminator, and composite primary key (1 mark).

**Key idea.**  
A strong entity set has enough attributes to tell every record apart. A weak entity set does not. A weak entity depends on an owner entity for its existence and identity. Its key is formed by taking the owner's primary key and attaching its own partial key (discriminator).

**Step-by-step solution.**  
**Entity Set:**  
An entity set is a collection of entities of the same type that share the same properties or attributes (e.g., the set of all students in a university).

| Feature | Strong Entity Set | Weak Entity Set |
| :--- | :--- | :--- |
| **Primary Key** | Has sufficient attributes to form its own primary key. | Lacks a primary key of its own. Uses a partial key (discriminator). |
| **Existence Dependency** | Independent. Does not depend on another entity set. | Existence-dependent on an identifying (strong) entity set. |
| **E-R Notation** | Single rectangle. | Double rectangle. |
| **Relationship Set** | Connected via regular relationship (single diamond). | Connected via identifying relationship (double diamond). |
| **Discriminator Key** | None (uses full primary key underlined with solid line). | Has a discriminator underlined with a dashed line. |
| **Composite PK** | Its own primary key. | Formed by (Owner Primary Key + Discriminator). |
| **Example** | `course` with primary key `course_id`. | `section` with discriminator `sec_id`, `semester`, `year`. |

![Weak entity set section connected to identifying strong entity set course via sec_course](../LectureSlides/diagrams/L05_p37_fig01.jpg)
*Figure: Expressing Weak Entity Sets in ER Diagram (Deck 05, Slide 37)*

- **Strong Entity Set Example:** `course` has attributes `course_id` (PK), `title`, `credits`. It exists independently.
- **Weak Entity Set Example:** `section` has attributes `sec_id`, `semester`, `year`. A section number like `Sec 1` is meaningless without knowing the course. Its full primary key is `(course_id, sec_id, semester, year)`.

*Short version for 2020 Q.2(c) and 2021 Q.8(c) (2 marks):*  
State the comparison table rows (Primary Key, Dependency, Notation, Example) and omit the separate entity set definition.

**Check.**  
*Quick self-test:*
- Q: What happens to a section tuple if the corresponding course tuple is deleted?  
  A: Because the section is existence-dependent, the section tuple must also be deleted (cascading delete).
- Q: How is a discriminator underlined in an E-R diagram?  
  A: With a dashed line.

> [!warning] Common mistakes
> - Thinking a weak entity set has no key attributes at all. It does have a discriminator (partial key).
> - Forgetting the double diamond for the identifying relationship. Drawing a single diamond loses marks.

**Exam tip.**  
Always mention the standard textbook example (`course` and `section`). Show the exact composite primary key formula.
