### Q.1(a) · 04 Marks · 1

*Topic: [[Topicwise_answers_explaination/T01_DB_Concepts_and_Architecture.md#T01.2 · File system vs DBMS|T01.2 · File system vs DBMS]] · Section A* · 1

**Question.**
A courier tracking company maintains large files for daily parcel updates. The data grows rapidly and requires fast retrieval. Choose between a file based system and a DBMS and justify the decision.

**Answer.**

**What the examiner wants.**  
An explicit recommendation (DBMS) and a justification directly using the scenario's facts: rapid data growth, fast retrieval, concurrent tracking updates, and data reliability. Mark split: 1 mark for the decision, 3 marks for linking scenario facts to technical justifications.

**Key idea.**  
A courier tracking service handles thousands of package updates and queries every hour. A file system would degrade rapidly because searching through growing flat files requires linear scans, and concurrent writes cause file corruption or severe locking delays. A DBMS provides indexing, concurrency control, and scalability.

**Step-by-step solution.**  
**Decision:** Choose a **DBMS (Database Management System)**.

**Justification:**
1. **Rapid Data Growth and Scalability:** As parcel records grow rapidly each day, a DBMS manages storage dynamically with tables and secondary storage. A file system suffers from large unwieldy files, data isolation, and slow sequential processing.
2. **Fast Retrieval via Indexing:** Customers and couriers need instant tracking updates. A DBMS builds B+ tree indexes on tracking numbers (`parcel_id`). This delivers lookup results in milliseconds instead of scanning large files line by line.
3. **Concurrent Multi-User Updates:** Delivery drivers, sorting hubs, and recipients update and read parcel records at the same time. A DBMS provides concurrency control to prevent lost updates and race conditions. A file system would require file locking, which blocks other users.
4. **Data Integrity and Constraints:** A DBMS automatically enforces rules. For example, status codes must be valid, and tracking IDs cannot be null or duplicated. File systems require custom application code to check every update.
5. **Crash Recovery and Backup:** Courier data cannot be lost during system crashes or power failures. A DBMS maintains write-ahead logs (WAL) and automatic transaction rollback to preserve tracking history.

**Check.**  
*Scenario link verification:*
- Fact: "Large files / grows rapidly" $\rightarrow$ Handled by DBMS dynamic page allocation and relational tables.
- Fact: "Requires fast retrieval" $\rightarrow$ Handled by B+ tree index lookups on parcel IDs.
- Operational reality: Couriers updating statuses on the road $\rightarrow$ Handled by row-level locking and ACID transactions.

> [!warning] Common mistakes
> - Writing a generic textbook essay about DBMS without mentioning the courier scenario.
> - Forgetting to state the decision explicitly in the opening line.

**Exam tip.**  
Start with a bold decision line. Then quote the scenario requirements directly in your justification bullet points.

### Q.1(c) · 04 Marks · 2

*Topic: [[Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.5 · Aggregation queries: GROUP BY + HAVING, CGPA, extremes without LIMIT|T05.5 · Aggregation queries: GROUP BY + HAVING, CGPA, extremes without LIMIT]] · Section A* · 2

**Question.**
STUDENT (SID, Name, Age, Major)<br>COURSE (CID, Title, Credits)<br>ENROLLMENT (SID, CID, Grade)<br>Using the above schema, write a SQL query to find the average grade for each course.

**Answer.**

**What the examiner wants.**  
A clean SQL aggregation query using `AVG(Grade)` grouped by course identifier (`CID`).

**Key idea.**  
The `ENROLLMENT` table contains both the course identifier (`CID`) and the student's grade (`Grade`). Grouping by `CID` allows `AVG()` to compute the arithmetic mean per course without requiring a join to other relations.

**Step-by-step solution.**  
```sql
SELECT CID,
       AVG(Grade) AS avg_grade
FROM ENROLLMENT
GROUP BY CID;
```

*(If course title is also retrieved by joining COURSE):*

```sql
SELECT c.CID, c.Title,
       AVG(e.Grade) AS avg_grade
FROM COURSE c
JOIN ENROLLMENT e ON c.CID = e.CID
GROUP BY c.CID, c.Title;
```

**Check.**  
*Trace:*
- If CID 'ECE2215' has three enrollment records with grades 3.5, 3.75, and 4.0, `AVG(Grade)` yields $\frac{3.5 + 3.75 + 4.0}{3} = 3.75$.
- Output relation contains `(CID, avg_grade)`.

> [!warning] Common mistakes
> - Joining `STUDENT` unnecessarily; `STUDENT` attributes are not required to compute course averages.
> - Omitting `GROUP BY CID`; without `GROUP BY`, `AVG(Grade)` computes the grand average across all courses combined into a single number.

**Exam tip.**  
Provide the direct single-table query first; append the joined version with `Title` as an alternative if descriptive course names are desired.

### Q.2(a) · 03 Marks · 2

*Topic: [[Topicwise_answers_explaination/T07_Triggers_and_Stored_Procedures.md#T07.2 · Triggers for security before and after a breach|T07.2 · Triggers for security before and after a breach]] · Section A* · 2
*(Repeated question: Also asked in 2017 | Solved in T07)*

**Question.**
Discuss how trigger can contribute to the security of database before and after a security breach. Explain with example.

**Answer.**

**What the examiner wants.**  
A structured analysis of database security in two distinct operational phases: prevention before a breach (2.5 marks) and auditing or forensics after a breach (2.5 marks). Both parts must provide practical SQL trigger examples.

**Key idea.**  
Think of `BEFORE` triggers as security guards stationed at the door. They check identity and inspect the request before letting changes touch the table. If anything looks wrong, they block the action on the spot. Think of `AFTER` triggers as security cameras. Once an action takes place, they record an unalterable log of who did what and when. This allows investigators to analyze the damage later.

**Step-by-step solution.**  

Triggers protect database security at two stages: proactive prevention before a breach and forensic auditing after a breach.

#### 1. Before a Security Breach: Prevention via BEFORE Triggers

`BEFORE` triggers act as real-time security gatekeepers. They evaluate incoming data modifications before changes reach the database.

- **Security Role:** They validate user identity, verify business timing, and inspect the values being written. If a policy violation appears, the trigger halts the transaction using `SIGNAL SQLSTATE '45000'`.
- **Key Contributions:**
  - Blocks unauthorized operations outside working hours.
  - Prevents illegal privilege escalation or unauthorized salary updates.
  - Validates and sanitizes input data to stop malicious updates.

**Example (Blocking salary changes outside working hours):**

```sql
DELIMITER //

CREATE TRIGGER trg_prevent_unauthorized_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT = 'Security Alert: Salary edits outside office hours are blocked';
        END IF;
    END IF;
END //

DELIMITER ;
```

#### 2. After a Security Breach: Auditing and Forensics via AFTER Triggers

`AFTER` triggers execute immediately after a modification succeeds on a table.

- **Security Role:** If an attacker bypasses application checks, `AFTER` triggers write the unauthorized changes into an independent audit log table.
- **Key Contributions:**
  - Creates a tamper-evident audit trail capturing `USER()`, `NOW()`, the modified table, and both `OLD` and `NEW` column values.
  - Supplies forensic evidence to pinpoint how and when the attacker breached the system.
  - Helps administrators trace unauthorized modifications and restore corrupted data to its original state.

**Example (Logging security role modifications):**

```sql
DELIMITER //

CREATE TRIGGER trg_audit_role_change
AFTER UPDATE ON user_roles
FOR EACH ROW
BEGIN
    IF OLD.role <> NEW.role THEN
        INSERT INTO security_audit_log (
            user_id, old_role, new_role, changed_by, changed_at
        ) VALUES (
            OLD.user_id, OLD.role, NEW.role, USER(), NOW()
        );
    END IF;
END //

DELIMITER ;
```

*Short version for 2024 Q.2(a) (3 marks):* State how `BEFORE` triggers block unauthorized actions with `SIGNAL` and how `AFTER` triggers record tamper-evident audit logs with `USER()` and timestamps. Provide one concise trigger example.

**Check.**  
*Execution trace comparison:*
1. **Trace 1 (Before breach test):**  
   An unauthorized script executes `UPDATE employees SET salary = salary + 5000 WHERE employee_id = 101;` at 20:30.  
   The `BEFORE UPDATE` trigger checks `CURRENT_TIME()`. The time falls outside the 09:00 to 17:00 window. The trigger raises `SIGNAL SQLSTATE '45000'`. The database rolls back the transaction. The database table remains completely untouched.
2. **Trace 2 (After breach test):**  
   An attacker compromises credentials and runs `UPDATE user_roles SET role = 'admin' WHERE user_id = 42;`.  
   The update succeeds. The `AFTER UPDATE` trigger immediately fires and inserts `(42, 'user', 'admin', 'attacker_session', '2026-10-30 14:15:00')` into `security_audit_log`. The administrator queries this log to detect the breach, identify the compromised account, and revert the unauthorized role change.

> [!warning] Common mistakes
> - Writing general database security points (like firewalls or user passwords) instead of explaining trigger mechanisms.
> - Attempting to use an `AFTER` trigger to block an unauthorized update. By the time an `AFTER` trigger executes, the row modification has already taken place.
> - Forgetting to capture both `OLD` and `NEW` values in the audit table. Without `OLD` values, security administrators cannot revert corrupted data.

**Exam tip.**  
Split your answer cleanly into two bold sections: "Before a Breach (Prevention via BEFORE Triggers)" and "After a Breach (Auditing and Forensics via AFTER Triggers)". Provide one short SQL example for each section.

### Q.2(b) · 04 Marks · 1

*Topic: [[Topicwise_answers_explaination/T04_Relational_Algebra_and_Calculus.md#T04.2 · Write RA queries on a given schema|T04.2 · Write RA queries on a given schema]] · Section A* · 1

**Question.**
EMPLOYEE (EID, Name, Department, Salary)<br>PROJECT (PID, Name, Budget)<br>WORKS_ON (EID, PID, Hours)<br>Suppose a company wants to find employees working on multiple projects. Write the relational algebra expression for it.

**Answer.**

**What the examiner wants.**  
A relational algebra expression worth 4 marks to find employees assigned to more than one project. The examiner expects either aggregation with grouping and threshold filtering ($\gamma$), or classical pure relational algebra using a self-join.

**Key idea.**  
Count the distinct projects per employee. An employee works on multiple projects if their project count exceeds 1. Alternatively, perform a self-join on `WORKS_ON` where the employee ID is the same but the project IDs differ.

**Step-by-step solution.**

**Method 1: Aggregation Operation (Standard Solution)**

1. Group `WORKS_ON` by `EID` and count the project IDs:

$$
T_{\text{counts}} \leftarrow {}_{\text{EID}}\gamma_{\text{count}(\text{PID}) \ \text{as} \ \text{proj\_count}}(\text{WORKS\_ON})
$$

2. Filter for employees associated with more than one project:

$$
T_{\text{multi}} \leftarrow \sigma_{\text{proj\_count} > 1}(T_{\text{counts}})
$$

3. Natural join with `EMPLOYEE` on `EID` to retrieve employee details and project the name:

$$
\boxed{\Pi_{\text{EID}, \text{Name}}(\text{EMPLOYEE} \bowtie T_{\text{multi}})}
$$

**Method 2: Pure Relational Algebra via Self-Join (Classical Alternative)**

1. Take the Cartesian product of `WORKS_ON` with a renamed copy of itself:

$$
W_1 \leftarrow \rho_{W_1}(\text{WORKS\_ON})
$$

$$
W_2 \leftarrow \rho_{W_2}(\text{WORKS\_ON})
$$

2. Select pairs having the same `EID` but different `PID`:

$$
T_{\text{multi\_ids}} \leftarrow \Pi_{W_1.\text{EID}}(\sigma_{W_1.\text{EID} = W_2.\text{EID} \land W_1.\text{PID} \neq W_2.\text{PID}}(W_1 \times W_2))
$$

3. Join with `EMPLOYEE` to retrieve employee names:

$$
\Pi_{\text{EID}, \text{Name}}(\text{EMPLOYEE} \bowtie T_{\text{multi\_ids}})
$$

**Check.**  
Sample data for `WORKS_ON`:
- `(E1, P1, 10)`, `(E1, P2, 15)`, `(E2, P1, 20)`.

- Method 1: E1 has count 2 ($> 1$). E2 has count 1 ($\not> 1$). Join with EMPLOYEE returns E1.
- Method 2: Pairing `(E1, P1)` with `(E1, P2)` matches $E1 = E1$ and $P1 \neq P2$. E1 is selected. E2 has only one project, so no pair with different PID exists.

> [!warning] Common mistakes
> - Forgetting to join with `EMPLOYEE`. `WORKS_ON` contains only `EID`, not employee names.
> - In Method 2, writing $W_1.\text{PID} = W_2.\text{PID}$. That checks if an employee works on the same project twice, not multiple distinct projects.
> - Filtering for `Hours > 1` instead of `count(PID) > 1`.

**Exam tip.**  
Method 1 using $\gamma$ is concise and preferred. Mentioning the self-join method in one sentence shows complete mastery of both modern extended algebra and classical pure algebra.

### Q.2(c) · 03 Marks · 1

*Topic: [[Topicwise_answers_explaination/T09_Transactions_ACID_and_Anomalies.md#T09.2 · Consistency property alone, with example|T09.2 · Consistency property alone, with example]] · Section A* · 1
*(Repeated question: Also asked in 2019 | Solved in T09)*

**Question.**
Explain the consistency property of a database system with a proper example.

**Answer.**

**What the examiner wants.**  
A dedicated discussion of the consistency property. The examiner looks for the distinction between explicit constraints and implicit application invariants, along with a concrete numerical example showing temporary internal inconsistency versus final restored consistency. Mark split: 1 mark for definition/types, 2 marks for the example.

**Key idea.**  
Consistency means preserving truth and valid business invariants. While a transaction is running, the database can be temporarily inconsistent internally. But once the transaction finishes, consistency must be fully restored.

**Step-by-step solution.**  
**Definition:**  
The **consistency** property requires that executing a transaction in isolation preserves the consistency of the database. If the database starts in a valid state that satisfies all integrity rules, it must end in a valid state after the transaction completes.

**Categories of Consistency Constraints:**
1. **Explicit Constraints:** Rules enforced automatically by the DBMS, including primary keys, foreign keys, data types, and `CHECK` constraints (such as `balance >= 0`).
2. **Implicit Invariants:** Business rules that cannot easily be expressed in DDL, such as preserving total assets across account transfers.

**Example (Bank Transfer):**  
Let account $A$ have \$1000 and account $B$ have \$2000. The consistency invariant requires total funds to remain constant:

$$
A + B = 1000 + 2000 = 3000
$$

Transaction $T_1$ transfers \$50 from $A$ to $B$:
1. $\text{read}(A)$
2. $A := A - 50$
3. $\text{write}(A) \quad [A \text{ becomes } 950]$
4. $\text{read}(B)$
5. $B := B + 50$
6. $\text{write}(B) \quad [B \text{ becomes } 2050]$

- **Temporary Inconsistency During Execution:** After step 3, $A = 950$ and $B = 2000$. The sum is $950 + 2000 = 2950$. The database enters a temporarily inconsistent state.
- **Restored Consistency at End:** After step 6 completes, $A = 950$ and $B = 2050$. The sum is $950 + 2050 = 3000$, restoring full consistency.
- **Responsibility:** Ensuring transaction logic is correct is primarily the responsibility of the **application programmer**.

**Check.**  
*Quick self-test:*
- Q: Is the database consistent between step 3 and step 6?  
  A: No. It is temporarily inconsistent internally ($A+B = 2950$).
- Q: Why is this temporary inconsistency acceptable?  
  A: Because isolation prevents other transactions from observing it, and atomicity ensures the entire transaction completes or rolls back.

> [!warning] Common mistakes
> - Believing that database data is consistent at every millisecond during execution. A transaction temporarily breaks consistency while performing intermediate updates.
> - Omitting the distinction between explicit constraints (enforced by DBMS) and implicit invariants (responsibility of the programmer).

**Exam tip.**  
Explicitly state that temporary inconsistency during execution is normal and necessary. The requirement is that consistency is restored when the transaction finishes.

### Q.3(a) · 04 Marks · 2

*Topic: [[Topicwise_answers_explaination/T08_Normalization_and_Functional_Dependencies.md#T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF|T08.8 · Normalize an unnormalized table → 1NF → 2NF → 3NF]] · Section A* · 2

**Question.**
A library database stores information about Books, Authors, Publishers and Borrowers. Create a table that contains some data redundancy and partial dependencies. Also, show the procedure to normalize the table.

**Answer.**

**What the examiner wants.**  
Designing an unnormalized library table that clearly exhibits data redundancy and partial dependencies (2 marks), followed by a clear step-by-step normalization procedure decomposing into 2NF and 3NF relations (2 marks).

**Key idea.**  
Create a table with a composite primary key like `(Book_ID, Borrower_ID)`. Store book details (title, publisher) and borrower details (borrower name) alongside the loan date. Because book details depend only on `Book_ID` and borrower name depends only on `Borrower_ID`, the table has clear partial dependencies and redundancy.

**Step-by-step solution.**

#### 1. Unnormalized / 1NF Table with Redundancy and Partial Dependencies

Consider a single table `LIBRARY_LOAN` designed to store all lending records:

| Book_ID | Borrower_ID | Title | Author_ID | Author_Name | Publisher_Name | Borrower_Name | Borrow_Date |
| :---: | :---: | :--- | :---: | :--- | :--- | :--- | :---: |
| B101 | U01 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Akib | 2024-01-10 |
| B101 | U02 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Shuvo | 2024-02-15 |
| B202 | U01 | Operating Systems | A1 | Silberschatz | Wiley | Akib | 2024-03-01 |

**Primary Key:** `(Book_ID, Borrower_ID)`

**Functional Dependencies:**
- `Book_ID -> Title, Author_ID, Publisher_Name` (partial dependency on subset `Book_ID`)
- `Author_ID -> Author_Name` (transitive dependency)
- `Borrower_ID -> Borrower_Name` (partial dependency on subset `Borrower_ID`)
- `(Book_ID, Borrower_ID) -> Borrow_Date` (full dependency)

**Data Redundancy:**
- Book title, author details, and publisher name are duplicated whenever the same book is loaned to another borrower.
- Borrower name is repeated whenever a user borrows multiple books.

---

#### 2. Procedure to Normalize the Table

##### Step 1: Eliminate Partial Dependencies (Convert to 2NF)
Decompose `LIBRARY_LOAN` so non-prime attributes depend only on the full primary key:

1. `BOOK_INFO(Book_ID, Title, Author_ID, Author_Name, Publisher_Name)` with PK `Book_ID`
2. `BORROWER(Borrower_ID, Borrower_Name)` with PK `Borrower_ID`
3. `LOAN(Book_ID, Borrower_ID, Borrow_Date)` with PK `(Book_ID, Borrower_ID)`

This eliminates partial dependencies and achieves 2NF.

##### Step 2: Eliminate Transitive Dependencies (Convert to 3NF)
In `BOOK_INFO`, the dependency `Author_ID -> Author_Name` is transitive because `Author_ID` is a non-prime attribute determining `Author_Name`.

We decompose `BOOK_INFO` into:
1. `BOOK(Book_ID, Title, Author_ID, Publisher_Name)` with PK `Book_ID` and FK `Author_ID`
2. `AUTHOR(Author_ID, Author_Name)` with PK `Author_ID`

#### Final Normalized 3NF Schema:
1. **BOOK** (`Book_ID`, `Title`, `Author_ID`, `Publisher_Name`)  
   PK: `Book_ID` | FK: `Author_ID` references `AUTHOR(Author_ID)`
2. **AUTHOR** (`Author_ID`, `Author_Name`)  
   PK: `Author_ID`
3. **BORROWER** (`Borrower_ID`, `Borrower_Name`)  
   PK: `Borrower_ID`
4. **LOAN** (`Book_ID`, `Borrower_ID`, `Borrow_Date`)  
   PK: `(Book_ID, Borrower_ID)` | FKs: `Book_ID` references `BOOK`, `Borrower_ID` references `BORROWER`

**Check.**  
*Self-test on entities:*
- Does the final schema represent Books, Authors, Publishers, and Borrowers cleanly?  
  Yes. Books, Authors, and Borrowers each have dedicated relations, and `Publisher_Name` is recorded with each Book.
- Are all partial dependencies removed?  
  Yes. `LOAN` contains only the composite key `(Book_ID, Borrower_ID)` and its fully dependent attribute `Borrow_Date`.

> [!warning] Common mistakes
> - Creating an example table with a single-attribute primary key. Partial dependencies require a composite primary key!
> - Forgetting to define the primary keys of the final normalized tables.

**Exam tip.**  
Keep your invented table small: 3 rows and 8 columns are enough to showcase both partial and transitive dependencies clearly.

### Q.3(b) · 04 Marks · 1

*Topic: [[Topicwise_answers_explaination/T12_Recovery_System_and_RAID.md#T12.1 · Failure classification, precautions, recovery methods|T12.1 · Failure classification, precautions, recovery methods]] · Section A* · 1
*(Repeated question: Also asked in 2019 | Solved in T12)*

**Question.**
Discuss the ways of DBMS can be failed. Also, mention the precautions should be taken considering the failure of DBMS and point out the recovery methods.

**Answer.**

**What the examiner wants.**  
A three-part answer covering failure modes (2 marks), runtime precautions (1.5 marks), and recovery methods (1.5 marks).

**Key idea.**  
A database handles failures in two distinct stages. First, it takes proactive precautions during normal runtime (logging, RAID, battery backups). Second, it executes reactive recovery algorithms (undo/redo, checkpoints) after a failure occurs.

**Step-by-step solution.**  

#### 1. Ways a DBMS Can Fail
A DBMS can fail in three primary ways:
- **Transaction Failure:** Caused by logical errors (overflow, invalid input) or system errors (deadlock aborts).
- **System Crash:** Loss of volatile main memory from power loss, CPU faults, or operating system crashes.
- **Disk Failure:** Loss of non-volatile disk storage caused by head crashes or bad sectors.
- *(Site / Disaster Failure):* Physical destruction of an entire data center caused by fire, flood, or earthquake.

#### 2. Precautions Against DBMS Failures
- **Write-Ahead Logging (WAL):** Force log records to stable storage before writing modified data pages to disk.
- **Uninterruptible Power Supply (UPS) & NVRAM:** Use battery-backed caches to prevent incomplete writes during sudden power loss.
- **Disk Redundancy (RAID):** Use mirroring (RAID 1) or parity (RAID 5/6) to survive single or double disk failures.
- **Archival Off-Site Backups:** Periodically copy full database dumps and log files to remote tape or cloud storage.

#### 3. Recovery Methods
- **Log-Based Recovery:**
  - *Undo:* Reverses uncommitted updates using old values from the log.
  - *Redo:* Re-applies committed updates using new values from the log.
- **Checkpoints:** Periodically flushes dirty buffer blocks and logs active transactions, bounding the restart log scan.
- **Shadow Paging:** Writes updates to a separate page copy and switches pointers atomically, avoiding undo/redo logs.
- **Archival Restore and Roll-Forward:** Restores the last offline backup and replays subsequent archived log records.

*Short version for 2024 Q.3(b) (CO1, 4 marks):* Provide the same three sections in concise bullet points to fit the 4-mark time limit.

**Check.**  
*Quick self-test:*
- Q: Why is Write-Ahead Logging (WAL) classified as a precaution rather than a recovery method?  
  A: WAL is performed during normal execution to guarantee that necessary recovery data exists before a failure happens.
- Q: How do checkpoints speed up recovery after a system crash?  
  A: Checkpoints ensure modified buffer blocks are flushed to disk, so the recovery manager does not need to scan the log before the checkpoint.

> [!warning] Common mistakes
> - Confusing precautions (preventive runtime actions) with recovery methods (restart algorithms).
> - Forgetting to distinguish between undo (reversing uncommitted data) and redo (replaying committed data).
> - Leaving out physical precautions such as RAID and UPS.

**Exam tip.**  
Use three distinct headings matching the prompt: Failures, Precautions, and Recovery Methods.

**Question.**
Differentiate between inner joining and outer joining.

**Answer.**

**What the examiner wants.**  
A concise, structured comparison highlighting the differences between inner joins and outer joins for 2 marks. Examiners look for tuple retention, handling of missing values, and query syntax.

**Key idea.**  
An inner join is strict: it only outputs rows where both tables satisfy the join condition. An outer join is inclusive: it preserves non-matching rows from one or both tables by padding empty columns with `NULL`.

**Step-by-step solution.**

| Feature | Inner Join | Outer Join |
| :--- | :--- | :--- |
| **Tuple Retention** | Keeps only matching tuples from both relations. Drops non-matching rows. | Preserves matching rows plus unmatched rows from one or both relations. |
| **Missing Values** | Never produces `NULL` values to represent missing relationship data. | Pads missing attributes of unmatched tuples with `NULL`. |
| **Information Loss** | Loses dangling records that fail the join predicate. | Prevents information loss by keeping all records from preserved relations. |
| **Forms / Syntax** | Theta join, equijoin, and natural join (`INNER JOIN`, `JOIN`). | Left outer, right outer, and full outer join (`LEFT JOIN`, `RIGHT JOIN`, `FULL JOIN`). |

**Check.**  
*Quick self-test:*
- Q: If table A has 5 rows and table B has 0 matching rows, how many rows does an inner join return?  
  A: 0 rows.
- Q: Under the same condition, how many rows does a left outer join return?  
  A: 5 rows, each padded with `NULL` for attributes of table B.

> [!warning] Common mistakes
> - Writing unstructured prose paragraphs instead of a clear comparison table.
> - Forgetting to mention that outer joins prevent loss of information by using `NULL` values.

### Q.6(a) · 04 Marks · 2

*Topic: [[Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.6 · Subqueries theory ("two examples"): IN, SOME/ALL, EXISTS, scalar, correlated, WITH|T05.6 · Subqueries theory ("two examples"): IN, SOME/ALL, EXISTS, scalar, correlated, WITH]] · Section B* · 2

**Question.**
Explain sub-queries with two suitable examples.

**Answer.**

**What the examiner wants.**  
A conceptual explanation of what a subquery is in SQL, followed by two well-structured, distinct query examples (e.g., set membership `IN` and scalar aggregate comparison) with explanations of how the inner and outer queries interact (2 marks for theory/structure, 1 mark per example).

**Key idea.**  
A subquery embeds one `SELECT` statement inside another. Instead of writing multiple separate programs to retrieve intermediate data, a subquery passes intermediate sets or single scalar values directly to the outer query's predicates.

**Step-by-step solution.**  
**Explanation:** A **subquery** (or nested query) is a `SELECT` statement embedded inside another SQL statement (the outer query). It can appear in the `WHERE` clause to filter tuples, in the `FROM` clause as a temporary derived relation, or in the `SELECT` clause as a scalar expression. Subqueries allow multi-step data retrieval in a single query.

**Example 1: Set Membership Subquery (`IN`)**  
Find all courses offered in Fall 2017 that were also offered in Spring 2018:

```sql
SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2017
  AND course_id IN (
      SELECT course_id
      FROM section
      WHERE semester = 'Spring' AND year = 2018
  );
```

The inner subquery generates the set of courses running in Spring 2018. The outer query checks whether Fall 2017 courses belong to that generated set.

**Example 2: Scalar Comparison Subquery (`AVG`)**  
Find instructors whose salary is higher than the average salary of all instructors:

```sql
SELECT name, salary
FROM instructor
WHERE salary > (
    SELECT AVG(salary)
    FROM instructor
);
```

### Q.6(b) · 04 Marks · 3

*Topic: [[Topicwise_answers_explaination/T07_Triggers_and_Stored_Procedures.md#T07.3 · Implement a trigger or stored procedure|T07.3 · Implement a trigger or stored procedure]] · Section B* · 3

**Question.**
An e-commerce system wants to automate actions when a new order is inserted such as updating stock and sending email. Implement a database trigger that handles this workflow.

**Answer.**

**What the examiner wants.**  
An `AFTER INSERT` trigger on the orders table that automates post-order actions: updating product inventory (2 marks) and queueing email dispatch (2 marks). The answer must address the architectural reality of sending emails from within a database.

**Key idea.**  
A database engine manages transactional data on disk. It cannot open network sockets or send SMTP emails directly. Doing so inside a database transaction would introduce huge network latencies, hold table locks, and create single points of failure. The standard engineering pattern updates stock directly and inserts an email job into an `email_queue` table. An external application service polls this queue and sends the actual email over the network.

**Step-by-step solution.**  

*Assumption: The tables are `orders(order_id, product_id, quantity, customer_email)`, `products(product_id, stock)`, and `email_queue(queue_id, recipient, subject, body, queued_at)`.*

A trigger runs inside the database engine and cannot send external emails directly.
Instead, the trigger updates product stock and inserts a row into an `email_queue` table. An external mailer application reads this queue and sends the email.

```sql
DELIMITER //

CREATE TRIGGER trg_after_order_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    -- 1. Deduct ordered quantity from product stock
    UPDATE products
    SET stock = stock - NEW.quantity
    WHERE product_id = NEW.product_id;

    -- 2. Enqueue email notification for external mailer service
    INSERT INTO email_queue (recipient, subject, body, queued_at)
    VALUES (
        NEW.customer_email,
        'Order Confirmation',
        CONCAT('Your order #', NEW.order_id, ' for product #', NEW.product_id, ' (Qty: ', NEW.quantity, ') has been placed successfully.'),
        NOW()
    );
END //

DELIMITER ;
```

**Check.**  
*Trace with concrete sample tuples:*
- Setup: `products(5, 50)`.
- Client runs: `INSERT INTO orders VALUES (501, 5, 4, 'customer@example.com');`.
- Execution:
  1. Row is written to `orders`.
  2. `trg_after_order_insert` fires immediately.
  3. `products.stock` becomes $50 - 4 = 46$.
  4. A row is added to `email_queue` with recipient `'customer@example.com'` and order details.
- Result: Product inventory stays accurate and an email task is queued without stalling the database engine.

> [!warning] Common mistakes
> - Writing pseudocode functions like `SEND_EMAIL()` directly inside the trigger. Database engines do not provide native email delivery mechanisms without external queues or helper daemons.
> - Using `BEFORE INSERT` instead of `AFTER INSERT`. If the order insertion fails later, the stock would have been decremented erroneously.
> - Hardcoding customer email or product identifiers instead of referencing `NEW.customer_email` and `NEW.product_id`.

**Exam tip.**  
Include the single-line note explaining that triggers cannot dispatch network emails directly. Then show the message queue pattern. Examiners award full marks for this practical engineering insight.

### Q.6(c) · 02 Marks · 3

*Topic: [[Topicwise_answers_explaination/T09_Transactions_ACID_and_Anomalies.md#T09.1 · ACID properties|T09.1 · ACID properties]] · Section B* · 3
*(Repeated question: Also asked in 2017 | Solved in T09)*

**Question.**
Briefly discuss the ACID properties of transaction.

**Answer.**

**What the examiner wants.**  
A concise definition of each of the four ACID properties. Examiners look for the specific database subsystem responsible for enforcing each property. The mark split is 1 mark per property (or 0.5 marks each in the 2-mark paper).

**Key idea.**  
A transaction is a logical unit of database work. To keep data safe during crashes and concurrent access, the DBMS treats every transaction as an atomic, isolated unit that leaves data consistent and permanently saved.

**Step-by-step solution.**  
A **transaction** is a logical unit of program execution that accesses and updates data items. To preserve data integrity during crashes and concurrent access, the DBMS must ensure the four **ACID** properties:

1. **Atomicity ("All-or-None"):**
   - Either all operations of the transaction are properly reflected in the database, or none are.
   - If a failure happens before the transaction completes, partial modifications are rolled back.
   - **Enforced by:** The **Recovery System** (using undo log records).

2. **Consistency (Preservation of Invariants):**
   - Executing a transaction in isolation preserves database consistency.
   - The database moves from one valid state to another valid state, satisfying all integrity constraints.
   - In a fund transfer, the total balance sum must remain unchanged.
   - **Enforced by:** The **Application Programmer** (correct business logic) and DBMS **Integrity Constraints**.

3. **Isolation (Shielding Concurrent Access):**
   - Each transaction executes as if it were running alone without interference from other concurrent transactions.
   - Intermediate results remain hidden from other concurrent transactions until commit.
   - **Enforced by:** The **Concurrency-Control System** (using locking or timestamp protocols).

4. **Durability (Persistence):**
   - After a transaction completes successfully and commits, its updates persist in the database permanently.
   - The committed data survives subsequent system crashes or power outages.
   - **Enforced by:** The **Recovery System** (using redo logs and non-volatile stable storage).

*Short version for 2024 Q.6(c) (2 marks):*
- **Atomicity:** All operations complete or none do. The recovery system undoes partial writes.
- **Consistency:** Execution in isolation preserves database validity and invariants.
- **Isolation:** Intermediate updates remain hidden from concurrent transactions.
- **Durability:** Committed changes persist permanently on disk despite crashes.

**Check.**  
*Quick self-test:*
- Q: Which DBMS subsystem enforces atomicity?  
  A: The recovery system, using write-ahead undo logs.
- Q: Who is primarily responsible for consistency?  
  A: The application programmer who codes correct business logic, assisted by DBMS integrity constraints.
- Q: Why is durability not handled by volatile main memory?  
  A: Main memory loses data on power failure. Durability requires writing to stable storage or non-volatile disk logs.

> [!warning] Common mistakes
> - Confusing Atomicity with Isolation. Atomicity handles failure and recovery. Isolation handles concurrent transactions.
> - Stating that the DBMS guarantees consistency automatically without programmer logic. Erroneous application code (like adding \$100 instead of \$50) produces valid SQL that still breaks business invariants.
> - Forgetting to name the enforcing subsystem for each property.

**Exam tip.**  
Start each bullet with the letter of the acronym, bold the property name, write a one-sentence definition, and end by naming the enforcing component.

### Q.7(b) · 04 Marks · 1

*Topic: [[Topicwise_answers_explaination/T05_SQL_DDL_DML_Aggregates_Subqueries.md#T05.8 · Short notes: ON DELETE CASCADE, GROUP BY, ORDER BY, AS|T05.8 · Short notes: ON DELETE CASCADE, GROUP BY, ORDER BY, AS]] · Section B* · 1

**Question.**
Write short note on the following statements –<br>i) ON CASCADE DELETE<br>ii) Group By<br>iii) Order By<br>iv) As

**Answer.**

**What the examiner wants.**  
Concise technical descriptions, purpose, and standard SQL syntax/examples for four fundamental SQL clauses and constraint actions (1 mark each).

**Key idea.**  
Each term serves a distinct role in relational data management: `ON DELETE CASCADE` governs referential integrity maintenance; `GROUP BY` partitions data for summary aggregation; `ORDER BY` controls output presentation order; `AS` introduces aliasing for projection expressions and relation names.

**Step-by-step solution.**  
**i) ON DELETE CASCADE (printed as "ON CASCADE DELETE"):**  
A foreign key referential integrity action. When a tuple in the parent table is deleted, the DBMS automatically deletes all corresponding referencing tuples in the child table. This maintains referential integrity and prevents orphaned records.

```sql
CREATE TABLE section (
    course_id VARCHAR(8),
    sec_id VARCHAR(8),
    semester VARCHAR(6),
    year NUMERIC(4, 0),
    PRIMARY KEY (course_id, sec_id, semester, year),
    FOREIGN KEY (course_id) REFERENCES course(course_id)
        ON DELETE CASCADE
);
```

**ii) GROUP BY:**  
An SQL clause used to partition table rows into distinct groups having identical values in specified columns. Aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) then compute summary statistics for each individual group.

```sql
SELECT dept_name, AVG(salary) AS avg_sal
FROM instructor
GROUP BY dept_name;
```

**iii) ORDER BY:**  
An SQL clause that sorts query result rows in ascending (`ASC`, default) or descending (`DESC`) order based on one or more attributes. Multiple sort keys break ties sequentially.

```sql
SELECT name, salary
FROM instructor
ORDER BY salary DESC, name ASC;
```

**iv) AS:**  
An SQL keyword used to define an alias (an alternative temporary name). It can rename an attribute or computed expression in the `SELECT` clause for readability, or rename a table in the `FROM` clause to shorten table references and enable self-joins.

```sql
SELECT salary * 1.15 AS revised_salary
FROM employee AS e;
```

*Short version for 2019 Q.8(c) (4 marks):* Provide parts (i) and (ii).  
*Short version for 2023 Q.6(c) (2 marks):* Provide part (i) with definition, syntax, and effect.

**Check.**  
*Referential trace of `ON DELETE CASCADE`:*
- Department 'Biology' exists in parent table `department`.
- Three courses in child table `course` have `dept_name = 'Biology'`.
- Deleting 'Biology' from `department` via `DELETE FROM department WHERE dept_name = 'Biology'` automatically removes the three referencing courses from `course`.

> [!warning] Common mistakes
> - Confusing `ON DELETE CASCADE` with `ON DELETE SET NULL`; cascading drops the entire referencing row, whereas `SET NULL` updates the referencing foreign key column to `NULL`.
> - Assuming `AS` permanently alters attribute names in physical storage; `AS` renames items only within the output result relation.

**Exam tip.**  
For short notes on SQL statements, always supply both the formal definition and a minimal code snippet illustrating syntax.

**Question.**
If concurrency-control management is not implemented properly what problem may occur? Explain with example.

**Answer.**

**What the examiner wants.**  
Identification and explanation of the data corruption anomalies that occur when concurrent transactions run without proper concurrency control. The examiner expects two-column chronological schedules showing exactly how values get corrupted. Mark split: 1 mark for naming the 5 anomalies, 2 marks for schedule tables and explanation.

**Key idea.**  
When concurrent operations interleave without control, they violate isolation. The five classic concurrency anomalies are: Lost Update, Dirty Read (temporary update), Unrepeatable Read, Phantom Read, and Incorrect Summary.

**Step-by-step solution.**  
If concurrency-control management is not implemented properly, uncoordinated interleaving violates transaction isolation. This causes five major anomalies:
1. **Lost Update Problem**
2. **Dirty Read Problem (Temporary Update Problem)**
3. **Unrepeatable Read Problem**
4. **Phantom Read Problem**
5. **Incorrect Summary Problem (Inconsistent Analysis)**

Below are the full schedule tables for the two primary anomalies:

#### 1. Lost Update Problem
- **Concept:** An update done by one transaction is overwritten and lost because another concurrent transaction writes to the same item without incorporating the first update.
- **Schedule ($A = 500$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Note |
| :--- | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | $A := A - 50$ | | $T_1$ computes local $A = 450$ |
| $t_3$ | $\text{write}(A)$ | | Database updated to $A = 450$ |
| $t_4$ | | $\text{write}(A)$ | $T_2$ performs blind write: $A = 25$ |
| $t_5$ | $\text{commit}$ | | $T_1$ commits |
| $t_6$ | | $\text{commit}$ | Final $A = 25$ (update by $T_1$ of $-50$ is lost!) |

#### 2. Dirty Read Problem (Temporary Update Problem)
- **Concept:** Occurs when a transaction reads a data item updated by another transaction that has not yet committed and later fails and rolls back.
- **Schedule ($A = 100$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Note |
| :--- | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads initial balance $A = 100$ |
| $t_2$ | $A := A + 100$ | | $T_1$ computes local $A = 200$ |
| $t_3$ | $\text{write}(A)$ | | Database $A = 200$ (uncommitted) |
| $t_4$ | | $\text{read}(A)$ | $T_2$ reads dirty value $A = 200$ |
| $t_5$ | | $A := A - 50$ | $T_2$ computes local $A = 150$ |
| $t_6$ | | $\text{write}(A)$ | Database updated to $A = 150$ |
| $t_7$ | | $\text{commit}$ | $T_2$ commits with invalid data |
| $t_8$ | $\text{abort}$ (Rollback) | | $T_1$ fails and aborts; recovery restores $A = 100$ |

$T_2$ based its computation on a temporary value that never officially existed, leaving the database inconsistent.

### Q.8(b) · 03 Marks · 3

*Topic: [[Topicwise_answers_explaination/T11_Concurrency_Control_Protocols.md#T11.6 · Timestamp ordering: R-TS/W-TS rules, trace a schedule; rolled-back transaction gets a NEW timestamp|T11.6 · Timestamp ordering: R-TS/W-TS rules, trace a schedule; rolled-back transaction gets a NEW timestamp]] · Section B* · 3
*(Repeated question: Also asked in 2018 | Solved in T11)*

**Question.**
When a transaction is rolled back under timestamp ordering and it is assigned a new timestamp? Why can it not simply keep its old timestamp?

**Answer.**

**What the examiner wants.**  
This question comes from Textbook Exercise 18.26. The examiner wants:
1. The exact conditions under which a transaction is rolled back under timestamp ordering on read and write (1.5 marks).
2. The statement that a new, larger timestamp is assigned upon restart (0.5 marks).
3. The reasoning for why keeping the old timestamp fails, specifically pointing out repeated failures and starvation (2 marks).

**Key idea.**  
Timestamp ordering makes older transactions execute before younger ones. If an older transaction arrives late and tries to read or write an item that a younger transaction already altered, the order is broken. So the older transaction is rolled back. When it restarts, it must get a new, higher timestamp. If it kept its old timestamp, the exact same conflict would happen all over again, causing starvation.

**Step-by-step solution.**  
**1. When a Transaction is Rolled Back Under Timestamp Ordering:**  
Under the Timestamp Ordering (TSO) protocol, a transaction $T_i$ with timestamp $\text{TS}(T_i)$ is rolled back when it attempts an out-of-order operation:

- **On a `read(Q)` Operation:**  
  If $\text{TS}(T_i) < \text{W-timestamp}(Q)$, transaction $T_i$ needs to read a value of $Q$ that was already overwritten by a younger transaction. The read operation is rejected, and $T_i$ is rolled back.
- **On a `write(Q)` Operation:**  
  - If $\text{TS}(T_i) < \text{R-timestamp}(Q)$, the value of $Q$ produced by $T_i$ was needed previously by a younger transaction that already read an older value. The write operation is rejected, and $T_i$ is rolled back.
  - If $\text{TS}(T_i) < \text{W-timestamp}(Q)$, transaction $T_i$ attempts to write an obsolete value over a newer value written by a younger transaction. The write operation is rejected, and $T_i$ is rolled back.

**2. Assigning a New Timestamp:**  
When $T_i$ is rolled back, the system aborts it and cleans up its partial changes. When $T_i$ is restarted, the system assigns it a **new, larger timestamp** based on the current system clock or logical counter.

**3. Why It Cannot Keep Its Old Timestamp:**

1. **Avoids Immediate Repeat Failure:**  
   If $T_i$ kept its old timestamp, its timestamp would still be smaller than the updated $\text{R-timestamp}(Q)$ and $\text{W-timestamp}(Q)$ values on the data items. Upon restarting, when $T_i$ attempts the same operation, the exact same condition fails again.
2. **Prevents Starvation (Livelock):**  
   Keeping the old timestamp locks the transaction into an infinite abort-restart loop. It could never complete. Assigning a new timestamp gives it a higher priority relative to newer arrivals and allows it to proceed.
3. **Restores Serialization Order:**  
   A new timestamp positions the restarted transaction at the current moment in logical time. It now executes after the transactions that conflicted with it, allowing its operations to succeed.

*Short version for 2024 Q.8(b) (3 marks):* Give the read and write rollback conditions concisely. Then explain in 2 points why the old timestamp causes repeated aborts and starvation.

**Check.**  
*Logic check:*
- Suppose $T_1$ ($\text{TS}=10$) writes $A$, but $T_2$ ($\text{TS}=20$) already read $A$ ($\text{R-TS}(A)=20$).
- $T_1$ fails because $10 < 20$. $T_1$ is rolled back.
- If $T_1$ restarts with old $\text{TS}=10$, it re-attempts $\text{write}(A)$. $\text{R-TS}(A)$ is still 20. $10 < 20$ fails again immediately.
- If $T_1$ restarts with new $\text{TS}=25$, $25 \ge 20$. The write succeeds.

> [!warning] Common mistakes
> - Confusing timestamp ordering with wait-die or wound-wait. In wait-die and wound-wait, a rolled-back transaction keeps its old timestamp so it gains priority. In standard timestamp ordering, a rolled-back transaction MUST get a NEW timestamp to avoid repeat failures.
> - Stating only the read rollback condition and omitting the write rollback conditions.
> - Forgetting to use the term starvation or livelock.

**Exam tip.**  
Be very clear on the distinction: deadlock prevention (wait-die) keeps old timestamps; timestamp ordering (TSO) assigns new timestamps. Examiners check for this exact distinction.

**Question.**
Consider the following schedule:<br><br><table border="1" style="border-collapse: collapse; text-align: left;"><thead><tr><th style="text-align: center; padding: 4px 14px;">$T_1$</th><th style="text-align: center; padding: 4px 14px;">$T_2$</th></tr></thead><tbody><tr><td style="padding: 4px 14px;">read (A);<br>A=A+10;</td><td style="padding: 4px 14px;"></td></tr><tr><td style="padding: 4px 14px;"></td><td style="padding: 4px 14px;">read (A);<br>A=A-100;<br>write (A);<br>read (B);</td></tr><tr><td style="padding: 4px 14px;">write (A);<br>read (B);<br>B=B-10;<br>write (B);</td><td style="padding: 4px 14px;"></td></tr><tr><td style="padding: 4px 14px;"></td><td style="padding: 4px 14px;">B=B+100;<br>write (B);</td></tr></tbody></table><br>Determine whether the schedule is conflict serializable or not.

**Answer.**

**What the examiner wants.** Extraction of read/write operations (1 mark), finding conflicts for items $A$ and $B$ (1.5 marks), precedence graph and cycle detection (1 mark), and concluding verdict (0.5 marks).

**Key idea.** The question presents blocks of operations per column. We convert them into a chronological timeline of database reads and writes. A conflict exists whenever two transactions touch the same item and at least one writes. If opposite conflicting directions exist, a cycle forms.

**Step-by-step solution.**

#### 1. Chronological Timeline of Read and Write Operations

- Step 1: $T_1: \text{read}(A)$
- Step 2: $T_2: \text{read}(A)$
- Step 3: $T_2: \text{write}(A)$
- Step 4: $T_2: \text{read}(B)$
- Step 5: $T_1: \text{write}(A)$
- Step 6: $T_1: \text{read}(B)$
- Step 7: $T_1: \text{write}(B)$
- Step 8: $T_2: \text{write}(B)$

#### 2. Conflicts on Item $A$

- Step 1 ($T_1: \text{read}(A)$) precedes Step 3 ($T_2: \text{write}(A)$) $\implies T_1 \to T_2$.
- Step 2 ($T_2: \text{read}(A)$) precedes Step 5 ($T_1: \text{write}(A)$) $\implies T_2 \to T_1$.
- Step 3 ($T_2: \text{write}(A)$) precedes Step 5 ($T_1: \text{write}(A)$) $\implies T_2 \to T_1$.

Because we have both $T_1 \to T_2$ and $T_2 \to T_1$, there is an immediate cycle on item $A$.

#### 3. Conflicts on Item $B$

- Step 4 ($T_2: \text{read}(B)$) precedes Step 7 ($T_1: \text{write}(B)$) $\implies T_2 \to T_1$.
- Step 6 ($T_1: \text{read}(B)$) precedes Step 8 ($T_2: \text{write}(B)$) $\implies T_1 \to T_2$.
- Step 7 ($T_1: \text{write}(B)$) precedes Step 8 ($T_2: \text{write}(B)$) $\implies T_1 \to T_2$.

Item $B$ also creates conflicting dependencies in both directions: $T_2 \to T_1$ and $T_1 \to T_2$.

#### 4. Precedence Graph

![2024 Q.8(c) Precedence Graph showing cycle T1-T2](diagrams/T10_2024_Q8c_precedence_graph.jpg)

The precedence graph consists of vertices $\{T_1, T_2\}$ and directed edges $T_1 \to T_2$ and $T_2 \to T_1$. This creates a cycle:
$$
T_1 \longleftrightarrow T_2
$$

**Result:** Because the precedence graph contains a cycle, the schedule is **NOT conflict serializable**.

**Check.**
- In schedule $S$, $T_1$ reads the old value of $A$. Then $T_2$ overwrites $A$. Then $T_1$ overwrites $A$ again.
- In serial schedule $\langle T_1, T_2 \rangle$, $T_2$ would perform the final write on $A$.
- In serial schedule $\langle T_2, T_1 \rangle$, $T_1$ would read $A$ after $T_2$ wrote it.
- Neither serial schedule matches $S$. This verifies non-serializability.

> [!warning] Common mistakes
> - Getting distracted by the arithmetic statements like `A=A-100` and `B=B+100`. Only the reads and writes determine conflict serializability.
> - Confusing cell order with time order. Remember that the table reads from top to bottom chronologically.

**Exam tip.** RUET repeated this exact question from 2018. Writing the steps clearly with step numbers gives maximum marks.
