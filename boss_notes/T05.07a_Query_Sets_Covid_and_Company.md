# T05.7a: Multi-Table SQL Query Sets — Covid and Company

> **Topic:** T05 — SQL (DDL, DML, Aggregates, Subqueries) | **Priority:** 🔴 | **Exam Frequency:** 5/7 finals (44 marks across T05.7, Rank #1 Subtopic)  
> **Sources:** Silberschatz 7e Ch. 3 (§3.4, §3.7, §3.8) · Lecture Deck 03 (Slides 12–61) · Lecture Deck 04 · Raidah Notes (p. 15, Employee DB)

## Why This Topic Matters

Multi-table SQL query sets form the single highest-scoring subtopic in ECE 2215 semester finals. RUET examiners present realistic multi-table relational schemas and test 3 to 4 complex queries per question. The 2019 Q.5(b) paper carries 8 marks on a Covid patient tracking database. The 2020 Q.3(b) paper carries 10 marks on the classic Elmasri-Navathe Company enterprise schema. Full marks require fluent join paths, nested aggregations via derived tables, and strict foreign key filtering.

## 📝 Key Definitions

> **Join Operation:** "The *join* operation allows us to combine a selection and a Cartesian product into a single operation." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.6.5 (p. 50)

> **Aggregate Function:** "Aggregate functions are functions that take a collection (a set or multiset) of values as input and return a single value." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7 (p. 92)

> **HAVING Clause:** "Predicates in the `having` clause are applied after the formation of groups, so aggregate functions can be used in the `having` clause." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.3 (p. 95)

> **Derived Relation:** "SQL allows a subquery expression to be used in the `from` clause. The key concept applied here is that any `select-from-where` expression returns a relation as a result and, therefore, can be inserted into another `select-from-where` anywhere that a relation can appear." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.8.5 (p. 104)

## Multi-Table Query Architecture & Join Traversal

Real-world database systems normalize entities into separate tables to eliminate redundancy. When writing queries across these tables, students must identify the foreign key path connecting each relation.

```text
[Employee] (ssn, fname, dept_no)
    │
    ▼ (dept_no = dnumber)
[Department] (dnumber, dname)
```

### Inner Joins vs Cartesian Products

In MySQL 8, join conditions should be explicitly declared using the `JOIN ... ON` construct:

```sql
SELECT e.fname, d.dname
FROM employee e
JOIN department d ON e.dept_no = d.dnumber;
```

This prevents accidental Cartesian products and separates join predicates from filtering predicates in the `WHERE` clause.

## Enterprise Pattern 1: Nested Aggregation and Peak Finding

A classic exam challenge asks for the **maximum of a grouped count** (such as finding the highest number of patients recorded on a single day, or the largest department headcount).

### The Syntax Trap: Nested Aggregates Are Illegal

In standard SQL, you cannot wrap one aggregate function directly inside another:

```sql
-- INVALID SQL: Triggers syntax error
SELECT MAX(COUNT(Patient_ID)) FROM History GROUP BY Date;
```

Why does SQL reject this? Because a single `SELECT` block only gets one aggregation pass. Once `GROUP BY Date` collapses the table into daily counts, there is no second grouping step in that same block to collapse those daily counts into a single overall maximum.

### The Derived Table Solution

To do two levels of aggregation, we split the work across two query blocks using a **derived table** (a subquery inside the `FROM` clause):
1. **Inner Query (Pass 1):** Groups rows by the partition column (such as `Date`) and computes the first aggregate (`COUNT(...) AS group_total`).
2. **Outer Query (Pass 2):** Treats that inner summary table like an ordinary table and applies `MAX(group_total)` across its rows.

## Enterprise Pattern 2: Department-Project Affiliation Constraints

In the Company schema, an employee can be assigned to any project through the `works_on` table, even if that project is managed by a different department. Exam questions (like 2020 Q.3(b)(ii)) test whether you can spot the difference between an employee's home department and a project's controlling department.

### Navigating the Two Department Links

Look closely at the two department foreign keys in the Company schema:
- `employee.dept_no`: The home department where the employee works.
- `project.dnum`: The department that controls the project.

```text
[employee] (ssn, dept_no) ──(ssn = essn)── [works_on] (essn, pno) ──(pno = pnumber)── [project] (pnumber, dnum)
```

When a question asks for employees working on project 5 who are **"from the same department"**, joining `employee`, `works_on`, and `project` on their primary-foreign key links only proves that the employee works on project 5. To also verify that the employee belongs to the department running project 5, you must add the equality check:

$$
\text{employee.dept_no} = \text{project.dnum}
$$

```sql
SELECT e.fname, e.lname
FROM employee e
JOIN works_on w ON e.ssn = w.essn
JOIN project p ON w.pno = p.pnumber
WHERE p.pnumber = 5
  AND e.dept_no = p.dnum;
```

## Enterprise Pattern 3: Grouped Filtering with HAVING vs WHERE

Remember the execution pipeline whenever a query combines joins, row conditions, and group conditions:
1. `FROM` and `JOIN` (connect the tables)
2. `WHERE` (filter individual rows before grouping)
3. `GROUP BY` (bucket rows into summary groups)
4. `HAVING` (filter the groups using aggregate functions)
5. `SELECT` (project the final columns)

### Grouping by Primary and Descriptive Attributes

Suppose we want the department name and employee headcount for every department whose average salary exceeds \$30,000. Because the condition `AVG(e.Salary) > 30000` depends on a group average rather than a single employee's salary, it belongs in `HAVING`, and we group by both `d.dnumber` and `d.dname` so that two departments with the same name never get merged by mistake:

```sql
SELECT d.dname AS department_name,
       COUNT(e.ssn) AS number_of_employees
FROM department d
JOIN employee e ON d.dnumber = e.dept_no
GROUP BY d.dnumber, d.dname
HAVING AVG(e.Salary) > 30000;
```

## Enterprise Pattern 4: Safe Counting of Weak Entities (Dependents)

In the Company schema, `dependent` is a weak entity tied to its owning `employee` via `essn = ssn`.

When counting how many dependents belong to employees of a specific department (such as `'H&R'`):
- Joining `department`, `employee`, and `dependent` produces one row for each dependent person.
- If an H&R employee has zero dependents, an inner join simply drops that employee, which does not hurt the total dependent count at all.
- Applying `COUNT(dp.dependent_name)` counts the exact number of dependents across that department.

```sql
SELECT COUNT(dp.dependent_name) AS total_dependents
FROM dependent dp
JOIN employee e ON dp.essn = e.ssn
JOIN department d ON e.dept_no = d.dnumber
WHERE d.dname = 'H&R';
```

## Schema Deep Dive: The Covid Relational Schema (2019 Q.5(b))

### Covid Relational Schema:
```text
Patient (Patient_ID, Patient_name, Mobile)
History (Patient_ID, Symptom, Date)
Report (Parient_ID, Corona_center, Test_result)
```

### Examination Typo Alert:
In the printed 2019 question paper, the first column of the `Report` table is spelled `Parient_ID`. This is a typo for `Patient_ID`. In an exam, always state a quick one-line note that `Report.Parient_ID` references `Patient.Patient_ID` and use `r.Parient_ID` in your `ON` clause so your answer matches the printed schema verbatim.

### Sub-Question Breakdown:
1. **Fever Symptom:** Use `LIKE '%fever%'` so your query catches `'fever'`, `'high fever'`, and `'mild fever'`.
2. **Maximum Suspects on a Single Date:** Group by `Date` inside a derived table in `FROM` to count daily high-fever patients, then take `MAX()` in the outer query.
3. **Rajshahi Positive Cases:** Join `Patient` and `Report` and filter with `Corona_center = 'Rajshahi' AND Test_result = 'positive'`.
4. **High Fever with Negative Test:** Join all three tables (`Patient`, `History`, and `Report`) and filter for `h.Symptom = 'high fever' AND r.Test_result = 'negative'`.

- `project.dnum` references `department.dnumber`.

## Worked Example: Finding Peak Project Staffing via a Derived Table

Before solving the full exam questions below, let's trace a compact derived-table example on the Company schema: **Find the maximum number of employees assigned to any single project.**

```sql
SELECT MAX(emp_count) AS peak_staffing
FROM (
    SELECT pno, COUNT(DISTINCT essn) AS emp_count
    FROM works_on
    GROUP BY pno
) AS proj_counts;
```

### Quick Trace
Suppose `works_on` has 5 rows: `(E1, P10, 10)`, `(E2, P10, 20)`, `(E1, P20, 15)`, `(E3, P20, 20)`, and `(E4, P20, 25)`.
1. **Inner query (`proj_counts`):** Groups by `pno` and counts employees per project, producing `(P10, 2)` and `(P20, 3)`.
2. **Outer query:** Computes `MAX(emp_count)` over `{2, 3}` and returns `3`.

### 🎯 GQ1 · 2019 Q.5(b) · Covid Tracking Relational Database Queries

> **Appeared:** 2019 Q.5(b) — (8 marks)

**Question:**

Consider the following relational database.  
`Patient (Patient_ID, Patient_name, Mobile)`  
`History (Patient_ID, Symptom, Date)`  
`Report (Parient_ID, Corona_center, Test_result)`

Now write down the SQL (Not Algebra) to find out the following queries.  
(i) Find the names of those patients who have-fever symptom.  
(ii) Consider that if any patient has high fever symptom he/she will be suspected as corona patient. Find out such maximum number of patients in a date.  
(iii) Find out the mobile numbers of those patients who have provided samples in Rajshahi corona center and their results have become positive.  
(iv) Find out the name of those patients who have high fever symptom but test result have become negative.

*(Note: In the physical question paper, SECTION-B heading and Q.5(a)–(b) appear at the bottom of Page 1; Q.5(c) continues at the top of Page 2)*  
*(Note: Printed as "Parient_ID" in Report schema in original question paper; refers to "Patient_ID")*

**Full Answer:**

*Assumption: In the `Report` relation, `Parient_ID` is a misprint for `Patient_ID` and joins with `Patient.Patient_ID`.*

#### (i) Names of patients who have fever symptom:
```sql
SELECT DISTINCT p.Patient_name
FROM Patient p
JOIN History h ON p.Patient_ID = h.Patient_ID
WHERE h.Symptom LIKE '%fever%';
```

#### (ii) Maximum number of high-fever suspected patients recorded on a single date:
```sql
SELECT MAX(daily_count) AS max_patients
FROM (
    SELECT Date, COUNT(DISTINCT Patient_ID) AS daily_count
    FROM History
    WHERE Symptom = 'high fever'
    GROUP BY Date
) AS daily_summary;
```

*(Alternative returning the specific date with the peak count:*  
```sql
SELECT Date, COUNT(DISTINCT Patient_ID) AS patient_count
FROM History
WHERE Symptom = 'high fever'
GROUP BY Date
ORDER BY patient_count DESC
LIMIT 1;
```
*)*

#### (iii) Mobile numbers of patients tested in Rajshahi corona center with positive result:
```sql
SELECT DISTINCT p.Mobile
FROM Patient p
JOIN Report r ON p.Patient_ID = r.Parient_ID
WHERE r.Corona_center = 'Rajshahi'
  AND r.Test_result = 'positive';
```

#### (iv) Names of patients with high fever symptom whose test result is negative:
```sql
SELECT DISTINCT p.Patient_name
FROM Patient p
JOIN History h ON p.Patient_ID = h.Patient_ID
JOIN Report r ON p.Patient_ID = r.Parient_ID
WHERE h.Symptom = 'high fever'
  AND r.Test_result = 'negative';
```

### 🎯 GQ2 · 2020 Q.3(b) · Enterprise Company Database Schema Queries

> **Appeared:** 2020 Q.3(b) — (10 marks)

**Question:**

Consider the following company database schema.  
  employee(<u>ssn</u>, fname, lname, DoB, Address, Sex, Salary, dept_no)  
  department(<u>dnumber</u>, dname, mgr_ssn, mgr_start_date)  
  dept_location(<u>dnumber</u>, <u>dlocation</u>)  
  project(<u>pnumber</u>, pname, dnum)  
  works_on(<u>essn</u>, <u>pno</u>, hours)  
  dependent(<u>essn</u>, <u>dependent_name</u>, Sex, DoB, relationship)  
Now write down the MySQL query for the followings.  
(i) For each department whose average salary is more than \$30,000, retrieve the department_name and the number of employees working for that department.  
(ii) Find the names of all employees who are working on project number "5" and are from the same department.  
(iii) Find the number of dependent people of those employees who are from "H&R" department.

**Full Answer:**

#### (i) Department name and employee count for departments with average salary > \$30,000:
```sql
SELECT d.dname AS department_name,
       COUNT(e.ssn) AS number_of_employees
FROM department d
JOIN employee e ON d.dnumber = e.dept_no
GROUP BY d.dnumber, d.dname
HAVING AVG(e.Salary) > 30000;
```

#### (ii) Names of employees working on project 5 who belong to the department controlling project 5:
*Assumption: "from the same department" means the employee's department (`dept_no`) matches the project's controlling department (`dnum`).*

```sql
SELECT e.fname, e.lname
FROM employee e
JOIN works_on w ON e.ssn = w.essn
JOIN project p ON w.pno = p.pnumber
WHERE p.pnumber = 5
  AND e.dept_no = p.dnum;
```

#### (iii) Total number of dependents for employees in the "H&R" department:
```sql
SELECT COUNT(dp.dependent_name) AS total_dependents
FROM dependent dp
JOIN employee e ON dp.essn = e.ssn
JOIN department d ON e.dept_no = d.dnumber
WHERE d.dname = 'H&R';
```

## ⚡ Exam Tips & Common Mistakes

1. **Avoid Nested Aggregates:** Never write `MAX(COUNT(*))` in standard SQL. Always compute the count inside a derived table in the `FROM` clause and apply `MAX()` in the outer query.
2. **Address Schema Typos Explicitly:** In 2019 Q.5(b), the paper prints `Parient_ID` instead of `Patient_ID`. State the join mapping explicitly (`ON p.Patient_ID = r.Parient_ID`) so examiners award full marks regardless of strict answer key scripts.
3. **Do Not Put Aggregates in WHERE:** In 2020 Q.3(b)(i), students frequently write `WHERE AVG(e.Salary) > 30000`. Aggregate filters must always go into the `HAVING` clause.
4. **Enforce Department Affiliation:** In 2020 Q.3(b)(ii), "from the same department" requires equating `e.dept_no = p.dnum`. Failing to add this condition queries all employees on project 5 regardless of department.
5. **Use DISTINCT on Projections:** Medical or transactional histories often record multiple visits or symptoms for the same person. Always use `SELECT DISTINCT` when outputting patient names or mobile numbers.
