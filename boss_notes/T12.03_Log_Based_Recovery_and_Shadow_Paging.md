# T12.3: Log-Based Recovery (WAL, Undo/Redo, Checkpoints) and Shadow Paging

> **Topic:** T12 — Recovery System & RAID | **Priority:** 🟡 Core | **Exam Frequency:** 2/7 finals (7 marks)
> **Sources:** Silberschatz 7e Ch. 19 (§19.3–19.4, Note 19.1) · Lecture Deck 07 (Slide 8)

## Why This Topic Matters

When a database server suddenly crashes, active transactions are cut off halfway through their work, and committed transactions may still have updates sitting in volatile RAM buffers that have not reached the hard drive yet. Log-based recovery is the standard mechanism that guarantees transaction **Atomicity** (undoing unfinished transactions) and **Durability** (keeping committed transactions) across crashes. This note covers Write-Ahead Logging (WAL), log record formats, undo and redo passes, checkpointing, and shadow paging, which were tested in 2017 Q.6(d) and 2023 Q.7(b) for 7 marks total.

---

## 📝 Key Definitions

> **Log:** The log is an append-only sequence of records kept on stable storage that tracks every update made to the database. Each update log record $\langle T_i, X, V_1, V_2 \rangle$ stores the transaction ID $T_i$, data item $X$, old value $V_1$ for undo, and new value $V_2$ for redo.

> **Write-Ahead Logging (WAL):** Write-Ahead Logging is a recovery protocol where the database must flush a log record to stable storage before writing the modified data block to disk. Also, a transaction is not committed until its $\langle T_i\text{ commit}\rangle$ log record is safely written to stable storage.

> **Undo and Redo Operations:** Undo and redo are the two log-replay passes used after a crash. Undo scans backward through an unfinished transaction's log records and restores each item $X$ to its old value $V_1$ ($X \leftarrow V_1$). Redo scans forward through a committed transaction's log records and sets each item $X$ to its new value $V_2$ ($X \leftarrow V_2$).

> **Checkpoint:** A checkpoint is a periodic synchronization step that shortens post-crash recovery time. The database flushes all in-memory log records and dirty buffer blocks to disk, then writes a $\langle\text{checkpoint } L\rangle$ record to stable storage listing all currently active transactions $L$. Any transaction that committed before the checkpoint never needs to be redone.

> **Shadow Paging:** Shadow paging is a copy-on-write recovery method that avoids log undo passes by keeping two page tables: a current page table and a shadow page table. Modified pages are written to fresh disk blocks pointed to by the current page table, while the shadow page table points to the untouched original blocks. A transaction commits by atomically flipping a single disk pointer (`db-pointer`) to the current page table.

## The Sequential Log and Log Records

Think of the database log as an accountant's ink ledger: before the database touches any actual data block, it writes down a permanent note in an append-only file on stable storage stating *who* is changing *what*, *what the old value was*, and *what the new value will be*.

### Structure of an Update Log Record
Every write operation creates an update log record with four fields:

$$\langle T_i, X, V_1, V_2 \rangle$$

1. **Transaction Identifier ($T_i$):** Which transaction performed the write.
2. **Data-Item Identifier ($X$):** Which data item is being changed (usually its disk block ID and offset).
3. **Old Value ($V_1$):** What $X$ held *before* this write. If $T_i$ fails or gets interrupted by a crash, the recovery manager needs $V_1$ to **undo** the change.
4. **New Value ($V_2$):** What $X$ holds *after* this write. If $T_i$ commits before a crash, the recovery manager needs $V_2$ to **redo** the change if the RAM buffer had not been flushed to disk yet.

### State Transition Log Records
In addition to data updates, three boundary records track when transactions start and finish:
- $\langle T_i\text{ start}\rangle$: Marks the moment transaction $T_i$ begins.
- $\langle T_i\text{ commit}\rangle$: Marks the exact moment transaction $T_i$ commits. Once this record hits stable storage, the transaction is officially committed!
- $\langle T_i\text{ abort}\rangle$: Marks that transaction $T_i$ has aborted and all of its changes have been completely undone.

---

## The Write-Ahead Logging (WAL) Protocol

Why is it called **Write-Ahead** Logging? Because the log record must always be written to stable disk *ahead* of the actual data change. Specifically, WAL enforces two strict rules:

```text
Rule 1 (Undo Rule):
[Update Log Record <Ti, X, V1, V2>]  ──must reach──>  [Stable Storage (Disk)]
                     BEFORE
[Modified Data Block with X=V2]      ──is written to──>  [Database Disk]

Rule 2 (Redo / Durability Rule):
[Commit Log Record <Ti commit>]      ──must reach──>  [Stable Storage (Disk)]
                     BEFORE
[Transaction Ti]                     ──reports success to──>  [Client Application]
```

1. **The Undo Rule:** Before a modified data block in RAM is ever written to the database disk, its update log record $\langle T_i, X, V_1, V_2 \rangle$ must already be safely on stable storage. Why? Because if the server crashes right after the dirty data block hits the disk, the recovery manager needs the old value $V_1$ on disk so it can undo the uncommitted change.
2. **The Commit Rule:** Before the database tells the user "Your transaction succeeded!", the $\langle T_i\text{ commit}\rangle$ record (and all earlier log records for $T_i$) must be flushed to stable storage. Notice that the actual data blocks do not need to be forced to disk at commit time. They can be written to disk lazily later, because the log already has every $V_2$ value needed to redo them if a crash happens.

## Deferred vs. Immediate Database Modification

Databases can choose *when* they allow a transaction's changes to touch the shared buffer pool and disk:

| Feature | Deferred Modification | Immediate Modification |
| :--- | :--- | :--- |
| **When Buffer is Modified** | Postponed until transaction commits | Occurs immediately while transaction is active |
| **Disk Writes During Execution** | None (updates stored in private memory) | Dirty blocks can be written to disk anytime |
| **Undo Requirement** | Never needs undo (uncommitted data never reaches buffer/disk) | **Requires Undo** (uncommitted writes may reach disk before a crash) |
| **Redo Requirement** | **Requires Redo** | **Requires Redo** |
| **Memory Overhead** | High (must buffer all updates in local transaction memory) | Low (uses standard shared buffer pool) |
| **Concurrency Fit** | Snapshot isolation, validation-based concurrency | Standard Two-Phase Locking (2PL) |

Almost all modern DBMS engines use **immediate modification** because holding all changes in private memory until commit wastes RAM on large transactions.

## Undo and Redo Mechanics

When the database reboots after a crash, how does it know which transactions to roll forward (redo) and which ones to roll back (undo)? It simply checks who crossed the finish line ($\langle T_i\text{ commit}\rangle$) before the crash!

![Log state at three different times showing active updates, committed transactions, and log records](diagrams/T12.03_log_recovery_three_states__TB_fig_19_04.jpg)
*Figure 12.3: System log states during transaction execution and failure points (Silberschatz Figure 19.4).*

### 1. Classifying Transactions into Redo and Undo Lists
The recovery manager scans the log and sorts transactions into two buckets:
- **Redo-List (Finished Transactions):** Put $T_i$ in the redo-list if the log has $\langle T_i\text{ start}\rangle$ **AND** a matching $\langle T_i\text{ commit}\rangle$ (or $\langle T_i\text{ abort}\rangle$). These transactions finished before the crash, so we must make sure their final state is reflected on disk.
- **Undo-List (Interrupted Transactions):** Put $T_i$ in the undo-list if the log has $\langle T_i\text{ start}\rangle$ **BUT NEITHER** $\langle T_i\text{ commit}\rangle$ nor $\langle T_i\text{ abort}\rangle$. These transactions were cut off mid-flight by the crash, so we must erase all their partial edits.

### 2. The Redo Phase (Replaying History Forward)
First, the recovery manager scans the log **forward**:
- Whenever it sees an update record $\langle T_i, X, V_1, V_2 \rangle$ for a transaction on the redo-list, it writes the new value $V_2$ into $X$:

$$X \leftarrow V_2$$

- Notice that redo is **idempotent**: even if $V_2$ had already made it to disk before the crash, overwriting $X$ with $V_2$ again leaves the exact same value.

### 3. The Undo Phase (Rolling Back Backward)
Next, the recovery manager scans the log **backward** (from newest change to oldest change):
- Whenever it sees an update record $\langle T_i, X, V_1, V_2 \rangle$ for a transaction on the undo-list, it puts the old value $V_1$ back into $X$:

$$X \leftarrow V_1$$

- As it reverses each change, it writes a redo-only Compensation Log Record (CLR) so it tracks its own undo progress.
- Once it reaches $\langle T_i\text{ start}\rangle$, all of $T_i$'s changes have been erased, so it writes $\langle T_i\text{ abort}\rangle$ to the log and removes $T_i$ from the undo-list.

## Checkpointing: Bounding Recovery Time

If a database runs for six months and then crashes, scanning six months of log records from the very beginning would take hours. **Checkpoints** solve this by periodically saving a "known-good" bookmark in the log.

```text
Log Timeline:
──────┬──────────────────────────┬─────────────────────────────┬────────────► (Crash)
      │                          │                             │
 Transactions Prior      <checkpoint L>             Active / New Txns
 to Checkpoint           L = {T2, T3}               T2 commits, T3 active
 (Fully on Disk)                                    T4 starts & active
 NO REDO NEEDED!         REDO scan starts here       T2 in Redo, T3 & T4 in Undo
```

### The Checkpoint Procedure
To take a standard checkpoint, the database performs three steps:
1. Flush all log records currently sitting in main memory out to stable storage.
2. Flush all modified (dirty) database buffer blocks out to disk.
3. Write a bookmark record $\langle\text{checkpoint } L\rangle$ to stable storage, where $L$ lists every transaction that is still active right now.

### Why Checkpoints Speed Up Recovery
- Because Step 2 forced all dirty buffers to disk, any transaction that committed *before* $\langle\text{checkpoint } L\rangle$ already has 100% of its changes safely on the database disk. The recovery manager never needs to redo it!
- Instead of scanning from the start of the log file, the recovery manager only looks at $L$ (the transactions active at the checkpoint) plus any transactions that started after the checkpoint.

## Shadow Paging

Instead of keeping a log of old and new values, what if we never overwrote existing disk pages in the first place? **Shadow paging** uses this copy-on-write idea to recover without undo/redo logs.

```text
               ┌───────────────────────────────┐
               │    db-pointer (on disk)       │
               └──────────────┬────────────────┘
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
       [Current Page Table]          [Shadow Page Table]
         (Points to New                (Points to Old
         Modified Pages)               Untouched Pages)
               │                             │
               ▼                             ▼
     [ Page 1 (New) ]               [ Page 1 (Old) ]
     [ Page 2 (Unchanged) ] ◄───────[ Page 2 (Unchanged) ]
     [ Page 3 (New) ]               [ Page 3 (Old) ]
```

### How Shadow Paging Works
1. The database accesses pages through a directory called a **page table**, and a single pointer on disk called `db-pointer` points to the active page table.
2. When a transaction starts, the database copies the page table into a **shadow page table** (saved on disk) and makes edits using the **current page table**.
3. Whenever the transaction modifies a page, it does not overwrite the original block on disk. Instead, it allocates a fresh disk block, writes the updated page there, and updates the **current page table** to point to the new block. The **shadow page table** still points to the untouched original block.
4. **To Commit:** The system flushes all new data pages to disk and then flips `db-pointer` in a single atomic disk write so it points to the current page table.
5. **To Abort (or Recover from a Crash):** Before `db-pointer` is flipped, the shadow page table still points to the clean pre-transaction database. If a crash happens, the system just reads `db-pointer` on reboot and throws away the new pages. No undo pass is needed!

### Why Modern Databases Prefer WAL Over Shadow Paging
- **Disk Fragmentation:** Writing updated pages to brand-new blocks scatters tables that used to be stored contiguously, ruining sequential scan speeds.
- **Page Table Overhead:** Copying large page tables and garbage-collecting old blocks adds heavy I/O overhead.
- **Hard to Run Concurrently:** Shadow paging works cleanly for one transaction at a time, but supporting dozens of concurrent transactions modifying the same page table is awkward. Because of this, enterprise databases use Write-Ahead Logging instead.

## Worked Example: Checkpoint & Crash Recovery Mini-Trace

Before looking at the 9-line past exam trace in `GQ2`, let's walk through a compact 6-line crash log that includes a checkpoint. Suppose data items $X$ and $Y$ start at $X = 500$ and $Y = 300$:

```text
1. <T1 start>
2. <T1, X, 500, 450>
3. <checkpoint (T1)>
4. <T2 start>
5. <T2, Y, 300, 380>
6. <T1 commit>
*** CRASH OCCURS HERE ***
```

### Step-by-Step Recovery Walkthrough:
1. **Classify Transactions at the Crash:**
   - Find the latest checkpoint at line 3: $\langle\text{checkpoint } (T_1)\rangle$. Only $T_1$ was active at the checkpoint, and $T_2$ started after it (line 4).
   - Since $T_1$ has `<T1 commit>` at line 6, **$T_1$ goes into the Redo-List**: $\text{Redo-List} = \{T_1\}$.
   - Since $T_2$ has `<T2 start>` at line 4 but no commit record before the crash, **$T_2$ goes into the Undo-List**: $\text{Undo-List} = \{T_2\}$.
2. **Redo Phase (Scan Forward):**
   - Reapply $T_1$'s update at line 2 ($\langle T_1, X, 500, 450 \rangle$) by setting $X \leftarrow 450$.
3. **Undo Phase (Scan Backward):**
   - Reverse $T_2$'s uncommitted update at line 5 ($\langle T_2, Y, 300, 380 \rangle$) by restoring $Y$ to its old value $V_1$: $Y \leftarrow 300$, and write $\langle T_2\text{ abort}\rangle$ to the log.
4. **Final Restored Values:** $X = 450$ (committed change kept) and $Y = 300$ (uncommitted change undone).

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.6(d) · Log-Based Recovery Approach to Ensure Atomicity

> **Appeared:** 2017 Q.6(d) (3 marks) — Section B

**Question:**

Discuss shortly the log-based recovery approach to ensure atomicity despite of failures of DBMS.

**Full Answer:**

Log-based recovery ensures transaction atomicity despite system crashes and transaction aborts by maintaining an append-only log on stable storage before altering database pages on disk.

1. **Structured Log Records:**
   The DBMS creates sequential log records for every update:
   - State indicators: $\langle T_i\text{ start}\rangle$, $\langle T_i\text{ commit}\rangle$, and $\langle T_i\text{ abort}\rangle$.
   - Update record: $\langle T_i, X, V_1, V_2 \rangle$, which stores the transaction ID $T_i$, the data item identifier $X$, the prior value $V_1$ (old value for undo), and the updated value $V_2$ (new value for redo).

2. **The Write-Ahead Logging (WAL) Protocol:**
   - The update log record $\langle T_i, X, V_1, V_2 \rangle$ must be written to stable storage before the modified database buffer block containing $X$ is written to disk.
   - All log records of a transaction must reach stable storage before the transaction issues its commit acknowledgment.

3. **Enforcing Atomicity During Failure:**
   - If a transaction aborts or the system crashes while transaction $T_i$ is active (no commit record exists in the log), the recovery manager executes an $\text{undo}(T_i)$ operation.
   - The recovery manager scans the log in reverse chronological order and restores each data item $X$ to its original pre-transaction value $V_1$.
   - At the conclusion of rollback, the engine writes $\langle T_i\text{ abort}\rangle$ to the log.
   - Thus, an uncommitted transaction leaves zero partial modifications in the database, preserving the "all-or-nothing" atomicity guarantee.

### 🎯 GQ2 · 2023 Q.7(b) · Log-Based Recovery and Worked Crash Trace

> **Appeared:** 2023 Q.7(b) (4 marks) — Section B · CLO2

**Question:**

What is log based recovery? Illustrate with an example of a system crash and recovery process.

**Full Answer:**

#### 1. Definition of Log-Based Recovery
**Log-based recovery** is a fault-tolerance technique in which every database modification is recorded sequentially in a dedicated log on stable storage before being applied to the physical database on disk. By storing both old values ($V_1$) and new values ($V_2$), the recovery manager can undo incomplete transactions to enforce atomicity and redo committed transactions to enforce durability following a system crash.

#### 2. System Crash Example
Consider three concurrent transactions running on accounts $A$, $B$, and $C$ with starting balances $A = 1000$, $B = 2000$, and $C = 500$:
- $T_1$ transfers \$100 from $A$ to $B$ (commits).
- $T_2$ deposits \$200 into $C$ (commits).
- $T_3$ withdraws \$50 from $B$ (still executing at crash time).

**State of Log on Stable Storage at Moment of Crash:**
```text
1. <T1 start>
2. <T1, A, 1000, 900>
3. <T1, B, 2000, 2100>
4. <T1 commit>
5. <T2 start>
6. <T2, C, 500, 700>
7. <T3 start>
8. <T2 commit>
9. <T3, B, 2100, 2050>
---- SYSTEM CRASH OCCURS HERE ----
```

#### 3. Post-Crash Recovery Process
When the database restarts, the recovery manager carries out three steps:

**Phase A: Transaction Classification**
The log is scanned to categorize active transactions:
- **Redo-List** $= \{T_1, T_2\}$ (both transactions contain matching `<start>` and `<commit>` records).
- **Undo-List** $= \{T_3\}$ (contains `<T3 start>` but lacks a `<commit>` or `<abort>` record).

**Phase B: Redo Operations (Forward Scan)**
The recovery manager scans forward and re-applies updates for committed transactions:
- Reapply line 2 ($T_1$): set $A \leftarrow 900$.
- Reapply line 3 ($T_1$): set $B \leftarrow 2100$.
- Reapply line 6 ($T_2$): set $C \leftarrow 700$.

**Phase C: Undo Operations (Backward Scan)**
The recovery manager scans backward and reverses updates for uncommitted transactions:
- Undo line 9 ($T_3$): restore $B \leftarrow 2100$ using the old value $V_1 = 2100$.
- Output $\langle T_3\text{ abort}\rangle$ to the log on stable storage.

#### 4. Final Database Values
- Account $A = 900$
- Account $B = 2100$
- Account $C = 700$

All updates of committed transactions $T_1$ and $T_2$ are preserved, while the incomplete update of $T_3$ is erased.

### 🎯 HYE-01 · Practice Exercise 19.1 · Reverse Ordering in Undo Recovery

> **Source:** Silberschatz 7e · Chapter 19 (Practice Exercise 19.1)  
> **Exam Relevance:** High-Probability Recovery Theory Question  
> **Key Tested Concept:** Why log records on the undo-list must be processed in reverse chronological order (backward scan).

**Problem Statement:**
> During database recovery using log-based recovery with immediate update, why is it essential that the **undo** phase processes log records in **reverse chronological order** (from the end of the log toward the beginning), rather than in forward chronological order? Provide a concrete example showing data corruption if forward processing were used.

**Model Exam-Style Solution:**

1. **The Theoretical Reason:**
   - A single uncommitted transaction (or multiple uncommitted transactions) may update the **same data item $Q$ multiple times** before a crash occurs.
   - Each update generates an update log record $\langle T_i, Q, V_{\text{old}}, V_{\text{new}} \rangle$.
   - To satisfy the **Atomicity** requirement, undoing a transaction requires restoring data item $Q$ to the value it held **prior to the start of the transaction**.
   - Processing in reverse chronological order (backward) guarantees that the earliest pre-image is applied last, leaving the data item in its correct pre-transaction state.

2. **Concrete Demonstration of Data Corruption under Forward Undo:**
   - Suppose data item $A$ initially has value $A = 10$.
   - Transaction $T_1$ updates $A$ twice, and the crash occurs before $T_1$ commits:
     1. $T_1$ modifies $A$ to $20 \implies \text{Log: } \langle T_1, A, 10, 20 \rangle$
     2. $T_1$ modifies $A$ to $30 \implies \text{Log: } \langle T_1, A, 20, 30 \rangle$
     3. **CRASH!**
   - **Correct Reverse Undo (Backward Scan):**
     1. First process $\langle T_1, A, 20, 30 \rangle \implies \text{restore } A := 20$.
     2. Next process $\langle T_1, A, 10, 20 \rangle \implies \text{restore } A := \mathbf{10}$.
     3. **Final Result:** $A = 10$, which is the original value before $T_1$ started ($\checkmark$).
   - **Flawed Forward Undo:**
     1. First process $\langle T_1, A, 10, 20 \rangle \implies \text{restore } A := 10$.
     2. Next process $\langle T_1, A, 20, 30 \rangle \implies \text{restore } A := \mathbf{20}$.
     3. **Final Result:** $A = 20$. The database contains an intermediate uncommitted value produced by $T_1$! Atomicity is violated, and the database is corrupt.

3. **Conclusion:**
   The undo phase must scan **backward** so that the oldest before-image overwrites any intermediate updates. $\blacksquare$

**💡 RUET Exam Takeaway:**
Redo scans **FORWARD** (replaying history to bring the database to the crash state); Undo scans **BACKWARD** (peeling away uncommitted changes to reach consistent past states).

### 🎯 HYE-02 · Practice Exercise 19.2 · Checkpoint Mechanism & Frequency Trade-offs

> **Source:** Silberschatz 7e · Chapter 19 (Practice Exercise 19.2)  
> **Exam Relevance:** High-Probability Exam Theory Drill  
> **Key Tested Concept:** Checkpoint execution steps, bounding log recovery scans, and checkpoint frequency trade-offs.

**Problem Statement:**
> 1. Describe the precise sequence of operations executed by the database recovery manager during a **checkpoint operation**.
> 2. Explain why checkpointing bounds the log scan during recovery, eliminating the need to scan back to the beginning of the log.
> 3. Analyze the trade-offs involved in choosing the **frequency of checkpoints**.

**Model Exam-Style Solution:**

1. **Steps in a Checkpoint Operation:**
   During a checkpoint, the DBMS performs four sequential steps:
   1. Output to stable storage all log records currently residing in main memory log buffers.
   2. Output to disk all modified database buffer blocks (dirty pages) residing in cache.
   3. Write a log record $\langle \text{checkpoint } L \rangle$ to stable storage, where $L$ is the list of all transactions currently active at the time of the checkpoint.
   4. Output the checkpoint record to stable storage.

2. **How Checkpoints Bound the Recovery Scan:**
   - Without checkpoints, the recovery manager must scan the log all the way back to system creation because it cannot know which committed transactions had their changes written to disk.
   - With a checkpoint record $\langle \text{checkpoint } L \rangle$:
     - Any transaction $T_k$ that committed *before* the checkpoint has already had all its dirty pages forced to disk (by Step 2). Thus, **$T_k$ never needs to be redone**!
     - Recovery only needs to scan back to the start of the oldest active transaction in list $L$.
     - Transactions outside $L$ that completed prior to the checkpoint can be completely ignored.

3. **Checkpoint Frequency Trade-offs:**
   - **High Checkpoint Frequency (Very Often):**
     - *Advantage:* Recovery time after a crash is extremely short because very few log records need to be scanned and redone/undone.
     - *Disadvantage:* High runtime overhead. Forcing dirty buffer pages to disk disrupts normal transaction processing, consumes disk I/O bandwidth, and degrades system throughput.
   - **Low Checkpoint Frequency (Infrequent):**
     - *Advantage:* Minimal I/O disruption during normal runtime, maximizing query throughput.
     - *Disadvantage:* Recovery time after a crash is very long because the recovery manager must scan a massive log segment, redoing and undoing hundreds of transactions. $\blacksquare$

**💡 RUET Exam Takeaway:**
When listing the steps of a checkpoint, explicitly include the active transaction list $L$ in the $\langle \text{checkpoint } L \rangle$ record.

### 🎯 HYE-03 · Practice Exercise 19.4 · Two-Phase Crash Recovery Algorithmic Trace

> **Source:** Silberschatz 7e · Chapter 19 (Practice Exercise 19.4)  
> **Exam Relevance:** Prime Overdue Mathematical Recovery Trace  
> **Key Tested Concept:** Classification of transactions into Redo-list and Undo-list, forward Redo phase, and backward Undo phase execution.

**Problem Statement:**
> The following log records reside on stable storage at the time of a system crash. The database uses immediate modification with logging:
> $$
> \begin{aligned}
> &\langle T_0 \text{ start} \rangle \\
> &\langle T_0, A, 100, 150 \rangle \\
> &\langle T_1 \text{ start} \rangle \\
> &\langle T_1, B, 50, 75 \rangle \\
> &\langle T_0 \text{ commit} \rangle \\
> &\langle \text{checkpoint } \{T_1\} \rangle \\
> &\langle T_2 \text{ start} \rangle \\
> &\langle T_2, C, 200, 250 \rangle \\
> &\langle T_1, D, 80, 90 \rangle \\
> &\langle T_2 \text{ commit} \rangle \\
> &\langle T_3 \text{ start} \rangle \\
> &\langle T_3, A, 150, 180 \rangle \\
> &\text{--- SYSTEM CRASH ---}
> \end{aligned}
> $$
> 1. Identify which transactions belong to the **Redo-list** and which belong to the **Undo-list**.
> 2. Trace the recovery process, showing all values written to $A, B, C, D$.
> 3. State the final values of $A, B, C, D$ in the database after recovery completes.

**Model Exam-Style Solution:**

1. **Transaction Classification:**
   - Scan log forward from the checkpoint $\langle \text{checkpoint } \{T_1\} \rangle$:
     - Initial active set from checkpoint: $\{T_1\}$.
     - $\langle T_2 \text{ start} \rangle \implies$ add $T_2$. Active: $\{T_1, T_2\}$.
     - $\langle T_2 \text{ commit} \rangle \implies T_2$ committed! Move to **Redo-list**. Active: $\{T_1\}$.
     - $\langle T_3 \text{ start} \rangle \implies$ add $T_3$. Active: $\{T_1, T_3\}$.
     - Crash occurs.
   - **Classification Result:**
     - **Redo-List:** Transactions that have both `start` and `commit` records:
       $$
       \text{Redo-List} = \{T_0, T_2\}
       $$
       *(Note: $T_0$ committed before checkpoint, but in ARIES/standard log recovery, redo scans from the oldest unwritten change; here $T_2$ is redone).*
     - **Undo-List:** Transactions that started but have no `commit` or `abort` record:
       $$
       \text{Undo-List} = \{T_1, T_3\}
       $$

2. **Step-by-Step Recovery Execution:**

   - **Phase 1: Redo Phase (Scan Forward):**
     - Replays all updates of committed transactions to restore database state:
       - Redo $\langle T_2, C, 200, 250 \rangle \implies \text{set } C := 250$.
     - *(Note: In modern ARIES "repeating history", all logged changes are redone first, then undo executes).*

   - **Phase 2: Undo Phase (Scan Backward from Crash):**
     - Undoes updates of all transactions on the Undo-list ($\{T_1, T_3\}$) using pre-images:
       1. $\langle T_3, A, 150, 180 \rangle$: $T_3 \in \text{Undo-list} \implies \text{restore } A := \mathbf{150}$.
       2. $\langle T_1, D, 80, 90 \rangle$: $T_1 \in \text{Undo-list} \implies \text{restore } D := \mathbf{80}$.
       3. $\langle T_2, C, 200, 250 \rangle$: $T_2 \notin \text{Undo-list}$ (skip).
       4. $\langle T_1, B, 50, 75 \rangle$: $T_1 \in \text{Undo-list} \implies \text{restore } B := \mathbf{50}$.
     - Write abort log records for uncommitted transactions: $\langle T_3 \text{ abort} \rangle$, $\langle T_1 \text{ abort} \rangle$.

3. **Final Values of Database Items:**
   - $A = \mathbf{150}$ (restored by undoing $T_3$, retaining $T_0$'s committed update).
   - $B = \mathbf{50}$ (restored by undoing $T_1$'s update).
   - $C = \mathbf{250}$ (redone from $T_2$'s committed update).
   - $D = \mathbf{80}$ (restored by undoing $T_1$'s update). $\blacksquare$

**💡 RUET Exam Takeaway:**
Always divide recovery clearly into the **Redo phase** (forward scan) and **Undo phase** (backward scan), and present a neat final summary table of all variable values.

## ⚡ Exam Tips & Common Mistakes

1. **Four-Field Log Record Trap:** An update record must include four items: $\langle T_i, X, V_1, V_2 \rangle$. Omitting the old value $V_1$ means the system cannot undo, and omitting $V_2$ means it cannot redo.
2. **Never Put Uncommitted Transactions in the Redo List:** A transaction enters the redo list if and only if it has both a `<start>` record and a `<commit>` record (or an `<abort>` record that had logged compensation records).
3. **Write-Ahead Logging Order:** Always state clearly that the log record must reach stable disk storage *before* the dirty database page is written to disk.
4. **Idempotency of Redo:** Mention that redo operations are idempotent. If a recovery phase crashes and restarts, re-running redo produces the same correct state.
5. **Shadow Paging Drawback:** If asked about shadow paging, always mention **disk fragmentation** and poor concurrency support. That explains why enterprise databases use WAL instead.
