# T02.2: Attribute Types

> **Topic:** T02 — E-R & EER Modeling | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (8 marks)  
> **Sources:** Silberschatz 7e Ch. 6 (§6.2, §6.3, pp. 244–252) · Lecture Deck 05 (Slides 17–19) · Classnote by Raidah (p. 18) · Handnote by Fahim (pp. 26–27)

## Why This Topic Matters

Attributes describe the actual pieces of data we store about entities and relationships, such as a student's name, phone numbers, or date of birth. RUET semester exams regularly test this topic through 4-mark questions that ask for definitions, comparison tables, and E-R diagram symbols. Understanding how different attribute types work also sets you up for converting E-R diagrams into relational tables and enforcing First Normal Form (1NF) in Topic T08.

---

## 📝 Key Definitions

> **Entity:** An entity is a real-world object or thing that can be clearly told apart from all other objects. Each entity is described by its own attribute values, such as a specific student or instructor.

> **Attribute:** An attribute is a descriptive property possessed by every member of an entity set. In Chen E-R notation, an attribute is drawn as an oval connected to its entity rectangle.

> **Domain:** The domain (or value set) of an attribute is the set of all allowed values for that attribute. Every value stored for that attribute must come from its domain.

> **Composite Attribute:** A composite attribute is an attribute that can be split into smaller, meaningful subparts. For example, `name` can be divided into `first_name`, `middle_initial`, and `last_name`.

> **Multivalued Attribute:** A multivalued attribute is an attribute that can hold multiple values for a single entity at once. It is drawn as a double oval in Chen notation, such as `phone_number`.

> **Derived Attribute:** A derived attribute is an attribute whose value is calculated on the fly from other stored attributes. It is not stored physically on disk and is drawn as a dashed oval, such as `age` calculated from `date_of_birth`.

---

## Core Classification of Attributes

Every attribute in an E-R diagram can be classified along three independent questions: *Can it be broken into smaller subparts? Can one entity have multiple values for it at the same time? And is it stored directly on disk or calculated on the fly?*

1. **Divisibility:** Simple (Atomic) vs. Composite
2. **Cardinality of Values:** Single-Valued vs. Multivalued
3. **Storage Source:** Stored (Base) vs. Derived

## 1. Simple vs. Composite Attributes

### Simple (Atomic) Attributes
- Simple attributes are atomic values that cannot be split into smaller, meaningful subparts.
- Because you always read or compare them as a single unit, they map directly to a normal column in a table.
- *Examples:* `salary`, `student_id`, `credits`, `gpa`.

### Composite Attributes
- Composite attributes can be broken down into smaller subparts, where each subpart has its own independent meaning.
- Grouping related fields under a composite attribute keeps the conceptual design tidy, and you can even nest them (for instance, `address` contains `street`, which splits further into `street_number`, `street_name`, and `apt_number`).
- *Examples:*
  - `name` $\rightarrow$ `first_name`, `middle_initial`, `last_name`.
  - `address` $\rightarrow$ `street`, `city`, `state`, `zip_code`.

### Comparison: Simple vs. Composite

| Feature | Simple (Atomic) Attribute | Composite Attribute |
| :--- | :--- | :--- |
| **Divisibility** | Indivisible. Cannot be broken into smaller meaningful parts. | Divisible. Made up of smaller independent attributes. |
| **Structure** | Flat, single scalar value. | Hierarchical tree of component parts. |
| **Chen E-R Notation** | Single ellipse connected to the entity rectangle. | Ellipse branching out into smaller sub-ellipses. |
| **Relational Mapping** | Becomes a single column in a relational table. | Flattened so each leaf subpart becomes its own column. |
| **When to Use** | When the attribute is always queried as a whole unit. | When queries need to filter or sort by individual parts (e.g., `last_name`). |
| **Examples** | `salary`, `credits`, `nid` | `name` (`first_name`, `last_name`), `address` (`city`, `state`, `zip`) |

---

## 2. Single-Valued vs. Multivalued Attributes

### Single-Valued Attributes
- A single-valued attribute holds at most one value for any given entity, which is true for the vast majority of table columns you see in everyday databases.
- *Examples:* `date_of_birth`, `national_id`, `department_name`.

### Multivalued Attributes
- Sometimes a single person or object legitimately has several values of the same kind at once, so a multivalued attribute lets one entity hold a set of zero, one, or many values.
- In formal notation, if a single phone number comes from a domain $D$, a multivalued attribute's value is a subset of $D$, written as the power set $2^D$.
- *Examples:*
  - `phone_numbers`: an instructor might have two mobile numbers and a home landline.
  - `degrees`: a professor might hold a B.Sc., M.Sc., and Ph.D.
  - `dependent_names`: an employee might have several family dependents.

### Comparison: Single-Valued vs. Multivalued

| Feature | Single-Valued Attribute | Multivalued Attribute |
| :--- | :--- | :--- |
| **Values per Entity** | At most one value (or null) per entity record. | A set of zero, one, or many values per record. |
| **Domain Type** | Atomic domain values (e.g., integer, string). | Set domain: $2^{\text{Domain}}$ (subsets of allowed values). |
| **Chen E-R Notation** | Single ellipse. | Double concentric ellipse ($\large\boldsymbol{\odot}$). |
| **Tabular E-R Notation** | Listed directly as the attribute name. | Enclosed in curly braces, e.g., `{ phone_number }`. |
| **Relational Reduction** | Stored directly as a column in the entity table. | Moved to a separate child table with a foreign key to satisfy 1NF. |
| **Examples** | `date_of_birth`, `roll_no`, `salary` | `phone_numbers`, `skills`, `degrees` |

---

## 3. Stored vs. Derived Attributes

### Stored (Base) Attributes
- A stored attribute is written physically to disk inside the table and serves as the raw source of truth.
- *Examples:* `date_of_birth`, `admission_date`, `unit_price`, `quantity`.

### Derived Attributes
- A derived attribute is not saved on disk because its value can be calculated whenever you need it from other stored attributes or related records.
- Calculating the value on demand saves storage space and guarantees the number never goes stale as time passes or underlying records change.
- *Examples:*
  - `age`: calculated on the fly from `current_date - date_of_birth`.
  - `total_price`: calculated from `unit_price * quantity`.
  - `students_advised`: calculated by counting the instructor's rows in the `advisor` table.

### Comparison: Stored vs. Derived

| Feature | Stored (Base) Attribute | Derived Attribute |
| :--- | :--- | :--- |
| **Storage Location** | Saved physically in disk blocks. | Not stored on disk, computed dynamically when queried. |
| **Data Freshness** | Can become outdated if related facts change without an update. | Always fresh because it is recalculated at query time. |
| **Chen E-R Notation** | Solid ellipse. | Dashed ellipse. |
| **Tabular E-R Notation** | Listed as a standard attribute name. | Written with empty parentheses, e.g., `age ()`. |
| **Implementation** | Normal table column with a standard data type. | SQL views, generated columns, or expressions in a `SELECT` query. |
| **Examples** | `date_of_birth`, `hourly_rate` | `age`, `gross_pay`, `students_advised` |

---

## 4. Null Values

When an entity does not have an applicable or known value for an attribute, the database uses a special **null** marker. Silberschatz points out three real-world situations where `NULL` appears:
1. **Not Applicable:** The property simply does not apply to this entity (such as `apt_number` for someone living in a single-family house).
2. **Missing (Unknown Value):** The value exists in the real world, but we do not know what it is yet (such as a customer whose middle initial was left blank on a form).
3. **Unknown Whether It Exists:** We do not even know if the entity has a value for this attribute (for example, we do not know whether a new student has a landline phone number).

## Relational Schema Reduction Rules

**Why We Transform Complex Attributes:** Relational tables must obey First Normal Form (1NF), which means every cell in a table can hold only a single, indivisible value. You cannot stuff a list of three phone numbers or a nested address tree into one SQL cell and still query it cleanly. Because of this, we convert complex attributes into flat table columns using four rules:

1. **Simple Attributes:** Become regular columns in the entity's table.
2. **Composite Attributes:** Get flattened out. We drop the parent label (like `name`) and create a separate column for each leaf subpart:
   $$
   \text{instructor}(\dots, \text{first\_name}, \text{last\_name}, \dots)
   $$
3. **Multivalued Attributes:** Get moved into their own separate table. This new table combines the parent entity's primary key (as a foreign key) with a column for the individual values, and the two columns together form the composite primary key:
   $$
   \text{instructor\_phone}(\underline{\text{ID}}, \underline{\text{phone\_number}})
   $$
4. **Derived Attributes:** Are left out of the physical table altogether and computed on the fly in SQL queries or views:
   ```sql
   SELECT ID, TIMESTAMPDIFF(YEAR, date_of_birth, CURDATE()) AS age
   FROM instructor;
   ```

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.5(a) · Differentiate Attribute Types

> **Appeared:** 2020 Q.5(a) — (4 marks)

> **Question:**
> Differentiate between-  
> (i) Simple and composite attribute  
> (ii) Single-valued and multi-valued attribute

**Full Answer:**

#### (i) Simple vs. Composite Attribute

| Feature | Simple (Atomic) Attribute | Composite Attribute |
| :--- | :--- | :--- |
| **Definition** | Cannot be divided into smaller subparts and holds a single atomic value. | Can be divided into smaller subparts that act as independent attributes. |
| **Structure** | Flat and indivisible. | Forms a hierarchy of component attributes. |
| **E-R Notation** | Drawn as a single ellipse attached to the entity rectangle. | Drawn as an ellipse branching out to multiple sub-ellipses. |
| **Relational Storage** | Maps directly to a single column in the relational table. | Flattened into separate columns for each component subpart. |
| **Example** | `salary`, `student_id`, `credits` | `name` (`first_name`, `last_name`), `address` (`street`, `city`, `zip_code`) |

#### (ii) Single-Valued vs. Multi-Valued Attribute

| Feature | Single-Valued Attribute | Multi-Valued Attribute |
| :--- | :--- | :--- |
| **Definition** | Holds at most one value for a specific entity instance. | Can hold a set of multiple values for a single entity instance. |
| **Values per Entity** | At most one value per record. | Zero, one, or many values per record. |
| **E-R Notation** | Drawn as a single ellipse. | Drawn as a double (concentric) ellipse or written in braces `{ attribute }`. |
| **Table Conversion** | Stored directly as a column in the main entity table. | Placed in a separate child table with the entity's primary key to satisfy 1NF. |
| **Example** | `date_of_birth`, `roll_no`, `nid` | `phone_numbers`, `degrees`, `email_addresses` |

### 🎯 GQ2 · 2021 Q.3(b) · Entity, Attribute, and Complex Attributes

> **Appeared:** 2021 Q.3(b) — (4 marks)

> **Question:**
> Define entity and attribute. Explain the following attributes-  
> (i) Multi-valued  
> (ii) Derived  
> (iii) Composite

**Full Answer:**

#### Definitions

- **Entity:** An entity is a real-world "thing" or "object" that can be distinguished from all other objects through its properties (for example, a specific instructor with `ID = 22222` or a particular student).
- **Attribute:** An attribute is a descriptive property shared by every member of an entity set, used to record a specific detail about each entity (such as `name`, `dept_name`, or `salary`).

#### Explanation of Attribute Types

1. **Multi-Valued Attribute:**
   - **Concept:** An attribute that can hold a set of several values for the same entity instance at the same time.
   - **E-R Notation:** Drawn as a **double ellipse** (concentric ovals) in Chen notation, or enclosed in curly braces `{ attribute }` in tabular notation.
   - **Relational Storage:** Because relational tables require atomic cells (1NF), a multivalued attribute is moved into its own separate table linked back to the parent entity's primary key.
   - **Example:** An instructor can have multiple contact numbers stored under `phone_numbers` (`{0171..., 0181...}`).

2. **Derived Attribute:**
   - **Concept:** An attribute whose value is not stored physically on disk, but is calculated on the fly from other stored attributes or related records whenever queried.
   - **E-R Notation:** Drawn as a **dashed ellipse** in Chen notation, or written with parentheses `attribute ()` in tabular notation.
   - **Advantage:** Avoids stale data. If you stored a person's `age` as a fixed integer, it would become wrong every year, whereas deriving it from `date_of_birth` keeps it accurate automatically.
   - **Example:** `age` computed from `current_date - date_of_birth`.

3. **Composite Attribute:**
   - **Concept:** An attribute that can be broken down into smaller, meaningful subparts, where each subpart has its own domain.
   - **E-R Notation:** Drawn as an ellipse connected to smaller component sub-ellipses.
   - **Advantage:** Lets users refer to the whole group at once or filter and sort by individual subparts.
   - **Example:** `name` divided into `first_name`, `middle_initial`, and `last_name`.

## ⚡ Exam Tips & Common Mistakes

1. **Always provide concrete examples:** Examiners deduct half marks if you state definitions without realistic database examples. Mention examples like `salary`, `name`, `phone_numbers`, and `age`.
2. **Do not confuse composite with multivalued:** A composite attribute contains multiple subparts with *different meanings* (e.g., `street` and `city`). A multivalued attribute contains multiple values of the *exact same meaning* (e.g., two phone numbers).
3. **Remember the 1NF rule:** When asked how attributes map to tables, state that multivalued attributes violate First Normal Form (1NF) if stored in a single cell. They must be moved to a separate table.
4. **Draw correct Chen symbols:** In written exams, draw concentric double ellipses for multivalued attributes and dashed ellipses for derived attributes.
