# T10.5: View Serializability and Blind Writes

> **Topic:** T10 — Serializability | **Priority:** 🟢 | **Exam Frequency:** 1/7 finals (6 marks)
> **Sources:** Silberschatz 7e Ch. 18 (§18.5 Note 18.1, p. 867) · Lecture Deck 07 (Slides 22–23, 27) · Raidah Notes (p. 27–28)

## Why This Topic Matters

Conflict serializability is fast to test with a precedence graph, but it is sometimes *too strict*. Because conflict serializability cares only about whether conflicting instructions can be swapped, it rejects certain schedules that are actually 100% safe and produce the exact same result as a serial run. This happens when transactions perform **blind writes**, which means writing to a data item without reading it first. **View serializability** looks at what really matters for correctness: which values each transaction reads and which transaction writes the final value to the database. Tested in 2020 Q.6(b) for 6 marks, this topic is a favorite for testing both your conceptual understanding of blind writes and your ability to verify the three view-equivalence rules step by step.

---

## 📝 Key Definitions

> **View Equivalence:** Two schedules $S$ and $S'$ over the same set of transactions are view equivalent if they satisfy three conditions for every data item $Q$:
> 1. **Initial Read:** If transaction $T_i$ reads the initial value of $Q$ in $S$, then $T_i$ must also read the initial value of $Q$ in $S'$.
> 2. **Updated Read (Read-From):** If transaction $T_i$ reads a value of $Q$ written by $T_j$ in $S$, then $T_i$ must read the value produced by that exact same $\text{write}(Q)$ operation of $T_j$ in $S'$.
> 3. **Final Write:** The transaction that performs the final $\text{write}(Q)$ at the end of $S$ must also perform the final $\text{write}(Q)$ in $S'$.

> **View Serializability:** A schedule $S$ is view serializable if it is view equivalent to some serial schedule. Every conflict-serializable schedule is automatically view serializable, but some view-serializable schedules with blind writes are not conflict serializable.

> **Blind Write:** A blind write is a $\text{write}(Q)$ operation executed by a transaction without having read data item $Q$ first. Every schedule that is view serializable but not conflict serializable must contain at least one blind write.

---

## Core Theory: The Three Rules of View Equivalence

### Intuition: Same Inputs In, Same Final State Out

Instead of asking *"Can I swap adjacent steps?"*, view equivalence asks a much simpler question: **"Does every transaction see the exact same data, and does the database end up with the exact same final values?"**

Suppose $S$ is a concurrent schedule and $S'$ is a candidate serial schedule over the same transactions. To check if $S$ and $S'$ are view equivalent, we check three rules for every data item $Q$:

### 1. Initial Read Rule (Who Sees the Starting Value?)
If transaction $T_i$ reads the original starting value of $Q$ in $S$ (before anyone has written to $Q$), then $T_i$ must also read the original starting value of $Q$ in $S'$.

### 2. Updated Read / Read-From Rule (Who Reads Whose Write?)
If transaction $T_i$ reads a value of $Q$ that was written by transaction $T_j$ in $S$, then $T_i$ must read the value produced by that exact same $\text{write}(Q)$ of $T_j$ in $S'$.

### 3. Final Write Rule (Who Leaves the Last Value?)
If transaction $T_k$ performs the very last $\text{write}(Q)$ at the end of schedule $S$, then $T_k$ must also perform the very last $\text{write}(Q)$ in $S'$.

Together, Rules 1 and 2 guarantee that every transaction reads the exact same inputs in both schedules (so it computes the exact same values), while Rule 3 guarantees that the final value left on disk for $Q$ is identical when everyone finishes.

---

## Blind Writes: Why a Schedule with a Precedence Cycle Can Still Be Safe

A **blind write** is a $\text{write}(Q)$ operation performed by a transaction that never executed $\text{read}(Q)$ first:

```text
T2: write(Q);   -- Blind write: T2 overwrites Q without ever reading Q first
```

In most everyday transactions, a write depends on an earlier read (such as `read(Q); Q := Q + 100; write(Q)`). In a blind write, the transaction simply stamps a new value onto $Q$ (like resetting a status flag or setting `Q := 0`) without looking at what was stored in $Q$ before.

### The Whiteboard Analogy: Why Precedence Graphs Get Fooled by Blind Writes

Imagine three people sharing an office whiteboard $Q$ that starts with the number `10`:
1. **$T_1$ looks at the board** (`read(Q)`) and sees `10`, then starts doing some math at their desk.
2. While $T_1$ is calculating, **$T_2$ walks up without looking at the board and writes `99`** (`write(Q)`).
3. Before anyone in the room ever looks at $T_2$'s `99`, **$T_1$ walks back up, erases `99`, and writes `25`** (`write(Q)`).
4. Finally, **$T_3$ walks up without looking, erases `25`, and writes `500`** (`write(Q)`).

Now ask yourself: **Did $T_2$'s write of `99` have any effect on anyone?**
- **No!** Nobody ever read `99`, and $T_1$ and $T_3$ immediately wiped it out. Whether $T_2$ wrote `99` before $T_1$'s write or after $T_1$'s write, $T_1$ still read `10` at the beginning and $T_3$ still left `500` on the board at the end!
- Yet **the precedence graph panics**: because $T_1$ read $Q$ before $T_2$ wrote $Q$ ($T_1 \to T_2$), and $T_2$ wrote $Q$ before $T_1$ wrote $Q$ ($T_2 \to T_1$), the precedence graph sees a cycle $T_1 \leftrightarrow T_2$ and declares the schedule **not conflict serializable**.
- **View serializability sees the truth:** Because $T_2$'s blind write was overwritten without ever being read, the schedule produces the exact same data flow and final state as the serial schedule $\langle T_1, T_2, T_3 \rangle$.

> **Key Rule to Remember:** Every view-serializable schedule that is *not* conflict serializable **must contain at least one blind write**. If a schedule has no blind writes at all, conflict serializability and view serializability give the exact same answer.

---

## Conflict Serializability vs. View Serializability

| Feature | Conflict Serializability | View Serializability |
| :--- | :--- | :--- |
| **Core Idea** | Preserves the order of all conflicting pairs ($R\text{-}W, W\text{-}R, W\text{-}W$) | Preserves initial reads, read-from pairs, and final writes |
| **How We Test It** | Precedence graph cycle check | Check the 3 view rules against candidate serial orders (NP-complete in general) |
| **Time Complexity** | Fast: $\mathcal{O}(V + E)$ polynomial time | Slow: Exponential time in the worst case |
| **How Strict Is It?** | Stricter (a smaller subset of schedules) | Broader (accepts safe schedules with blind writes) |
| **Blind Writes** | Rejects safe schedules if an unread blind write creates a cycle | Accepts them as long as the 3 view rules hold |
| **Real-World DBMS Use** | Used by standard 2PL lock managers and basic timestamp ordering | Theoretical gold standard, used in optimizations like Thomas' Write Rule |

The relationship between these schedule classes is a strict subset hierarchy:

$$
\text{Conflict Serializable Schedules} \subset \text{View Serializable Schedules} \subset \text{All Serializable Schedules}
$$

Every conflict-serializable schedule is automatically view serializable, but a view-serializable schedule with blind writes is not necessarily conflict serializable.

## Worked Example: View Serializability with Blind Writes

Consider the following classic schedule $S$ with transactions $T_1$, $T_2$, and $T_3$ operating on data item $Q$:

| Step | $T_1$ | $T_2$ | $T_3$ |
| :--: | :--- | :--- | :--- |
| 1 | $\text{read}(Q)$ | | |
| 2 | | $\text{write}(Q)$ | |
| 3 | $\text{write}(Q)$ | | |
| 4 | | | $\text{write}(Q)$ |

### Step 1: Check Conflict Serializability
Let us analyze the conflicting pairs on item $Q$:
- Step 1 ($\text{read}_1(Q)$) before Step 2 ($\text{write}_2(Q)$) $\implies T_1 \to T_2$.
- Step 2 ($\text{write}_2(Q)$) before Step 3 ($\text{write}_1(Q)$) $\implies T_2 \to T_1$.

We have edges $T_1 \to T_2$ and $T_2 \to T_1$. This forms a directed cycle:
$$
T_1 \longleftrightarrow T_2
$$
Because the precedence graph contains a cycle, schedule $S$ is **not conflict serializable**.

### Step 2: Check View Equivalence with Serial Schedule $S' = \langle T_1, T_2, T_3 \rangle$
Let us test the three view equivalence conditions:
1. **Initial read:**
   - In $S$: $T_1$ reads the initial database value of $Q$ at Step 1.
   - In $S'$ ($\langle T_1, T_2, T_3 \rangle$): $T_1$ executes first, reading the initial database value of $Q$. Condition 1 holds.
2. **Updated read (read-from):**
   - In $S$: Neither $T_2$ nor $T_3$ reads $Q$. No transaction reads a value produced by another transaction.
   - In $S'$: No transaction reads a value produced by another transaction. Condition 2 holds vacuously.
3. **Final write:**
   - In $S$: $T_3$ executes the final write on $Q$ at Step 4.
   - In $S'$: $T_3$ executes last, performing the final write on $Q$. Condition 3 holds.

All three view conditions are satisfied. Therefore, schedule $S$ is **view serializable**, equivalent to the serial schedule $\langle T_1, T_2, T_3 \rangle$.

Notice that $T_2$ and $T_3$ executed blind writes. Step 2 wrote to $Q$ without reading it, and was immediately overwritten by Step 3.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.6(b) · View Serializability Definition & Schedule Verification

> **Appeared:** 2020 Q.6(b) — (06 marks)

**Question:**

What is view serializability? Why do we need view serializability? Check the view serializability of the following schedule if any.

| $T_1$ | $T_2$ |
| :---: | :---: |
| $R(X)$ | |
| $W(X)$ | |
| | $R(X)$ |
| | $W(X)$ |
| $R(Y)$ | |
| $W(Y)$ | |
| | $R(Y)$ |
| | $W(Y)$ |

**Full Answer:**

#### Part 1: What is View Serializability?
A schedule $S$ is **view serializable** if it is view equivalent to some serial schedule $S'$. Two schedules $S$ and $S'$ over the same transactions are **view equivalent** if they satisfy three conditions for every data item $Q$:
1. **Initial Read:** If transaction $T_i$ reads the initial value of $Q$ in $S$, then $T_i$ must also read the initial value of $Q$ in $S'$.
2. **Read-From (Updated Read):** If transaction $T_i$ reads a value of $Q$ written by transaction $T_j$ in $S$, then $T_i$ must read the value produced by that same write operation of $T_j$ in $S'$.
3. **Final Write:** If transaction $T_k$ executes the final write on $Q$ in $S$, then $T_k$ must execute the final write on $Q$ in $S'$.

#### Part 2: Why Do We Need View Serializability?
We need view serializability for three primary reasons:
1. **Conflict serializability is too restrictive:** Conflict serializability requires preserving the order of all conflicting operations. It rejects schedules that alter conflicting instruction orders even when data flow remains intact.
2. **Accommodating blind writes:** When transactions write data without prior reading, intermediate writes may be overwritten without affecting any transaction. Conflict serializability rejects such schedules. View serializability correctly recognizes them as serializable.
3. **Foundational correctness benchmark:** It defines the exact semantic boundary where transactions read identical states and leave the database in an identical state. Protocols such as Thomas' Write Rule rely on view serializability to achieve higher concurrency.

#### Part 3: Checking View Serializability of the Given Schedule
Let the given schedule be $S$. We index the operations chronologically:

| Step | $T_1$ | $T_2$ | Description |
| :--: | :-- | :-- | :-- |
| 1 | $\text{read}(X)$ | | $T_1$ reads initial $X$ |
| 2 | $\text{write}(X)$ | | $T_1$ updates $X$ |
| 3 | | $\text{read}(X)$ | $T_2$ reads $X$ produced by $T_1$ |
| 4 | | $\text{write}(X)$ | $T_2$ performs final write on $X$ |
| 5 | $\text{read}(Y)$ | | $T_1$ reads initial $Y$ |
| 6 | $\text{write}(Y)$ | | $T_1$ updates $Y$ |
| 7 | | $\text{read}(Y)$ | $T_2$ reads $Y$ produced by $T_1$ |
| 8 | | $\text{write}(Y)$ | $T_2$ performs final write on $Y$ |

We test if $S$ is view equivalent to the serial schedule $S' = \langle T_1, T_2 \rangle$:

1. **Initial read condition:**
   - In schedule $S$: $T_1$ reads the initial value of $X$ at Step 1 and the initial value of $Y$ at Step 5.
   - In serial schedule $\langle T_1, T_2 \rangle$: $T_1$ executes first, so it reads the initial values of both $X$ and $Y$.
   - **Condition 1 holds.**

2. **Read-from (updated read) condition:**
   - In schedule $S$: $T_2$ reads $X$ written by $T_1$ (Step 3 reads Step 2). $T_2$ reads $Y$ written by $T_1$ (Step 7 reads Step 6).
   - In serial schedule $\langle T_1, T_2 \rangle$: $T_1$ executes completely before $T_2$. Thus $T_2$ reads the updated values of $X$ and $Y$ written by $T_1$.
   - **Condition 2 holds.**

3. **Final write condition:**
   - In schedule $S$: $T_2$ executes the final write on $X$ at Step 4 and the final write on $Y$ at Step 8.
   - In serial schedule $\langle T_1, T_2 \rangle$: $T_2$ executes last, performing the final writes on both $X$ and $Y$.
   - **Condition 3 holds.**

All three conditions are satisfied with respect to the serial schedule $\langle T_1, T_2 \rangle$.

![2020 Q.6(b) Precedence Graph showing acyclic edge T1 to T2](diagrams/T10_2020_Q6b_precedence_graph.jpg)
*Figure 1: Precedence graph for 2020 Q.6(b) confirming acyclic conflict serialization order $T_1 \to T_2$.*

Also, every conflicting instruction pair on both $X$ and $Y$ runs in $T_1$ before $T_2$:
- $w_1(X) \to r_2(X)$ and $w_1(X) \to w_2(X)$
- $w_1(Y) \to r_2(Y)$ and $w_1(Y) \to w_2(Y)$

Because all edges point from $T_1$ to $T_2$, the precedence graph is acyclic, and remember that every conflict-serializable schedule is automatically view serializable.

**Conclusion:** The schedule is **view serializable** (as well as conflict serializable), with equivalent serial execution order:

$$
\boxed{\langle T_1, T_2 \rangle}
$$

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 17.8 · View Serializability Conditions & Blind Writes

> **Source:** Silberschatz 7e · Chapter 17 (Practice Exercise 17.8)  
> **Exam Relevance:** High-Probability Advanced Exam Question  
> **Key Tested Concept:** The 3 formal conditions of View Equivalence, blind writes, and why View Serializability is strictly weaker than Conflict Serializability.

**Problem Statement:**
> 1. State the **three formal conditions** required for two schedules $S$ and $S'$ to be **view equivalent**.
> 2. Present an interleaved schedule containing **blind writes** that is **view serializable but NOT conflict serializable**.
> 3. Prove why the schedule is view serializable to a serial schedule and draw its cyclic precedence graph.

**Model Exam-Style Solution:**

1. **Three Formal Conditions of View Equivalence:**
   Two schedules $S$ and $S'$ on the same set of transactions are view equivalent if:
   1. **Initial Read:** For each data item $Q$, if transaction $T_i$ reads the initial value of $Q$ in $S$, then $T_i$ must also read the initial value of $Q$ in $S'$.
   2. **Updated Read (Read-From):** For each data item $Q$, if transaction $T_i$ executes $\text{read}(Q)$ and that value was produced by $\text{write}(Q)$ of transaction $T_j$ in $S$, then $T_i$ must also read the value produced by the same $\text{write}(Q)$ of $T_j$ in $S'$.
   3. **Final Write:** For each data item $Q$, the transaction that performs the final $\text{write}(Q)$ in $S$ must also perform the final $\text{write}(Q)$ in $S'$.

2. **The Classic Schedule with Blind Writes:**
   Consider schedule $S$ with transactions $T_1, T_2, T_3$:
   $$
   S: r_1(A); \quad w_2(A); \quad w_1(A); \quad w_3(A)
   $$
   *(Notice that $w_2(A)$ and $w_3(A)$ are **blind writes**—writes executed without reading $A$ first).*

3. **Proof of Non-Conflict Serializability:**
   - Conflicting pairs in $S$:
     - $r_1(A)$ is before $w_2(A) \implies T_1 \rightarrow T_2$
     - $w_2(A)$ is before $w_1(A) \implies T_2 \rightarrow T_1$
     - $w_1(A)$ is before $w_3(A) \implies T_1 \rightarrow T_3$
   - The precedence graph contains the cycle:
     $$
     T_1 \rightleftarrows T_2
     $$
   - Since the precedence graph has a cycle, $S$ is **NOT conflict serializable**.

4. **Proof of View Serializability to Serial Schedule $\langle T_1, T_2, T_3 \rangle$:**
   Let $S' = \langle T_1, T_2, T_3 \rangle$:
   - **Initial Read of $A$:** In $S$, $T_1$ reads the initial value of $A$. In $S'$, $T_1$ runs first and reads the initial value of $A$. ($\checkmark$)
   - **Updated Reads:** In $S$, no transaction reads a value produced by another transaction (no read follows a write). In $S'$, no transaction reads a value produced by another transaction. ($\checkmark$)
   - **Final Write of $A$:** In $S$, $T_3$ performs the final $\text{write}(A)$. In $S'$, $T_3$ runs last and performs the final $\text{write}(A)$. ($\checkmark$)
   - All three conditions hold! Thus, $S$ is view equivalent to the serial schedule $\langle T_1, T_2, T_3 \rangle$.
   - **Verdict:** Schedule $S$ is **view serializable**. $\blacksquare$

**💡 RUET Exam Takeaway:**
Every conflict serializable schedule is view serializable, but the converse is not true. A schedule can be view serializable without being conflict serializable **only if it contains blind writes**!

## ⚡ Exam Tips & Common Mistakes

1. **Write out all three view-equivalence conditions:** In RUET grading rubrics, listing only two of the three conditions loses marks. Always state (1) Initial read, (2) Updated read (read-from), and (3) Final write.
2. **Use the term "blind write" when explaining why view serializability is needed:** Examiners look specifically for the phrase **blind write** (writing a data item without reading it first) as the reason conflict serializability can be too restrictive.
3. **Mention why DBMS engines still prefer conflict serializability:** Note that testing view serializability is **NP-complete**, which is why practical database engines rely on conflict serializability (or specialized rules like Thomas' Write Rule) at runtime.
4. **Shortcut for acyclic schedules:** If a schedule's precedence graph has no cycles, it is conflict serializable, and therefore **automatically view serializable** with the exact same topological sort order. Still verify the 3 view conditions explicitly to earn full marks on a "check view serializability" prompt.
