# T03.3: Referential Integrity and Foreign Key Syntax

> **Topic:** T03 — Relational Model, Keys & Integrity | **Priority:** 🟢 | **Exam Frequency:** 1/7 finals (05 marks)
> **Sources:** Silberschatz 7e Ch. 2 (§2.3.2, pp. 45–46), Ch. 4 (§4.4.5, pp. 149–151) · Lecture Deck 03 (Slides 8–10) · Raidah Class Notes (T03, p. 19R)

## Why This Topic Matters

Relational databases split related information across separate tables to avoid data duplication. Because of this, we need a way to make sure the links between those tables stay valid over time. Referential integrity is the rule that keeps these cross-table links consistent so you never end up with "orphan" records when rows are inserted, updated, or deleted. In semester finals, this topic tests whether you can explain how the DBMS enforces these rules and write working MySQL DDL and DML queries to demonstrate them.

---

## 📝 Key Definitions

> **Referential Integrity Constraint:** "In general, a referential integrity constraint requires that the values appearing in specified attributes of any tuple in the referencing relation also appear in specified attributes of at least one tuple in the referenced relation." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3.2 (p. 46)

> **Foreign-Key Constraint:** "A foreign-key constraint from attribute(s) $A$ of relation $r_1$ to the primary-key $B$ of relation $r_2$ states that on any database instance, the value of $A$ for each tuple in $r_1$ must also be the value of $B$ for some tuple in $r_2$. Attribute set $A$ is called a foreign key from $r_1$, referencing $r_2$." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3.2 (p. 45)

> **Cascading Actions:** "Because of the `on delete cascade` clause associated with the foreign-key declaration, if a delete of a tuple in `department` results in this referential-integrity constraint being violated, the system does not reject the delete. Instead, the delete 'cascades' to the `course` relation..." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.4.5 (p. 150)

## Understanding Referential Integrity

### Intuitive Analogy: Why Referential Integrity Works

Think of a university enrollment roster that lists each student's department code. If a student's record says they belong to the `'Robotics'` department, then `'Robotics'` must actually exist in the university's official list of departments. Otherwise, that student record points to a nonexistent department. Referential integrity works like an automatic gatekeeper that checks the official list before allowing any new link to be created or any existing department to be removed.

### The Relationship Between Parent and Child Tables

In practice, referential integrity connects two tables:
1. **Referenced Relation (Parent Table):** Holds the master list of records, identified by a primary key or unique key.
2. **Referencing Relation (Child Table):** Contains a foreign key column whose values point back to the parent table's primary key.

For the database to stay consistent, every foreign key value in the child table must either:
- Match an existing primary key value in the parent table, or
- Be `NULL` (as long as the foreign key column allows null values).

```text
Parent: Department (dept_name [PK], building, budget)
           ^
           | (Foreign Key Reference)
           |
Child:  Student (student_id [PK], name, dept_name [FK])
```

For example, if a student row has `dept_name = 'ECE'`, there must be a matching `'ECE'` row in `Department`. If `'ECE'` does not exist in `Department`, the student row becomes a dangling "orphan record."

### Foreign Key vs. General Referential Integrity Constraint

The textbook makes a small but helpful distinction between these two terms:
- A **foreign-key constraint** requires the referenced column in the parent table to be its primary key (or a unique candidate key).
- A **referential integrity constraint** is the broader theoretical concept, which simply says a value in one table must appear in another table, even if that target column is not the primary key.

In practice, SQL database engines like MySQL enforce referential integrity through foreign key constraints that point to primary or unique keys.

## How a DBMS Achieves Referential Integrity

A DBMS keeps foreign key links valid automatically using three built-in mechanisms:

1. **Schema Constraint Declaration:**
   When creating or altering a table, the database designer declares foreign keys using the `FOREIGN KEY ... REFERENCES` clause inside `CREATE TABLE` or `ALTER TABLE`.

2. **Active Violation Checking:**
   Whenever a user runs an `INSERT`, `UPDATE`, or `DELETE` statement, the storage engine checks whether the change would leave behind orphan rows:
   - **Child Insertion or Update:** The DBMS rejects a new or updated child row if its foreign key value does not match any existing key in the parent table.
   - **Parent Deletion or Update:** By default, the DBMS blocks deleting or changing a parent key if any child rows still point to it.

3. **Automated Referential Actions (Cascading Rules):**
   Instead of always blocking parent changes, the designer can attach rules like `ON DELETE CASCADE` or `ON UPDATE CASCADE` so the DBMS automatically updates or cleans up child rows when a parent row changes.

### Automated Referential Actions

When a referenced parent row is deleted or updated, MySQL supports these actions:

| Action | Description | Exam Context |
| :--- | :--- | :--- |
| `CASCADE` | Deleting or updating the parent row automatically deletes or updates all matching child rows. | Best when child data makes no sense without the parent. |
| `SET NULL` | Deleting or updating the parent sets the child's foreign key column to `NULL`. | Requires the child foreign key column to allow `NULL`. |
| `RESTRICT` | Immediately rejects the parent deletion or update if any child row references it. | Default behavior in MySQL and standard SQL. |
| `NO ACTION` | Works the same as `RESTRICT` in MySQL by rejecting the change if child rows exist. | Standard SQL deferred check option. |
| `SET DEFAULT` | Sets the child foreign key to its default value when the parent is removed. | Part of standard SQL (not supported by MySQL InnoDB). |

## Worked Example: Library Author and Book Mini-Example

Before looking at the full university past-exam problem below, let us walk through a quick two-table example with `Author` (parent) and `Book` (child) to see how MySQL enforces foreign keys step by step.

### Step 1: Create the Parent and Child Tables

We always create the parent table (`Author`) first so that the child table (`Book`) has a valid primary key to reference:

```sql
CREATE TABLE Author (
    author_id INT PRIMARY KEY,
    author_name VARCHAR(40) NOT NULL
);

CREATE TABLE Book (
    book_id INT PRIMARY KEY,
    title VARCHAR(60) NOT NULL,
    author_id INT,
    FOREIGN KEY (author_id) REFERENCES Author(author_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

### Step 2: Test Valid Insert, Rejected Insert, and Cascade Delete

First, we insert a valid author (`author_id = 1`) and a book written by that author. Because author `1` exists, MySQL accepts the book. Next, if we try to insert a book with `author_id = 99` (which does not exist in `Author`), MySQL immediately blocks it with `ERROR 1452`:

```sql
INSERT INTO Author VALUES (1, 'Humayun Ahmed');
INSERT INTO Book VALUES (501, 'Deyal', 1);       -- Succeeds: author_id 1 exists

INSERT INTO Book VALUES (502, 'Unknown', 99);    -- Fails with ERROR 1452: author_id 99 missing
```

Finally, if we delete author `1` (`DELETE FROM Author WHERE author_id = 1;`), the `ON DELETE CASCADE` rule automatically removes book `501` from `Book` so no orphan book is left behind.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2021 Q.1(c) · Achieving Referential Integrity in MySQL

> **Appeared:** 2021 Q.1(c) — (05 marks)

**Question:**

How do we achieve referential integrity in DBMS? Provide necessary MySQL query with an appropriate example.

**Full Answer:**

#### 1. How Referential Integrity is Achieved in DBMS

Referential integrity ensures that relationships between tables remain consistent. It requires that any foreign key value in a referencing (child) table must exist as a primary key value in the referenced (parent) table, or be NULL.

A DBMS achieves referential integrity through three mechanisms:

1. **Constraint Declaration:** The database designer defines foreign keys in the DDL schema using the `FOREIGN KEY ... REFERENCES` clause.
2. **Active Violation Checking:** The DBMS monitors `INSERT`, `UPDATE`, and `DELETE` commands. It blocks any operation that creates orphan child records:
   - Inserting a child row with a nonexistent foreign key is blocked.
   - Deleting or updating a parent row that still has child rows is blocked (under `RESTRICT`).
3. **Automated Referential Actions:** The designer specifies rules for parent modifications:
   - `ON DELETE CASCADE`: Deleting a parent row automatically deletes matching child rows.
   - `ON UPDATE CASCADE`: Updating a parent key automatically updates matching child foreign keys.
   - `ON DELETE SET NULL`: Sets child foreign key columns to NULL when the parent row is deleted.
   - `ON DELETE RESTRICT`: Rejects the parent deletion if matching child rows exist.

#### 2. Necessary MySQL DDL Queries

```sql
-- Step 1: Create Parent Table (Referenced relation)
CREATE TABLE Department (
    dept_name VARCHAR(20) PRIMARY KEY,
    building VARCHAR(20),
    budget DECIMAL(12, 2)
);

-- Step 2: Create Child Table (Referencing relation)
CREATE TABLE Student (
    student_id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    dept_name VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES Department(dept_name)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

#### 3. Operation and Violation Demonstration

```sql
-- Valid Insertion
INSERT INTO Department VALUES ('ECE', 'Academic Building 2', 500000.00);
INSERT INTO Student VALUES (101, 'Akib', 'ECE'); -- Allowed

-- Attempting a Violating Insert
INSERT INTO Student VALUES (102, 'Shuvo', 'ME');
```

**MySQL System Response:**
MySQL rejects the insert and raises an integrity violation error:

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails 
(`university`.`Student`, CONSTRAINT `student_ibfk_1` FOREIGN KEY (`dept_name`) 
REFERENCES `Department` (`dept_name`) ON DELETE CASCADE ON UPDATE CASCADE)
```

**Cascading Demonstration:**
If `'ECE'` is deleted from `Department`:

```sql
DELETE FROM Department WHERE dept_name = 'ECE';
```

Because of `ON DELETE CASCADE`, MySQL automatically deletes student 101 from `Student`. This prevents orphan records and preserves database consistency.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 2.2 · Foreign Key Constraints & Cascade Actions

> **Source:** Silberschatz 7e · Chapter 2 (Practice Exercise 2.2)  
> **Exam Relevance:** Prime Overdue DDL Integrity Drill  
> **Key Tested Concept:** Referential integrity syntax, parent-child table dynamics, and cascade update/delete actions.

**Problem Statement:**
> Consider the relations:
> - $\text{department}(\underline{\text{dept\_name}}, \text{building}, \text{budget})$
> - $\text{instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$
> 1. Write the SQL DDL definition for the `instructor` table, specifying that `dept_name` is a foreign key referencing `department`.
> 2. Explain the behavior of the database under the following three options when a department tuple is deleted:
>    - `ON DELETE CASCADE`
>    - `ON DELETE SET NULL`
>    - `ON DELETE RESTRICT` (or `NO ACTION`)
> 3. Which option could lead to a violation if `dept_name` was declared `NOT NULL`?

**Model Exam-Style Solution:**

1. **SQL DDL with Foreign Key:**
```sql
CREATE TABLE instructor (
    ID          VARCHAR(5),
    name        VARCHAR(20) NOT NULL,
    dept_name   VARCHAR(20),
    salary      NUMERIC(8, 2),
    PRIMARY KEY (ID),
    FOREIGN KEY (dept_name) REFERENCES department (dept_name)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

2. **Analysis of Delete Actions:**
   - **`ON DELETE CASCADE`:**
     - If department `'Biology'` is deleted from `department`, all instructor tuples whose `dept_name = 'Biology'` are **automatically deleted** from the `instructor` table.
   - **`ON DELETE SET NULL`:**
     - If `'Biology'` is deleted, all instructors in `'Biology'` have their `dept_name` attribute value updated to **`NULL`**. The instructor tuples are preserved.
   - **`ON DELETE RESTRICT` (or `NO ACTION`):**
     - The DBMS immediately **rejects and aborts the delete operation** if any instructor tuple currently references `'Biology'`. The department cannot be deleted until all referencing instructors are reassigned or deleted.

3. **Integrity Violation Conflict:**
   - If `dept_name` in table `instructor` is declared with a `NOT NULL` constraint:

```sql
dept_name VARCHAR(20) NOT NULL
```
   - Then specifying `ON DELETE SET NULL` creates a direct contradiction!
   - When the referenced department is deleted, the cascade action attempts to write `NULL` into `dept_name`, but the `NOT NULL` domain constraint forbids nulls.
   - **Verdict:** The DBMS will reject table creation or abort the runtime delete operation. $\blacksquare$

**💡 RUET Exam Takeaway:**
`ON DELETE SET NULL` can ONLY be used on foreign key columns that are permitted to contain `NULL`!

## ⚡ Exam Tips & Common Mistakes

1. **Creation Order Trap:** Always create the parent table before the child table. If you create `Student` before `Department`, MySQL throws `ERROR 1215 (HY000): Cannot add foreign key constraint`.
2. **Data Type Matching:** The data type and width of the foreign key column must match the referenced primary key column exactly (for example, `VARCHAR(20)` must reference `VARCHAR(20)`).
3. **Show the Error:** In an exam, do not just write the `CREATE TABLE` statements. Write down the invalid `INSERT` and quote MySQL Error 1452. That proves practical understanding to the examiner.
4. **Drop Order Trap:** When dropping tables, drop the child table first, then the parent table (`DROP TABLE Student;` then `DROP TABLE Department;`).
