# T01.5: DDL vs. DML

> **Topic:** T01 — DB Concepts & Architecture | **Priority:** 🟢 | **Exam Frequency:** 1/7 finals (2 marks)
> **Sources:** Silberschatz 7e Ch. 1 (§1.4) · Lecture Deck 01 (Slides 16–19) · Class Notes (Raidah p. 11–12; Fahim p. 1–3)

## Why This Topic Matters

Every database language splits its commands into two basic jobs: building the empty table structures (**DDL**) and working with the rows stored inside those tables (**DML**). This distinction was tested directly in 2023 Q.1(c) for 2 marks and forms the foundation for all the SQL topics later in the course (`T05`–`T07`). In addition, understanding the difference between *procedural* and *declarative* DML is a classic viva and class-test question.

---

## 📝 Key Definitions

> **Data-Definition Language (DDL):** "We specify a database schema by a set of definitions expressed by a special language called a **data-definition language** (**DDL**)." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §1.4.1 (p. 13)

> **Data-Manipulation Language (DML):** "A **data-manipulation language** (**DML**) is a language that enables users to access or manipulate data as organized by the appropriate data model." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §1.4.3 (p. 15)

> **Procedural DMLs:** "**Procedural DMLs** require a user to specify what data are needed and how to get those data." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §1.4.3 (p. 15)

> **Declarative DMLs (Nonprocedural DMLs):** "**Declarative DMLs** (also referred to as **nonprocedural DMLs**) require a user to specify what data are needed without specifying how to get those data." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §1.4.3 (p. 15)

> **Data Dictionary:** "The output of the DDL is placed in the **data dictionary**, which contains **metadata**—that is, data about data." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §1.4.1 (p. 14)

## Core Theory: Data Definition Language (DDL)

Think of setting up a database like building a library. Before you can put a single book on a shelf, you first have to build the bookshelves and label each section. **DDL** commands build and label the "shelves" of your database by defining table schemas, column types, and validation rules.

### Functions of DDL

1. **Schema Definition:** Creates new tables, views, and database schemas.
2. **Integrity Constraint Specification:** Sets the rules that every row must obey before the DBMS will accept it:
   - **Domain Constraints:** Fixes the allowed data type for each column (such as `INT`, `VARCHAR(30)`, or `DATE`).
   - **Primary Key Constraints:** Ensures every row has a unique, non-null identifier.
   - **Referential Integrity:** Links foreign keys in one table to primary keys in another table.
3. **Authorization Specification:** Controls which users have read or write access to specific tables.
4. **Metadata Generation:** Whenever you run a DDL command, the DBMS compiles that definition and saves it as metadata inside the **data dictionary** (system catalog).

### Common DDL Commands

- `CREATE TABLE`: Builds a brand-new table schema.
- `ALTER TABLE`: Adds, modifies, or drops columns and constraints on an existing table.
- `DROP TABLE`: Deletes an entire table, wiping out both its rows and its schema definition from the data dictionary.
- `TRUNCATE TABLE`: Empties all data pages from a table at once while keeping the empty table schema intact.
- `CREATE INDEX`: Builds a fast lookup index on one or more columns.

```sql
-- Illustrative DDL Mini-Example: Creating a course table
CREATE TABLE course (
    course_id CHAR(7),
    title VARCHAR(50) NOT NULL,
    credits INT CHECK (credits > 0),
    PRIMARY KEY (course_id)
);
```

## Core Theory: Data Manipulation Language (DML)

Once your empty tables are built, **DML** is the language you use every day to put rows into those tables, update them, delete them, or search through them. DML commands only touch the **instance** (the rows inside the table) and never change the table's column structure.

### Four Core DML Operations

1. **Retrieval:** Searching and reading stored rows using queries (`SELECT`).
2. **Insertion:** Adding new rows (tuples) into a table (`INSERT`).
3. **Modification:** Changing column values inside existing rows (`UPDATE`).
4. **Deletion:** Removing specific rows that match a `WHERE` filter (`DELETE`).

```sql
-- Illustrative DML Mini-Examples on the course table

-- 1. Insert a new row
INSERT INTO course VALUES ('ECE2215', 'Database Systems', 3);

-- 2. Query rows (Retrieval)
SELECT title FROM course WHERE credits = 3;

-- 3. Update an existing row
UPDATE course SET title = 'Data Base Systems' WHERE course_id = 'ECE2215';

-- 4. Delete a specific row
DELETE FROM course WHERE course_id = 'ECE2215';
```

## Procedural vs. Declarative DML

How much detail do you have to give the database when you ask for data? That question splits DMLs into two styles, much like the difference between giving a taxi driver turn-by-turn street instructions versus simply dropping a destination pin on Google Maps:

### 1. Procedural DML (What + How)

In a **procedural DML**, you must tell the database both **what** data you want and **how** to fetch it step by step (which index or file to open, how to loop over rows, and how to join records).

- **Examples:** Relational Algebra ($\sigma, \Pi, \bowtie$) and PL/SQL cursor loops.
- **How it feels:** "Open the `course` file, scan each record one by one, check if `credits == 3`, and append the `title` field to the output list."

### 2. Declarative / Nonprocedural DML (What Only)

In a **declarative DML**, you only state **what** condition the result must satisfy, without writing any loops or file-scanning logic. The DBMS's internal **query optimizer** figures out the fastest way to fetch the data on its own.

- **Examples:** SQL (`SELECT ... FROM ... WHERE ...`), Tuple Relational Calculus, and Domain Relational Calculus.
- **How it feels:** "Give me the titles of all 3-credit courses." Because declarative queries are much easier to write and let the database optimize execution automatically, almost all modern queries use declarative SQL.

## Comparison: DDL vs. DML

| Feature | Data Definition Language (DDL) | Data Manipulation Language (DML) |
| :--- | :--- | :--- |
| **Main Job** | Defines and modifies the database schema (table structure) | Reads and modifies the data rows (instance) stored inside tables |
| **What It Affects** | Table schemas, columns, constraints, and the data dictionary | Individual rows (tuples) and column values |
| **Where Output Goes** | Stored as metadata inside the system catalog (data dictionary) | Returned to the user screen or saved inside data files |
| **Core SQL Commands** | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **Transaction Behavior** | Auto-commits immediately in most DBMS engines (like MySQL) | Can be undone with `ROLLBACK` before `COMMIT` is called |
| **Row-Level Triggers** | Does not fire standard row-level DML triggers | Fires row-level triggers (`BEFORE/AFTER INSERT`, `UPDATE`, `DELETE`) |
| **How Often Used** | Run occasionally during initial setup or schema upgrades | Run thousands of times a minute during normal app traffic |

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.1(c) · DDL and DML with Examples

> **Appeared:** 2023 Q.1(c) — (2 marks)

**Question:**

Explain DDL and DML with example.

**Full Answer:**

#### 1. Data Definition Language (DDL)

DDL is the subset of SQL commands used to create, modify, and remove database schemas, table structures, and integrity constraints. When a DDL command runs, its output is saved in the data dictionary as metadata.

**Example:**
```sql
CREATE TABLE instructor (
    ID CHAR(5),
    name VARCHAR(20),
    dept_name VARCHAR(20),
    salary NUMERIC(8,2),
    PRIMARY KEY (ID)
);
```

#### 2. Data Manipulation Language (DML)

DML is the subset of SQL commands used to query, insert, update, and delete the actual data rows stored inside database tables. SQL's DML is declarative, meaning users specify *what* data they want rather than coding step-by-step disk search loops.

**Example:**
```sql
-- Retrieval (Query)
SELECT name FROM instructor WHERE dept_name = 'Comp. Sci.';

-- Insertion
INSERT INTO instructor VALUES ('10101', 'Srinivasan', 'Comp. Sci.', 65000);
```

## ⚡ Exam Tips & Common Mistakes

1. **Always provide syntactically valid SQL code:** For 2-mark questions, examiners award 1 mark for the definition and 1 mark for valid SQL examples. Avoid pseudo-code.
2. **`SELECT` is declarative DML:** Do not label `SELECT` as a separate language category like "DQL" on exam answer sheets unless explicitly asked. Silberschatz treats `SELECT` as nonprocedural DML.
3. **`TRUNCATE` is DDL, not DML:** Even though `TRUNCATE` deletes table rows, it is a DDL command. It deallocates data pages and alters internal storage pointers without row-by-row logging.
4. **State the auto-commit difference:** DDL statements execute an implicit commit in MySQL. DML operations can be rolled back using `ROLLBACK` within an active transaction block.
