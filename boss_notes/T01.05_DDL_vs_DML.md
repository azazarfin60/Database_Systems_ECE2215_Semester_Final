# T01.5: DDL vs. DML

> **Topic:** T01 — DB Concepts & Architecture | **Priority:** 🟢 | **Exam Frequency:** 1/7 finals (2 marks)
> **Sources:** Silberschatz 7e Ch. 1 (§1.4) · Lecture Deck 01 (Slides 16–19) · Class Notes (Raidah p. 11–12; Fahim p. 1–3)

## Why This Topic Matters

Every database language splits its commands into two basic jobs: building the empty table structures (**DDL**) and working with the rows stored inside those tables (**DML**). This distinction was tested directly in 2023 Q.1(c) for 2 marks and forms the foundation for all the SQL topics later in the course (`T05`–`T07`). In addition, understanding the difference between *procedural* and *declarative* DML is a classic viva and class-test question.

---

## 📝 Key Definitions

> **Data-Definition Language (DDL):** A Data-Definition Language is the set of SQL commands used to create, modify, and remove database schemas, table structures, and integrity constraints. Common DDL commands include `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, and `TRUNCATE TABLE`.

> **Data-Manipulation Language (DML):** A Data-Manipulation Language is the set of SQL commands used to read, insert, update, and delete the actual data rows stored inside database tables. Common DML commands include `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

> **Procedural DML:** A procedural DML is a query language where the user must specify both what data is needed and the exact step-by-step procedure for how to fetch it. Relational Algebra is the classic example of a procedural DML.

> **Declarative DML (Nonprocedural DML):** A declarative DML is a query language where the user specifies only what data is needed without stating how to fetch it. SQL is a declarative DML because the database engine's query optimizer figures out the fastest search path automatically.

> **Data Dictionary:** The data dictionary, also called the system catalog, is a special set of internal tables that stores metadata about the database. Whenever a DDL command runs, the DBMS saves the resulting table definitions, column types, constraints, and user permissions inside the data dictionary.

---

## Core Theory: Data Definition Language (DDL)

Think of setting up a database like building a library. Before you can put a single book on a shelf, you first have to build the bookshelves and label each section. **DDL** commands build and label the "shelves" of your database by defining table schemas, column types, and validation rules.

### Functions of DDL

1. **Schema Definition:** Creates new tables, views, and database schemas.
2. **Integrity Constraint Specification:** Sets the rules that every row must obey before the DBMS will accept it:
   - **Domain Constraints:** Fixes the allowed data type for each column (such as `INT`, `VARCHAR(30)`, or `DATE`).
   - **Primary Key Constraints:** Ensures every row has a unique, non-null identifier.
   - **Referential Integrity:** Links foreign keys in one table to primary keys in another table.
3. **Authorization Specification:** Controls which users have read or write access to specific tables.
4. **Metadata Generation:** Whenever you run a DDL command, the DBMS compiles that definition and saves it as metadata inside the **data dictionary** (system catalog).

### Common DDL Commands

- `CREATE TABLE`: Builds a brand-new table schema.
- `ALTER TABLE`: Adds, modifies, or drops columns and constraints on an existing table.
- `DROP TABLE`: Deletes an entire table, wiping out both its rows and its schema definition from the data dictionary.
- `TRUNCATE TABLE`: Empties all data pages from a table at once while keeping the empty table schema intact.
- `CREATE INDEX`: Builds a fast lookup index on one or more columns.

```sql
-- Illustrative DDL Mini-Example: Creating a course table
CREATE TABLE course (
    course_id CHAR(7),
    title VARCHAR(50) NOT NULL,
    credits INT CHECK (credits > 0),
    PRIMARY KEY (course_id)
);
```

## Core Theory: Data Manipulation Language (DML)

Once your empty tables are built, **DML** is the language you use every day to put rows into those tables, update them, delete them, or search through them. DML commands only touch the **instance** (the rows inside the table) and never change the table's column structure.

### Four Core DML Operations

1. **Retrieval:** Searching and reading stored rows using queries (`SELECT`).
2. **Insertion:** Adding new rows (tuples) into a table (`INSERT`).
3. **Modification:** Changing column values inside existing rows (`UPDATE`).
4. **Deletion:** Removing specific rows that match a `WHERE` filter (`DELETE`).

```sql
-- Illustrative DML Mini-Examples on the course table

-- 1. Insert a new row
INSERT INTO course VALUES ('ECE2215', 'Database Systems', 3);

-- 2. Query rows (Retrieval)
SELECT title FROM course WHERE credits = 3;

-- 3. Update an existing row
UPDATE course SET title = 'Data Base Systems' WHERE course_id = 'ECE2215';

-- 4. Delete a specific row
DELETE FROM course WHERE course_id = 'ECE2215';
```

## Procedural vs. Declarative DML

How much detail do you have to give the database when you ask for data? That question splits DMLs into two styles, much like the difference between giving a taxi driver turn-by-turn street instructions versus simply dropping a destination pin on Google Maps:

### 1. Procedural DML (What + How)

In a **procedural DML**, you must tell the database both **what** data you want and **how** to fetch it step by step (which index or file to open, how to loop over rows, and how to join records).

- **Examples:** Relational Algebra ($\sigma, \Pi, \bowtie$) and PL/SQL cursor loops.
- **How it feels:** "Open the `course` file, scan each record one by one, check if `credits == 3`, and append the `title` field to the output list."

### 2. Declarative / Nonprocedural DML (What Only)

In a **declarative DML**, you only state **what** condition the result must satisfy, without writing any loops or file-scanning logic. The DBMS's internal **query optimizer** figures out the fastest way to fetch the data on its own.

- **Examples:** SQL (`SELECT ... FROM ... WHERE ...`), Tuple Relational Calculus, and Domain Relational Calculus.
- **How it feels:** "Give me the titles of all 3-credit courses." Because declarative queries are much easier to write and let the database optimize execution automatically, almost all modern queries use declarative SQL.

## Comparison: DDL vs. DML

| Feature | Data Definition Language (DDL) | Data Manipulation Language (DML) |
| :--- | :--- | :--- |
| **Main Job** | Defines and modifies the database schema (table structure) | Reads and modifies the data rows (instance) stored inside tables |
| **What It Affects** | Table schemas, columns, constraints, and the data dictionary | Individual rows (tuples) and column values |
| **Where Output Goes** | Stored as metadata inside the system catalog (data dictionary) | Returned to the user screen or saved inside data files |
| **Core SQL Commands** | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **Transaction Behavior** | Auto-commits immediately in most DBMS engines (like MySQL) | Can be undone with `ROLLBACK` before `COMMIT` is called |
| **Row-Level Triggers** | Does not fire standard row-level DML triggers | Fires row-level triggers (`BEFORE/AFTER INSERT`, `UPDATE`, `DELETE`) |
| **How Often Used** | Run occasionally during initial setup or schema upgrades | Run thousands of times a minute during normal app traffic |

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.1(c) · DDL and DML with Examples

> **Appeared:** 2023 Q.1(c) — (2 marks)

**Question:**

Explain DDL and DML with example.

**Full Answer:**

#### 1. Data Definition Language (DDL)

DDL is the subset of SQL commands used to create, modify, and remove database schemas, table structures, and integrity constraints. When a DDL command runs, its output is saved in the data dictionary as metadata.

**Example:**
```sql
CREATE TABLE instructor (
    ID CHAR(5),
    name VARCHAR(20),
    dept_name VARCHAR(20),
    salary NUMERIC(8,2),
    PRIMARY KEY (ID)
);
```

#### 2. Data Manipulation Language (DML)

DML is the subset of SQL commands used to query, insert, update, and delete the actual data rows stored inside database tables. SQL's DML is declarative, meaning users specify *what* data they want rather than coding step-by-step disk search loops.

**Example:**
```sql
-- Retrieval (Query)
SELECT name FROM instructor WHERE dept_name = 'Comp. Sci.';

-- Insertion
INSERT INTO instructor VALUES ('10101', 'Srinivasan', 'Comp. Sci.', 65000);
```

### 🎯 HYE-01 · Practice Exercise 1.2 · Programming Language Type Systems (Java/C++) vs Database DDL

> **Source:** Silberschatz 7e · Chapter 1 (Practice Exercise 1.2, p. 32)  
> **Exam Relevance:** High-Probability Comparative Architecture Question (5 Marks)  
> **Key Tested Concept:** Persistence, declarative integrity constraints, physical data independence, multi-user authorization, and dynamic schema evolution.

**Problem Statement:**
> List and explain **five significant ways** in which the type declaration system of a general-purpose programming language (such as Java or C++) differs from the Data Definition Language (DDL) used in a Database Management System.

**Model Exam-Style Solution:**

| Dimension | Programming Language Type System (Java / C++) | Database Data Definition Language (DDL / SQL) |
| :--- | :--- | :--- |
| **1. Data Persistence & Lifecycle** | Variables and objects are **transient**; they reside in volatile main memory (RAM) and are destroyed as soon as the process terminates or scope exits. | Schemas and data are **persistent**; table definitions and records are stored permanently on non-volatile secondary storage (SSD/HDD) and survive crashes and system reboots. |
| **2. Semantic Integrity Constraints** | Only enforces low-level structural types (e.g., `int`, `float`, `String`). Cannot natively enforce relational constraints or business rules without writing manual procedural validation code. | Declares and automatically enforces rich semantic integrity constraints (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `NOT NULL`, `UNIQUE`, `DEFAULT`) centrally inside the database engine. |
| **3. Physical Data Independence** | Type declarations directly dictate in-memory object memory layouts, struct padding, byte alignments, and memory addresses. | Strictly decouples the logical schema from physical storage. The DBA can alter indexing (B+-trees, hashes) or disk block clustering without changing column definitions. |
| **4. Multi-User Authorization & Security** | Access modifiers (`public`, `private`, `protected`) only control programmatic scope and compiler visibility within an application codebase. | Provides declarative, role-based security (`GRANT`, `REVOKE`) at the table and column level, enforced centrally across all concurrent users and applications. |
| **5. Dynamic Schema Evolution** | Changing a class definition or adding a field requires modifying source code, recompiling, relinking, and restarting the entire running application. | Supports dynamic schema modification (`ALTER TABLE ADD/DROP COLUMN`) on active, running databases with live transactional workloads without taking the system offline. |

$\blacksquare$

**💡 RUET Exam Takeaway:**
Remember the 5 core contrast keywords: **Persistence**, **Integrity Constraints**, **Physical Independence**, **Authorization**, and **Dynamic Evolution**.

### 🎯 HYE-02 · Exercise 1.10 & §1.4.3 · Procedural vs Declarative DML: Relational Algebra vs SQL

> **Source:** Silberschatz 7e · Chapter 1 (§1.4.3, Exercise 1.10)  
> **Exam Relevance:** High-Probability Theory & Class Test Question (4–5 Marks)  
> **Key Tested Concept:** Procedural DML (what + how) vs Declarative DML (what only), query optimizer role, and Relational Algebra vs SQL syntax.

**Problem Statement:**
> Data-manipulation languages (DMLs) fall into two broad categories: **procedural DMLs** and **declarative (nonprocedural) DMLs**.
> 1. Clearly distinguish between procedural and declarative DMLs.
> 2. Using the schema $\text{instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$, demonstrate how the query *"Find the names of all instructors in the 'Comp. Sci.' department who earn more than 70,000"* is expressed in both a **procedural language (Relational Algebra)** and a **declarative language (SQL)**.
> 3. State two major technical advantages that led modern relational database systems to adopt declarative DMLs for general application development.

**Model Exam-Style Solution:**

1. **Procedural vs Declarative DML Distinction:**
   - **Procedural DML:** The user instructs the system to perform a sequence of operations on the database to compute the desired result. The query explicitly specifies **what data is needed** AND the step-by-step procedure of **how to obtain that data**. (Example: Relational Algebra).
   - **Declarative (Nonprocedural) DML:** The user specifies **what data is needed** without specifying the procedural steps of how to obtain it. The DBMS handles navigation, index selection, and access methods internally. (Example: SQL).

2. **Query Demonstration across Both Paradigms:**
   - **Procedural Formulation (Relational Algebra):**
     $$
     \Pi_{\text{name}} \left( \sigma_{\text{dept\_name} = \text{'Comp. Sci.'} \land \text{salary} > 70000}(\text{instructor}) \right)
     $$
     - *Procedural Evaluation Steps:*
       1. First, access the `instructor` relation and evaluate the condition $(\text{dept\_name} = \text{'Comp. Sci.'} \land \text{salary} > 70000)$ on each tuple ($\sigma$ selection).
       2. Next, take the resulting intermediate relation and discard all attributes except $\text{name}$ ($\Pi$ projection).
       3. Finally, eliminate any duplicate names from the result stream.

   - **Declarative Formulation (SQL):**

```sql
SELECT name
FROM instructor
WHERE dept_name = 'Comp. Sci.' AND salary > 70000;
```
     - *Declarative Semantics:*
       - The user merely declares the filtering predicates and the desired projection list.
       - The user writes **zero instructions** regarding whether the DBMS should scan the entire table sequentially, use a B+-tree index on `salary`, or use a hash index on `dept_name`.

3. **Why Modern DBMSs Universally Adopt Declarative DML:**
   - **Physical Data Independence & Cost-Based Optimization:**
     - In procedural DML, if the DBA adds or removes an index, procedural code must be rewritten to take advantage of the new structure.
     - In declarative DML, the database engine's **Query Optimizer** automatically inspects catalog statistics, evaluates multiple candidate execution plans, and selects the lowest-cost procedural execution plan at runtime. Physical storage modifications never require altering the SQL query.
   - **Reduced Application Complexity & High Developer Productivity:**
     - Declarative queries express complex multi-table joins and aggregations in concise mathematical statements, eliminating nested loops, pointer-chasing logic, and buffer handling in application code. $\blacksquare$

**💡 RUET Exam Takeaway:**
Always emphasize that Relational Algebra is the internal **procedural target** of the DML compiler, while SQL is the external **declarative interface** for users. The **Query Optimizer** is the crucial bridge that translates declarative SQL into an optimal procedural execution plan.

## ⚡ Exam Tips & Common Mistakes

1. **Always provide syntactically valid SQL code:** For 2-mark questions, examiners award 1 mark for the definition and 1 mark for valid SQL examples. Avoid pseudo-code.
2. **`SELECT` is declarative DML:** Do not label `SELECT` as a separate language category like "DQL" on exam answer sheets unless explicitly asked. Silberschatz treats `SELECT` as nonprocedural DML.
3. **`TRUNCATE` is DDL, not DML:** Even though `TRUNCATE` deletes table rows, it is a DDL command. It deallocates data pages and alters internal storage pointers without row-by-row logging.
4. **State the auto-commit difference:** DDL statements execute an implicit commit in MySQL. DML operations can be rolled back using `ROLLBACK` within an active transaction block.
