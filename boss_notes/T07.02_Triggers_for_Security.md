# T07.2: Triggers for Database Security

> **Topic:** T07 — Triggers and Stored Procedures | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (8 marks)  
> **Sources:** Silberschatz 7e Ch. 5 (§5.3) · Silberschatz 7e Ch. 9 (§9.8) · Fahim Handnote (p. 59)

## Why This Topic Matters

Good database security needs both a guard at the door to block bad changes and a security camera inside to record whatever gets through. Triggers can play both roles right inside the database engine. This topic appeared in two RUET finals: 2017 Q.8(b) (5 marks) and 2024 Q.2(a) (3 marks). Both questions asked how triggers help secure a database *before* and *after* a security breach. The key to full marks is contrasting `BEFORE` triggers (which prevent bad writes using `SIGNAL`) against `AFTER` triggers (which record tamper-evident audit logs using `OLD`, `NEW`, `USER()`, and `NOW()`).

---

## 📝 Key Definitions

> **Database Security:** *(Course definition)* Protecting database schemas, records, and services against unauthorized access, malicious edits, data leaks, or accidental destruction.

> **Preventive Trigger:** "Triggers that execute before an event can serve as extra constraints that can prevent invalid updates, inserts, or deletes."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §5.3.2 (p. 208)

> **Audit Trail:** *(Course definition)* A time-ordered historical log of database changes that records who made the change, when it happened, what operation ran, and both the old and new values.

> **Security Breach:** *(Course definition)* Any unauthorized access, privilege escalation, or data tampering that compromises the confidentiality, integrity, or availability of the database.

---

## The Dual-Phase Security Model

Why do exam questions split trigger security into "before a breach" and "after a breach"? Because a trigger's timing (`BEFORE` vs. `AFTER`) determines whether it acts as a **gatekeeper** that stops an attack in its tracks, or as a **black-box flight recorder** that preserves evidence after an attacker uses stolen credentials to make a change:

```text
                                  DATABASE SECURITY PHASES
                                             │
                    ┌────────────────────────┴────────────────────────┐
                    ▼                                                 ▼
        BEFORE A SECURITY BREACH                           AFTER A SECURITY BREACH
        (Proactive Prevention)                             (Reactive Forensics)
        ────────────────────────                           ────────────────────
        • Timing: BEFORE Trigger                           • Timing: AFTER Trigger
        • Role: Security Gatekeeper                        • Role: Audit Recorder
        • Inspects incoming data                           • Records completed action
        • Enforces time/value rules                        • Captures USER(), NOW()
        • Halts attack with SIGNAL                         • Saves OLD and NEW values
        • Result: Table untouched                          • Result: Evidence preserved
```

## Phase 1: Security Before a Breach (Prevention via BEFORE Triggers)

`BEFORE` triggers inspect every incoming `INSERT`, `UPDATE`, or `DELETE` before the database engine writes anything to disk. If a change looks suspicious or violates a security rule, the trigger aborts the transaction on the spot.

### How `BEFORE` Triggers Stop Attacks

1. **Time-of-Day Access Control:** A trigger can block sensitive table edits outside normal working hours, so an attacker running a script at 2:00 AM gets rejected immediately.
2. **Sanity and Range Checks:** Even if a user has `UPDATE` permission on a table, a `BEFORE` trigger can block extreme changes, such as transferring more than a daily limit or slashing an account balance below zero.
3. **Blocking Privilege Escalation:** A trigger can stop non-admin sessions from changing sensitive security columns or deleting protected system rows.
4. **Aborting the Transaction (`SIGNAL`):** When a rule is violated, the trigger runs `SIGNAL SQLSTATE '45000'`. This throws a custom error and forces the database to roll back the statement, leaving the table completely untouched.

### Compact Example: Blocking Suspicious Bank Withdrawals

Suppose we want to block any withdrawal from `bank_accounts` that happens outside banking hours (`09:00` to `17:00`) or drains more than `50000` in a single update:

```sql
DELIMITER //

CREATE TRIGGER trg_guard_account_withdrawal
BEFORE UPDATE ON bank_accounts
FOR EACH ROW
BEGIN
    IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Security Alert: Account updates outside banking hours are blocked.';
    ELSEIF (OLD.balance - NEW.balance) > 50000 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Security Alert: Single withdrawal exceeds 50,000 limit.';
    END IF;
END //

DELIMITER ;
```

## Phase 2: Security After a Breach (Forensics and Auditing via AFTER Triggers)

What if an attacker steals a legitimate manager's password and makes an update during normal working hours that passes the `BEFORE` checks? Once a breach happens, you need to know *who* did it, *when* they did it, and *what* values they changed so you can undo the damage. That is the job of `AFTER` triggers.

### How `AFTER` Triggers Support Forensics and Recovery

1. **Automatic Database-Level Logging:** `AFTER` triggers write a log row into a separate audit table every time a modification succeeds. Even if an attacker bypasses the web application and runs SQL queries directly, the database trigger still fires.
2. **Capturing Session Identity and Time:** Using built-in functions like `USER()` (or `CURRENT_USER()`), `CONNECTION_ID()`, and `NOW()`, the trigger records exactly which account and IP address ran the query and at what second.
3. **Saving Before-and-After Snapshots (`OLD` and `NEW`):** By storing both the `OLD` (pre-breach) and `NEW` (post-breach) column values, the audit log preserves a complete record of what was overwritten.
4. **Fast Rollback and Recovery:** Because the audit table holds the exact `OLD` values, database administrators can write a simple `UPDATE` query joining the corrupted table with the audit table to restore every damaged row back to its pre-breach state.

### Compact Example: Logging Balance Changes for Forensics

Whenever a balance changes in `bank_accounts`, this `AFTER UPDATE` trigger saves the old balance, new balance, active database user, and timestamp into `account_audit_log`:

```sql
DELIMITER //

CREATE TRIGGER trg_log_balance_change
AFTER UPDATE ON bank_accounts
FOR EACH ROW
BEGIN
    IF OLD.balance <> NEW.balance THEN
        INSERT INTO account_audit_log (acct_id, old_bal, new_bal, modified_by, modified_at)
        VALUES (OLD.acct_id, OLD.balance, NEW.balance, USER(), NOW());
    END IF;
END //

DELIMITER ;
```

## Comparative Analysis: Prevention vs Auditing

| Dimension | Before a Breach (`BEFORE`) | After a Breach (`AFTER`) |
| :--- | :--- | :--- |
| **Trigger Timing** | `BEFORE INSERT / UPDATE / DELETE` | `AFTER INSERT / UPDATE / DELETE` |
| **Primary Goal** | Proactive attack prevention | Forensic evidence and data recovery |
| **Operating Role** | Security gatekeeper and policy inspector | Flight data recorder and audit logger |
| **Primary Mechanism** | Policy check followed by `SIGNAL SQLSTATE` | State capture followed by `INSERT INTO audit_log` |
| **Table State** | Unchanged (transaction rolled back on violation) | Modified (changes written and recorded) |
| **Captured Data** | Incoming values checked against security rules | Historical `OLD` and `NEW` values plus user context |
| **Recovery Utility** | Not needed (damage was prevented) | High (lets DBAs rebuild corrupted rows from `OLD`) |

---

## Architectural Limitations of Triggers for Security

While triggers are great for protecting and auditing data writes, keep four limitations in mind:

1. **No Triggers on `SELECT` Queries:** Standard SQL triggers fire only on data modifications (`INSERT`, `UPDATE`, `DELETE`). They never fire when someone simply reads a table with `SELECT`. To stop attackers from reading confidential columns, you need views, `GRANT`/`REVOKE` permissions, or encryption.
2. **Superuser Bypass:** A database administrator who holds `SUPER` or `TRIGGER` privileges can drop or disable triggers. Because of this, triggers protect against compromised application accounts, not against a rogue DBA.
3. **Write Overhead on Bulk Updates:** Because row-level triggers fire once for every modified row, heavy batch updates will run slower when multiple security triggers are attached.
4. **Part of Defense in Depth:** Triggers work best alongside prepared statements (to stop SQL injection), least-privilege user roles, and network firewalls.

## Worked Example: Tracing Both Phases During an Attack

Suppose our `bank_accounts` table has row `(acct_id: 501, balance: 120000)` and an attacker steals a clerk's database login:

1. **Attempt 1 (Midnight script tries to drain `80000` at 23:15):**
   - The attacker runs `UPDATE bank_accounts SET balance = 40000 WHERE acct_id = 501;`.
   - `trg_guard_account_withdrawal` fires **before** the table is updated.
   - Both the time check (`23:15` is outside `09:00`–`17:00`) and the withdrawal limit (`120000 - 40000 = 80000 > 50000`) fail.
   - The trigger executes `SIGNAL SQLSTATE '45000'`, aborting the update. Account `501` stays at `120000`.
2. **Attempt 2 (Attacker withdraws `30000` at 11:00 AM during office hours):**
   - The attacker runs `UPDATE bank_accounts SET balance = 90000 WHERE acct_id = 501;`.
   - Because `11:00` is within banking hours and `30000 <= 50000`, the `BEFORE` trigger allows the update.
   - Immediately after the row updates, `trg_log_balance_change` fires and inserts `(501, 120000, 90000, 'clerk2@10.0.4.12', '2026-10-30 11:00:05')` into `account_audit_log`.
   - When the fraud team spots the unauthorized transfer from `10.0.4.12`, they read `old_bal = 120000` from the audit log and restore the account balance.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.8(b) · Database Security Before and After a Breach

> **Appeared:** 2017 Q.8(b) — (5 marks)

**Question:**

Using examples, discuss how Trigger can contribute to the security of database, before and after a security breach.

**Full Answer:**

Triggers contribute to database security in two distinct operational phases: proactive prevention before a breach occurs, and forensic auditing after a breach occurs.

#### 1. Before a Security Breach: Proactive Prevention via BEFORE Triggers

`BEFORE` triggers act as real-time security gatekeepers. They evaluate incoming data modifications before they are written to the database tables.

- **Role and Mechanism:** The trigger inspects incoming data values, user credentials, and session conditions. If an operation violates security policy, the trigger aborts the transaction using `SIGNAL SQLSTATE '45000'`.
- **Security Contributions:**
  - **Temporal Controls:** Blocks operations outside authorized business hours.
  - **Sanity Checks:** Prevents unauthorized salary spikes or illegal credit allocations.
  - **Privilege Enforcement:** Prevents non-administrative users from altering sensitive configuration columns.

**Example (Blocking updates outside working hours):**

```sql
DELIMITER //

CREATE TRIGGER trg_prevent_unauthorized_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Security Alert: Edits outside office hours are blocked.';
    END IF;
END //

DELIMITER ;
```

If an unauthorized script runs at night, the trigger raises an error. The transaction rolls back, and the table remains completely protected.

#### 2. After a Security Breach: Auditing and Forensics via AFTER Triggers

If an attacker bypasses front-end authentication, `AFTER` triggers execute immediately after data is modified, functioning as a tamper-evident audit recorder.

- **Role and Mechanism:** The trigger automatically captures forensic details of the modification and inserts them into an independent audit table.
- **Security Contributions:**
  - **Non-Bypassable Logging:** Runs at the database level, capturing unauthorized changes even if application logs are deleted.
  - **Complete Context:** Records the user (`USER()`), timestamp (`NOW()`), target table, and both previous values (`OLD`) and modified values (`NEW`).
  - **Forensics and Recovery:** Enables administrators to identify compromised accounts, evaluate the damage scope, and restore corrupted data using `OLD` values.

**Example (Logging security role modifications):**

```sql
DELIMITER //

CREATE TRIGGER trg_audit_role_change
AFTER UPDATE ON user_roles
FOR EACH ROW
BEGIN
    IF OLD.role <> NEW.role THEN
        INSERT INTO security_audit_log (
            user_id, old_role, new_role, changed_by, changed_at
        ) VALUES (
            OLD.user_id, OLD.role, NEW.role, USER(), NOW()
        );
    END IF;
END //

DELIMITER ;
```

This ensures full accountability and provides the historical evidence needed to roll back malicious changes.

### 🎯 GQ2 · 2024 Q.2(a) · Trigger Contribution to Security (Before and After a Breach)

> **Appeared:** 2024 Q.2(a) — (3 marks)

**Question:**

Discuss how trigger can contribute to the security of database before and after a security breach. Explain with example.

**Full Answer:**

Database triggers enhance security in two fundamental ways:

1. **Before a Breach (Prevention):**  
   `BEFORE` triggers validate operations before execution. If an unauthorized modification or illegal value is detected, the trigger halts execution with `SIGNAL SQLSTATE '45000'`. This keeps the database tables safe from unauthorized modifications.

2. **After a Breach (Auditing and Forensics):**  
   `AFTER` triggers record modifications immediately after they succeed. They write immutable audit records containing the operator (`USER()`), execution time (`NOW()`), and original and updated values (`OLD` and `NEW`). This provides forensic evidence to determine how a breach occurred and restore corrupted records.

**Example:**

A `BEFORE UPDATE` trigger on `employees` preventing unauthorized salary modifications:

```sql
DELIMITER //

CREATE TRIGGER trg_salary_security
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary > (OLD.salary * 1.50) THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Security Alert: Salary increase exceeds maximum threshold.';
    END IF;
END //

DELIMITER ;
```

If the threshold is exceeded, the update is blocked. An associated `AFTER UPDATE` trigger logs legitimate salary changes to an audit table for post-breach inspection.

## ⚡ Exam Tips & Common Mistakes

1. **Never Use AFTER for Prevention:** An `AFTER` trigger fires after the table data has already changed. It cannot prevent unauthorized data from touching the table.
2. **Always Log Both OLD and NEW:** In audit triggers, recording only `NEW` values is incomplete. Without `OLD` values, security administrators cannot revert corrupted data during incident recovery.
3. **Trigger Scope Limitation:** Remember that triggers do not fire on `SELECT` statements. They cannot stop someone from stealing data by reading unauthorized records.
4. **Use Built-in Context Functions:** Mention MySQL context functions like `USER()` and `NOW()` in your audit triggers to demonstrate practical knowledge.
5. **Clear Headings:** Divide your exam answer into two distinct sections: "1. Before a Breach (Prevention)" and "2. After a Breach (Auditing and Forensics)".
