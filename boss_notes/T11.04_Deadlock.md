# T11.4: Deadlock Handling — Prevention, Detection, and Wait-For Graph

> **Topic:** T11 — Concurrency Control Protocols | **Priority:** 🟠 | **Exam Frequency:** 4/7 finals (17 marks)
> **Sources:** Silberschatz 7e Ch. 18 (§18.2, pp. 849–853) · Lecture Deck 08 (Slides 20–25) · Raidah Notes (pp. 28–29)

## Why This Topic Matters

Deadlock handling is one of the highest-yield concurrency control topics in ECE 2215, appearing in 4 out of 7 past final exams for a total of 17 marks. Because Two-Phase Locking (2PL) forces transactions to hold onto existing locks while waiting for new ones, two or more transactions can easily trap each other in a permanent stalemate. Examiners regularly test three angles of this topic: (1) the four methods for **preventing** deadlocks before they happen, (2) when prevention is cheaper than **detection**, and (3) tracing **wait-for graphs** to spot deadlock cycles and pick a victim to roll back.

---

## 📝 Key Definitions

> **Deadlock:** "A system is in a deadlock state if there exists a set of transactions such that every transaction in the set is waiting for another transaction in the set." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2 (p. 849)

> **Wait-For Graph:** "Deadlocks can be described precisely in terms of a directed graph called a wait-for graph. This graph consists of a pair $G = (V, E)$, where $V$ is a set of vertices (or nodes) and $E$ is a set of directed edges." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2.2.1 (p. 851)

> **Deadlock Prevention:** "We can use a deadlock prevention protocol to ensure that the system will *never* enter a deadlock state." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2 (p. 849)

---

## The Four Necessary Coffman Conditions

Imagine two drivers meeting head-on in a single-lane alley where neither car will back up. In a database, a deadlock can happen if and only if four conditions hold at the exact same time:

1. **Mutual Exclusion:** At least one lock is held in an exclusive (non-shareable) mode, so only one transaction can use the item at a time.
2. **Hold and Wait:** A transaction is already holding at least one lock while waiting to acquire another lock held by a different transaction.
3. **No Preemption:** The system does not forcibly take locks away from a holding transaction, so locks are only released voluntarily when the holder finishes.
4. **Circular Wait:** A closed loop of waiting transactions $\{T_0, T_1, \dots, T_n\}$ exists such that $T_0$ waits for $T_1$, $T_1$ waits for $T_2$, ..., and $T_n$ waits for $T_0$.

Every deadlock prevention method works by breaking at least one of these four conditions.

---

## Core Handling Strategies: Prevention vs. Detection & Recovery

Database systems deal with deadlocks using one of two main strategies:

| Strategy | Core Idea | Best Used When | Main Cost / Trade-off |
| :--- | :--- | :--- | :--- |
| **Deadlock Prevention** | Set strict lock rules so a circular wait can never form in the first place. | Lock conflicts are frequent and transactions are long or expensive to undo. | Lower concurrency, extra upfront rules, or unnecessary precautionary rollbacks. |
| **Deadlock Detection & Recovery** | Let transactions request locks freely, check a wait-for graph periodically for cycles, and abort one victim if a deadlock forms. | Lock conflicts are rare and transactions are short. | CPU overhead to maintain and scan the wait-for graph, plus lost work when a victim rolls back. |

---

## Deadlock Prevention Protocols

Deadlock prevention stops circular waits before they can ever form using four classic techniques (Lecture Deck 08, Slides 22–23):

### 1. Pre-declaration (Locking All Items Upfront)
- Every transaction must declare and lock **all** the data items it will need before it starts running, or else lock none of them and wait.
- **Why it works:** Breaks the *Hold and Wait* condition, because a transaction never holds one lock while waiting for another.
- **Drawbacks:**
  1. In real SQL queries, it is often impossible to know which rows a transaction will touch before reading earlier rows.
  2. Concurrency drops sharply because items sit locked and unused for most of the transaction's runtime.

### 2. Lock Ordering (Graph-Based / Total Ordering)
- Impose a fixed global order on all data items in the database (for example, alphabetical order $A < B < C < \dots$, or table/row ID order).
- Every transaction must request locks strictly in ascending order along this sequence. Once a transaction locks item $B$, it is never allowed to go backward and request item $A$.
- **Why it works:** Breaks *Circular Wait*. If every transaction requests items from lower to higher order, a wait chain can only point upward ($A \to B \to C$) and can never loop back on itself.

### 3. Timestamp-Based Preemption (`Wait-Die` and `Wound-Wait`)
- Each transaction $T_i$ is given a unique startup timestamp $\text{TS}(T_i)$ when it begins (smaller timestamp = older transaction).
- Whenever $T_i$ requests a lock currently held by $T_j$, the lock manager compares their ages to decide who waits and who rolls back:
  - **Wait-Die (Non-preemptive):** An **older** requester is allowed to **wait** for a younger holder, whereas a **younger** requester **dies** (rolls itself back immediately) instead of waiting for an older holder.
  - **Wound-Wait (Preemptive):** An **older** requester **wounds** (preempts and rolls back) a younger holder to take the lock immediately, whereas a **younger** requester is allowed to **wait** for an older holder.
- **Starvation Prevention Rule:** Whenever a transaction rolls back under `Wait-Die` or `Wound-Wait`, it restarts with its **original timestamp** so it gradually becomes the oldest transaction in the system and cannot starve. *(Full trace details in `T11.05`.)*

### 4. Timeout-Based Scheme
- Whenever a transaction waits for a lock, a countdown timer starts. If the lock is not granted before the timer expires, the transaction assumes it may be deadlocked, aborts itself, and restarts later.
- **Pros & Cons:** Super easy to implement with zero graph tracking, but hard to tune: a timeout that is too short aborts transactions that were merely waiting on a busy system, while a timeout that is too long wastes time sitting in real deadlocks.

## Deadlock Detection Using the Wait-For Graph

When a database does not use prevention, it lets transactions request locks freely and tracks who is waiting on whom using a **wait-for graph**.

![Interleaved schedule execution and wait-for graph showing deadlock cycle](diagrams/T11_2017_Q7a_deadlock_wait_for_graph.jpg)
*Figure 11.4.1: Two-transaction interleaved schedule and resulting circular wait-for graph (Source: Course archive).*

### Intuitive Meaning of the Wait-For Graph
Think of each active transaction as a dot (vertex), and draw an arrow $T_i \to T_j$ whenever "$T_i$ is waiting for $T_j$ to unlock something." As soon as $T_j$ unlocks the item and $T_i$ gets the lock, you erase the arrow. If the arrows ever form a closed loop (a cycle), every transaction in that loop is waiting on the next one in a circle, which means they are deadlocked!

### Formal Graph Definition: $G = (V, E)$
- **Vertices ($V$):** The set of all active transactions currently in the system:

$$
V = \{T_1, T_2, \dots, T_n\}
$$

- **Directed Edges ($E$):** A directed edge $T_i \to T_j$ is added to $E$ if and only if transaction $T_i$ is waiting for transaction $T_j$ to release a conflicting lock on some data item. When $T_j$ releases the lock and $T_i$ acquires it, the edge $T_i \to T_j$ is removed.

### Cycle Detection Theorem
> **Theorem:** A database system is in a deadlock state **if and only if** its wait-for graph $G = (V, E)$ contains at least one **directed cycle**.

> **Warning (Cycle Nodes vs. Blocked Nodes):**  
> Only the transactions *inside* the cycle (for example, $T_2 \to T_4 \to T_5 \to T_2$) are actually deadlocked. If another transaction $T_1$ has an arrow pointing into the cycle ($T_1 \to T_2$) but no arrow pointing back to $T_1$, then $T_1$ is simply **blocked waiting** for the deadlock to clear, and $T_1$ is **not** part of the deadlock cycle itself!

---

## Deadlock Recovery: Breaking the Cycle

Once the cycle-detection algorithm spots a loop in the wait-for graph, the recovery manager breaks the deadlock in three steps:

### 1. Select a Victim Transaction
The system picks one transaction from the cycle (the **victim**) to roll back. To waste as little work as possible, the lock manager weighs four cost factors:
- **How long the transaction has run** and how close it is to finishing (avoid killing a 99%-complete job).
- **How many data items it has already modified** (fewer writes = faster undo).
- **How many locks it currently holds** and how many other waiting transactions will be unblocked if it aborts.
- **How many transactions would be affected** by rolling it back.

### 2. Roll Back the Victim (Total vs. Partial Rollback)
- **Total Rollback:** Abort the victim completely and restart it from scratch. Simple and common, though it throws away all work done so far.
- **Partial Rollback:** Roll the victim back only to an earlier savepoint just before it acquired the specific lock causing the cycle, saving the rest of its work.

### 3. Guard Against Victim Starvation
If the cost formula always picks the youngest or smallest transaction as the victim, the same unlucky transaction could get aborted over and over again every time it restarts. To prevent this **starvation**, the system includes the **number of times a transaction has already been rolled back** in the victim-selection formula, making repeat victims protected after a few rollbacks.

---

## Avoidance/Prevention vs. Detection: Cost Trade-Off Analysis

A classic Silberschatz question (Exercise 18.20, tested verbatim in **2018 Q.5(b)**) asks: *When is it cheaper to prevent/avoid deadlocks upfront rather than letting them happen and detecting them?*

### Prevention / Avoidance Is Cheaper When:
1. **Lock Contention Is High:** Many transactions are constantly fighting over the same "hot" records, so deadlocks happen all the time. Allowing and recovering from constant deadlocks wastes massive CPU and I/O on repeated rollbacks.
2. **Transactions Are Long and Expensive:** If each transaction updates thousands of rows or runs heavy calculations, aborting a deadlocked transaction near the end throws away a huge amount of work.
3. **Maintaining the Wait-For Graph Is Too Costly:** When thousands of concurrent transactions acquire and release locks every millisecond, updating $G = (V, E)$ and running cycle-detection searches creates a bottleneck.

### Detection & Recovery Is Cheaper When:
1. **Deadlocks Are Rare (Low Contention):** Transactions mostly touch separate rows, so cycles almost never form.
2. **Transactions Are Short:** Quick OLTP queries finish in a few milliseconds, so rolling back an occasional victim costs almost nothing and lets normal transactions run at full speed without prevention restrictions.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.7(b) · Deadlock Definition and Prevention Methods

> **Appeared:** 2017 Q.7(b) — (04 marks)

**Question:**

Define deadlock. Explain how deadlock is prevented?

**Full Answer:**

#### 1. Deadlock Definition
A deadlock is a state in which a set of two or more concurrent transactions are blocked indefinitely because each transaction in the set holds a lock on a data item that another transaction in the set needs, creating a circular wait where none of the transactions can proceed.

#### 2. Deadlock Prevention Methods
Deadlock prevention protocols ensure that the database never enters a circular wait state using four main methods:

1. **Pre-declaration (Pre-claiming All Locks):**
   Every transaction must request and acquire all the locks it will need before it begins executing, or else wait without holding any locks.
   - *Drawback:* It is often hard to know all needed data items in advance, and locks are held idle for long periods.

2. **Lock Ordering (Graph-Based / Total Ordering):**
   All data items are assigned a strict global order ($d_1 < d_2 < \dots < d_n$), and transactions may only request locks in ascending order. Because requests always move forward along the order, a cycle can never form.

3. **Timestamp-Based Preemption Schemes (`Wait-Die` and `Wound-Wait`):**
   Each transaction $T_i$ receives a startup timestamp $\text{TS}(T_i)$ upon arrival. When $T_i$ requests a lock currently held by $T_j$:
   - **Wait-Die (Non-preemptive):** If $T_i$ is older than $T_j$ ($\text{TS}(T_i) < \text{TS}(T_j)$), $T_i$ waits. If $T_i$ is younger, $T_i$ dies (rolls back and restarts with its original timestamp).
   - **Wound-Wait (Preemptive):** If $T_i$ is older than $T_j$, $T_i$ wounds (preempts and rolls back) $T_j$ to take the lock immediately. If $T_i$ is younger, $T_i$ waits.

   | Scheme | Older $T_i$ requests item held by Younger $T_j$ | Younger $T_i$ requests item held by Older $T_j$ | Mechanism |
   | :--- | :--- | :--- | :--- |
   | **Wait-Die** | Older **waits** | Younger **dies** ($T_i$ rolls back) | Non-preemptive |
   | **Wound-Wait** | Older **wounds** younger ($T_j$ rolls back) | Younger **waits** | Preemptive |

4. **Timeout-Based Scheme:**
   A transaction waits for a requested lock only up to a fixed timeout limit. If the lock is not granted within that time, the transaction assumes a potential deadlock and rolls itself back.

### 🎯 GQ2 · 2018 Q.5(b) · Deadlock in Transaction Management and Cost Trade-offs

> **Appeared:** 2018 Q.5(b) — (04 marks)

**Question:**

What do you know about deadlock in transaction management? Under what conditions it is less expensive to avoid deadlock than to allow deadlocks to occur and then to detect them?

**Full Answer:**

#### 1. Deadlock in Transaction Management
In transaction management, a deadlock is a stalemate across a set of active transactions $\{T_0, T_1, \dots, T_n\}$ where each transaction holds a lock needed by the next transaction in the set, forming a closed cycle in the wait-for graph:

$$
T_0 \to T_1 \to \dots \to T_n \to T_0
$$

Because two-phase locking forbids releasing locks early during the growing phase, none of the transactions in the cycle can advance unless the database intervenes and rolls back a victim transaction.

#### 2. Conditions Where Deadlock Avoidance/Prevention Is Less Expensive Than Detection
Avoiding or preventing deadlocks upfront is cheaper than allowing and detecting them under three conditions:

1. **High Lock Contention (Frequent Deadlocks):**
   When many concurrent transactions update the same hot data items, deadlocks occur frequently. Under detection, the system would constantly waste CPU time running cycle-detection searches and rolling back deadlocked work.
2. **Long-Running or Resource-Heavy Transactions:**
   When transactions perform heavy calculations or modify thousands of records, aborting a deadlocked transaction near completion throws away a huge amount of CPU and disk I/O work. Prevention avoids these expensive deep rollbacks.
3. **High Graph-Maintenance & Cycle-Detection Overhead:**
   In systems with thousands of simultaneous transactions and rapid lock requests, continuously updating the wait-for graph and scanning it for cycles adds heavy CPU and memory overhead.

*(Conversely, detection and recovery is cheaper when deadlocks are rare, transactions are short, and data contention is low.)*

### 🎯 GQ3 · 2020 Q.7(a) · Deadlock Definition and Two-Phase Locking Protocol

> **Appeared:** 2020 Q.7(a) — (04 marks)

**Question:**

What is deadlock? Describe the time-shared locking protocol with example.

*(Sorting Note: Second part asks for "time-shared locking protocol" [misprint for 2PL, cross-ref T11.2])*

**Full Answer:**

*Note: "Time-shared locking protocol" on the 2020 question paper is a printing typo for the **Two-Phase Locking (2PL) protocol**.*

#### 1. Deadlock
A deadlock is a system state in which two or more concurrent transactions are blocked waiting for each other to release locks in a circular chain, so that none of the transactions can proceed without external rollback intervention.

#### 2. Two-Phase Locking (2PL) Protocol
The Two-Phase Locking protocol guarantees conflict serializability by requiring every transaction to acquire and release locks in two sequential phases:

1. **Growing Phase:**
   - The transaction may acquire new shared (`lock-S`) or exclusive (`lock-X`) locks, or upgrade an existing lock (`S` $\to$ `X`).
   - **Rule:** No lock may be released during this phase.
2. **Shrinking Phase:**
   - The transaction may release held locks (`unlock`), or downgrade an existing lock (`X` $\to$ `S`).
   - **Rule:** No new lock may be acquired once the first lock has been released.

**Lock Point:** The exact point where a transaction acquires its final lock (marking the end of the growing phase) is called its **lock point**. Transactions can be serialized in the order of their lock points.

#### 3. Example Schedule
Consider transaction $T_1$ reading account $A$ and updating account $B$:

| Step | Operation | Phase |
| :---: | :--- | :--- |
| 1 | $\text{lock-S}(A)$; $\text{read}(A)$ | Growing Phase |
| 2 | $\text{lock-X}(B)$; $\text{read}(B)$; $\text{write}(B)$ | Growing Phase (**Lock Point**) |
| 3 | $\text{unlock}(A)$ | Shrinking Phase begins |
| 4 | $\text{unlock}(B)$ | Shrinking Phase |

Because all lock acquisitions (Steps 1–2) occur before the first unlock (Step 3), $T_1$ obeys 2PL.

### 🎯 GQ4 · 2021 Q.8(a) · Deadlock Detection on Wait-For Graph

> **Appeared:** 2021 Q.8(a) — (05 marks)

**Question:**

What is deadlock? Consider the following wait-for-graph:

![Wait-for-graph for Q.8(a)](diagrams/T11_2021_Q8a_wait_for_graph_pyq.jpg)
*Figure 2021_Q8.a: Wait-for-graph for deadlock detection (Source: Page 2, Q.8(a))*

Determine whether the schedule contains any deadlock or not.

*(Refer to the Wait-for-Graph Diagram and Detailed Text Representation below)*

> *Wait-for-Graph Details (`2021 Q.8(a)`):* Vertices $V = \{T_1, T_2, T_3, T_4, T_5\}$; Directed edges $E = \{(T_1, T_4), (T_1, T_2), (T_1, T_3), (T_4, T_5), (T_5, T_2), (T_2, T_4)\}$; Cycle $T_4 \to T_5 \to T_2 \to T_4 \implies$ **Deadlock**.

**Full Answer:**

#### 1. What is Deadlock?
A deadlock is an execution state in which two or more transactions are waiting indefinitely for locks held by one another in a circular chain, preventing any of them from making progress.

#### 2. Wait-For Graph Representation
From the given diagram, the wait-for graph $G = (V, E)$ has:
- **Vertices (Transactions):**

$$
V = \{T_1, T_2, T_3, T_4, T_5\}
$$

- **Directed Edges ($T_i \to T_j$ means $T_i$ waits for $T_j$):**

$$
E = \{(T_1 \to T_4),\, (T_1 \to T_2),\, (T_1 \to T_3),\, (T_4 \to T_5),\, (T_5 \to T_2),\, (T_2 \to T_4)\}
$$

#### 3. Cycle Detection Analysis
Tracing the directed edges starting from $T_4$:
1. $T_4$ is waiting for $T_5$ ($T_4 \to T_5$).
2. $T_5$ is waiting for $T_2$ ($T_5 \to T_2$).
3. $T_2$ is waiting for $T_4$ ($T_2 \to T_4$).

This forms a closed directed cycle of length 3:

$$
T_4 \to T_5 \to T_2 \to T_4
$$

#### 4. Verdict & Transaction Status
**Yes, the schedule contains a deadlock** because the wait-for graph contains a directed cycle.

- **Deadlocked Transactions:** $\mathbf{T_2, T_4, \text{ and } T_5}$ form the cycle and are deadlocked.
- **Other Transactions:**
  - $T_1$ has outgoing arrows to $T_2, T_3,$ and $T_4$, so $T_1$ is blocked waiting for those transactions to finish, but $T_1$ is **not** inside the cycle itself.
  - $T_3$ has no outgoing arrows, so $T_3$ is not waiting on any lock and can run normally to completion.

#### 5. How to Recover
To break the deadlock, the recovery manager selects one victim from $\{T_2, T_4, T_5\}$ with the lowest rollback cost and rolls it back (totally or partially), removing its edges from the cycle so the remaining transactions can finish.

### 🎯 HYE-01 · Exercise 18.21 · Starvation Possibility under Deadlock Avoidance

> **Source:** Silberschatz 7e · Chapter 18 (Exercise 18.21)  
> **Exam Relevance:** Prime Conceptual Viva and Theoretical Exam Question  
> **Key Tested Concept:** Starvation hazards in deadlock-avoidance schemes and countermeasure protocols.

**Problem Statement:**
> If deadlock is avoided by deadlock-avoidance schemes, is starvation still possible? Explain your answer with concrete scenarios and identify how DBMSs prevent starvation.

**Model Exam-Style Solution:**

1. **Direct Verdict:**
   **Yes, starvation is still possible** under deadlock-avoidance schemes unless specific anti-starvation mechanisms (such as timestamp ordering or priority aging) are enforced.

2. **Scenario 1: Resource-Ordering Deadlock Prevention**
   - In a scheme where data items must be locked in a predetermined global linear order ($Q_1 < Q_2 < \dots < Q_n$), deadlocks are impossible because wait cycles cannot form.
   - However, suppose transaction $T_{\text{long}}$ requires both $Q_1$ and $Q_{100}$.
   - While $T_{\text{long}}$ holds $Q_1$ and waits for $Q_{100}$, a continuous stream of short transactions ($T_A, T_B, T_C, \dots$) repeatedly acquire and release $Q_{100}$.
   - If the lock manager grants $Q_{100}$ to arriving short transactions based on immediate availability or random selection, $T_{\text{long}}$ may be repeatedly passed over and **starve indefinitely**, even though no deadlock ever occurs.

3. **Scenario 2: Rollback-Based Avoidance without Timestamp Retention**
   - In schemes where transactions are rolled back to avoid potential deadlocks (such as preempting or aborting younger/older transactions upon resource contention), if a rolled-back transaction were restarted with a *new* priority or timestamp, it could repeatedly clash with existing transactions and be aborted again and again.
   - Without anti-starvation rules, repeated rollbacks cause **livelock / infinite starvation**.

4. **DBMS Countermeasures to Prevent Starvation:**
   - **FIFO Lock Queues:** A transaction waiting for a lock is placed in a first-in, first-out queue. Incompatible arriving requests are queued behind it rather than granted immediately.
   - **Timestamp Seniority Retention:** Under timestamp-based schemes (e.g., Wait-Die and Wound-Wait), rolled-back transactions **retain their original timestamps** upon restart. As time advances, their seniority increases until they become the oldest transaction in the system and cannot be preempted or denied locks.
   - **Aging / Priority Boosting:** Increasing the scheduling priority of waiting transactions proportional to their wait time. $\blacksquare$

**💡 RUET Exam Takeaway:**
Deadlock avoidance guarantees that the system as a whole never freezes in a cycle, but it does **not** automatically guarantee individual transaction progress. Always mention FIFO lock queues and timestamp seniority retention as the solutions to starvation.

## ⚡ Exam Tips & Common Mistakes

1. **Write out the cycle explicitly:** On wait-for graph questions like `2021 Q.8(a)`, always write the full loop ($T_4 \to T_5 \to T_2 \to T_4$) Including the repeated start/end node so the grader sees the closed cycle immediately.
2. **Don't include non-cycle nodes in the deadlocked set:** In `2021 Q.8(a)`, many students mistakenly list $T_1$ as deadlocked because $T_1$ points to $T_2$ and $T_4$. Pointing *into* a cycle makes $T_1$ temporarily blocked, not part of the circular deadlock!
3. **Spot the 2020 Q.7(a) misprint:** If an exam asks for the "time-shared locking protocol," note politely in one line that it refers to the **Two-Phase Locking (2PL) protocol** and then write the full 2PL answer.
4. **Wait-For Graph vs. Precedence Graph:** Keep their purposes distinct! A cycle in a **Precedence Graph** (`T10.03a`) means the schedule is **not conflict serializable**. A cycle in a **Wait-For Graph** (`T11.04`) means the system is currently in a **deadlock**.
