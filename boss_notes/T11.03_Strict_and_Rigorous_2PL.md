# T11.3: Strict 2PL, Rigorous 2PL, and Drawbacks of 2PL

> **Topic:** T11 — Concurrency Control Protocols | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (0 marks)
> **Sources:** Silberschatz 7e Ch. 18 (§18.1.3, pp. 842–844) · Lecture Deck 08 (Slides 16–19) · Raidah Notes (p. 30)

## Why This Topic Matters

Basic Two-Phase Locking (2PL) guarantees conflict serializability, yet virtually no commercial database engine uses Basic 2PL on its own. Why? Because Basic 2PL lets a transaction unlock modified data during its shrinking phase *before* the transaction actually commits. If that transaction crashes a millisecond later, any other transaction that read the unlocked dirty data is forced to roll back (or worse, may have already committed). **Strict 2PL** and **Rigorous 2PL** solve this problem by holding locks until the transaction commits or aborts. Understanding the exact difference between Basic, Strict, and Rigorous 2PL connects concurrency control (`T11`) directly to crash recovery (`T10.06`).

---

## 📝 Key Definitions

> **Strict Two-Phase Locking Protocol:** "This protocol requires not only that locking be two-phase, but also that all exclusive-mode locks taken by a transaction must be held until that transaction commits." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.1.3 (p. 842)

> **Rigorous Two-Phase Locking Protocol:** "Another variant of two-phase locking is the rigorous two-phase locking protocol, which requires that *all* locks be held until the transaction commits." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.1.3 (p. 842)

> **Lock Point:** "Consider any schedule; the point in the schedule where the transaction has obtained its final lock (that is, the end of its growing phase) is called the lock point of the transaction." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.1.3 (p. 841)

---

## Intuitive Mental Model: Basic vs. Strict vs. Rigorous 2PL

All three protocols follow the same growing-phase rule (acquire locks first). The **only difference** is *when* a transaction is allowed to release its Shared (`S`) and Exclusive (`X`) locks:

1. **Basic 2PL ("Unlock whenever you are done with the item"):**  
   Once a transaction hits its lock point, it can release **both `S` and `X` locks** gradually during the shrinking phase, even before committing. Fast, but exposes uncommitted writes to other transactions.
2. **Strict 2PL ("Hold write locks until commit"):**  
   Once a transaction hits its lock point, it can release **read (`S`) locks** early during the shrinking phase, but it must hold **every write (`X`) lock** until it commits or aborts. Because nobody can touch uncommitted writes, dirty reads and cascading rollbacks disappear.
3. **Rigorous 2PL ("Hold EVERY lock until commit"):**  
   The transaction holds **both `S` and `X` locks** all the way until commit or abort. There is no gradual shrinking phase at all, because every lock is released in one burst when the transaction finishes.

---

## Drawbacks of Basic Two-Phase Locking (2PL)

Even when transactions strictly obey Basic 2PL, three major operational problems can occur:

### 1. Cascading Rollbacks
Under Basic 2PL, a transaction enters its shrinking phase as soon as it releases its first lock. Suppose transaction $T_1$ modifies item $A$ and unlocks $A$ before committing. Transaction $T_2$ can immediately lock and read $A$. If $T_1$ then crashes and aborts, $T_2$ has read a dirty value and must also be rolled back. If $T_3$ read data written by $T_2$, $T_3$ must roll back too, creating a costly domino effect.

### 2. Irrecoverable Schedules
Worse still, after $T_1$ unlocks modified item $A$ early, $T_2$ might read $A$, finish its own work, and execute `commit` before $T_1$ finishes. If $T_1$ aborts afterward, the database cannot undo $T_2$ because committed transactions are permanent under ACID durability. The schedule becomes completely **irrecoverable**:

| Step | Transaction $T_1$ | Transaction $T_2$ | Description |
| :---: | :--- | :--- | :--- |
| 1 | $\text{lock-X}(A)$ | | $T_1$ acquires exclusive lock |
| 2 | $\text{read}(A)$ | | $T_1$ reads $A$ |
| 3 | $A := A + 100$ | | $T_1$ modifies $A$ |
| 4 | $\text{write}(A)$ | | $T_1$ writes updated $A$ |
| 5 | $\text{unlock}(A)$ | | $T_1$ enters shrinking phase early (valid in Basic 2PL!) |
| 6 | | $\text{lock-S}(A)$ | $T_2$ acquires shared lock |
| 7 | | $\text{read}(A)$ | $T_2$ reads dirty uncommitted data |
| 8 | | $\text{unlock}(A)$ | $T_2$ releases lock |
| 9 | | **commit** | $T_2$ commits permanently |
| 10 | **abort** | | $T_1$ fails and aborts (**Irrecoverable!**) |

### 3. Deadlock Susceptibility
Basic 2PL does not prevent deadlocks. When two transactions acquire locks in opposite orders (for example, $T_1$ locks $A$ and requests $B$, while $T_2$ locks $B$ and requests $A$), both transactions get stuck waiting for each other forever until the database aborts one of them.

## Anatomy of Cascading Rollback under Basic 2PL

Figure 18.8 from Silberschatz shows how an early unlock in Basic 2PL triggers a three-transaction cascading rollback:

![Partial schedule under two-phase locking showing cascading rollback](diagrams/T11.03_cascading_rollback_2pl__Textbook_fig_18_08.jpg)
*Figure 18.8: Partial schedule under basic two-phase locking showing cascading rollback (Source: Silberschatz 7e, Figure 18.8).*

### Step-by-Step Trace of Figure 18.8
1. Transaction $T_5$ locks $A$ in exclusive mode, reads $A$, locks $B$ in shared mode, reads $B$, writes $A$, and then **unlocks $A$ early** while still working on $B$. Notice that $T_5$ obeys Basic 2PL because it acquired both of its locks (`lock-X(A)` and `lock-S(B)`) before its first unlock (`unlock(A)`).
2. As soon as $T_5$ unlocks $A$, transaction $T_6$ acquires `lock-X(A)`, reads $T_5$'s uncommitted value of $A$, writes a new value of $A$, and unlocks $A$.
3. Next, transaction $T_7$ acquires `lock-S(A)` and reads the uncommitted value written by $T_6$.
4. Now suppose $T_5$ hits an error and aborts. Because $T_6$ read uncommitted data from $T_5$, $T_6$ must be rolled back. And because $T_7$ read uncommitted data from $T_6$, $T_7$ must be rolled back too!

---

## Strict Two-Phase Locking (Strict 2PL)

To stop both irrecoverable schedules and cascading rollbacks, **Strict Two-Phase Locking** adds one rule on top of Basic 2PL:

### Rules of Strict 2PL
1. **Two-Phase Rule:** A transaction must acquire all its locks during the growing phase before releasing any lock.
2. **Hold Exclusive Locks Until Commit:** Every **exclusive (`X`) lock** acquired by a transaction must be held until that transaction commits or aborts.
3. **Shared Locks Can Still Release Early:** Shared (`S`) locks may still be released gradually during the shrinking phase before commit.

### Why Strict 2PL Works
Because every modified item is protected by an `X` lock right up until the writer commits or aborts, no other transaction can ever read or overwrite uncommitted data. That means every schedule produced by Strict 2PL is guaranteed to be **strict** (and therefore both **cascadeless** and **recoverable**), while still allowing read-only locks to be freed early.

---

## Rigorous Two-Phase Locking (Rigorous 2PL)

Most production database engines go one step further and implement **Rigorous Two-Phase Locking**.

### Rules of Rigorous 2PL
1. **Two-Phase Rule:** A transaction acquires locks as needed during execution.
2. **Hold ALL Locks Until Commit:** **Every lock** (both **shared `S`** and **exclusive `X`**) must be held until the transaction commits or aborts.
3. **Single-Step Unlock at Commit:** Because no lock is ever released mid-transaction, the shrinking phase collapses into a single instant when the transaction commits or aborts and releases all its locks at once.

### Why Commercial Databases Love Rigorous 2PL
- **Commit-Order Serialization:** In Basic and Strict 2PL, the equivalent serial order depends on when transactions hit their internal *lock points*. In Rigorous 2PL, a transaction's lock point and its commit point effectively align, so transactions serialize in the exact **order in which they commit**.
- **Simpler Lock Manager:** An application programmer never has to write explicit `unlock` statements or worry about when the shrinking phase starts. The database engine automatically grabs `S` and `X` locks as SQL statements run and frees all of them in one batch when `COMMIT` or `ROLLBACK` executes.

---

## Side-by-Side Comparison: Basic 2PL vs. Strict 2PL vs. Rigorous 2PL

| Feature / Property | Basic Two-Phase Locking (2PL) | Strict Two-Phase Locking (Strict 2PL) | Rigorous Two-Phase Locking (Rigorous 2PL) |
| :--- | :--- | :--- | :--- |
| **Lock Acquisition** | During growing phase only | During growing phase only | During growing phase only |
| **When Shared (`S`) Locks Release** | Anytime during shrinking phase | Anytime during shrinking phase | **Only at commit / abort** |
| **When Exclusive (`X`) Locks Release** | Anytime during shrinking phase | **Only at commit / abort** | **Only at commit / abort** |
| **Conflict Serializability** | Guaranteed | Guaranteed | Guaranteed |
| **Recoverability** | Not guaranteed (can be irrecoverable) | **Guaranteed** | **Guaranteed** |
| **Cascading Rollback** | Possible | **Prevented (strict & cascadeless)** | **Prevented (strict & cascadeless)** |
| **Deadlock Freedom** | Not guaranteed (deadlocks can occur) | Not guaranteed (deadlocks can occur) | Not guaranteed (deadlocks can occur) |
| **Serialization Order** | Order of lock points | Order of lock points | **Order of transaction commit points** |
| **Concurrency Level** | Highest among the three | Moderate (readers freed early) | Slightly lower (all locks held until end) |
| **Real-World Adoption** | Rarely used alone | Used in specialized systems | **Standard in most commercial RDBMS** |

## Lock Conversions in Two-Phase Locking

As introduced in `T11.02`, two-phase locking protocols also use **lock conversions** so transactions do not have to hold exclusive locks longer than necessary:

### 1. Lock Upgrade (`lock-S` $\to$ `lock-X`)
- Converts a held shared lock into an exclusive lock.
- **Rule:** Permitted **only during the growing phase**.
- **Why it helps:** A transaction that reads an item first and updates it much later can hold a friendly `S` lock while reading (letting other readers run concurrently) and upgrade to `X` only when it is ready to write.

### 2. Lock Downgrade (`lock-X` $\to$ `lock-S`)
- Converts a held exclusive lock down to a shared lock.
- **Rule:** Permitted **only during the shrinking phase** (in Basic or Strict 2PL).
- **Why it helps:** Once a transaction finishes updating an item, downgrading lets other transactions read that item while the original transaction finishes its remaining steps.

## 🔮 Likely Questions

### 🎯 LQ1 · Drawbacks of Basic 2PL and the Strict 2PL Solution

> **Significance:** High-probability exam question based on Lecture Deck 08 Slides 16–19 and Textbook §18.1.3.

**Question:**

Explain the major drawbacks of the basic Two-Phase Locking (2PL) protocol. How does the Strict Two-Phase Locking protocol overcome these drawbacks?

**Full Answer:**

#### 1. Drawbacks of Basic Two-Phase Locking (2PL)
Basic 2PL requires a transaction to acquire all its locks before releasing any lock, but it allows locks to be released during the shrinking phase before the transaction commits. This creates three major drawbacks:
- **Cascading Rollbacks:** If transaction $T_1$ unlocks a modified item $A$ during its shrinking phase, transaction $T_2$ can lock and read $A$. If $T_1$ later crashes and aborts, $T_2$ has read uncommitted (dirty) data and must also be rolled back, triggering a chain of rollbacks across any transactions that read from $T_2$.
- **Irrecoverable Schedules:** If $T_2$ reads $T_1$'s uncommitted update on $A$ and commits before $T_1$ aborts, the recovery manager cannot roll back $T_2$ without violating durability, leaving the database inconsistent.
- **Deadlock Vulnerability:** Basic 2PL does not prevent circular waits when two transactions lock items in opposite orders.

#### 2. How Strict 2PL Overcomes These Drawbacks
Strict 2PL adds one rule on top of Basic 2PL:
- **Rule:** Every **exclusive (`X`) lock** acquired by a transaction must be held continuously until that transaction **commits or aborts** (while shared `S` locks may still be released during the shrinking phase).
- Because write locks are held until commit, no other transaction can read or overwrite uncommitted data. Dirty reads and dirty writes become impossible, guaranteeing that every schedule under Strict 2PL is **strict**, **cascadeless**, and **recoverable**.

### 🎯 LQ2 · Strict 2PL vs. Rigorous 2PL and Commit Ordering

> **Significance:** Standard university viva and exam comparison question from Textbook §18.1.3.

**Question:**

Differentiate between Strict Two-Phase Locking and Rigorous Two-Phase Locking protocols. Why is Rigorous 2PL easier to implement in commercial database management systems?

**Full Answer:**

#### 1. Distinction Between Strict 2PL and Rigorous 2PL

| Criteria | Strict Two-Phase Locking | Rigorous Two-Phase Locking |
| :--- | :--- | :--- |
| **Exclusive (`X`) Locks** | Held until transaction commit or abort | Held until transaction commit or abort |
| **Shared (`S`) Locks** | Can be released early during shrinking phase | **Held until transaction commit or abort** |
| **Shrinking Phase** | Present (for releasing shared locks) | Absent (all locks released at once at commit) |
| **Serialization Order** | Determined by transaction **lock points** | Determined by transaction **commit order** |
| **Concurrency Level** | Slightly higher concurrency for readers | Slightly lower concurrency |

#### 2. Why Rigorous 2PL Is Easier to Implement
1. **Natural Commit-Order Serialization:** Under Rigorous 2PL, transactions are serialized in the exact order in which they commit, matching what users and log-based replication tools expect without tracking internal lock points.
2. **Automatic Lock Management:** In Strict or Basic 2PL, the system would need to know when a transaction is done reading an item to release `S` locks early and verify that no new locks are requested afterward. In Rigorous 2PL, the database engine simply acquires `S` and `X` locks as SQL queries execute and releases all held locks in a single batch when `COMMIT` or `ROLLBACK` runs.

### 🎯 LQ3 · Proving Irrecoverability under Basic 2PL

> **Significance:** Core design drill verifying the dirty read failure mode under basic 2PL.

**Question:**

Can a schedule generated under the Basic 2PL protocol lead to an irrecoverable schedule? Justify your answer with an explicit execution schedule.

**Full Answer:**

**Yes, a schedule that strictly obeys Basic 2PL can still be irrecoverable.**

Basic 2PL only requires all `lock` operations to precede the first `unlock` operation within each transaction. It does not require locks to be held until `commit`. If a transaction unlocks a modified item early during its shrinking phase, another transaction can read the uncommitted value and commit before the writer aborts.

#### Explicit Execution Schedule
Consider transactions $T_1$ and $T_2$ operating on item $A$:

$$
\begin{aligned}
T_1 &: \text{lock-X}(A) \to \text{read}(A) \to \text{write}(A) \to \text{unlock}(A) \to \dots \to \text{abort} \\
T_2 &: \text{lock-S}(A) \to \text{read}(A) \to \text{unlock}(A) \to \text{commit}
\end{aligned}
$$

#### Step-by-Step Trace
1. $T_1$ executes $\text{lock-X}(A)$, reads $A$, and writes a new uncommitted value $A := A + 50$.
2. $T_1$ executes $\text{unlock}(A)$ and enters its shrinking phase while continuing local work. Because $T_1$ requests no further locks, it obeys Basic 2PL.
3. $T_2$ acquires $\text{lock-S}(A)$ and reads the uncommitted value written by $T_1$.
4. $T_2$ executes $\text{unlock}(A)$ and **commits**. The database reports success to the user.
5. $T_1$ then crashes and **aborts**.
6. Because $T_2$ read $T_1$'s uncommitted write and has already committed, $T_2$ cannot be rolled back without breaking durability, making the schedule **irrecoverable**.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 18.17 · Practical Trade-Offs of Strict 2PL and Rigorous 2PL

> **Source:** Silberschatz 7e · Chapter 18 (Exercise 18.17)  
> **Exam Relevance:** Prime Overdue Systems Architecture Question  
> **Key Tested Concept:** Comparative analysis of Basic 2PL, Strict 2PL, and Rigorous 2PL under concurrency, recovery, and commit ordering.

**Problem Statement:**
> 1. Define **Strict 2PL** and **Rigorous 2PL**, highlighting how they restrict lock release operations compared to Basic 2PL.
> 2. Explain why Rigorous 2PL guarantees that transactions can be serialized in the **exact order in which they commit**.
> 3. Summarize the practical trade-offs (benefits vs disadvantages) that lead almost all relational database engines (PostgreSQL, MySQL, Oracle) to implement Strict or Rigorous 2PL over Basic 2PL.

**Model Exam-Style Solution:**

1. **Definitions & Lock Release Restrictions:**
   - **Basic 2PL:** A transaction may release locks at any time after reaching its lock point. Once it releases its first lock, it enters the shrinking phase and cannot acquire any new locks.
   - **Strict 2PL:** Requires that **all Exclusive ($X$) locks** must be held until the transaction commits or aborts. Shared ($S$) locks may be released during the shrinking phase before commit.
   - **Rigorous 2PL:** Requires that **ALL locks (both Shared and Exclusive)** must be held until the transaction commits or aborts. (There is effectively no shrinking phase until after commit).

2. **Commit-Order Serialization under Rigorous 2PL:**
   - Under Rigorous 2PL, if transaction $T_1$ conflicts with transaction $T_2$ on data item $Q$, one of them must hold an exclusive lock on $Q$.
   - Suppose $T_1$ accesses $Q$ first. $T_1$ must hold its lock on $Q$ until it commits.
   - Therefore, $T_2$ cannot access $Q$ until after $T_1$ has committed!
   - This means that for every conflicting operation edge $T_1 \rightarrow T_2$ in the precedence graph, $T_1$ must commit before $T_2$ commits ($c_1 < c_2$).
   - Consequently, the serialization order of transactions is **identical to the chronological order in which they commit**.

3. **Practical Trade-offs & Engineering Justification:**

| Dimension | Basic 2PL | Strict 2PL | Rigorous 2PL |
| :--- | :--- | :--- | :--- |
| **Serializability** | Yes | Yes | Yes (in commit order) |
| **Cascading Aborts** | **Possible** (Not cascadeless) | **Completely Eliminated** | **Completely Eliminated** |
| **Recovery Mechanism** | Complex undo (non-strict) | Simple pre-image restore | Simple pre-image restore |
| **Concurrency Level** | Highest (locks released early) | Moderate | Lowest (reads held until commit) |
| **Deadlock Risk** | Present | Present | Present |

   - **Why Engines Choose Strict/Rigorous 2PL:**
     In commercial database systems, the catastrophic performance collapse caused by **cascading aborts** (where aborting one transaction forces rolling back hundreds of concurrent transactions) far outweighs the marginal concurrency gained by releasing write locks early. Strict 2PL guarantees cascadeless and strict schedules, ensuring fast, reliable crash recovery. $\blacksquare$

**💡 RUET Exam Takeaway:**
Memorize that **Strict 2PL holds all $X$-locks until commit**, whereas **Rigorous 2PL holds ALL ($S$ and $X$) locks until commit**.

## ⚡ Exam Tips & Common Mistakes

1. **None of the 2PL variants prevent deadlocks:** Basic 2PL, Strict 2PL, and Rigorous 2PL can **all** suffer from deadlocks. Holding locks longer (until commit) solves cascading rollbacks, not deadlocks!
2. **Remember which lock is held until commit:**
   - **Strict 2PL** = Hold **Exclusive (`X`)** locks until commit (`S` locks can release early).
   - **Rigorous 2PL** = Hold **ALL (`S` and `X`)** locks until commit.
3. **Lock Point Order vs. Commit Order:** Basic 2PL and Strict 2PL serialize in **lock-point order**, whereas Rigorous 2PL serializes in **commit order**.
4. **Upgrade vs. Downgrade timing:** Upgrades (`S` $\to$ `X`) are only valid in the **growing phase**, while downgrades (`X` $\to$ `S`) are only valid in the **shrinking phase**.
