# T05.4: SQL Aggregate Functions

> **Topic:** T05 — SQL (DDL, DML, Aggregates, Subqueries) | **Priority:** 🟡 | **Exam Frequency:** 2/7 finals (7 marks)
> **Sources:** Silberschatz 7e Ch. 3 (§3.7, pp. 91–98) · Lecture Deck 03 (Slides 30–31) · Classnote by Raidah (p. 2) · Handnote by Fahim (p. 43)

## Why This Topic Matters

Aggregate functions convert a collection of row values into a single summary value. They power all numeric calculations and analytical summaries in database queries. RUET final exams test both standard theoretical definitions (2019 Q.8(a)) and concrete calculation queries (2024 Q.7(a)). Understanding duplicate retention and NULL handling is essential to avoid common exam traps.

---

## 📝 Key Definitions

> **Aggregate Function:** "Aggregate functions are functions that take a collection (a set or multiset) of values as input and return a single value." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7 (p. 91)

> **Null Value Handling in Aggregation:** "All aggregate functions except count (*) ignore null values in their input collection." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.4 (p. 96)

> **Empty Collection Rule:** "As a result of this rule, if the input collection of values is empty, or contains only null values, the count aggregate returns 0, and all other aggregates return null." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.4 (p. 98)

---

## The Five Standard SQL Aggregate Functions

SQL provides five primary built-in aggregate functions. Each function operates on a column multiset:

| Function | Mathematical Purpose | Supported Data Types | Treatment of Duplicates | Example Query |
| :--- | :--- | :--- | :--- | :--- |
| `AVG([DISTINCT] A)` | Arithmetic mean of values | Numeric only (`INT`, `DECIMAL`, `FLOAT`) | Retains duplicates by default; drops duplicates if `DISTINCT` specified | `SELECT AVG(salary) FROM instructor;` |
| `SUM([DISTINCT] A)` | Arithmetic sum of values | Numeric only (`INT`, `DECIMAL`, `FLOAT`) | Retains duplicates by default; drops duplicates if `DISTINCT` specified | `SELECT SUM(salary) FROM instructor;` |
| `MIN([DISTINCT] A)` | Minimum (lowest) value | Any ordered type (numeric, string, date) | `DISTINCT` allowed but produces the same result | `SELECT MIN(salary) FROM instructor;` |
| `MAX([DISTINCT] A)` | Maximum (highest) value | Any ordered type (numeric, string, date) | `DISTINCT` allowed but produces the same result | `SELECT MAX(salary) FROM instructor;` |
| `COUNT([DISTINCT] A)` | Count of non-null values | Any data type | Counts all non-null entries; counts unique entries if `DISTINCT` specified | `SELECT COUNT(ID) FROM instructor;` |
| `COUNT(*)` | Count of total rows | Whole relation (tuples) | Counts every row, including rows with all null attributes | `SELECT COUNT(*) FROM instructor;` |

---

## Detailed Mechanics of Each Function

### 1. `COUNT` Variations and Distinctions

The `COUNT` function works in three slightly different ways depending on what you pass inside its parentheses:

1. **`COUNT(*)`:**
   - Counts every row in the table that passes the `WHERE` filter, regardless of what is inside the columns.
   - Because it counts whole rows rather than inspecting a specific column, it never ignores `NULL` values.
   - You cannot use `DISTINCT` here (`COUNT(DISTINCT *)` triggers a syntax error).

2. **`COUNT(attribute)`:**
   - Looks at the chosen column for each row and counts only the rows where that column is not `NULL`.
   - Duplicate non-null values are still counted separately.

3. **`COUNT(DISTINCT attribute)`:**
   - Looks at the chosen column, ignores any `NULL` entries, removes duplicate values, and counts only the unique values left over.

```sql
-- Count total course sections offered in Spring 2018
SELECT COUNT(*)
FROM teaches
WHERE semester = 'Spring' AND year = 2018;

-- Count total distinct instructors teaching in Spring 2018
SELECT COUNT(DISTINCT ID)
FROM teaches
WHERE semester = 'Spring' AND year = 2018;
```

### 2. `SUM` and `AVG`: Duplicate Retention Rule

Unlike set operations that strip out duplicates, `SUM` and `AVG` must keep duplicate numbers by default so the math stays accurate. For instance, suppose a department has three instructors earning \$75,000, \$75,000, and \$90,000. The true total payroll is:

$$
\text{Total Salary} = 75000 + 75000 + 90000 = 240000
$$

Dividing that total by all 3 instructors gives the true average salary:

$$
\text{Average Salary} = \frac{240000}{3} = 80000
$$

If you wrote `AVG(DISTINCT salary)` instead, SQL would throw away the second \$75,000 salary before averaging:

$$
\text{Distorted Average} = \frac{75000 + 90000}{2} = 82500
$$

Because of this, `ALL` is always the default inside `SUM` and `AVG`. Never put `DISTINCT` inside `SUM` or `AVG` unless an exam question specifically asks for the sum or average of distinct values.

### 3. `MIN` and `MAX`: Non-Numeric Types

While `SUM` and `AVG` only make sense for numbers, `MIN` and `MAX` work on any data type that has a natural sorting order:
- **Numbers:** Uses normal numerical order (for example, `MIN(salary)` finds the smallest salary).
- **Strings:** Uses alphabetical (ASCII/Unicode) order, where `'Ahmed'` comes before `'Zaman'`.
- **Dates and Times:** Uses chronological order, so `MIN(order_date)` gives the earliest date and `MAX(order_date)` gives the latest date.

## NULL Value Semantics in Aggregation

`NULL` values can easily trip you up in aggregate queries if you do not keep two simple rules in mind.

### The Two Fundamental NULL Rules

1. **The Ignore Rule:**
   Every column-level aggregate function (`SUM`, `AVG`, `MIN`, `MAX`, and `COUNT(col)`) completely skips `NULL` values before doing the math. Only `COUNT(*)` includes rows with `NULL`s because it counts rows rather than column values.

2. **The Empty Set Rule:**
   If a table has zero matching rows, or if every single value in the target column is `NULL`:
   - `COUNT` returns `0`.
   - `SUM`, `AVG`, `MIN`, and `MAX` return `NULL` (not `0`!).

### Concrete NULL Evaluation Trace

Suppose a relation `EMPLOYEE` has four rows:

| EID | Name | Salary |
| :--- | :--- | :--- |
| E01 | Alice | 50000 |
| E02 | Bob | NULL |
| E03 | Carol | 70000 |
| E04 | David | NULL |

The aggregate queries evaluate as follows:

| Query Expression | Evaluated Set | Result | Reason |
| :--- | :--- | :--- | :--- |
| `COUNT(*)` | 4 rows | `4` | Counts all physical rows |
| `COUNT(Salary)` | `{50000, 70000}` | `2` | Skips both NULL values |
| `SUM(Salary)` | `50000 + 70000` | `120000` | Ignores NULL entries |
| `AVG(Salary)` | `120000 / 2` | `60000` | Divides by count of non-null values ($n=2$) |
| `MIN(Salary)` | `{50000, 70000}` | `50000` | Smallest non-null number |
| `MAX(Salary)` | `{50000, 70000}` | `70000` | Largest non-null number |

> [!WARNING]
> Notice how `AVG(Salary)` divides by `2` rather than `4`. If it computed $\frac{120000}{4} = 30000$, it would be treating unknown (`NULL`) salaries as \$0 salaries, which would pull down the real average. Instead, SQL leaves `NULL` rows out of both the top and bottom of the fraction.

## Extended Relational Algebra Mapping

In relational algebra, we cannot express sums or averages using only basic operators like $\sigma$ or $\Pi$. Instead, SQL aggregation corresponds to the extended relational algebra **aggregation operator** $\gamma$ (sometimes written as calligraphic $\mathcal{G}$). Intuitively, $\gamma$ groups rows by a list of attributes on the left subscript and computes summary functions on the right subscript:

$$
{}_{G}\gamma_{F}(E)
$$

Where:
- $G$ is an optional list of grouping attributes (left blank when you aggregate the entire table as one big group).
- $F$ is the list of aggregate functions (`avg`, `sum`, `count`, `min`, `max`) applied to specific columns.
- $E$ is the input table or relational algebra expression.

For example, the SQL query:

```sql
SELECT AVG(salary) AS avg_sal
FROM instructor;
```

Maps directly to this relational algebra expression:

$$
\gamma_{\text{avg}(\text{salary}) \text{ as } \text{avg\_sal}}(\text{instructor})
$$

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2019 Q.8(a) · Four Aggregate Functions

> **Appeared:** 2019 Q.8(a) — (04 Marks)

**Question:**

Discuss about four aggregate functions.

**Full Answer:**

An **aggregate function** in SQL takes a collection (a set or multiset) of values from a column of a relation and computes a single summarizing scalar value. SQL automatically ignores null values during aggregation (except in `COUNT(*)`).

Four standard aggregate functions are:

#### 1. `COUNT()` Function
- **Purpose:** Counts the number of tuples or non-null attribute values in a relation.
- **Syntax Variants:**
  - `COUNT(*)`: Returns the total number of rows matching the query condition, including duplicate rows and rows with NULL values.
  - `COUNT(attribute)`: Returns the number of tuples with non-null values for the specified attribute.
  - `COUNT(DISTINCT attribute)`: Returns the count of unique, non-null values.
- **Example:** Count the total number of instructors:
  ```sql
  SELECT COUNT(*) AS total_instructors
  FROM instructor;
  ```

#### 2. `SUM()` Function
- **Purpose:** Computes the arithmetic total of all non-null values in a numeric column.
- **Data Type:** Operates strictly on numeric types (`INT`, `FLOAT`, `DECIMAL`).
- **Null Handling:** Skips all NULL values. Returns `NULL` if the relation is empty.
- **Example:** Calculate the total payroll across all instructors:
  ```sql
  SELECT SUM(salary) AS total_payroll
  FROM instructor;
  ```

#### 3. `AVG()` Function
- **Purpose:** Computes the arithmetic mean of all non-null values in a numeric column.
- **Formula:** Evaluates $\frac{\sum x_i}{n}$, where $n$ is the count of non-null values. Duplicates are retained by default to preserve the true mathematical mean.
- **Example:** Find the average salary of instructors in the Computer Science department:
  ```sql
  SELECT AVG(salary) AS avg_cs_salary
  FROM instructor
  WHERE dept_name = 'Comp. Sci.';
  ```

#### 4. `MIN()` and `MAX()` Functions
- **Purpose:** `MIN()` returns the lowest value in a column, while `MAX()` returns the highest value.
- **Data Types:** Works on numeric types, dates, and character strings (using lexicographical order).
- **Example:** Find the lowest and highest instructor salary:
  ```sql
  SELECT MIN(salary) AS lowest_salary,
         MAX(salary) AS highest_salary
  FROM instructor;
  ```

### 🎯 GQ2 · 2024 Q.7(a) · Definition of Aggregated Functions & Total Department Salary

> **Appeared:** 2024 Q.7(a) — (03 Marks | Sec B | CO1)

**Question:**

Define aggregated functions.  
EMPLOYEE (EID, Name, Department, Salary)  
SALES (SID, EID, SaleAmount, SaleDate)  
The management wants to reward the top-earing department. Write a SQL query to find the total salary paid per department.  
*(Note: "top-earing" printed verbatim in original paper; refers to top-earning)*

**Full Answer:**

#### 1. Definition of Aggregated Functions
An **aggregate function** is a built-in SQL function that takes a collection (multiset) of values from a column across multiple tuples (or subsets partitioned by a `GROUP BY` clause) and returns a single summarizing scalar value. The five standard aggregate functions defined in SQL are `AVG`, `MIN`, `MAX`, `SUM`, and `COUNT`.

#### 2. Schema Analysis
- `EMPLOYEE (EID, Name, Department, Salary)`: Contains the department name and employee salary.
- `SALES (SID, EID, SaleAmount, SaleDate)`: Contains individual sales transactions.
- **Exam Observation:** The problem asks to calculate the total salary paid per department. The required attributes (`Department` and `Salary`) reside entirely within the `EMPLOYEE` table. The `SALES` relation is an extraneous decoy table provided in the prompt and must not be joined. Joining `SALES` would multiply employee rows by their sales count, distorting the total salary sum.

#### 3. SQL Query

```sql
SELECT Department,
       SUM(Salary) AS Total_Salary
FROM EMPLOYEE
GROUP BY Department;
```

#### 4. Step-by-Step Execution Trace
Assume the `EMPLOYEE` table contains the following records:

| EID | Name | Department | Salary |
| :--- | :--- | :--- | :--- |
| 101 | Hasan | ECE | 60000 |
| 102 | Rafiq | CSE | 70000 |
| 103 | Tania | ECE | 65000 |
| 104 | Sohel | EEE | 55000 |

1. **`GROUP BY Department`:** Forms three distinct department groups:
   - Group `'ECE'`: Salaries `{60000, 65000}`
   - Group `'CSE'`: Salaries `{70000}`
   - Group `'EEE'`: Salaries `{55000}`
2. **`SUM(Salary)`:** Calculates the total for each group:
   - `'ECE'`: $60000 + 65000 = 125000$
   - `'CSE'`: $70000$
   - `'EEE'`: $55000$
3. **Output Relation:**

| Department | Total_Salary |
| :--- | :--- |
| ECE | 125000 |
| CSE | 70000 |
| EEE | 55000 |

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 3.30 · Formal Behavior of Aggregate Functions with NULLs and Empty Relations

> **Source:** Silberschatz 7e · Chapter 3 (Exercise 3.30)  
> **Exam Relevance:** High-Probability SQL Aggregation Theory & Edge-Case Drill  
> **Key Tested Concept:** Divergence between $\text{AVG}(A)$ and $\frac{\text{SUM}(A)}{\text{COUNT}(*)}$, null-value ignoring behavior, and empty relation semantics.

**Problem Statement:**
> Consider the following SQL query on the university schema:
>
> ```sql
> SELECT AVG(salary) - (SUM(salary) / COUNT(*))
> FROM instructor;
> ```
>
> We might expect that the result of this query is zero ($0$) since the average of a set of numbers is mathematically defined as the sum of the numbers divided by the count of numbers. Indeed, this holds true for relation instances where every tuple contains a valid, non-null salary.
> However, there are possible relation instances of `instructor` for which the result is **not zero** (or does not evaluate to $0$).
> 1. Provide an instance of the relation for which the result is **not zero**, and explain formally why the result is non-zero.
> 2. Explain what occurs if the `instructor` relation is **completely empty** ($0$ tuples).

**Model Exam-Style Solution:**

1. **Relation Instance with Non-Zero Result: The `NULL` Attribute Trap**
   - **Sample Instance of `instructor`:**
     Suppose the `instructor` table contains three tuples:

     | ID | name | dept_name | salary |
     | :--- | :--- | :--- | :--- |
     | 10101 | Srinivasan | Comp. Sci. | 65000 |
     | 12121 | Wu | Finance | 90000 |
     | 15151 | Mozart | Music | NULL |

   - **Evaluation of `AVG(salary)`:**
     - Standard SQL aggregate functions (except `COUNT(*)`) strictly **ignore `NULL` values** in their input collection.
     - Therefore, `AVG(salary)` computes the mean over only the non-null salaries $\{65000, 90000\}$:
       $$
       \text{AVG}(\text{salary}) = \frac{65000 + 90000}{2} = \frac{155000}{2} = 77500
       $$
     - The effective denominator is $\text{COUNT}(\text{salary}) = 2$.

   - **Evaluation of `SUM(salary) / COUNT(*)`:**
     - `SUM(salary)` ignores `NULL` and computes the sum of non-null salaries:
       $$
       \text{SUM}(\text{salary}) = 65000 + 90000 = 155000
       $$
     - However, `COUNT(*)` counts **all tuples** in the relation, regardless of whether any column contains `NULL`:
       $$
       \text{COUNT}(*) = 3
       $$
     - Thus:
       $$
       \frac{\text{SUM}(\text{salary})}{\text{COUNT}(*)} = \frac{155000}{3} \approx 51666.67
       $$

   - **Result of the Expression:**
     $$
     \text{Result} = 77500 - 51666.67 = 25833.33 \neq 0
     $$
     **Conclusion:** Whenever an attribute contains at least one `NULL` value alongside non-null values, $\text{COUNT}(*) > \text{COUNT}(A)$, causing $\text{AVG}(A) > \frac{\text{SUM}(A)}{\text{COUNT}(*)}$. The query evaluates to a positive non-zero value.

2. **The Empty Relation Edge Case ($0$ Tuples):**
   - Suppose the `instructor` relation is **empty** (contains $0$ tuples).
   - Under standard SQL aggregation rules:
     - `COUNT(*)` evaluates to `0`.
     - `SUM(salary)` evaluates to `NULL`.
     - `AVG(salary)` evaluates to `NULL`.
   - The subexpression `SUM(salary) / COUNT(*)` evaluates to `NULL / 0`. In SQL arithmetic, dividing `NULL` by any number (or division by zero) produces `NULL` (or raises a division-by-zero runtime error depending on engine settings).
   - The overall subtraction becomes `NULL - NULL = NULL`.
   - In SQL three-valued logic, `NULL` is an unknown/undefined value, **not zero** ($0$). Thus, the query does not return $0$.

**💡 RUET Exam Takeaway:**
Always emphasize the fundamental asymmetry in SQL: **`COUNT(*)` counts rows (including `NULL`s)**, whereas **all other aggregate functions (`AVG`, `SUM`, `MIN`, `MAX`, `COUNT(A)`) discard `NULL` values before computation**. On an empty table, `COUNT(*)` returns `0`, while all other aggregates return `NULL`.

## ⚡ Exam Tips & Common Mistakes

1. **The Decoy Table Trap:** When an exam gives multiple tables (like `EMPLOYEE` and `SALES`), inspect which table actually holds the target attributes. Joining `SALES` in 2024 Q.7(a) duplicates salary values whenever an employee makes multiple sales.
2. **`COUNT(*)` vs `COUNT(A)`:** Always state that `COUNT(*)` counts all rows including NULLs, whereas `COUNT(A)` counts only non-null values of attribute $A$.
3. **Empty Table Aggregation Trap:** An empty table produces `0` for `COUNT(*)`, but returns `NULL` for `SUM`, `AVG`, `MIN`, and `MAX`.
4. **No Aggregates on Incompatible Types:** Never apply `SUM()` or `AVG()` to character strings or dates. `MIN()` and `MAX()` work on strings and dates.
5. **Rename Aggregated Output with `AS`:** Raw aggregate outputs produce database-generated column headers like `avg(salary)`. Always assign meaningful aliases like `AS avg_salary`.
