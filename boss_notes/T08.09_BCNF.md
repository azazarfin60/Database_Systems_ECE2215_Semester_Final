# T08.9: Boyce-Codd Normal Form (BCNF) and 3NF vs. BCNF

> **Topic:** T08 — Normalization & Functional Dependencies | **Priority:** 🟢 | **Exam Frequency:** 0/7 finals (+ CT-03) (6 marks)
> **Sources:** Silberschatz 7e Ch. 7 (§7.3.1, §7.3.3, §7.5.1) · Lecture Deck 06 (Slides 41–46) · Classnote by Raidah (pp. 22–23)

## Why This Topic Matters

Boyce-Codd Normal Form (BCNF) is a stricter version of Third Normal Form (3NF) that eliminates all redundancy caused by functional dependencies. While 3NF has a special "escape clause" that allows a non-superkey on the left-hand side of a dependency if the right-hand side is part of a candidate key, BCNF closes that loophole completely. In RUET exams and class tests, you will be asked to find the highest normal form a relation satisfies, prove why every BCNF relation is in 3NF (but not vice versa), and explain why designers sometimes settle for 3NF to preserve dependencies.

---

## 📝 Key Definitions

> **Boyce-Codd Normal Form (BCNF):** "A relation schema $R$ is in BCNF with respect to a set $F$ of functional dependencies if, for all functional dependencies in $F^+$ of the form $\alpha \rightarrow \beta$, where $\alpha \subseteq R$ and $\beta \subseteq R$, at least one of the following holds:
> - $\alpha \rightarrow \beta$ is a trivial functional dependency (i.e., $\beta \subseteq \alpha$).
> - $\alpha$ is a superkey for schema $R$." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.3.1.1 (p. 314)

> **Third Normal Form (3NF):** "A relation schema $R$ is in **third normal form** (3NF) with respect to a set $F$ of functional dependencies if, for all functional dependencies in $F^+$ of the form $\alpha \rightarrow \beta$, where $\alpha \subseteq R$ and $\beta \subseteq R$, at least one of the following holds:
> - $\alpha \rightarrow \beta$ is a trivial functional dependency.
> - $\alpha$ is a superkey for $R$.
> - Each attribute $A$ in $\beta - \alpha$ is contained in a candidate key for $R$." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.3.2 (p. 317)

> **Determinant:** *(Course definition)* Any attribute or set of attributes on the left-hand side of a functional dependency $\alpha \to \beta$. In BCNF, every determinant of a non-trivial functional dependency must be a superkey.

## Understanding Boyce-Codd Normal Form

### Why 3NF Is Sometimes Not Enough (Intuitive Analogy)

Imagine a table where two candidate keys overlap, such as `(Student, Course)` and `(Student, Instructor)`. Because every attribute belongs to at least one candidate key, every attribute is a **prime attribute**. Now suppose each instructor only teaches one course ($\text{Instructor} \to \text{Course}$). Every time Professor Rahim advises a new student in Database Systems, we have to repeat the fact that Professor Rahim teaches Database Systems. Even though this table has obvious redundancy, it still passes 3NF because `Course` is a prime attribute!

Raymond F. Boyce and Edgar F. Codd introduced BCNF in 1974 to fix this exact loophole.

### The Core Rule of BCNF

In plain English, a relation is in BCNF if and only if:

$$
\text{Every determinant of a non-trivial FD is a superkey.}
$$

Whenever you see a non-trivial functional dependency $\alpha \to \beta$, ask one question: **Is the left-hand side $\alpha$ a superkey of $R$?**
- If **yes** for every non-trivial FD, the table is in BCNF.
- If **no** for even one non-trivial FD, the table violates BCNF. It does not matter whether the right-hand side $\beta$ is prime or non-prime.

```text
+-------------------------------------------------------------+
|                     BCNF Condition                          |
|                                                             |
|   For every non-trivial FD:  α → β                          |
|                                                             |
|   Condition: α MUST be a Superkey of R                      |
|                                                             |
|   (No prime-attribute escape clause permitted)              |
+-------------------------------------------------------------+
```

---

## 3NF vs. BCNF: The Core Theoretical Difference

The entire difference between 3NF and BCNF comes down to the third condition of 3NF.

### The 3NF "Escape Clause"

For any non-trivial dependency $\alpha \to \beta$, 3NF allows two ways to pass:
1. $\alpha$ is a superkey of $R$, **OR**
2. Each attribute $A \in (\beta - \alpha)$ is a **prime attribute** (part of some candidate key).

Why does 3NF include this second rule (often called the "escape clause")? Because without it, splitting a table with overlapping candidate keys can break a functional dependency across two separate tables. BCNF keeps rule 1 and throws out rule 2 completely, choosing zero redundancy over keeping all dependencies in one place.

| Feature | Third Normal Form (3NF) | Boyce-Codd Normal Form (BCNF) |
| :--- | :--- | :--- |
| **Strictness** | Less strict | Strictly stronger |
| **Condition on $\alpha \to \beta$** | $\alpha$ is superkey **OR** $\beta$ is prime | $\alpha$ MUST be a superkey |
| **Allows overlap anomalies?** | Yes, if overlapping candidate keys exist | No, all FD redundancy is eliminated |
| **Lossless-join decomposition** | Always achievable | Always achievable |
| **Dependency preservation** | Always guaranteed | Not always guaranteed |

### The Subset Relationship: Why Every BCNF Relation is in 3NF

Suppose a relation $R$ is in BCNF. That means for every non-trivial functional dependency $\alpha \to \beta$ in $F^+$:

$$
\alpha \text{ is a superkey of } R
$$

Notice that this is the exact first condition of 3NF! Since 3NF only requires condition 1 *or* condition 2 to hold, any table that passes BCNF automatically passes 3NF:

$$
\text{BCNF} \subset \text{3NF}
$$

In short, every BCNF relation is in 3NF, but a 3NF relation is not necessarily in BCNF (specifically when an FD uses the prime-attribute escape clause).

## Step-by-Step Procedure: Finding the Highest Normal Form

Follow this systematic 4-step checklist on any exam problem.

```text
Step 1: Check 1NF
        └── Are all attribute values atomic?
            ├── No  → Unnormalized (0NF)
            └── Yes → Relation is at least in 1NF. Proceed to Step 2.

Step 2: Check 2NF
        └── Find all Candidate Keys (CKs). Identify prime and non-prime attributes.
        └── Does any non-prime attribute depend on a proper subset of a CK?
            ├── Yes → Partial dependency exists. Highest NF is 1NF.
            └── No  → Relation satisfies 2NF. Proceed to Step 3.

Step 3: Check 3NF
        └── Does any non-prime attribute depend on another non-prime attribute?
            ├── Yes → Transitive dependency exists. Highest NF is 2NF.
            └── No  → Check every non-trivial FD α → β:
                      Is α a superkey OR is β - α composed of prime attributes?
                      ├── No  → Fails 3NF. Highest NF is 2NF.
                      └── Yes → Relation satisfies 3NF. Proceed to Step 4.

Step 4: Check BCNF
        └── For every non-trivial FD α → β:
            Is α a superkey of R?
            ├── Yes (for ALL FDs) → Highest NF is BCNF.
            └── No (at least one non-superkey α) → Highest NF is 3NF.
```

## Worked Mini-Example 1: A 3-Attribute Schema in 3NF but Not BCNF

Let's trace a quick 3-attribute example to see how overlapping candidate keys trigger the 3NF escape clause. *(Note: The 4-attribute Lecture Deck 06 Slide 40/43 counterexample $R(A, B, C, D)$ is solved in full in **GQ2** below.)*

Suppose we have a relation $R(X, Y, Z)$ with functional dependencies:

$$
F = \{XY \to Z, \; Z \to Y\}
$$

1. **Find Candidate Keys:**
   - $(XY)^+ = \{X, Y, Z\}$, so $XY$ is a candidate key.
   - Because $Z \to Y$, substituting $Z$ for $Y$ gives $(XZ)^+ = \{X, Z, Y\}$, so $XZ$ is also a candidate key.
   - **Prime attributes:** $\{X, Y, Z\}$ (every attribute belongs to a candidate key!).
2. **Check 3NF:**
   - $XY \to Z$ has superkey $XY$ on the left.
   - $Z \to Y$ does not have a superkey on the left ($Z^+ = \{Y, Z\}$), **but** the right-hand side $Y$ is a prime attribute (part of $XY$). So $R$ passes **3NF**.
3. **Check BCNF:**
   - In $Z \to Y$, the determinant $Z$ is not a superkey. Because BCNF has no escape clause for prime attributes, $R$ **violates BCNF**.

$$
\boxed{R(X, Y, Z) \text{ is in 3NF, but NOT in BCNF.}}
$$

## Worked Example 2: The University Advisor Scenario

This scenario corresponds to Lecture Deck 06 Slide 42 and Silberschatz 7e §7.3.1.2.

### Scenario

A university tracking student advisement uses the relation:

$$
R(\text{Student}, \text{Course}, \text{Instructor})
$$

Rules:
1. Each student in a course has exactly one instructor: $(\text{Student}, \text{Course}) \to \text{Instructor}$.
2. Each instructor teaches only one course: $\text{Instructor} \to \text{Course}$.

### Candidate Keys

Compute closures:
- $(\text{Student}, \text{Course})^+ = \{\text{Student}, \text{Course}, \text{Instructor}\} \implies \{\text{Student}, \text{Course}\}$ is a CK.
- $(\text{Student}, \text{Instructor})^+ = \{\text{Student}, \text{Instructor}, \text{Course}\} \implies \{\text{Student}, \text{Instructor}\}$ is a CK.

Prime attributes: $\{\text{Student}, \text{Course}, \text{Instructor}\}$. All attributes are prime.

### Normal Form Evaluation

1. **3NF Check:**
   - $(\text{Student}, \text{Course}) \to \text{Instructor}$: LHS is a superkey.
   - $\text{Instructor} \to \text{Course}$: LHS is not a superkey. But $\text{Course}$ is a prime attribute.
   - Therefore, $R$ is in **3NF**.

2. **BCNF Check:**
   - In $\text{Instructor} \to \text{Course}$, $\text{Instructor}$ is not a superkey.
   - Therefore, $R$ violates BCNF.

## BCNF Decomposition Algorithm

When a relation $R$ violates BCNF, we decompose it into smaller relations that satisfy BCNF.

### The Algorithm

```text
Input: Schema R, set of functional dependencies F
Output: A set of schemas {R1, R2, ..., Rk} in BCNF with a lossless join

Result := {R};
done := false;
compute F+;

while (not done) do
    if (there is a schema Ri in Result that is not in BCNF) then
    begin
        choose a non-trivial dependency α → β holding on Ri such that:
            1. α ∩ β = ∅
            2. α is not a superkey for Ri
            
        Result := (Result - {Ri}) ∪ {(α ∪ β), (Ri - (β - α))};
    end
    else
        done := true;
```

### Why BCNF Decomposition is Always Lossless

When we split $R$ using a violating dependency $\alpha \to \beta$ into:

$$
R_1 = \alpha \cup \beta \quad \text{and} \quad R_2 = R - (\beta - \alpha)
$$

 notice that both tables keep $\alpha$, while the dependent attributes $(\beta - \alpha)$ move exclusively into $R_1$. That means the overlap between the two tables is simply $\alpha$:

$$
R_1 \cap R_2 = (\alpha \cup \beta) \cap (R - (\beta - \alpha)) = \alpha
$$

Because $\alpha \to \beta$ holds, $\alpha$ determines all attributes of $R_1 = \alpha \cup \beta$:

$$
(R_1 \cap R_2) \to R_1
$$

In other words, $\alpha$ is the primary key of the new lookup table $R_1$ and acts as a foreign key in $R_2$. Joining them back on $\alpha$ is guaranteed to be lossless!

### The Trade-off: Loss of Dependency Preservation

While BCNF decomposition always gives you a **lossless join** and **zero FD redundancy**, it comes with a catch: **it can break functional dependencies across tables**.

Look at what happens when we split the university advisor schema $R(\text{Student}, \text{Course}, \text{Instructor})$ using the violating dependency $\text{Instructor} \to \text{Course}$:
- $R_1(\underline{\text{Instructor}}, \text{Course})$
- $R_2(\underline{\text{Student}, \text{Instructor}})$

Both $R_1$ and $R_2$ are now in BCNF. However, look at our first rule:

$$
(\text{Student}, \text{Course}) \to \text{Instructor}
$$

`Student` lives only in $R_2$, while `Course` lives only in $R_1$! Because neither table holds `Student`, `Course`, and `Instructor` together, the database cannot check whether a student has been assigned two instructors for the same course without running a `JOIN` ($R_1 \bowtie R_2$) on every insert. Because joins during inserts are slow, database designers sometimes prefer to keep a schema in 3NF when preserving every dependency locally is more important than removing the last bit of redundancy.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · CT-03 Q.01(d) · Highest Normal Form of Enrollment Relation

> **Appeared:** CT-03 Q.01(d) — (2 marks)

**Question:**

Consider $\text{ENROLLMENT}(\text{StudentID}, \text{StudentName}, \text{CourseID}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade})$ with functional dependencies: $\text{StudentID} \rightarrow \text{StudentName}$; $\text{CourseID} \rightarrow \text{CourseName}, \text{InstructorID}$; $\text{InstructorID} \rightarrow \text{InstructorName}$; $(\text{StudentID}, \text{CourseID}) \rightarrow \text{Grade}$.  
**(d)** Determine the highest normal form satisfied by the given relation. Give a proper justification.

**Full Answer:**

#### 1. First Normal Form (1NF) Check

All attribute values in $\text{ENROLLMENT}$ are single, indivisible data values. The relation contains no multi-valued attributes or repeating groups. Therefore, the relation satisfies **1NF**.

#### 2. Candidate Key and Attribute Classification

Compute attribute closure to find the candidate key:

$$
\begin{aligned}
(\text{StudentID}, \text{CourseID})^+ &= \{\text{StudentID}, \text{CourseID}\} \\
&\cup \{\text{StudentName}\} \quad (\text{by } \text{StudentID} \to \text{StudentName}) \\
&\cup \{\text{CourseName}, \text{InstructorID}\} \quad (\text{by } \text{CourseID} \to \text{CourseName}, \text{InstructorID}) \\
&\cup \{\text{InstructorName}\} \quad (\text{by } \text{InstructorID} \to \text{InstructorName}) \\
&\cup \{\text{Grade}\} \quad (\text{by } (\text{StudentID}, \text{CourseID}) \to \text{Grade}) \\
&= \{\text{StudentID}, \text{StudentName}, \text{CourseID}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade}\}
\end{aligned}
$$

Because $(\text{StudentID}, \text{CourseID})$ determines all attributes and no single attribute can do so, the composite candidate key is:

$$
\text{Candidate Key} = \{\text{StudentID}, \text{CourseID}\}
$$

- **Prime Attributes:** $\{\text{StudentID}, \text{CourseID}\}$
- **Non-prime Attributes:** $\{\text{StudentName}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade}\}$

#### 3. Second Normal Form (2NF) Check

A relation is in 2NF if it is in 1NF and no non-prime attribute depends on a proper subset of any candidate key.

Examine the given dependencies:
1. $\text{StudentID} \to \text{StudentName}$:
   $\text{StudentID}$ is a proper subset of candidate key $\{\text{StudentID}, \text{CourseID}\}$. The non-prime attribute $\text{StudentName}$ depends only on part of the key. This is a **partial functional dependency**.
2. $\text{CourseID} \to \text{CourseName}, \text{InstructorID}$:
   $\text{CourseID}$ is a proper subset of candidate key $\{\text{StudentID}, \text{CourseID}\}$. The non-prime attributes $\text{CourseName}$ and $\text{InstructorID}$ depend only on part of the key. This is also a **partial functional dependency**.

Because partial functional dependencies exist, the relation violates 2NF.

#### 4. Conclusion

$$
\boxed{\text{Highest Normal Form Satisfied: First Normal Form (1NF)}}
$$

### 🎯 GQ2 · CT-03 Q.04 · Justification of BCNF Subset of 3NF

> **Appeared:** CT-03 Q.04 — (4 marks)

**Question:**

Justify the statement: "Every BCNF relation is in 3NF, but every 3NF relation is not necessarily in BCNF."

**Full Answer:**

#### 1. Mathematical Definitions

- **Boyce-Codd Normal Form (BCNF):**  
  A relation schema $R$ is in BCNF with respect to a set $F$ of functional dependencies if, for every non-trivial functional dependency $\alpha \rightarrow \beta$ in $F^+$:
  
$$
\alpha \text{ is a superkey of } R
$$

- **Third Normal Form (3NF):**  
  A relation schema $R$ is in 3NF with respect to a set $F$ of functional dependencies if, for every non-trivial functional dependency $\alpha \rightarrow \beta$ in $F^+$, at least one of the following holds:
  1. $\alpha$ is a superkey of $R$, **OR**
  2. Each attribute $A \in (\beta - \alpha)$ is a **prime attribute** (contained in some candidate key of $R$).

#### 2. Why Every BCNF Relation is in 3NF

Suppose a relation $R$ is in BCNF. Then for every non-trivial functional dependency $\alpha \to \beta$, $\alpha$ is a superkey of $R$.

Because condition 1 of the 3NF definition is identical to the BCNF condition, every dependency that satisfies BCNF automatically satisfies condition 1 of 3NF. No dependency in $R$ violates 3NF.

Therefore, every relation in BCNF is necessarily in 3NF:

$$
\text{BCNF} \subset \text{3NF}
$$

#### 3. Why Every 3NF Relation is Not Necessarily in BCNF (Counterexample)

To prove that a 3NF relation is not necessarily in BCNF, consider the standard relation schema:

$$
R(A, B, C, D)
$$

with functional dependency set:

$$
F = \{AB \to CD, \; D \to A\}
$$

**Step A: Find Candidate Keys**
- $(AB)^+ = \{A, B, C, D\} \implies AB$ is a candidate key.
- $(BD)^+ = \{B, D\} \to \{B, D, A\} \to \{A, B, C, D\} \implies BD$ is a candidate key.
- Candidate keys of $R$: $\{AB, BD\}$.
- Prime attributes: $\{A, B, D\}$.
- Non-prime attribute: $\{C\}$.

**Step B: Evaluate 3NF**
- For $AB \to CD$: Left-hand side $AB$ is a candidate key, hence a superkey. Satisfies condition 1.
- For $D \to A$: Left-hand side $D$ is not a superkey. But attribute $A$ belongs to candidate key $AB$, making $A$ a prime attribute. Satisfies condition 2.
- Both dependencies satisfy 3NF. Therefore, relation $R$ is in **3NF**.

**Step C: Evaluate BCNF**
- For $D \to A$: The determinant $D$ is not a superkey of $R$.
- BCNF requires every determinant of a non-trivial dependency to be a superkey and does not permit the prime attribute exception.
- Therefore, dependency $D \to A$ violates BCNF.
- Relation $R$ is **NOT in BCNF**.

Because relation $R(A, B, C, D)$ is in 3NF but not in BCNF, the statement is fully justified.

## ⚡ Exam Tips & Common Mistakes

1. **State 1NF atomicity before concluding:** When asked for the highest normal form, always explicitly confirm that attribute values are atomic before demonstrating why higher normal forms fail.
2. **Memorize the standard counterexample:** The relation $R(A, B, C, D)$ with $F = \{AB \to CD, D \to A\}$ is the exact counterexample used in Lecture Deck 06 Slide 40 and Slide 43. Using this schema saves time in the examination hall.
3. **Remember prime attributes belong to ANY candidate key:** An attribute is prime if it belongs to at least one candidate key. It does not need to belong to all candidate keys.
4. **Identify why BCNF fails dependency preservation:** 3NF synthesis using canonical covers guarantees dependency preservation. BCNF decomposition cannot guarantee dependency preservation when overlapping candidate keys exist.
