# T05.5a: GROUP BY and HAVING Clauses

> **Topic:** T05 — SQL (DDL, DML, Aggregates, Subqueries) | **Priority:** 🟠 | **Exam Frequency:** 3/7 finals + CT-02 Q1(d) (24 marks total)
> **Sources:** Silberschatz 7e Ch. 3 (§3.7.2–3.7.3, pp. 92–96) · Lecture Deck 03 (Slides 32–34) · Classnote by Raidah (p. 15) · Handnote by Fahim (pp. 43–44)

## Why This Topic Matters

The `GROUP BY` clause groups relation tuples into summary subsets based on matching column values. The `HAVING` clause filters those generated groups using aggregate conditions. Together, they enable multi-level summary reporting and analytical filtering. In RUET exams, questions test query syntax rules, group filtering, and multi-table business reporting (2018 Q.7(b)). Understanding the boundary between `WHERE` and `HAVING` prevents frequent exam syntax errors.

---

## 📝 Key Definitions

> **Group By Clause:** "The attribute or attributes given in the group by clause are used to form groups. Tuples with the same value on all attributes in the group by clause are placed in one group." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.2 (p. 92)

> **Having Clause:** "Predicates in the having clause are applied after the formation of groups, so aggregate functions can be used in the having clause." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.3 (p. 95)

> **Single Group Fallback:** "If the group by clause is absent, the entire set of tuples satisfying the where predicate is treated as being in a single group." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §3.7.3 (p. 96)

---

## Mechanics of the GROUP BY Clause

When you run an aggregate function without `GROUP BY`, SQL treats the entire table as one big bucket and returns a single summary row. Adding a `GROUP BY` clause splits the table into separate smaller buckets (groups), where every row inside a bucket shares the exact same value on the grouping column(s). Then, the aggregate function runs independently on each bucket, producing one summary row per group.

![Tuples of the instructor relation, grouped by the dept_name attribute](diagrams/T05.05a_instructor_grouped_by_dept__Textbook_fig_03_13.jpg)
*Figure 3.13: Tuples of the instructor relation partitioned into groups by the dept_name attribute.*

### The Cardinal Rule of GROUP BY

Every `GROUP BY` query must obey one golden rule: **any column that appears in the `SELECT` list outside of an aggregate function must also be listed in the `GROUP BY` clause.**

To see why this rule exists, look at this broken query:

```sql
/* ILLEGAL QUERY in standard SQL and MySQL 8 with ONLY_FULL_GROUP_BY */
SELECT dept_name, ID, AVG(salary)
FROM instructor
GROUP BY dept_name;
```

**Why this fails:**
Suppose the `Comp. Sci.` bucket holds three instructors with three different IDs (`45565`, `10101`, and `83821`). Since `GROUP BY dept_name` collapses all three rows into a single summary row for `Comp. Sci.`, there is only room for one `ID` value next to the department's average salary. Because the database has no way to guess which of the three IDs you want to see, standard SQL rejects the query outright.

## Evaluation Order of a SQL Query

A SQL query executes in a strict logical pipeline that is quite different from the order in which you type the keywords:

| Step | Clause | Logical Operation | Row / Group Status |
| :---: | :--- | :--- | :--- |
| **1** | `FROM` | Identifies source tables and performs Cartesian products or joins | Individual tuples formed |
| **2** | `WHERE` | Evaluates row-level predicates and discards non-matching tuples | Non-matching tuples eliminated |
| **3** | `GROUP BY` | Splits remaining tuples into separate buckets by grouping columns | Group partitions formed |
| **4** | `HAVING` | Evaluates aggregate conditions and drops groups failing the test | Non-matching groups eliminated |
| **5** | `SELECT` | Computes aggregate values and projects the requested output columns | Final columns generated |
| **6** | `ORDER BY` | Sorts the resulting output rows in ascending (`ASC`) or descending (`DESC`) order | Sorted result set produced |

```sql
-- Example combining all clauses
SELECT dept_name, AVG(salary) AS avg_sal
FROM instructor
WHERE salary > 50000
GROUP BY dept_name
HAVING AVG(salary) > 70000
ORDER BY avg_sal DESC;
```

Here is how the database steps through this query from start to finish:
1. `FROM instructor`: Loads all rows from the `instructor` table.
2. `WHERE salary > 50000`: Filters out any individual instructor earning \$50,000 or less before any grouping happens.
3. `GROUP BY dept_name`: Gathers the remaining high-earning instructors into buckets by department.
4. `HAVING AVG(salary) > 70000`: Calculates each department's average salary (among those surviving instructors) and drops any department whose average is \$70,000 or less.
5. `SELECT dept_name, AVG(salary)`: Outputs the department name and average salary for the surviving groups.
6. `ORDER BY avg_sal DESC`: Sorts those final summary rows from highest average salary to lowest.

## Side-by-Side Comparison: WHERE vs. HAVING

Distinguishing `WHERE` from `HAVING` is one of the most common questions on RUET exams:

| Feature | `WHERE` Clause | `HAVING` Clause |
| :--- | :--- | :--- |
| **Filtering Target** | Individual tuples (rows) | Aggregated groups of tuples |
| **Execution Timing** | Before `GROUP BY` partitioning | After `GROUP BY` partitioning |
| **Aggregate Functions** | **Forbidden** (`WHERE SUM(qty) > 10` is an error) | **Allowed and expected** (`HAVING SUM(qty) > 10`) |
| **Operation on Raw Rows** | Discards rows before summary computation | Discards entire group summaries |
| **Can Exist Without GROUP BY?** | Yes, standard row filtering | Yes, treats the entire table as one single group |
| **Use with Column Aliases** | Column aliases from `SELECT` cannot be used | Column aliases often permitted in MySQL |

> [!TIP]
> A quick rule of thumb: if your condition checks a single row at a time (like `salary > 50000` or `status = 'ACTIVE'`), put it in `WHERE`. If your condition requires computing an aggregate over a whole group first (like `COUNT(*) > 5` or `AVG(salary) > 40000`), put it in `HAVING`.

---

## NULL Values in Grouping

In a normal `WHERE` comparison, `NULL = NULL` evaluates to `unknown` because two missing values are not guaranteed to be the same thing. However, `GROUP BY` treats `NULL` differently so that rows with missing category values do not get lost:

1. **Single Bucket Rule:**
   When grouping by a column, SQL puts all rows that have `NULL` in that column together into a single `NULL` group.
2. **Multiple Grouping Columns:**
   When grouping by two or more columns, two rows land in the same group if their non-null columns match and any `NULL`s appear in the exact same column positions.

## Worked Example: Inventory and Multi-Table Grouping

Consider an order database with `Product (p_id, p_name, unit_price)` and `Sales (c_id, p_id, quantity)`.
We need a query to list all products that generated total sales revenue exceeding \$1,000.

### Step-by-Step Construction

1. **Identify Required Tables:**
   `Product` holds `p_name` and `unit_price`. `Sales` holds `quantity`. We must join them on `p_id`.
2. **Form Groups:**
   We want one summary row per product. Thus, we group by `p.p_id, p.p_name`.
3. **Compute Revenue:**
   Total revenue per product equals the sum of quantity multiplied by unit price: `SUM(s.quantity * p.unit_price)`.
4. **Filter Groups:**
   Since the \$1,000 threshold applies to the aggregated total, we place the condition in `HAVING`.

```sql
SELECT p.p_id,
       p.p_name,
       SUM(s.quantity * p.unit_price) AS total_revenue
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name
HAVING SUM(s.quantity * p.unit_price) > 1000;
```

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.7(b) · E-Commerce Multi-Table Business Reporting

> **Appeared:** 2018 Q.7(b) — (08 Marks | Sec B)

**Question:**

Consider the following data tables:

`Product (p_id, p_name, quantity, unit_price)`  
`Customer (c_id, c_name, contact)`  
`Sales (c_id, p_id, quantity)`

Write down SQL expressions for following queries.  
(i) Show the information of those customers who have bought more than five different products.  
(ii) Show the information of those products that were sold more than ten pieces.  
(iii) Show the information of the product with maximum sale (maximum sold amount of money or bought by the maximum customer).  
(iv) Show the product id and corresponding remaining quantity of that product.

**Full Answer:**

#### (i) Customers who bought more than five different products

To count different products, we use `COUNT(DISTINCT s.p_id)` rather than `COUNT(s.p_id)`.
If a customer bought the same item multiple times, `COUNT(DISTINCT)` ensures it counts only once.

```sql
SELECT c.c_id, c.c_name, c.contact
FROM Customer c
JOIN Sales s ON c.c_id = s.c_id
GROUP BY c.c_id, c.c_name, c.contact
HAVING COUNT(DISTINCT s.p_id) > 5;
```

#### (ii) Products sold more than ten pieces

We join `Product` and `Sales`, group by product attributes, and filter using `SUM(s.quantity)` in the `HAVING` clause:

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
HAVING SUM(s.quantity) > 10;
```

#### (iii) Product with maximum sale

The question permits two interpretations for "maximum sale":

**Interpretation A: Maximum monetary revenue ($\sum (\text{quantity} \times \text{unit\_price})$)**

Using `ORDER BY ... DESC LIMIT 1`:

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price,
       SUM(s.quantity * p.unit_price) AS total_sales_value
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
ORDER BY total_sales_value DESC
LIMIT 1;
```

Alternative standard SQL query without `LIMIT` (preserves all tied top-selling products):

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
HAVING SUM(s.quantity * p.unit_price) = (
    SELECT MAX(prod_rev)
    FROM (
        SELECT SUM(s2.quantity * p2.unit_price) AS prod_rev
        FROM Sales s2
        JOIN Product p2 ON s2.p_id = p2.p_id
        GROUP BY s2.p_id
    ) AS sub
);
```

**Interpretation B: Bought by the maximum number of distinct customers**

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price,
       COUNT(DISTINCT s.c_id) AS customer_count
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
ORDER BY customer_count DESC
LIMIT 1;
```

#### (iv) Product ID and corresponding remaining quantity

**Critical Exam Point:**
If a product has never been sold, it has no rows in the `Sales` table.
An `INNER JOIN` would drop that unsold product completely.
We must use a `LEFT JOIN` and wrap the sales sum with `COALESCE(..., 0)` so unsold products evaluate to zero sold units:

$$
\text{Remaining Quantity} = \text{Initial Quantity} - \text{Total Sold}
$$

```sql
SELECT p.p_id,
       p.quantity - COALESCE(SUM(s.quantity), 0) AS remaining_quantity
FROM Product p
LEFT JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.quantity;
```

### 🎯 GQ2 · CT-02 Q.01(d) · Second-Highest CGPA Without LIMIT

> **Appeared:** CT-02 Q.01(d) — (03 Marks | CO2)

**Question:**

Given $\text{STUDENT}(\text{StudentID}, \text{Name}, \text{Department}, \text{Semester}, \text{CGPA})$, write SQL query:  
**(d)** Display the students having the second-highest CGPA without using LIMIT.

**Full Answer:**

#### 1. Core Logic Without LIMIT
The second-highest value in a set is the maximum value strictly less than the overall maximum value:

$$
\text{Second Highest} = \max \{ x \in \text{CGPA} \mid x < \max(\text{CGPA}) \}
$$

Once this dynamic scalar value is determined by a nested subquery, the outer query retrieves all student records matching that CGPA.

#### 2. SQL Query

```sql
SELECT *
FROM STUDENT
WHERE CGPA = (
    SELECT MAX(CGPA)
    FROM STUDENT
    WHERE CGPA < (
        SELECT MAX(CGPA)
        FROM STUDENT
    )
);
```

#### 3. Step-by-Step Evaluation Trace
Suppose the `STUDENT` table contains the following records:

| StudentID | Name | Department | Semester | CGPA |
| :--- | :--- | :--- | :--- | :--- |
| 2010001 | Alice | ECE | 4 | 4.00 |
| 2010002 | Bob | CSE | 4 | 4.00 |
| 2010003 | Carol | ECE | 4 | 3.85 |
| 2010004 | David | EEE | 4 | 3.85 |
| 2010005 | Emily | ECE | 4 | 3.60 |

1. **Innermost Subquery:**
   `SELECT MAX(CGPA) FROM STUDENT` evaluates to `4.00`.
2. **Intermediate Subquery:**
   `SELECT MAX(CGPA) FROM STUDENT WHERE CGPA < 4.00` evaluates to `3.85`.
3. **Outer Query:**
   `SELECT * FROM STUDENT WHERE CGPA = 3.85` retrieves all matching rows:
   - `(2010003, Carol, ECE, 4, 3.85)`
   - `(2010004, David, EEE, 4, 3.85)`

#### 4. Why `LIMIT 1 OFFSET 1` Fails
A query like `SELECT * FROM STUDENT ORDER BY CGPA DESC LIMIT 1 OFFSET 1` fails in two ways:
1. `LIMIT` is vendor-specific and explicitly forbidden by the exam prompt.
2. In the sample data above, both Alice and Bob have `4.00`. `LIMIT 1 OFFSET 1` returns Bob (who has `4.00`), failing to return the second-highest grade. The subquery method handles duplicate top grades correctly.

## ⚡ Exam Tips & Common Mistakes

1. **Never Put Aggregates in `WHERE`:** Writing `WHERE SUM(quantity) > 10` is an immediate syntax error. Group aggregates belong strictly in the `HAVING` clause.
2. **Select List Rule:** In any `GROUP BY` query, every column listed in `SELECT` that is not inside an aggregate function must appear in the `GROUP BY` clause.
3. **`COUNT(*)` vs. `COUNT(DISTINCT)` in `HAVING`:** When a question specifies "different products" or "distinct courses", always use `COUNT(DISTINCT column)`.
4. **Outer Joins for Inventory:** When calculating remaining stock or balances, always use `LEFT JOIN` and `COALESCE(SUM(...), 0)`. An inner join drops records that have zero transaction rows.
5. **Handling Ties in Extremes:** When asked for maximum, minimum, or $N$-th highest values without `LIMIT`, use scalar subqueries with `MAX` or `MIN`. This guarantees tie-safety.
