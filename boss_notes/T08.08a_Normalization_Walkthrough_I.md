# T08.8a: Table Normalization Walkthroughs I (2017 & 2024)

> **Topic:** T08 — Normalization & Functional Dependencies | **Priority:** 🟠 | **Exam Frequency:** 4/7 finals (27 marks total across T08.8)
> **Sources:** Silberschatz 7e Ch. 7 (§7.1, §7.3, §7.8) · Lecture Deck 06 (Slides 30–40) · Raidah Notes (p. 22–23)

## Why This Topic Matters

Table normalization problems carry some of the highest marks in RUET semester finals. For example, Question 3(b) in 2017 was worth 9 marks on its own, and 2024 Question 3(a) tested how to design and normalize a library table with partial dependencies. In these problems, examiners give you a populated business table and ask you to spot functional dependencies, remove anomalies, and split the table step by step from an unnormalized state (UNF) up to Third Normal Form (3NF). Once you know the standard 5-step recipe below, you can solve any table normalization problem smoothly and pick up full marks.

---

## 📝 Key Definitions

Before jumping into the formal textbook definitions, here is the simple intuition behind the first three normal forms:
- **1NF (No lists in a cell):** Every single cell in the table must hold just one value, never a comma-separated list or a group of repeating values.
- **2NF (Depend on the whole key):** If your primary key is made of multiple columns (like `Project_ID` + `Emp_ID`), every non-key column must depend on the *entire* pair together, not just on `Project_ID` alone or `Emp_ID` alone.
- **3NF (Depend on nothing but the key):** Non-key columns must depend directly on the key, not on some other non-key column (like `Emp_ID` $\to$ `Dept_No` $\to$ `Dept_Name`).

> **First Normal Form (1NF):** "A domain is **atomic** if elements of the domain are considered to be indivisible units. We say that a relation schema $R$ is in **first normal form** (1NF) if the domains of all attributes of $R$ are atomic."
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.8 (p. 342)

> **Second Normal Form (2NF):** "A functional dependency $\alpha \rightarrow \beta$ is called a partial dependency if there is a proper subset $\gamma$ of $\alpha$ such that $\gamma \rightarrow \beta$; we say that $\beta$ is partially dependent on $\alpha$. A relation schema $R$ is in **second normal form** (2NF) if each attribute $A$ in $R$ meets one of the following criteria:
> - It appears in a candidate key.
> - It is not partially dependent on a candidate key."
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.7 / Practice Exercise 7.19 (pp. 356–357)

> **Third Normal Form (3NF):** "A relation schema $R$ is in **third normal form** (3NF) with respect to a set $F$ of functional dependencies if, for all functional dependencies in $F^+$ of the form $\alpha \rightarrow \beta$, where $\alpha \subseteq R$ and $\beta \subseteq R$, at least one of the following holds:
> - $\alpha \rightarrow \beta$ is a trivial functional dependency.
> - $\alpha$ is a superkey for $R$.
> - Each attribute $A$ in $\beta - \alpha$ is contained in a candidate key for $R$."
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.3.2 (p. 317)

## The Universal Step-by-Step Normalization Recipe

Whenever you see an unnormalized table on an exam, follow these five steps in order:

```text
Step 0: Analyze Table & List FDs
        │
        ▼
Step 1: Convert to 1NF (Flatten multi-valued cells, define composite PK)
        │
        ▼
Step 2: Convert to 2NF (Isolate partial dependencies into dedicated tables)
        │
        ▼
Step 3: Convert to 3NF (Isolate transitive non-key dependencies)
        │
        ▼
Step 4: Verify Schema (Identify PKs, FKs, and lossless join property)
```

### Step 0: Analyze the Given Table and List All Functional Dependencies

1. Look closely at the rows to see which columns uniquely determine other columns.
2. Check whether each non-key column depends on the entire composite key or only on one part of it.
3. Check for calculated columns (such as $\text{Total} = \text{Rate} \times \text{Hours}$). You should drop derived columns because the database can compute them anytime on the fly.

### Step 1: Conversion to First Normal Form (1NF)

1. Spot any cells that hold comma-separated lists, multiple values, or merged rows.
2. Unpack those lists by creating a separate row for each single value so that every cell holds exactly one atomic value.
3. Write down the primary key for your new 1NF table. In almost every exam problem, this 1NF key is a composite key combining the main entity IDs and the unpacked multi-valued column.

### Step 2: Conversion to Second Normal Form (2NF)

1. Test every functional dependency against your composite 1NF primary key.
2. Whenever a non-key attribute depends on only part of the composite key, you have a **partial dependency**.
3. Pull each partial determinant and its dependent columns out into their own dedicated table, where that determinant becomes the primary key.
4. Keep the composite primary key and any columns that depend on the *entire* key together in an assignment or bridge table.

### Step 3: Conversion to Third Normal Form (3NF)

1. Check each of your 2NF tables for **transitive dependencies**, where a non-key attribute $A$ determines another non-key attribute $B$ ($A \rightarrow B$).
2. Pull $A$ and $B$ out into a new lookup table with $A$ as its primary key.
3. Remove $B$ from the original table, but leave $A$ behind as a foreign key pointing to the new lookup table.

### Step 4: Verification and Final Schema Summary

1. Underline the primary key in every final table schema.
2. State each foreign key and the parent table it references.
3. Confirm that your split is a lossless-join decomposition by checking that every link between tables connects through a primary key or superkey.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.3(b) · Normalizing `com_employee` Table up to 3NF

> **Appeared:** 2017 Q.3(b) — (09 Marks)

**Question:**

Consider the following data table com_employee. Is it already normalized? If not then normalize the table com_employee up to $3^{\text{rd}}$ normal form.

**com_employee**  
<table border="1" style="border-collapse: collapse;"><thead><tr><th>Pcode</th><th>Ptitle</th><th>EmpNo</th><th>EmName</th><th>EmCon</th><th>dNo</th><th>dName</th><th>HRate</th></tr></thead><tbody><tr><td>p1</td><td>Admission Test System</td><td>E1</td><td>Jones</td><td>501, 502</td><td>D1</td><td>IT</td><td>1000</td></tr><tr><td>p1</td><td>Admission Test System</td><td>E3</td><td>Smith</td><td>505</td><td>D2</td><td>Database</td><td>1100</td></tr><tr><td>p1</td><td>Admission Test System</td><td>E4</td><td>James</td><td>508, 509</td><td>D3</td><td>HR</td><td>800</td></tr><tr><td>p2</td><td>Salary System</td><td>E1</td><td>Jones</td><td>501, 502</td><td>D1</td><td>IT</td><td>900</td></tr><tr><td>p2</td><td>Salary System</td><td>E3</td><td>Smith</td><td>505</td><td>D2</td><td>Database</td><td>1000</td></tr></tbody></table>

**Full Answer:**

#### Part 1: Is the Table Already Normalized?

**No, the table is not normalized.**

First, the `EmCon` column holds comma-separated lists of phone numbers (`501, 502` and `508, 509`), which directly violates the single-value rule of **First Normal Form (1NF)**.

Second, the table mixes facts about projects, employees, departments, and project assignments all in one place. Because of this, the table suffers from both partial dependencies and transitive dependencies.

#### Part 2: Functional Dependencies in the Data

By looking at how the values repeat across rows, we can identify five key relationships:
1. $\text{Pcode} \rightarrow \text{Ptitle}$ (Each project code has a single project title.)
2. $\text{EmpNo} \rightarrow \text{EmName}, \text{dNo}$ (Each employee number identifies the employee's name and department code.)
3. $\text{dNo} \rightarrow \text{dName}$ (Each department code identifies the department name.)
4. $(\text{Pcode}, \text{EmpNo}) \rightarrow \text{HRate}$ (An employee can earn different hourly rates on different projects. For example, Jones earns 1000 on `p1`, but 900 on `p2`.)
5. $\text{EmCon}$ is a multi-valued phone number attribute belonging to each employee (`EmpNo`).

---

#### Step 1: 1NF Conversion for com_employee

To bring the table into 1NF, we unpack the comma-separated phone numbers in `EmCon` so that every phone number gets its own row:

| Pcode | Ptitle | EmpNo | EmName | EmCon | dNo | dName | HRate |
| :---: | :--- | :---: | :--- | :---: | :---: | :--- | :---: |
| p1 | Admission Test System | E1 | Jones | 501 | D1 | IT | 1000 |
| p1 | Admission Test System | E1 | Jones | 502 | D1 | IT | 1000 |
| p1 | Admission Test System | E3 | Smith | 505 | D2 | Database | 1100 |
| p1 | Admission Test System | E4 | James | 508 | D3 | HR | 800 |
| p1 | Admission Test System | E4 | James | 509 | D3 | HR | 800 |
| p2 | Salary System | E1 | Jones | 501 | D1 | IT | 900 |
| p2 | Salary System | E1 | Jones | 502 | D1 | IT | 900 |
| p2 | Salary System | E3 | Smith | 505 | D2 | Database | 1000 |

**Primary Key for 1NF:** `(Pcode, EmpNo, EmCon)`

---

#### Step 2: 2NF Decomposition for com_employee

In the 1NF table, several non-prime attributes depend on proper subsets of the composite primary key `(Pcode, EmpNo, EmCon)`:
- $\text{Pcode} \rightarrow \text{Ptitle}$ (Partial dependency on `Pcode` alone.)
- $\text{EmpNo} \rightarrow \text{EmName}, \text{dNo}, \text{dName}$ (Partial dependency on `EmpNo` alone.)
- $\text{EmpNo} \rightarrow \text{EmCon}$ (Contact numbers depend on `EmpNo` alone.)
- $(\text{Pcode}, \text{EmpNo}) \rightarrow \text{HRate}$ (Partial dependency with respect to `EmCon`.)

To eliminate partial dependencies, we decompose into four 2NF relations:

1. **PROJECT**

| Pcode | Ptitle |
| :---: | :--- |
| p1 | Admission Test System |
| p2 | Salary System |

Primary Key: `Pcode`.

2. **EMPLOYEE_2NF**

| EmpNo | EmName | dNo | dName |
| :---: | :--- | :---: | :--- |
| E1 | Jones | D1 | IT |
| E3 | Smith | D2 | Database |
| E4 | James | D3 | HR |

Primary Key: `EmpNo`.

3. **EMP_CONTACT**

| EmpNo | EmCon |
| :---: | :---: |
| E1 | 501 |
| E1 | 502 |
| E3 | 505 |
| E4 | 508 |
| E4 | 509 |

Primary Key: `(EmpNo, EmCon)`. Foreign Key: `EmpNo` references `EMPLOYEE_2NF(EmpNo)`.

4. **PROJECT_ASSIGNMENT**

| Pcode | EmpNo | HRate |
| :---: | :---: | :---: |
| p1 | E1 | 1000 |
| p1 | E3 | 1100 |
| p1 | E4 | 800 |
| p2 | E1 | 900 |
| p2 | E3 | 1000 |

Primary Key: `(Pcode, EmpNo)`. Foreign Keys: `Pcode` references `PROJECT(Pcode)`, `EmpNo` references `EMPLOYEE_2NF(EmpNo)`.

---

#### Step 3: 3NF Decomposition for com_employee

Next, let's check our four 2NF tables for any transitive dependencies:
- In `PROJECT`, `Pcode` is the only key and determines `Ptitle` directly, so there is no transitive dependency.
- In `EMP_CONTACT`, both columns are part of the primary key, so no transitive dependency is possible.
- In `PROJECT_ASSIGNMENT`, `HRate` depends directly on the full composite key `(Pcode, EmpNo)`, so it is already in 3NF.
- In `EMPLOYEE_2NF`, however, we have a chain of dependencies:

$$
\text{EmpNo} \rightarrow \text{dNo} \quad \text{and} \quad \text{dNo} \rightarrow \text{dName}
$$

Here, both `dNo` and `dName` are non-prime attributes. Because the non-prime column `dNo` determines another non-prime column `dName`, this is a transitive dependency that violates 3NF.

To fix it, we split `EMPLOYEE_2NF` into two tables:
1. `DEPARTMENT(dNo, dName)` with Primary Key: `dNo`.
2. `EMPLOYEE(EmpNo, EmName, dNo)` with Primary Key: `EmpNo` and Foreign Key: `dNo` referencing `DEPARTMENT(dNo)`.

---

#### Final 3NF Relations and Populated Data

1. **PROJECT**

| Pcode | Ptitle |
| :---: | :--- |
| p1 | Admission Test System |
| p2 | Salary System |

Primary Key: `Pcode`.

2. **DEPARTMENT**

| dNo | dName |
| :---: | :--- |
| D1 | IT |
| D2 | Database |
| D3 | HR |

Primary Key: `dNo`.

3. **EMPLOYEE**

| EmpNo | EmName | dNo |
| :---: | :--- | :---: |
| E1 | Jones | D1 |
| E3 | Smith | D2 |
| E4 | James | D3 |

Primary Key: `EmpNo`.  
Foreign Key: `dNo` references `DEPARTMENT(dNo)`.

4. **EMP_CONTACT**

| EmpNo | EmCon |
| :---: | :---: |
| E1 | 501 |
| E1 | 502 |
| E3 | 505 |
| E4 | 508 |
| E4 | 509 |

Primary Key: `(EmpNo, EmCon)`.  
Foreign Key: `EmpNo` references `EMPLOYEE(EmpNo)`.

5. **PROJECT_ASSIGNMENT**

| Pcode | EmpNo | HRate |
| :---: | :---: | :---: |
| p1 | E1 | 1000 |
| p1 | E3 | 1100 |
| p1 | E4 | 800 |
| p2 | E1 | 900 |
| p2 | E3 | 1000 |

Primary Key: `(Pcode, EmpNo)`.  
Foreign Keys: `Pcode` references `PROJECT(Pcode)`, `EmpNo` references `EMPLOYEE(EmpNo)`.

This schema satisfies 3NF, preserves all functional dependencies, and provides a lossless join.

### 🎯 GQ2 · 2024 Q.3(a) · Designing and Normalizing a Library Table

> **Appeared:** 2024 Q.3(a) — (04 Marks)

**Question:**

A library database stores information about Books, Authors, Publishers and Borrowers. Create a table that contains some data redundancy and partial dependencies. Also, show the procedure to normalize the table.

**Full Answer:**

#### 1. Designing the Unnormalized / 1NF Table

Let's design a single combined table named `LIBRARY_LOAN` that stores book loans alongside book, author, publisher, and borrower details.

**Initial Relation Schema:**
$$
\text{LIBRARY\_LOAN}(\underline{\text{Book\_ID}, \text{Borrower\_ID}}, \text{Title}, \text{Author\_ID}, \text{Author\_Name}, \text{Publisher\_Name}, \text{Borrower\_Name}, \text{Borrow\_Date})
$$

**Sample Populated Table:**

| Book_ID | Borrower_ID | Title | Author_ID | Author_Name | Publisher_Name | Borrower_Name | Borrow_Date |
| :---: | :---: | :--- | :---: | :--- | :--- | :--- | :---: |
| B101 | U01 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Akib | 2024-01-10 |
| B101 | U02 | DBMS Concepts | A1 | Silberschatz | McGraw-Hill | Shuvo | 2024-02-15 |
| B202 | U01 | Operating Systems | A1 | Silberschatz | Wiley | Akib | 2024-03-01 |

**Primary Key:** `(Book_ID, Borrower_ID)`

**Observed Functional Dependencies:**
1. $\text{Book\_ID} \rightarrow \text{Title}, \text{Author\_ID}, \text{Publisher\_Name}$ (Partial dependency on `Book_ID` alone.)
2. $\text{Author\_ID} \rightarrow \text{Author\_Name}$ (Transitive dependency through `Author_ID`.)
3. $\text{Borrower\_ID} \rightarrow \text{Borrower\_Name}$ (Partial dependency on `Borrower_ID` alone.)
4. $(\text{Book\_ID}, \text{Borrower\_ID}) \rightarrow \text{Borrow\_Date}$ (Full dependency on the composite key.)

**Why This Table Has Redundancy:**
- The book title (`DBMS Concepts`), author details (`A1`, `Silberschatz`), and publisher (`McGraw-Hill`) are repeated every time a new borrower checks out book `B101`.
- The borrower name (`Akib`) is repeated every time user `U01` borrows another book.

---

#### 2. Procedure to Normalize the Table

##### Step 1: Eliminate Partial Dependencies (Convert to 2NF)

To reach 2NF, we split out the columns that depend on only one part of the composite key `(Book_ID, Borrower_ID)`:

1. Move the book-specific attributes into `BOOK_INFO`:
   $$\text{BOOK\_INFO}(\underline{\text{Book\_ID}}, \text{Title}, \text{Author\_ID}, \text{Author\_Name}, \text{Publisher\_Name})$$
   Primary Key: `Book_ID`.
2. Move the borrower-specific attributes into `BORROWER`:
   $$\text{BORROWER}(\underline{\text{Borrower\_ID}}, \text{Borrower\_Name})$$
   Primary Key: `Borrower_ID`.
3. Keep the loan transaction details in `LOAN`:
   $$\text{LOAN}(\underline{\text{Book\_ID}, \text{Borrower\_ID}}, \text{Borrow\_Date})$$
   Primary Key: `(Book_ID, Borrower_ID)`.

Now every non-prime attribute depends on the whole primary key of its table, so the schema is in 2NF.

##### Step 2: Eliminate Transitive Dependencies (Convert to 3NF)

Looking at `BOOK_INFO`, the non-prime column `Author_ID` determines another non-prime column `Author_Name`:

$$
\text{Book\_ID} \rightarrow \text{Author\_ID} \quad \text{and} \quad \text{Author\_ID} \rightarrow \text{Author\_Name}
$$

Because `Author_ID` is not a superkey of `BOOK_INFO`, this transitive dependency violates 3NF.

We fix this by splitting `BOOK_INFO` into two tables:
1. `BOOK(Book_ID, Title, Author_ID, Publisher_Name)` with Primary Key: `Book_ID` and Foreign Key: `Author_ID` referencing `AUTHOR(Author_ID)`.
2. `AUTHOR(Author_ID, Author_Name)` with Primary Key: `Author_ID`.

---

#### Final Normalized 3NF Schema

1. **BOOK** ($\underline{\text{Book\_ID}}$, $\text{Title}$, $\text{Author\_ID}$, $\text{Publisher\_Name}$)  
   Primary Key: `Book_ID`  
   Foreign Key: `Author_ID` references `AUTHOR(Author_ID)`
2. **AUTHOR** ($\underline{\text{Author\_ID}}$, $\text{Author\_Name}$)  
   Primary Key: `Author_ID`
3. **BORROWER** ($\underline{\text{Borrower\_ID}}$, $\text{Borrower\_Name}$)  
   Primary Key: `Borrower_ID`
4. **LOAN** ($\underline{\text{Book\_ID}, \text{Borrower\_ID}}$, $\text{Borrow\_Date}$)  
   Primary Key: `(Book_ID, Borrower_ID)`  
   Foreign Keys: `Book_ID` references `BOOK(Book_ID)`, `Borrower_ID` references `BORROWER(Borrower_ID)`

This final schema completely eliminates partial and transitive dependencies while preserving all facts without redundancy.

## ⚡ Exam Tips & Common Mistakes

1. **Watch Hourly Rates and Assignment Attributes:** In `com_employee` (2017 Q.3b), Jones has `HRate = 1000` on project `p1`, but `HRate = 900` on project `p2`. Because his hourly rate changes from project to project, never put `HRate` in the `EMPLOYEE` table. It depends on both `Pcode` and `EmpNo` together.
2. **Never Leave Multi-Valued Attributes in 2NF Tables:** In `com_employee`, `EmCon` holds employee phone numbers. You must pull it out into its own table `EMP_CONTACT(EmpNo, EmCon)` during 2NF so that multiple phone numbers do not duplicate the employee's name and department in `EMPLOYEE`.
3. **Keep Designed Tables Small and Concrete:** For open-ended design questions like 2024 Q.3(a), create a small 3-row, 8-column table with realistic book titles, author IDs, and borrower names so the grader can immediately see the repeated values.
4. **State Functional Dependencies Before Drawing Tables:** Always list the functional dependencies before splitting the tables. This shows the examiner *why* you are making each split.
