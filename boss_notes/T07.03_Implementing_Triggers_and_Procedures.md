# T07.3: Implementing Triggers and Stored Procedures

> **Topic:** T07 — Triggers and Stored Procedures | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (10 marks)  
> **Sources:** Silberschatz 7e Ch. 5 (§5.2–5.3) · Fahim Handnote (p. 59, 60) · (No lecture slides for Unit 4 advanced SQL)

## Why This Topic Matters

In recent RUET finals, examiners have moved beyond simple definitions to test whether you can write practical SQL routines that coordinate multi-table workflows. Both 2023 Q.6(b) (6 marks) and 2024 Q.6(b) (4 marks) asked students to write stored procedures and triggers that check stock, log updates into an audit table, and handle outbound email notifications. Knowing how to combine `START TRANSACTION`, row locking with `FOR UPDATE`, `SIGNAL` error handling, and queue tables makes these 4-to-6-mark implementation questions easy to score.

---

## 📝 Key Definitions

> **Stored Procedure:** A stored procedure is a named program of SQL statements saved inside the database. Applications run it explicitly using `CALL proc_name(...)` and can pass `IN`, `OUT`, or `INOUT` parameters. It bundles multi-step business workflows and transaction checks into a single database call.

> **Stored Procedure vs Trigger:** A stored procedure takes parameters and runs only when called explicitly with `CALL`. A trigger takes no parameters and fires automatically whenever an `INSERT`, `UPDATE`, or `DELETE` modifies its target table.

> **Pessimistic Concurrency Control (`FOR UPDATE`):** `FOR UPDATE` is a locking clause added to a `SELECT` query inside a transaction. It places an exclusive lock on the selected rows until the transaction commits or rolls back. This stops concurrent transactions from modifying the same stock or balance rows at once.

> **Out-of-Process Task Queue (Asynchronous Decoupling):** A database trigger cannot safely perform external actions like sending emails over a network. Instead, the trigger inserts a job row into a queue table such as `email_queue`. A separate background worker reads that queue table after commit and sends the actual email.

---

## Architectural Comparison: Stored Procedures vs Triggers

How do you decide whether logic belongs in a stored procedure or a trigger? Think of a **stored procedure** as a function you call on purpose to run a multi-step workflow, and a **trigger** as a watchdog that reacts automatically whenever a table changes:

| Dimension | Stored Procedure | Database Trigger |
| :--- | :--- | :--- |
| **Invocation** | Explicitly called by the application (`CALL proc()`) | Fired automatically by the DBMS on table events |
| **Parameters** | Accepts `IN`, `OUT`, and `INOUT` parameters | Takes no parameters (reads row data via `OLD` and `NEW`) |
| **Transaction Control** | Can start, `COMMIT`, or `ROLLBACK` transactions | Runs inside the existing transaction of the triggering DML |
| **Return Data** | Can return result tables or `OUT` parameter values | Cannot return query result sets to the caller |
| **Primary Role** | Running multi-step business workflows (orders, transfers) | Enforcing integrity rules, audit logging, and syncing tables |
| **Scheduling** | Runs on demand when called by a user or scheduled job | Runs automatically on `INSERT`, `UPDATE`, or `DELETE` |

## Implementing Stored Procedures for Business Workflows

When an exam asks you to write a stored procedure that checks availability (like account balance, available seats, or item stock) before updating tables, follow three practical habits:

1. **Prefix Parameters and Local Variables:** Use `p_` for parameters (like `p_book_id`) and `v_` for local variables declared with `DECLARE` (like `v_available`). That way, MySQL never confuses your variable names with table column names.
2. **Lock the Checked Row with `FOR UPDATE`:**  
   Why can't we just run a plain `SELECT available_copies INTO v_available FROM Books WHERE book_id = p_book_id;`? Imagine only `1` copy of a book is left, and two students click "Borrow" at the exact same millisecond. With a plain `SELECT`, both transactions read `v_available = 1`, both pass the `IF` check, and both subtract `1`, leaving `available_copies = -1`!  
   Adding `FOR UPDATE` at the end of the `SELECT` locks that row immediately. The second transaction has to wait in line until the first transaction finishes and commits, so it sees `0` copies left and cleanly rejects the second request.
3. **Wrap Multi-Table Writes in a Transaction:**  
   Start with `START TRANSACTION;`. If your `IF` check fails, run `ROLLBACK;` to release the lock and throw a clear error using `SIGNAL SQLSTATE '45000'`. If everything succeeds, finish with `COMMIT;`.

### Illustrative Example: Library Book Checkout Procedure

Here is how those three rules fit together in a compact stored procedure `BorrowBook` that checks if a library book is in stock before recording a loan:

```sql
DELIMITER //

CREATE PROCEDURE BorrowBook (
    IN p_book_id INT,
    IN p_student_id INT
)
BEGIN
    DECLARE v_copies INT;

    START TRANSACTION;

    -- Lock the book row so two students cannot grab the last copy at once
    SELECT available_copies INTO v_copies
    FROM Books
    WHERE book_id = p_book_id
    FOR UPDATE;

    IF v_copies IS NULL THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Book ID does not exist.';
    ELSEIF v_copies < 1 THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: No copies currently available.';
    ELSE
        INSERT INTO Loans (book_id, student_id, loan_date)
        VALUES (p_book_id, p_student_id, NOW());

        UPDATE Books
        SET available_copies = available_copies - 1
        WHERE book_id = p_book_id;

        COMMIT;
    END IF;
END //

DELIMITER ;
```

## Implementing Automated Audit and Sync Triggers

While stored procedures handle explicit user actions, triggers make sure secondary tables stay in sync no matter how a table is updated.

### 1. Why Sync and Audit Triggers Use `AFTER` Timing

When a trigger updates another table or writes an audit log, always use `AFTER INSERT` or `AFTER UPDATE` rather than `BEFORE`. Why? Because if an `INSERT` or `UPDATE` later fails a foreign key or `NOT NULL` check on the table itself, you do not want your trigger to have wasted work beforehand. With `AFTER`, the trigger runs only after the row change on the main table has succeeded, and both actions still commit or roll back together as a single atomic transaction.

### 2. Attaching Audit Triggers to the Right Table

Suppose you want to log every change to available book copies in a `BookAudit` table. Should you attach your trigger to `Loans` (`AFTER INSERT ON Loans`) or to `Books` (`AFTER UPDATE ON Books`)?  
Always attach an audit trigger directly to the table holding the value being tracked (`Books`), and check `IF OLD.available_copies <> NEW.available_copies`. That way, whether copies change because of a student loan, a returned book, or a librarian adding new copies, every change is captured automatically:

```sql
DELIMITER //

CREATE TRIGGER trg_audit_book_copies
AFTER UPDATE ON Books
FOR EACH ROW
BEGIN
    IF OLD.available_copies <> NEW.available_copies THEN
        INSERT INTO BookAudit (book_id, old_copies, new_copies, changed_at)
        VALUES (OLD.book_id, OLD.available_copies, NEW.available_copies, NOW());
    END IF;
END //

DELIMITER ;
```

## Architectural Reality: Sending External Notifications (Emails)

Exam questions like 2024 Q.6(b) often ask: *"Implement a trigger that handles updating stock and sending email."*

Here is the key architectural insight that examiners love to see: **a relational database engine manages disk pages and transactions, not external network sockets or SMTP mail servers.** As Silberschatz notes in §5.3.1 (p. 206), triggers cannot safely perform actions outside the database directly.

```text
[ Client Order Insert ]
          │
          ▼
┌────────────────────────────────────────────────────────┐
│ DATABASE ENGINE (Transactional Boundary)               │
│                                                        │
│  AFTER INSERT TRIGGER Fires:                           │
│  1. UPDATE products SET stock = stock - NEW.qty;       │
│  2. INSERT INTO email_queue (recipient, body, ...);    │
└────────────────────────────────────────────────────────┘
          │
          ▼ (Commit Successful)
┌────────────────────────────────────────────────────────┐
│ EXTERNAL APPLICATION SERVICE (Asynchronous Worker)     │
│                                                        │
│  1. Daemon polls email_queue periodically              │
│  2. Connects to SMTP Server / Network Gateway          │
│  3. Dispatches physical email over the Internet        │
└────────────────────────────────────────────────────────┘
```

### Why Triggers Should Never Call an SMTP Server Directly

1. **Row Locks Would Freeze the Database:** Sending an email over the network takes hundreds of milliseconds (or several seconds if the mail server is slow). Because a trigger runs *inside* the active transaction, every row lock held by that transaction would stay locked the entire time the database waits for the mail server.
2. **You Cannot Roll Back a Sent Email:** What if the trigger sends the confirmation email over SMTP, and two milliseconds later the transaction aborts and rolls back? The customer gets an "Order Confirmed!" email for an order that was never saved in the database.
3. **Security Risks:** Giving the database server direct access to external network sockets or shell scripts opens dangerous attack surfaces.

### The Outbox / Queue Table Pattern

Instead of calling an imaginary `SEND_EMAIL()` function, your trigger simply inserts a row into an `email_queue` (or `notifications`) table inside the same transaction. Once the transaction commits, a separate background worker process reads new rows from `email_queue` and sends the actual emails over SMTP. If the transaction rolls back, the `email_queue` insert rolls back with it, so no false emails are ever sent.

## Worked Example: Tracing the Library Checkout & Audit Flow

Let's trace what happens step by step when a student borrows a book using our `BorrowBook` procedure and `trg_audit_book_copies` trigger:

1. **Starting State:** `Books` has `(book_id: 42, title: 'Database System Concepts', available_copies: 3)`.
2. **Procedure Call:** The library app runs `CALL BorrowBook(42, 2310035);`.
3. **Lock and Validate:** `BorrowBook` starts a transaction and runs `SELECT available_copies INTO v_copies ... FOR UPDATE;`, locking row `42` and reading `v_copies = 3`. Since `3 >= 1`, the check passes.
4. **Insert and Update:** The procedure inserts a loan row `(42, 2310035, NOW())` into `Loans`, then updates `Books.available_copies` from `3` to `2`.
5. **Automatic Trigger Fire:** That `UPDATE` on `Books` immediately wakes up `trg_audit_book_copies`. Because `OLD.available_copies (3) <> NEW.available_copies (2)`, the trigger inserts `(42, 3, 2, NOW())` into `BookAudit`.
6. **Commit:** `BorrowBook` executes `COMMIT;`, saving the loan, the updated copy count (`2`), and the audit log entry together while releasing the row lock on `book_id = 42`.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.6(b) · Stored Procedure for Order Placement and Audit Log Trigger

> **Appeared:** 2023 Q.6(b) — (6 marks)

**Question:**

Considering the tables (Products, Orders, and Auditlog) answer (i) and (ii).  
(i) Create a stored procedure to place an order consider stock availability, updates the stock.  
(ii) Create a trigger to log every stock update in the Auditlog table automatically.

**Full Answer:**

#### Schema Definitions

Assume the following relational schemas:
- `Products (product_id, name, stock, price)`
- `Orders (order_id, product_id, quantity, order_date)`
- `Auditlog (log_id, product_id, old_stock, new_stock, changed_at)`

#### (i) Stored Procedure to Place an Order

The stored procedure checks stock availability using row-level locking (`FOR UPDATE`), places the order, and updates stock within a transaction:

```sql
DELIMITER //

CREATE PROCEDURE PlaceOrder (
    IN p_product_id INT,
    IN p_quantity INT
)
BEGIN
    DECLARE v_stock INT;

    START TRANSACTION;

    -- Lock product row to avoid race conditions during concurrent orders
    SELECT stock INTO v_stock
    FROM Products
    WHERE product_id = p_product_id
    FOR UPDATE;

    -- Validate product existence and available stock
    IF v_stock IS NULL THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Product ID does not exist.';
    ELSEIF v_stock < p_quantity THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Insufficient stock available.';
    ELSE
        -- Insert the customer order record
        INSERT INTO Orders (product_id, quantity, order_date)
        VALUES (p_product_id, p_quantity, NOW());

        -- Deduct ordered quantity from inventory
        UPDATE Products
        SET stock = stock - p_quantity
        WHERE product_id = p_product_id;

        COMMIT;
    END IF;
END //

DELIMITER ;
```

#### (ii) Trigger to Automatically Log Stock Updates

An `AFTER UPDATE` trigger on `Products` detects when the `stock` attribute changes and records an entry into `Auditlog`:

```sql
DELIMITER //

CREATE TRIGGER trg_log_stock_update
AFTER UPDATE ON Products
FOR EACH ROW
BEGIN
    -- Log only when the stock value is actually modified
    IF OLD.stock <> NEW.stock THEN
        INSERT INTO Auditlog (
            product_id,
            old_stock,
            new_stock,
            changed_at
        ) VALUES (
            OLD.product_id,
            OLD.stock,
            NEW.stock,
            NOW()
        );
    END IF;
END //

DELIMITER ;
```

### 🎯 GQ2 · 2024 Q.6(b) · Trigger for Stock Update and Email Dispatch

> **Appeared:** 2024 Q.6(b) — (4 marks)

**Question:**

An e-commerce system wants to automate actions when a new order is inserted such as updating stock and sending email. Implement a database trigger that handles this workflow.

**Full Answer:**

#### Architectural Note

A relational database engine operates within transaction boundaries and cannot open network sockets to send SMTP emails directly. Doing so would cause serious blocking delays and rollback inconsistencies. The standard architecture has the trigger update stock and write an email job into an `email_queue` table. An external mailer daemon polls the queue and dispatches the email.

#### Relational Schemas

Assume the following schemas:
- `products (product_id, name, stock)`
- `orders (order_id, product_id, quantity, customer_email, order_date)`
- `email_queue (queue_id, recipient, subject, body, queued_at)`

#### Trigger Implementation

```sql
DELIMITER //

CREATE TRIGGER trg_after_order_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    -- 1. Deduct ordered quantity from inventory
    UPDATE products
    SET stock = stock - NEW.quantity
    WHERE product_id = NEW.product_id;

    -- 2. Enqueue outbound email notification for background delivery
    INSERT INTO email_queue (recipient, subject, body, queued_at)
    VALUES (
        NEW.customer_email,
        'Order Confirmation',
        CONCAT(
            'Dear Customer, your order #', NEW.order_id,
            ' for product #', NEW.product_id,
            ' (Quantity: ', NEW.quantity, ') has been received successfully.'
        ),
        NOW()
    );
END //

DELIMITER ;
```

This ensures inventory updates execute immediately while email dispatching is safely handled without blocking the database engine.

### 🎯 HYE-01 · Practice Exercise 5.7 · Bank Overdraft Protection Trigger

> **Source:** Silberschatz 7e · Chapter 5 (Practice Exercise 5.7)  
> **Exam Relevance:** High-Probability Enterprise Financial Trigger Drill  
> **Key Tested Concept:** Autonomous balance reconciliation across checking and savings accounts using `BEFORE UPDATE`.

**Problem Statement:**
> A bank provides overdraft protection for checking accounts linked to savings accounts:
> - `account(account_number, customer_id, account_type, balance)` where `account_type` is either `'checking'` or `'savings'`.
> - If a withdrawal on a checking account causes its balance to become negative, the required deficit is automatically transferred from the customer's savings account.
> - If the combined balance of checking and savings is insufficient to cover the withdrawal, the transaction is rejected.
> Write an SQL trigger to implement this overdraft protection policy.

**Model Exam-Style Solution:**

```sql
DELIMITER $$

CREATE TRIGGER overdraft_protection
BEFORE UPDATE ON account
FOR EACH ROW
BEGIN
    DECLARE deficit NUMERIC(12, 2);
    DECLARE savings_bal NUMERIC(12, 2);
    DECLARE savings_acc VARCHAR(10);

    -- Check if this is a checking account and the new balance drops below zero
    IF NEW.account_type = 'checking' AND NEW.balance < 0 THEN
        SET deficit = -NEW.balance;

        -- Find the customer's linked savings account
        SELECT account_number, balance INTO savings_acc, savings_bal
        FROM account
        WHERE customer_id = NEW.customer_id
          AND account_type = 'savings'
        LIMIT 1;

        -- Verify if savings account has sufficient funds
        IF savings_bal >= deficit THEN
            -- Deduct deficit from savings account
            UPDATE account
            SET balance = balance - deficit
            WHERE account_number = savings_acc;

            -- Restore checking account balance to zero
            SET NEW.balance = 0.00;
        ELSE
            -- Insufficient total funds: Abort withdrawal
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT = 'Transaction Declined: Insufficient funds in checking and linked savings!';
        END IF;
    END IF;
END$$

DELIMITER ;
```

**Step-by-Step Logic:**
1. Evaluates whether the proposed update leaves `NEW.balance < 0`.
2. Computes the required shortfall (`deficit = -NEW.balance`).
3. Queries the customer's linked savings account balance.
4. If savings cover the deficit, updates the savings account and resets `NEW.balance = 0.00`.
5. If funds are insufficient, triggers `SIGNAL SQLSTATE '45000'`, preventing the invalid withdrawal. $\blacksquare$

**💡 RUET Exam Takeaway:**
Modifying `NEW.column` directly is only possible in **`BEFORE` triggers**! In an `AFTER` trigger, the row is already written, making `NEW.balance = 0` illegal.

### 🎯 HYE-02 · Exercise 5.18 · Stored Procedure for Student Course Registration

> **Source:** Silberschatz 7e · Chapter 5 (Exercise 5.18)  
> **Exam Relevance:** Prime Overdue Stored Procedure Question (RUET Syllabus Unit 4)  
> **Key Tested Concept:** Modular business logic encapsulating prerequisite validation, seating capacity limits, transaction atomicity, and status return codes.

**Problem Statement:**
> Write an SQL stored procedure `RegisterStudent` with parameters:
> - `p_student_id VARCHAR(5)`
> - `p_course_id VARCHAR(8)`
> - `p_sec_id VARCHAR(8)`
> - `p_semester VARCHAR(6)`
> - `p_year NUMERIC(4, 0)`
> - `OUT p_status_code INT` (0 = Success, 1 = Prereq Missing, 2 = Section Full)
> The procedure must:
> 1. Verify that the student has completed all required prerequisites for the course.
> 2. Verify that the section has available seating capacity.
> 3. If both pass, insert the registration tuple into `takes` and return `p_status_code = 0`.

**Model Exam-Style Solution:**

```sql
DELIMITER $$

CREATE PROCEDURE RegisterStudent (
    IN p_student_id VARCHAR(5),
    IN p_course_id  VARCHAR(8),
    IN p_sec_id     VARCHAR(8),
    IN p_semester   VARCHAR(6),
    IN p_year       NUMERIC(4, 0),
    OUT p_status_code INT
)
BEGIN
    DECLARE missing_prereq_count INT;
    DECLARE current_enrollment INT;
    DECLARE max_capacity INT;

    -- Step 1: Check Prerequisites
    -- Count prerequisites of course_id that student has NOT passed with a grade other than 'F'
    SELECT COUNT(*) INTO missing_prereq_count
    FROM prereq p
    WHERE p.course_id = p_course_id
      AND p.prereq_id NOT IN (
          SELECT t.course_id
          FROM takes t
          WHERE t.ID = p_student_id
            AND t.grade IS NOT NULL
            AND t.grade <> 'F'
      );

    IF missing_prereq_count > 0 THEN
        SET p_status_code = 1; -- Prerequisite Missing
    ELSE
        -- Step 2: Check Seating Capacity
        SELECT COUNT(*) INTO current_enrollment
        FROM takes
        WHERE course_id = p_course_id
          AND sec_id = p_sec_id
          AND semester = p_semester
          AND year = p_year;

        SELECT c.capacity INTO max_capacity
        FROM section s
        JOIN classroom c ON s.building = c.building AND s.room_number = c.room_number
        WHERE s.course_id = p_course_id
          AND s.sec_id = p_sec_id
          AND s.semester = p_semester
          AND s.year = p_year;

        IF current_enrollment >= max_capacity THEN
            SET p_status_code = 2; -- Section Full
        ELSE
            -- Step 3: Register Student
            INSERT INTO takes (ID, course_id, sec_id, semester, year, grade)
            VALUES (p_student_id, p_course_id, p_sec_id, p_semester, p_year, NULL);

            SET p_status_code = 0; -- Success
        END IF;
    END IF;
END$$

DELIMITER ;
```

**💡 RUET Exam Takeaway:**
Stored procedures use **`IN`** and **`OUT`** parameters and execute complex multi-step procedural logic containing control-flow (`IF ... ELSE`), which is impossible inside a single standard SQL query.

## ⚡ Exam Tips & Common Mistakes

1. **The Missing FOR UPDATE Trap:** Forgetting `FOR UPDATE` when checking inventory in stored procedures leads to race conditions. Under concurrent requests, two users can buy the same last item.
2. **The Direct Email Trap:** Never write imaginary SQL functions like `SEND_EMAIL()` without explanation. State that triggers cannot send external emails directly, and explain the message queue pattern (`email_queue`).
3. **Stating Explicit Schemas:** When an exam question omits table column definitions, explicitly write a one-line schema assumption. This proves your solution is syntactically coherent.
4. **Trigger Placement for Auditing:** Attach inventory audit triggers to `Products`, not `Orders`. Stock levels can change through restocking or manual adjustments, not just through sales.
5. **Prefixing Variables:** Always prefix parameter names with `p_` and local variables with `v_`. This prevents SQL confusion where a variable name matches a table column name.
