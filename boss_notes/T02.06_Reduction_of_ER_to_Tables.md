# T02.6: Reduction of E-R Diagrams to Relational Tables

> **Topic:** T02 — E-R & EER Modeling | **Priority:** 🟢 Low | **Exam Frequency:** 1/7 finals (5 marks)
> **Sources:** Silberschatz 7e Ch. 6 (§6.7, §6.8.6) · Lecture Deck 05 (Slides 40–48) · Fahim Notes (p. 28–30)

## Why This Topic Matters

An E-R diagram is a visual blueprint for humans, but a relational database engine only understands rows and columns inside tables. **Reduction** is the step-by-step process of translating your rectangles, diamonds, and ovals into concrete relational schemas (`CREATE TABLE` definitions) without losing any constraints or creating unnecessary duplicates. In RUET exams, this topic appeared directly in 2018 Q.2(c) (5 marks) for a ternary exam-marks database, and in 2018 Q.3(c) on converting many-to-many relationships into tables.

---

## 📝 Key Definitions

> **Reduction to Relation Schemas:** Reduction to relation schemas is the process of converting an E-R diagram into a set of relational tables. Each entity set and relationship set is mapped to a table with defined columns, primary keys, and foreign keys.

> **Strong Entity Set Reduction:** A strong entity set reduces directly to a relational table containing all of its simple attributes. The primary key of the strong entity set becomes the primary key of the resulting table.

> **Weak Entity Set Reduction:** A weak entity set reduces to a table containing all of its own attributes plus the primary key of its identifying strong entity set. The primary key of the table is the combination of the owner's primary key and the weak entity's discriminator.

> **Relationship Set Reduction:** A relationship set $R$ reduces to a table whose columns are the primary keys of all participating entity sets $\{a_1, a_2, \dots, a_m\}$ plus any descriptive attributes $\{b_1, b_2, \dots, b_n\}$ of $R$. For many-to-many or ternary relationships, the union of the participating primary keys forms the composite primary key.

---

## Intuitive Analogy: Why the Reduction Rules Work

Before memorizing the formal schema notation, keep one simple constraint in mind: **every cell in a relational table can hold only a single atomic value** (no lists or nested sub-tables). Every reduction rule is a direct consequence of that single rule:
- If an attribute has sub-parts (like `name` split into `first_name` and `last_name`), we flatten the sub-parts into ordinary columns.
- If an attribute can hold multiple values for one person (like `phone_number`), putting a list into one cell is illegal, so we spin it off into a separate helper table tied back to the owner's primary key.
- If a relationship is **One-to-Many ($1:N$)** (one teacher teaches many courses, and each course has just one teacher), each course row only needs to remember *one* `teacher_id`. That means we can absorb `teacher_id` right into the `course` table without creating an extra table.
- If a relationship is **Many-to-Many ($M:N$)** (one student takes many courses, and one course has many students), neither table can hold the other's ID without storing a list. Because of this, we must create a third "bridge" (junction) table where each row pairs one `student_id` with one `course_id`.

## Systematic Reduction Rules: E-R Constructs to Relational Tables

Follow these nine conversion rules from Silberschatz §6.7 and Lecture Deck 05 (Slides 40–48):

### Rule 1: Strong Entity Sets with Simple Attributes
A strong entity set turns directly into a table with the exact same columns and primary key.
- **Attributes:** All simple attributes of the entity set.
- **Primary Key:** The primary key of the entity set (underlined).
- **Example:** Entity set `STUDENT` with attributes `ID`, `name`, `tot_cred` becomes:
  $$\text{student}(\underline{\text{ID}}, \text{name}, \text{tot\_cred})$$

### Rule 2: Composite Attributes (Flattening)
When an attribute is made of smaller sub-attributes, flatten it by creating a separate column for each sub-attribute and dropping the parent group name.
- **Example:** An `instructor` entity with composite attribute `name` (`first_name`, `last_name`) and `address` (`street`, `city`, `zip`) reduces to:
  $$\text{instructor}(\underline{\text{ID}}, \text{first\_name}, \text{last\_name}, \text{street}, \text{city}, \text{zip})$$

### Rule 3: Multivalued Attributes (Separate Table)
Because a single column cannot store a comma-separated list of values, a multivalued attribute $M$ on entity set $E$ gets its own separate table $E_M$.
- **Attributes:** The primary key of $E$ plus the multivalued attribute $M$.
- **Primary Key:** Both columns together form a composite primary key (so one person can have multiple rows, one per value).
- **Foreign Key:** The primary key of $E$ references table $E$.
- **Example:** Instructor phone numbers become:
  $$\text{inst\_phone}(\underline{\text{ID}}, \underline{\text{phone\_number}})$$
  `FK: ID references instructor(ID)`

### Rule 4: Weak Entity Sets
A weak entity set $A$ cannot identify its rows without its owner strong entity set $B$. So its table includes all of its own attributes plus the primary key of $B$.
- **Attributes:** $\{ \text{attributes of } A \} \cup \{ \text{primary key of } B \}$.
- **Primary Key:** The primary key of $B$ combined with the discriminator (partial key) of $A$.
- **Foreign Key:** The owner key column references strong entity table $B$.
- **Example:** Weak entity `section` (owned by strong entity `course`) becomes:
  $$\text{section}(\underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}})$$
  `FK: course_id references course(course_id)`

### Rule 5: Many-to-Many ($M:N$) Relationship Sets
A many-to-many relationship set $R$ between entity sets $A$ and $B$ always becomes its own junction table.
- **Attributes:** Primary key of $A$ + Primary key of $B$ + any descriptive attributes attached to the diamond $R$.
- **Primary Key:** The combination of the primary keys of $A$ and $B$.
- **Foreign Keys:** Separate foreign keys referencing $A$ and $B$.
- **Example:** `Registers` linking `STUDENT` and `COURSE` becomes:
  $$\text{registers}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{session}, \text{semester})$$
  `FK: student_id references student(student_id), course_id references course(course_id)`

### Rule 6: Many-to-One and One-to-Many ($N:1$ / $1:N$) Relationships & Schema Merging
In a $1:N$ relationship, each entity on the "many" ($N$) side connects to at most one entity on the "one" ($1$) side. Creating a separate table for the diamond is usually redundant.
- **How to Merge:** Take the primary key of the "one" side and add it as a foreign key column inside the "many" side's table, along with any descriptive attributes of the relationship.
- **Example:** Each course is taught by one teacher (`Teaches`, $1:N$ from `TEACHER` to `COURSE`). Instead of making a `teaches` table, we add `teacher_id` straight into `course`:
  $$\text{course}(\underline{\text{course\_id}}, \text{title}, \text{credits}, \text{teacher\_id})$$
  `FK: teacher_id references teacher(teacher_id)`
- **When Not to Merge (Partial Participation):** If many courses have no assigned teacher yet, `teacher_id` in `course` would be filled with `NULL` values. To avoid storing `NULL`s, a designer can keep a separate `teaches` table whose primary key is simply `course_id`.

### Rule 7: One-to-One ($1:1$) Relationship Sets
In a $1:1$ relationship between $A$ and $B$, you can merge the relationship into either table:
- Add the primary key of $B$ as a foreign key in $A$, or add the primary key of $A$ as a foreign key in $B$.
- Always place the foreign key inside the table that has **total participation** so that the foreign key column is never `NULL`.

### Rule 8: Omitting the Identifying Relationship Diamond
Never create a separate table for the double-lined identifying relationship that connects a weak entity set to its owner.
- By Rule 4, the weak entity table already stores the owner's primary key and the weak entity's discriminator.
- A table for the identifying diamond would contain the exact same key columns and zero new information, so it is always dropped.

### Rule 9: Non-Binary (Ternary / $n$-ary) Relationship Sets
When a single relationship diamond links three or more entity sets at once, it always requires its own table.
- **Attributes:** The primary keys of all participating entity sets, plus any descriptive attributes on the diamond.
- **Primary Key:** Usually the composite combination of all three (or $n$) primary keys. (If one entity has an arrow pointing to it, meaning at most one entity is associated with a pair of the others, its key is excluded from the composite primary key.)
- **Foreign Keys:** Separate foreign keys referencing each participating entity table.

## Comprehensive Reduction Summary Table

| E-R Construct | Relational Table Generated | Primary Key | Foreign Key Constraints |
| :--- | :--- | :--- | :--- |
| **Strong Entity Set $E$** | Table $E(\underline{K}, A_1, A_2, \dots)$ | $K$ (PK of $E$) | None (unless recursive) |
| **Composite Attribute** | Component columns flattened into table $E$ | $K$ | None |
| **Multivalued Attribute $M$ of $E$** | Table $E_M(\underline{K}, \underline{M})$ | $(K, M)$ | $K \to E(K)$ |
| **Weak Entity Set $W$ (Owner $S$)** | Table $W(\underline{K_S}, \underline{D_W}, A_1, \dots)$ | $(K_S, D_W)$ | $K_S \to S(K_S)$ |
| **$M:N$ Relationship Set $R(A, B)$** | Junction table $R(\underline{K_A}, \underline{K_B}, \text{attrs})$ | $(K_A, K_B)$ | $K_A \to A(K_A)$, $K_B \to B(K_B)$ |
| **$1:N$ Relationship Set (Total on $N$)** | Merged into table on "Many" side: $N(\underline{K_N}, \dots, K_1)$ | $K_N$ | $K_1 \to \text{One}(K_1)$ |
| **$1:1$ Relationship Set** | Merged into either table (preferred on total side) | Existing PK | References the other table |
| **Identifying Relationship** | Redundant (Omitted) | N/A | Handled inside weak entity table |
| **Ternary Relationship $R(A, B, C)$** | Table $R(\underline{K_A}, \underline{K_B}, \underline{K_C}, \text{attrs})$ | $(K_A, K_B, K_C)$ | $K_A \to A, K_B \to B, K_C \to C$ |

## Converting Many-to-Many Relationships (2018 Q.3(c) Cross-Reference)

Past exam question **2018 Q.3(c)** asks how an $M:N$ relationship is converted into a table:

1. **Why a Separate Table is Required:**
   - In a many-to-many relationship, one entity in $A$ links to multiple entities in $B$, and one entity in $B$ links to multiple entities in $A$.
   - If you tried to put $B$'s primary key column inside table $A$, a single row in $A$ would have to store multiple IDs at once, which violates First Normal Form (1NF). Putting $A$'s key inside $B$ causes the exact same problem.
2. **The Conversion Steps:**
   - Create a new junction table named after the relationship diamond.
   - Add the primary key of $A$ and the primary key of $B$ as foreign key columns.
   - Add any descriptive attributes attached to the relationship (such as `date`, `grade`, or `session`).
   - Make the pair $(K_A, K_B)$ the composite primary key of the new table.

## Non-Binary & Ternary Reductions: Quick Mini-Example

Before tackling the full exam question below, let's see how a ternary relationship works on a simple supply-chain example. Suppose a company tracks which **`SUPPLIER`** (`s_id`) delivers which **`PART`** (`p_id`) to which construction **`PROJECT`** (`proj_id`), along with the `quantity` shipped:

1. **Why Two Keys Are Not Enough:** Knowing only `(s_id, p_id)` tells you a supplier makes a part, but not which project received it. Knowing only `(proj_id, p_id)` tells you a project uses a part, but not which supplier delivered it.
2. **Resulting Schemas:**
   - $\text{supplier}(\underline{\text{s\_id}}, \text{s\_name})$
   - $\text{part}(\underline{\text{p\_id}}, \text{p\_name})$
   - $\text{project}(\underline{\text{proj\_id}}, \text{location})$
   - $\text{supplies}(\underline{\text{s\_id}}, \underline{\text{p\_id}}, \underline{\text{proj\_id}}, \text{quantity})$
3. **Why `quantity` Goes in `supplies`:** The quantity shipped depends on all three pieces together (who supplied what part to which project), so it sits as a regular column alongside the 3-part composite primary key.

### 🎯 GQ1 · 2018 Q.2(c) · Ternary Examination Marks E-R Diagram & Relational Data Model

> **Appeared:** 2018 Q.2(c) (05 Marks, Sec A)

*(Cross-ref: 2018 Q.3(c) asks how a many-to-many relationship is converted into a table).*

**Question:**

Consider a database used to record the marks that students get in different examinations of different course offerings. (i) Construct an E-R diagram that models examinations as entities, and uses a ternary relationship for the above database; (ii) Draw a relational data model for the above corresponding E-R diagram.

**Full Answer:**

#### (i) E-R Diagram with Ternary Relationship (2.5 Marks)

##### 1. Entity Sets and Attributes
- **`STUDENT`:** `student_id` (PK, underlined), `name`, `dept_name`
- **`COURSE_OFFERING`:** `offering_id` (PK, underlined), `semester`, `year`
- **`EXAM`:** `exam_id` (PK, underlined), `exam_type`, `max_marks`

##### 2. Ternary Relationship
- **`Scores`:** A ternary relationship diamond connected by three solid lines to `STUDENT`, `COURSE_OFFERING`, and `EXAM`.
- **Relationship Attribute:** `marks` (descriptive attribute oval attached to the `Scores` diamond, recording the numeric score obtained by a student in a specific exam of a course offering).

#### (ii) Relational Data Model (Relational Schemas) (2.5 Marks)

We reduce the E-R diagram into four relational tables according to Silberschatz reduction rules:

##### 1. Relation `student`
- **Schema:** **student**(**student_id**, name, dept_name)
- **Primary Key:** `student_id`
- **Foreign Keys:** None

##### 2. Relation `course_offering`
- **Schema:** **course_offering**(**offering_id**, semester, year)
- **Primary Key:** `offering_id`
- **Foreign Keys:** None

##### 3. Relation `exam`
- **Schema:** **exam**(**exam_id**, exam_type, max_marks)
- **Primary Key:** `exam_id`
- **Foreign Keys:** None

##### 4. Relation `scores` (Reduced from Ternary Relationship)
- **Schema:** **scores**(**student_id**, **offering_id**, **exam_id**, marks)
- **Primary Key:** Composite key `(student_id, offering_id, exam_id)`
- **Foreign Keys:**
  - `student_id` REFERENCES **student**(`student_id`)
  - `offering_id` REFERENCES **course_offering**(`offering_id`)
  - `exam_id` REFERENCES **exam**(`exam_id`)

#### Verification Check
- Can a student take multiple exams in the same course offering? Yes, `exam_id` distinguishes rows.
- Can different students take the same exam in the same course offering? Yes, `student_id` distinguishes rows.
- Does each tuple uniquely identify a single mark value? Yes, the composite primary key guarantees uniqueness.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 6.6 · Ternary Relationship Reduction vs Binary Decomposition

> **Source:** Silberschatz 7e · Chapter 6 (Practice Exercise 6.6)  
> **Exam Relevance:** Prime Overdue Exam Theory & Design Question  
> **Key Tested Concept:** Reduction of ternary relationships into relational tables and why binary decomposition can be lossy.

**Problem Statement:**
> 1. Give the formal rule for reducing a **ternary relationship set $R$** connecting entity sets $A, B, C$ into a relational table.
> 2. Explain why decomposing a ternary relationship set $R(A, B, C)$ into three binary relationship sets $R_{AB}(A, B)$, $R_{BC}(B, C)$, and $R_{AC}(A, C)$ can fail to represent the original real-world constraints (i.e., causes **spurious relationships**).

**Model Exam-Style Solution:**

1. **Relational Table Reduction Rule for Ternary Relationships:**
   - Let $R$ be a ternary relationship set among entity sets $A, B, C$ with primary keys $K_A, K_B, K_C$ respectively.
   - The relational schema for $R$ contains:
     $$
     \text{Schema}(R) = (K_A \cup K_B \cup K_C \cup \text{descriptive attributes of } R)
     $$
   - **Primary Key Determination:**
     - If the ternary relationship is many-to-many-to-many ($M:N:P$), the primary key is the composite key:
       $$
       \text{Primary Key}(R) = \{K_A, K_B, K_C\}
       $$
     - If an entity (say $C$) has a functional constraint (each pair $(A, B)$ is associated with at most one $C$), the primary key is $\{K_A, K_B\}$.

2. **Why Binary Decomposition Fails (Lossy Relationship Decomposition):**
   - Suppose ternary relationship `examines(doctor, patient, disease)` records which doctor diagnosed which disease for which patient.
   - Suppose the database holds the following two true facts:
     1. Dr. Adams diagnosed Patient John with Malaria: `(Adams, John, Malaria)`.
     2. Dr. Baker diagnosed Patient Mary with Flu: `(Baker, Mary, Flu)`.
   - Now decompose `examines` into three binary tables:
     - $R_{DP}(\text{doctor, patient}) = \{(\text{Adams, John}), (\text{Baker, Mary})\}$
     - $R_{PD}(\text{patient, disease}) = \{(\text{John, Malaria}), (\text{Mary, Flu})\}$
     - $R_{DD}(\text{doctor, disease}) = \{(\text{Adams, Malaria}), (\text{Baker, Flu})\}$
   - Now suppose Dr. Baker also tests Patient John for Malaria:
     - Add `(Baker, John)` to $R_{DP}$, and Dr. Adams also treats Flu: `(Adams, Flu)` to $R_{DD}$.
   - When joining the three binary tables $R_{DP} \bowtie R_{PD} \bowtie R_{DD}$, tuples like `(Adams, Mary, Malaria)` or `(Baker, John, Flu)` will be generated that **never existed** in the real world!
   - **Conclusion:** A ternary relationship represents a 3-way simultaneous association. Projecting into binary pairs destroys the joint association and allows **spurious associations** upon reconstruction. $\blacksquare$

**💡 RUET Exam Takeaway:**
Ternary relationships should be preserved as a single table containing all three foreign keys. Do NOT decompose a ternary relationship into binary tables unless a specific functional dependency justifies it!

## ⚡ Exam Tips & Common Mistakes

1. **Marks Attribute Placement Trap:** Never place obtained marks inside `EXAM` or `STUDENT`. Exam entities hold only the exam type (Quiz, Midterm) and maximum marks. Obtained marks depend on the student, offering, and exam combined, so `marks` belongs on the relationship diamond.
2. **Do Not Decompose into Binary Diamonds:** When an exam question specifies a ternary relationship, draw a single diamond connected to three entity rectangles. Do not draw three separate binary relationships.
3. **Composite Primary Keys in Relational Schemas:** When writing relational schemas for junction tables or ternary relationships, underline or bold all component primary key attributes. Clearly state the composite primary key on a dedicated line.
4. **Identify Redundant Schemas:** In $1:N$ relationships, merge the foreign key into the table on the "many" side instead of creating a redundant junction table, unless the question asks for pure uncombined reduction.
