# T08.10: Pros and Cons of Normalization & Denormalization

> **Topic:** T08 — Normalization & Functional Dependencies | **Priority:** 🟡 | **Exam Frequency:** 0/7 finals (0 marks) [Cross-ref: 2017 Q.3(a) in T08.06]
> **Sources:** Silberschatz 7e Ch. 7 (§7.9.3, §7.1.3) · Lecture Deck 06 (Slides 47–51) · Classnote by Raidah (p. 23)

## Why This Topic Matters

Normalization is the backbone of relational database design because it removes duplicate data and protects your tables from insertion, update, and deletion anomalies. However, splitting data across lots of small tables comes with a real-world catch: every time an application wants to display a complete record, the database has to run expensive `JOIN` operations across all those tables. In read-heavy systems, joining five or six tables on every page load can slow queries to a crawl. To speed things up, database designers sometimes intentionally put controlled redundancy back into a normalized schema, a technique called **denormalization**. In RUET exams, this topic tests how well you understand the practical engineering trade-off between write safety and read speed.

---

## 📝 Key Definitions

> **Normalization:** "The method for designing a relational database is to use a process commonly known as **normalization**. The goal is to generate a set of relation schemas that allows us to store information without unnecessary redundancy, yet also allows us to retrieve information easily." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.1.3 (p. 308)

> **Denormalization:** "The process of taking a normalized schema and making it non-normalized is called **denormalization**, and designers use it to tune the performance of systems to support time-critical operations." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.9.3 (p. 346)

> **Materialized View:** "A view whose result is stored in the database and brought up to date when the relations used in the view are updated." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §7.9.3 (p. 346)

---

## Advantages of Normalization

Normalizing a database gives you six major design benefits that keep data clean and easy to maintain (Lecture Deck 06 Slide 47):

1. **Elimination of Data Redundancy:**
   Every fact is stored in one single place, which saves disk space and prevents conflicting copies of the same data.

2. **Prevention of Update Anomalies:**
   When a fact changes (such as an instructor's address), you only have to update one row in one table instead of hunting down dozens of rows in a giant combined table.

3. **Prevention of Insertion Anomalies:**
   You can record new entities right away without waiting for other relationships to exist. For example, you can add a new department even before it hires its first instructor.

4. **Prevention of Deletion Anomalies:**
   Deleting a relationship does not wipe out the entities themselves. Dropping the last student from a course will not accidentally delete the course or instructor from the database.

5. **Stronger Data Consistency and Integrity:**
   Because each table represents one clear concept, the DBMS can easily enforce primary keys, foreign keys, and `CHECK` constraints on individual tables.

6. **Easier Database Maintenance:**
   Smaller, narrower tables are much easier to index, back up, and modify without locking up the entire database.

---

## Disadvantages of Normalization

Even though normalization is great for data integrity, pushing it too far creates performance headaches in production systems (Lecture Deck 06 Slide 48):

1. **Table Proliferation:**
   Normalizing a large business system splits data into dozens or even hundreds of small tables, making the schema harder to navigate.

2. **Heavy JOIN Overhead:**
   Putting the pieces back together for a user screen or report requires joining multiple tables, which burns CPU cycles, disk I/O, and memory buffer space.

3. **Slower Read Performance:**
   When high-traffic queries have to join five or six tables across millions of rows, response times drop noticeably.

4. **More Complex SQL Queries:**
   Developers have to write long multi-table `JOIN` queries for routine tasks, which takes longer to write and makes bugs harder to spot.

5. **Extra Index Overhead:**
   Every split table needs its own primary key index and foreign key indexes, which eats back some of the disk space saved by removing duplicate columns.

---

## What is Denormalization?

Denormalization is the deliberate act of adding controlled redundancy back into a schema that has *already* been normalized (Lecture Deck 06 Slide 49, Silberschatz 7e §7.9.3).

```text
Normalized Schema (3NF / BCNF)
        │
        │   Apply Controlled Redundancy (Pre-join tables, store aggregates)
        ▼
Denormalized Schema
        ├── Fewer JOIN operations
        ├── Faster read performance
        └── Trade-off: Slower updates, extra storage, application-managed consistency
```

It is important to remember that **denormalized is not the same thing as unnormalized**. An unnormalized table is what you get when nobody designed the schema properly in the first place. Denormalization happens *after* you design a clean 3NF or BCNF schema, spot a real read-performance bottleneck, and selectively merge two tables or duplicate a column so your most frequent queries can run without expensive joins.

---

## When to Use Denormalization?

A database designer should reach for denormalization in four specific situations (Lecture Deck 06 Slide 50):

### 1. Read-Intensive Workloads

When 90% or more of your database traffic consists of `SELECT` queries (like an online product catalog or news site), speeding up reads is worth paying a small penalty on writes.

### 2. High-Frequency Time-Critical Queries

When a core user-facing feature has to join several big tables and return results in a few milliseconds, pre-joining those columns removes the bottleneck.

### 3. Reporting and Data Warehousing (OLAP Systems)

Online Analytical Processing (OLAP) systems and data warehouses scan millions of historical rows to build charts and reports. They regularly use Star or Snowflake schemas that store pre-joined dimension columns and pre-calculated totals.

### 4. Expensive Cross-Table Aggregations

If an application constantly runs `SUM()`, `COUNT()`, or `AVG()` across thousands of child rows (like counting total likes or calculating an account balance), storing that running total directly on the parent row avoids scanning the child table every time.

## Common Denormalization Techniques

In practice, database engineers use four main techniques to denormalize a schema:

### Technique 1: Pre-Joining Tables (Flattening)

Instead of maintaining separate tables for related entities, combine them into a single relation.

**Example:**
- Normalized:
  - `CUSTOMER(CustomerID, CustomerName, Address)`
  - `ORDERS(OrderID, OrderDate, CustomerID, Amount)`
- Denormalized:
  - `ORDERS(OrderID, OrderDate, CustomerID, CustomerName, Address, Amount)`

*Benefit:* Queries displaying orders with customer names require zero joins.  
*Penalty:* If a customer changes address, every historic order must be updated.

### Technique 2: Replicating Frequently Accessed Columns

Add one or two heavily requested attributes from a parent table directly into a child table.

**Example:**
In a university database, relation `STUDENT_SECTION(StudentID, SectionID, Grade)` stores student enrollments. Course title is frequently queried alongside grades. Adding `CourseTitle` to `STUDENT_SECTION` eliminates joining through `SECTION` to `COURSE`.

### Technique 3: Storing Derived or Aggregate Attributes

Store summary metrics directly in parent tables rather than computing them dynamically.

**Example:**
In a banking schema, table `ACCOUNT(AccountID, Balance, TotalTransactions)` stores `TotalTransactions`. Every time a deposit or withdrawal row is inserted into `TRANSACTION`, `ACCOUNT.TotalTransactions` is incremented.

### Technique 4: Horizontal or Vertical Partitioning

- **Horizontal Partitioning:** Split a table into separate tables based on row ranges (such as `ORDERS_2023`, `ORDERS_2024`).
- **Vertical Partitioning:** Split infrequently accessed columns (such as large text blobs or profile images) into a secondary table to keep the primary row footprint small in memory.

## Normalization vs. Denormalization: Comparison Matrix

The table below contrasts the two design paradigms across key operational dimensions (Lecture Deck 06 Slide 51).

| Criterion | Normalization | Denormalization |
| :--- | :--- | :--- |
| **Primary Goal** | Eliminate redundancy and prevent anomalies | Maximize read performance and reduce join latency |
| **Data Redundancy** | Minimized to zero | Controlled redundancy introduced deliberately |
| **Table Structure** | Many narrow, highly specialized tables | Fewer, wider tables containing combined attributes |
| **Query Complexity** | Complex SQL with multiple `JOIN` operations | Simpler SQL queries requiring fewer or no `JOIN`s |
| **Read Speed** | Slower for complex queries due to join costs | Fast and efficient for targeted read queries |
| **Write Speed (Insert/Update)** | Fast (single row modified in one table) | Slower (multiple redundant copies must be updated) |
| **Data Integrity Risk** | Very low (enforced via relational constraints) | High (application must synchronize duplicate values) |
| **Storage Requirement** | Lower physical disk space | Higher disk space due to repeated attributes |
| **Typical Environment** | OLTP (Online Transaction Processing systems) | OLAP (Data warehouses, analytics, reporting) |

## Materialized Views: A Modern Alternative

Silberschatz 7e (§7.9.3, p. 346) points out that modern relational DBMS engines offer a much cleaner alternative to manual denormalization: **materialized views**.

### How Materialized Views Work

A normal SQL `VIEW` is just a saved query. Every time you `SELECT` from a normal view, the database still has to run the underlying `JOIN` from scratch.

A **materialized view**, on the other hand, actually computes the join once and saves the result table on disk. Whenever a query reads from the materialized view, the DBMS serves the precomputed rows straight from disk without re-running the join.

### Advantage Over Manual Denormalization

When you denormalize base tables by hand, your application code has to remember to update every duplicate column whenever data changes. If a bug in your code misses one copy, your data becomes corrupted.

With materialized views, you get the best of both worlds:
1. Your base tables stay cleanly normalized in 3NF or BCNF.
2. The DBMS automatically keeps the materialized view up to date whenever the base tables change.
3. If your query patterns change later, you can drop or tweak the materialized view without touching your actual production tables.

## 🔮 Likely Questions

### 🎯 LQ1 · Discuss the Advantages and Disadvantages of Normalization in Relational Database Design

> **Likely Question:** High-Probability Exam Problem — (5 marks)

**Question:**

Define normalization. Discuss the principal advantages and disadvantages of normalizing a relational database schema.

**Full Answer:**

#### 1. Definition of Normalization

Normalization is the systematic process of decomposing relation schemas to minimize data redundancy and eliminate operational anomalies (insertion, update, and deletion anomalies) while preserving data integrity and functional relationships.

#### 2. Advantages of Normalization

1. **Elimination of Data Redundancy:** Storing each piece of information once saves physical storage and ensures single-point truth.
2. **Anomaly Prevention:**
   - *Insertion Anomaly:* Entities can be recorded without requiring unrelated parent or child associations.
   - *Update Anomaly:* Modifying an attribute requires updating a single tuple rather than multiple scattered instances.
   - *Deletion Anomaly:* Deleting one record does not cause the unintentional loss of distinct entity information.
3. **Enhanced Data Consistency:** Enforcing primary and foreign key constraints on narrow tables guarantees referential integrity.
4. **Flexible and Extensible Schema:** Adding new attributes or entities requires modifying localized tables without breaking unrelated business logic.

#### 3. Disadvantages of Normalization

1. **Increased Query Latency (Join Overhead):** Normalized data is spread across many tables. Reconstructing business views requires multi-table `JOIN` operations, which consume CPU, memory buffers, and disk I/O.
2. **Table Proliferation:** Decomposing large tables produces many smaller relations, increasing schema complexity and metadata management overhead.
3. **Complex SQL Development:** Developers must write complex queries involving multiple join conditions, increasing maintenance effort.
4. **Slower Analytical Reporting:** Batch reporting queries that aggregate data across millions of rows suffer from poor performance on highly normalized OLTP structures.

### 🎯 LQ2 · What is Denormalization? Explain When and Why a Database Designer Might Choose to Denormalize

> **Likely Question:** High-Probability Exam Problem — (4 marks)

**Question:**

What is meant by denormalization? Under what circumstances is denormalization justified, and what penalties does it introduce?

**Full Answer:**

#### 1. Definition of Denormalization

Denormalization is the intentional process of introducing controlled redundancy or combining normalized tables into wider schemas. It is performed after normalization to improve read performance for time-critical queries.

#### 2. When Denormalization is Justified

A database designer chooses denormalization under the following circumstances:
1. **Read-Heavy Workloads:** In systems where reads vastly outnumber writes (for example, 95% reads vs. 5% writes in e-commerce product catalogs or news portals).
2. **Costly Join Operations:** When critical user-facing queries frequently join four or more large tables, causing unacceptable response delays.
3. **Reporting and Analytics (OLAP):** In data warehousing environments where decision-support queries require pre-aggregated summaries and flattened dimension tables.
4. **Frequent Aggregate Calculations:** When queries repeatedly compute summary values (such as account balances, order totals, or item counts) over thousands of transaction records.

#### 3. Penalties and Costs of Denormalization

1. **Write Overhead:** Updating a redundant attribute requires modifying multiple rows across tables, slowing down `INSERT`, `UPDATE`, and `DELETE` operations.
2. **Risk of Data Inconsistency:** If an application crashes mid-update or fails to update all copies of a redundant attribute, the database enters an inconsistent state.
3. **Storage Overhead:** Storing duplicate columns increases the overall storage footprint on disk and consumes additional database buffer pool cache.
4. **Increased Application Complexity:** Developers must write extra application logic or database triggers to ensure redundant data stays synchronized.

### 🎯 LQ3 · Distinguish Between Normalization and Denormalization. How Can Materialized Views Serve as an Alternative?

> **Likely Question:** High-Probability Exam Problem — (5 marks)

**Question:**

Distinguish between normalization and denormalization using a comparative table. How can materialized views achieve the performance benefits of denormalization without compromising schema integrity?

**Full Answer:**

#### 1. Comparison: Normalization vs. Denormalization

| Parameter | Normalization | Denormalization |
| :--- | :--- | :--- |
| **Objective** | Remove redundancy and anomalies | Boost read speed and reduce join latency |
| **Redundancy** | Minimized to zero | Controlled redundancy introduced deliberately |
| **Number of Tables** | Many smaller, specialized tables | Fewer, wider tables |
| **Join Requirements** | Frequent joins required for queries | Minimizes or eliminates joins |
| **Read Performance** | Slower for complex multi-table queries | Very fast for targeted reads |
| **Write Performance** | Fast and efficient | Slower due to duplicate updates |
| **Integrity Enforcement** | Handled natively by DBMS constraints | Handled by application logic or triggers |
| **Target Application** | OLTP (transaction processing) | OLAP (data warehouses, dashboards) |

#### 2. Materialized Views as an Alternative

A materialized view provides an elegant bridge between normalization and read performance:

1. **Mechanism:** The underlying base tables remain strictly normalized in 3NF or BCNF, preserving data integrity and preventing update anomalies. The database engine precomputes the expensive multi-table join and stores the resulting dataset physically on disk as a materialized view.
2. **Automated Maintenance:** Unlike manual denormalization where application code must synchronize redundant copies, the database management system automatically refreshes the materialized view when base relations change.
3. **Performance Benefit:** Analytical and read-heavy queries read directly from the materialized view without paying the cost of real-time join execution.
4. **Flexibility:** If query requirements change, the database administrator can drop or recreate the materialized view without modifying the logical database schema or restructuring production tables.

## ⚡ Exam Tips & Common Mistakes

1. **Do not confuse unnormalized tables with denormalized tables:** An unnormalized table is bad design caused by lack of schema planning. A denormalized table is a conscious engineering trade-off applied *after* reaching 3NF or BCNF.
2. **Always state both read advantages and write penalties:** When explaining denormalization, never discuss only faster reads. Examiners look for the write overhead, risk of data inconsistency, and extra storage requirements.
3. **Contrast OLTP and OLAP:** Associate normalization with OLTP (transactional workloads requiring fast single-row writes) and denormalization with OLAP (reporting workloads requiring fast multi-row aggregations).
4. **Mention materialized views for full credit:** Adding a short paragraph explaining that modern DBMS engines use materialized views to achieve denormalization performance without sacrificing schema normalization demonstrates textbook mastery.
