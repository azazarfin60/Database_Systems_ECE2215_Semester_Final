# T09.2: The Consistency Property in Depth

> **Topic:** T09: Transactions, ACID & Anomalies | **Priority:** 🟡 Medium Priority | **Exam Frequency:** 2/7 finals (6 marks: 2019 Q.3(b), 2024 Q.2(c))  
> **Sources:** Silberschatz 7e Ch. 17 (§17.1–§17.2, pp. 800–802) · Lecture Deck 07 (Slide 6) · Raidah Class Notes (p. 26)

## Why This Topic Matters

While exams often test all four ACID properties together, the consistency property was singled out as a standalone 3-mark question in both 2019 and 2024. Examiners want to see if you understand the difference between explicit database schema rules and implicit application rules. To earn full marks, you need to explain why a transaction is allowed to pass through a temporarily inconsistent state while it runs, and why keeping the database consistent is mainly the job of the application programmer rather than the DBMS engine alone.

---

## 📝 Key Definitions

> **Consistency:** "Execution of a transaction in isolation (i.e., with no other transaction executing concurrently) preserves the consistency of the database."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.1 (p. 800)

> **Consistency Requirement:** "A transaction must preserve database consistency—if a transaction is run atomically in isolation starting from a consistent database, the database must again be consistent at the end of the transaction. This consistency requirement goes beyond the data-integrity constraints we have seen earlier (such as primary-key constraints, referential integrity, **check** constraints, and the like). Rather, transactions are expected to go beyond that to ensure preservation of those application-dependent consistency constraints that are too complex to state using the SQL constructs for data integrity. How this is done is the responsibility of the programmer who codes a transaction."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.1 (p. 800)

## Anatomy of the Consistency Property

### Intuitive Analogy: Why Consistency Needs Both the DBMS and the Programmer

Think of database consistency like accounting rules in a real bank. Some rules are simple form checks, like making sure an account number exists or a balance never drops below zero. The database software can check those automatically. However, other rules depend on the meaning of the business action itself. For example, when you transfer money between two accounts, every dollar deducted from one account must show up in the other. Because the database engine does not know whether your SQL code is meant to be a transfer, a fee, or a deposit, the programmer writing the transaction has to make sure the math balances out.

In a relational database, a state is **consistent** when every stored value obeys all declared schema constraints and all real-world business rules (invariants).

### Two Tiers of Consistency Constraints

Database consistency works across two distinct levels:

1. **Explicit Integrity Constraints (Enforced by the DBMS):**
   These are formal rules written directly into the SQL schema using DDL statements. Whenever a query breaks one of these rules, the DBMS engine immediately stops the operation and throws an error. Common examples include:
   - **Entity Integrity:** Primary key values must be unique and never null (`PRIMARY KEY`).
   - **Referential Integrity:** Foreign keys must point to existing primary keys (`FOREIGN KEY ... REFERENCES`).
   - **Domain Constraints:** Column values must match their declared data types and lengths (`NOT NULL`, `VARCHAR(20)`).
   - **Check Constraints:** Values must stay within allowed bounds, such as `CHECK (balance >= 0)` or `CHECK (status IN ('active', 'closed'))`.

2. **Implicit Application Invariants (Enforced by the Programmer):**
   These are real-world business rules that are too complex to express with basic table constraints. Because the DBMS engine does not understand the business logic behind arbitrary formulas, the application programmer must write transaction code that preserves them. Common examples include:
   - **Conservation of money:** During a fund transfer between account $A$ and account $B$, the combined total $A + B$ must stay the same before and after the transaction.
   - **Bank-wide asset balance:** The sum of all customer deposits minus total loans must match the bank's cash on hand.
   - **Inventory reservation:** Booking a flight seat or warehouse item must reduce available stock by 1 and create a matching ticket or order row at the same time.

### Division of Responsibility

| Constraint Type | Description | Who Enforces It? | What Happens on Violation? |
| :--- | :--- | :--- | :--- |
| **Explicit Constraints** | Schema-level rules (`PK`, `FK`, `CHECK`, `NOT NULL`) | DBMS Engine | DBMS rejects the statement or aborts the transaction automatically |
| **Implicit Invariants** | Business rules and multi-table math invariants | Application Programmer | Wrong data gets committed because the DBMS cannot spot the logic bug |

## The Paradox of Temporary Inconsistency

A common misconception is that a database must stay consistent at every single microsecond. In reality, **a transaction almost always passes through a temporarily inconsistent state while it executes**.

Why does this happen? A computer executes instructions one step at a time. When a transaction updates two related pieces of data, there is always a brief moment after the first update finishes where the second update has not happened yet.

### Illustrative Mini-Example: Warehouse Stock Reservation

Suppose a warehouse tracks 100 laptops across two counters: `Available_Stock` ($S = 100$) and `Reserved_Stock` ($R = 0$). The business invariant requires the total physical count to remain constant:

$$
S + R = 100
$$

Now suppose transaction $T_1$ reserves 5 laptops for a customer order:

$$
\begin{aligned}
1.&\quad \text{read}(S),\quad S := S - 5,\quad \text{write}(S) \quad [S = 95] \\
2.&\quad \text{read}(R),\quad R := R + 5,\quad \text{write}(R) \quad [R = 5]
\end{aligned}
$$

Look at the database state right after Step 1 finishes, before Step 2 runs:

| Point in Time | `Available_Stock` ($S$) | `Reserved_Stock` ($R$) | Total ($S + R$) | Database Status |
| :---: | :---: | :---: | :---: | :--- |
| **Before Step 1** | 100 | 0 | 100 | **Consistent** (Initial state) |
| **Between Step 1 & Step 2** | 95 | 0 | 95 | **Temporarily Inconsistent** (5 laptops appear missing!) |
| **After Step 2** | 95 | 5 | 100 | **Consistent** (Final state restored) |

### Why Temporary Inconsistency is Safe

Right between Step 1 and Step 2, the total count is 95 instead of 100, breaking the invariant $S + R = 100$. Even so, this temporary inconsistency is completely safe because two other ACID properties protect the transaction during that gap:

1. **Isolation:** The concurrency-control manager hides unfinished work. No other transaction $T_2$ is allowed to read $S$ or $R$ while $T_1$ is halfway through its update. To the outside world, the intermediate state of 95 never exists.
2. **Atomicity:** If the power fails or the server crashes right after Step 1, the recovery manager rolls back $T_1$ and restores $S$ to 100. The half-finished state is never left behind permanently.

Because of this partnership, the consistency rule simply states: if the database is consistent when a transaction starts, and the transaction runs to completion by itself, the database will be consistent again when the transaction finishes.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2019 Q.3(b) & 2024 Q.2(c) · Consistency Property with Example

> **Appeared:** 2019 Q.3(b), 2024 Q.2(c) (3 marks)

> **Question:**
>
> Explain the consistency property of a database system with a proper example.

**Full Answer:**

#### 1. Definition of Consistency

The **consistency** property requires that running a transaction in isolation (without interference from other concurrent transactions) preserves the consistency of the database. If the database starts in a valid state that obeys all integrity constraints and business rules, it must also end in a valid state once the transaction finishes.

Consistency covers two types of rules:
- **Explicit Constraints:** Schema rules declared in SQL and enforced automatically by the DBMS engine, such as `PRIMARY KEY` uniqueness, `FOREIGN KEY` referential integrity, and `CHECK` conditions (like `balance >= 0`).
- **Implicit Invariants:** Application-specific business rules that cannot easily be written as simple table constraints, such as keeping total money constant during a transfer. Enforcing implicit invariants is the responsibility of the **application programmer**.

#### 2. Concrete Example: Bank Fund Transfer

Consider a banking database with two accounts, $A$ and $B$, holding initial balances of \$1000 and \$2000.

The consistency invariant requires the sum of both balances to remain constant before and after the transfer:

$$
A + B = \$1000 + \$2000 = \$3000
$$

Transaction $T_1$ transfers \$50 from account $A$ to account $B$ through six steps:

$$
\begin{aligned}
1.&\quad \text{read}(A) \\
2.&\quad A := A - 50 \\
3.&\quad \text{write}(A) \quad [A = \$950] \\
4.&\quad \text{read}(B) \\
5.&\quad B := B + 50 \\
6.&\quad \text{write}(B) \quad [B = \$2050] \\
7.&\quad \text{commit}
\end{aligned}
$$

#### 3. State Analysis

- **Initial State (Consistent):** Before Step 1, $A = \$1000$ and $B = \$2000$, so the sum is $A + B = \$3000$.
- **Intermediate State (Temporarily Inconsistent):** After Step 3 writes $A = \$950$ but before Step 6 updates $B$, account $B$ still holds \$2000. At this moment, the sum is $\$950 + \$2000 = \$2950$. The database is temporarily inconsistent because \$50 appears to be missing.
- **Final State (Consistent):** After Step 6 writes $B = \$2050$ and the transaction commits, account $A$ holds \$950 and account $B$ holds \$2050. The sum is back to $\$950 + \$2050 = \$3000$, restoring full consistency.

#### 4. Conclusion

Temporary inconsistency inside an active transaction is completely normal because instructions execute one at a time. The consistency property guarantees that once the transaction commits, all invariants hold again. If a crash happens halfway through, atomicity rolls back the partial changes and returns the database to its initial consistent state.

## ⚡ Exam Tips & Common Mistakes

1. **Highlight Temporary Inconsistency:** Never write that a database stays consistent at every single instant during execution. Intermediate steps naturally break balance totals for a brief moment. The key point for full marks is that consistency is guaranteed *before* the transaction starts and *after* it finishes.
2. **Contrast Explicit vs. Implicit Rules:** Point out that the DBMS enforces explicit schema rules (`PK`, `FK`, `CHECK`), while the application programmer is responsible for implicit business invariants.
3. **Write Out the Three Sums:** Always show the three exact numbers in your example: the initial sum (\$3000), the temporary intermediate sum (\$2950), and the final restored sum (\$3000).
4. **Connect Consistency to Isolation and Atomicity:** Add one sentence explaining that temporary inconsistency is harmless because Isolation hides it from other users and Atomicity undoes it if the system crashes.
