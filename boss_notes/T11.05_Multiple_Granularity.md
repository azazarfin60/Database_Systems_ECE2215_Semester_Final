# T11.5: Multiple Granularity Locking Protocol

> **Topic:** T11 — Concurrency Control Protocols | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (Explicit in RUET Syllabus Unit 4: *"multiple granularity locking"*)  
> **Sources:** Silberschatz 7e Ch. 18 (§18.3, pp. 854–857) · Gray et al. (1975) · Lecture Deck 08

## Why This Topic Matters

In standard Two-Phase Locking, the database engine treats each individual data item (such as a single tuple or record) as an isolated unit of locking. While locking individual tuples allows fine-grained concurrency, it introduces severe operational overhead for queries that scan entire tables:
- A query reading a relation of 100,000 records would have to request, track, and release 100,000 separate tuple locks. This consumes massive CPU time and overfills the database lock table.
- Conversely, if the database only permitted locking entire relations or entire databases (coarse granularity), locking overhead would be tiny, but concurrent transactions updating different records in the same table would be completely blocked.

**Multiple Granularity Locking** resolves this fundamental engineering conflict by organizing data items into a tree hierarchy (Database $\to$ Area $\to$ File/Relation $\to$ Record/Tuple) and introducing **Intention Locks** ($IS, IX, SIX$). This allows transactions with coarse-grained requirements (e.g., report generators scanning relations) to coexist seamlessly with fine-grained transactions (e.g., online bank transfers updating individual records).

---

## 📝 Key Definitions

> **Granularity:** "The size of data items chosen as the unit of synchronization is called the granularity of data items. Small granularities (e.g., tuples) permit high concurrency but high overhead; large granularities (e.g., relations or files) minimize overhead but restrict concurrency."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.3 (p. 854)

> **Intention Lock Modes:** "If a node is locked in an intention mode, explicit locking is being done at a lower level of the tree (that is, at a finer granularity). Intention locks are put on all the ancestors of a node before that node is locked explicitly."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.3 (p. 855)

> **Lock Escalation:** "In case a transaction acquires a large number of tuple locks, the lock table may become overfull. To deal with this situation, the lock manager may perform lock escalation, replacing many lower-level locks by a single higher-level lock (e.g., replacing many record locks with a single table lock)."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.3 (p. 857)

## The Granularity Hierarchy Tree

A multiple granularity database organizes lockable units as a rooted tree where parents represent coarse-grained containers and children represent fine-grained elements:

```text
                  +-----------------------+
                  |     Database (DB)     |  (Coarsest Granularity)
                  +-----------+-----------+
                              |
                +-------------+-------------+
                |                           |
        +-------v-------+           +-------v-------+
        |    Area A1    |           |    Area A2    |
        +-------+-------+           +---------------+
                |
        +-------+-------+
        |               |
  +-----v-----+   +-----v-----+
  |  File Fa  |   |  File Fb  |  (Relations / Tables)
  +-----+-----+   +-----------+
        |
   +----+----+----+
   |         |    |
+--v---+  +--v---+ +--v---+
| ra1  |  | ra2  | | ran  |      (Records / Tuples - Finest Granularity)
+------+  +------+ +------+
```

### Implicit vs. Explicit Locking
- **Explicit Locking:** A transaction explicitly issues a lock request on node $Q$ (e.g., requesting an $X$-lock on record $r_{a1}$ or an $S$-lock on File $F_a$).
- **Implicit Locking:** When a transaction locks a node $Q$ in shared ($S$) or exclusive ($X$) mode, the transaction **implicitly locks all descendant nodes** of $Q$ in that identical mode.
  - *Example:* Locking File $F_a$ in exclusive mode ($X$) implicitly grants an exclusive lock on every record $r_{a1}, r_{a2}, \dots, r_{an}$ inside $F_a$. The transaction does not need to issue separate lock requests for those individual records.

---

## Why Intention Locks Are Mandatory

Suppose transaction $T_1$ acquires an explicit exclusive lock on a single record $r_{a1}$ inside File $F_a$.
Now suppose another transaction $T_2$ arrives and wants to lock the entire File $F_a$ in shared mode to compute an aggregate sum.

How does the concurrency control manager know whether $F_a$ can be locked?
- **Without Intention Locks:** The manager would have to traverse the entire subtree rooted at $F_a$, inspecting every record to verify if any record is locked. In a table with millions of rows, this full subtree search completely destroys system performance.
- **With Intention Locks:** Before $T_1$ is allowed to lock record $r_{a1}$, it must first tag every ancestor of $r_{a1}$ (File $F_a$, Area $A_1$, and Database) with an **Intention-Exclusive ($IX$) lock**.
- When $T_2$ subsequently requests an $S$-lock on File $F_a$, the manager immediately inspects node $F_a$. Seeing the existing $IX$-lock held by $T_1$, the manager detects the conflict instantly at the file level without inspecting a single record!

---

## Intention Lock Modes ($IS, IX, SIX$)

To support both read and write operations at fine granularities alongside coarse-grained operations, the protocol defines three intention lock modes in addition to the standard Shared ($S$) and Exclusive ($X$) modes:

### 1. Intention-Shared ($IS$) Mode
- **Meaning:** Explicit locking is currently being conducted at a lower level of the tree, but **strictly using shared ($S$) locks**.
- **Use Case:** A transaction plans to read specific individual tuples inside a relation. It places $IS$ locks on the Database and Relation, and then requests $S$ locks on the specific tuples.

### 2. Intention-Exclusive ($IX$) Mode
- **Meaning:** Explicit locking is currently being conducted at a lower level of the tree with **exclusive ($X$) locks or a mixture of shared ($S$) and exclusive ($X$) locks**.
- **Use Case:** A transaction plans to update or insert specific individual tuples. It places $IX$ locks on the Database and Relation, and then requests $X$ locks on the specific tuples.

### 3. Shared and Intention-Exclusive ($SIX$) Mode
- **Meaning:** The subtree rooted at this node is locked **explicitly in shared ($S$) mode**, and simultaneously, explicit locking is being done at a lower level with **exclusive ($X$) locks**.
- **Use Case:** A transaction reads an entire relation (needs to inspect all records, e.g., scanning employee salaries) and selectively updates a few matching records.
- **Efficiency:** An $SIX$ lock on the table allows the transaction to read all records implicitly without requesting tuple-level $S$ locks, while requiring explicit $X$ locks only on the few tuples being modified.

> [!NOTE]
> **Why is $XIS$ (Exclusive and Intention-Shared) mode useless?**  
> An exclusive lock ($X$) at node $Q$ already grants full exclusive access to the entire subtree rooted at $Q$, including reading and writing all descendants. Adding an intention to read below ($IS$) provides zero extra privileges because the holding transaction already has total exclusivity. Hence, $XIS \equiv X$.

## The $5 \times 5$ Lock-Compatibility Matrix

Whenever transaction $T_i$ requests a lock mode on node $Q$ while another transaction $T_j$ already holds a lock mode on $Q$, the concurrency-control manager consults the following matrix:

| Requested Mode $\downarrow$ \ Held Mode $\rightarrow$ | $IS$ | $IX$ | $S$ | $SIX$ | $X$ |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$IS$** | **True** | **True** | **True** | **True** | False |
| **$IX$** | **True** | **True** | False | False | False |
| **$S$** | **True** | False | **True** | False | False |
| **$SIX$** | **True** | False | False | False | False |
| **$X$** | False | False | False | False | False |

### Comprehensive Cell-by-Cell Derivation:
1. **$IS$ Row:**
   - With $IS$: **True** (Multiple transactions reading at lower levels cannot conflict at this node).
   - With $IX$: **True** (One transaction reads below, another updates below; if they target different records, both can proceed. If they target the same record, the conflict is caught at the tuple level).
   - With $S$: **True** ($S$ reads the entire subtree; $IS$ reads lower levels. Readers never conflict with readers).
   - With $SIX$: **True** ($SIX$ reads the whole subtree and modifies some items below; $IS$ only reads below. Since reading cannot alter data, concurrent reads are safe).
   - With $X$: **False** ($X$ has exclusive access to the entire subtree; no concurrent access is allowed).
2. **$IX$ Row:**
   - With $IS$: **True** (Symmetric with $IS \times IX$).
   - With $IX$: **True** (Two transactions updating different records in the same file can execute concurrently; conflicts on identical records are caught at the tuple level).
   - With $S$: **False** (An active writer below ($IX$) would cause unrepeatable reads or phantom phenomena for a transaction reading the whole subtree ($S$)).
   - With $SIX$: **False** ($SIX$ is reading the entire subtree; an independent $IX$ writer below conflicts with that broad read).
   - With $X$: **False** (Absolute exclusivity).
3. **$S$ Row:**
   - With $IS$: **True** (Both are read-only).
   - With $IX$: **False** (Cannot read the whole tree while someone is modifying records below).
   - With $S$: **True** (Concurrent readers of the whole tree).
   - With $SIX$: **False** ($SIX$ transaction is modifying records below; a pure $S$ lock would see inconsistent data).
   - With $X$: **False**.
4. **$SIX$ Row:**
   - With $IS$: **True** (Symmetric; incoming reader at lower level is compatible with $SIX$'s broad read).
   - With $IX, S, SIX, X$: **False** ($SIX$ holds an explicit $S$ lock on the whole node AND executes updates below, conflicting with any other writer or subtree reader).
5. **$X$ Row:**
   - **False for all modes** ($X$ requires unconditional, complete exclusivity).

## Multiple Granularity Locking Protocol Rules

To guarantee serializability and prevent hierarchical lock conflicts, every transaction $T_i$ must adhere to six mandatory operational rules:

1. **Matrix Compliance:** The $5 \times 5$ lock-compatibility matrix must be strictly observed.
2. **Root First:** The root of the hierarchy tree must be locked first, and it may be locked in any mode.
3. **Top-Down Rule for Shared Modes:** A node $Q$ can be locked by $T_i$ in $S$ or $IS$ mode only if the parent of $Q$ is currently locked by $T_i$ in either $IX$ or $IS$ mode.
4. **Top-Down Rule for Exclusive Modes:** A node $Q$ can be locked by $T_i$ in $X$, $SIX$, or $IX$ mode only if the parent of $Q$ is currently locked by $T_i$ in either $IX$ or $SIX$ mode.
5. **Two-Phase Locking (2PL) Rule:** A transaction $T_i$ cannot acquire any new lock after it has released any lock (growing phase followed by shrinking phase).
6. **Bottom-Up Unlock Rule:** A transaction $T_i$ can unlock a node $Q$ only if **none of the children of $Q$ are currently locked** by $T_i$.

```text
Lock Acquisition: TOP-DOWN (Root -> Area -> File -> Record)
==============================================================>
      [Database]  ----locks first---->  IS or IX
          |
       [Area]     ----locks next----->  IS or IX
          |
       [File]     ----locks next----->  IS or IX (or S/X)
          |
      [Record]    ----locks last----->  S or X

<==============================================================
Lock Release:     BOTTOM-UP (Record -> File -> Area -> Database)
```

## Walkthrough: Lock Sequences for Concurrent Queries

Consider File $F_a$ containing records $r_{a1}, r_{a2}, \dots, r_{an}$:

### Scenario 1: Reader and Writer on Different Records
- **Transaction $T_1$:** Reads record $r_{a2}$.
  1. Lock Database in $IS$ mode.
  2. Lock Area $A_1$ in $IS$ mode.
  3. Lock File $F_a$ in $IS$ mode.
  4. Lock Record $r_{a2}$ in $S$ mode.
- **Transaction $T_2$:** Modifies record $r_{a9}$.
  1. Lock Database in $IX$ mode (compatible with $T_1$'s $IS$).
  2. Lock Area $A_1$ in $IX$ mode (compatible with $T_1$'s $IS$).
  3. Lock File $F_a$ in $IX$ mode (compatible with $T_1$'s $IS$).
  4. Lock Record $r_{a9}$ in $X$ mode (no conflict, since $r_{a9} \neq r_{a2}$).
- **Verdict:** Both transactions execute concurrently with zero stalls!

### Scenario 2: Whole-Table Scan vs Record Modification
- **Transaction $T_3$:** Computes the total sum of all records in File $F_a$.
  1. Locks Database in $IS$ mode.
  2. Locks Area $A_1$ in $IS$ mode.
  3. Requests $S$-lock on File $F_a$.
- If $T_2$ currently holds an $IX$-lock on $F_a$, $T_3$'s request for an $S$-lock on $F_a$ is **BLOCKED** immediately at the file level by the compatibility matrix (`Held: IX, Requested: S` $\implies$ `False`). $T_3$ waits until $T_2$ commits without ever scanning individual records.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 18.6 · Multiple Granularity Locking Compatibility Matrix & Intention Lock Protocol

> **Source:** Silberschatz 7e · Chapter 18 (§18.3 & Practice Exercise 18.6)  
> **Exam Relevance:** High-Probability Unasked Syllabus Topic (RUET Syllabus Unit 4: Multiple Granularity Locking)  
> **Key Tested Concept:** Construction of the $5 \times 5$ compatibility matrix, intention lock rules, justification of $SIX$, and top-down vs bottom-up locking order.

**Problem Statement:**
> 1. Draw the complete $5 \times 5$ lock-compatibility matrix for the multiple granularity lock modes: $IS, IX, S, SIX, X$.
> 2. Explain why an intention-shared ($IS$) lock is compatible with a shared and intention-exclusive ($SIX$) lock, whereas an intention-exclusive ($IX$) lock is incompatible with an $SIX$ lock.
> 3. State why locks in the multiple-granularity protocol must be acquired in **top-down (root-to-leaf)** order and released in **bottom-up (leaf-to-root)** order.
> 4. Suppose transaction $T_1$ reads all records in relation $R$ and updates 2% of those records. Which lock should $T_1$ acquire on relation $R$, and which locks should it acquire on the modified records?

**Model Exam-Style Solution:**

1. **The $5 \times 5$ Lock Compatibility Matrix:**

| Requested Mode $\downarrow$ \ Held Mode $\rightarrow$ | $IS$ | $IX$ | $S$ | $SIX$ | $X$ |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$IS$** | **True** | **True** | **True** | **True** | False |
| **$IX$** | **True** | **True** | False | False | False |
| **$S$** | **True** | False | **True** | False | False |
| **$SIX$** | **True** | False | False | False | False |
| **$X$** | False | False | False | False | False |

2. **Compatibility Justification ($IS$ vs $IX$ with $SIX$):**
   - **$IS$ compatible with $SIX$ (`True`):** An $SIX$ lock on node $Q$ explicitly locks the entire subtree in shared ($S$) mode while allowing the holder to update items below. A transaction requesting $IS$ on $Q$ only intends to read specific records below. Since multiple readers do not conflict ($S \times S$ is compatible), the incoming reader ($IS$) can safely read any record not currently locked in $X$ mode by the $SIX$ transaction. Any record-level clash is caught at the tuple level.
   - **$IX$ incompatible with $SIX$ (`False`):** An $SIX$ lock is actively reading the entire subtree under an implicit shared lock. If another transaction were granted $IX$ on $Q$, it would proceed to write records below. This independent writer could modify records that the $SIX$ transaction is reading, causing unrepeatable reads or inconsistent states. Hence, $IX$ must be blocked.

3. **Justification of Top-Down Acquisition and Bottom-Up Release:**
   - **Top-Down Acquisition (Root-to-Leaf):** To lock node $Q$ at a fine granularity, intention locks must first be established on all ancestors of $Q$. If a transaction locked a child before locking the parent, an incoming transaction requesting a coarse-grained lock on the parent would see no intention lock and would mistakenly grant the parent lock, creating an undetected conflict with the child.
   - **Bottom-Up Release (Leaf-to-Root):** A transaction cannot unlock an ancestor node while it still holds locks on child nodes. If the parent were unlocked first, another transaction could immediately acquire an incompatible lock on the parent, invalidating the implicit locking guarantees on the active child locks.

4. **Optimal Locking Sequence for $T_1$ (Scan + 2% Updates):**
   - On the Database and Area nodes: $T_1$ acquires **$IX$ locks** (or $IS$).
   - On relation $R$: $T_1$ acquires a **$SIX$ (Shared and Intention-Exclusive) lock**.
     - *Benefit:* The explicit $S$ component of $SIX$ allows $T_1$ to scan all records without requesting millions of individual tuple-level $S$ locks.
   - On the 2% updated records: $T_1$ acquires individual **$X$ locks** on only those specific tuples. $\blacksquare$

**💡 RUET Exam Takeaway:**
When asked to design locks for a "read-all and update-few" transaction, the standard textbook answer is always the **$SIX$ lock on the table** and **$X$ locks on updated tuples**.

## ⚡ Exam Tips & Common Mistakes

1. **Remember the Top-Down / Bottom-Up Asymmetry:**
   - Lock Acquisition = **Top-Down** (Root $\to$ Leaf).
   - Lock Release = **Bottom-Up** (Leaf $\to$ Root).
   - Reversing either order breaks hierarchical synchronization and loses full marks.
2. **Matrix Symmetry:** The $5 \times 5$ multiple granularity compatibility matrix is completely **symmetric** ($\text{Matrix}[A, B] = \text{Matrix}[B, A]$). Double-check your table row vs column during exams.
3. **The Only `True` in the $SIX$ Row/Column:** Aside from the diagonal, $SIX$ is only compatible with **$IS$**. It conflicts with $IX, S, SIX,$ and $X$.
4. **Lock Escalation Definition:** Be ready to define lock escalation in 1–2 sentences: converting many fine-grained locks into a single coarse-grained lock when the lock manager's memory table is saturated.
