# T08.2: Functional Dependencies and Attribute Classification

> **Topic:** T08 — Normalization & Functional Dependencies | **Priority:** 🟢 Foundational | **Exam Frequency:** 0/7 finals (+ CT-03 Q1(b–c)) (4 marks)
> **Sources:** Silberschatz 7e Ch. 7 (§7.2, §7.2.2, pp. 308–312) · Lecture Deck 06 (Slides 14–17) · Raidah Class Notes (p. 20)

## Why This Topic Matters

Functional dependencies (FDs) form the formal mathematical language of relational schema design. Every normal form definition from 1NF through BCNF depends directly on recognizing different types of functional dependencies. In semester finals and class tests, RUET examiners test your ability to classify attributes into prime and non-prime sets and to distinguish full dependencies from partial and transitive dependencies (tested directly in CT-03 Q.01(b–c) for 4 marks). Mastering attribute classification is also a prerequisite for testing 2NF schemas (T08.7) and decomposing relations into 3NF and BCNF (T08.8 and T08.9).

---

## 📝 Key Definitions

> **Functional Dependency:** A functional dependency $\alpha \rightarrow \beta$ is a constraint between two attribute sets in a relation $R$. It states that for any two rows $t_1$ and $t_2$, if $t_1[\alpha] = t_2[\alpha]$, then $t_1[\beta] = t_2[\beta]$ must also hold. In simple terms, each value of $\alpha$ uniquely determines the value of $\beta$.

> **Trivial Functional Dependency:** A functional dependency $\alpha \rightarrow \beta$ is trivial if the right-hand side is a subset of the left-hand side ($\beta \subseteq \alpha$). Trivial dependencies are always true in every table and add no new constraint.

> **Full Functional Dependency:** An attribute set $Y$ is fully functionally dependent on $X$ if $X \rightarrow Y$ holds and no proper subset $A \subset X$ can determine $Y$ on its own ($A \nrightarrow Y$). Removing any attribute from $X$ breaks the dependency.

> **Partial Dependency:** A partial dependency happens when a non-prime attribute $Y$ depends on a proper subset $A \subset K$ of a composite candidate key $K$. Partial dependencies cause redundancy and violate Second Normal Form (2NF).

> **Transitive Dependency:** A transitive dependency happens when a candidate key $K$ determines a non-prime attribute $Y$ indirectly through another non-prime attribute $X$ ($K \rightarrow X$ and $X \rightarrow Y$, where $X \nrightarrow K$). Transitive dependencies violate Third Normal Form (3NF).

> **Prime Attribute:** A prime attribute is any attribute that belongs to at least one candidate key of the relation.

> **Non-Prime Attribute:** A non-prime attribute is any attribute that does not belong to any candidate key of the relation.

---

## Understanding Functional Dependencies

A functional dependency is an integrity constraint between two sets of attributes in a relational database. Think of it as a mathematical rule that says one column (or group of columns) uniquely predicts another.

Notation:

$$
X \rightarrow Y
$$

Read as:
- "$X$ functionally determines $Y$"
- "$Y$ is functionally dependent on $X$"

Here, $X$ is called the **determinant** (the input side), and $Y$ is called the **dependent** (the output side).

### Intuition: The Function Analogy

In mathematics, a function $y = f(x)$ maps each input $x$ to at most one output $y$. In a database table, $X \rightarrow Y$ works the exact same way. Whenever two rows have the exact same value for attribute set $X$, they must also have the exact same value for attribute set $Y$.

Consider the student table from Lecture Deck 06 (Slide 14):

| Student_ID | Student_Name | Department |
| :--- | :--- | :--- |
| S01 | Ferdous | CSE |
| S02 | Zaman | ETE |
| S03 | Nabila | ECE |

Here, $\text{Student\_ID} \rightarrow \text{Student\_Name}$ holds because each distinct ID maps to one name. If a new row arrives with ID `S01` and name `Kamal`, the rule is broken and the functional dependency is violated.

## Classification of Functional Dependencies

We can group functional dependencies into different categories based on set overlap, how much of a key they use, and whether they chain through other attributes.

```text
Functional Dependencies
├── By Set Containment
│   ├── Trivial FDs (Y ⊆ X)
│   ├── Non-Trivial FDs (X ∩ Y = ∅)
│   └── Semi-Trivial FDs (Y ⊈ X, but X ∩ Y ≠ ∅)
├── By Key Relationship
│   ├── Full Functional Dependency (Y depends on entire X, no subset suffices)
│   └── Partial Dependency (Non-prime Y depends on proper subset of composite key)
└── By Chain of Dependency
    └── Transitive Dependency (Key → Non-prime A → Non-prime B)
```

### 1. Trivial vs. Non-Trivial Functional Dependencies

#### A. Trivial Functional Dependency

Intuitively, if you already know a student's ID and Name, you obviously know their ID. Any rule where the output is just a piece of the input is called trivial. Formally, a functional dependency $X \rightarrow Y$ is trivial if the right-hand side is a subset of the left-hand side:

$$
Y \subseteq X
$$

Because a set of attributes always determines its own parts, trivial dependencies are automatically true in every table and tell us nothing new about real-world business rules.

**Examples:**
- $\{\text{StudentID}, \text{Name}\} \rightarrow \text{StudentID}$ (because $\text{StudentID} \in \{\text{StudentID}, \text{Name}\}$)
- $A \rightarrow A$
- $ABC \rightarrow AB$

#### B. Non-Trivial Functional Dependency

A functional dependency $X \rightarrow Y$ is completely non-trivial when the output gives us brand-new information not already sitting on the left-hand side. Formally, the determinant and dependent share no attributes in common:

$$
X \cap Y = \emptyset
$$

**Examples:**
- $\text{StudentID} \rightarrow \text{Name}$
- $\text{CourseID} \rightarrow \text{Credits}$

#### C. Semi-Trivial Functional Dependency

A functional dependency $X \rightarrow Y$ is semi-trivial if $Y$ repeats some attributes from $X$, while also determining at least one new attribute outside $X$:

$$
Y \nsubseteq X \quad \text{and} \quad X \cap Y \neq \emptyset
$$

**Example:**
- $\{A, B\} \rightarrow \{B, C\}$

Using Armstrong's decomposition rule, we can split this into $\{A, B\} \rightarrow B$ (which is trivial) and $\{A, B\} \rightarrow C$ (which is non-trivial).

---

### 2. Full vs. Partial Functional Dependencies

This distinction is the exact boundary between First Normal Form (1NF) and Second Normal Form (2NF). Intuitively, we want to know whether a non-key attribute needs the *entire* composite key to identify it, or if just a piece of the key is enough.

#### A. Full Functional Dependency

A functional dependency $X \rightarrow Y$ is a full functional dependency if every single attribute in $X$ is needed to determine $Y$. If you drop any attribute $A$ from $X$, the dependency breaks:

$$
(X - \{A\}) \not\rightarrow Y \quad \text{for every } A \in X
$$

**Example:**
In a student course registration schema:

$$
\{\text{StudentID}, \text{CourseID}\} \rightarrow \text{Grade}
$$

- `Grade` cannot be determined by `StudentID` alone, because one student takes many courses and earns different grades.
- `Grade` cannot be determined by `CourseID` alone, because many students take the same course and earn different grades.
- Since you need both attributes together to know the grade, `Grade` has a **full functional dependency** on the composite key.

#### B. Partial Functional Dependency

A dependency $X \rightarrow Y$ is a partial dependency if $Y$ is a non-prime attribute, $X$ is a composite candidate key, and $Y$ only needs a piece (a proper subset) of $X$ to be identified:

$$
\exists A \subset X \quad \text{such that} \quad A \rightarrow Y
$$

**Example:**
Suppose our composite key is $\{\text{StudentID}, \text{CourseID}\}$:

$$
\{\text{StudentID}, \text{CourseID}\} \rightarrow \text{StudentName}
$$

Here, we don't actually need `CourseID` to find a student's name, because:

$$
\text{StudentID} \rightarrow \text{StudentName}
$$

Because `StudentName` depends on `StudentID` alone (a proper subset of the composite key), this dependency is **partial**. Partial dependencies force the database to repeat a student's name for every course they take, so we must eliminate them to reach 2NF.

> [!IMPORTANT]
> A partial dependency can ONLY exist when a candidate key is composite (made of two or more attributes). If every candidate key in a table is a single attribute, you can't take a non-empty proper subset of it, so the table is automatically in 2NF!

---

### 3. Transitive Functional Dependencies

A transitive dependency happens when a candidate key determines a non-prime attribute indirectly through a chain, passing through another non-prime attribute in the middle.

#### Formal Definition

Given a relation $R$ with candidate key $K$, a functional dependency $K \rightarrow Z$ is transitive if there is an intermediate attribute set $Y$ such that:
1. $K \rightarrow Y$ holds
2. $Y \not\rightarrow K$ holds ($Y$ is not a candidate key or superkey)
3. $Y \rightarrow Z$ holds
4. $Z$ is a non-prime attribute outside both $Y$ and $K$

In plain course terms, a transitive dependency looks like a chain:

$$
\text{Candidate Key} \longrightarrow \text{Non-Prime Attribute } Y \longrightarrow \text{Non-Prime Attribute } Z
$$

**Example from Lecture Deck 06 (Slide 17):**
Consider the relation:

$$
\text{STUDENT}(\text{Student\_ID}, \text{Student\_Name}, \text{Dept\_ID}, \text{Department\_Name})
$$

With dependencies:
- $\text{Student\_ID} \rightarrow \text{Dept\_ID}$
- $\text{Dept\_ID} \rightarrow \text{Department\_Name}$

Here, the candidate key is $\{\text{Student\_ID}\}$, while both `Dept_ID` and `Department_Name` are non-prime attributes. Because `Student_ID` determines `Dept_ID`, and `Dept_ID` in turn determines `Department_Name`, we get the chain:

$$
\text{Student\_ID} \longrightarrow \text{Dept\_ID} \longrightarrow \text{Department\_Name}
$$

This is a **transitive dependency**. It causes update and insertion anomalies (for example, repeating the full department name for every student in that department) and must be removed to reach 3NF.

## Prime vs. Non-Prime Attributes

Before you can test a table for 2NF or 3NF, you have to sort every attribute into one of two groups: prime or non-prime.

```text
All Attributes in Relation Schema R
├── Prime Attributes (Union of all Candidate Keys)
└── Non-Prime Attributes (Attributes not in ANY Candidate Key)
```

### Classification Algorithm

1. **Step 1: Find All Candidate Keys.**
   Find every minimal superkey for relation $R$. Be careful not to stop at just one if the table has multiple candidate keys (such as $CK_1 = \{A, B\}$ and $CK_2 = \{B, C\}$).
2. **Step 2: Combine the Candidate Keys to Get Prime Attributes.**
   Take the union of all candidate keys:

$$
\text{Prime}(R) = \bigcup_{i} CK_i
$$

   Any attribute that appears in at least one candidate key is a **prime attribute**.
3. **Step 3: List the Remaining Attributes as Non-Prime.**
   Every other attribute in $R$ that never appears in any candidate key is a **non-prime attribute**:

$$
\text{NonPrime}(R) = R - \text{Prime}(R)
$$

### The Determinant Trap

A very common exam mistake is assuming that any attribute on the left-hand side of an arrow ($X \rightarrow Y$) is automatically a prime attribute.
- **Fact:** Being a determinant does NOT make an attribute prime!
- For example, in $\text{InstructorID} \rightarrow \text{InstructorName}$, `InstructorID` is a determinant. However, if `InstructorID` is not part of any candidate key of the table, it is still a **non-prime attribute**.

## Summary Comparison of Dependency Types

| Dependency Type | Mathematical Condition | Normal Form Violated | Solution |
| :--- | :--- | :--- | :--- |
| **Trivial** | $X \rightarrow Y$ where $Y \subseteq X$ | None (valid in all forms) | Retain (no action needed) |
| **Partial** | $A \rightarrow Y$ where $A \subset CK$ and $Y \in \text{NonPrime}$ | Violated in **1NF** (prevents 2NF) | Move $A$ and $Y$ into a separate table |
| **Transitive** | $Y \rightarrow Z$ where $Y, Z \in \text{NonPrime}$ and $CK \rightarrow Y$ | Violated in **2NF** (prevents 3NF) | Move $Y$ and $Z$ into a separate table |
| **Full** | $X \rightarrow Y$ and $\forall A \subset X, A \not\rightarrow Y$ | Satisfies **2NF** requirement | Keep together in table |

## Worked Example: Attribute Classification Drill

Consider a schema representing a hospital clinic:
$$
R(\text{P\_ID}, \text{D\_ID}, \text{Date}, \text{P\_Name}, \text{D\_Name}, \text{Diagnosis}, \text{Fee})
$$
With the following functional dependencies:
1. $\text{P\_ID} \rightarrow \text{P\_Name}$
2. $\text{D\_ID} \rightarrow \text{D\_Name}, \text{Fee}$
3. $\{\text{P\_ID}, \text{D\_ID}, \text{Date}\} \rightarrow \text{Diagnosis}$

### Step 1: Find the Candidate Key
Look at attributes that never appear on the right-hand side of any dependency:
- $\text{Date}$ never appears on the RHS.
- $\text{P\_ID}$ and $\text{D\_ID}$ never appear on the RHS of any dependency that does not already require them.
Compute the closure of $\{\text{P\_ID}, \text{D\_ID}, \text{Date}\}$:
$$
\begin{aligned}
\{\text{P\_ID}, \text{D\_ID}, \text{Date}\}^+ &= \{\text{P\_ID}, \text{D\_ID}, \text{Date}\} \cup \{\text{P\_Name}\} \cup \{\text{D\_Name}, \text{Fee}\} \cup \{\text{Diagnosis}\} \\
&= \{\text{P\_ID}, \text{D\_ID}, \text{Date}, \text{P\_Name}, \text{D\_Name}, \text{Diagnosis}, \text{Fee}\} = R
\end{aligned}
$$
No proper subset can determine $\text{Diagnosis}$.
Therefore, the unique Candidate Key is:
$$
CK = \{\text{P\_ID}, \text{D\_ID}, \text{Date}\}
$$

### Step 2: Classify Attributes
- **Prime Attributes:** $\{\text{P\_ID}, \text{D\_ID}, \text{Date}\}$ (members of the candidate key).
- **Non-Prime Attributes:** $\{\text{P\_Name}, \text{D\_Name}, \text{Diagnosis}, \text{Fee}\}$ (not in the candidate key).

### Step 3: Classify Dependencies
1. $\text{P\_ID} \rightarrow \text{P\_Name}$: **Partial Dependency**, because $\text{P\_ID}$ is a proper subset of the composite candidate key, and $\text{P\_Name}$ is non-prime.
2. $\text{D\_ID} \rightarrow \text{D\_Name}, \text{Fee}$: **Partial Dependency**, because $\text{D\_ID}$ is a proper subset of the composite candidate key, and $\text{D\_Name}, \text{Fee}$ are non-prime.
3. $\{\text{P\_ID}, \text{D\_ID}, \text{Date}\} \rightarrow \text{Diagnosis}$: **Full Functional Dependency**, because all three key attributes are strictly required to determine $\text{Diagnosis}$.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · CT-03 Q.01(b–c) · Prime/Non-Prime Attributes and Partial/Transitive Dependencies in ENROLLMENT

> **Appeared:** CT-03 Q.01(b–c) — (04 Marks)

**Question:**

Consider $\text{ENROLLMENT}(\text{StudentID}, \text{StudentName}, \text{CourseID}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade})$ with functional dependencies: $\text{StudentID} \rightarrow \text{StudentName}$; $\text{CourseID} \rightarrow \text{CourseName}, \text{InstructorID}$; $\text{InstructorID} \rightarrow \text{InstructorName}$; $(\text{StudentID}, \text{CourseID}) \rightarrow \text{Grade}$.  
**(b)** Identify the prime and non-prime attributes. `[02 Marks]`  
**(c)** Identify the partial and transitive dependencies. `[02 Marks]`

**Full Answer:**

#### Preliminary Step: Determine the Candidate Key

To classify prime and non-prime attributes, we first find the candidate keys of $\text{ENROLLMENT}$.

1. **Examine the Right-Hand Sides (RHS):**
   - $\text{StudentID}$ never appears on the RHS of any dependency.
   - $\text{CourseID}$ never appears on the RHS of any dependency.
   Therefore, both $\text{StudentID}$ and $\text{CourseID}$ must be present in every candidate key.

2. **Compute the Attribute Closure of $\{\text{StudentID}, \text{CourseID}\}$:**
$$
\begin{aligned}
\{\text{StudentID}, \text{CourseID}\}^+ &= \{\text{StudentID}, \text{CourseID}\} \\
&\quad \cup \{\text{StudentName}\} \quad (\text{via } \text{StudentID} \rightarrow \text{StudentName}) \\
&\quad \cup \{\text{CourseName}, \text{InstructorID}\} \quad (\text{via } \text{CourseID} \rightarrow \text{CourseName}, \text{InstructorID}) \\
&\quad \cup \{\text{InstructorName}\} \quad (\text{via } \text{InstructorID} \rightarrow \text{InstructorName}) \\
&\quad \cup \{\text{Grade}\} \quad (\text{via } (\text{StudentID}, \text{CourseID}) \rightarrow \text{Grade}) \\
&= \{\text{StudentID}, \text{CourseID}, \text{StudentName}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade}\}
\end{aligned}
$$

Because $\{\text{StudentID}, \text{CourseID}\}^+$ generates all attributes of the relation and no single attribute alone can generate all of them, the relation has exactly one Candidate Key:

$$
\text{Candidate Key} = \{\text{StudentID}, \text{CourseID}\}
$$

---

#### (b) Identify the Prime and Non-Prime Attributes

- **Prime Attributes:**
  Attributes that belong to at least one Candidate Key:
$$
\text{Prime Attributes} = \{\text{StudentID}, \text{CourseID}\}
$$

- **Non-Prime Attributes:**
  Attributes that do not belong to any Candidate Key:
$$
\text{Non-Prime Attributes} = \{\text{StudentName}, \text{CourseName}, \text{InstructorID}, \text{InstructorName}, \text{Grade}\}
$$

*Verification Check:* The relation has 7 attributes in total. Prime attributes (2) + Non-prime attributes (5) = 7 attributes. All attributes are partitioned correctly.

---

#### (c) Identify the Partial and Transitive Dependencies

- **Partial Dependencies:**
  A partial dependency occurs when a non-prime attribute depends functionally on a proper subset of the composite candidate key $\{\text{StudentID}, \text{CourseID}\}$:
  1. $\text{StudentID} \rightarrow \text{StudentName}$  
     *(The non-prime attribute $\text{StudentName}$ depends only on the key attribute $\text{StudentID}$)*
  2. $\text{CourseID} \rightarrow \text{CourseName}$  
     *(The non-prime attribute $\text{CourseName}$ depends only on the key attribute $\text{CourseID}$)*
  3. $\text{CourseID} \rightarrow \text{InstructorID}$  
     *(The non-prime attribute $\text{InstructorID}$ depends only on the key attribute $\text{CourseID}$)*

- **Transitive Dependencies:**
  A transitive dependency occurs when a non-prime attribute depends on another non-prime attribute:
$$
\text{InstructorID} \rightarrow \text{InstructorName}
$$
  **Explanation:** In this dependency, $\text{InstructorID}$ is a non-prime attribute, and $\text{InstructorName}$ is also a non-prime attribute. Through the candidate key, we have the indirect dependency chain:
$$
\{\text{StudentID}, \text{CourseID}\} \longrightarrow \text{CourseID} \longrightarrow \text{InstructorID} \longrightarrow \text{InstructorName}
$$
  Because $\text{InstructorName}$ depends on the key via the non-key attribute $\text{InstructorID}$, it is a transitive dependency.

*(Note: The dependency $(\text{StudentID}, \text{CourseID}) \rightarrow \text{Grade}$ is a **full functional dependency**, not a partial or transitive dependency, because it requires the complete composite key).*

## ⚡ Exam Tips & Common Mistakes

1. **Calculate the Candidate Key First:** Even if the question asks for prime and non-prime attributes directly (like part (b) in CT-03 Q.01), always show the candidate key derivation first. You cannot mathematically define prime attributes without establishing all candidate keys.
2. **Determinants Are Not Automatically Prime:** In CT-03 Q.01, many students mistakenly listed `InstructorID` as a prime attribute because it appears on the left side of $\text{InstructorID} \rightarrow \text{InstructorName}$. Remember: an attribute is prime IF AND ONLY IF it is part of a candidate key.
3. **Do Not Overlook Multiple Partial Dependencies:** When a composite key is split, check every dependency whose determinant is a subset. In CT-03 Q.01, $\text{CourseID} \rightarrow \text{CourseName}, \text{InstructorID}$ yields two distinct partial dependencies.
4. **Distinguish Full from Partial Dependencies:** The dependency $(\text{StudentID}, \text{CourseID}) \rightarrow \text{Grade}$ is a full dependency because dropping either attribute makes it impossible to determine the grade. Never list it as partial!
