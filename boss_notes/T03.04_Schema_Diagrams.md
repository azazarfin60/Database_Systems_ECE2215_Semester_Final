# T03.4: Schema Diagrams

> **Topic:** T03 — Relational Model, Keys & Integrity | **Priority:** 🟢 | **Exam Frequency:** 0/7 finals (+ CT-01 Q02) (05 marks)
> **Sources:** Silberschatz 7e Ch. 2 (§2.4, pp. 46–47) · Lecture Deck 02 (Slide 8) · CT-01 Q.02

## Why This Topic Matters

A relational schema diagram gives you a clean visual blueprint of an entire database at a glance. It shows every table as a box, lists its columns, underlines primary keys, and connects foreign keys to their parent tables using directed arrows. In RUET exams, drawing a schema diagram is a popular way to test whether you understand how tables link together through keys, and it appeared directly in CT-01 for 5 marks.

---

## 📝 Key Definitions

> **Schema Diagram:** A schema diagram is a visual blueprint of a relational database schema. It displays each relation as a rectangular box with the relation name in the header and all its attributes listed inside.

> **Foreign-Key Arrow Convention:** In a schema diagram, primary key attributes are underlined inside their relation box. Each foreign-key constraint is drawn as a directed arrow starting from the foreign key in the child relation and pointing to the primary key of the parent relation.

---

## Anatomy of a Relational Schema Diagram

### Intuitive Analogy: Why the Notation Works

When a database has five or ten tables, reading raw SQL `CREATE TABLE` statements makes it hard to see how tables connect. A schema diagram turns those text definitions into a wiring map. Underlining the primary key shows what uniquely identifies each row, and drawing an arrow from a foreign key to a primary key shows exactly which parent table validates that column's values.

In the Silberschatz textbook and lecture slides, every relational schema diagram is built from four simple parts:

1. **Relation Box:** Draw each table as a rectangular box with the table name written in bold in a top header section.
2. **Attribute List:** List all columns belonging to that table vertically inside the box.
3. **Primary Key Underline:** Underline every attribute that belongs to the primary key. If a table uses a composite primary key made of multiple columns, underline all of those columns.
4. **Directed Dependency Arrow:** Draw an arrow starting from a foreign key attribute in the child table and pointing to the primary key attribute in the parent table.

```text
+-----------------------+               +-----------------------+
|        Courses        |               |      Instructors      |
+-----------------------+               +-----------------------+
| course_id (PK)        |               | instructor_id (PK)    |
| title                 |               | name                  |
| instructor_id (FK) ---+-------------->| dept_name             |
| credits               |               | salary                |
+-----------------------+               +-----------------------+
```

### Key Rule: Which Way Does the Arrow Point?

The arrow direction in a relational schema diagram follows one strict rule:
- **Origin (Tail):** Starts at the foreign key attribute in the **referencing (child)** relation.
- **Destination (Head):** Points directly to the primary key attribute in the **referenced (parent)** relation.

Students frequently lose marks by drawing the arrow backward from parent to child. A simple way to remember the right direction is that the child foreign key "looks up to" the parent primary key for permission, so the arrow always points to the parent primary key.

---

## Schema Diagram vs. Entity-Relationship (ER) Diagram

It is very common to mix up relational schema diagrams with ER diagrams during a timed test. They represent different stages of database design and use completely different shapes:

| Feature | Relational Schema Diagram | Entity-Relationship (ER) Diagram |
| :--- | :--- | :--- |
| **Model Level** | Logical / Table-Level Relational Model | Conceptual Design Model |
| **Basic Shapes** | Rectangular boxes divided into header and column list | Rectangles (Entities), Diamonds (Relationships), Ovals (Attributes) |
| **Connections** | Directed arrows from child FK to parent PK | Lines connecting entities to relationship diamonds |
| **Attribute Display** | Listed as text rows inside the table box | Drawn as separate ovals attached to boxes or diamonds |
| **Keys** | Primary keys are underlined inside the box and foreign keys start arrows | Primary keys are underlined inside attribute ovals |
| **Exam Trap** | Drawing diamonds or ovals here costs you all marks | Drawing table column boxes here costs you all marks |

## The Standard University Schema Diagram

Both Silberschatz and Lecture Deck 02 (Slide 8) use the 11-table University database as their main reference schema. Notice how composite primary keys (such as in `section` and `takes`) have multiple underlined columns, and foreign keys are shown with $\rightarrow$ pointing to the referenced table:

1. **`classroom`** ($\underline{\text{building}}, \underline{\text{room\_number}}, \text{capacity}$)
2. **`department`** ($\underline{\text{dept\_name}}, \text{building}, \text{budget}$)
3. **`course`** ($\underline{\text{course\_id}}, \text{title}, \text{dept\_name}, \text{credits}$)
   - $\text{dept\_name} \rightarrow \text{department}(\text{dept\_name})$
4. **`instructor`** ($\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary}$)
   - $\text{dept\_name} \rightarrow \text{department}(\text{dept\_name})$
5. **`section`** ($\underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}}, \text{building}, \text{room\_number}, \text{time\_slot\_id}$)
   - $\text{course\_id} \rightarrow \text{course}(\text{course\_id})$
   - $(\text{building}, \text{room\_number}) \rightarrow \text{classroom}(\text{building}, \text{room\_number})$
6. **`teaches`** ($\underline{\text{ID}}, \underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}}$)
   - $\text{ID} \rightarrow \text{instructor}(\text{ID})$
   - $(\text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}) \rightarrow \text{section}(\dots)$
7. **`student`** ($\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{tot\_cred}$)
   - $\text{dept\_name} \rightarrow \text{department}(\text{dept\_name})$
8. **`takes`** ($\underline{\text{ID}}, \underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}}, \text{grade}$)
   - $\text{ID} \rightarrow \text{student}(\text{ID})$
   - $(\text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}) \rightarrow \text{section}(\dots)$
9. **`advisor`** ($\underline{\text{s\_id}}, \text{i\_id}$)
   - $\text{s\_id} \rightarrow \text{student}(\text{ID})$
   - $\text{i\_id} \rightarrow \text{instructor}(\text{ID})$
10. **`time\_slot`** ($\underline{\text{time\_slot\_id}}, \underline{\text{day}}, \underline{\text{start\_time}}, \text{end\_time}$)
11. **`prereq`** ($\underline{\text{course\_id}}, \underline{\text{prereq\_id}}$)
    - $\text{course\_id} \rightarrow \text{course}(\text{course\_id})$
    - $\text{prereq\_id} \rightarrow \text{course}(\text{course\_id})$

## Worked Example: Banking Mini-Schema (`Branch`, `Account`, `Depositor`)

Before tackling the 5-table ECE department problem in the Golden Questions section, let us walk through a quick 3-table banking schema to see how you turn relational schemas into a box-and-arrow diagram.

### Step 1: Write Down the Relations and Underline Primary Keys
Suppose we want to model bank branches, customer accounts, and which customer owns which account:
- $\text{Branch}(\underline{\text{branch\_name}}, \text{branch\_city}, \text{assets})$
- $\text{Account}(\underline{\text{account\_number}}, \text{branch\_name}, \text{balance})$
- $\text{Depositor}(\underline{\text{customer\_id}}, \underline{\text{account\_number}})$

### Step 2: Trace the Foreign Key Arrows
- In `Account`, `branch_name` is a foreign key pointing to `Branch(branch_name)`.
- In `Depositor`, `account_number` is part of a composite primary key, and it also acts as a foreign key pointing to `Account(account_number)`.

### Step 3: Sketch the Boxes and Arrows

```text
+--------------------+      +--------------------+      +--------------------+
|     Depositor      |      |      Account       |      |       Branch       |
+--------------------+      +--------------------+      +--------------------+
| customer_id (PK)   |      | account_number(PK)<+--+   | branch_name (PK)  <+--+
| account_number(PK)-+--+   | branch_name (FK) --+--+-->| branch_city        |  |
+--------------------+  |   | balance            |  |   | assets             |  |
                        +-->+--------------------+  +---+--------------------+--+
```

Notice how each arrow starts at the foreign key column in the referencing table (`Depositor` or `Account`) and lands squarely on the underlined primary key in the parent table (`Account` or `Branch`).

### 🎯 LQ1 · University 4-Table Core Schema Diagram

**Question:**
Draw a relational schema diagram for a university database consisting of `Department`, `Instructor`, `Course`, and `Section`. Clearly indicate primary keys and foreign key constraints.

**Answer:**

#### 1. Relational Schemas
- $\text{Department}(\underline{\text{dept\_name}}, \text{building}, \text{budget})$
- $\text{Instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$
  - $\text{dept\_name} \rightarrow \text{Department}(\text{dept\_name})$
- $\text{Course}(\underline{\text{course\_id}}, \text{title}, \text{dept\_name}, \text{credits})$
  - $\text{dept\_name} \rightarrow \text{Department}(\text{dept\_name})$
- $\text{Section}(\underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}}, \text{building}, \text{room\_number})$
  - $\text{course\_id} \rightarrow \text{Course}(\text{course\_id})$

#### 2. Schema Diagram Structure
- Draw four rectangular boxes labeled with the relation names.
- Underline primary key attributes: `dept_name` in `Department`, `ID` in `Instructor`, `course_id` in `Course`, and composite key `(course_id, sec_id, semester, year)` in `Section`.
- Connect arrows pointing from:
  - `Instructor.dept_name` $\rightarrow$ `Department.dept_name`
  - `Course.dept_name` $\rightarrow$ `Department.dept_name`
  - `Section.course_id` $\rightarrow$ `Course.course_id`

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 2.13 · Relational Schema Diagram for Banking Database

> **Source:** Silberschatz 7e · Chapter 2 (Exercise 2.13)  
> **Exam Relevance:** High-Probability Exam Diagram Question (CT-01 & Finals)  
> **Key Tested Concept:** Visual schema diagrams: relation boxes, underlined primary keys, and foreign-key reference arrows.

**Problem Statement:**
> Construct a formal **Relational Schema Diagram** for the classic bank database containing the following relations:
> - $\text{branch}(\underline{\text{branch\_name}}, \text{branch\_city}, \text{assets})$
> - $\text{customer}(\underline{\text{customer\_id}}, \text{customer\_name}, \text{customer\_street}, \text{customer\_city})$
> - $\text{account}(\underline{\text{account\_number}}, \text{branch\_name}, \text{balance})$
> - $\text{loan}(\underline{\text{loan\_number}}, \text{branch\_name}, \text{amount})$
> - $\text{depositor}(\underline{\text{customer\_id}, \text{account\_number}})$
> - $\text{borrower}(\underline{\text{customer\_id}, \text{loan\_number}})$

**Model Exam-Style Solution:**

1. **Schema Diagram Conventions:**
   - Each relation is represented by a named rectangular box with its attributes listed inside.
   - Primary keys are explicitly **underlined**.
   - Foreign-key constraints are indicated by directed arrows originating from the foreign key attribute and pointing directly to the referenced primary key attribute in the parent table.

2. **Schema Diagram:**

![Relational Schema Diagram for Bank Database](diagrams/T03.04_bank_schema_diagram__TB_fig_02_18.jpg)
*Figure 4: Schema Diagram for the Bank Database (Silberschatz 7e Fig. 2.18).*

3. **Key Referential Integrity Invariants:**
   - `account.branch_name` $\rightarrow$ `branch.branch_name`
   - `loan.branch_name` $\rightarrow$ `branch.branch_name`
   - `depositor.customer_id` $\rightarrow$ `customer.customer_id`
   - `depositor.account_number` $\rightarrow$ `account.account_number`
   - `borrower.customer_id` $\rightarrow$ `customer.customer_id`
   - `borrower.loan_number` $\rightarrow$ `loan.loan_number` $\blacksquare$

**💡 RUET Exam Takeaway:**
In schema diagrams, arrowheads must point to the **referenced primary key**, NOT the other way around. Examiners deduct marks if the arrow points from parent to child.

## ⚡ Exam Tips & Common Mistakes

1. **Do Not Draw an ER Diagram:** When an exam asks for a "schema diagram", never draw diamonds, entity boxes with connected attribute ovals, or cardinality ratios ($1:N$). Draw rectangular table boxes with column names listed inside.
2. **Underline Primary Keys:** Every table box must have its primary key attribute(s) clearly underlined. Omitting the underline loses key constraint marks.
3. **Double-Headed Arrows for Non-PK Referential Integrity:** Silberschatz uses single-headed arrows for foreign keys that point to primary keys. If a referential integrity constraint points to a non-primary key attribute, Silberschatz uses a two-headed arrow.
4. **Arrow Direction Trap:** Arrows always flow from child foreign key to parent primary key. Do not draw them backward.
