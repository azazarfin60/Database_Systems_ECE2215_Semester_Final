# T06.4: SQL Views — Benefits and CREATE VIEW

> **Topic:** T06 — Joins & Views | **Priority:** 🟢 Foundation | **Exam Frequency:** 1/7 finals (6 marks) [2023 Q.5(a), 2023 Q.5(b)]  
> **Sources:** Silberschatz 7e Ch. 4 (§4.2.1, §4.2.2) · Lecture Deck 04 (Slides 24–28) · Raidah Notes (pp. 3, 11, 18) · Fahim Notes (pp. 58–59)

## Why This Topic Matters

Views are a core part of the ANSI/SPARC three-level database architecture because they define external schemas that give different users customized, secure access to data. In RUET exams, views show up both as short theory questions and as practical SQL query problems. For instance, in 2023 Q.5(a) and Q.5(b), examiners tested the benefits of views and asked for a multi-table `CREATE VIEW` query worth 6 marks total. Once you understand how views support logical data independence and know the `CREATE VIEW` syntax, these questions are straightforward marks.

---

## 📝 Key Definitions

> **View (Virtual Relation):** A view is a virtual table defined by a saved SQL query rather than stored as physical rows on disk. It is not part of the physical storage layout, but users can query it just like a regular table. Every time a view is queried, the database computes its rows dynamically from the underlying base tables.

> **View Definition:** You create a view in SQL using the command `CREATE VIEW v AS <query expression>;`, where `v` is the view name and `<query expression>` is any valid `SELECT` query. The database saves only this query text in the system catalog and runs it on demand.

> **Logical Data Independence:** Logical data independence is the ability to change the logical schema of base tables without rewriting external views or application programs. If an administrator splits or restructures base tables, updating the view definition keeps existing user queries working without change.

---

## Core Concepts: What is a View?

Think of a view as a saved lens over your tables rather than a new copy of the data. When you create a view, you are simply giving a name to a `SELECT` query so you can treat its result like a regular table.

### 1. Stored Definition vs. Physical Storage
In a standard relational database, a view does not store a duplicate copy of rows on disk. Instead, the system catalog stores only the `SELECT` query that defines the view. Whenever a user or application queries that view, the database engine substitutes the saved query into the user's statement and computes the result on the fly.

### 2. View vs. Physical Table
- **Physical Table (`CREATE TABLE`):** Allocates disk space for rows and indexes, and writes every update directly to storage.
- **Virtual View (`CREATE VIEW`):** Uses zero disk space for row data because it is recalculated on demand every time you query it.
- **Snapshot Table (`CREATE TABLE ... AS SELECT`):** Computes the query once and writes the resulting rows to disk at creation time. Because it is a separate static copy, it goes stale as soon as the original tables change, whereas a virtual view always shows the latest live data.

### 3. Views vs. Common Table Expressions (WITH Clause)
- A **view** is a permanent schema object stored in the database catalog. Once created, it stays available to all authorized users until someone removes it with `DROP VIEW`.
- A **Common Table Expression (CTE)** defined with `WITH` is temporary and exists only for the duration of a single SQL statement.

---

## Key Benefits of Database Views

### 1. Security and Access Control
Views let administrators control access down to specific columns and rows:
- **Column-level security:** You can create a view that shows employee names and job titles while hiding sensitive columns like salary or national ID numbers.
- **Row-level security:** You can give a department head access to a view that filters rows with a `WHERE` clause so they only see employees in their own department.

### 2. Query Simplicity
Views hide complex SQL logic behind a clean, simple table name. Even if the underlying query joins four tables and computes several aggregates, users can query the view with a simple one-liner:

```sql
SELECT * FROM high_performing_departments;
```

### 3. Logical Data Independence
Views shield application code from structural changes in the underlying base tables. For example, if a database administrator splits a large table into two smaller normalized tables, they can create a view with the original table's name that joins those two new tables together. Existing applications can keep querying that view name without any code changes.

### 4. Consistent and Standardized Calculations
When business formulas (such as net pay after tax, profit margins, or student CGPA) are written once inside a view definition, everyone queries the exact same logic. This prevents different departments from accidentally using slightly different formulas in their reports.

### 5. Customized Data Presentation
Different teams often need different slices of the same underlying data. For instance, academic advisors need to see student course histories, while the accounts office only needs tuition payment records. Views let each group work with a tailored table layout without duplicating the underlying records.

## SQL CREATE VIEW Syntax and Patterns

### 1. Basic Syntax
```sql
CREATE VIEW view_name AS
SELECT column1, column2, ...
FROM table_name
WHERE condition;
```

### 2. Explicit Column Naming
When your view's `SELECT` list includes arithmetic expressions or aggregate functions like `SUM()` and `AVG()`, those output columns do not have natural table column names. You can name them cleanly right after the view name in parentheses:

```sql
CREATE VIEW dept_salary_summary (dept_name, total_salary, avg_salary) AS
SELECT dept_name, SUM(salary), AVG(salary)
FROM instructor
GROUP BY dept_name;
```

### 3. Multi-Table Join Views
Views often join several related tables so users do not have to write the join conditions repeatedly:

```sql
CREATE VIEW faculty_courses AS
SELECT instructor.ID, instructor.name, course.title, section.semester, section.year
FROM instructor
JOIN teaches ON instructor.ID = teaches.ID
JOIN section ON teaches.course_id = section.course_id 
            AND teaches.sec_id = section.sec_id
            AND teaches.semester = section.semester 
            AND teaches.year = section.year
JOIN course ON section.course_id = course.course_id;
```

### 4. Dropping a View
To remove a view definition from the database catalog, use `DROP VIEW`:

```sql
DROP VIEW view_name;
```
*(Dropping a view deletes only the saved query definition from the catalog. It never deletes any rows from the underlying base tables.)*

## Worked Example: Creating a Filtered Join View

### Scenario
Suppose a university database has two tables:
- `Student(Roll, Name, DeptID)`
- `Result(Roll, CGPA)`

We want to create a view named `Dean_List_ECE` that shows the `Roll`, `Name`, and `CGPA` of all students in `'ECE'` whose `CGPA` is at least `3.75`.

### Step 1: Write the `CREATE VIEW` Query
We join `Student` and `Result` on `Roll`, filter for `DeptID = 'ECE'` and `CGPA >= 3.75`, and wrap the query inside `CREATE VIEW`:

```sql
CREATE VIEW Dean_List_ECE AS
SELECT S.Roll, S.Name, R.CGPA
FROM Student S
JOIN Result R ON S.Roll = R.Roll
WHERE S.DeptID = 'ECE' AND R.CGPA >= 3.75;
```

### Step 2: Trace the Output on Sample Rows
If `Student` and `Result` contain:
- `(211001, 'Nadia', 'ECE', 3.82)` -> Matches both `'ECE'` and `3.82 >= 3.75` (**Included**)
- `(211002, 'Farhan', 'ECE', 3.60)` -> Fails `3.60 >= 3.75` (Excluded)
- `(211003, 'Tariq', 'CSE', 3.90)` -> Fails `DeptID = 'ECE'` (Excluded)

Querying `SELECT * FROM Dean_List_ECE;` returns only Nadia's row, and if Farhan's CGPA is later updated to `3.78` in `Result`, he will automatically appear the next time `Dean_List_ECE` is queried.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.5(a) · Benefits of VIEW in Database Systems

> **Appeared:** 2023 Q.5(a) — (3 marks)

**Question:**

What are the benefits of VIEW?

**Full Answer:**

A **view** is a virtual relation defined by an SQL query. The DBMS stores the query specification rather than physical tuples on disk.

The four primary benefits of using views in database systems are:

1. **Security and Access Control:** Views restrict user visibility to specific columns and rows. Administrators can expose general employee data while concealing confidential columns such as salaries or social security numbers.
2. **Query Simplicity:** Views encapsulate complicated SQL statements involving multiple joins, unions, and aggregate computations. Users can query the simplified virtual table using basic `SELECT * FROM view_name` syntax.
3. **Logical Data Independence:** When physical base tables undergo structural modifications (such as splitting or renaming tables), altering only the view definition allows external client applications to continue operating without disruption.
4. **Data Standardization and Consistency:** Standard business expressions and formulas are coded once in the view definition. This ensures that every department and report retrieves identical, reliable results.

#### Approach 1: Direct SQL Query on Given Tables (E, D, S)
The provided data relations are **E**, **D**, and **S**. Note that attribute `Department ID` in table **E** contains a whitespace and is delimited by backticks:

```sql
CREATE VIEW High_Salary_Employees AS
SELECT E.EmployeeName, D.DepartmentName, S.Salary
FROM E
JOIN D ON E.`Department ID` = D.DepartmentID
JOIN S ON E.EmployeeID = S.EmployeeID
WHERE S.Salary > 55000;
```

#### Approach 2: Query Under Standard University/Enterprise Schema
If assuming a consolidated schema `Employee(EmployeeID, EmployeeName, DeptID, Salary)` and `Department(DeptID, DepartmentName)`:

```sql
CREATE VIEW High_Salary_Employees AS
SELECT Employee.EmployeeName, Department.DepartmentName, Employee.Salary
FROM Employee
JOIN Department ON Employee.DeptID = Department.DeptID
WHERE Employee.Salary > 55000;
```

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 4.6 · Defining Complex Aggregated Views & Query Rewriting

> **Source:** Silberschatz 7e · Chapter 4 (Exercise 4.6)  
> **Exam Relevance:** High-Probability Views Implementation Drill  
> **Key Tested Concept:** Defining views with aggregation and conditional expressions, and understanding view substitution / query rewriting.

**Problem Statement:**
> Using the university database relations:
> - $\text{student}(\underline{\text{ID}}, \text{name}, \text{dept\_name})$
> - $\text{takes}(\underline{\text{ID}, \text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}}, \text{grade})$
> - $\text{course}(\underline{\text{course\_id}}, \text{title}, \text{dept\_name}, \text{credits})$
> Assume letter grades map to grade points: `'A'`=4, `'B'`=3, `'C'`=2, `'D'`=1, `'F'`=0.
> 1. Write an SQL DDL statement to define a view `student_grades(ID, name, GPA)` that computes each student's GPA. If a student has taken no courses, GPA should be `NULL`.
> 2. Write a query against this view to find all students whose GPA is greater than 3.5.
> 3. Show how the database engine rewrites the query on the view into an equivalent query on the underlying base tables.

**Model Exam-Style Solution:**

1. **View Definition:**
```sql
CREATE VIEW student_grades AS
SELECT 
    s.ID,
    s.name,
    ROUND(
        SUM(
            CASE t.grade
                WHEN 'A' THEN 4.0
                WHEN 'B' THEN 3.0
                WHEN 'C' THEN 2.0
                WHEN 'D' THEN 1.0
                ELSE 0.0
            END * c.credits
        ) / SUM(c.credits),
        2
    ) AS GPA
FROM student s
LEFT JOIN takes t ON s.ID = t.ID
LEFT JOIN course c ON t.course_id = c.course_id
GROUP BY s.ID, s.name;
```

2. **Query Against the View:**
```sql
SELECT ID, name, GPA
FROM student_grades
WHERE GPA > 3.5;
```

3. **Query Rewriting (View Expansion by the Query Processor):**
   - The query processor expands the view definition into a derived table (inline view) in the `FROM` clause:
```sql
SELECT ID, name, GPA
FROM (
    SELECT 
        s.ID,
        s.name,
        ROUND(
            SUM(
                CASE t.grade
                    WHEN 'A' THEN 4.0
                    WHEN 'B' THEN 3.0
                    WHEN 'C' THEN 2.0
                    WHEN 'D' THEN 1.0
                    ELSE 0.0
                END * c.credits
            ) / SUM(c.credits),
            2
        ) AS GPA
    FROM student s
    LEFT JOIN takes t ON s.ID = t.ID
    LEFT JOIN course c ON t.course_id = c.course_id
    GROUP BY s.ID, s.name
) AS inline_student_grades
WHERE GPA > 3.5;
```
   - *Optimization Note:* Alternatively, the query optimizer pushes the predicate `HAVING GPA > 3.5` into the aggregated query directly. $\blacksquare$

**💡 RUET Exam Takeaway:**
Views are virtual relations; they store **only the query definition**, not the physical data. When queried, the DBMS substitutes the view definition directly into the execution tree.

## ⚡ Exam Tips & Common Mistakes

1. **Strict Inequality Trap:** Notice whether the question says "more than 55,000" or "at least 55,000". "More than 55,000" requires `> 55000`, which excludes Alice (\$55,000). Writing `>= 55000` loses marks.
2. **Backticks for Attributes with Spaces:** In table **E**, the column is printed as `Department ID`. In MySQL, column names containing spaces must be enclosed in backticks (`` `Department ID` ``).
3. **Project Only Requested Attributes:** The prompt specifically asks for `EmployeeName, DepartmentName and salary`. Do not write `SELECT *`.
4. **Virtual Nature:** Never say views duplicate table data on disk. State clearly that views store the query definition in the data dictionary.
