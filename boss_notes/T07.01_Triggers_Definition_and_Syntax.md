# T07.1: SQL Triggers — Definition, Purpose, and Syntax

> **Topic:** T07 — Triggers and Stored Procedures | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (9 marks)  
> **Sources:** Silberschatz 7e Ch. 5 (§5.3) · Fahim Handnote (p. 59, 60, 62) · (No lecture slides for Unit 4 advanced SQL)

## Why This Topic Matters

Triggers let a database react automatically whenever rows are inserted, updated, or deleted, without waiting for an application program to call a function. In RUET finals, this topic appeared in both 2018 and 2020 for a total of 9 marks, and both papers asked the exact same three-part question: define triggering, list the purposes of triggers, and write the SQL syntax for creating one. Once you know the Event-Condition-Action (ECA) model, the `OLD` and `NEW` row variables, and the MySQL `CREATE TRIGGER` template, you can answer any variant of this question effortlessly.

---

## 📝 Key Definitions

> **Trigger:** "A trigger is a statement that the system executes automatically as a side effect of a modification to the database."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §5.3 (p. 206)

> **Triggering:** *(Course definition)* The automatic process where the database engine detects a table modification event (`INSERT`, `UPDATE`, or `DELETE`), checks its trigger condition, and runs the associated trigger action.

> **Event-Condition-Action (ECA) Model:** "To design a trigger mechanism, we must: Specify when a trigger is to be executed. This is broken up into an **event** that causes the trigger to be checked and a **condition** that must be satisfied for trigger execution to proceed. Specify the **actions** to be taken when the trigger executes."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §5.3 (p. 206)

> **Transition Variables (`OLD` and `NEW`):** *(Course definition)* Special row references available inside a row-level trigger that hold a snapshot of the row before the change (`OLD`) and after the change (`NEW`).

---

## The Event-Condition-Action (ECA) Framework

Think of a trigger as an automatic "if-this-happens-then-do-that" rule living inside the database. Formally, every trigger follows the **Event-Condition-Action (ECA)** model:

1. **Event:** The data change statement (`INSERT`, `UPDATE`, or `DELETE`) on a specific table that wakes the trigger up.
2. **Condition:** An optional `IF` check or `WHERE` filter evaluated when the event happens. If the check is true, the trigger runs its action. If it is false, the database skips the action and moves on.
3. **Action:** The procedural SQL statements that run automatically when the condition holds. An action might validate values, write an audit log entry into another table, or block the transaction with an error.

```text
[ DML Event Occurs ] ──> ( INSERT | UPDATE | DELETE on Table )
                               │
                               ▼
[ Check Condition ]   ──> Is the condition met? (e.g., IF NEW.stock < 0)
                               │
                     ┌─────────┴─────────┐
                    YES                  NO
                     │                   │
                     ▼                   ▼
            [ Execute Action ]      [ Ignore / Finish ]
            (Run SQL Statements)
```

## Trigger Mechanics: Timing, Events, and Granularity

When you write a trigger, you make three design choices: *when* it fires (`BEFORE` or `AFTER`), *which operation* activates it (`INSERT`, `UPDATE`, or `DELETE`), and *how many times* it runs (`FOR EACH ROW` or once per statement).

### 1. Trigger Timing: `BEFORE` vs `AFTER`

- **`BEFORE` Triggers:** Fire *before* the database writes the row change to the table. Use `BEFORE` triggers when you want to clean up incoming values, fill in default fields, or reject invalid updates before bad data ever touches the disk.
- **`AFTER` Triggers:** Fire *after* the table change has succeeded. Use `AFTER` triggers when you need to record an audit log, update a summary table, or queue a follow-up task based on a completed change.

### 2. Trigger Events and Transition Variables

Inside a row-level trigger, you often need to compare the old value of a column against the new value being written. SQL gives you two special row qualifiers, `OLD.column_name` and `NEW.column_name`, whose availability depends on the event:

| Trigger Event | Available Qualifiers | Why This Rule Makes Sense |
| :--- | :---: | :--- |
| **`INSERT`** | `NEW` only | You are inserting a brand-new row. Because no row existed before this operation, `OLD` does not exist. |
| **`UPDATE`** | Both `OLD` and `NEW` | You are changing an existing row, so `OLD` holds the values before the update and `NEW` holds the updated values. |
| **`DELETE`** | `OLD` only | You are removing an existing row. Because the row is gone after deletion, `NEW` does not exist. |

### 3. Trigger Granularity: Row-Level vs Statement-Level

- **Row-Level (`FOR EACH ROW`):** The trigger body runs once for every single row affected by the triggering SQL statement. For example, if an `UPDATE` modifies 50 rows, a `FOR EACH ROW` trigger executes 50 times.
- **Statement-Level:** The trigger body runs just once for the entire SQL statement, whether that statement updates zero rows or a million rows. (Note that MySQL 8 supports only row-level `FOR EACH ROW` triggers.)

## Core Purposes of Database Triggers

When a RUET exam asks for the purposes of using triggers, highlight these four practical use cases:

1. **Enforcing Complex Business Rules:** Standard table constraints like `CHECK` and `FOREIGN KEY` can only check simple rules on a single row or foreign key match. Triggers can enforce multi-table business rules, such as checking that a student does not register for more than 24 total credits across all enrolled sections in a semester.
2. **Auditing and Security Tracking:** Triggers can automatically build tamper-evident audit logs. Whenever someone updates a sensitive table, an `AFTER` trigger can record who made the change (`USER()`), when it happened (`NOW()`), and both the `OLD` and `NEW` values in a separate audit table.
3. **Keeping Derived and Summary Data in Sync:** Triggers can maintain precalculated totals automatically. For example, whenever a new item is inserted into `order_items`, a trigger can add its price to the `total_amount` column in the parent `orders` table.
4. **Automating Workflows and Restock Alerts:** When product stock drops below a reorder point after an update, a trigger can automatically insert a restock request into a `reorders` or notification queue table.

---

## When Not to Use Triggers

In §5.3.3, Silberschatz points out that triggers should be used carefully because overusing them creates several headaches:

1. **Cascading Triggers and Infinite Loops:** One trigger's action can update a second table, which fires a second trigger, which updates a third table, and so on. If a poorly designed chain loops back to the first table, it creates an infinite loop until the DBMS aborts the query.
2. **Hidden "Invisible" Logic:** Because triggers run silently in the background, an application developer running a simple `UPDATE` might have no idea that a trigger is also modifying three other tables behind the scenes, making bugs hard to trace.
3. **Backup and Replication Trouble:** When you reload data from a backup file or replicate rows from a primary server to a replica, you usually do not want triggers firing all over again and creating duplicate audit logs or double-deducting inventory.
4. **Slow Bulk Updates:** Because row-level triggers run once per row, a bulk `UPDATE` on 1,000,000 rows will run the trigger body 1,000,000 times inside that transaction, holding row locks much longer than usual.

## MySQL 8 Trigger Syntax

### The MySQL Delimiter Requirement

In MySQL client tools, the default statement terminator is the semicolon (`;`). Because a trigger body contains multiple statements ending with semicolons, you must temporarily redefine the statement delimiter using `DELIMITER //`. This prevents the client from cutting the definition short before the closing `END`.

### Complete Syntax Template

```sql
DELIMITER //

CREATE TRIGGER trigger_name
{ BEFORE | AFTER } { INSERT | UPDATE | DELETE }
ON target_table
FOR EACH ROW
BEGIN
    -- Declarations and procedural logic
    -- Access column values using OLD.col_name and NEW.col_name
    -- Abort execution and rollback using SIGNAL
END //

DELIMITER ;
```

- `CREATE TRIGGER trigger_name`: Assigns a unique identifier to the trigger.
- `BEFORE | AFTER`: Selects whether logic runs before data modification or after data modification.
- `INSERT | UPDATE | DELETE`: Identifies the activating table operation.
- `ON target_table`: Identifies the monitored table.
- `FOR EACH ROW`: Declares a row-level trigger.
- `BEGIN ... END`: Groups compound SQL statements into a single block.

## Worked Example (Salary Validation Trigger)

### Scenario
An enterprise database must enforce that no employee receives a salary decrease, and that salary increases cannot exceed 50% in a single update.

```sql
DELIMITER //

CREATE TRIGGER trg_validate_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    -- Check 1: Prevent salary reduction
    IF NEW.salary < OLD.salary THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Salary reductions are prohibited by policy.';
    END IF;

    -- Check 2: Prevent excessive salary increase
    IF NEW.salary > (OLD.salary * 1.50) THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Single salary increase cannot exceed 50%.';
    END IF;
END //

DELIMITER ;
```

### Execution Trace
1. Current tuple: `(emp_id: 101, salary: 50000)`.
2. Client executes: `UPDATE employees SET salary = 45000 WHERE emp_id = 101;`.
3. The `BEFORE UPDATE` trigger fires.
4. The condition `NEW.salary (45000) < OLD.salary (50000)` evaluates to true.
5. The engine executes `SIGNAL SQLSTATE '45000'`.
6. The update is rolled back. The database table remains completely unchanged.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.8(a) / 2020 Q.8(a) · Definition, Purposes, and Syntax of Triggers

> **Appeared:** 2018 Q.8(a) (5 marks), 2020 Q.8(a) (4 marks)

**Question:**

*(2018 Q.8(a))*  
What is triggering? What are the purposes of using trigger? Write the syntax for creating trigger?

*(2020 Q.8(a))*  
What is triggering? What are the purposes of using triggering? Write the syntax for creating a trigger.

**Full Answer:**

#### 1. Definition of Trigger and Triggering

A **trigger** is a stored SQL program stored in the database that executes automatically in response to a specified modification event (`INSERT`, `UPDATE`, or `DELETE`) on a particular table or view.

**Triggering** is the automatic process by which the database management system detects the event, evaluates the associated condition, and executes the specified action statements.

Triggers are governed by the **Event-Condition-Action (ECA)** framework:
- **Event:** A database modification that activates the trigger mechanism.
- **Condition:** An optional boolean check evaluated when the event occurs.
- **Action:** The SQL statements executed if the condition is satisfied.

#### 2. Purposes of Using Triggers

1. **Enforcing Complex Business Rules:** Triggers enforce integrity constraints spanning multiple tables that declarative constraints (`CHECK`, `FOREIGN KEY`) cannot express.
2. **Automated Auditing and Security:** Triggers log sensitive data modifications into dedicated audit tables, recording the modified data, user identity, and timestamp.
3. **Maintaining Derived and Aggregate Data:** Triggers keep calculated values synchronized across tables, such as updating account balances or total student credits automatically.
4. **Automating Workflow Tasks:** Triggers create automated alerts, populate notification queues, or insert restock orders when inventory levels fall below safety thresholds.

#### 3. Syntax for Creating a Trigger (MySQL 8)

**General Template:**

```sql
DELIMITER //

CREATE TRIGGER trigger_name
{ BEFORE | AFTER } { INSERT | UPDATE | DELETE }
ON table_name
FOR EACH ROW
BEGIN
    -- Trigger body statements
    -- Reference old column values via OLD.column_name
    -- Reference new column values via NEW.column_name
    -- Signal an exception to abort and rollback:
    -- SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Custom error message';
END //

DELIMITER ;
```

**Clause Breakdown:**
- `BEFORE | AFTER`: Specifies whether the action executes before or after the row modification.
- `INSERT | UPDATE | DELETE`: Specifies the triggering database operation.
- `ON table_name`: Designates the target table monitored by the trigger.
- `FOR EACH ROW`: Specifies that the trigger executes once for every individual row modified.
- `OLD` and `NEW`: Transition variables representing the row state before and after modification.

**Concrete Example:**

Enforcing that product stock levels cannot be negative upon insertion:

```sql
DELIMITER //

CREATE TRIGGER trg_check_stock_positive
BEFORE INSERT ON products
FOR EACH ROW
BEGIN
    IF NEW.stock < 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Initial product stock cannot be negative';
    END IF;
END //

DELIMITER ;
```

### 🎯 HYE-01 · Practice Exercise 5.5 · Trigger Enforcing Scheduling Conflict Constraint

> **Source:** Silberschatz 7e · Chapter 5 (Practice Exercise 5.5)  
> **Exam Relevance:** Prime Overdue Advanced Trigger Drill  
> **Key Tested Concept:** `BEFORE INSERT` trigger, event-condition-action (ECA) architecture, and aborting invalid operations using `SIGNAL SQLSTATE`.

**Problem Statement:**
> In the university database, an instructor cannot be scheduled to teach two different course sections that meet at the **same time slot in the same semester and year**.
> Consider relations:
> - $\text{teaches}(\underline{\text{ID}, \text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}})$
> - $\text{section}(\underline{\text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}}, \text{building}, \text{room\_number}, \text{time\_slot\_id})$
> Write an SQL trigger `check_instructor_schedule` that runs **BEFORE INSERT** on `teaches` and prevents scheduling conflicts by raising an error and aborting the insertion if an overlap is detected.

**Model Exam-Style Solution:**

```sql
DELIMITER $$

CREATE TRIGGER check_instructor_schedule
BEFORE INSERT ON teaches
FOR EACH ROW
BEGIN
    DECLARE conflict_count INT;
    DECLARE new_time_slot VARCHAR(4);

    -- Step 1: Retrieve the time_slot_id of the section being assigned
    SELECT time_slot_id INTO new_time_slot
    FROM section
    WHERE course_id = NEW.course_id
      AND sec_id = NEW.sec_id
      AND semester = NEW.semester
      AND year = NEW.year;

    -- Step 2: Check if this instructor already teaches a section in that time slot
    SELECT COUNT(*) INTO conflict_count
    FROM teaches t
    JOIN section s ON t.course_id = s.course_id
                  AND t.sec_id = s.sec_id
                  AND t.semester = s.semester
                  AND t.year = s.year
    WHERE t.ID = NEW.ID
      AND t.semester = NEW.semester
      AND t.year = NEW.year
      AND s.time_slot_id = new_time_slot;

    -- Step 3: If conflict exists, abort the transaction
    IF conflict_count > 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Scheduling Conflict: Instructor is already teaching during this time slot!';
    END IF;
END$$

DELIMITER ;
```

**Step-by-Step Logic:**
1. **Trigger Event:** `BEFORE INSERT ON teaches` ensures the check occurs before the conflicting row is committed to disk.
2. **Granularity:** `FOR EACH ROW` ensures row-level execution.
3. **Condition Check:** Joins `teaches` and `section` for the instructor's ID and current semester/year to match `time_slot_id`.
4. **Action:** If `conflict_count > 0`, `SIGNAL SQLSTATE '45000'` immediately raises a user-defined exception, rolling back the statement. $\blacksquare$

**💡 RUET Exam Takeaway:**
To abort an operation in modern MySQL/PostgreSQL triggers, use `SIGNAL SQLSTATE '45000'`. Always explain the ECA (Event, Condition, Action) model clearly in prose.

### 🎯 HYE-02 · Exercise 5.19 · SQL Trigger Emulating `ON DELETE CASCADE`

> **Source:** Silberschatz 7e · Chapter 5 (Exercise 5.19)  
> **Exam Relevance:** High-Probability Systems Implementation Question  
> **Key Tested Concept:** Emulating declarative referential integrity cascades via programmatic procedural triggers.

**Problem Statement:**
> Some legacy or distributed database systems lack built-in support for `ON DELETE CASCADE` foreign-key clauses.
> Consider parent table `department(dept_name, building, budget)` and child table `instructor(ID, name, dept_name, salary)`.
> Write an SQL trigger that automatically deletes all corresponding instructor tuples whenever a department tuple is deleted from the `department` table.

**Model Exam-Style Solution:**

```sql
DELIMITER $$

CREATE TRIGGER cascade_department_delete
AFTER DELETE ON department
FOR EACH ROW
BEGIN
    -- Delete all child records in instructor referencing the deleted department
    DELETE FROM instructor
    WHERE dept_name = OLD.dept_name;
END$$

DELIMITER ;
```

**Step-by-Step Logic:**
1. **Trigger Event:** `AFTER DELETE ON department` ensures the trigger fires only after the department has successfully been removed.
2. **Special Transition Variable `OLD`:** `OLD.dept_name` captures the primary key value of the row that was just deleted.
3. **Cascade Action:** The `DELETE FROM instructor WHERE dept_name = OLD.dept_name` statement executes automatically within the same transaction, removing all dependent child rows and preserving referential integrity. $\blacksquare$

**💡 RUET Exam Takeaway:**
Use **`OLD`** for `DELETE` operations (and old values of `UPDATE`), and use **`NEW`** for `INSERT` operations (and new values of `UPDATE`). Never mix them up!

## ⚡ Exam Tips & Common Mistakes

1. **The Missing DELIMITER Trap:** Always include `DELIMITER //` and `DELIMITER ;` in your exam answer. Omitting delimiters causes MySQL parsing errors because of semicolons inside the `BEGIN ... END` block.
2. **Transition Variable Availability:** Remember that `OLD` does not exist during `INSERT`, and `NEW` does not exist during `DELETE`. Referencing `OLD` in an `INSERT` trigger produces a runtime compilation error.
3. **Timing Selection:** Use `BEFORE` to validate or modify values before saving. Use `AFTER` when logging or updating dependent tables.
4. **Standard SQL vs MySQL 8 Syntax:** Standard SQL uses `REFERENCING NEW ROW AS nrow`. MySQL 8 does not support this clause and uses `NEW.column_name` directly. Use MySQL 8 syntax in exam papers.
5. **Aborting Transactions:** Always mention `SIGNAL SQLSTATE '45000'` as the standard mechanism to abort operations and display custom error messages.
