# T10.2: Conflict Equivalence by Swapping Non-Conflicting Instructions

> **Topic:** T10: Serializability | **Priority:** 🟢 Foundational Priority | **Exam Frequency:** 1/7 finals (4 marks: 2020 Q.5(c))  
> **Sources:** Silberschatz 7e Ch. 17 (§17.6, pp. 814–816) · Lecture Deck 07 (Slides 19–20) · Classnote by Raidah (T10, pp. 26–27)

## Why This Topic Matters

Conflict serializability is defined through instruction swapping. If you can rearrange an interleaved concurrent schedule into a clean serial schedule by swapping adjacent non-conflicting instructions one pair at a time, you have mathematically proved that the schedule is conflict serializable. In 2020 Q.5(c), RUET asked students to draw a concurrent schedule and write out this exact step-by-step swapping proof for 4 marks.

---

## 📝 Key Definitions

> **Conflict Equivalent:** "If a schedule $S$ can be transformed into a schedule $S'$ by a series of swaps of nonconflicting instructions, we say that $S$ and $S'$ are **conflict equivalent**."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.6 (p. 815)

> **Conflict Serializable:** "We say that a schedule $S$ is **conflict serializable** if it is conflict equivalent to a serial schedule."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.6 (p. 815)

> **The Swapping Rule:** Two adjacent instructions $I_i$ and $I_j$ from different transactions can be swapped if and only if they do not conflict.

---

## 1. Intuition: Why Some Swaps Are Safe and Others Are Forbidden

Before memorizing a proof, make sure the physical intuition behind instruction swapping is crystal clear. Suppose two transactions $T_1$ and $T_2$ have two instructions sitting right next to each other in the timeline. When can we swap their places without changing what happens in the database?

1. **Why you CAN always swap operations on different data items ($A$ vs. $B$):**
   Suppose $T_2$ writes to account $A$, and right after that $T_1$ reads account $B$. Because $A$ and $B$ are two completely separate variables in the database ($A \neq B$), changing $A$ has zero effect on the value stored in $B$. Whether $T_2$ updates $A$ first or $T_1$ checks $B$ first, $T_1$ still reads the exact same balance in $B$ and $A$ still gets the exact same update from $T_2$.
2. **Why you CAN always swap two reads on the same data item ($\text{read}(A)$ vs. $\text{read}(A)$):**
   Reading a variable only copies its value without changing it. If $T_1$ and $T_2$ both read $A$ back to back, swapping who reads first gives both transactions the exact same number.
3. **Why you can NEVER swap a read/write or write/write on the same item ($A$ vs. $A$):**
   - **Read vs. Write on $A$:** If $T_1:\text{write}(A)$ runs before $T_2:\text{read}(A)$, then $T_2$ sees the *new* value written by $T_1$. If you swapped them so $T_2$ read $A$ first, $T_2$ would read the *old* value instead! That changes the calculation.
   - **Write vs. Write on $A$:** If $T_1:\text{write}(A)$ runs before $T_2:\text{write}(A)$, then $T_2$'s write overwrites $T_1$'s write and stays in the database. If you swapped them, $T_1$'s write would win instead, leaving a different final value on disk.
4. **Why you can NEVER swap two steps of the same transaction ($T_1$ vs. $T_1$):**
   Inside a single transaction, instructions depend on each other in program order (for example, $T_1$ must read $A$ before it can compute and write the new $A$). You can only swap adjacent steps that belong to *different* transactions.

### Why Must Every Swap Be Adjacent?

Think of instruction swapping like bubble sort. You can only swap two instructions when they are standing **immediately next to each other** in the schedule. If you want to move an instruction past three other steps, you cannot just teleport it across all three at once. Instead, you have to bubble it past them **one adjacent swap at a time**, checking at each step that the two neighbors do not conflict.

## 2. Illustrative Mini-Example: A Quick 2-Swap Proof

Before tackling the full 8-instruction textbook schedule in `GQ1`, let's trace a compact 5-instruction schedule to see how the bubbling mechanics work.

Suppose transactions $T_1$ and $T_2$ run on items $X$ and $Y$ in this interleaved schedule $S$:

| Step | Transaction $T_1$ | Transaction $T_2$ | Target Item |
| :---: | :--- | :--- | :---: |
| 1 | $\text{read}(X)$ | | $X$ |
| 2 | $\text{write}(X)$ | | $X$ |
| 3 | | $\text{read}(X)$ | $X$ |
| 4 | | $\text{read}(Y)$ | $Y$ |
| 5 | $\text{write}(Y)$ | | $Y$ |

Let's write $S$ as a single line of instructions:

$$
S:\quad (1)\;T_1:\text{r}(X),\quad (2)\;T_1:\text{w}(X),\quad (3)\;T_2:\text{r}(X),\quad (4)\;T_2:\text{r}(Y),\quad (5)\;T_1:\text{w}(Y)
$$

Notice that $T_1$ finishes $X$ before $T_2$ reads $X$ (Steps 2 and 3 conflict on $X$, so $T_1$ must precede $T_2$). However, at the bottom of the schedule, $T_2:\text{r}(Y)$ (Step 4) runs *before* $T_1:\text{w}(Y)$ (Step 5)! Because those two steps both touch $Y$ and Step 5 is a write, they **conflict** (an RW conflict on $Y$).

Wait: can we swap Step 4 and Step 5? **No!** $T_2:\text{r}(Y)$ and $T_1:\text{w}(Y)$ both touch $Y$ and one is a write, so they conflict and block each other.

What if Step 5 in $T_1$ had been $\text{read}(Y)$ instead of $\text{write}(Y)$? Let's trace that schedule $S_{\text{safe}}$:

$$
S_{\text{safe}}:\quad (1)\;T_1:\text{r}(X),\quad (2)\;T_1:\text{w}(X),\quad (3)\;T_2:\text{r}(X),\quad (4)\;T_2:\text{r}(Y),\quad (5)\;T_1:\text{r}(Y)
$$

1. **Swap 1 (Positions 4 and 5):** Swap $T_2:\text{r}(Y)$ and $T_1:\text{r}(Y)$.
   - *Why it is valid:* Both touch $Y$, but **two reads never conflict**!
   - *Result:* $T_1:\text{r}(X),\; T_1:\text{w}(X),\; T_2:\text{r}(X),\; \mathbf{T_1:\text{r}(Y)},\; \mathbf{T_2:\text{r}(Y)}$
2. **Swap 2 (Positions 3 and 4):** Swap $T_2:\text{r}(X)$ and $T_1:\text{r}(Y)$.
   - *Why it is valid:* They access different items ($X \neq Y$) and neither is a write.
   - *Result:* $T_1:\text{r}(X),\; T_1:\text{w}(X),\; \mathbf{T_1:\text{r}(Y)},\; \mathbf{T_2:\text{r}(X)},\; T_2:\text{r}(Y)$

Now all of $T_1$'s operations come before all of $T_2$'s operations, giving the serial schedule $\langle T_1, T_2 \rangle$!

## 3. When Swapping Is Impossible (Non-Serializable Schedule)

To see a classic schedule that can **never** be serialized by swapping, look at Schedule 7 from Silberschatz 7e (Figure 17.9) and Lecture Deck 07 (Slide 21):

| Step | Transaction $T_3$ | Transaction $T_4$ | Target Item |
| :---: | :--- | :--- | :---: |
| 1 | $\text{read}(Q)$ | | $Q$ |
| 2 | | $\text{write}(Q)$ | $Q$ |
| 3 | $\text{write}(Q)$ | | $Q$ |

Why does every possible swap fail here?
- **Can we reach serial order $\langle T_3, T_4 \rangle$?** To group $T_3$'s steps together at the top, we would have to swap Step 2 ($T_4:\text{write}(Q)$) and Step 3 ($T_3:\text{write}(Q)$). However, both are writes on the **same item $Q$** (a WW conflict), so swapping them is forbidden.
- **Can we reach serial order $\langle T_4, T_3 \rangle$?** To group $T_3$'s steps together at the bottom, we would have to swap Step 1 ($T_3:\text{read}(Q)$) and Step 2 ($T_4:\text{write}(Q)$). However, a read and a write on the **same item $Q$** also conflict (an RW conflict), so swapping them is forbidden too.

Because every adjacent pair of instructions from different transactions conflicts, zero valid swaps exist. Therefore, this schedule is **not conflict serializable**.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.5(c) · Step-by-Step Swapping Proof

> **Appeared:** 2020 Q.5(c) (4 marks)

> **Question:**
>
> Draw a concurrent schedule equivalent to serial schedule. Prove its step by step swapping process.

**Full Answer:**

#### 1. Concurrent Schedule ($S$)

Consider two transactions $T_1$ and $T_2$ that each read and write accounts $A$ and $B$ (from Lecture Deck 07, Slide 20 / Silberschatz Fig. 17.6):
- $T_1$: $\text{read}(A) \to \text{write}(A) \to \text{read}(B) \to \text{write}(B)$
- $T_2$: $\text{read}(A) \to \text{write}(A) \to \text{read}(B) \to \text{write}(B)$

Below is the interleaved concurrent schedule $S$:

| Step | Transaction $T_1$ | Transaction $T_2$ | Target Item |
| :---: | :--- | :--- | :---: |
| 1 | $\text{read}(A)$ | | $A$ |
| 2 | $\text{write}(A)$ | | $A$ |
| 3 | | $\text{read}(A)$ | $A$ |
| 4 | | $\text{write}(A)$ | $A$ |
| 5 | $\text{read}(B)$ | | $B$ |
| 6 | $\text{write}(B)$ | | $B$ |
| 7 | | $\text{read}(B)$ | $B$ |
| 8 | | $\text{write}(B)$ | $B$ |

#### 2. Swapping Rule

Two adjacent instructions from different transactions can be swapped if and only if they do **not** conflict. Because instructions that access **different data items** ($A \neq B$) never conflict, we can swap $T_1$'s operations on $B$ upward past $T_2$'s operations on $A$ without changing the final state of the database.

#### 3. Step-by-Step Swapping Process

We write schedule $S$ as an ordered list of 8 instructions and transform it into the serial schedule $\langle T_1, T_2 \rangle$ using 4 adjacent swaps:

- **Initial Order ($S$):**

$$
\begin{aligned}
&(1)\; T_1:\text{r}(A),\quad (2)\; T_1:\text{w}(A),\quad (3)\; T_2:\text{r}(A),\quad (4)\; T_2:\text{w}(A), \\
&(5)\; T_1:\text{r}(B),\quad (6)\; T_1:\text{w}(B),\quad (7)\; T_2:\text{r}(B),\quad (8)\; T_2:\text{w}(B)
\end{aligned}
$$

- **Swap 1 (Swap positions 4 and 5):** Swap $T_2:\text{write}(A)$ and $T_1:\text{read}(B)$.
  - *Reason:* They access different data items ($A \neq B$), so they do not conflict.
  - *Order after Swap 1:*

$$
T_1:\text{r}(A),\; T_1:\text{w}(A),\; T_2:\text{r}(A),\; \mathbf{T_1:\text{r}(B)},\; \mathbf{T_2:\text{w}(A)},\; T_1:\text{w}(B),\; T_2:\text{r}(B),\; T_2:\text{w}(B)
$$

- **Swap 2 (Swap positions 3 and 4):** Swap $T_2:\text{read}(A)$ and $T_1:\text{read}(B)$.
  - *Reason:* They access different data items ($A \neq B$), so they do not conflict.
  - *Order after Swap 2:*

$$
T_1:\text{r}(A),\; T_1:\text{w}(A),\; \mathbf{T_1:\text{r}(B)},\; \mathbf{T_2:\text{r}(A)},\; T_2:\text{w}(A),\; T_1:\text{w}(B),\; T_2:\text{r}(B),\; T_2:\text{w}(B)
$$

- **Swap 3 (Swap positions 5 and 6):** Swap $T_2:\text{write}(A)$ and $T_1:\text{write}(B)$.
  - *Reason:* Even though both are writes, they access different data items ($A \neq B$), so they do not conflict.
  - *Order after Swap 3:*

$$
T_1:\text{r}(A),\; T_1:\text{w}(A),\; T_1:\text{r}(B),\; T_2:\text{r}(A),\; \mathbf{T_1:\text{w}(B)},\; \mathbf{T_2:\text{w}(A)},\; T_2:\text{r}(B),\; T_2:\text{w}(B)
$$

- **Swap 4 (Swap positions 4 and 5):** Swap $T_2:\text{read}(A)$ and $T_1:\text{write}(B)$.
  - *Reason:* They access different data items ($A \neq B$), so they do not conflict.
  - *Final Order after Swap 4 ($S'$):*

$$
T_1:\text{r}(A),\; T_1:\text{w}(A),\; T_1:\text{r}(B),\; \mathbf{T_1:\text{w}(B)},\; \mathbf{T_2:\text{r}(A)},\; T_2:\text{w}(A),\; T_2:\text{r}(B),\; T_2:\text{w}(B)
$$

#### 4. Resulting Serial Schedule ($S'$)

After the 4 valid swaps, all instructions of $T_1$ execute together before any instruction of $T_2$ begins:

| Step | Transaction $T_1$ | Transaction $T_2$ | Target Item |
| :---: | :--- | :--- | :---: |
| 1 | $\text{read}(A)$ | | $A$ |
| 2 | $\text{write}(A)$ | | $A$ |
| 3 | $\text{read}(B)$ | | $B$ |
| 4 | $\text{write}(B)$ | | $B$ |
| 5 | | $\text{read}(A)$ | $A$ |
| 6 | | $\text{write}(A)$ | $A$ |
| 7 | | $\text{read}(B)$ | $B$ |
| 8 | | $\text{write}(B)$ | $B$ |

**Conclusion:** Because concurrent schedule $S$ was transformed into the serial schedule $S' = \langle T_1, T_2 \rangle$ through a sequence of valid swaps of adjacent non-conflicting instructions, $S$ is **conflict equivalent** to $\langle T_1, T_2 \rangle$ and is therefore **conflict serializable**.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 17.16 · Transforming an Interleaved Schedule via Successive Swapping

> **Source:** Silberschatz 7e · Chapter 17 (Exercise 17.16 / §17.6)  
> **Exam Relevance:** High-Probability Section B Proof Drill (Direct extension of 2020 Q.5c)  
> **Key Tested Concept:** Identifying non-conflicting adjacent operations, algebraic bubble-swapping across distinct data items, and proving conflict equivalence to a serial schedule.

**Problem Statement:**
> Consider the following interleaved concurrent schedule $S$ involving two transactions $T_1$ and $T_2$ operating on data items $A$, $B$, and $C$:
>
> | Step | Transaction $T_1$ | Transaction $T_2$ | Target Item |
> | :---: | :--- | :--- | :---: |
> | 1 | | $\text{read}(B)$ | $B$ |
> | 2 | $\text{read}(A)$ | | $A$ |
> | 3 | | $\text{write}(B)$ | $B$ |
> | 4 | $\text{write}(A)$ | | $A$ |
> | 5 | $\text{read}(B)$ | | $B$ |
> | 6 | | $\text{read}(C)$ | $C$ |
> | 7 | $\text{write}(B)$ | | $B$ |
> | 8 | | $\text{write}(C)$ | $C$ |
>
> 1. Identify all conflicting pairs of instructions between $T_1$ and $T_2$ and determine the serialization order.
> 2. Transform schedule $S$ into an equivalent serial schedule step-by-step by successively swapping adjacent non-conflicting instructions. Explicitly justify each swap.
> 3. Conclude whether $S$ is conflict serializable and state the resulting serial schedule.

**Model Exam-Style Solution:**

#### 1. Conflicting Pairs and Serialization Direction
Two operations conflict if and only if they are issued by different transactions, access the **same data item**, and at least one is a $\text{write}$:
- **Item $A$:** Only accessed by $T_1$ ($\text{read}(A), \text{write}(A)$). No inter-transaction conflict.
- **Item $C$:** Only accessed by $T_2$ ($\text{read}(C), \text{write}(C)$). No inter-transaction conflict.
- **Item $B$ (Shared Item):**
  - Step 1: $T_2: \text{read}(B)$ precedes Step 7: $T_1: \text{write}(B)$ $\implies T_2 \longrightarrow T_1$
  - Step 3: $T_2: \text{write}(B)$ precedes Step 5: $T_1: \text{read}(B)$ $\implies T_2 \longrightarrow T_1$
  - Step 3: $T_2: \text{write}(B)$ precedes Step 7: $T_1: \text{write}(B)$ $\implies T_2 \longrightarrow T_1$

Because all conflicting pairs on item $B$ flow from $T_2$ to $T_1$, the precedence graph contains only the directed edge $T_2 \longrightarrow T_1$ (strictly acyclic). The required equivalent serial schedule is:
$$
S' = \langle T_2, T_1 \rangle
$$

#### 2. Step-by-Step Swapping Process

We represent schedule $S$ as the sequence of 8 indexed instructions:
$$
\begin{aligned}
S = \langle & (1)\; T_2:\text{r}(B),\quad (2)\; T_1:\text{r}(A),\quad (3)\; T_2:\text{w}(B),\quad (4)\; T_1:\text{w}(A), \\
& (5)\; T_1:\text{r}(B),\quad (6)\; T_2:\text{r}(C),\quad (7)\; T_1:\text{w}(B),\quad (8)\; T_2:\text{w}(C) \;\rangle
\end{aligned}
$$

To produce serial schedule $\langle T_2, T_1 \rangle$, all operations of $T_2$ must move ahead of the operations of $T_1$ by swapping adjacent non-conflicting instructions:

- **Swap 1 (Swap positions 2 and 3):** Swap $T_1:\text{read}(A)$ and $T_2:\text{write}(B)$.
  - *Justification:* Valid swap because they access different data items ($A \neq B$).
  - *Sequence after Swap 1:*
    $$
    T_2:\text{r}(B),\; \mathbf{T_2:\text{w}(B)},\; \mathbf{T_1:\text{r}(A)},\; T_1:\text{w}(A),\; T_1:\text{r}(B),\; T_2:\text{r}(C),\; T_1:\text{w}(B),\; T_2:\text{w}(C)
    $$
    *(Notice: $T_2$'s operations on $B$ are now together at positions 1 and 2).*

- **Swap 2 (Swap positions 5 and 6):** Swap $T_1:\text{read}(B)$ and $T_2:\text{read}(C)$.
  - *Justification:* Valid swap because they access different data items ($B \neq C$).
  - *Sequence after Swap 2:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; T_1:\text{r}(A),\; T_1:\text{w}(A),\; \mathbf{T_2:\text{r}(C)},\; \mathbf{T_1:\text{r}(B)},\; T_1:\text{w}(B),\; T_2:\text{w}(C)
    $$

- **Swap 3 (Swap positions 4 and 5):** Swap $T_1:\text{write}(A)$ and $T_2:\text{read}(C)$.
  - *Justification:* Valid swap because they access different data items ($A \neq C$).
  - *Sequence after Swap 3:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; T_1:\text{r}(A),\; \mathbf{T_2:\text{r}(C)},\; \mathbf{T_1:\text{w}(A)},\; T_1:\text{r}(B),\; T_1:\text{w}(B),\; T_2:\text{w}(C)
    $$

- **Swap 4 (Swap positions 3 and 4):** Swap $T_1:\text{read}(A)$ and $T_2:\text{read}(C)$.
  - *Justification:* Valid swap because they access different data items ($A \neq C$).
  - *Sequence after Swap 4:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; \mathbf{T_2:\text{r}(C)},\; \mathbf{T_1:\text{r}(A)},\; T_1:\text{w}(A),\; T_1:\text{r}(B),\; T_1:\text{w}(B),\; T_2:\text{w}(C)
    $$
    *(Notice: $T_2:\text{read}(C)$ has now bubbled into $T_2$'s block at position 3).*

- **Swap 5 (Swap positions 7 and 8):** Swap $T_1:\text{write}(B)$ and $T_2:\text{write}(C)$.
  - *Justification:* Valid swap because they access different data items ($B \neq C$).
  - *Sequence after Swap 5:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; T_2:\text{r}(C),\; T_1:\text{r}(A),\; T_1:\text{w}(A),\; T_1:\text{r}(B),\; \mathbf{T_2:\text{w}(C)},\; \mathbf{T_1:\text{w}(B)}
    $$

- **Swap 6 (Swap positions 6 and 7):** Swap $T_1:\text{read}(B)$ and $T_2:\text{write}(C)$.
  - *Justification:* Valid swap because they access different data items ($B \neq C$).
  - *Sequence after Swap 6:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; T_2:\text{r}(C),\; T_1:\text{r}(A),\; T_1:\text{w}(A),\; \mathbf{T_2:\text{w}(C)},\; \mathbf{T_1:\text{r}(B)},\; T_1:\text{w}(B)
    $$

- **Swap 7 (Swap positions 5 and 6):** Swap $T_1:\text{write}(A)$ and $T_2:\text{write}(C)$.
  - *Justification:* Valid swap because they access different data items ($A \neq C$).
  - *Sequence after Swap 7:*
    $$
    T_2:\text{r}(B),\; T_2:\text{w}(B),\; T_2:\text{r}(C),\; T_1:\text{r}(A),\; \mathbf{T_2:\text{w}(C)},\; \mathbf{T_1:\text{w}(A)},\; T_1:\text{r}(B),\; T_1:\text{w}(B)
    $$

- **Swap 8 (Swap positions 4 and 5):** Swap $T_1:\text{read}(A)$ and $T_2:\text{write}(C)$.
  - *Justification:* Valid swap because they access different data items ($A \neq C$).
  - *Final Sequence after Swap 8 ($S'$):*
    $$
    \mathbf{T_2:\text{r}(B)},\; \mathbf{T_2:\text{w}(B)},\; \mathbf{T_2:\text{r}(C)},\; \mathbf{T_2:\text{w}(C)},\; \mathbf{T_1:\text{r}(A)},\; \mathbf{T_1:\text{w}(A)},\; \mathbf{T_1:\text{r}(B)},\; \mathbf{T_1:\text{w}(B)}
    $$

#### 3. Resulting Serial Schedule ($S'$)

| Step | Transaction $T_1$ | Transaction $T_2$ | Target Item |
| :---: | :--- | :--- | :---: |
| 1 | | $\text{read}(B)$ | $B$ |
| 2 | | $\text{write}(B)$ | $B$ |
| 3 | | $\text{read}(C)$ | $C$ |
| 4 | | $\text{write}(C)$ | $C$ |
| 5 | $\text{read}(A)$ | | $A$ |
| 6 | $\text{write}(A)$ | | $A$ |
| 7 | $\text{read}(B)$ | | $B$ |
| 8 | $\text{write}(B)$ | | $B$ |

**Conclusion:**
Through a finite sequence of 8 adjacent non-conflicting instruction swaps, concurrent schedule $S$ was transformed into the purely serial schedule $S' = \langle T_2, T_1 \rangle$. Therefore, by definition:
1. Schedule $S$ is **conflict equivalent** to serial schedule $\langle T_2, T_1 \rangle$.
2. Schedule $S$ is **conflict serializable** with serialization order $\boxed{\langle T_2, T_1 \rangle}$. $\blacksquare$

**💡 RUET Exam Takeaway:**
When swapping instructions, never attempt to jump an instruction across multiple positions in a single step. RUET examiners look specifically for each discrete adjacent swap pair and the justification that $Q_i \neq Q_j$.

## ⚡ Exam Tips & Common Mistakes

1. **Draw Both Tables:** In 2020 Q.5(c), always draw both the starting concurrent schedule table and the final serial schedule table. Leaving out either table costs easy presentation marks.
2. **Show All 4 Individual Swaps:** Never jump $T_1:\text{read}(B)$ across both $T_2:\text{read}(A)$ and $T_2:\text{write}(A)$ in a single step. Write out Swap 1, Swap 2, Swap 3, and Swap 4 one adjacent pair at a time.
3. **Write the Justification on Every Swap:** Next to each swap, explicitly state: *"Valid because they access different data items ($A \neq B$) and therefore do not conflict."*
4. **Never Swap Across Same-Item Writes:** Notice that in `GQ1`, we never tried to swap $T_1:\text{write}(A)$ with $T_2:\text{read}(A)$ (Steps 2 and 3), because both touch $A$ and Step 2 is a write. Instead, we bubbled $T_1$'s operations on $B$ upward past $T_2$'s operations on $A$.
