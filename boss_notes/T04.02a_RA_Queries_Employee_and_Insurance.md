# T04.2a: RA Queries — Employee, Insurance, and RA Updates

> **Topic:** T04 — Relational Algebra & Calculus | **Priority:** 🔴 | **Exam Frequency:** 6/7 finals (+ CT-01 Q4) (41 marks in T04.2)
> **Sources:** Silberschatz 7e Ch. 2 (§2.6), Ch. 16 (§16.1) · Lecture Deck 02 (Slides 9–29) · Raidah Class Notes (pp. 13–14)

## Why This Topic Matters

Almost every RUET semester final gives you a multi-table schema and asks you to write relational algebra expressions (explicitly warning "Not SQL"). Two of the classic textbook schemas tested in Section A are the **Employee-Company-Manages** database (2017) and the **Car Insurance-Accident** database (2018). These questions test whether you can chain natural joins and theta joins across three tables, group and count rows with $\gamma$, and update specific rows using relational assignment ($\leftarrow$). Once you know the five-step recipe below, you can turn any English prompt into a clean algebraic expression.

---

## 📝 Key Definitions

> **Relational Algebra:** Relational algebra is a procedural query language made of operators that take one or two relations as input and return a new relation as output. Because the output is always a relation, operations can be nested to build complex queries.

> **Select Operation ($\sigma$):** The select operation filters rows horizontally and returns all tuples from a relation $r$ that satisfy a condition $p$. It is written as $\sigma_p(r)$ where the predicate $p$ can compare attributes and constants using $=, \neq, <, \le, >, \ge$ and logical connectives $\land, \lor, \lnot$.

> **Project Operation ($\Pi$):** The project operation selects specific columns vertically from a relation $r$ and discards the rest. It is written as $\Pi_{A_1, A_2, \dots, A_k}(r)$ and automatically eliminates duplicate rows from the resulting relation.

> **Set-Difference Operation ($-$):** The set-difference operation takes two union-compatible relations $r$ and $s$ and returns all tuples that appear in $r$ but do not appear in $s$. It is written as $r - s$.

> **Database Modification (Assignment $\leftarrow$):** The assignment operator ($\leftarrow$) writes the result of a relational algebra expression into a relation variable. Assigning to a temporary variable breaks a complex query into steps. Assigning back to a permanent relation ($r \leftarrow E$) modifies the stored database by inserting ($r \leftarrow r \cup E$), deleting ($r \leftarrow r - E$), or updating rows.

> **Aggregate Functions:** Aggregate functions take a multiset (bag with duplicates) of column values as input and return a single summary value. The five standard aggregate functions are `avg`, `min`, `max`, `sum`, and `count`, applied in extended relational algebra using the grouping operator ${}_G\gamma_F(r)$.

## Relational Algebra Query-Writing Recipe

### Intuitive Analogy: Inside-Out vs. Outside-In Thinking

When you read a relational algebra expression like $\Pi_{\text{name}}(\sigma_{\text{salary}>50000}(\text{works}))$, you evaluate it **from the inside out**: first take the table `works`, then filter its rows with $\sigma$, and finally keep the `name` column with $\Pi$. When you *write* a query from an English sentence, follow this five-step checklist so you never miss a join or a projection:

```text
[English Specification]
        │
        ▼
Step 1: Identify Target Output Attributes  ──► Choose final Projection: Π_{attributes}
        │
        ▼
Step 2: Identify Source Tables & Keys      ──► Combine via Natural Join (⨝) or Theta Join (⨝_θ)
        │
        ▼
Step 3: Identify Filtering Conditions       ──► Apply Selection: σ_{predicate}
        │
        ▼
Step 4: Check for Idiomatic Patterns       ──► Set difference (-), Aggregation (γ), or Update (←)
        │
        ▼
Step 5: Verify Schema Compatibility        ──► Confirm attribute names, arity, and types
```

### 1. Identify Target Attributes (Projection $\Pi$)
Look at what the question asks you to return. If it asks for "names of employees", your outermost step must be $\Pi_{\text{person\_name}}(\dots)$. Leaving off the outer $\Pi$ returns extra columns and loses marks.

### 2. Identify Source Relations and Join Conditions ($\bowtie$ or $\bowtie_\theta$)
Check which tables hold the columns you need to filter on and which tables hold the columns you need to output:
- If two tables share the **exact same column name** (and all shared column names mean the same thing), connect them with a **natural join** ($\bowtie$).
- If the matching columns have **different names** (for example, `owns.license` and `participated.car` in the Insurance database), connect them with an explicit **theta join** ($r \bowtie_{r.A = s.B} s$).

### 3. Translate Common Query Idioms

| English Idiom | Relational Algebra Construct | Mathematical Expression / Pattern |
| :--- | :--- | :--- |
| **"Matching both / across tables"** | Natural join ($\bowtie$) or intersection ($\cap$) | $r \bowtie s$ or $\Pi_A(r) \cap \Pi_A(s)$ |
| **"Only / exclusively / but not"** | Set difference ($-$) | $\Pi_A(\sigma_{P_1}(r)) - \Pi_A(\sigma_{P_2}(s))$ |
| **"Either ... or ... (both included)"** | Set union ($\cup$) | $\Pi_A(r) \cup \Pi_A(s)$ (must be union-compatible) |
| **"Count, average, sum per group"** | Grouped aggregation (${}_{G}\gamma_{F}$) | ${}_{\text{group\_attrs}}\gamma_{\text{agg\_func}(\text{target\_attr})}(r)$ |
| **"Peak / Maximum value overall"** | Scalar aggregation ($\gamma_{\text{max}(\dots)}$) | $\gamma_{\text{max}(C)}({}_G\gamma_{\text{count}(A) \ \text{as} \ C}(r))$ |
| **"Extremes without aggregation"** | Self-Cartesian product with violation filtering | $\Pi_A(r) - \Pi_{r_1.A}(\sigma_{r_1.\text{val} < r_2.\text{val}}(r_1 \times r_2))$ |

## Mechanics of Relational Algebra Updates (6e-Style)

### Why Updates Need Set Difference and Union

In SQL, an `UPDATE` statement modifies matching rows right inside the table and leaves the other rows alone. In relational algebra, operators do not modify rows in place. Instead, every expression computes a new set of rows. That means if you want to update *only some* rows in a table $r$ (for example, giving a raise only to managers), you must split the table into two parts: the rows being changed ($T_{\text{modified}}$) and the rows staying the same ($T_{\text{untouched}}$). Then you union those two parts back together and assign the result to $r$:

$$
r \leftarrow T_{\text{modified}} \cup T_{\text{untouched}}
$$

### The Four-Step Update Recipe

1. **Isolate Target Records:**
   First we filter the table $r$ using $\sigma_P$ to grab only the rows that need to be updated:

$$
T_{\text{target}} \leftarrow \sigma_P(r)
$$

2. **Compute Modified Tuples:**
   Next we use generalized projection ($\Pi$) on $T_{\text{target}}$ to compute the new value for the updated column while keeping all other columns in their original positions:

$$
T_{\text{modified}} \leftarrow \Pi_{A_1, A_2, \dots, \text{new\_expression}, \dots, A_n}(T_{\text{target}})
$$

3. **Isolate Untouched Records:**
   Then we subtract $T_{\text{target}}$ from the original table $r$ so we keep all the rows that were not supposed to change:

$$
T_{\text{untouched}} \leftarrow r - T_{\text{target}}
$$

4. **Combine and Reassign:**
   Finally, we union the updated rows with the untouched rows and assign the full set back to $r$:

$$
r \leftarrow T_{\text{modified}} \cup T_{\text{untouched}}
$$

> [!WARNING]
> Forgetting $T_{\text{untouched}}$ is one of the most common exam mistakes! If you write $r \leftarrow T_{\text{modified}}$ by itself, you overwrite the entire table with *only* the updated rows and wipe out everyone else in the database.

## Worked Example: Employee Salary Filter & 5% Company Raise

Consider the employee schema from Silberschatz Figure 2.17:
- $\text{employee}(\text{person\_name}, \text{street}, \text{city})$
- $\text{works}(\text{person\_name}, \text{company\_name}, \text{salary})$
- $\text{company}(\text{company\_name}, \text{city})$
- $\text{manages}(\text{person\_name}, \text{manager\_name})$

### Problem Statement
1. Find the names of all employees who work for `"First Bank Corporation"` and earn more than \$50,000.
2. Give a 5% salary raise to all employees who work for `"First Bank Corporation"`.

### Step-by-Step Derivation

#### Query 1: Filter and Project
Both `company_name`, `salary`, and `person_name` live inside the `works` table, so we do not even need a join:
1. First we filter `works` using $\sigma$ for rows where `company_name = "First Bank Corporation"` and `salary > 50000`:

$$
T_1 \leftarrow \sigma_{\text{company\_name} = \text{"First Bank Corporation"} \land \text{salary} > 50000}(\text{works})
$$

2. Next we project `person_name` using $\Pi$ to output only the employee names:

$$
\Pi_{\text{person\_name}}(T_1)
$$

Or as a single nested expression:

$$
\Pi_{\text{person\_name}}(\sigma_{\text{company\_name} = \text{"First Bank Corporation"} \land \text{salary} > 50000}(\text{works}))
$$

#### Query 2: Relational Update with a 5% Raise
1. First we filter `works` to isolate the employees of `"First Bank Corporation"`:

$$
T_{\text{target}} \leftarrow \sigma_{\text{company\_name} = \text{"First Bank Corporation"}}(\text{works})
$$

2. Next we project `person_name`, `company_name`, and `salary * 1.05` on those target rows to calculate their 5% raise:

$$
T_{\text{raised}} \leftarrow \Pi_{\text{person\_name}, \text{company\_name}, \text{salary} * 1.05}(T_{\text{target}})
$$

3. Then we subtract $T_{\text{target}}$ from `works` to keep all employees who work at other companies untouched:

$$
T_{\text{untouched}} \leftarrow \text{works} - T_{\text{target}}
$$

4. Finally, we union the raised rows with the untouched rows and assign the result back to `works`:

$$
\text{works} \leftarrow T_{\text{raised}} \cup T_{\text{untouched}}
$$

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.2(a) · Employee Database Queries & Updates

> **Appeared:** 2017 Q.2(a) — (8 marks)

**Question:**

Consider the following relational database.  
  `employee(person_name, street, city)`  
  `works(person_name, company_name, salary)`  
  `company(company_name, city)`  
  `manages(person_name, manager_name)`  
Now write down the relational algebra(Not SQL) to express each of following queries:  
(i) Find the names of all employees who live in the city same as their corresponding company location.  
(ii) Give a 10% salary raise to all the managers only.  
(iii) Update the city information of the employee named "James" to "Newtown".  
(iv) Find the company with most employees.

*(Sorting Note: Part iv uses $\gamma$ aggregation, see T04.4; parts ii–iii use RA updates)*

**Full Answer:**

#### (i) Employees living in the same city as their company

First we join `employee` with `works` on `person_name` to see which company each person works for. Then we join that result with `company`. Because both `employee` and `company` share the column name `city` (and `works` and `company` share `company_name`), the natural join ($\bowtie$) automatically checks that `works.company_name = company.company_name` AND `employee.city = company.city`:

$$
T_1 \leftarrow \text{employee} \bowtie \text{works} \bowtie \text{company}
$$

Finally, we project `person_name` to list the matching employees:

$$
\Pi_{\text{person\_name}}(T_1)
$$

Or as a single one-line expression:

$$
\Pi_{\text{person\_name}}(\text{employee} \bowtie \text{works} \bowtie \text{company})
$$

#### (ii) Give a 10% salary raise to all managers only

1. First we project `manager_name` from `manages` to get all distinct managers, and we use $\rho$ to rename that column to `person_name` so it can natural-join with `works`:

$$
M \leftarrow \rho_{M(\text{person\_name})}(\Pi_{\text{manager\_name}}(\text{manages}))
$$

2. Next we natural-join `works` with $M$ on `person_name` to get the `works` tuples belonging to managers:

$$
T_{\text{mgr}} \leftarrow \text{works} \bowtie M
$$

3. Then we project `person_name`, `company_name`, and `salary * 1.1` on $T_{\text{mgr}}$ to give every manager a 10% raise:

$$
T_{\text{raised}} \leftarrow \Pi_{\text{person\_name}, \text{company\_name}, \text{salary} * 1.1}(T_{\text{mgr}})
$$

4. Next we subtract $T_{\text{mgr}}$ from `works` so we keep all non-manager employees untouched:

$$
T_{\text{untouched}} \leftarrow \text{works} - T_{\text{mgr}}
$$

5. Finally, we union the raised manager rows with the untouched non-manager rows and assign the result back to `works`:

$$
\text{works} \leftarrow T_{\text{raised}} \cup T_{\text{untouched}}
$$

#### (iii) Update the city of employee "James" to "Newtown"

1. First we filter `employee` using $\sigma$ to isolate the row for `"James"`:

$$
T_{\text{james}} \leftarrow \sigma_{\text{person\_name} = \text{"James"}}(\text{employee})
$$

2. Next we project `person_name`, `street`, and the constant string `"Newtown"` in place of `city`:

$$
T_{\text{updated}} \leftarrow \Pi_{\text{person\_name}, \text{street}, \text{"Newtown"}}(T_{\text{james}})
$$

3. Then we subtract $T_{\text{james}}$ from `employee` to keep every other employee's row unchanged:

$$
T_{\text{untouched}} \leftarrow \text{employee} - T_{\text{james}}
$$

4. Finally, we union the updated row for James with the untouched rows and assign the result back to `employee`:

$$
\text{employee} \leftarrow T_{\text{updated}} \cup T_{\text{untouched}}
$$

#### (iv) Find the company with the most employees

1. First we group `works` by `company_name` using $\gamma$ and count `person_name` to find how many employees work at each company:

$$
T_{\text{counts}} \leftarrow {}_{\text{company\_name}}\gamma_{\text{count}(\text{person\_name}) \ \text{as} \ \text{num\_emp}}(\text{works})
$$

2. Next we apply scalar aggregation $\gamma_{\text{max}}$ on $T_{\text{counts}}$ to find the highest employee headcount across all companies:

$$
T_{\text{max}} \leftarrow \gamma_{\text{max}(\text{num\_emp}) \ \text{as} \ \text{max\_emp}}(T_{\text{counts}})
$$

3. Finally, we pair $T_{\text{counts}}$ with $T_{\text{max}}$ using $\times$, filter for the company whose `num_emp` equals `max_emp`, and project `company_name`:

$$
\Pi_{\text{company\_name}}(\sigma_{\text{num\_emp} = \text{max\_emp}}(T_{\text{counts}} \times T_{\text{max}}))
$$

### 🎯 GQ2 · 2018 Q.3(a) · Insurance Database Aggregation & Damage Update

> **Appeared:** 2018 Q.3(a) — (6 marks)

**Question:**

Consider the following insurance database, where primary keys are underlined.  
person (<u>driver_id</u>, name, address)  
car (<u>license</u>, model, year)  
accident (<u>report_number</u>, date, location)  
owns (<u>driver_id</u>, license)  
participated (<u>driver_id</u>, car, <u>report_number</u>, damage_amount)

Write down the relational algebra statement for the following queries:  
(i) Find the total number of people who owned cars that were involved in accidents in 1989.  
(ii) Find the number of accidents in which the cars belonging to "John Smith" were involved.  
(iii) Update the damage amounts for the car with license number "AABB2019" in the accident with report_number "AR201930" to \$3000.

*(Sorting Note: Parts i–ii use $\gamma$ aggregation, see T04.4; part iii uses RA update)*

**Full Answer:**

#### (i) Total number of people who owned cars involved in accidents in 1989

*Assumption: We extract the calendar year from `date` using $\text{year}(\text{date}) = 1989$. Notice also that `participated.driver_id` is the driver in the crash, whereas `owns.driver_id` is the car's owner, and the vehicle column is named `car` in `participated` but `license` in `owns`.*

1. First we filter `accident` for the year 1989 and natural-join with `participated` on `report_number`:

$$
T_1 \leftarrow \sigma_{\text{year}(\text{date}) = 1989}(\text{accident}) \bowtie \text{participated}
$$

2. Next we theta-join $T_1$ with `owns` by matching `participated.car = owns.license` (we use a theta join instead of a natural join so we match on the car's license rather than forcing the driver in the crash to be the car owner):

$$
T_2 \leftarrow T_1 \bowtie_{\text{participated.car} = \text{owns.license}} \text{owns}
$$

3. Finally, we use $\gamma$ with `count-distinct` on `owns.driver_id` so an owner whose cars were in multiple 1989 accidents is counted only once:

$$
\gamma_{\text{count-distinct}(\text{owns.driver\_id})}(T_2)
$$

#### (ii) Number of accidents involving cars belonging to "John Smith"

1. First we filter `person` for `name = "John Smith"` and natural-join with `owns` on `driver_id` to find all license numbers owned by John Smith:

$$
T_{\text{john\_cars}} \leftarrow \sigma_{\text{name} = \text{"John Smith"}}(\text{person}) \bowtie \text{owns}
$$

2. Next we theta-join $T_{\text{john\_cars}}$ with `participated` where `owns.license = participated.car` to find every accident involving one of his cars:

$$
T_{\text{accidents}} \leftarrow T_{\text{john\_cars}} \bowtie_{\text{owns.license} = \text{participated.car}} \text{participated}
$$

3. Finally, we apply $\gamma$ with `count-distinct(report_number)` to count how many distinct accidents his cars were involved in:

$$
\gamma_{\text{count-distinct}(\text{report\_number})}(T_{\text{accidents}})
$$

#### (iii) Update damage amounts for car "AABB2019" in accident "AR201930" to \$3000

1. First we define the selection predicate $P$ that matches car `"AABB2019"` in accident report `"AR201930"`:

$$
P \equiv (\text{car} = \text{"AABB2019"} \land \text{report\_number} = \text{"AR201930"})
$$

2. Next we filter `participated` using $\sigma_P$ to extract the target row:

$$
T_{\text{target}} \leftarrow \sigma_P(\text{participated})
$$

3. Then we project `driver_id`, `car`, `report_number`, and the new damage amount `3000`:

$$
T_{\text{updated}} \leftarrow \Pi_{\text{driver\_id}, \text{car}, \text{report\_number}, 3000}(T_{\text{target}})
$$

4. Next we subtract $T_{\text{target}}$ from `participated` to keep all other accident participation rows untouched:

$$
T_{\text{untouched}} \leftarrow \text{participated} - T_{\text{target}}
$$

5. Finally, we union the updated row with the untouched rows and assign the result back to `participated`:

$$
\text{participated} \leftarrow T_{\text{updated}} \cup T_{\text{untouched}}
$$

### 🎯 HYE-01 · Practice Exercise 2.8 · Universal Comparison & Payroll Extremes in Relational Algebra

> **Source:** Silberschatz 7e · Chapter 2 (Practice Exercise 2.8)  
> **Exam Relevance:** Prime Overdue Advanced Relational Algebra Drill  
> **Key Tested Concept:** Simulating universal quantification ("earns more than every manager") using Cartesian product and set difference.

**Problem Statement:**
> Using the employee database schema:
> - $\text{employee}(\underline{\text{person\_name}}, \text{street}, \text{city})$
> - $\text{works}(\underline{\text{person\_name}, \text{company\_name}}, \text{salary})$
> - $\text{company}(\underline{\text{company\_name}}, \text{city})$
> - $\text{manages}(\underline{\text{person\_name}}, \text{manager\_name})$
> Write relational algebra expressions to:
> 1. Find all employees who earn more than **every manager** of "Small Bank Corporation".
> 2. Find the company that has the **smallest payroll** (sum of salaries).

**Model Exam-Style Solution:**

1. **Query 1: Employees earning more than EVERY manager of "Small Bank Corporation":**
   - **Step 1: Identify all managers of "Small Bank Corporation" and their salaries:**
     A manager of "Small Bank Corporation" is an employee who works for "Small Bank Corporation" and manages other employees:
     $$
     \text{MgrSalaries} \leftarrow \Pi_{\text{works.person\_name}, \text{works.salary}}\big(\sigma_{\text{company\_name} = \text{'Small Bank Corporation'}}(\text{works}) \bowtie_{\text{works.person\_name} = \text{manages.manager\_name}} \text{manages}\big)
     $$
   - **Step 2: Find employees who earn LESS THAN OR EQUAL TO at least one manager:**
     - Pair all employees with these managers using a theta join to identify existential violations:
       $$
       \text{NotHigher} \leftarrow \Pi_{\text{works.person\_name}}\big(\text{works} \bowtie_{\text{works.salary} \le \text{mgr.salary}} \rho_{\text{mgr}}(\text{MgrSalaries})\big)
       $$
   - **Step 3: Set Difference:** All employees minus those who earn less than or equal to some manager:
     $$
     \text{Result} \leftarrow \Pi_{\text{person\_name}}(\text{works}) - \text{NotHigher}
     $$

2. **Query 2: Company with the smallest payroll:**
   - **Step 1: Compute total payroll per company using extended aggregation ($\gamma$):**
     $$
     \text{Payrolls} \leftarrow {}_{\text{company\_name}}\gamma_{\text{sum}(\text{salary}) \ \text{as} \ \text{tot\_payroll}}(\text{works})
     $$
   - **Step 2: Find all companies that have a payroll LARGER than some other company:**
     $$
     \text{NotSmallest} \leftarrow \Pi_{\text{Payrolls.company\_name}}\big(\text{Payrolls} \bowtie_{\text{Payrolls.tot\_payroll} > \text{P2.tot\_payroll}} \rho_{\text{P2}}(\text{Payrolls})\big)
     $$
   - **Step 3: Set Difference:**
     $$
     \text{Result} \leftarrow \Pi_{\text{company\_name}}(\text{Payrolls}) - \text{NotSmallest} \quad \blacksquare
     $$

**💡 RUET Exam Takeaway:**
To express universal quantification ("greater than ALL $X$") in pure relational algebra:
1. Find all pairs where $\text{value} \le X$ (existential violation).
2. Project and subtract from the universe: $\text{Universe} - \text{Violations}$.

## ⚡ Exam Tips & Common Mistakes

1. **Write Relational Algebra, Not SQL:** When the prompt states "Not SQL", never write `SELECT`, `UPDATE`, `WHERE`, or `GROUP BY`. Use Greek letters ($\sigma, \Pi, \rho, \gamma$) and relational operators ($\bowtie, \times, -, \cup, \cap$).
2. **Include Untouched Tuples in Updates:** An update in relational algebra is not an in-place modification. Always compute $T_{\text{untouched}} = r - T_{\text{target}}$ and take its union with the modified tuples.
3. **Use count-distinct for Real-World Entities:** When counting persons or accident reports across joined tables, write `count-distinct`. A plain `count` inflates counts whenever a person owns multiple vehicles or participates in multiple events.
4. **Natural Join Name Collision Trap:** If two relations share an attribute name that represents different things, a natural join will mistakenly equate them. Check attribute names before using $\bowtie$. If names differ (such as `owns.license` and `participated.car`), write an explicit theta join $\bowtie_{\text{owns.license} = \text{participated.car}}$.
5. **Use Assignment Notation for Clean Steps:** Complex queries written as massive single-line expressions often lead to missing parentheses. Break your solution into named intermediate steps using $\leftarrow$. Examiners reward clear, structured steps with full marks.
