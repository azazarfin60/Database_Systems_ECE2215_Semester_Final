# T09.4: Concurrent Execution and Schedules

> **Topic:** T09: Transactions, ACID & Anomalies | **Priority:** 🟢 Foundational Priority | **Exam Frequency:** 1/7 finals + CT-04 Q2 (4 final marks + 4 CT marks = 8 marks total)  
> **Sources:** Silberschatz 7e Ch. 17 (§17.1, §17.5, pp. 799, 808–812) · Lecture Deck 07 (Slides 10–15) · Raidah Class Notes (p. 26)

## Why This Topic Matters

In a real multi-user database, running transactions strictly one after another (serially) leaves expensive hardware sitting idle and forces users to wait in long queues. To keep the system fast, database engines interleave operations from multiple transactions at the same time, just like multiprogramming in an operating system. Exam questions on this topic focus on two classic comparisons: contrasting a **serial schedule** against a **concurrent schedule**, and contrasting a **serial schedule** against a **serializable schedule**. Clear comparison tables and a solid explanation of how CPU and disk operations overlap will earn you full marks.

---

## 📝 Key Definitions

> **Transaction:** "A **transaction** is a **unit** of program execution that accesses and possibly updates various data items. ... A transaction is delimited by statements (or function calls) of the form **begin transaction** and **end transaction**. The transaction consists of all operations executed between the **begin transaction** and **end transaction**."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.1 (p. 799)

> **Schedule:** "The execution sequences just described are called **schedules**. They represent the chronological order in which instructions are executed in the system. Clearly, a schedule for a set of transactions must consist of all instructions of those transactions and they must preserve the order in which the instructions appear in each individual transaction."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.5 (p. 810)

> **Serial Schedule:** "Each serial schedule consists of a sequence of instructions from various transactions, where the instructions belonging to one single transaction appear together in that schedule."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.5 (p. 811)

> **Serializable Schedule:** "We can ensure consistency of the database under concurrent execution by making sure that any schedule that is executed has the same effect as a schedule that could have occurred without any concurrent execution. That is, the schedule should, in some sense, be equivalent to a serial schedule. Such schedules are called **serializable** schedules."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.5 (p. 812)

> **Throughput and Resource Utilization:** "A transaction consists of many steps. Some involve I/O activity; others involve CPU activity. The CPU and the disks in a computer system can operate in parallel. ... All of this increases the throughput of the system—that is, the number of transactions executed in a given amount of time. Correspondingly, the processor and disk utilization also increase..."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.5 (p. 808)

## The Need for Concurrent Execution

If a database ran only one transaction at a time from start to finish, keeping data consistent would be effortless. However, strict one-by-one execution creates a huge performance bottleneck. Because of this, every modern DBMS runs multiple transactions concurrently, for the exact same reasons that operating systems use multiprogramming.

### Two Major Advantages of Concurrency

1. **Higher Processor and Disk Utilization (Better Throughput):**
   Every transaction is a mix of fast CPU steps (math, comparisons) and slow disk I/O steps (reading pages from disk or writing log records). Because the CPU and the disk controller are separate hardware components, they can work in parallel. When transaction $T_1$ pauses to wait for a slow disk read, the CPU does not just sit idle. Instead, it immediately switches over to run calculations for another transaction $T_2$. This overlap keeps both the processor and the disks busy, boosting **system throughput** (the number of transactions finished per second).

2. **Lower Average Response Time (Shorter Waiting Times):**
   Database workloads mix tiny, 5-millisecond tasks (like checking an ATM balance) with massive, 2-hour batch jobs (like calculating monthly interest for every customer in a bank). Under a serial schedule, if your 5-millisecond balance check arrives right after a 2-hour audit starts, you have to stare at the screen for 2 hours. By interleaving operations across active transactions, short queries finish almost immediately without getting stuck behind long batch jobs, which sharply cuts the **average response time** and waiting time for users.

## Anatomy of a Schedule

A **schedule** is simply the timeline showing the exact chronological order in which the DBMS executes instructions from a group of transactions.

### Three Rules Every Valid Schedule Must Follow

For an execution timeline $S$ over transactions $\{T_1, T_2, \dots, T_n\}$ to count as a valid schedule, it must obey three basic rules:
1. **Completeness:** It must contain every single instruction belonging to all participating transactions.
2. **Internal Order Preservation:** It must keep each individual transaction's own steps in their original program order. For example, if $T_1$ is written to do $\text{read}(A)$ before $\text{write}(A)$, then $T_1$'s $\text{read}(A)$ must still appear before $T_1$'s $\text{write}(A)$ in the combined schedule.
3. **Explicit Termination:** Each transaction must end with either a `commit` (success) or an `abort` (rollback).

## Comparing Schedule Classes

To master exam questions on scheduling, you need to keep three terms straight: **Serial**, **Concurrent**, and **Serializable**.

### Intuitive Analogy: Checkout Lanes at a Grocery Store

- **Serial Schedule:** One cashier serves Customer 1 completely from first item to receipt before scanning a single item for Customer 2. It is 100% mistake-free, but if Customer 1 has two full carts, Customer 2 (holding one bottle of water) waits forever. For $n$ transactions, there are $n!$ possible serial orders.
- **Concurrent Schedule:** The cashier switches back and forth between customers (scanning a few items for Customer 1 while Customer 2 looks for their wallet). This is much faster, but if the cashier forgets whose items are on the belt, Customer 1 gets charged for Customer 2's groceries. The number of possible interleaved schedules is vastly greater than $n!$.
- **Serializable Schedule:** A concurrent schedule where the cashier interleaves work to save time, yet every customer still walks out with the exact same receipt and total they would have gotten in a one-by-one line. It gives you the speed of concurrency with the safety of serial execution.

### Comparison 1: Serial Schedule vs. Concurrent Schedule

| Feature | Serial Schedule | Concurrent Schedule |
| :--- | :--- | :--- |
| **Execution Pattern** | Non-interleaved. One transaction finishes completely before the next starts. | Interleaved. Operations from different transactions overlap in time. |
| **Hardware Usage** | Low. The CPU sits idle whenever the active transaction waits for disk I/O. | High. The CPU runs one transaction while the disk handles I/O for another. |
| **Waiting & Response Time** | High average response time because short queries wait behind long batch jobs. | Low average response time because short queries finish quickly. |
| **Concurrency Control** | None needed. Execution is safe from interference by default. | Required. Needs locking or timestamp rules unless you want corrupted data. |
| **Number of Schedules ($n$ txns)** | Exactly $n!$ possible serial orders. | Vastly greater than $n!$ due to all possible interleavings. |

### Comparison 2: Serial Schedule vs. Serializable Schedule

| Feature | Serial Schedule | Serializable Schedule |
| :--- | :--- | :--- |
| **Instruction Interleaving** | Never allowed. Transactions run strictly one after another. | Allowed. Instructions from multiple transactions interleave over time. |
| **Throughput & Speed** | Low concurrency and low system throughput. | High concurrency and high system throughput. |
| **Final Database State** | Always consistent by default. | Always consistent because its final effect matches some serial schedule. |
| **Testing Needed?** | None. Trivially safe. | Must be verified (for example, by checking for cycles in a precedence graph). |
| **Subset Relationship** | Every serial schedule is automatically serializable. | Most serializable schedules are interleaved (not strictly serial). |

## Worked Example: Tracing Serial, Serializable, and Corrupted Schedules

Let's trace the classic textbook example with two accounts, $A = 1000$ and $B = 2000$, where the total money must remain $A + B = 3000$.
- **Transaction $T_1$:** Transfers \$50 from $A$ to $B$.
- **Transaction $T_2$:** Transfers 10% of $A$'s current balance to $B$.

### Case 1: Serial Schedule ($T_1$ Followed by $T_2$)

Here, $T_1$ runs all the way to completion before $T_2$ starts:

| Step | $T_1$ Operations | $T_2$ Operations | Account $A$ (\$) | Account $B$ (\$) | Sum $A+B$ (\$) |
| :---: | :--- | :--- | :---: | :---: | :---: |
| 1–3 | $\text{read}(A),\; A := A - 50,\; \text{write}(A)$ | | **950** | 2000 | 2950 |
| 4–7 | $\text{read}(B),\; B := B + 50,\; \text{write}(B),\; \text{commit}$ | | 950 | **2050** | **3000** |
| 8–11 | | $\text{read}(A),\; \text{temp} := A * 0.1,\; A := A - \text{temp},\; \text{write}(A)$ | **855** | 2050 | 2905 |
| 12–15 | | $\text{read}(B),\; B := B + \text{temp},\; \text{write}(B),\; \text{commit}$ | **855** | **2145** | **3000** |

- **Result:** $A = 855$, $B = 2145$, and the total sum is \$3000.
- *(Note: If we ran the opposite serial order $T_2 \to T_1$ instead, $T_2$ would move 10% of \$1000 = \$100 first, and then $T_1$ would move \$50, ending with $A = 850, B = 2150$, which also sums to \$3000. Different serial orders can produce different final balances, and both are considered valid!)*

### Case 2: Concurrent and Serializable Schedule

Now watch what happens if the CPU switches to $T_2$ right after $T_1$ finishes updating $A$:

| $T_1$ | $T_2$ | What Happens |
| :--- | :--- | :--- |
| $\text{read}(A),\; A := A - 50,\; \text{write}(A)$ | | $T_1$ updates $A$ from \$1000 to **950** |
| | $\text{read}(A),\; \text{temp} := A * 0.1,\; A := A - \text{temp},\; \text{write}(A)$ | $T_2$ reads $A = 950$, sets $\text{temp} = 95$, and writes $A =$ **855** |
| $\text{read}(B),\; B := B + 50,\; \text{write}(B),\; \text{commit}$ | | $T_1$ updates $B$ from \$2000 to **2050** |
| | $\text{read}(B),\; B := B + \text{temp},\; \text{write}(B),\; \text{commit}$ | $T_2$ reads $B = 2050$, adds \$95, and writes $B =$ **2145** |

- **Result:** Even though $T_1$ and $T_2$ were interleaved, $T_2$ saw $T_1$'s updated value for both $A$ and $B$. The final balances ($A = 855, B = 2145$) and total (\$3000) match Serial Schedule $T_1 \to T_2$ down to the penny. Thus, this concurrent schedule is **serializable**.

### Case 3: Concurrent but Non-Serializable (Corrupted) Schedule

What if $T_2$ reads $A = 1000$ *before* $T_1$ deducts \$50 (so $T_2$ calculates $\text{temp} = 100$), and then $T_1$ overwrites $A = 950$ only for $T_2$ to overwrite $A = 900$, while both add their transfers to $B$?
- Final balances become $A = 900$ (or 950) and $B = 2150$.
- The sum $A + B$ becomes $950 + 2150 = 3100$, creating \$100 out of thin air!
- Because no serial order could ever produce \$3100, this concurrent schedule is **not serializable**.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.6(a) · Definitions & Serial vs. Serializable Schedule

> **Appeared:** 2018 Q.6(a) (4 marks)

> **Question:**
>
> Define transaction and schedule. What is the difference between serial schedule and serializable schedule?

**Full Answer:**

#### 1. Definition of Transaction

A **transaction** is a logical unit of program execution that accesses and possibly updates various data items in a database. It is bounded by `begin transaction` and `end transaction` (`commit` or `abort`) statements. To the user, a transaction behaves as a single all-or-nothing operation that moves the database from one consistent state to another.

#### 2. Definition of Schedule

A **schedule** is the chronological sequence of instructions executed by the system for a set of concurrent transactions. To be valid, a schedule must contain all instructions of every participating transaction and must preserve the original internal order of instructions within each individual transaction.

#### 3. Difference Between Serial Schedule and Serializable Schedule

| Comparison Basis | Serial Schedule | Serializable Schedule |
| :--- | :--- | :--- |
| **Instruction Interleaving** | Strictly sequential. One transaction runs completely from start to finish before the next transaction begins. | Interleaved. Instructions from different transactions overlap and alternate over time. |
| **Hardware Concurrency** | Zero concurrency. The CPU sits idle whenever the running transaction waits for disk I/O. | High concurrency. The CPU and disk work in parallel across multiple active transactions. |
| **Throughput & Waiting Time** | Low throughput and long waiting times when short queries get stuck behind large batch jobs. | High throughput and fast average response time for short queries. |
| **Consistency Guarantee** | Guaranteed consistent automatically because there is no concurrent interference. | Guaranteed consistent because its final effect is identical to some serial schedule. |
| **Testing Requirement** | No verification test is needed. | Must be checked for serializability (such as testing its precedence graph for cycles). |
| **Relationship** | Every serial schedule is trivially serializable. | Most serializable schedules are concurrent (non-serial). |

### 🎯 GQ2 · CT-04 Q.02 · Serial vs. Concurrent Schedule & Advantages of Concurrency

> **Appeared:** CT-04 Q.02 (4 marks)

> **Question:**
>
> Differentiate between a serial schedule and a concurrent schedule. Mention two advantages of concurrent execution of transactions.

**Full Answer:**

#### 1. Difference Between Serial Schedule and Concurrent Schedule

| Comparison Basis | Serial Schedule | Concurrent Schedule |
| :--- | :--- | :--- |
| **Execution Pattern** | Non-interleaved. Each transaction finishes all of its steps before the next transaction starts. | Interleaved. Steps from multiple transactions are mixed together over time. |
| **Resource Utilization** | Low. The CPU waits idly whenever the current transaction performs slow disk reads or writes. | High. The CPU runs calculations for one transaction while the disk serves another. |
| **Average Response Time** | High. Short transactions have to wait in line behind long-running transactions. | Low. Short transactions get interleaved CPU slices and finish quickly. |
| **Concurrency Control** | Not required, since transactions never overlap. | Essential. Without locking or timestamp rules, interleaving can corrupt the database. |

#### 2. Two Advantages of Concurrent Execution of Transactions

1. **Higher Processor and Disk Utilization (Increased Throughput):**  
   Every transaction performs both CPU calculations and disk I/O operations. Because the computer's CPU and disk subsystem operate independently, concurrent execution lets them work in parallel. While transaction $T_1$ is waiting for a disk page to load, the CPU can execute instructions for transaction $T_2$. Keeping both hardware components busy increases the total number of transactions completed per second (**throughput**).

2. **Reduced Average Response Time (Shorter Waiting Time):**  
   Transactions vary widely in length, from tiny balance lookups to multi-hour batch updates. If transactions ran serially, a quick query arriving right behind a multi-hour job would be forced to wait hours before starting. By interleaving operations concurrently, short transactions share CPU cycles and finish right away, which greatly reduces the **average response time** and waiting delay for users.

## ⚡ Exam Tips & Common Mistakes

1. **Never Treat "Concurrent" and "Serializable" as Synonyms:** A **concurrent** schedule is *any* interleaved schedule, including bad ones that corrupt data. A **serializable** schedule is a *safe* concurrent schedule whose outcome matches a serial run.
2. **Name Both Hardware Parts (CPU + Disk):** When explaining throughput, explicitly state that the **CPU** runs one transaction while the **disk** performs I/O for another. Examiners look for this exact parallel mechanism.
3. **Remember the $n!$ Count:** For $n$ transactions, there are exactly $n!$ serial schedules, while the number of possible concurrent schedules is much larger than $n!$.
4. **Always Use Comparison Tables:** Whenever a question asks to "differentiate" or find "the difference between" schedule types, write a clean 4-to-6 row table with labeled comparison criteria in the left column.
