# T05.9: TRUNCATE vs. DELETE

> **Topic:** T05 — SQL (DDL, DML, Aggregates, Subqueries) | **Priority:** 🟢 Foundation | **Exam Frequency:** 1/7 finals (2 marks) [2023 Q.6(a)]  
> **Sources:** MySQL 8.0 Reference Manual (§13.1.37, §13.2.2) · Silberschatz 7e Ch. 3 (§3.2.3, §3.9.1) · Lecture Deck 03 (Slide 54) · Fahim Notes (p. 50)

## Why This Topic Matters

The difference between `TRUNCATE` and `DELETE` is a classic database interview and exam question. Although both commands remove rows from a table, they work at completely different levels inside the database engine. `DELETE` is a row-by-row Data Manipulation Language (DML) command that logs every single row removal so you can undo it with `ROLLBACK`. In contrast, `TRUNCATE` is a table-level Data Definition Language (DDL) command that wipes the table's storage pages all at once and cannot be rolled back in MySQL. RUET tested this exact comparison in 2023 Q.6(a) for 2 marks, where a clean comparison table earns full credit right away.

---

## 📝 Key Definitions

> **DELETE Statement:** The `DELETE` statement is a DML command that removes rows from a table one by one. You can attach a `WHERE` clause to remove only specific rows, or omit `WHERE` to empty the whole table. Because it logs every deleted row, `DELETE` fires row-level delete triggers and can be undone with `ROLLBACK`.

> **TRUNCATE TABLE Statement:** The `TRUNCATE TABLE` statement is a DDL command that empties a table all at once by dropping and recreating its underlying data pages. It does not allow a `WHERE` clause, skips row-level delete triggers, resets the `AUTO_INCREMENT` counter back to `1`, and cannot be rolled back in MySQL.

> **DROP TABLE Statement:** The `DROP TABLE` statement is a DDL command that permanently removes an entire table from the database. Unlike `DELETE` and `TRUNCATE`, which keep the empty table schema intact, `DROP TABLE` destroys both the stored rows and the table definition itself.

## Architectural Mechanics: DDL vs. DML

### Intuitive Analogy: Erasing Lines vs. Ripping Out Pages vs. Shredding the Notebook
Think of a database table as a lined notebook:
- **`DELETE`** is like using an eraser to rub out specific lines one by one. You can choose which lines to erase (`WHERE`), and because you keep a careful undo log of every line you erased, you can restore them (`ROLLBACK`) if you change your mind. Also, the page numbering (`AUTO_INCREMENT`) keeps counting up from where you left off.
- **`TRUNCATE`** is like ripping out all the written pages at once and putting in fresh blank paper while keeping the notebook cover and column headers intact. It is super fast, resets the numbering back to `1`, and cannot be undone.
- **`DROP`** is like throwing the entire notebook into the shredder. Both the data and the table structure itself are gone.

### 1. How DELETE Executes (Row-by-Row DML)
When you run `DELETE FROM table_name WHERE condition;`, the query engine scans the table for matching rows, locks each row individually, and removes them one at a time.
- Because the database writes an undo-log record for every single deleted row, you can undo the entire operation before committing by running `ROLLBACK`.
- Any `BEFORE DELETE` or `AFTER DELETE` triggers attached to the table will fire once for every deleted row.
- Even if you delete every row in the table (`DELETE FROM student;`), `DELETE` does **not** reset the `AUTO_INCREMENT` counter. The next row you insert will just continue from the old counter value.

```sql
/* Deleting specific rows using DML */
DELETE FROM student
WHERE dept_name = 'History';

/* Deleting all rows while keeping the auto-increment counter as-is */
DELETE FROM student;
```

### 2. How TRUNCATE Executes (Table-Level DDL)
When you run `TRUNCATE TABLE table_name;`, the database skips row-by-row scanning completely. In MySQL InnoDB, it simply drops the underlying data pages and creates a fresh, empty `.ibd` storage file with the same schema.
- Because it frees data pages in bulk instead of logging each row, `TRUNCATE` is dramatically faster on large tables.
- In MySQL, `TRUNCATE` is a DDL statement that triggers an automatic `COMMIT` before and after it runs, which means **you cannot undo it with `ROLLBACK`**.
- Because individual rows are never scanned, row-level `DELETE` triggers (`BEFORE DELETE` / `AFTER DELETE`) do **not** fire.
- The `AUTO_INCREMENT` counter is reset all the way back to its starting value (usually `1`).

```sql
/* Instantly emptying a table and resetting auto-increment via DDL */
TRUNCATE TABLE student;
```

### 3. Contrast with DROP TABLE
While both `DELETE` and `TRUNCATE` leave the empty table structure (columns, constraints, and indexes) intact so you can keep inserting new rows later, `DROP TABLE table_name;` deletes the data **and** removes the table definition from the database catalog. If you try to query a table after dropping it, MySQL returns a `Table doesn't exist` error.

## Side-by-Side 8-Point Comparison Matrix

| Comparison Feature | `DELETE FROM` | `TRUNCATE TABLE` | `DROP TABLE` |
| :--- | :--- | :--- | :--- |
| **SQL Category** | **DML** (Data Manipulation) | **DDL** (Data Definition) | **DDL** (Data Definition) |
| **Row Filtering (`WHERE`)** | Supported (can delete specific rows) | Not supported (always empties table) | Not applicable |
| **Table Structure / Schema** | Kept intact (table stays empty) | Kept intact (table stays empty) | Completely removed from database |
| **Transaction Rollback** | Yes (can roll back inside a transaction) | No (triggers an implicit commit in MySQL) | No (triggers an implicit commit in MySQL) |
| **Trigger Execution** | Fires `BEFORE/AFTER DELETE` triggers | Skips all row-level delete triggers | Skips delete triggers |
| **`AUTO_INCREMENT` Counter** | Keeps the current sequence value | Resets counter back to start (1) | Counter is destroyed with the table |
| **Execution Speed** | Slower (scans and logs row by row) | Very fast (frees data pages in bulk) | Instant (drops catalog & file) |
| **Disk Space Reclamation** | Leaves freed space inside table pages | Returns allocated data pages to the OS | Frees all disk space completely |

## Foreign Key Traps and InnoDB Restrictions

1. **Foreign Key Block on `TRUNCATE`:** In MySQL InnoDB, if a parent table is referenced by a `FOREIGN KEY` from any child table, running `TRUNCATE TABLE` on the parent fails with Error 1701, even if the child table is currently empty or uses `ON DELETE CASCADE`! (Because `TRUNCATE` does not scan rows, it cannot trigger cascading deletes.)
2. **The Maintenance Workaround:** If you need to truncate a referenced table during testing, you have to temporarily turn off foreign-key checks first:
   ```sql
   SET FOREIGN_KEY_CHECKS = 0;
   TRUNCATE TABLE parent_table;
   SET FOREIGN_KEY_CHECKS = 1;
   ```
3. **`DELETE` Works Normally with Foreign Keys:** Because `DELETE FROM` processes rows one by one, it works smoothly with foreign keys and triggers `ON DELETE CASCADE` on child tables whenever configured.

## Transaction and Rollback Walkthrough

### Scenario A: Testing DELETE with ROLLBACK
```sql
START TRANSACTION;

/* Delete all 12 rows from instructor */
DELETE FROM instructor;

/* Check row count inside the transaction */
SELECT COUNT(*) FROM instructor; -- Output: 0

/* Undo the deletion using the undo log */
ROLLBACK;

/* Check row count again */
SELECT COUNT(*) FROM instructor; -- Output: 12 (All original rows are back!)
```

### Scenario B: Testing TRUNCATE with Attempted ROLLBACK
```sql
START TRANSACTION;

/* Truncate table instructor */
TRUNCATE TABLE instructor; -- Fires an implicit COMMIT right away!

/* Try to undo the truncate */
ROLLBACK;

/* Check row count */
SELECT COUNT(*) FROM instructor; -- Output: 0 (Rows are permanently gone!)
```

## Worked Example: Auto-Increment Behavior After DELETE vs. TRUNCATE

Suppose we create an `orders` table and insert three customer orders:

```sql
CREATE TABLE orders (
    order_id INT AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(50),
    order_amount NUMERIC(10, 2)
);

INSERT INTO orders (customer_name, order_amount) VALUES 
('Rahim', 1200.00),
('Karim', 3400.50),
('Tanvir', 850.00);
-- Three rows inserted (IDs 1, 2, 3), so the next AUTO_INCREMENT value is 4
```

### Case 1: Emptying with `DELETE FROM`
```sql
DELETE FROM orders;
INSERT INTO orders (customer_name, order_amount) VALUES ('Sultana', 500.00);
SELECT * FROM orders;
```
*Result:* Sultana's row gets `order_id = 4` because `DELETE` never resets the `AUTO_INCREMENT` counter.

### Case 2: Emptying with `TRUNCATE TABLE`
```sql
TRUNCATE TABLE orders;
INSERT INTO orders (customer_name, order_amount) VALUES ('Sultana', 500.00);
SELECT * FROM orders;
```
*Result:* Sultana's row gets `order_id = 1` because `TRUNCATE` resets the `AUTO_INCREMENT` counter back to `1`.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.6(a) · Difference Between TRUNCATE and DELETE in SQL

> **Appeared:** 2023 Q.6(a) — (2 marks)

**Question:**

What is the difference between 'Truncate' and 'Delete' in SQL?

**Full Answer:**

`TRUNCATE` and `DELETE` both remove rows from an SQL table, but they work differently under the hood:

| Feature | `TRUNCATE` | `DELETE` |
| :--- | :--- | :--- |
| **Command Category** | **DDL** (Data Definition Language) | **DML** (Data Manipulation Language) |
| **`WHERE` Clause** | Not supported, so it always removes all rows from the table | Supported, so it can filter and delete specific rows |
| **Rollback / Transaction** | Runs an implicit `COMMIT` in MySQL and cannot be rolled back | Logs every deleted row and can be undone with `ROLLBACK` |
| **Triggers** | Does not fire `DELETE` triggers | Fires `BEFORE DELETE` and `AFTER DELETE` triggers for each row |
| **`AUTO_INCREMENT` Counter** | Resets the counter back to its starting value (1) | Keeps the existing counter value unchanged |
| **Execution Speed** | Very fast because it drops and recreates data pages in bulk | Slower because it locks, deletes, and logs rows one by one |

**Summary:** Use `DELETE` when you want to remove specific rows with a `WHERE` clause or need the safety of `ROLLBACK`. Use `TRUNCATE` when you want to wipe an entire table clean and reset its `AUTO_INCREMENT` counter as fast as possible.

---

### 🎯 GQ2 · Exam Variant · TRUNCATE vs. DELETE vs. DROP

> **Appeared:** Anticipated Exam Variant — (3 marks)

**Question:**

Compare TRUNCATE, DELETE, and DROP commands in SQL with respect to command category, table schema, and rollback capability.

**Full Answer:**

1. **DELETE (DML):**
   - Removes specific rows (using `WHERE`) or all rows one by one.
   - Keeps the table schema, columns, and indexes intact.
   - Logs each row deletion in the undo log, so changes can be undone using `ROLLBACK`.
2. **TRUNCATE (DDL):**
   - Empties all rows from the table at once by resetting its data pages.
   - Keeps the table schema, columns, and indexes intact.
   - Causes an implicit commit in MySQL, so changes cannot be undone using `ROLLBACK`.
3. **DROP (DDL):**
   - Deletes all table data along with the entire table schema, constraints, and indexes.
   - Removes the table completely from the database catalog.
   - Causes an implicit commit, so changes cannot be undone using `ROLLBACK`.

## ⚡ Exam Tips & Common Mistakes

1. **Command Category Trap:** Never classify `TRUNCATE` as DML on an exam. In both the SQL standard and MySQL, `TRUNCATE TABLE` is classified as a **DDL** statement.
2. **The Rollback Misconception:** Do not write that `TRUNCATE` can be rolled back in MySQL. Because MySQL treats `TRUNCATE` as DDL, it runs an automatic `COMMIT` that makes the deletion permanent right away.
3. **Tabular Answers Win Full Marks:** On a 2-mark "differentiate between" question, a clean 5-or-6 row comparison table is much faster to write and easier for the examiner to grade than a wall of text.
