# T10.4: Building Serializable and Non-Serializable Schedules

> **Topic:** T10 — Serializability | **Priority:** 🟡 | **Exam Frequency:** 2/7 finals (13 marks)  
> **Sources:** Silberschatz 7e Ch. 17 (§17.1, §17.6, Exercise 17.15 pp. 832–833) · Lecture Deck 07 (Slides 10–21) · Classnote by Raidah (T10)

## Why This Topic Matters

Instead of handing you a finished schedule and asking whether it is serializable, this subtopic flips the task around: **you are given the code of two transactions and asked to build a schedule yourself**. Adapted from the classic Silberschatz Exercise 17.15, this problem has appeared twice on RUET finals for a combined 13 marks. Examiners use it to test whether you can trace `if` conditions across interleaved steps, construct a concurrent schedule that breaks database consistency, and prove why *no* genuinely interleaved execution of two mutually cross-reading transactions can ever be serializable.

---

## 📝 Key Definitions

> **Serializable Schedule:** A concurrent schedule is serializable if its execution produces the exact same outcome and final database state as some serial schedule of the same transactions. Because every serial schedule preserves database consistency, any serializable schedule also keeps the database consistent.

> **Concurrency Control:** Concurrency control is the DBMS mechanism that coordinates simultaneous transactions so they can share system resources safely without corrupting database consistency. It enforces isolation rules to prevent anomalies such as dirty reads, lost updates, and non-serializable schedules.

> **Precedence Graph:** A precedence graph is a directed graph $G = (V, E)$ where each vertex in $V$ is a transaction and each directed edge $T_i \to T_j$ in $E$ represents a read-write, write-read, or write-write conflict on a shared item where $T_i$ acts before $T_j$. The schedule is conflict serializable if and only if this graph has no cycles.

## 1. The Cross-Reading Conditional Pattern

### Intuition: Why Mutual "Check-the-Other-Variable" Guards Clash

Imagine two roommates, $T_1$ and $T_2$, who share two light switches $X$ and $Y$ that both start ON ($X = 1, Y = 1$). Their house rule (the **consistency requirement**) says that *at least one light must stay ON* ($X = 1 \lor Y = 1$).
- $T_1$ checks switch $X$: if $X$ is still ON ($X = 1$), $T_1$ turns $Y$ OFF ($Y := 0$).
- $T_2$ checks switch $Y$: if $Y$ is still ON ($Y = 1$), $T_2$ turns $X$ OFF ($X := 0$).

If they go **one at a time** (serially), the first roommate turns one switch OFF, and the second roommate sees that it is now OFF and leaves the other switch ON. The house rule stays safe.

But if they **both look at the switches at the same time** before flipping anything, both see $X = 1$ and $Y = 1$, so both flip their target switch OFF! The house ends up in the dark ($X = 0, Y = 0$), breaking the consistency requirement.

---

## 2. Illustrative Mini-Example: Tracing Serial vs. Interleaved Runs

Let us trace this two-switch mini-example with initial values $X = 1, Y = 1$ and consistency rule $X = 1 \lor Y = 1$:

```text
T1:                              T2:
  read(X);                         read(Y);
  read(Y);                         read(X);
  if X = 1 then Y := 0;            if Y = 1 then X := 0;
  write(Y);                        write(X);
```

### Step 1: Verify That Both Serial Orders Preserve Consistency
- **Serial order $\langle T_1, T_2 \rangle$:** $T_1$ reads $X = 1, Y = 1$, sees `X = 1` is true, and writes $Y = 0$. Next, $T_2$ reads $Y = 0, X = 1$, sees `Y = 1` is false, and writes $X = 1$ unchanged. The final state is $X = 1, Y = 0$, which satisfies $X = 1 \lor Y = 1$.
- **Serial order $\langle T_2, T_1 \rangle$:** By symmetry, $T_2$ sets $X = 0$ first, so $T_1$ sees `X = 1` is false and leaves $Y = 1$. The final state is $X = 0, Y = 1$, which also satisfies $X = 1 \lor Y = 1$.

### Step 2: How to Build a Non-Serializable Schedule (Read-First Interleaving)
Whenever an exam asks you to construct a **non-serializable** concurrent schedule for cross-reading transactions, use this simple recipe: **let both transactions finish all of their `read` steps before either transaction executes its `write` step.**

| Step | $T_1$ | $T_2$ | What Happens |
| :---: | :--- | :--- | :--- |
| 1 | `read(X);` | | $T_1$ reads initial $X = 1$ |
| 2 | | `read(Y);` | $T_2$ reads initial $Y = 1$ |
| 3 | `read(Y);` | | $T_1$ reads initial $Y = 1$ |
| 4 | | `read(X);` | $T_2$ reads initial $X = 1$ |
| 5 | `if X = 1 then Y := 0;`<br>`write(Y);` | | $T_1$ sees $X = 1$ and writes $Y = 0$ |
| 6 | | `if Y = 1 then X := 0;`<br>`write(X);` | $T_2$ sees $Y = 1$ and writes $X = 0$ |

- **Broken Consistency:** The schedule ends with $X = 0$ and $Y = 0$, violating $X = 1 \lor Y = 1$.
- **Precedence Graph Cycle:** $T_1$ reads $X$ (Step 1) before $T_2$ writes $X$ (Step 6), giving $T_1 \to T_2$. Meanwhile, $T_2$ reads $Y$ (Step 2) before $T_1$ writes $Y$ (Step 5), giving $T_2 \to T_1$. That creates the cycle $T_1 \leftrightarrow T_2$.

---

## 3. Why NO Genuinely Concurrent Execution Can Be Serializable

A favorite follow-up question on RUET finals is: *"Is there a concurrent execution of $T_1$ and $T_2$ that produces a serializable schedule?"*

When two transactions have the structure above, where **each transaction reads the other's target item first and performs its own `write` as its very last instruction**, the answer for any genuinely interleaved schedule is **No**:

1. **Look at $T_2$'s final instruction (`write`):** For $T_1$ and $T_2$ to overlap in time, $T_1$ cannot wait until after $T_2$'s final `write` to start reading. If $T_2$ already finished its final `write` before $T_1$ even started its first `read`, then $T_2$ ran completely before $T_1$ ($\langle T_2, T_1 \rangle$), which is a strictly serial schedule, not an interleaved concurrent one. Thus, in any genuinely interleaved run, $T_1$'s `read` must happen before $T_2$'s final `write`, forcing the edge $T_1 \to T_2$.
2. **Look at $T_1$'s final instruction (`write`):** By the exact same logic, if $T_1$ finished its final `write` before $T_2$ started its first `read`, the schedule would just be the serial execution $\langle T_1, T_2 \rangle$. So in any genuinely interleaved run, $T_2$'s `read` must happen before $T_1$'s final `write`, forcing the reverse edge $T_2 \to T_1$.

Because every genuinely interleaved schedule forces both $T_1 \to T_2$ and $T_2 \to T_1$, every concurrent interleaving creates the cycle $T_1 \leftrightarrow T_2$. Only the two non-interleaved serial runs ($\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$) are serializable.

## 4. Navigating the 2019 Q.4(a) Paper Misprints

In the 2019 semester final, the examiner adapted Silberschatz Exercise 17.15 by changing the variables to $P$ and $Q$ with initial values $P = 5, Q = 5$ and consistency rule $P = 5 \lor Q = 5$. However, the printed question paper introduced two quirks you need to know how to handle:

1. **Condition Value Mismatch:**
   - The initial values are $P = 5, Q = 5$, yet the printed `if` statements check `if P=10 then Q:=Q-5;` and `if Q=10 then P:=P+5;`.
   - Because $5 \neq 10$, both `if` conditions evaluate to **false** right from the start, so both transactions simply write back the unchanged values $5$ and $5$.
2. **Duplicate Sub-Question Printing:**
   - Sub-question (i) asks to *"Show a concurrent execution of T1 and T2 that produces a serializable schedule,"* and sub-question (ii) is printed identically to (i) as *"Is there a concurrent execution of T1 and T2 that produces a serializable schedule?"*

### How to Write a Bulletproof Exam Answer for 2019 Q.4(a)
To get full marks no matter which marking key the grader uses:
1. Trace the literal printed values ($P = 5, Q = 5$ against `P = 10` / `Q = 10`) and note that the conditions evaluate to false.
2. In part (i), show the conflict-serializable schedule where $T_1$'s operations precede $T_2$'s conflicting operations ($T_1 \to T_2$).
3. In part (ii), note the duplicate printing and show the classic interleaved schedule where both transactions read before either writes, producing the precedence cycle $T_1 \leftrightarrow T_2$ (and showing how $P = 10, Q = 0$ would violate $P = 5 \lor Q = 5$ under the intended `if P = 5` / `if Q = 5` guards).

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.5(c) · Building Non-Serializable Schedule and Concurrency Proof

> **Appeared:** 2017 Q.5(c) (6 marks)

**Question:**

Consider the following two transactions.

**T1:**  
  `read(A);`  
  `read(B);`  
  `if A = 0 then B:=B+1;`  
  `write(B);`

**T2:**  
  `read(B);`  
  `read(A);`  
  `if B = 0 then A:=A+1;`  
  `write(A);`

Let the consistency requirement be $A = 0$ or $B = 0$ with $A=B=0$ the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a nonserializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

**Full Answer:**

#### Initial State and Serial Baseline
- Initial values: $A = 0, B = 0$.
- Consistency condition: $A = 0 \lor B = 0$.
- In serial order $\langle T_1, T_2 \rangle$: $T_1$ reads $A=0, B=0$, sets $B := 1$, and writes $B = 1$. Then $T_2$ reads $B=1$. The condition `B = 0` evaluates to false ($1 \neq 0$), so $T_2$ writes $A = 0$. Final state: $A = 0, B = 1$ (consistent).
- In serial order $\langle T_2, T_1 \rangle$: $T_2$ reads $B=0, A=0$, sets $A := 1$, and writes $A = 1$. Then $T_1$ reads $A=1$. The condition `A = 0` evaluates to false ($1 \neq 0$), so $T_1$ writes $B = 0$. Final state: $A = 1, B = 0$ (consistent).

---

#### Part (i): Concurrent Execution Producing a Nonserializable Schedule

Consider the following interleaved execution where both transactions read both items before either executes its write operation:

| Step | Transaction | Instruction Executed | State Description |
| :---: | :---: | :--- | :--- |
| 1 | $T_1$ | `read(A);` | $T_1$ reads initial value $A = 0$ |
| 2 | $T_2$ | `read(B);` | $T_2$ reads initial value $B = 0$ |
| 3 | $T_1$ | `read(B);` | $T_1$ reads initial value $B = 0$ |
| 4 | $T_2$ | `read(A);` | $T_2$ reads initial value $A = 0$ |
| 5 | $T_1$ | `if A = 0 then B:=B+1;`<br>`write(B);` | Condition $0 = 0$ is true $\implies B := 1$. Writes $B = 1$. |
| 6 | $T_2$ | `if B = 0 then A:=A+1;`<br>`write(A);` | Condition $0 = 0$ is true $\implies A := 1$. Writes $A = 1$. |

**Final Database State:**
$$
A = 1 \quad \text{and} \quad B = 1
$$

This violates the consistency requirement $A = 0 \lor B = 0$ because neither variable is 0.

**Proof of Nonserializability:**
- $T_1: \text{read}(A)$ (step 1) occurs before $T_2: \text{write}(A)$ (step 6) $\implies T_1 \longrightarrow T_2$.
- $T_2: \text{read}(B)$ (step 2) occurs before $T_1: \text{write}(B)$ (step 5) $\implies T_2 \longrightarrow T_1$.
- The precedence graph contains the cycle:

$$
T_1 \longleftrightarrow T_2
$$

![2017 Q.5(c) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2017_Q5c_precedence_graph.jpg)
*Figure 10.1: Precedence graph for 2017 Q.5(c) showing the 2-node cycle between T1 and T2.*

- Because the precedence graph has a cycle and ends in an inconsistent state ($A=1, B=1$) that is impossible under any serial schedule, this schedule is **non-serializable**.

---

#### Part (ii): Can Any Concurrent Execution Be Serializable?

**Answer:** **No.**

**Proof:**
For an execution to be genuinely concurrent (interleaved), both transactions must overlap in time:
1. $T_1$ reads $A$ and $T_2$ writes $A$. If $T_1$ reads $A$ before $T_2$ writes $A$, this enforces $T_1 \longrightarrow T_2$. If $T_2$ wrote $A$ before $T_1$ read $A$, $T_2$ would have already completed its execution (since `write(A)` is $T_2$'s final operation), making it a serial schedule $\langle T_2, T_1 \rangle$.
2. $T_2$ reads $B$ and $T_1$ writes $B$. If $T_2$ reads $B$ before $T_1$ writes $B$, this enforces $T_2 \longrightarrow T_1$. If $T_1$ wrote $B$ before $T_2$ read $B$, $T_1$ would have already completed its execution, making it a serial schedule $\langle T_1, T_2 \rangle$.

Therefore, any interleaved concurrent execution forces both dependency edges:
$$
T_1 \longrightarrow T_2 \quad \text{and} \quad T_2 \longrightarrow T_1
$$

This guarantees a directed cycle $T_1 \longleftrightarrow T_2$. Hence, **no concurrent execution of $T_1$ and $T_2$ can produce a serializable schedule**. Only strictly serial executions are serializable.

### 🎯 GQ2 · 2019 Q.4(a) · Concurrency Control and Serializable/Non-Serializable Schedules

> **Appeared:** 2019 Q.4(a) (7 marks)

**Question:**

What is concurrency control? Consider the following two transactions.

**T1:**  
`read (P);`  
`read (Q);`  
`if P=10 then Q:=Q-5;`  
`write (Q);`

**T2:**  
`read (Q);`  
`read (P);`  
`if Q=10 then P:=P+5;`  
`write (P);`

Let the consistency requirement be P=5 or Q=5 with P=Q=5 the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a serializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

*(Note: In the printed question paper, sub-question (ii) is printed identically to (i) as "Is there a concurrent execution of T1 and T2 that produces a serializable schedule?")*

**Full Answer:**

#### 1. What is Concurrency Control?
**Concurrency control** is the management subsystem of a DBMS that coordinates the simultaneous execution of transactions. Its primary objectives are:
1. **Preserving Consistency:** Ensure concurrent execution leaves the database in a correct and consistent state.
2. **Enforcing Isolation:** Guarantee that concurrent transactions do not interfere with each other, preventing anomalies like dirty reads, lost updates, and unrepeatable reads.
3. **Maximizing Throughput:** Achieve high system throughput and reduced transaction response times by sharing CPU and disk resources.

---

#### 2. Analysis of the Scenario as Printed ($P = 5, Q = 5$)
- Initial values: $P = 5, Q = 5$. Consistency condition: $P = 5 \lor Q = 5$.
- In $T_1$, $P$ is read as 5. The condition `P = 10` evaluates to **false**. $Q$ is not decremented, and $T_1$ writes $Q = 5$.
- In $T_2$, $Q$ is read as 5. The condition `Q = 10` evaluates to **false**. $P$ is not incremented, and $T_2$ writes $P = 5$.
- Under all execution orders, the values of $P$ and $Q$ remain 5, trivially satisfying consistency.

---

#### 3. Part (i): Concurrent Execution That Produces a Serializable Schedule
To ensure conflict serializability, one transaction must complete its accesses on the shared variables before the other begins:

| Step | Transaction $T_1$ | Transaction $T_2$ | Local Actions |
| :---: | :--- | :--- | :--- |
| 1 | `read(P);` | | $T_1$ reads $P = 5$ |
| 2 | `read(Q);` | | $T_1$ reads $Q = 5$ |
| 3 | `if P=10 then Q:=Q-5;`<br>`write(Q);` | | Condition false; writes $Q = 5$ |
| 4 | | `read(Q);` | $T_2$ reads $Q = 5$ |
| 5 | | `read(P);` | $T_2$ reads $P = 5$ |
| 6 | | `if Q=10 then P:=P+5;`<br>`write(P);` | Condition false; writes $P = 5$ |

**Conflict Analysis:**
- $T_1: \text{read}(P)$ occurs before $T_2: \text{write}(P) \implies T_1 \longrightarrow T_2$.
- $T_1: \text{write}(Q)$ occurs before $T_2: \text{read}(Q) \implies T_1 \longrightarrow T_2$.
- The precedence graph contains only the edge $T_1 \longrightarrow T_2$, which is strictly acyclic.
- The schedule is **conflict serializable**, with equivalent serial order $\langle T_1, T_2 \rangle$.

---

#### 4. Part (ii): Non-Serializable Interleaving and Textbook Reading
Because sub-question (ii) repeats (i) due to a misprint, we also analyze the interleaved concurrent execution where both transactions read before either writes:

| Step | Transaction $T_1$ | Transaction $T_2$ |
| :---: | :--- | :--- |
| 1 | `read(P);` | |
| 2 | | `read(Q);` |
| 3 | `read(Q);` | |
| 4 | | `read(P);` |
| 5 | `write(Q);` | |
| 6 | | `write(P);` |

![2019 Q.4(a) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2019_Q4a_precedence_graph.jpg)
*Figure 10.2: Precedence graph for 2019 Q.4(a) interleaved execution exhibiting a cycle.*

**Conflicts:**
- $T_1$ reads $P$ (step 1) before $T_2$ writes $P$ (step 6) $\implies T_1 \longrightarrow T_2$.
- $T_2$ reads $Q$ (step 2) before $T_1$ writes $Q$ (step 5) $\implies T_2 \longrightarrow T_1$.

The precedence graph contains a directed cycle:

$$
T_1 \longleftrightarrow T_2
$$

This schedule is **NOT conflict serializable**. Also, if the `if` conditions had matched the initial values (`if P = 5 then Q := Q - 5` and `if Q = 5 then P := P + 5`), this interleaving would produce $P = 10, Q = 0$, breaking the consistency requirement $P = 5 \lor Q = 5$.

## ⚡ Exam Tips & Common Mistakes

1. **Show the `if` condition evaluation step by step:** Always write down whether each `if` check evaluates to true or false based on the value the transaction read into its local variable.
2. **Never answer "Yes" to part (ii) by giving a serial schedule:** A serial schedule does not run the transactions concurrently. Any genuinely interleaved concurrent execution of $T_1$ and $T_2$ creates the cycle $T_1 \leftrightarrow T_2$.
3. **Point out the 2019 Q.4(a) misprint politely:** If the 2019 variant appears again, add a one-line note stating that sub-question (ii) was printed identically to (i), and show both the conflict-serializable schedule in (i) and the cyclic non-serializable interleaving in (ii).
4. **Do not forget the opening definition in 2019 Q.4(a):** The 7-mark prompt begins with *"What is concurrency control?"* Skipping that definition costs 2 marks before you even start tracing $T_1$ and $T_2$.
