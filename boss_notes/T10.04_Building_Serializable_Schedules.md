# T10.4: Building Serializable and Non-Serializable Schedules

> **Topic:** T10 — Serializability | **Priority:** 🟡 | **Exam Frequency:** 2/7 finals (13 marks)  
> **Sources:** Silberschatz 7e Ch. 17 (§17.1, §17.6, Exercise 17.15 pp. 832–833) · Lecture Deck 07 (Slides 10–21) · Classnote by Raidah (T10)

## Why This Topic Matters

In most T10 questions, the examiner gives you a finished schedule table and asks whether it is serializable. Here, the task is flipped: **you are given the code of two transactions ($T_1$ and $T_2$) and asked to build a schedule yourself**. Adapted from Silberschatz Exercise 17.15, this question appeared in **2017 Q.5(c)** (6 marks) and **2019 Q.4(a)** (7 marks). Once you understand the simple cross-reading pattern behind $T_1$ and $T_2$, you can solve both parts in under five minutes.

---

## 📝 Key Definitions

> **Consistency Requirement (Database Invariant):** A rule that the data in the database must always obey before and after every transaction (for example, $A = 0 \lor B = 0$). Every individual transaction is written so that if the database starts in a consistent state and the transaction runs *alone*, the database ends in a consistent state.

> **Serializable Schedule:** A schedule whose outcome and final database state are identical to some serial execution ($\langle T_1, T_2 \rangle$ or $\langle T_2, T_1 \rangle$) of the same transactions. Because every serial execution preserves database consistency, any serializable schedule also preserves consistency.

> **Concurrency Control:** The DBMS mechanism that coordinates simultaneous transactions so they can run concurrently without breaking database consistency. It enforces isolation to prevent dirty reads, lost updates, and non-serializable schedules.

---

## 1. The Core Problem (Silberschatz Exercise 17.15)

Look at the two transactions from **2017 Q.5(c)**:

```text
T1:                              T2:
  read(A);                         read(B);
  read(B);                         read(A);
  if A = 0 then B := B + 1;        if B = 0 then A := A + 1;
  write(B);                        write(A);
```

- **Starting values:** $A = 0$ and $B = 0$.
- **Consistency rule:** At least one variable must stay $0$ ($A = 0 \text{ or } B = 0$).

Notice how $T_1$ and $T_2$ mirror each other:
- **$T_1$ checks $A$ and updates $B$:** If $A$ is still $0$, $T_1$ adds $1$ to $B$.
- **$T_2$ checks $B$ and updates $A$:** If $B$ is still $0$, $T_2$ adds $1$ to $A$.

---

## 2. Step 1: What Happens When They Run Serially? (One After Another)

Before building a concurrent schedule, always check the two **serial** schedules ($\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$). When one transaction finishes completely before the other starts, the consistency rule ($A = 0 \text{ or } B = 0$) stays safe:

1. **Serial Order $\langle T_1, T_2 \rangle$ ($T_1$ runs first, then $T_2$):**
   - $T_1$ reads $A = 0$ and $B = 0$. Since `A = 0` is **true**, $T_1$ sets $B := 1$ and writes $B = 1$.
   - Now $T_2$ starts. It reads the new $B = 1$ and $A = 0$. Since `B = 0` is **false** ($1 \neq 0$), $T_2$ does not change $A$ and writes $A = 0$.
   - **Final state:** $A = 0, B = 1$. Since $A = 0$, the rule $A = 0 \lor B = 0$ is **satisfied**.

2. **Serial Order $\langle T_2, T_1 \rangle$ ($T_2$ runs first, then $T_1$):**
   - $T_2$ reads $B = 0$ and $A = 0$. Since `B = 0` is **true**, $T_2$ sets $A := 1$ and writes $A = 1$.
   - Now $T_1$ starts. It reads the new $A = 1$ and $B = 0$. Since `A = 0` is **false** ($1 \neq 0$), $T_1$ does not change $B$ and writes $B = 0$.
   - **Final state:** $A = 1, B = 0$. Since $B = 0$, the rule $A = 0 \lor B = 0$ is **satisfied**.

> **Takeaway:** Any valid serial execution produces either $(A=0, B=1)$ or $(A=1, B=0)$. It can **never** produce $(A=1, B=1)$.

---

## 3. Step 2: How to Build a Non-Serializable Concurrent Schedule

When Part (i) asks you to **show a concurrent execution that produces a non-serializable schedule**, use one simple rule:

> **The Read-First Recipe:** Let both $T_1$ and $T_2$ finish all of their `read` steps **before** either transaction executes its `write` step.

Why does this break consistency? Because both transactions read the starting values ($A = 0, B = 0$) before either one changes anything. Both `if` conditions evaluate to **true**, so both transactions increment their variable!

| Step | $T_1$ | $T_2$ | What Happens |
| :---: | :--- | :--- | :--- |
| 1 | `read(A);` | | $T_1$ reads starting value $A = 0$ |
| 2 | | `read(B);` | $T_2$ reads starting value $B = 0$ |
| 3 | `read(B);` | | $T_1$ reads starting value $B = 0$ |
| 4 | | `read(A);` | $T_2$ reads starting value $A = 0$ |
| 5 | `if A = 0 then B:=B+1;`<br>`write(B);` | | $T_1$ sees $A = 0$ (true), sets $B = 1$, and writes $B = 1$ |
| 6 | | `if B = 0 then A:=A+1;`<br>`write(A);` | $T_2$ sees $B = 0$ (true), sets $A = 1$, and writes $A = 1$ |

### Two Ways to Prove This Schedule Is Non-Serializable

1. **Inconsistent Final State:**
   - The schedule finishes with $A = 1$ and $B = 1$.
   - That breaks the consistency rule ($A = 0 \lor B = 0$) and matches neither $\langle T_1, T_2 \rangle$ nor $\langle T_2, T_1 \rangle$.
2. **Precedence Graph Cycle:**
   - On item $A$: $T_1$ reads $A$ (Step 1) before $T_2$ writes $A$ (Step 6) $\implies T_1 \to T_2$.
   - On item $B$: $T_2$ reads $B$ (Step 2) before $T_1$ writes $B$ (Step 5) $\implies T_2 \to T_1$.
   - The graph has a cycle $T_1 \longleftrightarrow T_2$, so it is not conflict-serializable.

---

## 4. Step 3: Can ANY Concurrent Execution Be Serializable?

Part (ii) asks: **"Is there a concurrent execution of $T_1$ and $T_2$ that produces a serializable schedule?"**

The answer is **No**. Here is the exact 2-point proof to write in the exam:

For an execution to be genuinely **concurrent (interleaved)**, both transactions must start before either one finishes:

1. **Look at item $A$ ($T_1$'s first step vs. $T_2$'s last step):**
   - $T_1$'s very first instruction is `read(A)`, and $T_2$'s very last instruction is `write(A)`.
   - If $T_2$ executed `write(A)` before $T_1$ executed `read(A)`, then all of $T_2$ would have finished before $T_1$ even started. That is the **serial** schedule $\langle T_2, T_1 \rangle$, not a concurrent one.
   - So in any concurrent (interleaved) schedule, $T_1$ must execute `read(A)` before $T_2$ executes `write(A)`. That forces the edge:
     $$
     T_1 \longrightarrow T_2
     $$
2. **Look at item $B$ ($T_2$'s first step vs. $T_1$'s last step):**
   - Symmetrically, $T_2$'s very first instruction is `read(B)`, and $T_1$'s very last instruction is `write(B)`.
   - If $T_1$ executed `write(B)` before $T_2$ executed `read(B)`, then all of $T_1$ would have finished before $T_2$ even started. That is the **serial** schedule $\langle T_1, T_2 \rangle$.
   - So in any concurrent (interleaved) schedule, $T_2$ must execute `read(B)` before $T_1$ executes `write(B)`. That forces the reverse edge:
     $$
     T_2 \longrightarrow T_1
     $$

Because every concurrent (interleaved) schedule forces both $T_1 \to T_2$ and $T_2 \to T_1$, it **always** creates the cycle $T_1 \longleftrightarrow T_2$. Only the two non-interleaved serial runs ($\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$) are serializable.

---

## 5. How to Handle the 2019 Q.4(a) Question Paper Typos

In **2019 Q.4(a)**, the examiner took the exact 2017 problem and changed $A, B$ (initially $0$) to $P, Q$ (initially $5$, with rule $P = 5 \lor Q = 5$). However, the printed 2019 question paper has **two typos**:

| What the 2019 Paper Printed | What Was Intended (from Silberschatz Ex. 17.15) | Why It Matters |
| :--- | :--- | :--- |
| **Typo 1 (in `T1` and `T2`):**<br>`if P=10 then Q:=Q-5;`<br>`if Q=10 then P:=P+5;` | `if P=5 then Q:=Q-5;`<br>`if Q=5 then P:=P+5;` | Because $P = 5$ and $Q = 5$ initially, checking `P=10` and `Q=10` is immediately **false** ($5 \neq 10$), so neither variable changes if taken literally. |
| **Typo 2 (in Sub-question (i)):**<br>*(i) Show a concurrent execution of T1 and T2 that produces a **serializable** schedule.* | *(i) Show a concurrent execution of T1 and T2 that produces a **non-serializable** schedule.* | Printing *"serializable"* instead of *"non-serializable"* made Part (i) ask the exact same thing as Part (ii). |

### How to Write a Full-Marks Answer for 2019 Q.4(a)
1. **Define Concurrency Control first** (the prompt starts with *"What is concurrency control?"*).
2. **State the two paper typos in one line** so the grader sees you understand both the literal numbers ($P=10$ vs $P=5$) and the intended Silberschatz problem.
3. **In Part (i):** Write the **Read-First interleaved schedule** (steps 1–6) and show its cycle $T_1 \longleftrightarrow T_2$ (plus the serial baseline $\langle T_1, T_2 \rangle$ in case the grader's key looked for a serial schedule).
4. **In Part (ii):** Answer **"No"** and give the 2-step cycle proof from Section 4 above.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.5(c) · Building Non-Serializable Schedule and Concurrency Proof

> **Appeared:** 2017 Q.5(c) (6 marks)

**Question:**

Consider the following two transactions.

**T1:**  
  `read(A);`  
  `read(B);`  
  `if A = 0 then B:=B+1;`  
  `write(B);`

**T2:**  
  `read(B);`  
  `read(A);`  
  `if B = 0 then A:=A+1;`  
  `write(A);`

Let the consistency requirement be $A = 0$ or $B = 0$ with $A=B=0$ the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a nonserializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

**Full Answer:**

#### Initial State and Serial Baseline
- **Initial values:** $A = 0, B = 0$.
- **Consistency condition:** $A = 0 \lor B = 0$.
- **Serial order $\langle T_1, T_2 \rangle$:** $T_1$ reads $A=0, B=0$, sees `A = 0` is true, sets $B := 1$, and writes $B = 1$. Then $T_2$ reads $B=1, A=0$. Because `B = 0` is false ($1 \neq 0$), $T_2$ leaves $A = 0$. Final state: $A = 0, B = 1$ (consistent).
- **Serial order $\langle T_2, T_1 \rangle$:** $T_2$ reads $B=0, A=0$, sees `B = 0` is true, sets $A := 1$, and writes $A = 1$. Then $T_1$ reads $A=1, B=0$. Because `A = 0` is false ($1 \neq 0$), $T_1$ leaves $B = 0$. Final state: $A = 1, B = 0$ (consistent).

---

#### Part (i): Concurrent Execution Producing a Nonserializable Schedule

We interleave $T_1$ and $T_2$ so that both transactions finish their `read` operations before either executes its `write` operation:

| Step | $T_1$ | $T_2$ | State Description |
| :---: | :--- | :--- | :--- |
| 1 | `read(A);` | | $T_1$ reads initial $A = 0$ |
| 2 | | `read(B);` | $T_2$ reads initial $B = 0$ |
| 3 | `read(B);` | | $T_1$ reads initial $B = 0$ |
| 4 | | `read(A);` | $T_2$ reads initial $A = 0$ |
| 5 | `if A = 0 then B:=B+1;`<br>`write(B);` | | Condition $0 = 0$ is true $\implies B := 1$; writes $B = 1$ |
| 6 | | `if B = 0 then A:=A+1;`<br>`write(A);` | Condition $0 = 0$ is true $\implies A := 1$; writes $A = 1$ |

**Final Database State:**
$$
A = 1 \quad \text{and} \quad B = 1
$$

This violates the consistency requirement $A = 0 \lor B = 0$ because neither variable is $0$.

**Proof of Nonserializability:**
- $T_1: \text{read}(A)$ (Step 1) happens before $T_2: \text{write}(A)$ (Step 6) $\implies T_1 \longrightarrow T_2$.
- $T_2: \text{read}(B)$ (Step 2) happens before $T_1: \text{write}(B)$ (Step 5) $\implies T_2 \longrightarrow T_1$.
- The precedence graph contains a cycle:

$$
T_1 \longleftrightarrow T_2
$$

![2017 Q.5(c) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2017_Q5c_precedence_graph.jpg)
*Figure 10.1: Precedence graph for 2017 Q.5(c) showing the cycle between T1 and T2.*

Because the precedence graph has a cycle and the final state $(A=1, B=1)$ cannot be produced by any serial schedule, this schedule is **non-serializable**.

---

#### Part (ii): Is There a Concurrent Execution That Produces a Serializable Schedule?

**Answer:** **No.**

**Proof:**
For an execution to be genuinely concurrent (interleaved), both transactions must start before either finishes:
1. **Conflict on $A$:** $T_1$'s first step is `read(A)` and $T_2$'s last step is `write(A)`. If $T_2$ wrote $A$ before $T_1$ read $A$, then $T_2$ would have finished completely before $T_1$ started (which is the serial schedule $\langle T_2, T_1 \rangle$). Thus, in any interleaved execution, $T_1$ reads $A$ before $T_2$ writes $A$, forcing $T_1 \longrightarrow T_2$.
2. **Conflict on $B$:** $T_2$'s first step is `read(B)` and $T_1$'s last step is `write(B)`. If $T_1$ wrote $B$ before $T_2$ read $B$, then $T_1$ would have finished completely before $T_2$ started (which is the serial schedule $\langle T_1, T_2 \rangle$). Thus, in any interleaved execution, $T_2$ reads $B$ before $T_1$ writes $B$, forcing $T_2 \longrightarrow T_1$.

Therefore, every concurrent (interleaved) execution forces both edges:
$$
T_1 \longrightarrow T_2 \quad \text{and} \quad T_2 \longrightarrow T_1
$$

This always creates the cycle $T_1 \longleftrightarrow T_2$. Hence, **no concurrent execution of $T_1$ and $T_2$ can produce a serializable schedule**. Only strictly serial executions ($\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$) are serializable.

### 🎯 GQ2 · 2019 Q.4(a) · Concurrency Control and Serializable/Non-Serializable Schedules

> **Appeared:** 2019 Q.4(a) (7 marks)

**Question:**

What is concurrency control? Consider the following two transactions.

**T1:**  
`read (P);`  
`read (Q);`  
`if P=10 then Q:=Q-5;`  
`write (Q);`

**T2:**  
`read (Q);`  
`read (P);`  
`if Q=10 then P:=P+5;`  
`write (P);`

Let the consistency requirement be P=5 or Q=5 with P=Q=5 the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a serializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

*(Note: In the printed question paper, sub-question (ii) is printed identically to (i) as "Is there a concurrent execution of T1 and T2 that produces a serializable schedule?")*

**Full Answer:**

#### 1. What is Concurrency Control?
**Concurrency control** is the DBMS mechanism that coordinates the simultaneous execution of transactions on a shared database. Its main goals are:
1. **Preserving Consistency:** Ensure concurrent executions leave the database in a valid state that obeys all consistency rules.
2. **Enforcing Isolation:** Prevent concurrent transactions from interfering with each other (avoiding dirty reads, lost updates, and unrepeatable reads).
3. **Maximizing Throughput:** Allow transactions to share CPU and disk resources safely to reduce waiting time.

---

#### 2. Initial State and Note on Question Paper Typos
- **Initial values:** $P = 5, Q = 5$. **Consistency rule:** $P = 5 \lor Q = 5$.
- **Note on the two paper typos (modeled on Silberschatz Exercise 17.15 / 2017 Q.5c):**
  1. In Part (i), the word **"non-serializable"** was misprinted as **"serializable"** (making (i) and (ii) ask the same question).
  2. The `if` guards were printed as `P = 10` and `Q = 10` instead of `P = 5` and `Q = 5`:
     - **With the intended guards (`if P=5` and `if Q=5`):** Serial order $\langle T_1, T_2 \rangle$ produces $P = 5, Q = 0$, and serial order $\langle T_2, T_1 \rangle$ produces $P = 10, Q = 5$ (both satisfy $P = 5 \lor Q = 5$).
     - **With the literal printed guards (`if P=10` and `if Q=10`):** Both conditions are false for $P = Q = 5$, so both transactions write back $P = 5, Q = 5$.

---

#### 3. Part (i): Concurrent Execution

##### (a) Intended Reading: Concurrent Execution Producing a Non-Serializable Schedule
We interleave $T_1$ and $T_2$ so that both transactions finish their `read` steps before either executes its `write` step:

| Step | $T_1$ | $T_2$ | Action (Intended `if P=5` / `if Q=5`) | Action (Literal `if P=10` / `if Q=10`) |
| :---: | :--- | :--- | :--- | :--- |
| 1 | `read(P);` | | $T_1$ reads $P = 5$ | $T_1$ reads $P = 5$ |
| 2 | | `read(Q);` | $T_2$ reads $Q = 5$ | $T_2$ reads $Q = 5$ |
| 3 | `read(Q);` | | $T_1$ reads $Q = 5$ | $T_1$ reads $Q = 5$ |
| 4 | | `read(P);` | $T_2$ reads $P = 5$ | $T_2$ reads $P = 5$ |
| 5 | `write(Q);` | | $P=5$ is true $\implies$ writes $Q = 0$ | $P=10$ is false $\implies$ writes $Q = 5$ |
| 6 | | `write(P);` | $Q=5$ is true $\implies$ writes $P = 10$ | $Q=10$ is false $\implies$ writes $P = 5$ |

![2019 Q.4(a) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2019_Q4a_precedence_graph.jpg)
*Figure 10.2: Precedence graph for 2019 Q.4(a) interleaved execution showing the cycle between T1 and T2.*

**Proof of Non-Serializability:**
- $T_1: \text{read}(P)$ (Step 1) happens before $T_2: \text{write}(P)$ (Step 6) $\implies T_1 \longrightarrow T_2$.
- $T_2: \text{read}(Q)$ (Step 2) happens before $T_1: \text{write}(Q)$ (Step 5) $\implies T_2 \longrightarrow T_1$.
- This forms a cycle $T_1 \longleftrightarrow T_2$, so the schedule is **NOT conflict serializable** (and under the intended `if P=5` / `if Q=5` guards ends with $P = 10, Q = 0$, breaking $P = 5 \lor Q = 5$).

##### (b) Literal Reading: Serial Baseline $\langle T_1, T_2 \rangle$
As proven in Part (ii) below, no genuinely interleaved execution of $T_1$ and $T_2$ is conflict-serializable. Only a non-interleaved **serial** schedule where $T_1$ finishes all of its steps before $T_2$ starts has an acyclic precedence graph ($T_1 \longrightarrow T_2$, order $\langle T_1, T_2 \rangle$):

| Step | $T_1$ | $T_2$ | Local Actions |
| :---: | :--- | :--- | :--- |
| 1 | `read(P);` | | $T_1$ reads $P = 5$ |
| 2 | `read(Q);` | | $T_1$ reads $Q = 5$ |
| 3 | `if P=10 then Q:=Q-5;`<br>`write(Q);` | | Writes $Q$ ($0$ if `P=5` guard; $5$ as printed) |
| 4 | | `read(Q);` | $T_2$ reads $Q$ |
| 5 | | `read(P);` | $T_2$ reads $P = 5$ |
| 6 | | `if Q=10 then P:=P+5;`<br>`write(P);` | Writes $P = 5$ |

---

#### 4. Part (ii): Is There a Concurrent Execution That Produces a Serializable Schedule?

**Answer:** **No** (not for conflict serializability).

**Proof:**
For an execution of $T_1$ and $T_2$ to be genuinely concurrent (interleaved), both transactions must start before either finishes:
1. **Conflict on $P$:** $T_1$'s first step is `read(P)` and $T_2$'s last step is `write(P)`. If $T_2$ wrote $P$ before $T_1$ read $P$, then $T_2$ would have finished completely before $T_1$ started (serial schedule $\langle T_2, T_1 \rangle$). Thus, in any interleaved schedule, $T_1: \text{read}(P)$ precedes $T_2: \text{write}(P)$, forcing:
   $$
   T_1 \longrightarrow T_2
   $$
2. **Conflict on $Q$:** Symmetrically, $T_2$'s first step is `read(Q)` and $T_1$'s last step is `write(Q)`. If $T_1$ wrote $Q$ before $T_2$ read $Q$, then $T_1$ would have finished completely before $T_2$ started (serial schedule $\langle T_1, T_2 \rangle$). Thus, in any interleaved schedule, $T_2: \text{read}(Q)$ precedes $T_1: \text{write}(Q)$, forcing:
   $$
   T_2 \longrightarrow T_1
   $$

Every concurrent (interleaved) execution forces both $T_1 \to T_2$ and $T_2 \to T_1$, creating the cycle $T_1 \longleftrightarrow T_2$. Therefore, **no concurrent execution of $T_1$ and $T_2$ is conflict-serializable**. Only the strictly serial executions $\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$ are conflict-serializable.

## ⚡ Exam Tips & Common Mistakes

1. **Use the Read-First Recipe for non-serializable schedules:** Whenever you need to build a non-serializable schedule for two cross-reading transactions, let both transactions finish all of their `read` steps before either executes its `write` step.
2. **Never answer "Yes" to Part (ii) by giving a serial schedule:** A serial schedule ($\langle T_1, T_2 \rangle$) is not a concurrent (interleaved) execution. Any genuinely interleaved execution of $T_1$ and $T_2$ creates the cycle $T_1 \longleftrightarrow T_2$.
3. **Mention the two typos if 2019 Q.4(a) repeats:** Briefly note that Part (i) printed *"serializable"* instead of *"non-serializable"* and the `if` guards printed `10` instead of `5`. Then show the Read-First interleaved schedule in Part (i) and the **"No"** cycle proof in Part (ii).
4. **Do not skip the opening definition in 2019 Q.4(a):** The 7-mark question starts with *"What is concurrency control?"* Always write that 3-point definition first so you do not lose 2 easy marks.
