# T11.5: Wait-Die vs. Wound-Wait Deadlock Prevention

> **Topic:** T11 — Concurrency Control Protocols | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (0 marks)
> **Sources:** Silberschatz 7e Ch. 18 (§18.2.1, p. 850) · Lecture Deck 08 (Slide 23) · Raidah Notes (p. 29)

## Why This Topic Matters

Timestamp-based deadlock prevention protocols stop circular waiting before it can even start, so the database engine does not need to maintain a runtime wait-for graph. Although wait-die and wound-wait have not been asked by name in standalone past final questions, they form the core theory behind 2017 Q.7(b) on deadlock prevention and frequently appear in class tests and viva exams. If you understand how preemption works here and remember the timestamp retention rule, you can handle any deadlock prevention question with ease.

---

## 📝 Key Definitions

> **Wait-Die Scheme:** "The wait–die scheme is a nonpreemptive technique. When transaction $T_i$ requests a data item currently held by $T_j$, $T_i$ is allowed to wait only if it has a timestamp smaller than that of $T_j$ (that is, $T_i$ is older than $T_j$). Otherwise, $T_i$ is rolled back (dies)." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2.1 (p. 850)

> **Wound-Wait Scheme:** "The wound–wait scheme is a preemptive technique. It is a counterpart to the wait–die scheme. When transaction $T_i$ requests a data item currently held by $T_j$, $T_i$ is allowed to wait only if it has a timestamp larger than that of $T_j$ (that is, $T_i$ is younger than $T_j$). Otherwise, $T_j$ is rolled back ($T_j$ is wounded by $T_i$)." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2.1 (p. 850)

> **Timestamp Precedence Rule:** "Whenever the system rolls back a transaction, it does not assign the transaction a new timestamp. Thus, to the system, the transaction appears to have been in the system for a long time, and therefore it has a higher priority than newer transactions." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.2.1 (p. 850)

## Timestamp Principles in Deadlock Prevention

Think of transaction timestamps like ticket numbers at a bakery counter: the earlier you arrive, the smaller your ticket number, and the more seniority you have. In timestamp-based deadlock prevention, the database still uses locks for concurrency control, but it checks these timestamps whenever two transactions clash over the same lock:
- Every transaction $T_i$ gets a unique, increasing timestamp $\text{TS}(T_i)$ the moment it starts.
- If transaction $T_1$ enters the system before transaction $T_2$, its timestamp is smaller:

$$\text{TS}(T_1) < \text{TS}(T_2)$$

- A smaller timestamp means an **older (earlier)** transaction with higher seniority.
- A larger timestamp means a **younger (later)** transaction.

Whenever transaction $T_i$ requests a lock currently held by transaction $T_j$, the system compares $\text{TS}(T_i)$ and $\text{TS}(T_j)$ to decide who waits and who gets rolled back.

---

## ⚠️ The Critical Timestamp Retention Trap

One of the easiest ways to lose marks on an exam is mixing up the timestamp rules for deadlock prevention and timestamp-ordering concurrency control:

> [!IMPORTANT]
> - **In Deadlock Prevention (Wait-Die and Wound-Wait):** A rolled-back transaction **KEEPS ITS ORIGINAL (OLD) TIMESTAMP** when it restarts.
> - **Why?** Keeping its original timestamp makes the transaction look older and older compared to newly arriving transactions. Its seniority keeps rising until it becomes the oldest transaction in the system, and at that point it can never be aborted or preempted again. This guarantees it will never starve.
> - **Contrast with Timestamp-Ordering (TSO) Protocol:** Under TSO concurrency control, a rolled-back transaction **MUST GET A BRAND-NEW TIMESTAMP** when it restarts so it does not hit the exact same timestamp conflict all over again.

---

## The Wait-Die Scheme (Non-Preemptive)

Wait-die is a **non-preemptive** protocol, which means a requesting transaction can never kick an active transaction off a lock it already holds. Instead, the requesting transaction either waits politely or gives up and aborts itself.

### Wait-Die Decision Rules:
Suppose transaction $T_i$ requests a data item currently held by transaction $T_j$:

1. **Older requests Younger ($\text{TS}(T_i) < \text{TS}(T_j)$):**
   - Because $T_i$ is older than $T_j$, it has seniority and is allowed to **WAIT** until $T_j$ finishes and releases the lock.
2. **Younger requests Older ($\text{TS}(T_i) > \text{TS}(T_j)$):**
   - Because $T_i$ is younger than $T_j$, it is not allowed to wait on a senior transaction, so $T_i$ **DIES** (rolls back and restarts with its original timestamp).

```text
Wait-Die Mnemonic: "Old can wait, Young must die."
Only older transactions are ever permitted to wait.
```

### Wait-Die Trace Example:
Suppose we have three transactions with timestamps $\text{TS}(T_1) = 10$, $\text{TS}(T_2) = 20$, and $\text{TS}(T_3) = 30$, and $T_2$ currently holds the lock on data item $A$:
- If $T_1$ requests $A$: $T_1$ is older ($10 < 20$), so $T_1$ **waits**.
- If $T_3$ requests $A$: $T_3$ is younger ($30 > 20$), so $T_3$ **dies** (rolls back).

---

## The Wound-Wait Scheme (Preemptive)

Wound-wait is a **preemptive** protocol, meaning an older transaction acts like a VIP that can forcibly take locks away from younger transactions by rolling them back.

### Wound-Wait Decision Rules:
Suppose transaction $T_i$ requests a data item currently held by transaction $T_j$:

1. **Older requests Younger ($\text{TS}(T_i) < \text{TS}(T_j)$):**
   - Because $T_i$ is older than $T_j$, $T_i$ **WOUNDS** $T_j$. The system takes the lock away from $T_j$, rolls $T_j$ back, and hands the lock immediately to $T_i$.
2. **Younger requests Older ($\text{TS}(T_i) > \text{TS}(T_j)$):**
   - Because $T_i$ is younger than $T_j$, it cannot preempt a senior transaction, so $T_i$ is allowed to **WAIT** until $T_j$ finishes and unlocks the item.

```text
Wound-Wait Mnemonic: "Old wounds young, Young must wait."
Only younger transactions are ever permitted to wait.
```

### Wound-Wait Trace Example:
Using the same timestamps $\text{TS}(T_1) = 10$, $\text{TS}(T_2) = 20$, and $\text{TS}(T_3) = 30$ where $T_2$ holds the lock on data item $A$:
- If $T_1$ requests $A$: $T_1$ is older ($10 < 20$), so $T_1$ **wounds $T_2$** ($T_2$ rolls back and releases $A$ to $T_1$).
- If $T_3$ requests $A$: $T_3$ is younger ($30 > 20$), so $T_3$ **waits**.

## Side-by-Side Comparison: Wait-Die vs. Wound-Wait

The table below compares how wait-die and wound-wait behave in practice:

| Feature / Metric | Wait-Die Scheme | Wound-Wait Scheme |
| :--- | :--- | :--- |
| **Preemption Style** | Non-preemptive | Preemptive |
| **Older requests Younger** | Older **waits** | Older **wounds younger** (younger rolls back) |
| **Younger requests Older** | Younger **dies** (younger rolls back) | Younger **waits** |
| **Who is allowed to wait?** | **Only older transactions** | **Only younger transactions** |
| **Who is rolled back?** | Requesting transaction (younger) | Holding transaction (younger) |
| **Rollback Frequency** | **Higher** (a young transaction may die and restart several times while an older one still holds the lock) | **Lower** (once wounded, a young transaction simply waits when it requests the lock again from the older holder) |
| **Wasted Work** | Low (aborted transactions are young and have done little work) | Moderate (the holding transaction may be rolled back partway through its work) |
| **Restart Timestamp** | **Original timestamp** retained | **Original timestamp** retained |
| **Starvation Freedom** | Guaranteed (aging ensures completion) | Guaranteed (aging ensures completion) |
| **Deadlock Freedom** | Guaranteed (no circular waits) | Guaranteed (no circular waits) |

## Why It Works: Proof That Deadlock is Impossible

Intuitively, a deadlock requires a closed loop where transactions wait on each other in a circle. If we force every waiting arrow to point strictly in one age direction (always from older to younger, or always from younger to older), a path of waiting transactions can never loop back to where it started.

### 1. Proof for Wait-Die:
In wait-die, transaction $T_i$ can wait for $T_j$ if and only if $T_i$ is older than $T_j$:

$$\text{TS}(T_i) < \text{TS}(T_j)$$

So every directed wait edge $T_i \to T_j$ guarantees that $\text{TS}(T_i) < \text{TS}(T_j)$. For a deadlock cycle $T_1 \to T_2 \to \dots \to T_k \to T_1$ to form, the timestamps along the loop would have to satisfy:

$$\text{TS}(T_1) < \text{TS}(T_2) < \dots < \text{TS}(T_k) < \text{TS}(T_1)$$

That would mean $\text{TS}(T_1) < \text{TS}(T_1)$, which is impossible. Because of this, no cycle can ever form.

### 2. Proof for Wound-Wait:
In wound-wait, transaction $T_i$ can wait for $T_j$ if and only if $T_i$ is younger than $T_j$:

$$\text{TS}(T_i) > \text{TS}(T_j)$$

So every directed wait edge $T_i \to T_j$ requires $\text{TS}(T_i) > \text{TS}(T_j)$. For a cycle $T_1 \to T_2 \to \dots \to T_k \to T_1$ to exist, the timestamps would have to satisfy:

$$\text{TS}(T_1) > \text{TS}(T_2) > \dots > \text{TS}(T_k) > \text{TS}(T_1)$$

Again, $\text{TS}(T_1) > \text{TS}(T_1)$ is impossible, so circular waiting can never happen.

## 🔮 Likely Questions

### 🎯 LQ1 · Explain Wait-Die and Wound-Wait Schemes with Examples

> **Significance:** Flagship theoretical deadlock prevention question based on Lecture Deck 08 Slide 23 and Textbook §18.2.1.

**Question:**

Explain the wait-die and wound-wait deadlock prevention schemes with clear examples. How do they differ in terms of preemption?

**Full Answer:**

**1. Wait-Die Scheme (Non-Preemptive):**
Wait-die is a non-preemptive deadlock prevention protocol based on transaction timestamps $\text{TS}(T)$. When transaction $T_i$ requests a lock held by $T_j$:
- If $\text{TS}(T_i) < \text{TS}(T_j)$ ($T_i$ is older), $T_i$ is permitted to **wait**.
- If $\text{TS}(T_i) > \text{TS}(T_j)$ ($T_i$ is younger), $T_i$ **dies** (it is rolled back and restarted with its original timestamp).
- *Example:* Let $\text{TS}(T_1) = 100$ and $\text{TS}(T_2) = 200$. If $T_1$ requests an item held by $T_2$, $T_1$ waits because $100 < 200$. If $T_2$ requests an item held by $T_1$, $T_2$ dies because $200 > 100$.

**2. Wound-Wait Scheme (Preemptive):**
Wound-wait is a preemptive deadlock prevention protocol. When transaction $T_i$ requests a lock held by $T_j$:
- If $\text{TS}(T_i) < \text{TS}(T_j)$ ($T_i$ is older), $T_i$ **wounds** $T_j$. The lock is preempted, $T_j$ is rolled back, and $T_i$ receives the lock.
- If $\text{TS}(T_i) > \text{TS}(T_j)$ ($T_i$ is younger), $T_i$ is permitted to **wait**.
- *Example:* With the same timestamps, if $T_1$ requests an item held by $T_2$, $T_1$ wounds $T_2$ ($T_2$ rolls back and yields the lock to $T_1$). If $T_2$ requests an item held by $T_1$, $T_2$ waits.

**3. Difference in Preemption:**
- **Wait-Die is Non-Preemptive:** A lock is never seized from a transaction already holding it. Only the requesting transaction is ever aborted.
- **Wound-Wait is Preemptive:** An older requesting transaction forcefully revokes locks from a younger holding transaction by rolling the younger transaction back.

### 🎯 LQ2 · Why Rolled-Back Transactions Retain Original Timestamps

> **Significance:** High-yield viva and conceptual exam question testing starvation mechanics.

**Question:**

Why does a rolled-back transaction retain its original timestamp in the wait-die and wound-wait schemes? What would happen if it were assigned a new timestamp?

**Full Answer:**

**1. Reason for Retaining the Original Timestamp:**
In both wait-die and wound-wait schemes, a rolled-back transaction retains its original timestamp upon restarting to **prevent starvation (livelock)**.
- Over time, newly entering transactions receive larger (younger) timestamps.
- Because the rolled-back transaction keeps its early timestamp, it becomes older relative to active transactions in the system.
- In **Wait-Die**, an older transaction is allowed to wait and never dies.
- In **Wound-Wait**, an older transaction wounds younger holders and is never forced to wait.
- Eventually, the transaction becomes the oldest active transaction in the database. At that stage, it can never be aborted or wounded again, guaranteeing that it completes execution within a finite number of attempts.

**2. Consequence of Assigning a New Timestamp:**
If the database assigned a new timestamp on every rollback:
- The restarted transaction would become younger than all existing transactions.
- In Wait-Die, it would repeatedly request locks from older transactions and die again.
- In Wound-Wait, older transactions would repeatedly wound it and abort it.
- The transaction could be repeatedly aborted indefinitely, suffering from **infinite starvation**.

### 🎯 LQ3 · Rollback Frequency and Overhead Comparison

> **Significance:** Advanced analytical question comparing operational overheads.

**Question:**

Compare wait-die and wound-wait in terms of the number of rollbacks and waiting times. Under what conditions is wound-wait preferred?

**Full Answer:**

**1. Number of Rollbacks:**
- **Wait-Die Experiences More Rollbacks:** In wait-die, if transaction $T_2$ (younger) requests a lock on an item held by $T_1$ (older), $T_2$ dies. When $T_2$ restarts, if $T_1$ is still executing and holds the lock, $T_2$ attempts to request the item again, fails, and dies again. A transaction may undergo several rollbacks before the older transaction releases the lock.
- **Wound-Wait Experiences Fewer Rollbacks:** In wound-wait, if younger transaction $T_2$ requests an item held by older $T_1$, $T_2$ waits without dying. Rollbacks occur only when an older transaction needs a lock held by a younger transaction. Once wounded, the younger transaction waits until the older transaction commits before restarting, minimizing repeated aborts.

**2. Waiting Times:**
- In wait-die, older transactions spend substantial time waiting in queues.
- In wound-wait, older transactions preempt younger ones immediately, ensuring minimal latency for high-priority transactions.

**3. Preferred Conditions for Wound-Wait:**
Wound-wait is preferred when:
1. Long-running or high-priority transactions enter the system and must complete with minimal delay.
2. The overhead of repeatedly aborting and restarting transactions under wait-die would saturate system I/O and processor capacity.

## ⚡ Exam Tips & Common Mistakes

1. **Wait vs. Die Rule:** Remember the rule: In wait-die, **only the older transaction waits**. In wound-wait, **only the younger transaction waits**.
2. **Preemption Direction:** In wait-die, the requesting transaction dies. In wound-wait, the holding transaction is wounded and dies.
3. **The Timestamp Trap:** Do not say that rolled-back transactions receive new timestamps here. They keep their **original** timestamps to prevent starvation.
4. **Locking Still Required:** Both schemes use locking for concurrency control. Timestamps are used only to decide whether to wait or preempt when a lock conflict arises.
