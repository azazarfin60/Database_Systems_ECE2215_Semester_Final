# T03.2: Relational Keys (Super, Candidate, Primary, Foreign)

> **Topic:** T03 — Relational Model, Keys & Integrity | **Priority:** 🔴 High | **Exam Frequency:** 5/7 finals (21 marks: 2018 Q2a, 2019 Q6b, 2020 Q2b, 2021 Q2b, 2023 Q3b)
> **Sources:** Silberschatz 7e Ch. 2 (§2.3) · Lecture Deck 02 (Slide 7) · Lecture Deck 06 (Slides 11–13) · Class Notes (Raidah p. 5, 7, 13, 19, 20; Fahim p. 36, 46–47)

## Why This Topic Matters

Relational keys are the most frequently tested topic in Unit 3, appearing in 5 out of 7 RUET semester finals (21 marks total). Since relational tables have no row numbers or pointers, keys are the only way a database can tell two rows apart and link records across different tables. In the exam, you will almost certainly be asked to contrast **super keys**, **candidate keys**, **primary keys**, **composite keys**, and **foreign keys** using clear definitions, the subset hierarchy formula, and a small table example.

---

## 📝 Key Definitions

> **Superkey:** "A **superkey** is a set of one or more attributes that, taken collectively, allow us to identify uniquely a tuple in the relation."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3 (p. 43)

> **Candidate Key:** "We are often interested in superkeys for which no proper subset is a superkey. Such minimal superkeys are called **candidate keys**."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3 (p. 44)

> **Primary Key:** "We shall use the term **primary key** to denote a candidate key that is chosen by the database designer as the principal means of identifying tuples within a relation."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3 (p. 44)

> **Foreign Key:** "A **foreign-key constraint** from attribute(s) $A$ of relation $r_1$ to the primary-key $B$ of relation $r_2$ states that on any database instance, the value of $A$ for each tuple in $r_1$ must also be the value of $B$ for some tuple in $r_2$. Attribute set $A$ is called a **foreign key** from $r_1$, referencing $r_2$."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §2.3 (p. 45)

## Intuitive Analogy: How the Key Hierarchy Works

Imagine trying to identify a specific RUET student out of the entire university:
1. **Super Key (Unique, even with extra baggage):** If someone gives you `{roll_no, name, blood_group}`, you can find that exact student. Of course, `name` and `blood_group` were extra baggage you did not actually need, because `roll_no` alone was already unique. Any combination of columns that guarantees uniqueness (with or without extra columns) is a **super key**.
2. **Candidate Key (Stripped down to the bare minimum):** Now trim away every extra column until removing anything else would break uniqueness. Both `{roll_no}` and `{nid}` pass this test on their own. These minimal super keys are your **candidate keys** (they are the "candidates" competing to become the main ID).
3. **Primary Key vs. Alternate Key (The winner vs. the runner-up):** The database designer picks **one** candidate key (say, `{roll_no}`) to be the official **primary key** of the table. The leftover candidate keys that were not picked (like `{nid}` and `{email}`) become **alternate keys**.

```text
               +--------------------------------------+
               |              Superkey                |
               | (Any set that guarantees uniqueness) |
               +--------------------------------------+
                                  |
                                  | (Strip away redundant columns)
                                  v
               +--------------------------------------+
               |            Candidate Key             |
               |        (Minimal Superkeys)           |
               +--------------------------------------+
                       /                      \
                      / (Designer picks one)   \ (Remaining candidates)
                     v                          v
      +-----------------------------+    +----------------------------+
      |        Primary Key          |    |       Alternate Key        |
      | (Main ID, never NULL)       |    | (Secondary UNIQUE keys)    |
      +-----------------------------+    +----------------------------+
```

### The Subset Inclusion Formula

Because every primary key is chosen from the candidate keys, and every candidate key is a special (minimal) super key, they form a nested subset chain:

$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

### Master Comparison Matrix

| Key Type | Plain-English Definition | Minimal (No Extra Columns)? | NULL Allowed? | Max Per Table | Main Purpose |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **Super Key** | Any set of columns where no two rows can ever have the exact same values. | No (extra columns allowed) | No for identifying columns | Unlimited | Baseline uniqueness rule. |
| **Candidate Key** | A minimal super key where no smaller subset of its columns is unique. | Yes (strictly minimal) | Yes (unless marked `NOT NULL`) | Multiple | Pool of minimal unique identifiers. |
| **Primary Key** | The single candidate key chosen by the designer as the main row identifier. | Yes | No (never allowed) | Exactly 1 | Official row ID (`PRIMARY KEY`). |
| **Alternate Key** | Any candidate key that was not chosen as the primary key. | Yes | Yes (unless marked `NOT NULL`) | Multiple | Enforced via `UNIQUE` constraints. |
| **Composite Key** | Any key made up of **two or more** columns working together. | Depends on key tier | Depends on key tier | Multiple | Identifies rows in junction tables. |
| **Foreign Key** | Column(s) in a child table that point to the primary key of a parent table. | Matches parent PK | Yes (if relationship is optional) | Multiple | Links tables & prevents orphan rows. |

## Detailed Breakdown of Each Key Type

### 1. Super Key
Suppose $R$ is the set of all columns in table $r(R)$. A subset of columns $K \subseteq R$ is a **super key** if no two distinct rows $t_1$ and $t_2$ can ever agree on all columns of $K$ at the same time. In math notation, that simply means "different rows must have different values on $K$":

$$
\forall t_1, t_2 \in r, \quad t_1 \neq t_2 \implies t_1[K] \neq t_2[K]
$$

Notice what this rule implies: once a set of columns $K$ is unique, glueing *any* extra column $A$ onto it ($K \cup \{A\}$) will still keep it unique! That is why a single column like `{ID}` can generate dozens of super keys (`{ID, name}`, `{ID, dept_name}`, and even the entire row of all columns combined).

### 2. Candidate Key
A **candidate key** is a super key with zero wasted columns. It must satisfy two rules:
- **Uniqueness:** $K$ is a super key for $r(R)$.
- **Minimality (Irreducibility):** No proper subset $K' \subset K$ is a super key.

If you drop even a single column from a candidate key, it immediately loses its ability to uniquely identify rows. Keep in mind that "minimal" does **not** mean "only one column." If a table requires `{student_id, course_id}` together to identify a grade, that 2-column pair is minimal because neither column works alone.

### 3. Primary Key
The **primary key** is the single candidate key chosen by the database designer as the main way to identify tuples in the table:
- **Entity Integrity Rule:** No column inside a primary key is ever allowed to be `NULL` (because you cannot identify a record using an unknown ID).
- **Stability:** Designers pick a candidate key whose value is short and never changes over time.
- **Schema Notation:** In relational schemas, primary key columns are always underlined, like $\text{Student}(\underline{\text{student\_id}}, \text{name})$.

### 4. Alternate Key (Secondary Key)
When a table has two or more candidate keys, the designer picks one as the primary key, and all the remaining candidate keys are called **alternate keys**. In SQL, you still protect alternate keys from duplicates by declaring them with the `UNIQUE` keyword.

### 5. Composite Key
A **composite key** is not a separate tier in the hierarchy. Instead, it simply means *any* key (whether super, candidate, primary, or foreign) that is built from **two or more attributes** rather than a single attribute. For example, `{student_id, name}` is a composite super key, while `{student_id, course_id}` in an enrollment table is a composite candidate and primary key.

### 6. Foreign Key
A **foreign key** is a column (or set of columns) in a child table whose value must match an existing primary key (or unique candidate key) value in a parent table, or else be `NULL`:
- It acts as a bridge connecting two tables.
- It enforces **referential integrity**, which stops anyone from inserting a child record that refers to a nonexistent parent (like assigning a student to a department that does not exist).

## Master Running Example (University Schema)

Consider the relation schema for students in an academic department:
$$
\text{Student}(\underline{\text{student\_id}}, \text{nid}, \text{email}, \text{name}, \text{dept\_name})
$$

### Sample Relation Instance

| student_id | nid | email | name | dept_name |
| :---: | :---: | :--- | :--- | :---: |
| 101 | 1999123456 | akib@gmail.com | Akib | ECE |
| 102 | 2000654321 | shuvo@gmail.com | Shuvo | ECE |
| 103 | 2001987654 | sakib@gmail.com | Sakib | ETE |

### Key Classification Walkthrough

1. **Super Keys:**
   - Single-attribute unique sets: $\{\text{student\_id}\}$, $\{\text{nid}\}$, $\{\text{email}\}$.
   - Sets with extra attributes: $\{\text{student\_id}, \text{name}\}$, $\{\text{email}, \text{dept\_name}\}$, $\{\text{student\_id}, \text{nid}, \text{email}, \text{name}, \text{dept\_name}\}$.
2. **Candidate Keys:**
   - Minimal unique sets: $\{\text{student\_id}\}$, $\{\text{nid}\}$, $\{\text{email}\}$.
   - Notice that $\{\text{student\_id}, \text{name}\}$ is **not** a candidate key because its proper subset $\{\text{student\_id}\}$ is already unique.
3. **Primary Key:**
   - The designer selects $\{\text{student\_id}\}$. It is underlined and cannot be `NULL`.
4. **Alternate Keys:**
   - The unselected candidate keys: $\{\text{nid}\}$ and $\{\text{email}\}$.
5. **Composite Key Example:**
   - Consider the course enrollment relation:
     $$
     \text{Takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{semester}, \text{grade})
     $$
   - A student enrolls in many courses, and a course has many students.
   - Neither $\text{student\_id}$ nor $\text{course\_id}$ alone uniquely identifies a row.
   - The combination $\{\text{student\_id}, \text{course\_id}\}$ forms a composite candidate key and primary key.
6. **Foreign Key Example:**
   - In table $\text{Student}$, attribute $\text{dept\_name}$ is a foreign key referencing the primary key of $\text{Department}(\underline{\text{dept\_name}}, \text{building}, \text{budget})$.
   - If a tuple in $\text{Student}$ contains $\text{dept\_name} = \text{'ECE'}$, the value `'ECE'` must exist in the parent $\text{Department}$ table.

## Foreign Key Mechanics & Referential Actions

When parent records are deleted or modified, foreign keys prevent dangling (orphan) child records. Database designers configure automated actions using SQL clauses:

```sql
CREATE TABLE Student (
    student_id   INT PRIMARY KEY,
    name         VARCHAR(50) NOT NULL,
    dept_name    VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES Department(dept_name)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

- **ON DELETE CASCADE:** If a parent department is deleted, all students enrolled in that department are automatically deleted.
- **ON UPDATE CASCADE:** If a department name changes (e.g., from `'ETE'` to `'ECE'`), all child records update automatically to reflect the new value.
- **RESTRICT / NO ACTION:** The DBMS rejects any delete or update on a parent record if child records currently reference it.
- **SET NULL:** The DBMS sets the foreign key in child records to `NULL` when the parent record is deleted.

### 🎯 GQ1 · 2023 Q.3(b) · Distinctions Among Primary, Candidate, Super, and Composite Keys

> **Appeared:** 2023 Q.3(b) — (4 marks)

**Question:**

Explain the distinctions among the terms-  
(i) Primary key  
(ii) Candidate key  
(iii) Super key  
(iv) Composite key

**Full Answer:**

A key is an attribute or set of attributes used to identify tuples uniquely in a relation.

**1. Distinctions Among the Four Keys:**

| Key Type | Definition | Minimality Required? | NULL Permitted? |
| :--- | :--- | :---: | :---: |
| **(i) Primary Key** | The specific candidate key chosen by the database designer as the main tuple identifier. | Yes (strictly minimal) | No (`NOT NULL` mandatory) |
| **(ii) Candidate Key** | A minimal super key where no proper subset can uniquely identify a tuple. | Yes (strictly minimal) | Yes (unless constrained `NOT NULL`) |
| **(iii) Super Key** | Any set of attributes that uniquely identifies each tuple. Can contain extra attributes. | No (redundant attributes allowed) | No for identifying columns |
| **(iv) Composite Key** | Any key that consists of two or more attributes rather than a single attribute. | Can be minimal or non-minimal | Depends on whether it is PK or unique |

**2. Hierarchy Formula:**

$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

**3. Illustrative Examples:**
Consider relation $\text{Student}(\underline{\text{student\_id}}, \text{nid}, \text{email}, \text{name})$:
- **Super Key:** $\{\text{student\_id}, \text{name}\}$ is a super key. It uniquely identifies a student, but contains an extra attribute (`name`).
- **Candidate Key:** Both $\{\text{student\_id}\}$ and $\{\text{email}\}$ are candidate keys. Removing any attribute ruins uniqueness.
- **Primary Key:** The designer chooses $\{\text{student\_id}\}$ as the primary key. It uniquely identifies every record and cannot contain `NULL`.
- **Composite Key:** In table $\text{Takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{grade})$, neither column alone can identify an enrollment. The combination $\{\text{student\_id}, \text{course\_id}\}$ forms a composite primary key.

### 🎯 GQ2 · 2018 Q.2(a) · Distinctions Among Primary, Candidate, and Super Key with Example

> **Appeared:** 2018 Q.2(a) — (4 marks)

**Question:**

Explain the distinctions among the terms primary key, candidate key, and super key with proper example.

**Full Answer:**

**1. Conceptual Distinctions:**
- **Super Key:** A set of one or more attributes that taken collectively allows us to identify uniquely a tuple in a relation. It may contain redundant columns.
- **Candidate Key:** A super key that is minimal. No proper subset of a candidate key is a super key. It has zero redundant attributes.
- **Primary Key:** The single candidate key selected by the database designer as the official unique identifier for the relation. It must be unique and cannot contain `NULL`.

**2. Relationship:**
$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}
$$

**3. Concrete Example:**  
Consider the relation schema $\text{Instructor}(\underline{\text{ID}}, \text{name}, \text{email}, \text{dept\_name})$:

| ID | name | email | dept_name |
| :---: | :--- | :--- | :--- |
| 10101 | Srinivasan | srini@univ.edu | Comp. Sci. |
| 12121 | Wu | wu@univ.edu | Finance |
| 15151 | Mozart | mozart@univ.edu | Music |

- **Super Keys:** $\{\text{ID}\}$, $\{\text{email}\}$, $\{\text{ID}, \text{name}\}$, $\{\text{ID}, \text{dept\_name}\}$, $\{\text{ID}, \text{name}, \text{dept\_name}\}$.
- **Candidate Keys:** $\{\text{ID}\}$ and $\{\text{email}\}$. Both uniquely identify every row with no extra attributes. The set $\{\text{ID}, \text{name}\}$ is not a candidate key because its proper subset $\{\text{ID}\}$ is already unique.
- **Primary Key:** The designer chooses $\{\text{ID}\}$ as the primary key.

### 🎯 GQ3 · 2019 Q.6(b) · Different Keys in DBMS and Importance/Use of Foreign Key

> **Appeared:** 2019 Q.6(b) — (6 marks)

**Question:**

Discuss the different keys in DBMS. Write down the importance and use of foreign key with example.

**Full Answer:**

**Part 1: Different Keys in DBMS**

1. **Super Key:** An attribute or group of attributes that uniquely identifies a record in a table. It may include extra attributes (e.g., $\{\text{student\_id}, \text{name}\}$).
2. **Candidate Key:** A minimal super key. Removing any attribute destroys uniqueness. A table can have multiple candidate keys (e.g., $\{\text{student\_id}\}$, $\{\text{email}\}$).
3. **Primary Key:** The candidate key chosen by the database designer to identify tuples uniquely. It cannot be `NULL` and should never change.
4. **Alternate Key:** Any candidate key not chosen as the primary key (e.g., if $\text{student\_id}$ is primary key, $\text{email}$ is an alternate key).
5. **Composite Key:** A key consisting of two or more attributes working together to uniquely identify a record (e.g., $\{\text{course\_id}, \text{sec\_id}, \text{semester}, \text{year}\}$).
6. **Foreign Key:** An attribute in a table that references the primary key of another table to establish a relational link.

**Part 2: Importance and Use of Foreign Key**

- **Importance of Foreign Keys:**
  1. **Enforces Referential Integrity:** Guarantees that child rows point to valid parent records. It prevents orphan records from entering the database.
  2. **Establishes Relationships:** Links separate entities cleanly without duplicating non-key attributes across tables.
  3. **Automates Consistency:** Supports cascading operations (`ON DELETE CASCADE`, `ON UPDATE CASCADE`). Updating or deleting parent records automatically synchronizes child records.

- **Illustrative Example:**  
  Consider two tables:
  - Parent Table: $\text{Department}(\underline{\text{dept\_name}}, \text{building}, \text{budget})$
  - Child Table: $\text{Instructor}(\underline{\text{ID}}, \text{name}, \text{dept\_name}, \text{salary})$

  Here, attribute $\text{dept\_name}$ in $\text{Instructor}$ is a foreign key referencing $\text{dept\_name}$ in $\text{Department}$.
  - **Valid Operation:** Inserting an instructor with $\text{dept\_name} = \text{'Comp. Sci.'}$ succeeds if `'Comp. Sci.'` exists in $\text{Department}$.
  - **Integrity Protection:** If a user tries to insert an instructor with $\text{dept\_name} = \text{'Robotics'}$, and `'Robotics'` does not exist in $\text{Department}$, the DBMS rejects the operation with a referential integrity violation.

### 🎯 GQ4 · 2020 Q.2(b) · Short Notes on Super Key, Candidate Key, Primary Key, and Foreign Key

> **Appeared:** 2020 Q.2(b) — (4 marks)

**Question:**

Write short note about: Super Key, Candidate Key, Primary Key, and Foreign Key.

**Full Answer:**

**1. Super Key:**
- **Definition:** A set of one or more attributes that uniquely identifies a tuple within a relation.
- **Key Feature:** Minimality is not required. If $K$ is a super key, any superset of $K$ is also a super key.
- **Example:** In $\text{Student}(\underline{\text{ID}}, \text{name}, \text{email})$, both $\{\text{ID}\}$ and $\{\text{ID}, \text{name}\}$ are super keys.

**2. Candidate Key:**
- **Definition:** A minimal super key. No proper subset can uniquely identify tuples in the relation.
- **Key Feature:** Contains zero redundant attributes. A relation may have multiple candidate keys.
- **Example:** Both $\{\text{ID}\}$ and $\{\text{email}\}$ are candidate keys for $\text{Student}$.

**3. Primary Key:**
- **Definition:** The specific candidate key chosen by the database designer as the principal identifier of tuples.
- **Key Feature:** Must be unique and cannot contain `NULL` values (`NOT NULL` constraint).
- **Example:** $\{\text{ID}\}$ is chosen as the primary key of $\text{Student}$.

**4. Foreign Key:**
- **Definition:** An attribute in a referencing table that matches the primary key of a referenced table.
- **Key Feature:** Enforces referential integrity. Values must either exist in the referenced parent table or be `NULL`.
- **Example:** $\text{dept\_name}$ in $\text{Student}$ references the primary key $\text{dept\_name}$ in $\text{Department}$.

> **Appeared:** 2021 Q.2(b) — (3 marks)

**Question:**

Differentiate among Superkey, Candidate Key and Primary Key with an appropriate example.

**Full Answer:**

**1. Distinctions Table:**

| Comparison Point | Superkey | Candidate Key | Primary Key |
| :--- | :--- | :--- | :--- |
| **Definition** | Any set of attributes that uniquely identifies a row. | A minimal superkey with no redundant attributes. | The candidate key chosen by the designer to identify records. |
| **Minimality** | Not required (may have extraneous columns). | Strictly required (irreducible). | Strictly required (minimal). |
| **NULL Permitted** | No for identifying attributes. | Permitted unless constrained `NOT NULL`. | Never permitted (`NOT NULL` enforced). |

$$
\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Superkeys}
$$

**3. Example:**  
Consider relation schema $\text{Student}(\underline{\text{roll\_no}}, \text{reg\_no}, \text{name}, \text{phone})$:
- **Superkey:** $\{\text{roll\_no}, \text{name}\}$ uniquely identifies a student, but contains redundant column `name`.
- **Candidate Key:** $\{\text{roll\_no}\}$ and $\{\text{reg\_no}\}$ are minimal superkeys.
- **Primary Key:** The designer selects $\{\text{roll\_no}\}$ as the primary key.

### 🎯 HYE-01 · Practice Exercise 2.1 · Key Identification on Employee Database Schema

> **Source:** Silberschatz 7e · Chapter 2 (Practice Exercise 2.1)  
> **Exam Relevance:** High-Probability Foundational Exam Drill  
> **Key Tested Concept:** Identifying primary keys and candidate keys under varying real-world business constraints.

**Problem Statement:**
> Consider the standard employee relational schema:
> - $\text{employee}(\underline{\text{person\_name}}, \text{street}, \text{city})$
> - $\text{works}(\text{person\_name}, \text{company\_name}, \text{salary})$
> - $\text{company}(\underline{\text{company\_name}}, \text{city})$
> - $\text{manages}(\text{person\_name}, \text{manager\_name})$
> 1. Specify the primary key for the relation `works` under the assumption that **each person can work for at most one company**.
> 2. Specify the primary key for `works` if people are permitted to work for **multiple companies simultaneously** (e.g., part-time consultants).
> 3. Specify the primary key for `manages` assuming an employee can have **at most one manager**, versus **multiple managers**.

**Model Exam-Style Solution:**

1. **Primary Key of `works` (Single Employer Assumption):**
   - If each person can work for at most one company, `person_name` uniquely identifies the tuple.
   - For any given `person_name`, there is only one corresponding `company_name` and `salary`.
   - **Primary Key:** $\{\mathbf{\text{person\_name}}\}$.
   - Schema: $\text{works}(\underline{\text{person\_name}}, \text{company\_name}, \text{salary})$.

2. **Primary Key of `works` (Multiple Employer Assumption):**
   - If a person can work for multiple companies, `person_name` can appear in multiple tuples (once for each employer).
   - A person can work for the same company at most once.
   - Thus, the combination of employee and company uniquely identifies the tuple.
   - **Primary Key:** $\{\mathbf{\text{person\_name}, \text{company\_name}}\}$ (Composite Key).
   - Schema: $\text{works}(\underline{\text{person\_name}, \text{company\_name}}, \text{salary})$.

3. **Primary Key of `manages`:**
   - **Case A: Each employee has at most one manager:**
     - Each `person_name` maps to a unique `manager_name`.
     - **Primary Key:** $\{\mathbf{\text{person\_name}}\}$.
   - **Case B: An employee can have multiple managers (e.g., matrix management):**
     - A `person_name` can be associated with multiple `manager_name` values.
     - **Primary Key:** $\{\mathbf{\text{person\_name}, \text{manager\_name}}\}$. $\blacksquare$

**💡 RUET Exam Takeaway:**
Always state the underlying business assumption when choosing keys. A key is NOT a mathematical accident; it is determined by enterprise policy!

## ⚡ Exam Tips & Common Mistakes

1. **State the Inclusion Formula:** Writing $\text{Primary Key} \subseteq \text{Candidate Keys} \subseteq \text{Super Keys}$ demonstrates complete conceptual mastery to the examiner.
2. **Never Call a Composite Key a Fourth Category:** A composite key is simply any key that contains two or more attributes. It can be a composite super key, composite candidate key, or composite primary key.
3. **Remember `NOT NULL` for Primary Keys:** Entity integrity forbids `NULL` in primary keys. Candidate keys and alternate keys can theoretically permit `NULL` unless explicitly declared `NOT NULL`.
4. **Foreign Keys Reference Candidate Keys Too:** Foreign keys do not only reference primary keys. They can also reference any unique candidate key in the parent relation.
