# T09.5: Concurrency Anomalies (Dirty Read, Lost Update, Unrepeatable Read)

> **Topic:** T09: Transactions, ACID & Anomalies | **Priority:** 🟡 Medium Priority | **Exam Frequency:** 2/7 finals (+ CT-04) (7 marks)  
> **Sources:** Silberschatz 7e Ch. 17 (§17.5) · Lecture Deck 07 (Slides 28–33) · Classnote by Raidah (T09, pp. 26, 28)

## Why This Topic Matters

Running transactions concurrently keeps the CPU and disks busy, but if the DBMS lets transactions interleave without any rules, they step on each other's toes and break **Isolation**. This causes classic data corruption bugs known as concurrency anomalies. RUET exams regularly ask you to list what goes wrong when concurrency control is missing and prove your point with a step-by-step schedule table.

---

## 📝 Key Definitions

> **Concurrency-Control Component:** "The concurrency-control component of the database system carries out this task [ensuring that any schedule that is executed will leave the database in a consistent state]."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §17.5 (p. 812)

> **Lost Update:** "In the lost update problem, an update done to a data item by a transaction is lost as it is overwritten by the update done by another transaction."  
> — Lecture Deck 07, Slide 31 *(Course definition)*

> **Dirty Read (Temporary Update):** "The dirty read problem occurs when one transaction update an data item of database, and somehow the transaction fails. But before the item gets rollback, the updated database item is accessed by another transaction."  
> — Lecture Deck 07, Slide 29 *(Course definition)*

> **Unrepeatable Read:** "This problem occurs when two or more read operation of the same transaction read different values of the same database item."  
> — Lecture Deck 07, Slide 30 *(Course definition)*

> **Phantom Read:** "The phantom read problem occurs when a transaction reads a variable once but when it tries to read that same variable again, an error occurs saying that the variable does not exist."  
> — Lecture Deck 07, Slide 32 *(Course definition)*

## 1. Overview of Concurrency Anomalies

### Intuitive Analogy: Two People Editing a Shared Spreadsheet Offline

Imagine you and a teammate both open a shared inventory spreadsheet showing 20 laptops in stock. You sell 2 laptops and save "18", while your teammate receives 5 new laptops and saves "25" a second later. Because your teammate's save overwrites yours, the 2 laptops you sold vanish from the record (**Lost Update**). Or suppose your teammate types "1,000" by mistake, you copy that number into a financial report, and then your teammate hits Undo (**Dirty Read**). Every concurrency anomaly is just a database version of two people reading and writing the same shared data without coordinating.

When transaction isolation fails, five classic concurrency anomalies can corrupt the database:

| Anomaly Name | Alternative Name | What Causes It | What Goes Wrong |
| :--- | :--- | :--- | :--- |
| **Lost Update** | Overwrite Problem | A second transaction overwrites a value written by the first transaction | The first transaction's update disappears completely |
| **Dirty Read** | Temporary Update | A transaction reads an uncommitted update from another transaction that later aborts | Calculations are based on phantom numbers that were rolled back |
| **Unrepeatable Read** | Fuzzy Read | Another transaction modifies and commits an item between two reads in the same transaction | Reading the same variable twice inside one transaction gives two different answers |
| **Phantom Read** | Missing / Appearing Item | Another transaction deletes a variable (or inserts new matching rows) between two reads | The second read fails because the variable is gone (or sees brand-new rows) |
| **Incorrect Summary** | Inconsistent Analysis | A summary query (`SUM` / `AVG`) runs while a transfer is halfway across accounts | The total either misses money in transit or counts it twice |

## 2. Detailed Breakdown of the Five Anomalies

### A. Lost Update Problem

A **lost update** happens when two concurrent transactions update the same data item and the second write blindly overwrites the first write. As a result, the first transaction's change is wiped out as if it never happened.

#### Illustrative Mini-Trace (Initial stock $S = 20$):

Suppose $T_1$ deducts 4 items from stock $S = 20$ and writes $S = 16$. Before or right after $T_1$ commits, $T_2$ performs a write setting $S = 30$ (either from an old read of 20 plus 10, or a direct blind write). Once both commit, the database stores $S = 30$, and $T_1$'s deduction of 4 items is completely lost. *(See the full exam table with $A = 500$ in GQ1 below).*

---

### B. Dirty Read Problem (Temporary Update Problem)

A **dirty read** happens when transaction $T_1$ updates a data item, and transaction $T_2$ reads that new value *before* $T_1$ commits. We call uncommitted data "dirty" because it is not final yet. If $T_1$ crashes or aborts a moment later, the recovery system rolls $T_1$'s write back, leaving $T_2$ holding a value that never officially existed.

#### Illustrative Mini-Trace (Initial balance $X = 300$):

1. $T_1$ reads $X = 300$, adds 200, and writes the uncommitted value $X = 500$.
2. $T_2$ reads the uncommitted ("dirty") value $X = 500$, deducts 100, writes $X = 400$, and commits.
3. $T_1$ hits an error and aborts, rolling its own work back.
Because $T_2$ already committed $X = 400$ based on the cancelled +200 deposit, the database balance is now permanently wrong (it should be $300 - 100 = 200$). *(See the full exam table with $A = 100$ in GQ1 below).*

---

### C. Unrepeatable Read Problem

An **unrepeatable read** happens when a single transaction $T_1$ reads the same data item twice during its run, but gets two different values because another transaction $T_2$ modified and committed that item in between the two reads.

#### Step-by-Step Timeline ($A = 500$ initially):

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / What Happens |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | | $\text{read}(A)$ | $T_2$ also reads $A = 500$ |
| $t_3$ | | $A := A + 100$ | $T_2$ calculates $A = 600$ locally |
| $t_4$ | | $\text{write}(A)$ | $T_2$ updates database to $A = 600$ |
| $t_5$ | | $\text{commit}$ | $T_2$ commits its change permanently |
| $t_6$ | $\text{read}(A)$ | | $T_1$ reads $A$ a second time and gets $600$ instead of $500$! |

**Result:** Inside a single transaction, $T_1$ asked for the value of $A$ twice and got two contradictory answers ($500$ vs. $600$).

---

### D. Phantom Read Problem

In the RUET lecture slides (Deck 07, Slide 32), the **phantom read** problem is taught as a concurrent deletion error: transaction $T_2$ reads variable $A$ once, then transaction $T_1$ deletes $A$, and when $T_2$ tries to read $A$ a second time, the database throws an error saying $A$ no longer exists.

#### Step-by-Step Timeline:

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / What Happens |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | $\text{read}(A)$ | Both transactions read data item $A$ successfully |
| $t_2$ | $\text{delete}(A)$ | | $T_1$ deletes data item $A$ from the database |
| $t_3$ | | $\text{read}(A)$ | $T_2$ tries to read $A$ again, triggering a "variable does not exist" error |

> **Note:** In standard SQL and Silberschatz textbook terminology, a phantom read also refers to running a `WHERE` range query twice in one transaction and seeing brand-new ("phantom") rows appear on the second run because another transaction inserted rows in the meantime. In RUET exams, always give the Slide 32 deletion table above first, and you can mention the textbook row-insertion meaning as a bonus note.

---

### E. Incorrect Summary Problem (Inconsistent Analysis)

The **incorrect summary** problem happens when an aggregate transaction $T_2$ calculates a `SUM` or `AVG` across several accounts while another transaction $T_1$ is transferring money between those accounts. If $T_2$ reads one account *after* money is deducted and reads the other account *before* the money is added, its total will come up short.

#### Step-by-Step Timeline ($A = 1000, B = 1000, C = 1000$ initially):

| Time | Transaction $T_1$ (Transfer \$50: $A \to B$) | Transaction $T_2$ (Average of $A, B, C$) | Running Total in $T_2$ |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A);\; A := A - 50;\; \text{write}(A);$ | | $T_1$ reduces $A$ to $950$ on disk |
| $t_2$ | | $\text{sum} := 0;\; \text{read}(C);\; \text{sum} := \text{sum} + C;$ | $T_2$ reads $C = 1000 \implies \text{sum} = 1000$ |
| $t_3$ | | $\text{read}(A);\; \text{sum} := \text{sum} + A;$ | $T_2$ reads updated $A = 950 \implies \text{sum} = 1950$ |
| $t_4$ | | $\text{read}(B);\; \text{sum} := \text{sum} + B;$ | $T_2$ reads old $B = 1000 \implies \text{sum} = 2950$ |
| $t_5$ | | $\text{avg} := \text{sum} / 3;\; \text{commit};$ | $T_2$ reports $\text{avg} = 2950 / 3 = \$983.33$ |
| $t_6$ | $\text{read}(B);\; B := B + 50;\; \text{write}(B);\; \text{commit};$ | | $T_1$ finishes adding \$50 to $B$ ($B = 1050$) |

**Result:** The true total across $A, B,$ and $C$ is \$3000 (an average of \$1000). Because $T_2$ caught $T_1$ halfway through its transfer, \$50 was missed and $T_2$ reported a false average of \$983.33.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.5(a) & 2024 Q.8(a) · Concurrency Problems and Examples

> **Appeared:** 2018 Q.5(a) (4 marks), 2024 Q.8(a) (3 marks)

> **Question:**
>
> If concurrency-control management is not implemented properly what problem may occur? Explain with example.

**Full Answer:**

If concurrency-control management is not implemented properly, concurrent transactions interleave without restriction and violate the ACID property of **Isolation**, leaving the database in an inconsistent, corrupted state.

The five major concurrency problems that can occur are:
1. **Lost Update Problem**
2. **Dirty Read Problem (Temporary Update Problem)**
3. **Unrepeatable Read Problem**
4. **Phantom Read Problem**
5. **Incorrect Summary Problem (Inconsistent Analysis)**

Below are two detailed examples with step-by-step schedules showing how data corruption happens:

#### 1. Lost Update Problem

In the **lost update problem**, an update made to a data item by one transaction is lost because a second concurrent transaction overwrites that data item without accounting for the first update.

*Initial State:* Account $A = 500$.

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Description |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | $A := A - 50$ | | $T_1$ computes new balance $450$ locally |
| $t_3$ | $\text{write}(A)$ | | Database is updated to $A = 450$ |
| $t_4$ | | $\text{write}(A)$ | $T_2$ performs a blind write setting $A := 25$ |
| $t_5$ | $\text{commit}$ | | $T_1$ commits |
| $t_6$ | | $\text{commit}$ | $T_2$ commits, leaving final database value $A = 25$ |

*Impact:* The \$50 deduction made by $T_1$ is completely overwritten and lost.

#### 2. Dirty Read Problem (Temporary Update Problem)

In the **dirty read problem**, one transaction updates a data item and a second transaction reads that uncommitted ("dirty") value before the first transaction finishes. When the first transaction later fails and rolls back, the second transaction has calculated and saved results based on a temporary number that was cancelled.

*Initial State:* Account $A = 100$.

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Description |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads initial balance $A = 100$ |
| $t_2$ | $A := A + 100$ | | $T_1$ computes $A = 200$ locally |
| $t_3$ | $\text{write}(A)$ | | Database is updated to $A = 200$ (uncommitted) |
| $t_4$ | | $\text{read}(A)$ | $T_2$ reads the uncommitted dirty value $A = 200$ |
| $t_5$ | | $A := A - 50$ | $T_2$ computes $A = 150$ locally |
| $t_6$ | | $\text{write}(A)$ | Database is updated to $A = 150$ |
| $t_7$ | | $\text{commit}$ | $T_2$ commits its update based on dirty data |
| $t_8$ | **Failure / Rollback** | | $T_1$ fails and aborts (its $+100$ change is cancelled) |

*Impact:* $T_2$ committed $A = 150$ based on a temporary value of $200$ that was rolled back, corrupting the database.

### 🎯 GQ2 · CT-04 Q.03 · Explain Any Two Problems Caused by Concurrent Execution

> **Appeared:** CT-04 Q.03 (4 marks)

> **Question:**
>
> Explains any two problems caused by concurrent execution. *(Note: Printed verbatim in original script)*.

**Full Answer:**

Two major problems caused by uncontrolled concurrent execution are the **Dirty Read Problem** and the **Lost Update Problem**:

#### 1. Dirty Read Problem (Temporary Update Problem)
- **Definition:** Occurs when a transaction reads a data item that was updated by another uncommitted transaction, and that modifying transaction later fails and rolls back.
- **Example Schedule ($A = 100$ initially):**

| Step | Transaction $T_1$ | Transaction $T_2$ | Action |
| :---: | :--- | :--- | :--- |
| 1 | $\text{read}(A)$ | | $T_1$ reads $A = 100$ |
| 2 | $A := A + 100;\; \text{write}(A)$ | | $T_1$ writes uncommitted value $A = 200$ |
| 3 | | $\text{read}(A)$ | $T_2$ reads dirty value $A = 200$ |
| 4 | | $A := A - 50;\; \text{write}(A)$ | $T_2$ writes $A = 150$ |
| 5 | | $\text{commit}$ | $T_2$ commits permanently |
| 6 | $\text{rollback}$ | | $T_1$ fails and rolls back |

Because $T_2$ used $T_1$'s uncommitted value of $200$ before $T_1$ aborted, the committed balance $A = 150$ is wrong.

#### 2. Lost Update Problem
- **Definition:** Occurs when two concurrent transactions update the same data item and the second transaction overwrites the value written by the first transaction, causing the first update to vanish.
- **Example Schedule ($A = 500$ initially):**

| Step | Transaction $T_1$ | Transaction $T_2$ | Action |
| :---: | :--- | :--- | :--- |
| 1 | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| 2 | $A := A - 50;\; \text{write}(A)$ | | $T_1$ updates $A$ to $450$ |
| 3 | | $\text{write}(A)$ | $T_2$ overwrites $A$ with a blind write $A = 25$ |
| 4 | $\text{commit}$ | | $T_1$ commits |
| 5 | | $\text{commit}$ | $T_2$ commits, leaving $A = 25$ in the database |

The \$50 reduction performed by $T_1$ is overwritten and permanently lost.

## ⚡ Exam Tips & Common Mistakes

1. **Always Draw Schedule Tables:** Never explain concurrency anomalies with plain paragraphs alone. Draw a two-column schedule table ($T_1$ and $T_2$) with numbered time steps ($t_1, t_2, \dots$).
2. **Include Starting Numbers and Final Corrupted Values:** Start with a clean number like $A = 500$ or $A = 100$ from Lecture Deck 07, show the math at each step, and state why the final value is wrong.
3. **Don't Mix Up Dirty Read and Unrepeatable Read:** In a **Dirty Read**, $T_2$ reads an *uncommitted* write from $T_1$ before $T_1$ aborts. In an **Unrepeatable Read**, $T_1$ reads $A$ twice and gets two different values because $T_2$ updated and *committed* $A$ in between.
4. **Best Two to Pick on Exams:** When a question asks for "any two problems" or "an example", always write **Lost Update** and **Dirty Read**. Their tables are only 5 to 8 rows long and match Slides 29 and 31 directly.
