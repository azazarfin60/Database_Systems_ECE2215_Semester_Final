# T03.1: Relation, Tuple, Attribute, and Domain

> **Topic:** T03 — Relational Model, Keys & Integrity | **Priority:** 🟢 Low | **Exam Frequency:** 1/7 finals (2 marks: 2018 Q3b)
> **Sources:** Silberschatz 7e Ch. 2 (§2.1–2.2) · Lecture Deck 02 (Slides 2–5) · Lecture Deck 03 (Slide 6) · Class Notes (Raidah p. 12; Fahim p. 18, 26)

## Why This Topic Matters

The relational model forms the theoretical backbone of modern relational database management systems. Understanding formal relational terminology (relation, tuple, attribute, and domain) is essential for relational algebra and SQL. In semester finals, RUET tests this foundation with sharp conceptual questions, most notably the distinction between domain and data type (2018 Q.3(b)).

---

## 📝 Key Definitions

> **Relation:** A relation is a two-dimensional table made of rows and columns. Mathematically, a relation $r$ on schema $R(A_1, A_2, \dots, A_n)$ is a subset of the Cartesian product of its attribute domains: $r(R) \subseteq \text{dom}(A_1) \times \text{dom}(A_2) \times \dots \times \text{dom}(A_n)$.

> **Tuple:** A tuple is a single row or record in a relation. Mathematically, an $n$-tuple is a list of $n$ values $\langle v_1, v_2, \dots, v_n \rangle$ where each value $v_i$ belongs to the domain of attribute $A_i$.

> **Attribute:** An attribute is a named column of a relation. It represents a specific property of each record in the table.

> **Domain:** A domain is the set of all permitted and meaningful values that an attribute is allowed to take.

> **Atomic Domain:** A domain is atomic if every value in it is a single indivisible unit. Composite lists or sets are not allowed inside a single cell.

The relational data model represents all data in the form of two-dimensional tables called relations.

## Core Relational Invariants

The relational model is built on four simple rules that every table must obey:

### 1. Mathematical Foundation (Why a Table is a Subset of a Cartesian Product)
Imagine a tiny table with just two columns: `dept_name` (which can only be `'ECE'` or `'CSE'`) and `year` (which can only be `1`, `2`, `3`, or `4`). If you list every possible pair of valid values (`('ECE', 1)`, `('ECE', 2)`, ..., `('CSE', 4)`), you get $2 \times 4 = 8$ possible combinations. In math, that complete list of all possible combinations is called the **Cartesian product** ($\times$) of the domains.

At any moment, your actual database table only holds the combinations that currently exist in the real world. That is why a relation $r$ on schema $R(A_1, A_2, \dots, A_n)$ is formally defined as a **subset** ($\subseteq$) of the Cartesian product of its column domains:

$$
r(R) \subseteq \text{dom}(A_1) \times \text{dom}(A_2) \times \dots \times \text{dom}(A_n)
$$

Because a mathematical relation is a **set** of tuples, duplicate rows are strictly forbidden in pure relational theory.

### 2. Tuples are Unordered
Just like the elements of a math set $\{1, 2, 3\}$ are the same as $\{3, 1, 2\}$, the order of rows in a relational table does not matter. Whether a table is printed sorted by `ID` or sorted by `salary`, both printouts represent the exact same relation instance because they contain the same set of tuples.

### 3. Domains Must Be Atomic (Indivisible)
Every cell in a relational table must hold a single, indivisible value:
- **No composite structures in one cell:** Full addresses containing street, city, and zip code should be split into separate columns when you need to query those parts individually.
- **No lists or sets in one cell:** Multivalued attributes (like a list of three phone numbers for one person) cannot be crammed into a single cell. Instead, they must be split into separate rows or moved into a child table.
- This single-value-per-cell rule is the exact definition of **First Normal Form (1NF)**.

### 4. The Special `null` Value
The special marker `null` belongs to every domain. It is not zero or an empty string. Instead, it means the value is **unknown**, **unrecorded**, or **not applicable** (such as a `middle_name` for someone who does not have one). Because you cannot tell whether two unknown values are equal, `null` introduces three-valued logic (`TRUE`, `FALSE`, and `UNKNOWN`) into SQL queries.

## Domain vs. Data Type: The Critical Distinction

Students often treat **domain** and **data type** as synonyms, but they sit at two completely different levels of database design (tested directly in **2018 Q.3(b)**):

- A **data type** is a **machine-level storage format**. It tells the computer how many bytes to allocate and how to interpret the bits (such as `INT`, `VARCHAR(50)`, or `FLOAT`).
- A **domain** is a **real-world meaning and rule set**. It defines what values actually make sense for that specific column in your business or university.

### Detailed Comparison Table

| Comparison Feature | Domain (Logical Level) | Data Type (Physical Level) |
| :--- | :--- | :--- |
| **Definition** | The set of all valid, meaningful real-world values for an attribute. | The physical storage format and bit layout defined by the DBMS and hardware. |
| **Abstraction Level** | Conceptual and semantic layer. | Physical storage and execution layer. |
| **Enforcement** | Business rules, range constraints, and `CHECK` clauses. | Built-in system storage limits (such as 4-byte integer width). |
| **Value Permissibility** | Strict semantic subset (for example, letter grades `{'A', 'B', 'C', 'D', 'F'}`). | Broad computer format (for example, `CHAR(1)` allows 256 different ASCII characters). |
| **Semantic Compatibility** | Comparing values from different domains makes no sense even if their storage types match. | Comparing values with matching data types is accepted by the CPU without error. |

### Concrete Illustrative Example

Think about two columns in a university database: `student_age` and `monthly_stipend`.

In SQL, a programmer might declare both columns using the exact same **data type**: `INT`. However, they come from two completely different **domains**:
- $\text{dom}(\text{student\_age}) = \{x \in \mathbb{Z} \mid 16 \le x \le 100\}$ (measured in years)
- $\text{dom}(\text{monthly\_stipend}) = \{x \in \mathbb{Z} \mid 0 \le x \le 50000\}$ (measured in Taka)

Because they belong to different domains, writing a query condition like `WHERE student_age = monthly_stipend` or `student_age + monthly_stipend` is meaningless in the real world, even though the database engine can physically compare or add two `INT` numbers without throwing a syntax error.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.3(b) · Differentiate Between Domain and Data Type

> **Appeared:** 2018 Q.3(b) — (2 marks)

**Question:**

Differentiate between domain and data type.

**Full Answer:**

**1. Definitions:**
- **Domain:** A domain is the logical set of all valid and semantically meaningful values that an attribute can take in the real world. It reflects conceptual business rules.
- **Data Type:** A data type is a physical computer representation and storage specification recognized by the hardware and DBMS. It defines memory size and storage layout.

**2. Distinction Table:**

| Comparison Point | Domain | Data Type |
| :--- | :--- | :--- |
| **Concept Level** | Conceptual and semantic level (real-world meaning). | Physical implementation level (machine storage format). |
| **Values Allowed** | Strict subset of valid values (e.g., letter grades `{'A', 'B', 'C', 'F'}`). | Broad machine-level range (e.g., `CHAR(1)` accepts any ASCII symbol). |
| **Validation** | Carries logical rules (e.g., `age BETWEEN 18 AND 65`). | Restricts memory width and type category (e.g., `INTEGER`). |
| **Compatibility** | Two attributes with the same data type can have different domains. | Two attributes share a data type if their byte representations match. |

**3. Example:**  
Both `roll_number` and `bus_fare` can be implemented using the `INT` data type. However, they belong to different domains. Performing arithmetic operations like `roll_number + bus_fare` is mathematically possible for the CPU, but conceptually and semantically meaningless in the relational model.

### 🎯 HYE-01 · Exercise 2.10 · Relation Schema vs. Relation Instance & Formal Tuple Structure

> **Source:** Silberschatz 7e · Chapter 2 (Exercise 2.10)  
> **Exam Relevance:** High-Probability Foundational Theory Drill (Complements 2018 Q.3(b))  
> **Key Tested Concept:** Formal mathematical definitions of relation schema $R(A_1, \dots, A_n)$, dynamic relation instance $r(R) \subseteq D_1 \times \dots \times D_n$, tuple structure, and atomic domain constraints.

**Problem Statement:**
> 1. Formally describe the differences in meaning between the terms **relation** (or relation instance) and **relation schema**.
> 2. State the mathematical definition of a relation schema $R$ and a relation instance $r(R)$ defined over attribute domains $D_1, D_2, \dots, D_n$.
> 3. Define what constitutes a **tuple** in the relational model, and explain why the ordering of tuples within a relation instance has no significance.
> 4. Clarify how an attribute **domain** differs from a programming language **data type** in this formal relational context.

**Model Exam-Style Solution:**

1. **Relation Schema vs. Relation Instance (Core Difference):**
   - **Relation Schema ($R$):** The logical design, structure, and blueprint of the relation. It specifies the relation name, the set of attributes (columns), and integrity constraints. It corresponds to a type declaration in a programming language and is **static** (changes infrequently, only via DDL `ALTER TABLE`).
   - **Relation Instance ($r$):** The actual table content or snapshot at a specific point in time, consisting of a set of tuples (rows). It corresponds to the runtime value of a variable and is **dynamic** (changes frequently whenever tuples are inserted, deleted, or modified via DML).

2. **Formal Mathematical Definition:**
   - Let $A_1, A_2, \dots, A_n$ be attributes, and let each attribute $A_i$ be associated with an atomic domain of permitted values denoted by $\text{dom}(A_i)$ (or $D_i$).
   - A **relation schema** is denoted by:
     $$
     R = (A_1, A_2, \dots, A_n)
     $$
   - A **relation instance** $r$ on schema $R$, denoted $r(R)$, is a mathematical **subset of the Cartesian product** of the attribute domains:
     $$
     r(R) \subseteq \text{dom}(A_1) \times \text{dom}(A_2) \times \dots \times \text{dom}(A_n)
     $$
   - Since $r$ is mathematically a set of elements, every element (tuple) must be unique (enforced by candidate keys), and there is no inherent ordering among elements.

3. **Formal Tuple Structure & Order-Independence:**
   - A **tuple** $t \in r$ is an ordered list (or mathematical mapping) of $n$ atomic values:
     $$
     t = \langle v_1, v_2, \dots, v_n \rangle \quad \text{where } v_i \in \text{dom}(A_i) \text{ for all } i \in \{1, 2, \dots, n\}
     $$
   - **Why Tuples are Unordered:** In set theory, a set is defined purely by membership, not sequence ($\{t_1, t_2\} = \{t_2, t_1\}$). Thus, swapping any two rows in a table results in the exact same mathematical relation instance $r(R)$.

4. **Domain vs. Data Type in the Formal Context:**
   - **Domain:** The conceptual set of valid atomic real-world values. It provides semantic meaning and defines which values are logically comparable.
   - **Data Type:** The physical machine encoding and memory footprint (e.g., `INT`, `CHAR(10)`).
   - *Formal Semantic Implication:* Even if $\text{ID}$ and $\text{salary}$ are both stored as machine `INTEGER` data types, their domains $\text{dom}(\text{ID}) \subset \mathbb{Z}^+$ and $\text{dom}(\text{salary}) \subset \mathbb{R}^+$ are semantically distinct. The relational model forbids comparing attributes across incompatible domains. $\blacksquare$

**💡 RUET Exam Takeaway:**
Remember the golden analogy for the exam script: **Relation Schema $\equiv$ Class Definition** (static blueprint), while **Relation Instance $\equiv$ Object State at Runtime** (dynamic snapshot).

## ⚡ Exam Tips & Common Mistakes

1. **Always Use the Age vs. Salary Example:** When asked to contrast domain and data type, always provide the example of two integer attributes (`student_age` and `salary`). Showing that they share a data type but belong to distinct domains earns full marks instantly.
2. **Remember Atomicity:** In relational model theory questions, state that attribute domains must be atomic (indivisible). This links directly to First Normal Form (1NF).
3. **Use the 4-Row Distinction Table:** For a 2-mark question, a crisp table with 4 rows is much easier to grade and score than a continuous paragraph of prose.
