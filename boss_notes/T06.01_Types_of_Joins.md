# T06.1: Types of SQL Joins (Inner, Outer, Natural, Cross)

> **Topic:** T06 — Joins & Views | **Priority:** 🟠 High | **Exam Frequency:** 3/7 finals (11 marks)
> **Sources:** Silberschatz 7e Ch. 4 (§4.1, pp. 125–136) · Lecture Deck 04 (Slides 3–23) · Fahim Notes (pp. 50–55) · Raidah Notes (p. 18)

## Why This Topic Matters

In a normalized database, information is split across multiple tables to avoid redundancy. Join operations let you stitch those tables back together during a query. This topic shows up in nearly half of all RUET semester finals (earning 11 marks across 2019, 2023, and 2024). Examiners ask this in two main ways: either explaining every join type using a small two-table example, or contrasting inner joins with outer joins in a comparison table.

---

## 📝 Key Definitions

> **Join Operations:** A join operation combines rows from two tables into one result table based on a matching condition. In relational algebra, it works like a Cartesian product followed by a selection filter. It also specifies which columns appear in the final result.

> **Inner Join:** An inner join ($\bowtie$ or $\bowtie_\theta$) pairs rows from two tables that satisfy a given matching condition. It keeps only the rows that match in both tables and drops any unmatched rows.

> **Outer Join:** An outer join ($\mathbin{⟕}$, $\mathbin{⟖}$, or $\mathbin{⟗}$) keeps all matching rows plus unmatched rows from one or both tables. It fills the missing columns of unmatched rows with `NULL` values to prevent information loss.

> **Natural Join:** A natural join ($\bowtie$) pairs rows that have equal values in all columns sharing the same name across two tables. It removes duplicate shared columns so each common column appears only once in the output.

---

## Core Classification: Join Types vs. Join Conditions

Why does SQL have so many join keywords? Because every join actually answers two separate questions: **"How do we check if two rows match?"** (the *join condition*) and **"What do we do with rows that don't have a match?"** (the *join type*). Lecture Deck 04 (Slide 4) breaks this down cleanly:

![Summary of SQL join types and join conditions](diagrams/T06.01_join_types_conditions__L04_p04_fig01.jpg)
*Figure 1: Summary of SQL join types and join conditions.*

1. **Join Condition (How rows match):**
   - `natural`: Automatically matches rows that have the exact same values in **every** column that shares the same name in both tables.
   - `on <predicate>`: Lets you write any custom matching rule (like `course.course_id = prereq.course_id`).
   - `using (A1, A2, ...)`: Matches rows only on the specific shared column names you list inside the parentheses.
2. **Join Type (What happens to unmatched "dangling" rows):**
   - `inner join`: Keeps **only** rows that match in both tables, and throws away any unmatched rows.
   - `left outer join`: Keeps every row from the **left** table, filling in `NULL` for the right table's columns whenever there is no match.
   - `right outer join`: Keeps every row from the **right** table, filling in `NULL` for the left table's columns whenever there is no match.
   - `full outer join`: Keeps every row from **both** tables, filling in `NULL` on whichever side is missing a match.

You can picture how each join type treats matched and unmatched rows using Venn diagrams:

*Figure 2: Venn diagrams illustrating tuple retention across SQL join types.*

## Detailed Mechanics of Each Join Type

Let's see how each join works on two 3-row tables from the university schema: `course` and `prereq`.

**Base Table: `course`**

| course_id | title | dept_name | credits |
| :--- | :--- | :--- | :---: |
| BIO-301 | Genetics | Biology | 4 |
| CS-190 | Game Design | Comp. Sci. | 4 |
| CS-315 | Robotics | Comp. Sci. | 3 |

**Base Table: `prereq`**

| course_id | prereq_id |
| :--- | :--- |
| BIO-301 | BIO-101 |
| CS-190 | CS-101 |
| CS-347 | CS-101 |

Notice how the rows line up: `BIO-301` and `CS-190` appear in both tables. However, `CS-315` (Robotics) has no prerequisite listed in `prereq`, and `CS-347` appears in `prereq` even though it is missing from the `course` table.

---

### 1. Inner Join (and Natural Join)

An inner join (written as $\bowtie$ in relational algebra) only keeps rows that have a match in both tables. Because `CS-315` and `CS-347` are missing from one of the tables, both are dropped from the output.

**Relational Algebra:**
$$
\text{course} \bowtie_{\text{course.course\_id} = \text{prereq.course\_id}} \text{prereq}
$$

**SQL Query:**
```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
INNER JOIN prereq ON course.course_id = prereq.course_id;
```

**Result Relation (2 rows):**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |

Because `course_id` is the only column name shared by `course` and `prereq`, writing `NATURAL JOIN` produces the exact same 2-row result without needing an `ON` clause, and automatically removes the duplicate `course_id` column:

```sql
SELECT course_id, title, dept_name, prereq_id
FROM course
NATURAL JOIN prereq;
```

---

### 2. Left Outer Join

Notice how the little "wings" on the left outer join symbol ($\mathbin{⟕}$) point to the left table. That is a handy visual reminder that `LEFT JOIN` keeps **every** row from the left table (`course`). Since `CS-315` has no match in `prereq`, it still stays in the result, and its missing `prereq_id` is padded with `NULL`.

**Relational Algebra:**
$$
\text{course} \mathbin{⟕} \text{prereq}
$$

**SQL Query:**
```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
LEFT JOIN prereq ON course.course_id = prereq.course_id;
```

**Result Relation (3 rows):**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-315 | Robotics | Comp. Sci. | `NULL` |

---

### 3. Right Outer Join

In a right outer join ($\mathbin{⟖}$), the wings point to the right table (`prereq`), meaning every row from `prereq` is kept. Because `CS-347` has no match in the `course` table, it is still kept in the output with `NULL` filled in for `title` and `dept_name`.

**Relational Algebra:**
$$
\text{course} \mathbin{⟖} \text{prereq}
$$

**SQL Query:**
```sql
SELECT prereq.course_id, title, dept_name, prereq_id
FROM course
RIGHT JOIN prereq ON course.course_id = prereq.course_id;
```

**Result Relation (3 rows):**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-347 | `NULL` | `NULL` | CS-101 |

---

### 4. Full Outer Join

In a full outer join ($\mathbin{⟗}$), the wings are on both sides, so every row from **both** tables is preserved. Matched rows are paired up normally, while unmatched rows from either side (`CS-315` and `CS-347`) are padded with `NULL` on the missing side.

**Relational Algebra:**
$$
\text{course} \mathbin{⟗} \text{prereq}
$$

**Standard SQL Syntax:**
```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
FULL OUTER JOIN prereq ON course.course_id = prereq.course_id;
```

> [!IMPORTANT]
> **MySQL Emulation Requirement:** MySQL 8 does not have a `FULL OUTER JOIN` keyword! To write a full outer join in MySQL, you run a `LEFT JOIN` and a `RIGHT JOIN` and combine them with `UNION` (which automatically removes the duplicate matched rows):

```sql
SELECT course.course_id, title, dept_name, prereq_id
FROM course
LEFT JOIN prereq ON course.course_id = prereq.course_id
UNION
SELECT prereq.course_id, title, dept_name, prereq_id
FROM course
RIGHT JOIN prereq ON course.course_id = prereq.course_id;
```

**Result Relation (4 rows):**

| course_id | title | dept_name | prereq_id |
| :--- | :--- | :--- | :--- |
| BIO-301 | Genetics | Biology | BIO-101 |
| CS-190 | Game Design | Comp. Sci. | CS-101 |
| CS-315 | Robotics | Comp. Sci. | `NULL` |
| CS-347 | `NULL` | `NULL` | CS-101 |

---

### 5. Cross Join (Cartesian Product)

A cross join ($\times$) does not check any matching condition at all. Instead, it pairs every single row from the first table with every single row from the second table. So if table $A$ has $m$ rows and table $B$ has $n$ rows, `CROSS JOIN` always outputs $m \times n$ rows.

**Relational Algebra:**
$$
\text{course} \times \text{prereq}
$$

**SQL Query:**
```sql
SELECT *
FROM course
CROSS JOIN prereq;
```

Because `course` has 3 rows and `prereq` has 3 rows, this query produces $3 \times 3 = 9$ rows.

## Inner Joining vs. Outer Joining (2024 Q.3(c))

RUET 2024 Q.3(c) asked students to differentiate between inner joining and outer joining. Here is the clean side-by-side comparison:

| Feature / Dimension | Inner Join | Outer Join |
| :--- | :--- | :--- |
| **Tuple Retention** | Keeps only matching rows and drops unmatched rows from both tables. | Keeps all matching rows plus unmatched rows from one or both tables. |
| **Handling Missing Data** | Never adds `NULL` values for missing matches. | Fills missing columns of unmatched rows with `NULL`. |
| **Information Loss** | Loses information whenever a row has no match in the other table. | Avoids losing information by keeping unmatched ("dangling") rows. |
| **Join Forms / Subtypes** | Equijoin, theta join, and natural inner join. | Left outer join, right outer join, and full outer join. |
| **SQL Keywords** | `INNER JOIN`, `JOIN`, or `NATURAL JOIN`. | `LEFT JOIN`, `RIGHT JOIN`, or `FULL JOIN` (via `UNION` in MySQL). |
| **Relational Algebra Symbol** | $\bowtie$ or $\bowtie_\theta$ | $\mathbin{⟕}$, $\mathbin{⟖}$, $\mathbin{⟗}$ |

## Worked Example: The `NATURAL JOIN` Hidden Column Trap

Why do database engineers often prefer `INNER JOIN ... ON` or `JOIN ... USING` instead of `NATURAL JOIN`? Let's trace a compact 2-row university example to see how `NATURAL JOIN` can silently drop valid rows.

Suppose a student in the `ECE` department takes an elective course offered by the `CSE` department:
- `student(ID, name, dept_name)` = `{(101, 'Nabil', 'ECE')}`
- `takes(ID, course_id)` = `{(101, 'CSE-2101')}`
- `course(course_id, title, dept_name)` = `{('CSE-2101', 'Algorithms', 'CSE')}`

Now compare what happens when we join `(student NATURAL JOIN takes)` with `course`:
1. **Using `NATURAL JOIN`:**  
   `SELECT name, title FROM student NATURAL JOIN takes NATURAL JOIN course;`  
   Because both `student` and `course` happen to have a column named `dept_name`, `NATURAL JOIN` checks `student.ID = takes.ID`, `takes.course_id = course.course_id`, **and** `student.dept_name = course.dept_name`. Since `'ECE' != 'CSE'`, Nabil's row is **dropped** and the query returns **0 rows**!
2. **Using `JOIN ... USING (course_id)`:**  
   `SELECT name, title FROM (student NATURAL JOIN takes) JOIN course USING (course_id);`  
   This explicitly tells SQL to match *only* on `course_id` and ignore `dept_name`, returning `(Nabil, Algorithms)` as intended.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2019 Q.3(c) · Join Definition and Types with Examples

> **Appeared:** 2019 Q.3(c) — (05 Marks)

**Question:**

What is joining? Discuss each type of joining between two data tables with example.

**Full Answer:**

**1. Definition of Joining:**  
A join operation combines tuples from two or more relations into a single result relation based on a specified matching condition. In relational algebra, a join acts as a Cartesian product followed by a selection condition and attribute projection. It allows relational databases to reconstruct entity relationships split across normalized tables.

**2. Base Example Tables:**  
Consider two tables: `Department` and `Employee`.

**Table: `Department`**

| dept_id | dept_name |
| :---: | :--- |
| D1 | Sales |
| D2 | Engineering |
| D3 | Marketing |

**Table: `Employee`**

| emp_id | emp_name | dept_id |
| :---: | :--- | :---: |
| 1 | Alice | D1 |
| 2 | Bob | D2 |
| 3 | Charlie | D4 |

Here, D1 and D2 match in both tables. D3 has no employees. Charlie belongs to D4, which has no department record.

**3. Discussion of Join Types:**

**(i) Inner Join:**  
Retains only rows where `dept_id` matches in both tables. Non-matching rows (D3 and Charlie) are discarded.
```sql
SELECT Employee.emp_id, Employee.emp_name, Department.dept_name
FROM Employee
INNER JOIN Department ON Employee.dept_id = Department.dept_id;
```
*Result (2 rows):*

| emp_id | emp_name | dept_name |
| :---: | :--- | :--- |
| 1 | Alice | Sales |
| 2 | Bob | Engineering |

**(ii) Left Outer Join:**  
Preserves every row from the left table (`Employee`). Unmatched right attributes are padded with `NULL`.
```sql
SELECT Employee.emp_id, Employee.emp_name, Department.dept_name
FROM Employee
LEFT JOIN Department ON Employee.dept_id = Department.dept_id;
```
*Result (3 rows):*

| emp_id | emp_name | dept_name |
| :---: | :--- | :--- |
| 1 | Alice | Sales |
| 2 | Bob | Engineering |
| 3 | Charlie | `NULL` |

**(iii) Right Outer Join:**  
Preserves every row from the right table (`Department`). Unmatched left attributes are padded with `NULL`.
```sql
SELECT Employee.emp_id, Employee.emp_name, Department.dept_name
FROM Employee
RIGHT JOIN Department ON Employee.dept_id = Department.dept_id;
```
*Result (3 rows):*

| emp_id | emp_name | dept_name |
| :---: | :--- | :--- |
| 1 | Alice | Sales |
| 2 | Bob | Engineering |
| `NULL` | `NULL` | Marketing |

**(iv) Full Outer Join:**  
Preserves all rows from both tables. Attributes missing on either side are padded with `NULL`. MySQL emulates this via `UNION`:
```sql
SELECT Employee.emp_id, Employee.emp_name, Department.dept_name
FROM Employee LEFT JOIN Department ON Employee.dept_id = Department.dept_id
UNION
SELECT Employee.emp_id, Employee.emp_name, Department.dept_name
FROM Employee RIGHT JOIN Department ON Employee.dept_id = Department.dept_id;
```
*Result (4 rows):*

| emp_id | emp_name | dept_name |
| :---: | :--- | :--- |
| 1 | Alice | Sales |
| 2 | Bob | Engineering |
| 3 | Charlie | `NULL` |
| `NULL` | `NULL` | Marketing |

**(v) Cross Join (Cartesian Product):**  
Pairs each of the 3 employee rows with each of the 3 department rows without any condition, producing $3 \times 3 = 9$ rows.
```sql
SELECT Employee.emp_name, Department.dept_name
FROM Employee CROSS JOIN Department;
```

### 🎯 GQ2 · 2023 Q.5(c) · Define Joining and Discuss Join Types

> **Appeared:** 2023 Q.5(c) — (04 Marks)

**Question:**

Define joining. Discuss different types of joining with suitable example.

**Full Answer:**

**1. Definition:**  
A join operation takes two relations as input and produces a new relation by pairing tuples that satisfy a join predicate. It prevents redundant physical storage by allowing relations to be linked dynamically during query execution.

**2. Sample Tables:**  
Let `Student` be `{(1, 'Rahim'), (2, 'Karim')}` and `Course` be `{(1, 'ECE 2215'), (3, 'ECE 2201')}` with common join attribute `ID`.

**3. Discussion of Types:**
- **Inner Join:** Returns matching rows only:

  $$
  \text{Student} \bowtie_{\text{Student.ID} = \text{Course.ID}} \text{Course}
  $$

  *Result:* `(1, 'Rahim', 'ECE 2215')`.
- **Left Outer Join:** Preserves all students. Pads non-enrolled students with `NULL`:

  $$
  \text{Student} \mathbin{⟕} \text{Course}
  $$

  *Result:* `(1, 'Rahim', 'ECE 2215')` and `(2, 'Karim', NULL)`.
- **Right Outer Join:** Preserves all courses. Pads courses without students with `NULL`:

  $$
  \text{Student} \mathbin{⟖} \text{Course}
  $$

  *Result:* `(1, 'Rahim', 'ECE 2215')` and `(NULL, NULL, 'ECE 2201')`.
- **Full Outer Join:** Preserves all tuples from both sides, padding missing attributes with `NULL`:

  $$
  \text{Student} \mathbin{⟗} \text{Course}
  $$

  *Result:* Contains all three rows above.
- **Natural Join:** Equates identical attribute names automatically and eliminates duplicate columns.

### 🎯 GQ3 · 2024 Q.3(c) · Inner Joining vs. Outer Joining

> **Appeared:** 2024 Q.3(c) — (02 Marks)

**Question:**

Differentiate between inner joining and outer joining.

**Full Answer:**

| Feature | Inner Joining | Outer Joining |
| :--- | :--- | :--- |
| **Tuple Preservation** | Retains only tuples that satisfy the join predicate in both relations. Non-matching tuples are omitted. | Preserves matching tuples plus non-matching tuples from one or both relations. |
| **Null Padding** | Never introduces `NULL` values to represent missing relational pairings. | Pads unmatched attributes with `NULL` to keep dangling records visible. |
| **Information Loss** | Suffers from information loss because unlinked records are dropped. | Prevents information loss by keeping dangling records from specified tables. |
| **Subtypes** | Theta join, equijoin, and natural inner join. | Left outer join, right outer join, and full outer join. |
| **Relational Algebra** | Denoted by $\bowtie$ or $\bowtie_\theta$. | Denoted by $\mathbin{⟕}$, $\mathbin{⟖}$, and $\mathbin{⟗}$. |

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 4.3 · Computing Outer Joins Without `OUTER JOIN` Syntax

> **Source:** Silberschatz 7e · Chapter 4 (Practice Exercise 4.3)  
> **Exam Relevance:** Prime Overdue SQL Formulation Drill  
> **Key Tested Concept:** Expressing Left, Right, and Full Outer Joins using basic inner joins, `UNION`, and `NOT IN` subqueries.

**Problem Statement:**
> Many early relational database management systems supported inner joins and `UNION` operations, but lacked native `LEFT OUTER JOIN`, `RIGHT OUTER JOIN`, or `FULL OUTER JOIN` syntax.
> Consider schemas $R(\underline{A}, B)$ and $S(\underline{A}, C)$.
> 1. Write an SQL query to compute the **Left Outer Join** ($R \mathbin{⟕} S$) strictly using inner joins, `UNION`, and `NOT IN` (or `NOT EXISTS`).
> 2. Write an SQL query to compute the **Full Outer Join** ($R \mathbin{⟗} S$) strictly without using `FULL OUTER JOIN` or `OUTER JOIN` keywords.

**Model Exam-Style Solution:**

1. **Left Outer Join ($R \mathbin{⟕} S$) Without Outer Join Syntax:**
   - A left outer join consists of two disjoint sets:
     1. Matching tuples from both tables (the standard inner join).
     2. Tuples in $R$ that have no matching tuple in $S$, padded with `NULL` for attributes of $S$.

```sql
-- Part 1: Matching tuples (Inner Join)
SELECT r.A, r.B, s.C
FROM R r
JOIN S s ON r.A = s.A

UNION ALL

-- Part 2: Non-matching tuples from R, padded with NULL
SELECT r.A, r.B, NULL AS C
FROM R r
WHERE r.A NOT IN (SELECT s.A FROM S s WHERE s.A IS NOT NULL);
```

2. **Full Outer Join ($R \mathbin{⟗} S$) Without Outer Join Syntax:**
   - A full outer join consists of three components:
     1. Matching tuples from $R$ and $S$ (Inner Join).
     2. Non-matching tuples from $R$, padded with `NULL` for $S$.
     3. Non-matching tuples from $S$, padded with `NULL` for $R$.

```sql
-- Part 1: Matching tuples (Inner Join)
SELECT r.A, r.B, s.C
FROM R r
JOIN S s ON r.A = s.A

UNION ALL

-- Part 2: Non-matching tuples from R (padded with NULL for S)
SELECT r.A, r.B, NULL AS C
FROM R r
WHERE r.A NOT IN (SELECT s.A FROM S s WHERE s.A IS NOT NULL)

UNION ALL

-- Part 3: Non-matching tuples from S (padded with NULL for R)
SELECT s.A, NULL AS B, s.C
FROM S s
WHERE s.A NOT IN (SELECT r.A FROM R r WHERE r.A IS NOT NULL);
```

*(Note: In MySQL, which natively lacks `FULL OUTER JOIN`, the standard workaround is `LEFT JOIN ... UNION ... RIGHT JOIN`).* $\blacksquare$

**💡 RUET Exam Takeaway:**
When using `NOT IN` with subqueries, **always add `WHERE col IS NOT NULL`** to avoid the SQL Three-Valued Logic NULL trap!

## ⚡ Exam Tips & Common Mistakes

1. **MySQL Has No `FULL OUTER JOIN` Syntax:** Never write `FULL OUTER JOIN` as valid MySQL code on RUET exam scripts without noting MySQL syntax limits. State clearly that MySQL requires `LEFT JOIN ... UNION ... RIGHT JOIN`.
2. **`ON` vs. `WHERE` in Outer Joins:** In an `INNER JOIN`, placing a condition in the `ON` clause versus the `WHERE` clause produces identical results. In a `LEFT OUTER JOIN`, placing a right-table predicate in the `WHERE` clause filters out the `NULL`-padded rows, converting the query into an accidental inner join. Always place join conditions inside the `ON` clause.
3. **The Natural Join Trap:** Natural join automatically equates every column sharing the same name in both relations. In university databases, if both `Student` and `Course` contain a column named `dept_name`, `NATURAL JOIN` requires both student department and course department to match. This erroneously omits students taking elective courses outside their department.
4. **Always Use Compact Tables for Theory Answers:** When asked to provide examples for join types, draw 2-row or 3-row tables. Large tables waste exam time and increase arithmetic errors.
