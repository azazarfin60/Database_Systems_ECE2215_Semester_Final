# T06.3: Outer-Join Relational Algebra

## Why This Topic Matters

Outer-join relational algebra gives you the exact mathematical formulas behind SQL's `LEFT JOIN`, `RIGHT JOIN`, and `FULL OUTER JOIN`. While past RUET finals have tested outer joins by asking for output tables (covered in `T06.2`), questions asking you to express outer joins using basic relational algebra operators ($\sigma, \Pi, \times, \cup, -$) or prove whether outer joins are associative are high-yield theoretical targets. Mastering these formulas connects your relational algebra toolkit (`T04`) directly to SQL joins (`T06`).

## 📝 Key Definitions

> **Relational Algebra Outer Join Operators:** "The relational algebra supports the left outer-join operation, denoted by $\mathbin{⟕}_\theta$, the right outer-join operation, denoted by $\mathbin{⟖}_\theta$, and the full outer-join operation, denoted by $\mathbin{⟗}_\theta$. It also supports the natural join operation, denoted by $\bowtie$, as well as the natural join versions of the left, right and full outer-join operations, denoted by $\mathbin{⟕}$, $\mathbin{⟖}$, and $\mathbin{⟗}$." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.1.3, Note 4.1 (p. 136)

> **Information Retention:** "An extension of the join operation that avoids loss of information. Computes the join and then adds tuples form one relation that does not match tuples in the other relation to the result of the join. Uses null values." — Lecture Deck 04, Slide 5 *(Course definition)*

> **Null-Rejecting Predicate:** "A predicate $\theta_1$ satisfying the above property is said to be null rejecting on $E_2$. For example, if $\theta_1$ is of the form $A < 4$ where $A$ is an attribute from $E_2$, then $\theta_1$ would evaluate to unknown whenever $A$ is null, and as a result any tuples in $E_1 \mathbin{⟕}_\theta E_2$ that are not in $E_1 \bowtie_\theta E_2$ would be rejected by $\sigma_{\theta_1}$." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §16.2 (p. 751)

## Defining Outer Joins Using Basic Relational Algebra

### Intuitive Idea: Why Do We Need Projection and Cartesian Product?
Basic relational algebra only gives us six core operators: selection ($\sigma$), projection ($\Pi$), Cartesian product ($\times$), set union ($\cup$), set difference ($-$), and rename ($\rho$). Outer joins ($\mathbin{⟕}$, $\mathbin{⟖}$, $\mathbin{⟗}$) are "extended" shortcuts built out of those basic pieces.

To build a Left Outer Join $r(R) \mathbin{⟕} s(S)$ from basic operators, think about what rows belong in the final table:
1. First, we want all the **matching rows**, which is just the normal natural join: $r \bowtie s$.
2. Second, we want the **unmatched (dangling) rows from $r$**. How do we find which rows of $r$ did *not* match? We take all of $r$ and subtract the rows of $r$ that *did* match! Wait: we cannot just write $r - (r \bowtie s)$, because $r \bowtie s$ has extra columns from $s$, and set difference ($-$) requires both tables to have the exact same columns. So we first trim $r \bowtie s$ down to just $r$'s columns using projection ($\Pi_R(r \bowtie s)$), and then subtract: $r - \Pi_R(r \bowtie s)$.
3. Finally, before we can union ($\cup$) those unmatched rows of $r$ with $r \bowtie s$, both sides must have the exact same column width! Since the unmatched rows of $r$ are missing the columns that belong only to $s$ (the columns in $S - R$), we glue a tuple of `null` values onto the end of each unmatched row using a Cartesian product: $\times \{(\text{null}, \text{null}, \dots, \text{null})\}$.

Let relation $r(R)$ and relation $s(S)$ have schemas $R$ and $S$. Now the formal equations read just like plain English:

### 1. Natural Left Outer Join ($\mathbin{⟕}$)

A natural left outer join takes the natural join $r \bowtie s$ and unions it with the `null`-padded dangling tuples of $r$:

$$
r \mathbin{⟕} s = (r \bowtie s) \cup \left( \left( r - \Pi_R(r \bowtie s) \right) \times \{(\text{null}, \text{null}, \dots, \text{null})\} \right)
$$

Here, each part of the formula has a clear job:
1. $(r \bowtie s)$: The matched rows from both tables.
2. $(r - \Pi_R(r \bowtie s))$: The dangling rows of $r$ that had no match in $s$.
3. $\times \{(\text{null}, \dots, \text{null})\}$: Pads each dangling row of $r$ with `null` values for every column in $S - R$.

### 2. Natural Right Outer Join ($\mathbin{⟖}$)

A natural right outer join works the exact same way in reverse, keeping all rows of $s$ and padding its dangling rows with `null` values on the left across all columns in $R - S$:

$$
r \mathbin{⟖} s = (r \bowtie s) \cup \left( \{(\text{null}, \text{null}, \dots, \text{null})\} \times \left( s - \Pi_S(r \bowtie s) \right) \right)
$$

### 3. Natural Full Outer Join ($\mathbin{⟗}$)

A natural full outer join is simply the union of the left outer join and the right outer join, so it keeps all matched rows plus the `null`-padded dangling rows from both sides:

$$
r \mathbin{⟗} s = (r \mathbin{⟕} s) \cup (r \mathbin{⟖} s)
$$

Writing this out completely in terms of basic operators gives:

$$
r \mathbin{⟗} s = (r \bowtie s) \cup \left( \left(r - \Pi_R(r \bowtie s)\right) \times \{\text{null}\} \right) \cup \left( \{\text{null}\} \times \left(s - \Pi_S(r \bowtie s)\right) \right)
$$

### 4. Conditional (Theta) Outer Joins

When two tables are joined using a custom condition $\theta$ (like $r.A = s.D$) instead of matching column names automatically, simply replace the natural join $\bowtie$ with the theta join $\bowtie_\theta$:

$$
r \mathbin{⟕}_\theta s = (r \bowtie_\theta s) \cup \left( \left( r - \Pi_R(r \bowtie_\theta s) \right) \times \{(\text{null}, \dots, \text{null})\} \right)
$$

$$
r \mathbin{⟖}_\theta s = (r \bowtie_\theta s) \cup \left( \{(\text{null}, \dots, \text{null})\} \times \left( s - \Pi_S(r \bowtie_\theta s) \right) \right)
$$

## Algebraic Properties & Equivalence Rules

Database query optimizers use algebraic equivalence rules to rewrite slow queries into faster ones without changing the final answer. Silberschatz 7e (§16.2) highlights four rules you need to know for outer joins:

### 1. Commutativity (Does Order Matter?)

- **Full Outer Join is commutative** (up to column order), because both sides are preserved either way:
  $$
  E_1 \mathbin{⟗} E_2 \equiv E_2 \mathbin{⟗} E_1
  $$
- **Left and Right Outer Joins are NOT commutative:**
  $$
  E_1 \mathbin{⟕} E_2 \not\equiv E_2 \mathbin{⟕} E_1
  $$
  Why? Because $E_1 \mathbin{⟕} E_2$ keeps unmatched rows from $E_1$, whereas $E_2 \mathbin{⟕} E_1$ keeps unmatched rows from $E_2$. However, if you swap the tables **and** flip the join symbol from left to right, they are equivalent:
  $$
  E_1 \mathbin{⟕} E_2 \equiv E_2 \mathbin{⟖} E_1
  $$

### 2. Associativity (The Non-Associativity Trap)

Normal inner joins and Cartesian products are associative, meaning you can move parentheses freely:
$$
(A \bowtie B) \bowtie C \equiv A \bowtie (B \bowtie C)
$$

In contrast, **outer joins are NOT associative**:
$$
(A \mathbin{⟕} B) \mathbin{⟕} C \not\equiv A \mathbin{⟕} (B \mathbin{⟕} C)
$$

Why does moving the parentheses change the answer? Because evaluating $(B \mathbin{⟕} C)$ first can introduce `null` values into attributes shared with $A$, and since `1 = null` evaluates to `unknown` (not true), rows that matched in $(A \mathbin{⟕} B) \mathbin{⟕} C$ can fail to match in $A \mathbin{⟕} (B \mathbin{⟕} C)$! (See `LQ2` below for the classic 1-row counterexample proof.)

### 3. Pushing Selection ($\sigma$) Inside Outer Joins

Can we push a filter $\sigma_{\theta_1}$ inside an outer join to shrink the tables early? Only if the filter checks columns from the **preserved** side:
- If condition $\theta_1$ only checks attributes of the left table $E_1$, we can safely push $\sigma_{\theta_1}$ inside a left outer join:
  $$
  \sigma_{\theta_1}(E_1 \mathbin{⟕}_\theta E_2) \equiv (\sigma_{\theta_1}(E_1)) \mathbin{⟕}_\theta E_2
  $$
- Similarly, for a right outer join where $\theta_1$ only checks attributes of $E_1$:
  $$
  \sigma_{\theta_1}(E_2 \mathbin{⟖}_\theta E_1) \equiv E_2 \mathbin{⟖}_\theta (\sigma_{\theta_1}(E_1))
  $$

If $\theta_1$ checks attributes from the unpreserved side ($E_2$), pushing it inside the join before `null` padding happens can change the output!

### 4. Converting an Outer Join into an Inner Join (Null-Rejecting Predicates)

What happens if you run a `LEFT JOIN` (which carefully pads unmatched rows of $E_2$ with `null`), and then immediately apply a `WHERE` filter $\sigma_{\theta_1}$ that requires a column of $E_2$ to equal a real value like `B > 50` or `B = 'Sales'`?

Because comparing `null` with anything (`null > 50` or `null = 'Sales'`) evaluates to `unknown`, that filter throws away every single `null`-padded row that the outer join created! A condition $\theta_1$ with this property is called **null-rejecting** on $E_2$.

**Optimization Rule:** Whenever a selection condition $\theta_1$ is null-rejecting on $E_2$, the outer join is doing extra work for nothing, so the query optimizer rewrites the outer join into a much faster inner join:

$$
\sigma_{\theta_1}(E_1 \mathbin{⟕}_\theta E_2) \equiv \sigma_{\theta_1}(E_1 \bowtie_\theta E_2)
$$

This rewrite is super useful in practice because inner joins let the database engine reorder tables freely and use fast index lookups.

## Worked Example: Tracing a Full Outer Join ($r \mathbin{⟗} s$) Using Basic Operators

Let's evaluate the full outer join $r \mathbin{⟗} s$ step by step using the basic relational algebra formula on two tiny 2-row tables $r(A, B)$ and $s(B, C)$:

**Relation $r(A, B)$:**

| A | B |
| :---: | :---: |
| 10 | 5 |
| 20 | 8 |

**Relation $s(B, C)$:**

| B | C |
| :---: | :---: |
| 5 | P |
| 9 | Q |

### Step 1: Compute the Natural Inner Join $(r \bowtie s)$
Match rows on the shared column $B$:
- $(10, 5)$ in $r$ matches $(5, P)$ in $s$ on $B = 5$.
- $(20, 8)$ in $r$ and $(9, Q)$ in $s$ have no match.

$$
r \bowtie s = \{(10, 5, P)\}
$$

### Step 2: Find and Pad the Left Dangling Tuples of $r$
Project the matched row onto $R(A, B)$ and subtract from $r$:
$$
r - \Pi_R(r \bowtie s) = \{(10, 5), (20, 8)\} - \{(10, 5)\} = \{(20, 8)\}
$$
Pad on the right with `null` for attribute $C \in S - R$:
$$
\{(20, 8)\} \times \{(\text{null})\} = \{(20, 8, \text{null})\}
$$

### Step 3: Find and Pad the Right Dangling Tuples of $s$
Project the matched row onto $S(B, C)$ and subtract from $s$:
$$
s - \Pi_S(r \bowtie s) = \{(5, P), (9, Q)\} - \{(5, P)\} = \{(9, Q)\}
$$
Pad on the left with `null` for attribute $A \in R - S$:
$$
\{(\text{null})\} \times \{(9, Q)\} = \{(\text{null}, 9, Q)\}
$$

### Step 4: Union All Three Sets Together
$$
r \mathbin{⟗} s = \{(10, 5, P)\} \cup \{(20, 8, \text{null})\} \cup \{(\text{null}, 9, Q)\}
$$

**Final Result Table ($r \mathbin{⟗} s$):**

| A | B | C |
| :---: | :---: | :---: |
| 10 | 5 | P |
| 20 | 8 | `null` |
| `null` | 9 | Q |

## 🔮 Likely Questions (High-Probability Exam Predictions)

### 🎯 LQ1 · Formal Definition of Outer Joins in Relational Algebra

> **Probability:** ⭐ Very High | **Estimated Marks:** 4–5 Marks

**Question:**

Define Left Outer Join ($\mathbin{⟕}$), Right Outer Join ($\mathbin{⟖}$), and Full Outer Join ($\mathbin{⟗}$) using the fundamental operators of relational algebra. Demonstrate the evaluation of Left Outer Join on a sample relational instance.

**Full Answer:**

**1. Algebraic Formulations:**  
Let $r(R)$ and $s(S)$ be two relations with schemas $R$ and $S$. Let $\bowtie$ denote natural join and let $\{(\text{null}, \dots, \text{null})\}$ denote a tuple of null values corresponding to missing attributes.

- **Natural Left Outer Join ($\mathbin{⟕}$):**  
  Preserves all tuples from $r$. Unmatched tuples of $r$ are padded with nulls:
  $$
  r \mathbin{⟕} s = (r \bowtie s) \cup \left( \left( r - \Pi_R(r \bowtie s) \right) \times \{(\text{null}, \dots, \text{null})\} \right)
  $$
- **Natural Right Outer Join ($\mathbin{⟖}$):**  
  Preserves all tuples from $s$. Unmatched tuples of $s$ are padded with nulls:
  $$
  r \mathbin{⟖} s = (r \bowtie s) \cup \left( \{(\text{null}, \dots, \text{null})\} \times \left( s - \Pi_S(r \bowtie s) \right) \right)
  $$
- **Natural Full Outer Join ($\mathbin{⟗}$):**  
  Preserves all tuples from both $r$ and $s$:
  $$
  r \mathbin{⟗} s = (r \mathbin{⟕} s) \cup (r \mathbin{⟖} s)
  $$
  Expanded into basic operators:
  $$
  r \mathbin{⟗} s = (r \bowtie s) \cup \left( (r - \Pi_R(r \bowtie s)) \times \{\text{null}\} \right) \cup \left( \{\text{null}\} \times (s - \Pi_S(r \bowtie s)) \right)
  $$

**2. Demonstration on Sample Instance:**  
Let $r(A, B) = \{(1, a), (2, b)\}$ and $s(B, C) = \{(a, 10), (c, 30)\}$.
- Step 1: Natural join $r \bowtie s = \{(1, a, 10)\}$.
- Step 2: Matched left projection $\Pi_R(r \bowtie s) = \{(1, a)\}$.
- Step 3: Unmatched left tuples $r - \Pi_R(r \bowtie s) = \{(2, b)\}$.
- Step 4: Pad with null for attribute $C$: $\{(2, b, \text{null})\}$.
- Step 5: Union gives $r \mathbin{⟕} s = \{(1, a, 10), (2, b, \text{null})\}$.

### 🎯 LQ2 · Commutativity and Associativity of Outer Joins

> **Probability:** ⭐ High | **Estimated Marks:** 3–4 Marks

**Question:**

Discuss the algebraic properties of outer joins regarding commutativity and associativity. Provide a counterexample to show whether Left Outer Join is associative.

**Full Answer:**

**1. Commutativity:**
- **Full Outer Join is commutative:**
  $$
  E_1 \mathbin{⟗} E_2 \equiv E_2 \mathbin{⟗} E_1
  $$
- **Left Outer Join is not commutative:**
  $$
  E_1 \mathbin{⟕} E_2 \not\equiv E_2 \mathbin{⟕} E_1
  $$
  In $E_1 \mathbin{⟕} E_2$, tuples from $E_1$ are preserved. In $E_2 \mathbin{⟕} E_1$, tuples from $E_2$ are preserved. However, left and right outer joins are symmetric:
  $$
  E_1 \mathbin{⟕} E_2 \equiv E_2 \mathbin{⟖} E_1
  $$

**2. Associativity and Counterexample:**  
Left outer join is **not associative**:
$$
(r \mathbin{⟕} s) \mathbin{⟕} t \not\equiv r \mathbin{⟕} (s \mathbin{⟕} t)
$$

*Proof by Counterexample (Silberschatz 7e, p. 751–752):*  
Let the relations and schemas be:
- $r(A, B) = \{(1, 1)\}$
- $s(B, C) = \{(1, 1)\}$
- $t(A, C) = \emptyset$ (empty relation with schema attributes $A$ and $C$)

*Evaluate Left-Hand Side: $(r \mathbin{⟕} s) \mathbin{⟕} t$*
1. **Compute $(r \mathbin{⟕} s)$:**  
   $r(1, 1)$ matches $s(1, 1)$ on common attribute $B=1$. The result has schema $(A, B, C)$ and contains tuple $(1, 1, 1)$.
2. **Compute $(r \mathbin{⟕} s) \mathbin{⟕} t$:**  
   Join $(1, 1, 1)$ with the empty relation $t(A, C)$. Because this is a left outer join, the left tuple is preserved and padded with nulls if needed. Since schema $(A, B, C)$ already covers all attributes, the tuple remains unchanged:
   $$
   (r \mathbin{⟕} s) \mathbin{⟕} t = \{(1, 1, 1)\}
   $$

*Evaluate Right-Hand Side: $r \mathbin{⟕} (s \mathbin{⟕} t)$*
1. **Compute $(s \mathbin{⟕} t)$:**  
   Relation $s(B, C)$ has tuple $(1, 1)$ with $B=1, C=1$. Relation $t(A, C)$ has no tuples. Preserving $s$ pads the missing attribute $A$ with `null`. The result has schema $(A, B, C)$ and contains tuple:
   $$
   s \mathbin{⟕} t = \{(\text{null}, 1, 1)\}
   $$
2. **Compute $r \mathbin{⟕} (s \mathbin{⟕} t)$:**  
   Now compute the natural left outer join of $r(A, B) = \{(1, 1)\}$ with $\{(\text{null}, 1, 1)\}$. The common attributes are $A$ and $B$.
   - In $r$: $A = 1$ and $B = 1$.
   - In $(s \mathbin{⟕} t)$: $A = \text{null}$ and $B = 1$.
   - The equality test on attribute $A$ evaluates $1 = \text{null}$, which is unknown (not true). Hence the tuples fail to match.
   - Because this is a left outer join, the left tuple from $r(1, 1)$ is preserved, and missing attribute $C$ is padded with `null`:
   $$
   r \mathbin{⟕} (s \mathbin{⟕} t) = \{(1, 1, \text{null})\}
   $$

*Conclusion:*  
$$
\{(1, 1, 1)\} \neq \{(1, 1, \text{null})\}
$$
Therefore, $(r \mathbin{⟕} s) \mathbin{⟕} t \not\equiv r \mathbin{⟕} (s \mathbin{⟕} t)$, proving that the left outer join operation is strictly non-associative.

### 🎯 LQ3 · Null-Rejecting Predicates and Outer Join Optimization

> **Probability:** ⭐ High | **Estimated Marks:** 3–4 Marks

**Question:**

Explain the concept of a "null-rejecting predicate" in query optimization. How can a query engine simplify an outer join into an inner join using this property?

**Full Answer:**

**1. Definition:**  
A predicate $\theta$ is **null-rejecting** with respect to a relation $E_2$ if $\theta$ evaluates to `false` or `unknown` whenever any attribute of $E_2$ involved in $\theta$ contains a `null` value.

**2. Mathematical Basis:**  
In SQL three-valued logic, comparison with `null` (e.g., `null > 50` or `null = 'ECE'`) evaluates to `unknown`. Selection filters in relational engines require conditions to evaluate to `true` to keep a row. Therefore, any tuple padded with nulls will be rejected.

**3. Equivalence Transformation:**  
When a query applies a null-rejecting selection predicate $\theta_1$ on the right relation $E_2$ after a left outer join:
$$
\sigma_{\theta_1}(E_1 \mathbin{⟕}_\theta E_2) \equiv \sigma_{\theta_1}(E_1 \bowtie_\theta E_2)
$$

**4. Example:**  
Consider the SQL query:
```sql
SELECT *
FROM Student
LEFT JOIN Department ON Student.Dept_ID = Department.Dept_ID
WHERE Department.Building = 'Taylor';
```
- The `LEFT JOIN` generates rows for students without departments, setting `Department.Building = NULL`.
- The `WHERE` clause tests `Department.Building = 'Taylor'`.
- For `NULL` building values, `'NULL' = 'Taylor'` evaluates to `unknown`, eliminating the row.
- Because all `NULL`-padded rows are rejected, the query optimizer converts the expensive `LEFT JOIN` into a fast `INNER JOIN`:
```sql
SELECT *
FROM Student
INNER JOIN Department ON Student.Dept_ID = Department.Dept_ID
WHERE Department.Building = 'Taylor';
```

### 🎯 HYE-01 · Practice Exercise 4.4 · Associativity of Full Outer Joins: Proof & Counterexample

> **Source:** Silberschatz 7e · Chapter 4 (Practice Exercise 4.4)  
> **Exam Relevance:** Prime Overdue Relational Algebra Proof Drill  
> **Key Tested Concept:** Demonstrating that natural full outer join is NOT associative in general ($R \mathbin{⟗} (S \mathbin{⟗} T) \neq (R \mathbin{⟗} S) \mathbin{⟗} T$).

**Problem Statement:**
> 1. State whether the **natural full outer join operator** ($\mathbin{⟗}$) is **associative**. That is, does the identity:
>    $$
>    (R \mathbin{⟗} S) \mathbin{⟗} T = R \mathbin{⟗} (S \mathbin{⟗} T)
>    $$
>    hold for all relations $R, S, T$?
> 2. Prove your assertion by providing a concrete relation instance counterexample.

**Model Exam-Style Solution:**

1. **Mathematical Assertion:**
   - **The natural full outer join is NOT associative in general.**
   - While regular natural inner join ($\bowtie$) is associative ($R \bowtie (S \bowtie T) = (R \bowtie S) \bowtie T$), full outer join can introduce null values that distort subsequent joins, causing the association order to matter.

2. **Concrete Counterexample (Silberschatz 7e, p. 751–752):**
   - Let relations and schemas be:
     - $R(A, B) = \{(1, 1)\}$
     - $S(B, C) = \{(1, 1)\}$
     - $T(A, C) = \emptyset$ (empty relation with schema attributes $A$ and $C$)

   - **Evaluation of Left Association: $((R \mathbin{⟗} S) \mathbin{⟗} T)$:**
     - Step 1: Compute $R(A, B) \mathbin{⟗} S(B, C)$.
       - $R(1, 1)$ matches $S(1, 1)$ on common attribute $B=1$. The result has schema $(A, B, C)$ and contains tuple $(1, 1, 1)$:
         $$
         R \mathbin{⟗} S = \{(1, 1, 1)\}
         $$
     - Step 2: Join with $T(A, C) = \emptyset$:
       - Schema of $(R \mathbin{⟗} S)$ is $(A, B, C)$; schema of $T$ is $(A, C)$.
       - Because $T$ has no tuples, the left tuple $(1, 1, 1)$ has no match in $T$. Under full outer join, unmatched tuples are preserved:
         $$
         ((R \mathbin{⟗} S) \mathbin{⟗} T) = \mathbf{\{(1, 1, 1)\}} \quad (1\text{ tuple})
         $$

   - **Evaluation of Right Association: $(R \mathbin{⟗} (S \mathbin{⟗} T))$:**
     - Step 1: Compute $S(B, C) \mathbin{⟗} T(A, C)$.
       - $S$ has $(1, 1)$ with $B=1, C=1$. $T$ is empty on $(A, C)$.
       - In full outer join, $S$ is preserved and padded with $\text{null}$ for missing attribute $A$:
         $$
         S \mathbin{⟗} T = \{(\text{null}, 1, 1)\} \quad \text{on schema } (A, B, C)
         $$
     - Step 2: Join $R(A, B) = \{(1, 1)\}$ with $(S \mathbin{⟗} T) = \{(\text{null}, 1, 1)\}$:
       - The common attributes between $R$ and $(S \mathbin{⟗} T)$ are $A$ and $B$.
       - In $R$: $A = 1$ and $B = 1$.
       - In $(S \mathbin{⟗} T)$: $A = \text{null}$ and $B = 1$.
       - The natural join equality test on attribute $A$ evaluates $1 = \text{null}$, which is `unknown` (fails match condition).
       - Because this is a full outer join, **both** non-matching tuples are preserved and padded with nulls:
         - $R(1, 1)$ is padded with $\text{null}$ for $C \implies (1, 1, \text{null})$
         - $(\text{null}, 1, 1)$ already spans schema $(A, B, C) \implies (\text{null}, 1, 1)$
       - Therefore:
         $$
         R \mathbin{⟗} (S \mathbin{⟗} T) = \mathbf{\{(1, 1, \text{null}), (\text{null}, 1, 1)\}} \quad (2\text{ tuples})
         $$

3. **Conclusion:**
   $$
   \{(1, 1, 1)\} \neq \{(1, 1, \text{null}), (\text{null}, 1, 1)\}
   $$
   Because outer joins generate null-padded attributes that alter the common attribute set and equality evaluations of subsequent joins, **full outer join is strictly non-associative** ($((R \mathbin{⟗} S) \mathbin{⟗} T \neq R \mathbin{⟗} (S \mathbin{⟗} T)$). Database query optimizers cannot freely reorder outer joins as they do with inner joins. $\blacksquare$

**💡 RUET Exam Takeaway:**
Query optimizers can reorder inner joins freely because $\bowtie$ is commutative and associative. They **CANNOT** reorder outer joins because $\mathbin{⟗}$ is not associative!

## ⚡ Exam Tips & Common Mistakes

1. **Projection is Mandatory in Set Difference:** When expressing outer join using basic relational algebra, you cannot write $r - (r \bowtie s)$. The degree of $(r \bowtie s)$ is larger than $r$, so set difference is undefined. You must project first:
   $$
   r - \Pi_R(r \bowtie s)
   $$
2. **Outer Joins Are Not Associative:** Never rearrange parentheses across outer joins during algebraic derivations. $(A \mathbin{⟕} B) \mathbin{⟕} C$ does not equal $A \mathbin{⟕} (B \mathbin{⟕} C)$.
3. **Symbols Matter:**
   - Left Outer Join: $\mathbin{⟕}$
   - Right Outer Join: $\mathbin{⟖}$
   - Full Outer Join: $\mathbin{⟗}$
   - Natural Inner Join: $\bowtie$
4. **Recognize Null-Rejection in SQL Questions:** If a question asks why an outer join query behaves like an inner join, look for a condition in the `WHERE` clause that tests an attribute from the optional table.
