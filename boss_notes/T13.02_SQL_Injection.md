# T13.2: SQL Injection — Mechanism and Prevention

> **Topic:** T13 — Security, Indexing & Hashing | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (+ 0 CTs) (9 marks)
> **Sources:** Silberschatz 7e Ch. 9 (§9.8.1), Ch. 5 (§5.1.1.5)

## Why This Topic Matters

SQL injection is one of the most prominent web application security threats tested in semester finals. It appeared in 2020 Q.4(a) for 4 marks and in 2021 Q.8(b) for 5 marks (totaling 9 marks). The examiner consistently asks three things: the exact definition of an SQL injection attack, a concrete code example illustrating how the attack operates, and the technical precautions required to neutralize it. Mastering parameterized queries in JDBC and Python guarantees full marks.

---

## 📝 Key Definitions

> **SQL Injection:** "In SQL injection attacks, the attacker manages to get an application to execute an SQL query created by the attacker." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §9.8.1 (p. 438)

> **Prepared Statement:** "We can create a prepared statement in which some values are replaced by '?', thereby specifying that actual values will be provided later. The database system compiles the query when it is prepared. Each time the query is executed (with new values to replace the '?'s), the database system can reuse the previously compiled form of the query and apply the new values as parameters." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §5.1.1.5 (p. 188)

---

## The Root Cause of SQL Injection

SQL injection happens when an application mixes untrusted user input directly into an SQL command by gluing strings together (string concatenation).

### Intuitive Analogy: Mixing Up Instructions and Data

Imagine filling out a paper withdrawal slip at a bank where the blank space asks for your account name. If a normal customer writes `Alice`, the teller reads the instruction: *"Transfer \$100 from account `'Alice'`."* Now imagine an attacker writes: `Alice' OR '1'='1`. Because the bank clerk blindly copies whatever is written on the slip into the master instruction sheet, the sentence becomes: *"Transfer \$100 from account `'Alice'` OR whenever `'1'='1'`."* Since `1=1` is always true, the clerk empties every account in the bank!

In a safe system, **code** (the SQL query structure) and **data** (what the user typed) are kept completely separate. However, when a program builds SQL queries by pasting strings together like this:

```python
  # Insecure dynamic SQL construction
query = "SELECT * FROM users WHERE username = '" + user_input + "'"
```

The database SQL parser receives a **single combined string**. Because everything arrives mashed together, the parser has no way to tell where the developer's SQL commands end and where the user's input begins. If the user types special SQL characters like `'`, `"`, `;`, or `--`, those characters break out of the data quote and rewrite the query's parse tree (Abstract Syntax Tree, or AST). As a result, the database runs commands the developer never intended.

---

## Classic Attack Scenarios: How It Works

To see how attackers exploit string concatenation in practice, let's walk through four common attack patterns.

### Scenario 1: Authentication Bypass via Tautology (`OR '1'='1'`)

Suppose an online banking portal looks up a customer's account using string concatenation:

```sql
SELECT * FROM accounts WHERE owner = '<user_input>';
```

- **Attacker Input:** `' OR '1'='1`
- **Resulting SQL Query:**
  ```sql
  SELECT * FROM accounts WHERE owner = '' OR '1'='1';
  ```
- **Why It Works Step-by-Step:**
  1. The first single quote `'` closes the opening quote of `owner = '` early.
  2. The injected `OR '1'='1'` adds a new boolean condition to the `WHERE` clause.
  3. Because `'1'='1'` is a tautology (it is always `TRUE` for every row), the entire `WHERE` condition becomes `TRUE` for every row in the table.
  4. Instead of returning one customer's row, the database dumps every account in the `accounts` table!

### Scenario 2: Stacked Queries (Running a Second Destructive Command)

If the database driver allows multiple semicolon-separated statements in a single call, an attacker can finish the first query early and start a brand-new command:

```sql
SELECT * FROM orders WHERE order_id = '<user_input>';
```

- **Attacker Input:** `'; DROP TABLE orders; -- `
- **Resulting SQL Query:**
  ```sql
  SELECT * FROM orders WHERE order_id = ''; DROP TABLE orders; -- ';
  ```
- **Why It Works Step-by-Step:**
  1. The leading single quote `'` closes the `order_id` string literal.
  2. The semicolon `;` marks the end of the `SELECT` statement.
  3. The database then runs the attacker's second statement, `DROP TABLE orders`, which deletes the entire `orders` table.
  4. Finally, the double hyphen `-- ` turns the leftover `' ` at the end of the developer's original query into a harmless SQL comment so the parser does not throw a syntax error.

### Scenario 3: Sorting and Column Name Injection

SQL injection can also happen outside the `WHERE` clause whenever user input controls column names, table names, or sort order:

```java
// Dynamically appending an order attribute
String query = "SELECT * FROM takes ORDER BY " + orderAttribute;
```

- **Attacker Input:** `year; DELETE FROM takes; --`
- **Impact:** Standard `?` placeholders cannot be used for column names or `ASC`/`DESC` keywords. If the developer does not check `orderAttribute` against a strict allowlist of valid column names, an attacker can piggyback destructive commands right after the `ORDER BY` clause.

### Scenario 4: Stealing Data from Other Tables with `UNION`

An attacker can use the `UNION` operator to tack results from a secret table onto the output of an ordinary search page:

```sql
SELECT item_name, price FROM products WHERE category = '<user_input>';
```

- **Attacker Input:** `' UNION SELECT username, password FROM admin_users -- `
- **Resulting SQL Query:**
  ```sql
  SELECT item_name, price FROM products WHERE category = '' 
  UNION 
  SELECT username, password FROM admin_users -- ';
  ```
- **Mechanism:** Because both `SELECT` queries return two columns, the database merges the admin usernames and passwords into the product list and prints them right on the web page.

## Technical Precautions and Prevention Techniques

Stopping SQL injection requires separating user data from SQL commands and limiting what the database account is allowed to do.

### 1. Primary Defense: Prepared Statements (Parameterized Queries)

**Prepared statements** (also called **parameterized queries**) are the gold-standard defense against SQL injection.

#### Why Prepared Statements Work

Instead of sending one combined string to the database, a prepared statement splits query execution into two strict steps:

1. **Step 1 (Compile the Query Skeleton):** The application sends the SQL query template with question mark placeholders (`?`) to the database *before* touching any user input. The database parses, compiles, and locks in the query's execution plan (AST).
2. **Step 2 (Fill in the Parameter Boxes):** Next, the application sends the user's input separately to fill in the `?` placeholders.
3. **Why It Cannot Be Exploited:** Because the query tree is already compiled and locked, the database treats whatever arrives in a `?` slot strictly as a **literal data value**, never as executable SQL commands. Even if the user types `' OR '1'='1`, the database simply looks for someone whose literal name is the 10-character string `' OR '1'='1`.

```text
Untrusted Input: ' OR '1'='1
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ Precompiled Query Plan:                                │
│   SELECT * FROM instructor WHERE name = [Parameter 1]  │
└────────────────────────────────────────────────────────┘
       │
       ▼
Execution Engine looks for an instructor whose literal name
is the exact 10-character string: "' OR '1'='1"
       │
       ▼
No match found → Returns 0 rows safely!
```

#### Code Implementation: Java JDBC

```java
// SECURE: Using PreparedStatement with parameterized values
String query = "SELECT * FROM instructor WHERE name = ?";
PreparedStatement pstmt = conn.prepareStatement(query);

// Bind the untrusted user input as a string literal
pstmt.setString(1, user_input);

// Execute the safe query
ResultSet rs = pstmt.executeQuery();
```

#### Code Implementation: Python DB-API

```python
  # SECURE: Database driver binds parameters separately
query = "SELECT * FROM instructor WHERE name = %s"
cursor.execute(query, (user_input,))
records = cursor.fetchall()
```

### 2. Secondary Defense: Input Validation and Allowlisting

Applications should also check that incoming inputs match the expected type, length, and format before running a query:

- **Strict Type Conversion:** If an input is supposed to be a numeric ID, convert it to an integer first (for example, `int(user_id)`). If an attacker submits `' OR 1=1`, the conversion fails immediately before the database is ever contacted.
- **Allowlisting Dynamic Identifiers:** Because `?` placeholders only work for data values (not table names, column names, or `ASC`/`DESC`), check any dynamic column or sort keyword against a hardcoded allowlist:

```java
// SECURE: Allowlisting dynamic column names
Set<String> allowedColumns = Set.of("ID", "name", "dept_name", "salary");
if (!allowedColumns.contains(orderAttribute)) {
    throw new IllegalArgumentException("Invalid sort attribute");
}
String query = "SELECT * FROM instructor ORDER BY " + orderAttribute;
```

### 3. Principle of Least Privilege

Even if a bug slips into the code, the web application's database account should only have the bare minimum permissions needed for its job:

- Grant only `SELECT`, `INSERT`, and `UPDATE` on the specific tables the app uses.
- Never connect a web app to the database as `root`, `sa`, or `DBA`.
- Keep DDL commands like `DROP TABLE`, `ALTER TABLE`, and `GRANT` revoked from the application account so an attacker can never wipe out tables.

### 4. Parameterized Stored Procedures

You can also wrap queries inside stored procedures that take typed parameters:

```sql
DELIMITER //
CREATE PROCEDURE GetInstructorByName(IN p_name VARCHAR(50))
BEGIN
    SELECT * FROM instructor WHERE name = p_name;
END //
DELIMITER ;
```

Because `p_name` is bound as a typed `VARCHAR` variable rather than glued into a command string, it behaves safely just like a prepared statement (as long as the procedure does not build dynamic strings inside itself with `EXECUTE IMMEDIATE`).

### 5. Hide Detailed Database Error Messages

Attackers often deliberately send broken quotes just to read the database's error message and learn table and column names. Always log detailed SQL errors privately on the server and show a polite, generic error message to the user.

## Worked Example: Comment-Out Login Bypass (`admin' -- `)

While `OR '1'='1'` bypasses a login check by making the `WHERE` clause true for every row, attackers can also log into a *specific* user's account (such as `admin`) by commenting out the password check!

Suppose a student portal checks logins using this vulnerable PHP snippet:

```php
// VULNERABLE CODE
$user = $_POST['username'];
$pass = $_POST['password'];
$sql = "SELECT * FROM students WHERE username = '$user' AND password = '$pass'";
$result = $db->query($sql);
if ($result->num_rows > 0) {
    // Log user in
}
```

### How the Attack Plays Out

1. The attacker types `admin' -- ` into the username box and types anything (or nothing) into the password box.
2. When PHP pastes `$user` into `$sql`, the query string becomes:
   ```sql
   SELECT * FROM students WHERE username = 'admin' -- ' AND password = ''
   ```
3. Notice what `-- ` does: in SQL, a double hyphen starts a single-line comment. Everything after `-- ` (including `AND password = ''`) is completely ignored by the parser!
4. That means the database actually runs:
   ```sql
   SELECT * FROM students WHERE username = 'admin'
   ```
5. As long as an `'admin'` user exists in the `students` table, the query returns 1 row, and the attacker logs straight into the admin account without knowing the password.

### Fixing the Code with a Prepared Statement

Replacing string concatenation with a prepared statement stops the attack cold:

```php
// SECURE CODE
$stmt = $db->prepare("SELECT * FROM students WHERE username = ? AND password = ?");
$stmt->bind_param("ss", $user, $pass);
$stmt->execute();
$result = $stmt->get_result();
```

Now when the attacker submits `admin' -- `, the query structure (`WHERE username = ? AND password = ?`) is already compiled and locked. The database searches for a student whose literal username is `"admin' -- "` and whose password matches `$pass`. Because no student has that username, the query returns 0 rows and blocks the login.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.4(a) · SQL Injection Attack, Mechanism, and Precautions

> **Appeared:** 2020 Q.4(a) — (04 marks)

**Question:**

What is an SQL injection attack? Explain how it works and what precautions must be taken to prevent SQL injection attack.

**Full Answer:**

**1. Definition of SQL Injection Attack:**  
An **SQL injection attack** occurs when an attacker inputs malicious SQL syntax into an unsanitized application input field. The application concatenates this input directly into a dynamic SQL query string. The database parser interprets the attacker's input as executable SQL commands rather than data, allowing unauthorized data access, authentication bypass, or data destruction.

**2. How It Works:**  
Consider a web application that constructs a dynamic query using string concatenation:

```sql
SELECT * FROM instructor WHERE name = '<user_input>';
```

If an attacker enters the string `' OR '1'='1`, the resulting query constructed by the application becomes:

```sql
SELECT * FROM instructor WHERE name = '' OR '1'='1';
```

- **Mechanism:** The single quote terminates the string literal for the `name` attribute. The `OR '1'='1'` condition is a tautology that always evaluates to `TRUE`.
- **Result:** The `WHERE` clause evaluates to `TRUE` for every row in the relation. The database returns all records in the `instructor` table, exposing sensitive data.

Alternatively, if the database permits stacked queries, an attacker can input:

```text
'; DROP TABLE student; -- 
```

The semicolon terminates the initial query and immediately executes the destructive `DROP TABLE` command, while `-- ` comments out the remaining closing quotation marks.

**3. Precautions to Prevent SQL Injection:**

1. **Use Prepared Statements (Parameterized Queries):**  
   This is the primary defense. The application precompiles the query structure using placeholders (`?`). Parameter values are bound separately out-of-band:
   ```java
   PreparedStatement stmt = conn.prepareStatement("SELECT * FROM instructor WHERE name = ?");
   stmt.setString(1, user_input);
   ResultSet rs = stmt.executeQuery();
   ```
   The database never treats the contents of the parameter as executable SQL grammar.

2. **Input Validation and Whitelisting:**  
   Validate all input data types and lengths. For dynamic identifiers (like table or column names in `ORDER BY` clauses) that cannot be parameterized, check values against an explicit whitelist of permitted names.

3. **Enforce Principle of Least Privilege:**  
   Configure database connection accounts with minimal necessary permissions. Application accounts should only have `SELECT`, `INSERT`, or `UPDATE` privileges, and must never hold administrative permissions such as `DROP TABLE` or `GRANT`.

### 🎯 GQ2 · 2021 Q.8(b) · SQL Injection Attack and Prevention Precautions

> **Appeared:** 2021 Q.8(b) — (05 marks)

**Question:**

What is SQL injection attack? Describe the precautions that should be taken to prevent this attack.

**Full Answer:**

**1. What is an SQL Injection Attack?**  
An **SQL injection attack** is a code injection technique where malicious SQL statements are inserted into entry fields of a data-driven application. It exploits a design flaw where application code concatenates user-supplied strings directly into dynamic SQL queries without sufficient validation or escaping. As a result, the database query parser cannot distinguish between application control code and user data, allowing the attacker to execute arbitrary SQL commands on the database.

**2. Precautions to Prevent SQL Injection Attacks:**

1. **Adopt Prepared Statements with Parameterized Queries (Primary Defense):**
   - The query structure is compiled and optimized by the DBMS before receiving runtime parameters.
   - When parameter values are passed, the database handles them strictly as typed data literals within existing parse tree nodes.
   - Even if the parameter string contains quotation marks, semicolons, or SQL keywords, they are evaluated purely as literal text characters and cannot alter the query structure.

2. **Implement Input Validation and Whitelisting:**
   - Enforce strict typing (e.g., rejecting non-numeric input for numeric ID fields).
   - Use regular expressions to enforce valid patterns for names, emails, and postal codes.
   - When dynamic query parts cannot use placeholders (such as table names or `ASC`/`DESC` keywords), validate the user input against a hardcoded whitelist of approved tokens.

3. **Enforce Least Privilege for Database Users:**
   - Configure application connection strings to connect with low-privileged database roles.
   - Deny access to administrative commands (`DROP`, `ALTER`, `GRANT`, `SHUTDOWN`).
   - If an injection flaw exists in an isolated query, least privilege limits the attacker's ability to destroy tables or access other schemas.

4. **Use Parameterized Stored Procedures:**
   - Restrict application accounts to invoking predefined stored procedures rather than executing ad-hoc SQL strings.
   - Ensure the stored procedures themselves use typed parameters rather than dynamic concatenation.

5. **Suppress Verbose Database Errors:**
   - Disable raw database error logging to client browsers.
   - Returning internal SQL error strings, database types, or table structures helps attackers craft targeted injection exploits. Return generic error messages instead.

### 🎯 HYE-01 · Practice Exercise 9.8 · SQL Injection Prevention via Parameterized Prepared Statements

> **Source:** Silberschatz 7e · Chapter 9 (Practice Exercise 9.8)  
> **Exam Relevance:** High-Probability Exam Security Question  
> **Key Tested Concept:** Why dynamic string concatenation creates injectable syntax trees, and how PreparedStatement parameterization prevents injection.

**Problem Statement:**
> 1. Demonstrate how a malicious user input creates an **Abstract Syntax Tree (AST) injection** in a dynamically concatenated SQL query.
> 2. Write the corrected code using **Java JDBC `PreparedStatement`** (or Python parameterized DB-API).
> 3. Explain technically why prepared statements are 100% immune to SQL injection, even if the input string contains SQL syntax keywords like `' OR '1'='1` or `; DROP TABLE`.

**Model Exam-Style Solution:**

1. **The Vulnerable Dynamic String Concatenation:**
```java
// VULNERABLE CODE:
String sql = "SELECT * FROM users WHERE username = '" + userInputUser + "' AND password = '" + userInputPass + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```
   - When an attacker inputs:
     - `userInputUser = admin' --`
   - The resulting string sent to the DBMS parser is:
     ```sql
     SELECT * FROM users WHERE username = 'admin' --' AND password = '...'
     ```
   - **Syntax Tree Mutation:** The database parser parses the input string as SQL grammar. The single quote `'` closes the string literal early, and `--` turns the remainder of the query into a comment. The syntax tree itself is altered, bypassing authentication!

2. **The Secure Parameterized Implementation (`PreparedStatement`):**
```java
// SECURE CODE:
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement pstmt = connection.prepareStatement(sql);
pstmt.setString(1, userInputUser);
pstmt.setString(2, userInputPass);
ResultSet rs = pstmt.executeQuery();
```

3. **Why Prepared Statements are 100% Immune:**
   - **Two-Phase Compilation Architecture:**
     1. **Phase 1: Pre-compilation (Parsing & Syntax Tree Creation):** The SQL statement template with placeholders `?` is sent to the database engine first:
        $$
        \text{AST constructed: } \text{Query} \rightarrow \text{Filter(username = [Param 1] } \land \text{ password = [Param 2])}
        $$
        The Abstract Syntax Tree is compiled and fixed **before any user input is ever touched**.
     2. **Phase 2: Literal Parameter Binding:** When `pstmt.setString(1, "admin' --")` is executed, the DBMS treats the input strictly as a **raw literal data value**, never as executable code.
   - Even if the input contains quotes, semicolons, or comments, the DBMS does not re-parse the syntax tree. It simply searches for a user whose literal username literally contains the characters `a-d-m-i-n-'- -`.
   - The syntactic structure of the query cannot be altered under any circumstances. $\blacksquare$

**💡 RUET Exam Takeaway:**
Always explain that **Prepared Statements pre-compile the SQL syntax tree BEFORE binding parameters**. Data and code are fundamentally segregated.

## ⚡ Exam Tips & Common Mistakes

1. **Always Provide a Concrete Query Example:** Never just write a theoretical definition. Show the original query, the attacker's malicious input string, and the resulting modified SQL statement. Showing `' OR '1'='1` or `'; DROP TABLE ...; --` guarantees full marks.
2. **Explain Why Prepared Statements Work:** Examiners look for the explanation that query compilation occurs *before* parameters are bound, ensuring user input is treated as raw data literals rather than executable syntax.
3. **Client-Side Validation is Not a Defense:** Mention that browser-based validation (HTML5 `required` or JavaScript form checks) can be completely bypassed using command-line HTTP clients like `curl` or Postman. Server-side parameterized queries are mandatory.
4. **Distinguish SQL Injection from XSS:** SQL injection targets the backend database parser. Cross-Site Scripting (XSS) targets the victim's client-side web browser.
