# T13.1: Database Security Threats and Authorization

> **Topic:** T13 — Security, Indexing & Hashing | **Priority:** 🟢 Low | **Exam Frequency:** 1/7 finals (+ 0 CTs) (4 marks)
> **Sources:** Silberschatz 7e Ch. 4 (§4.7), Ch. 9 (§9.8) · Lecture Deck 01 (Slides 22–23)

## Why This Topic Matters

Database security protects valuable enterprise data from unauthorized access, malicious modification, and theft. The RUET syllabus examines database security under Unit 8 (Advanced DBMS). Past exams test core threats to database security and require matching technical countermeasures. Mastering SQL authorization commands (`GRANT`, `REVOKE`), role hierarchies, and authorization graphs guarantees full marks on security theory questions.

---

## 📝 Key Definitions

> **Database Security:** Database security is the set of tools, access controls, and policies used to protect a database. It prevents unauthorized access, tampering, or service disruption to preserve confidentiality, integrity, and availability.

> **Authorization:** Authorization defines what actions an authenticated user is allowed to perform on specific parts of a database. The core data privileges are permission to read (`SELECT`), insert (`INSERT`), update (`UPDATE`), and delete (`DELETE`) records.

> **Role:** A role is a named group of privileges created in the database to match a job function. Administrators grant permissions to a role once and then assign that role to multiple users.

> **Audit Trail:** An audit trail is a chronological log of all changes (`INSERT`, `UPDATE`, and `DELETE`) made to database data. It records what changed, which user performed the action, and when the change happened.

---

## The CIA Triad in Database Systems

Database security policies revolve around three core goals, known as the **CIA triad**:

1. **Confidentiality:** Keeps private data hidden from unauthorized users. We enforce this through access control lists, security views, and encryption.
2. **Integrity:** Prevents unauthorized users from inserting, updating, or deleting records. We protect integrity through domain constraints, foreign keys, triggers, and privilege rules.
3. **Availability:** Ensures that authorized users have reliable, uninterrupted access to data whenever they need it. We defend availability against Denial of Service (DoS) attacks, hardware crashes, and resource deadlocks.

---

## Four Main Threats to Database Security

When exams ask for the main threats to database security, focus on the four database-specific attack surfaces below: application query manipulation, insider privilege misuse, network or disk snooping, and server resource exhaustion.

### 1. SQL Injection (Dynamic Query Manipulation)

- **How the Attack Works:** An attacker types malicious SQL fragments into a web form, URL parameter, or API field. Because the application glues this raw input directly into a query string without checking it, the database parser is tricked into running the attacker's commands.
- **Damage Caused:** Bypassing login screens, stealing large amounts of private data, modifying records, or deleting entire tables.
- **How to Stop It:**
  - Always use prepared statements with parameterized queries (`PreparedStatement` in JDBC) so user input is treated strictly as data.
  - Validate input types and check dynamic column or table names against a strict allowlist.
  - Give the web application's database account only the minimum permissions it needs.

### 2. Privilege Abuse and Unauthorized Access

- **How the Attack Works:** Employees or rogue insiders are given far more database permissions than their job requires, or an attacker steals a valid user's login credentials to read or alter restricted tables.
- **Damage Caused:** Insider data leaks, unauthorized salary or grade changes, and theft of sensitive records.
- **How to Stop It:**
  - Use Role-Based Access Control (RBAC) and follow the **principle of least privilege**.
  - Hide sensitive columns (like salaries or national IDs) behind restricted SQL views instead of granting access to raw base tables.
  - Require multi-factor authentication (MFA) and split sensitive duties across multiple admins.

### 3. Data Eavesdropping and Storage Leakage

- **How the Attack Works:** When query strings and result tables travel across a network in plain text, attackers on the same network can capture them with packet sniffers. Attackers can also steal unencrypted hard drives, log files, or backup tapes.
- **Damage Caused:** Direct theft of plaintext passwords, financial records, and personal data.
- **How to Stop It:**
  - Encrypt all network traffic between clients and database servers using TLS/SSL.
  - Encrypt database files and backups on disk using Transparent Data Encryption (TDE), and store the encryption keys on a separate Key Management Service (KMS).

### 4. Denial of Service (DoS)

- **How the Attack Works:** Attackers flood the database server with thousands of fake connection requests, or they trigger slow queries that force massive full-table scans, huge Cartesian products, and heavy sorting.
- **Damage Caused:** The server runs out of CPU, RAM, or open connection slots, causing real users to get connection timeouts.
- **How to Stop It:**
  - Place a database firewall in front of the server and enforce query rate limits.
  - Set strict connection pool caps and automatic query execution timeouts.
  - Build proper indices so common queries do not trigger slow full-table scans.

## SQL Authorization Architecture

SQL includes built-in Data Control Language (DCL) commands to grant and revoke fine-grained permissions on tables, views, and schemas.

### SQL Privilege Types

The SQL standard defines five specific privileges you can grant on a table or view:

| Privilege | Operation Permitted | Example Command Target |
| :--- | :--- | :--- |
| `SELECT` | Reading tuples from a relation or view | `SELECT * FROM instructor` |
| `INSERT` | Adding new tuples (optionally restricted to specific attributes) | `INSERT INTO department VALUES (...)` |
| `UPDATE` | Modifying existing attribute values | `UPDATE instructor SET salary = salary * 1.05` |
| `DELETE` | Removing tuples from a relation | `DELETE FROM student WHERE tot_cred = 0` |
| `REFERENCES` | Declaring foreign keys that reference the target relation | `FOREIGN KEY (dept_name) REFERENCES department` |
| `ALL PRIVILEGES`| Shorthand for granting all allowable rights on the object | Full administrative control of the relation |

> [!NOTE]
> Why does SQL require a separate `REFERENCES` privilege just to create a foreign key?
> Suppose user A creates a table with a foreign key pointing to user B's `department` table. Once that foreign key exists, user B can no longer delete or update a department row if user A's table references it! Because a foreign key restricts what the table owner can do with their own data, SQL requires user B to explicitly grant `REFERENCES` permission first.

### The `GRANT` and `REVOKE` Commands

Database administrators hand out permissions using the `GRANT` statement:

```sql
GRANT SELECT, INSERT ON student TO registrar, dean;
GRANT UPDATE (salary) ON instructor TO payroll_dept;
```

To take back permissions that were granted earlier, administrators run the `REVOKE` statement:

```sql
REVOKE INSERT ON student FROM registrar;
REVOKE UPDATE (salary) ON instructor FROM payroll_dept;
```

## Role-Based Access Control (RBAC)

In a large university or company with hundreds of staff members, granting permissions to one user account at a time is slow and easy to mess up. If someone changes jobs, an admin might forget to revoke their old permissions. SQL solves this problem with **roles**. Think of a role as a job title badge: you attach permissions to the badge, and then hand the badge to anyone doing that job.

```sql
-- Step 1: Create a role
CREATE ROLE instructor;

-- Step 2: Grant object privileges to the role
GRANT SELECT ON takes TO instructor;
GRANT UPDATE (grade) ON takes TO instructor;

-- Step 3: Grant the role to individual users
GRANT instructor TO Satoshi, Amit;
```

Roles can also inherit from other roles in a hierarchy:

```sql
CREATE ROLE dean;
GRANT instructor TO dean;
GRANT dean TO Satoshi;
```

Because `dean` inherits from `instructor`, `Satoshi` automatically gets every permission granted to `dean` plus every permission granted to `instructor`.

## Authorization via Views

Sometimes you want a user to see only certain columns or certain rows of a table. Instead of splitting the physical table, you can create a **view** that filters the data and grant `SELECT` permission on the view alone:

```sql
-- Create a security view hiding instructor salaries
CREATE VIEW faculty_public AS
    SELECT ID, name, dept_name
    FROM instructor;

-- Grant access on the view, while denying access on the base table
GRANT SELECT ON faculty_public TO academic_advisors;
```

Now members of `academic_advisors` can look up faculty names and departments through `faculty_public`, while any attempt to query the `instructor` table directly to see salaries is blocked by the DBMS.

## Authorization Graphs and Cascading Revocation

By default, when you receive a privilege, you can use it yourself, but you cannot pass it on to anyone else. However, if the administrator adds the `WITH GRANT OPTION` clause, you also get permission to grant that privilege to other users:

```sql
GRANT SELECT ON instructor TO Amit WITH GRANT OPTION;
```

### Intuitive Analogy: Why We Need an Authorization Graph

Imagine the `DBA` gives manager $U_1$ a master keycard that allows $U_1$ to issue copies to $U_4$ and $U_5$. Later, if $U_1$ is fired and loses their keycard, $U_4$'s copy should also be deactivated automatically. That chain reaction is called **cascading revocation**.

What if $U_5$ was *also* given the exact same keycard permission by a second manager, $U_2$, who is still employed? Then $U_5$ should keep their access! To track who gave permissions to whom, the DBMS maintains a directed **authorization-grant graph**, where nodes are users (starting from the `DBA` root) and arrows show who granted the privilege to whom.

![Authorization-grant graph with DBA, U1 through U5](diagrams/T13.01_authorization_grant_graph__TB_fig_04_11.jpg)
*Figure 13.1: Authorization-grant graph ($U_1, \dots, U_5$ are users and DBA is the database administrator) (Source: Textbook Ch. 4, Fig. 4.11).*

### Rules of Privilege Revocation

A user keeps a privilege if and only if there is still at least one unbroken chain of arrows from the `DBA` root to that user's node in the graph:

- **Cascading Revocation (`CASCADE`):** This is the default behavior in SQL. When a user loses a privilege, every grant arrow coming *out* of that user is deleted. Any downstream user who no longer has a valid path back to the `DBA` loses the privilege too.
  - For example, in Figure 13.1, if the `DBA` revokes the privilege from $U_1$, the arrow $\text{DBA} \rightarrow U_1$ is removed. User $U_4$ loses the privilege because its only path back to the `DBA` went through $U_1$.
  - In contrast, user $U_5$ **keeps** the privilege! Even though the arrow $U_1 \rightarrow U_5$ is gone, $U_5$ still has a second valid path from the root: $\text{DBA} \rightarrow U_2 \rightarrow U_5$.
- **Restricted Revocation (`RESTRICT`):** If an admin runs `REVOKE ... RESTRICT`, the database checks whether anyone else depends on that user's grant. If revoking the privilege would cause a cascade to downstream users, the command aborts and returns an error.

## Audit Trails and Forensic Accountability

Access controls try to block bad actions up front, whereas an **audit trail** acts like a security camera that records every change (`INSERT`, `UPDATE`, `DELETE`) that actually happens inside the database:

- Which user account ran the query and from what client IP address.
- The exact timestamp of the transaction.
- Which operation ran (`INSERT`, `UPDATE`, or `DELETE`).
- The before-and-after values of the modified rows.

If a hacker compromises an admin account or an insider tampers with records, administrators can read the audit trail to see exactly what was changed and roll those changes back. To stop attackers from erasing their tracks, production systems write audit logs to append-only storage or immutable ledger tables.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.8(a) · Four Main Threats to Database Security

> **Appeared:** 2017 Q.8(a) — (04 marks)

**Question:**

Describe four of the main threats to database security.

**Full Answer:**

Four main threats to database security, along with their attack mechanisms and technical countermeasures, are:

1. **SQL Injection Attack:**
   - **Mechanism:** Attackers enter malicious SQL control characters and fragments into unsanitized application input fields. When the application concatenates these inputs into dynamic queries, the SQL parser executes unintended attacker instructions.
   - **Countermeasure:** Use prepared statements with parameterized queries (`PreparedStatement` in JDBC). The database treats user parameters strictly as literal values rather than executable code.

2. **Privilege Abuse and Excessive Rights:**
   - **Mechanism:** Legitimate users, rogue insiders, or stolen accounts possess permissions far exceeding their actual operational responsibilities. They access, leak, or modify sensitive data without business justification.
   - **Countermeasure:** Enforce the principle of least privilege using Role-Based Access Control (RBAC). Use SQL `GRANT` and `REVOKE` statements to assign minimal privileges, and deploy security views to restrict table visibility.

3. **Data Eavesdropping and Network Transit Leakage:**
   - **Mechanism:** Unencrypted database traffic between client applications and database servers can be intercepted by network sniffers. Plaintext database files or storage backups can also be stolen directly from disk drives.
   - **Countermeasure:** Encrypt all network communication using Transport Layer Security (TLS/SSL). Protect stored database files and backups using Transparent Data Encryption (TDE) with hardware-secured keys.

4. **Denial of Service (DoS):**
   - **Mechanism:** Attackers flood the database engine with massive volumes of connection requests or intentionally run expensive, unindexed queries. These queries consume server CPU, memory, and connection pools, preventing legitimate users from accessing the system.
   - **Countermeasure:** Implement database connection pooling, configure query timeout thresholds, enforce rate limiting through database firewalls, and maintain proper indexing to prevent slow full-table scans.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Exercise 4.7 · SQL Authorization GRANT and REVOKE with CASCADE vs RESTRICT

> **Source:** Silberschatz 7e · Chapter 4 (§4.7 / Exercise 4.7 & 4.24)  
> **Exam Relevance:** High-Probability SQL Authorization Question (RUET Syllabus Unit 8 & Unit 4)  
> **Key Tested Concept:** SQL `GRANT ... WITH GRANT OPTION`, authorization-grant graph reachability, cascading revocation (`CASCADE`), and dependency-blocking revocation (`RESTRICT`).

**Problem Statement:**
> Consider the following sequence of authorization operations performed on the `instructor` relation:
> 1. The database administrator (`DBA`) executes:
>    ```sql
>    GRANT SELECT ON instructor TO U1 WITH GRANT OPTION;
>    GRANT SELECT ON instructor TO U2 WITH GRANT OPTION;
>    ```
> 2. User $U_1$ executes:
>    ```sql
>    GRANT SELECT ON instructor TO U4;
>    GRANT SELECT ON instructor TO U5;
>    ```
> 3. User $U_2$ executes:
>    ```sql
>    GRANT SELECT ON instructor TO U5;
>    ```
> 
> Answer the following:
> - **(a)** Draw the resulting directed **authorization-grant graph**.
> - **(b)** Suppose the `DBA` now revokes the privilege from $U_1$ using:
>   ```sql
>   REVOKE SELECT ON instructor FROM U1 CASCADE;
>   ```
>   Explain what happens to the privileges of $U_4$ and $U_5$. State the formal reachability rule governing privilege retention.
> - **(c)** What happens if the `DBA` instead executes:
>   ```sql
>   REVOKE SELECT ON instructor FROM U1 RESTRICT;
>   ```
> - **(d)** Suppose users $U_2$ and $U_3$ grant the privilege to each other in a closed cycle ($U_2 \rightarrow U_3$ and $U_3 \rightarrow U_2$), and the `DBA` revokes authorization from $U_2$. Explain why the cycle cannot prevent both users from losing their authorization.

**Model Exam-Style Solution:**

1. **(a) Authorization-Grant Graph:**
   - In an authorization graph, each node represents a user or role, and a directed edge $U_i \rightarrow U_j$ signifies that user $U_i$ granted the privilege to user $U_j$. The root of the graph is the `DBA`.

   ```text
            ┌─────────┐
            │   DBA   │
            └──┬───┬──┘
               │   │
        ┌──────┘   └──────┐
        ▼                 ▼
     ┌────┐            ┌────┐
     │ U1 │            │ U2 │
     └┬──┬┘            └──┬─┘
      │  └──────┐         │
      ▼         ▼         ▼
   ┌────┐     ┌─────────────┐
   │ U4 │     │     U5      │
   └────┘     └─────────────┘
   ```
   - Edges present: $\text{DBA} \rightarrow U_1$, $\text{DBA} \rightarrow U_2$, $U_1 \rightarrow U_4$, $U_1 \rightarrow U_5$, and $U_2 \rightarrow U_5$.

2. **(b) Cascading Revocation (`CASCADE`):**
   - **Formal Reachability Rule:** In standard SQL authorization, a user $U$ retains a privilege if and only if there exists a **directed path from the root (`DBA`) to $U$** in the authorization-grant graph.
   - When the `DBA` executes `REVOKE SELECT ON instructor FROM U1 CASCADE;`:
     - The edge $\text{DBA} \rightarrow U_1$ is removed.
     - Because `CASCADE` propagates to all dependent privileges granted by $U_1$, the outgoing edges $U_1 \rightarrow U_4$ and $U_1 \rightarrow U_5$ are also revoked.
   - **Impact on $U_4$:** User $U_4$ was granted the privilege solely by $U_1$. With edge $U_1 \rightarrow U_4$ removed, no directed path remains from `DBA` to $U_4$. Therefore, **$U_4$ loses the `SELECT` privilege**.
   - **Impact on $U_5$:** Although the grant edge from $U_1$ ($U_1 \rightarrow U_5$) is deleted, user $U_5$ also received the privilege from $U_2$. The alternative path $\text{DBA} \rightarrow U_2 \rightarrow U_5$ remains intact and valid. Therefore, **$U_5$ retains the `SELECT` privilege**.

3. **(c) Restricted Revocation (`RESTRICT`):**
   - When the administrator runs:

```sql
REVOKE SELECT ON instructor FROM U1 RESTRICT;
```
   - The `RESTRICT` clause directs the DBMS to verify whether revoking the privilege from $U_1$ would cause any cascading revocations to downstream users.
   - Because user $U_4$ depends entirely on $U_1$ for access, revoking from $U_1$ would cascade to $U_4$.
   - Consequently, the DBMS **aborts the command with an error** and carries out no revocation.
   - To revoke from $U_1$ under `RESTRICT`, the administrator must first explicitly revoke access from all dependent grantees ($U_4$ and $U_5$) before revoking from $U_1$.

4. **(d) Devious Cyclic Grants ($U_2 \rightleftharpoons U_3$):**
   - Consider the scenario where $U_2$ grants the privilege to $U_3$, and $U_3$ grants it back to $U_2$:
     $$
     \text{DBA} \rightarrow U_2 \rightleftarrows U_3
     $$
   - When the `DBA` revokes the authorization from $U_2$, the incoming edge $\text{DBA} \rightarrow U_2$ is severed.
   - Although a cycle exists ($U_2 \rightarrow U_3 \rightarrow U_2$), **neither $U_2$ nor $U_3$ has a path connected back to the root (`DBA`)**.
   - Because the authorization definition strictly requires a path originating from the `DBA`, the closed cycle cannot sustain itself. The DBMS prunes the unrooted cycle, and **both $U_2$ and $U_3$ lose the privilege**. $\blacksquare$

**💡 RUET Exam Takeaway:**
Remember the golden rule of authorization revocation: **Privilege retention strictly depends on path reachability from the DBA root.** `CASCADE` prunes dependent edges down the tree; `RESTRICT` throws an error if dependent edges exist.

## ⚡ Exam Tips & Common Mistakes

1. **Include Countermeasures:** The question says "Describe four threats", but exam scorers expect both the threat mechanism and its technical countermeasure for each point. Always supply both to secure the full 4 marks.
2. **Avoid Vague Terminology:** Do not write generic computer threats like "computer viruses" or "hardware breakdown". Focus on database-specific vulnerabilities: SQL injection, privilege escalation, unencrypted data leakage, and query-based DoS.
3. **Remember the Multi-Parent Graph Rule:** In authorization graphs, revoking privileges from user A does not automatically strip privileges from user B if user B still has another valid grant path leading back to the DBA root.
4. **Distinguish Authentication from Authorization:** Authentication verifies *who* the user is (e.g., passwords, certificates, MFA). Authorization determines *what* actions that authenticated user can perform on specific tables and views.
