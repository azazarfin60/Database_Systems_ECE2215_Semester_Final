# T06.2: Computing Join Outcome Tables in MySQL

> **Topic:** T06 — Joins & Views | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals (11 marks)
> **Sources:** Silberschatz 7e Ch. 4 (§4.1, pp. 125–136) · Lecture Deck 04 (Slides 5–23) · Raidah Notes (p. 18) · Fahim Notes (pp. 51–55)

## Why This Topic Matters

Join outcome table questions test whether you can act like a human SQL engine and trace join results row by row on paper. This exact question format appeared in both 2020 (5 marks) and 2024 (6 marks), where examiners gave two small tables (`Courses` and `Teacher`) and asked for the exact output table of a Natural Join, Left Outer Join, Right Outer Join, and Full Outer Join. To score full marks, you need clean output tables with the right column headers, accurate row matches, and explicit `NULL` values wherever a match is missing.

---

## 📝 Key Definitions

> **Natural Join:** "Natural join considers only those pairs of tuples with the same value on those attributes that appear in the schemas of both relations." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.1.1 (p. 127)

> **Left Outer Join:** "The left outer join preserves tuples only in the relation named before (to the left of) the left outer join operation." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.1.3 (p. 131)

> **Right Outer Join:** "The right outer join preserves tuples only in the relation named after (to the right of) the right outer join operation." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.1.3 (p. 132)

> **Full Outer Join:** "Said differently, full outer join is the union of a left outer join and the corresponding right outer join." — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §4.1.3 (p. 133)

## Step-by-Step Algorithm for Tracing Join Outcome Tables

Why try to guess four different join tables from scratch when they all share the exact same core rows? The easiest, most error-proof way to solve these problems on an exam is to break the two input tables into **three building blocks** first: (1) **Matched Pairs**, (2) **Left Dangling Rows** (left rows with no match on the right), and (3) **Right Dangling Rows** (right rows with no match on the left). Once you have those three pieces, every join table is just a simple combination of them:

```text
Step 1: Find the Shared Join Column & Combined Schema
        └── Spot the column name that appears in both tables (e.g., `t_code` or `t code`).
        └── List the output columns (keeping the shared column only ONCE).

Step 2: Build Block A — The Matched Tuples
        └── Pair up every (left_row, right_row) that shares the same join key.
        └── If one key in the right table matches two rows in the left table, write BOTH pairs!

Step 3: Build Block B — Left Dangling Tuples
        └── Find any left-table rows whose join key does NOT exist in the right table.
        └── Pad their missing right-table columns with `NULL`.

Step 4: Build Block C — Right Dangling Tuples
        └── Find any right-table rows whose join key does NOT exist in the left table.
        └── Pad their missing left-table columns with `NULL`.

Step 5: Snap the Blocks Together for All 4 Answers
        ├── (i)   Natural Join     = Block A only
        ├── (ii)  Left Outer Join  = Block A + Block B
        ├── (iii) Right Outer Join = Block A + Block C
        └── (iv)  Full Outer Join  = Block A + Block B + Block C
```

## MySQL Dialect Rules for Outer Joins

When writing the accompanying MySQL queries above your outcome tables, watch out for two MySQL rules:

### 1. Handling Column Names with Spaces
In the 2020 exam paper, the teacher code column was printed with a space inside its name (`t code`). In MySQL, any column or table name that contains a space must be wrapped in backticks like `` `t code` `` so the parser does not mistake it for two separate words. In the 2024 paper, it was printed with an underscore (`t_code`), which needs no backticks.

### 2. Emulating `FULL OUTER JOIN` in MySQL
MySQL does not support the `FULL OUTER JOIN` keyword directly. If you write `FULL OUTER JOIN` in MySQL, you get a syntax error. Instead, write a `LEFT JOIN` and a `RIGHT JOIN` connected by `UNION`:

```sql
SELECT Courses.Code, Courses.Series, Courses.t_code, Teacher.Designation
FROM Courses
LEFT JOIN Teacher ON Courses.t_code = Teacher.t_code
UNION
SELECT Courses.Code, Courses.Series, Teacher.t_code, Teacher.Designation
FROM Courses
RIGHT JOIN Teacher ON Courses.t_code = Teacher.t_code;
```

Because `UNION` automatically removes duplicate rows, the matched rows (`Block A`) appear only once, while both sets of `NULL`-padded dangling rows (`Block B` and `Block C`) are kept.

## Worked Example: Tracing Both Left and Right Dangling Tuples

In both the 2020 and 2024 RUET exams (solved in full in `GQ1` and `GQ2` below), every course in the left table happened to have a valid teacher, so there were zero left-dangling rows. What if **both** tables have unmatched rows? Let's trace a quick 3-row mini-example so you are ready if the next exam includes dangling rows on both sides!

**Relation: `Student`**

| Roll | Name | advisor_id |
| :---: | :--- | :---: |
| 101 | Nabil | A1 |
| 102 | Sadia | A1 |
| 103 | Tanvir | A9 |

**Relation: `Advisor`**

| advisor_id | Room |
| :---: | :--- |
| A1 | Room-204 |
| A2 | Room-310 |

### Step-by-Step Building Blocks:
1. **Shared Join Column:** `advisor_id`. Output schema: `(Roll, Name, advisor_id, Room)`.
2. **Block A (Matched Rows):** Both Nabil (`101`) and Sadia (`102`) have `advisor_id = A1`, which matches `A1` (`Room-204`). That gives **2 matched rows**: `(101, Nabil, A1, Room-204)` and `(102, Sadia, A1, Room-204)`.
3. **Block B (Left Dangling Rows):** Tanvir (`103`) has `advisor_id = A9`, which is not in `Advisor`. Padding `Room` with `NULL` gives **1 left-dangling row**: `(103, Tanvir, A9, NULL)`.
4. **Block C (Right Dangling Rows):** Advisor `A2` (`Room-310`) advises no students in `Student`. Padding `Roll` and `Name` with `NULL` gives **1 right-dangling row**: `(NULL, NULL, A2, Room-310)`.

### Resulting Join Outcomes:
- **Natural Join (Block A — 2 rows):** Only Nabil and Sadia.
- **Left Outer Join (Block A + Block B — 3 rows):** Nabil, Sadia, plus `(103, Tanvir, A9, NULL)`.
- **Right Outer Join (Block A + Block C — 3 rows):** Nabil, Sadia, plus `(NULL, NULL, A2, Room-310)`.
- **Full Outer Join (Block A + Block B + Block C — 4 rows):** Nabil, Sadia, Tanvir (`Room = NULL`), and Advisor A2 (`Roll = NULL, Name = NULL`).

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.4(c) · Join Outcome Tables on Courses & Teacher (Space in Join Key)

> **Appeared:** 2020 Q.4(c) — (05 Marks)

**Question:**

Consider the following tables:

What will happen when the following actions will be performed on these two relations?  
(i) Natural Join  
(ii) Left Outer Join  
(iii) Right Outer Join  
(iv) Full Outer Join

**Full Answer:**

The common attribute connecting `Courses` and `Teacher` is `t code`. In MySQL syntax, column names containing spaces are enclosed in backticks (`` `t code` ``).

#### (i) Natural Join

A natural join equates tuples with equal values on all common attributes (`t code`) and retains a single copy of `t code`.

- **Relational Algebra:**
  $$
  \text{Courses} \bowtie \text{Teacher}
  $$
- **MySQL Query:**
  ```sql
  SELECT Code, Series, `t code`, Designation
  FROM Courses
  NATURAL JOIN Teacher;
  ```

**Outcome Table (4 rows):**

| Code | Series | t code | Designation |
| :--- | :---: | :---: | :--- |
| ECE 2215 | 2017 | T1 | Head |
| ECE 4127 | 2016 | T2 | Professor |
| ECE 1203 | 2019 | T3 | Lecturer |
| ECE 2219 | 2017 | T2 | Professor |

*Explanation:* Every course tuple has an assigned teacher (T1, T2, T3). Teacher T2 appears twice because two courses share T2. Teacher T4 is omitted because T4 has no matching course.

---

#### (ii) Left Outer Join

A left outer join preserves all tuples from the left table (`Courses`). Any unmatched right attributes are filled with `NULL`.

- **Relational Algebra:**
  $$
  \text{Courses} \mathbin{⟕} \text{Teacher}
  $$
- **MySQL Query:**
  ```sql
  SELECT Courses.Code, Courses.Series, Courses.`t code`, Teacher.Designation
  FROM Courses
  LEFT JOIN Teacher ON Courses.`t code` = Teacher.`t code`;
  ```

**Outcome Table (4 rows):**

| Code | Series | t code | Designation |
| :--- | :---: | :---: | :--- |
| ECE 2215 | 2017 | T1 | Head |
| ECE 4127 | 2016 | T2 | Professor |
| ECE 1203 | 2019 | T3 | Lecturer |
| ECE 2219 | 2017 | T2 | Professor |

*Explanation:* All four course records find a matching teacher code in `Teacher`. No row is left unmatched, so no `NULL` padding is required. The outcome table is identical to the Natural Join.

---

#### (iii) Right Outer Join

A right outer join preserves all tuples from the right table (`Teacher`). Any unmatched left attributes are filled with `NULL`.

- **Relational Algebra:**
  $$
  \text{Courses} \mathbin{⟖} \text{Teacher}
  $$
- **MySQL Query:**
  ```sql
  SELECT Courses.Code, Courses.Series, Teacher.`t code`, Teacher.Designation
  FROM Courses
  RIGHT JOIN Teacher ON Courses.`t code` = Teacher.`t code`;
  ```

**Outcome Table (5 rows):**

| Code | Series | t code | Designation |
| :--- | :---: | :---: | :--- |
| ECE 2215 | 2017 | T1 | Head |
| ECE 4127 | 2016 | T2 | Professor |
| ECE 2219 | 2017 | T2 | Professor |
| ECE 1203 | 2019 | T3 | Lecturer |
| `NULL` | `NULL` | T4 | Lecturer |

*Explanation:* Teachers T1, T2, and T3 match courses in `Courses`. Teacher T4 has no course assignments. T4 is retained in the result with `NULL` in the `Code` and `Series` columns.

---

#### (iv) Full Outer Join

A full outer join retains all tuples from both relations. Non-matching attributes on either side are filled with `NULL`.

- **Relational Algebra:**
  $$
  \text{Courses} \mathbin{⟗} \text{Teacher}
  $$
- **MySQL Query:**
  ```sql
  SELECT Courses.Code, Courses.Series, Courses.`t code`, Teacher.Designation
  FROM Courses
  LEFT JOIN Teacher ON Courses.`t code` = Teacher.`t code`
  UNION
  SELECT Courses.Code, Courses.Series, Teacher.`t code`, Teacher.Designation
  FROM Courses
  RIGHT JOIN Teacher ON Courses.`t code` = Teacher.`t code`;
  ```

**Outcome Table (5 rows):**

| Code | Series | t code | Designation |
| :--- | :---: | :---: | :--- |
| ECE 2215 | 2017 | T1 | Head |
| ECE 4127 | 2016 | T2 | Professor |
| ECE 2219 | 2017 | T2 | Professor |
| ECE 1203 | 2019 | T3 | Lecturer |
| `NULL` | `NULL` | T4 | Lecturer |

*Explanation:* All four courses match teachers. The unmatched teacher T4 is preserved with `NULL` for `Code` and `Series`.

*Explanation:* Every course row has an assigned `t_code` present in `Teacher`. No left tuple is unmatched, so no `NULL` padding is needed. The outcome matches the Natural Join.

## ⚡ Exam Tips & Common Mistakes

1. **Explicit `NULL` Values:** Never leave table cells blank or write dashes (`-`). Examiners expect explicit `NULL` text in uppercase.
2. **Never Duplicate Common Columns in Natural Join:** In Natural Join, the common attribute (`t_code`) appears once in the schema header. Listing `t_code` twice is a common penalty trap.
3. **Handle 1-to-Many Matches Correctly:** When teacher `T3` teaches two courses (`E_1203` and `E_2219`), `T3` must appear in two distinct output rows. Do not accidentally merge or drop course rows.
4. **State MySQL `FULL JOIN` Limitation:** Always mention that MySQL lacks native `FULL OUTER JOIN` syntax and requires `LEFT JOIN ... UNION ... RIGHT JOIN`. This demonstrates deep system awareness to RUET examiners.
5. **Always Write Queries Alongside Tables:** Even if the question asks "What will happen?", write the relational algebra expression and the SQL query above each outcome table. This secures full partial credit if you make a minor transcription typo in the table cells.
