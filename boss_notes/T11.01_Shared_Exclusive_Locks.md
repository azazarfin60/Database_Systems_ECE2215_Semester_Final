# T11.1: Shared and Exclusive Locks & Compatibility Matrix

> **Topic:** T11 — Concurrency Control Protocols | **Priority:** 🟠 | **Exam Frequency:** 0/7 finals (⭐ Foundation for 2PL; Starvation asked in 2017 Q7a)
> **Sources:** Silberschatz 7e Ch. 18 (§18.1.1–18.1.2, pp. 835–841) · Lecture Deck 08 (Slides 9–12) · Raidah Notes (p. 28, 30)

## Why This Topic Matters

Locking is the main tool database systems use to keep concurrent transactions from stepping on each other's work. If every transaction locked the entire database one at a time, performance would grind to a halt. Instead, databases distinguish between **Shared (`S`) locks** for reading and **Exclusive (`X`) locks** for writing, allowing many readers to inspect the same record at once while giving writers isolated access. However, acquiring and releasing locks naively leads to four classic hazards: non-serializable schedules, irrecoverable states, starvation, and deadlocks. Starvation was directly tested in 2017 Q.7(a), and understanding lock compatibility is the foundation for Two-Phase Locking (2PL).

---

## 📝 Key Definitions

> **Lock-Compatibility Function:** "Let $A$ and $B$ represent arbitrary lock modes. Suppose that a transaction $T_i$ requests a lock of mode $A$ on item $Q$ on which transaction $T_j$ ($T_i \neq T_j$) currently holds a lock of mode $B$. If transaction $T_i$ can be granted a lock on $Q$ immediately, in spite of the presence of the mode $B$ lock, then we say mode $A$ is **compatible** with mode $B$. Such a function can be represented conveniently by a matrix."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.1.1 (p. 836)

> **Starvation:** "A transaction may never be granted the lock on the data item. Transaction $T_1$ may never get to make progress, and is said to be **starved**."  
> — Silberschatz, Korth & Sudarshan, *Database System Concepts* (7th Ed.), §18.1.2 (p. 840)

> **Shared-Mode Lock (`lock-S`):** "Data item can only be read. S-lock is requested using **lock-S** instruction."  
> — Lecture Deck 08, Slide 10 *(Course definition)*

> **Exclusive-Mode Lock (`lock-X`):** "Data item can be both read as well as written. X-lock is requested using **lock-X** instruction."  
> — Lecture Deck 08, Slide 10 *(Course definition)*

## Lock Modes: Shared (S) vs. Exclusive (X)

Think of database locks like a shared Google Doc: hundreds of people can open the document in **View-Only mode** at the same time without causing any conflict, but if someone wants to **Edit** the document without interference, nobody else can be editing or reading a half-written sentence at that moment.

Database systems formalize this idea using two lock modes on any data item $Q$:

### 1. Shared Mode ($S$)
- Requested with the `lock-S(Q)` instruction and grants **read-only** access to item $Q$.
- Multiple transactions can hold shared locks on $Q$ at the same time because reading never alters the underlying data.

### 2. Exclusive Mode ($X$)
- Requested with the `lock-X(Q)` instruction and grants both **read and write** access to item $Q$.
- Only a single transaction can hold an exclusive lock on $Q$ at any moment. While an exclusive lock is held, no other transaction can hold either a shared or an exclusive lock on $Q$.

Once a transaction finishes working with $Q$, it releases its lock by executing `unlock(Q)`.

---

## The Lock-Compatibility Matrix

Whenever transaction $T_i$ requests a lock on item $Q$ while another transaction $T_j$ already holds a lock on $Q$, the lock manager checks the **lock-compatibility matrix** to decide whether $T_i$ can proceed immediately or must wait:

| Requested Mode $\downarrow$ \ Currently Held Mode $\to$ | Shared ($S$) | Exclusive ($X$) |
| :---: | :---: | :---: |
| **Shared ($S$)** | **True** (Compatible) | **False** (Conflict) |
| **Exclusive ($X$)** | **False** (Conflict) | **False** (Conflict) |

### Why Each Cell Works This Way
- **$S$ requested while $S$ is held (`True`):** Readers never change values, so letting a new reader join existing readers maximizes concurrency safely.
- **$S$ requested while $X$ is held (`False`):** An active writer is modifying $Q$. Blocking the reader until the writer finishes prevents **dirty reads**.
- **$X$ requested while $S$ is held (`False`):** Someone is currently reading $Q$. Blocking the writer until active readers finish prevents **unrepeatable reads**.
- **$X$ requested while $X$ is held (`False`):** Two simultaneous writers would overwrite each other's updates, so blocking the second writer prevents **lost updates**.

---

## Pitfalls of Simple Locking Protocols

In a naive ("simple") locking protocol, a transaction acquires a lock right before accessing an item and unlocks it immediately after that single operation finishes.

Although releasing locks right away sounds good for concurrency, Lecture Deck 08 (Slide 11) highlights four major flaws with simple locking:

1. **Serializability is not guaranteed:**  
   Unlocking an item before the transaction finishes its other steps lets other transactions see half-completed updates (inconsistent analysis).
2. **Irrecoverable schedules can occur:**  
   Unlocking a modified item before committing lets other transactions read dirty data and commit before the writer commits.
3. **Starvation can occur:**  
   A transaction waiting for an `X` lock can be bypassed endlessly by a steady stream of incoming `S` lock requests.
4. **Deadlocks can occur:**  
   Two transactions can each hold a lock that the other needs, trapping both in a circular wait.

### Quick Intuition: Why Early Unlocking Breaks Serializability

Suppose $T_1$ is moving $10$ units of stock from warehouse $X$ (initially $50$) to warehouse $Y$ (initially $50$), so total stock should always be $100$. Meanwhile, $T_2$ audits total inventory $X + Y$:

1. $T_1$ locks $X$, subtracts $10$ (so $X = 40$), and **immediately unlocks $X$** before touching $Y$.
2. While $T_1$ is paused, $T_2$ locks and reads $X = 40$ and $Y = 50$, computing a total of $90$ instead of $100$!
3. $T_1$ then locks $Y$ and adds $10$ (so $Y = 60$).

Even though both transactions used locks for every access, $T_2$ saw an inconsistent state where $10$ units had vanished in transit. Because $T_1$ released its lock on $X$ before acquiring its lock on $Y$, the schedule is not serializable. This flaw is why databases use **Two-Phase Locking (2PL)**, where a transaction cannot release any lock until it has acquired every lock it will ever need.

## Starvation and Fair Lock Scheduling

### How Starvation Happens
**Starvation** (indefinite blocking) occurs when a waiting transaction never gets its turn because the system keeps granting locks to newly arriving transactions.

In locking protocols, writers are especially vulnerable to starvation by readers:
1. Suppose transaction $T_2$ holds a shared lock `lock-S(A)`.
2. Transaction $T_1$ arrives and requests an exclusive lock `lock-X(A)`. Because $X$ conflicts with $S$, $T_1$ is forced to wait for $T_2$ to finish.
3. While $T_1$ is waiting, transaction $T_3$ arrives and requests `lock-S(A)`. Since $S$ is compatible with $T_2$'s held $S$ lock, a naive lock manager grants `lock-S(A)` to $T_3$ right away.
4. Next, $T_2$ finishes and unlocks $A$, but $T_1$ is still stuck waiting because $T_3$ now holds `lock-S(A)`.
5. Before $T_3$ finishes, $T_4$ arrives and is also granted `lock-S(A)`. As long as new readers keep overlapping like a relay race, $T_1$ waits forever and starves.

### Slide 12 Schedule Matrix for Starvation

| Time | $T_1$ (Needs $X$) | $T_2$ | $T_3$ | $T_4$ | Lock State of $A$ |
| :--: | :---: | :---: | :---: | :---: | :--- |
| 1 | | $\text{lock-S}(A)$ | | | Held by $T_2$ ($S$) |
| 2 | $\text{lock-X}(A)$ **[WAIT]** | | | | $T_1$ waiting for $T_2$ |
| 3 | | | $\text{lock-S}(A)$ | | Granted to $T_3$ ($S$) |
| 4 | | $\text{unlock}(A)$ | | | Still held by $T_3$ ($S$) |
| 5 | | | | $\text{lock-S}(A)$ | Granted to $T_4$ ($S$) |
| 6 | | | $\text{unlock}(A)$ | | Still held by $T_4$ ($S$) |
| 7 | | | | $\text{unlock}(A)$ | Lock finally becomes free |
| 8 | $\text{Grant}(\text{lock-X}(A))$ | | | | Finally granted to $T_1$ |

If new shared lock requests keep arriving before Step 7, Step 8 never happens.

### How the Lock Manager Prevents Starvation
To eliminate starvation, the concurrency control manager uses a **First-Come, First-Served (FIFO) queue** with two strict granting conditions:

> **Fair Lock Granting Rules:**  
> When transaction $T_i$ requests a lock of mode $A$ on item $Q$, the lock manager grants the lock if and only if:  
> 1. No other transaction currently holds a lock on $Q$ in a mode that conflicts with $A$.  
> 2. **No other transaction is already waiting in the queue for $Q$ with a conflicting request that arrived before $T_i$.**

With Rule 2 in place, as soon as $T_1$ queues its request for `lock-X(A)`, later readers like $T_3$ and $T_4$ are not allowed to jump ahead of $T_1$. Instead, they wait in line behind $T_1$. Once $T_2$ unlocks $A$, $T_1$ gets its exclusive lock immediately.

## 🔮 Likely Questions

### 🎯 LQ1 · Explain Shared and Exclusive Locks with the Lock Compatibility Matrix

**Question:**

Explain the difference between shared-mode and exclusive-mode locks in database systems. Draw the lock-compatibility matrix and explain the conditions under which a lock request is granted or made to wait.

**Full Answer:**

#### 1. Difference Between Shared and Exclusive Locks
- **Shared-Mode Lock (`lock-S`):**
  - Grants read-only access to data item $Q$ and prohibits write operations.
  - Multiple transactions can hold shared locks on $Q$ simultaneously, allowing high read concurrency.
- **Exclusive-Mode Lock (`lock-X`):**
  - Grants both read and write access to data item $Q$.
  - Only one transaction can hold an exclusive lock on $Q$ at a time, and no other transaction may hold any lock (shared or exclusive) on $Q$ while the exclusive lock is active.

#### 2. Lock-Compatibility Matrix

| Requested Mode $\downarrow$ \ Held Mode $\to$ | Shared ($S$) | Exclusive ($X$) |
| :---: | :---: | :---: |
| **Shared ($S$)** | True | False |
| **Exclusive ($X$)** | False | False |

#### 3. Granting and Waiting Conditions
- **Grant condition:** A lock request in mode $A$ on item $Q$ is granted immediately if mode $A$ is compatible with all locks currently held on $Q$ (for example, requesting $S$ when only $S$ locks are held) and no earlier conflicting request is waiting in the queue.
- **Wait condition:** If another transaction holds a conflicting lock on $Q$, or if an older conflicting request is already waiting in the queue, the requesting transaction is blocked and placed in the wait queue until the conflicting locks are released.

### 🎯 LQ2 · What is Starvation in Locking Protocols? How Can It Be Prevented?

*(Cross-reference: Appeared in past exam 2017 Q.7(a))*

**Question:**

What is starvation in database concurrency control? Illustrate how a transaction requesting an exclusive lock can suffer from starvation. How does the concurrency control manager prevent starvation?

**Full Answer:**

#### 1. Definition of Starvation
Starvation (indefinite blocking) occurs when a waiting transaction can never acquire a requested lock because the lock manager repeatedly grants locks to other concurrent transactions first, preventing the waiting transaction from ever making progress.

#### 2. Illustration of Starvation
Suppose transaction $T_1$ requests an exclusive lock `lock-X(A)` while transaction $T_2$ currently holds a shared lock `lock-S(A)`:
- Because $X$ and $S$ conflict, $T_1$ must wait for $T_2$ to unlock $A$.
- While $T_1$ is waiting, transaction $T_3$ arrives and requests `lock-S(A)`. Because $S$ is compatible with $T_2$'s held $S$ lock, a naive lock manager grants `lock-S(A)` to $T_3$.
- When $T_2$ finishes and executes `unlock(A)`, $T_1$ still cannot run because $T_3$ now holds a shared lock on $A$.
- If new transactions $T_4, T_5, \dots$ keep arriving and acquiring shared locks before the previous readers finish, $T_1$ waits forever and is starved.

#### 3. Prevention Mechanism
The concurrency control manager prevents starvation by enforcing a **First-Come, First-Served (FIFO) wait queue**:
- A lock request by $T_i$ is granted only if (1) it is compatible with currently held locks, and (2) no earlier transaction is already waiting in the queue for a conflicting lock on that item.
- Under this rule, once $T_1$ queues `lock-X(A)`, any later `lock-S(A)` requests ($T_3, T_4, \dots$) must wait behind $T_1$. As soon as $T_2$ unlocks $A$, $T_1$ acquires the exclusive lock without being bypassed.

### 🎯 LQ3 · Show How Simple Locking Can Lead to Inconsistent Analysis (Non-Serializable Schedules)

**Question:**

Using an example of two transactions accessing bank accounts $A$ and $B$, demonstrate how a simple locking protocol where locks are released immediately after access can result in a non-serializable schedule.

**Full Answer:**

#### 1. Setup
Let bank accounts have initial balances $A = 100$ and $B = 200$, so the true total balance is $A + B = 300$ (initial balances \$100 and \$200).
- **Transaction $T_1$:** Transfers \$50 from account $B$ to account $A$.
- **Transaction $T_2$:** Reads accounts $A$ and $B$ and displays their sum $A + B$.

#### 2. Interleaved Execution under Simple Locking

| Step | Transaction $T_1$ | Transaction $T_2$ | Local Work | $A$ | $B$ |
| :--: | :--- | :--- | :--- | :---: | :---: |
| 1 | $\text{lock-X}(B)$ | | | | |
| 2 | $\text{read}(B)$ | | $B = 200$ | | $200$ |
| 3 | $B := B - 50$ | | | | |
| 4 | $\text{write}(B)$ | | $B = 150$ | | $150$ |
| 5 | $\text{unlock}(B)$ | | | | |
| 6 | | $\text{lock-S}(A)$ | | | |
| 7 | | $\text{read}(A)$ | $A = 100$ | $100$ | |
| 8 | | $\text{unlock}(A)$ | | | |
| 9 | | $\text{lock-S}(B)$ | | | |
| 10 | | $\text{read}(B)$ | $B = 150$ | | $150$ |
| 11 | | $\text{unlock}(B)$ | | | |
| 12 | | $\text{display}(A+B)$ | **Displays \$250** | | |
| 13 | $\text{lock-X}(A)$ | | | | |
| 14 | $\text{read}(A)$ | | $A = 100$ | $100$ | |
| 15 | $A := A + 50$ | | | | |
| 16 | $\text{write}(A)$ | | $A = 150$ | $150$ | |
| 17 | $\text{unlock}(A)$ | | | | |

#### 3. Analysis
- In the serial schedule $\langle T_1, T_2 \rangle$, $T_2$ reads $A = 150$ and $B = 150$, displaying \$300.
- In the serial schedule $\langle T_2, T_1 \rangle$, $T_2$ reads $A = 100$ and $B = 200$, displaying \$300.
- In the concurrent schedule above, $T_2$ displays \$250, which does not match either serial execution. Therefore, the schedule is **not serializable**.
- **Root Cause:** $T_1$ released its lock on $B$ at Step 5 before acquiring its lock on $A$ at Step 13, allowing $T_2$ to read the new balance of $B$ alongside the old balance of $A$.

## 📖 High-Yield Exercises from the Book

### 🎯 HYE-01 · Practice Exercise 18.1 · Lock Compatibility Matrix & Starvation Prevention

> **Source:** Silberschatz 7e · Chapter 18 (Practice Exercise 18.1)  
> **Exam Relevance:** High-Probability Concurrency Control Drill  
> **Key Tested Concept:** Shared ($S$) vs Exclusive ($X$) lock compatibility, transaction starvation, and FIFO queuing solutions.

**Problem Statement:**
> 1. Formulate the **lock compatibility matrix** for shared and exclusive lock modes.
> 2. Explain why multiple transactions are allowed to concurrently hold shared locks on the same data item, whereas an exclusive lock requires absolute exclusivity.
> 3. Describe a scenario where a transaction requesting an exclusive lock suffers from **starvation (indefinite postponement)** due to incoming shared locks, and describe how the concurrency-control manager prevents this problem.

**Model Exam-Style Solution:**

1. **Lock Compatibility Matrix:**
   Let $M$ and $N$ denote lock modes requested on data item $Q$:

| Requested Mode $\downarrow$ \ Mode Held $\rightarrow$ | Shared ($S$) | Exclusive ($X$) |
| :---: | :---: | :---: |
| **Shared ($S$)** | **Compatible ($\text{True}$)** | Incompatible ($\text{False}$) |
| **Exclusive ($X$)** | Incompatible ($\text{False}$) | Incompatible ($\text{False}$) |

2. **Justification of Compatibility Rules:**
   - **Shared-Shared Compatibility:** Two transactions executing concurrent reads on item $Q$ cannot interfere with each other or alter data state. Hence, granting multiple $S$-locks maximizes system throughput without risking inconsistency.
   - **Exclusive Incompatibility:** An $X$-lock grants permission to write (mutate) $Q$. If another transaction reads or writes $Q$ concurrently, lost updates, dirty reads, or unrepeatable reads will occur. Thus, $X$ is incompatible with both $S$ and $X$.

3. **Starvation Scenario & Concurrency Manager Solution:**
   - **The Starvation Problem:**
     1. Transaction $T_1$ acquires a shared lock $S\text{-lock}(Q)$.
     2. Transaction $T_2$ arrives and requests an exclusive lock $X\text{-lock}(Q)$. Because $T_1$ holds an $S$-lock, $T_2$ is blocked and put into a waiting queue.
     3. While $T_2$ is waiting, transaction $T_3$ arrives and requests $S\text{-lock}(Q)$. Since $S$ is compatible with $S$ (held by $T_1$), the manager immediately grants $S\text{-lock}(Q)$ to $T_3$.
     4. $T_1$ completes and releases its lock, but $T_3$ still holds an $S$-lock.
     5. Before $T_3$ finishes, another transaction $T_4$ requests $S\text{-lock}(Q)$ and is granted the lock.
     6. If a continuous stream of read-only transactions requesting $S$-locks arrives, $T_2$ will wait **indefinitely**. $T_2$ is starved!
   - **Concurrency Manager Prevention Protocol (FIFO Queue Rule):**
     - When transaction $T_2$ requests $X\text{-lock}(Q)$ and is forced to wait, the manager places $T_2$ in a FIFO lock queue for $Q$.
     - When subsequent transaction $T_3$ requests $S\text{-lock}(Q)$, the manager checks the queue: because an incompatible lock request ($T_2$'s $X$-lock) is already queued ahead of $T_3$, **$T_3$'s request is queued behind $T_2$**, even though $T_3$'s mode is compatible with $T_1$'s currently held lock!
     - Once $T_1$ releases its lock, $T_2$ is immediately granted its $X$-lock, preventing starvation. $\blacksquare$

**💡 RUET Exam Takeaway:**
Never say "shared locks are always granted immediately if another shared lock is held." In modern DBMSs, shared locks are BLOCKED if an exclusive lock request is already waiting in the queue to prevent starvation!

## ⚡ Exam Tips & Common Mistakes

1. **Remember the 1-True / 3-False matrix pattern:** In the $2 \times 2$ compatibility matrix, only `(S, S)` is `True`. Every combination involving an `X` lock (`(S, X)`, `(X, S)`, and `(X, X)`) is `False`.
2. **List all four pitfalls of simple locking:** When asked why simple locking is insufficient, state all four issues from Slide 11: (1) non-serializable schedules, (2) irrecoverable schedules, (3) starvation, and (4) deadlocks.
3. **Starvation vs. Deadlock:** Do not confuse the two! In a **deadlock**, a group of transactions are stuck waiting on each other in a closed cycle and none of them can move. In **starvation**, the system keeps running other transactions normally while one waiting transaction keeps getting skipped in line.
4. **Connect simple locking to 2PL:** Conclude any simple-locking critique by noting that early unlocking is fixed by the **Two-Phase Locking (2PL)** rule, which forbids unlocking any item until all needed locks have been acquired.
