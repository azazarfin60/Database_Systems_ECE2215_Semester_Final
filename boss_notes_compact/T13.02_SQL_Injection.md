# T13.2: SQL Injection: Mechanism and Prevention

> **Topic:** T13 · Security, Indexing & Hashing | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals · 9 marks
> **Sources:** Silberschatz 7e Ch. 9 (§9.8.1), Ch. 5 (§5.1.1.5)

---

## Root Cause of SQL Injection

**SQL Injection:** An SQL injection attack occurs when an attacker enters malicious SQL syntax into an application input field. The application concatenates this untrusted input into a dynamic SQL query string. The database parser executes the injected instructions as SQL commands rather than treating them as data.

The root cause of SQL injection is mixing application control code with untrusted user data via string concatenation:

```python
# Insecure dynamic query construction
query = "SELECT * FROM users WHERE username = '" + user_input + "'"
```

The database SQL parser receives a single combined text string. When untrusted input contains SQL syntax characters (such as `'`, `"`, `;`, or `--`), those characters break out of the literal string quotes. This mutates the query Abstract Syntax Tree (AST), making the database execute commands the developer never planned.

---

## How SQL Injection Works: Common Scenarios

### 1. Authentication Bypass via Tautology (`OR '1'='1'`)

Suppose an application checks user logins:

```sql
SELECT * FROM users WHERE username = '<user_input>';
```

- **Attacker Input:** `' OR '1'='1`
- **Resulting SQL Query:**
  ```sql
  SELECT * FROM users WHERE username = '' OR '1'='1';
  ```
- **How It Operates:**
  1. The leading single quote closes the username literal early.
  2. The injected `OR '1'='1'` condition is a tautology (always evaluates to `TRUE`).
  3. The entire `WHERE` clause evaluates to `TRUE` for every row in the table.
  4. The query returns all records in the table, bypassing authentication.

### 2. Stacked Queries (Piggybacked Destructive Commands)

When database drivers allow multiple semicolon-separated statements in a single call:

```sql
SELECT * FROM orders WHERE order_id = '<user_input>';
```

- **Attacker Input:** `'; DROP TABLE orders; -- `
- **Resulting SQL Query:**
  ```sql
  SELECT * FROM orders WHERE order_id = ''; DROP TABLE orders; -- ';
  ```
- **How It Operates:**
  1. The single quote closes the `order_id` literal.
  2. The semicolon finishes the first `SELECT` statement.
  3. The engine executes the injected `DROP TABLE orders` statement.
  4. The double hyphen `-- ` comments out the trailing quotation mark, preventing syntax errors.

### 3. Comment-Out Authentication Bypass (`admin' -- `)

```sql
SELECT * FROM students WHERE username = '<user_input>' AND password = '<password>';
```

- **Attacker Input (Username):** `admin' -- `
- **Resulting SQL Query:**
  ```sql
  SELECT * FROM students WHERE username = 'admin' -- ' AND password = '...';
  ```
- **How It Operates:** The `-- ` sequence comments out the rest of the query. The database checks only whether `username = 'admin'`, ignoring the password check completely.

## Technical Precautions and Countermeasures

### 1. Prepared Statements (Parameterized Queries)

**Prepared Statement:** A prepared statement is a precompiled SQL query template using placeholders (`?`). The database compiles the query structure first, binding runtime values strictly as literal data.

Prepared statements are the primary defense against SQL injection. They separate code from data using a two-phase process:

1. **Pre-compilation Phase:** The application sends the parameterized SQL statement to the database before inserting user values. The database parses and compiles the AST structure.
2. **Literal Parameter Binding Phase:** User inputs are transmitted out-of-band as typed values into the placeholder slots.
3. **Security Guarantee:** Even if an input string contains `' OR '1'='1` or `; DROP TABLE`, the engine never re-parses the AST. The database looks for a literal string matching those exact characters.

#### Java JDBC Implementation

```java
// SECURE: PreparedStatement with parameterized values
String sql = "SELECT * FROM instructor WHERE name = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, user_input);
ResultSet rs = pstmt.executeQuery();
```

#### Python DB-API Implementation

```python
# SECURE: Database driver binds parameters separately
sql = "SELECT * FROM instructor WHERE name = %s"
cursor.execute(sql, (user_input,))
records = cursor.fetchall()
```

### 2. Input Validation and Whitelisting

- **Strict Type Conversion:** Convert inputs to integers, floats, or dates before building queries. Non-numeric input for an integer field fails immediately before hitting the database.
- **Identifier Allowlisting:** Placeholders (`?`) bind data values only. They cannot bind table names, column names, or sort orders (`ASC`/`DESC`). Validate dynamic identifiers against a hardcoded allowlist:

```java
Set<String> validColumns = Set.of("ID", "name", "dept_name", "salary");
if (!validColumns.contains(sortColumn)) {
    throw new IllegalArgumentException("Invalid sort column");
}
String sql = "SELECT * FROM instructor ORDER BY " + sortColumn;
```

### 3. Enforcing Least Privilege

Configure database user accounts with minimal necessary permissions:
- Application connections should use accounts with `SELECT`, `INSERT`, or `UPDATE` privileges only.
- Never use administrative accounts (`root`, `sa`, `DBA`) for application connections.
- Revoke DDL rights (`DROP TABLE`, `ALTER TABLE`, `GRANT`) from application accounts.

### 4. Parameterized Stored Procedures

Wrap SQL operations in stored procedures with typed parameters:

```sql
DELIMITER //
CREATE PROCEDURE GetInstructor(IN p_name VARCHAR(50))
BEGIN
    SELECT * FROM instructor WHERE name = p_name;
END //
DELIMITER ;
```

Input passed into typed parameters cannot alter the procedure query structure.

### 5. Suppressing Detailed Database Errors

Disable verbose database error output to clients. Stack traces and database dialect messages help attackers map schemas. Display generic error messages to users and log errors privately.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2021 Q.8(b) / 2020 Q.4(a) · SQL Injection: Definition, Mechanism, and Prevention · 05 Marks

> *Section B / Section A · Asked in: 2021 Q.8(b) (05 marks), 2020 Q.4(a) (04 marks) · L2 Merge*

**Question (2021 Q.8(b)).** What is SQL injection attack? Describe the precautions that should be taken to prevent this attack.

**Question (2020 Q.4(a)).** What is an SQL injection attack? Explain how it works and what precautions must be taken to prevent SQL injection attack.

**Answer.**

**1. What is an SQL Injection Attack?**  
An **SQL injection attack** occurs when an attacker inputs malicious SQL commands into an application input field. The application concatenates this untrusted input directly into a dynamic SQL query string. The database parser interprets the malicious input as SQL instructions rather than data. This allows the attacker to bypass authentication, read unauthorized data, or modify and delete tables.

**2. How It Works**  
Consider an application that builds a query using string concatenation:

```python
# Vulnerable query construction
query = "SELECT * FROM instructor WHERE name = '" + user_input + "'"
```

- **Scenario 1: Authentication Bypass / Data Dumping**
  - **Attacker input:** `' OR '1'='1`
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = '' OR '1'='1';
    ```
  - **Mechanism:** The quote closes the name literal. The `'1'='1'` condition is always true. The database returns all records in the `instructor` table.

- **Scenario 2: Destructive Attack (Piggybacked Query)**
  - **Attacker input:** `'; DROP TABLE student; -- `
  - **Resulting SQL:**
    ```sql
    SELECT * FROM instructor WHERE name = ''; DROP TABLE student; -- ';
    ```
  - **Mechanism:** The semicolon terminates the first query. The database engine executes the injected `DROP TABLE student` statement. The trailing `--` treats the remaining query syntax as a comment.

**3. Precautions to Prevent SQL Injection**  

1. **Use Prepared Statements (Parameterized Queries):**
   This is the primary defense. The application precompiles the SQL query structure with placeholders. User input is bound separately as data parameters. The parser never executes parameter content as SQL commands.
   ```python
   # Secure parameterized query
   cursor.execute("SELECT * FROM instructor WHERE name = %s", (user_input,))
   ```
   In Java/JDBC, use `PreparedStatement` with `?` markers and `setString()`.

2. **Input Validation and Whitelisting:**
   Validate data types, lengths, and patterns before passing them to queries. For dynamic query parts like table or column names that cannot use parameters, check input against an explicit whitelist of allowed identifiers.

3. **Enforce Least Privilege:**
   Configure database user accounts with minimal necessary privileges. A public web application account should only have `SELECT` or `INSERT` access. It must never have administrative permissions like `DROP TABLE` or `GRANT`.

4. **Use Parameterized Stored Procedures:**
   Wrap database operations inside stored procedures with typed parameters. Do not concatenate dynamic SQL inside the stored procedure body.

5. **Suppress Database Error Messages:**
   Hide internal database error details, table names, and stack traces from end users. Display generic error pages instead.

*Variant for 2020 Q.4(a) (4 marks):* Provide the definition, the `' OR '1'='1` exploit example, and the three core precautions: prepared statements, input validation, and least privilege.

## ⚡ Exam Tips & Common Mistakes

- **Always Provide a Query Example:** Do not stop at a written definition. Write out the vulnerable string concatenation, the attacker input, and the resulting SQL string with `' OR '1'='1`.
- **Explain Two-Phase Compilation:** Scores increase when you explain that prepared statements pre-compile the SQL syntax tree before binding values as literal data.
- **Client-Side Validation Is Not Enough:** Note that browser-based validation (JavaScript checks) can be bypassed with tools like curl. Server-side prepared statements are required.
- **SQL Injection vs. XSS:** SQL injection attacks the backend database parser. Cross-Site Scripting (XSS) attacks the victim browser.
