# T11.05: Multiple Granularity Locking Protocol

> **Topic:** T11 · Concurrency Control Protocols | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (0 marks; Explicit in RUET Syllabus Unit 4)
> **Sources:** Silberschatz 7e Ch. 18 (§18.3, pp. 854–857) · Gray et al. (1975) · Lecture Deck 08

---

## The Granularity Hierarchy Tree

**Granularity:** The size of the data item that the lock manager locks, such as a single record, a file, an area, or the entire database. Fine granularity (locking records) allows high concurrency but creates large locking overhead. Coarse granularity (locking tables or databases) lowers lock overhead but reduces concurrency.

**Intention Lock Modes:** Locks placed on ancestor nodes in a hierarchy tree ($IS, IX, SIX$) before locking child nodes. They warn other transactions that fine-grained locking is active below.

**Lock Escalation:** A process where the lock manager converts many fine-grained locks into a single coarse-grained lock to save lock table memory.

A multiple granularity database organizes lockable units as a tree hierarchy:

```text
                  +-----------------------+
                  |     Database (DB)     |  (Coarsest Granularity)
                  +-----------+-----------+
                              |
                +-------------+-------------+
                |                           |
        +-------v-------+           +-------v-------+
        |    Area A1    |           |    Area A2    |
        +-------+-------+           +---------------+
                |
        +-------+-------+
        |               |
  +-----v-----+   +-----v-----+
  |  File Fa  |   |  File Fb  |  (Relations / Tables)
  +-----+-----+   +-----------+
        |
   +----+----+----+
   |         |    |
+--v---+  +--v---+ +--v---+
| ra1  |  | ra2  | | ran  |      (Records / Tuples - Finest Granularity)
+------+  +------+ +------+
```

### Implicit vs. Explicit Locking

- **Explicit Locking:** A transaction explicitly requests a lock on node $Q$ (for example, requesting an $X$ lock on record $r_{a1}$).
- **Implicit Locking:** When a transaction locks a node $Q$ in shared ($S$) or exclusive ($X$) mode, it **implicitly locks all descendant nodes** of $Q$ in that same mode. For example, locking File $F_a$ in exclusive mode ($X$) implicitly grants an exclusive lock on every record inside $F_a$.

---

## Why Intention Locks Are Mandatory

Suppose transaction $T_1$ acquires an explicit exclusive lock on a single record $r_{a1}$ inside File $F_a$.
Another transaction $T_2$ arrives and wants to lock the entire File $F_a$ in shared mode to calculate an aggregate sum:

- **Without Intention Locks:** The lock manager would have to traverse the entire subtree of $F_a$, checking every record to see if any lock is held. In a table with millions of rows, this search causes severe performance degradation.
- **With Intention Locks:** Before $T_1$ locks record $r_{a1}$, it must first tag every ancestor of $r_{a1}$ (File $F_a$, Area $A_1$, and Database) with an **Intention-Exclusive ($IX$) lock**.
- When $T_2$ requests an $S$ lock on File $F_a$, the manager inspects node $F_a$ directly. Seeing the existing $IX$ lock held by $T_1$, the manager catches the conflict instantly at the file level without scanning a single record!

---

## Intention Lock Modes: IS, IX, and SIX

In addition to standard Shared ($S$) and Exclusive ($X$) modes, the protocol defines three intention lock modes:

### 1. Intention-Shared ($IS$) Mode
- **Meaning:** Explicit locking is currently active at a lower level of the tree using **shared ($S$) locks**.
- **Use Case:** A transaction plans to read specific records inside a table. It places $IS$ locks on the Database and Table, and then places $S$ locks on the specific records.

### 2. Intention-Exclusive ($IX$) Mode
- **Meaning:** Explicit locking is active at a lower level of the tree using **exclusive ($X$) locks or mixed ($S$ and $X$) locks**.
- **Use Case:** A transaction plans to update specific records. It places $IX$ locks on ancestors, and then places $X$ locks on target records.

### 3. Shared and Intention-Exclusive ($SIX$) Mode
- **Meaning:** The subtree rooted at this node is locked **explicitly in shared ($S$) mode**, and simultaneously, explicit locking is being conducted at lower levels with **exclusive ($X$) locks**.
- **Use Case:** A transaction reads an entire table (e.g., scanning all employee records) and selectively updates a few matching records.
- **Efficiency:** The $SIX$ lock on the table allows scanning all records implicitly without separate tuple locks, while taking explicit $X$ locks only on the few updated tuples.

> [!NOTE]
> **Why $XIS$ Mode Does Not Exist:**  
> An exclusive lock ($X$) on node $Q$ already grants total exclusive access to read and write all descendants. Adding intention to read below provides zero additional privileges. Therefore, $XIS \equiv X$.

## The $5 \times 5$ Lock-Compatibility Matrix

| Requested Mode $\downarrow$ \ Held Mode $\to$ | $IS$ | $IX$ | $S$ | $SIX$ | $X$ |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$IS$** | **True** | **True** | **True** | **True** | False |
| **$IX$** | **True** | **True** | False | False | False |
| **$S$** | **True** | False | **True** | False | False |
| **$SIX$** | **True** | False | False | False | False |
| **$X$** | False | False | False | False | False |

### Matrix Derivation Rules

The matrix is completely **symmetric**:
- **$IS$ Row:** Compatible with $IS, IX, S, SIX$. Only conflicts with $X$ because $X$ demands complete exclusivity over the whole subtree.
- **$IX$ Row:** Compatible with $IS$ and $IX$ (two transactions updating different records can run together; tuple-level locks catch item clashes). Conflicts with $S, SIX,$ and $X$.
- **$S$ Row:** Compatible with $IS$ and $S$ (readers never conflict with readers). Conflicts with $IX, SIX,$ and $X$.
- **$SIX$ Row:** Compatible only with $IS$ (readers below do not conflict with the broad read). Conflicts with $IX, S, SIX,$ and $X$.
- **$X$ Row:** Incompatible with all modes.

---

## Multiple Granularity Locking Protocol Rules

To guarantee serializability, every transaction $T_i$ must follow five mandatory rules:

1. **Matrix Compliance:** The $5 \times 5$ lock-compatibility matrix must be observed.
2. **Root First:** The root of the tree must be locked first in any mode.
3. **Top-Down Acquisition Rule:**
   - A node $Q$ can be locked in $S$ or $IS$ mode only if its parent is held in $IX$ or $IS$ mode.
   - A node $Q$ can be locked in $X, SIX,$ or $IX$ mode only if its parent is held in $IX$ or $SIX$ mode.
4. **Two-Phase Rule:** A transaction cannot acquire any new lock after releasing any lock.
5. **Bottom-Up Unlock Rule:** A node $Q$ can be unlocked only if **none of its children are currently locked** by that transaction.

```text
Lock Acquisition: TOP-DOWN (Root -> Area -> File -> Record)
=============================================================>
      [Database]  --locks first-->  IS or IX
          |
       [Area]     --locks next--->  IS or IX
          |
       [File]     --locks next--->  IS or IX (or S/X/SIX)
          |
      [Record]    --locks last--->  S or X

<=============================================================
Lock Release:     BOTTOM-UP (Record -> File -> Area -> Database)
```

## 🔮 Likely Questions

### 🎯 LQ1 · Multiple Granularity Locking Compatibility Matrix and Intention Modes · [04 Marks]

> *Expected Exam Format · 4 Marks (RUET Syllabus Unit 4)*

**Question.** Explain the purpose of multiple granularity locking. Draw the $5 \times 5$ lock-compatibility matrix for $IS, IX, S, SIX,$ and $X$ modes, and explain why $SIX$ is compatible with $IS$ but incompatible with $IX$.

**Answer.**

**1. Purpose of Multiple Granularity Locking:**
Multiple granularity locking organizes data items into a tree hierarchy (Database $\to$ Area $\to$ File $\to$ Record). It allows fine-grained transactions (updating single records) to run alongside coarse-grained transactions (scanning whole tables) without excessive lock table overhead or unnecessary full-table locking.

**2. The $5 \times 5$ Compatibility Matrix:**

| Requested Mode $\downarrow$ \ Held Mode $\to$ | $IS$ | $IX$ | $S$ | $SIX$ | $X$ |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$IS$** | **True** | **True** | **True** | **True** | False |
| **$IX$** | **True** | **True** | False | False | False |
| **$S$** | **True** | False | **True** | False | False |
| **$SIX$** | **True** | False | False | False | False |
| **$X$** | False | False | False | False | False |

**3. Compatibility Justification ($SIX$ with $IS$ vs. $IX$):**
- **$SIX$ with $IS$ is Compatible (`True`):** A $SIX$ lock explicitly locks the entire subtree in shared ($S$) mode while updating some records below. An incoming $IS$ transaction only plans to read specific records below. Since readers do not conflict with readers, concurrent reads are safe. Any conflict on a modified record is caught at the tuple level.
- **$SIX$ with $IX$ is Incompatible (`False`):** A transaction holding $SIX$ is actively reading the entire table under an implicit shared lock. If an incoming transaction were granted $IX$, it would update records below, modifying data that the $SIX$ transaction is reading. This would cause unrepeatable reads and dirty data.

### 🎯 LQ2 · Top-Down Acquisition, Bottom-Up Release, and Lock Design · [04 Marks]

> *Expected Exam Format · 4 Marks*

**Question.** Why must lock acquisition be top-down and lock release bottom-up in multiple granularity locking? What locking sequence should a transaction follow if it reads all records in relation $R$ and updates 2% of them?

**Answer.**

**1. Why Acquisition Is Top-Down and Release Is Bottom-Up:**
- **Top-Down Acquisition (Root to Leaf):** Intention locks must be placed on ancestor nodes before locking child nodes. If a child were locked first, another transaction could acquire an incompatible coarse-grained lock on the parent because no intention lock was visible, causing an undetected conflict.
- **Bottom-Up Release (Leaf to Root):** A parent node cannot be unlocked while its children are still locked. If the parent were unlocked early, another transaction could lock the parent in an incompatible mode, breaking the isolation of active child locks.

**2. Optimal Lock Sequence for Table Scan with 2% Updates:**
For a transaction scanning relation $R$ and updating 2% of records:
- On Database and Area: Acquire **$IX$ locks**.
- On Relation $R$: Acquire a **$SIX$ (Shared and Intention-Exclusive) lock**.
  - *Advantage:* The explicit $S$ mode permits scanning all records without requesting thousands of individual tuple-level shared locks.
- On Updated Records: Acquire individual **$X$ locks** on only the 2% of tuples being modified.

## ⚡ Exam Tips & Common Mistakes

- **Top-Down vs. Bottom-Up Direction:**
  - Lock Acquisition = **Top-Down** (Root $\to$ Leaf).
  - Lock Release = **Bottom-Up** (Leaf $\to$ Root).
  Reversing either order breaks hierarchical locking and loses marks.
- **Matrix Symmetry:** The $5 \times 5$ matrix is completely symmetric: $\text{Matrix}[A, B] = \text{Matrix}[B, A]$. Use this to verify your table in the exam.
- **The $SIX$ Cell Rule:** Aside from the diagonal, $SIX$ is compatible **only with $IS$**. It conflicts with $IX, S, SIX,$ and $X$.
- **Define Lock Escalation:** Be prepared to define lock escalation in 1–2 sentences: replacing many row locks with a single table lock when lock table memory is full.
