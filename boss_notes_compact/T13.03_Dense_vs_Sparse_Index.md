# T13.3: Ordered Indexing: Dense vs. Sparse Index and B+-Trees

> **Topic:** T13 · Security, Indexing & Hashing | **Priority:** 🟢 Low | **Exam Frequency:** 1/7 finals · 2 marks
> **Sources:** Silberschatz 7e Ch. 14 (§14.1, §14.2, §14.3)

---

## Fundamentals of Database Indexing

**Index Entry:** An index entry (or index record) consists of a search-key value and one or more pointers to the disk block and offset where matching data records reside.

Indices speed up record retrieval, avoiding slow full-table scans. Four core concepts define ordered indices:

1. **Search Key:** Any attribute or set of attributes used to look up records in a file. A search key does not need to be a candidate key.
2. **Clustering Index (Primary Index):** An index built on the attribute that defines the physical storage order of the data file. A table can have at most one clustering index.
3. **Non-Clustering Index (Secondary Index):** An index built on an attribute other than the physical sort order. A table can have multiple secondary indices.
4. **Ordered Index:** An index where search keys are stored in sorted order.

---

## Dense Indices: Structure and Mechanics

**Dense Index:** An index structure that contains an index record for every search-key value in the data file. To find a record, the database looks up the search key directly in the index and follows its pointer.

![Dense index on instructor file with search key ID](diagrams/T13.03_dense_index__TB_fig_14_02.jpg)
*Figure 13.2: Dense clustering index on the instructor file sorted by ID (Source: Textbook Ch. 14, Fig. 14.2).*

### Operational Mechanics

- **On Sorted Files (Clustering):** The index entry points to the first record with that search-key value. Subsequent identical keys sit contiguously in the block.
- **On Unsorted Files (Secondary Index):** The index entry stores pointers to all records with that search-key value. All secondary indices must be dense.
- **Lookup Process:** The engine conducts a binary search on the index for key $K$, finding the entry and following its pointer directly to disk.
- **Advantages:** Fast lookups. The engine verifies key existence without reading the data file.
- **Disadvantages:** Large storage overhead. Frequent record inserts and deletes require updating index entries.

---

## Sparse Indices: Structure and Mechanics

**Sparse Index:** An index structure that contains index records for only some search-key values (typically one entry per disk block). A sparse index strictly requires the data file to be ordered on the search key.

![Sparse index on instructor file with search key ID](diagrams/T13.03_sparse_index__TB_fig_14_03.jpg)
*Figure 13.3: Sparse clustering index on the instructor file sorted by ID (Source: Textbook Ch. 14, Fig. 14.3).*

### Why Sparse Indices Require Sorted Files

In a sparse index, the engine finds key $K$ by locating the largest index key $K_i \le K$, following that pointer, and scanning the block sequentially. This scan works only if records are physically sorted between $K_i$ and the next index key. If the file were unordered, target records could reside in any block, making sparse indexing impossible.

### One Entry Per Disk Block

Reading a disk block into memory takes milliseconds, while scanning records in RAM takes microseconds. Storing one sparse index entry per disk block minimizes index size while guaranteeing that finding any record takes at most one data-block read.

### Operational Trade-offs

- **Advantages:** Compact size. The index often fits entirely in main memory. Low maintenance cost on insertions and deletions within blocks.
- **Disadvantages:** Slower lookups due to sequential scanning inside data blocks. Cannot be used on secondary (unsorted) search keys.

---

## Side-by-Side Comparison: Dense vs. Sparse Index

| Feature | Dense Index | Sparse Index |
| :--- | :--- | :--- |
| **Index Entries** | One entry for every search-key value in the file. | One entry for only some search-key values (usually one per disk block). |
| **Lookup Speed** | Faster. Locates the exact record or its list of duplicates directly. | Slower. Requires an index lookup followed by a sequential block scan. |
| **Space Overhead** | Large. The index file consumes significant disk or memory space. | Small. The index file is much smaller and often fits in main memory. |
| **File Ordering** | Can be built on sorted (clustering) or unsorted (non-clustering) files. | Requires the data file to be ordered on the search key (clustering only). |
| **Maintenance Cost** | High. Insertions and deletions often require adding or removing index entries. | Low. Records can often be inserted or deleted inside a block without updating the index. |

## Multilevel Indices and B+-Tree Architecture

When files grow to millions of rows, even a sparse index exceeds memory capacity. Binary searching an index across $b$ disk blocks requires:

$$
\lceil \log_2(b) \rceil
$$

random disk reads. A **multilevel index** treats the original index as a data file and builds a sparse index on top of it.

**B+-Tree:** A B+-tree is a self-balancing multilevel index where all leaf nodes reside at equal depth. Leaf nodes form a dense index linked sequentially, while internal nodes form a multilevel sparse index.

![B+-tree for instructor file with fanout n = 4](diagrams/T13.03_b_plus_tree__TB_fig_14_09.jpg)
*Figure 13.4: Complete balanced B+-tree index on the instructor file with fanout n = 4 (Source: Textbook Ch. 14, Fig. 14.9).*

### B+-Tree Node Structure

A node holds up to $n$ pointers and $n - 1$ search keys (where $n$ is the node fanout):

1. **Leaf Nodes:** Store every search key in sorted order. Pointers $P_1, \dots, P_{n-1}$ point to data records. The final pointer $P_n$ points to the next sibling leaf node, enabling rapid range scans (`BETWEEN`) without climbing the tree.
2. **Internal Nodes:** Route searches down the tree. For search key $K$, pointer $P_1$ addresses keys $< K_1$, pointer $P_i$ addresses keys in $[K_{i-1}, K_i)$, and pointer $P_m$ addresses keys $\ge K_{m-1}$.
3. **Balanced Growth:** Nodes split when they exceed $n - 1$ keys, pushing median keys to parent nodes. The tree grows taller only when the root splits, keeping all leaves at identical depth.

### 🎯 GQ1 · 2023 Q.8(a) · Short Note on Dense and Sparse Index · 02 Marks

> *Section B · Asked in: 2023 (02 marks)*

**Question (2023 Q.8(a)).** Write short note on dense and sparse index.

**Answer.**

**1. Definitions**  
- **Dense Index:** An index that contains an index record for **every** search-key value in the data file. To find a record, the system looks up the search key directly in the index and follows its pointer.
- **Sparse Index:** An index that contains index records for only **some** search-key values (typically one entry per disk block). The data file **must be sorted** on the search key. To find a record, the system finds the largest index key less than or equal to the target value, then scans the data block sequentially.

## ⚡ Exam Tips & Common Mistakes

- **File Ordering Prerequisite:** Never say a sparse index works on unsorted files. A sparse index strictly requires the data file to be sorted on the search key.
- **Secondary Indices Are Always Dense:** Secondary indices index attributes different from the physical file order, so they must be dense.
- **Block-Level Design:** Mention that setting one sparse index entry per disk block is standard practice, trading microsecond memory scans for minimal index size.
- **B+-Tree Chaining:** Remember that leaf nodes in B+-trees include pointer $P_n$ to chain leaves, making range queries efficient.
