## View Dependencies and View Expansion

**View Expansion:** View expansion is a query rewrite transformation where the DBMS replaces a view name with its stored `SELECT` query definition until the query refers only to physical base relations.

Because views act like virtual relations, you can define one view on top of another view:
- **Direct Dependency ($v_1 \to v_2$):** View $v_1$ directly depends on $v_2$ if $v_2$ appears in the `FROM` clause of $v_1$.
- **Transitive Dependency:** View $v_1$ depends on $v_3$ if there is a chain of views linking them ($v_1 \to v_2 \to v_3$).
- **Recursive Views:** A view is recursive if it depends on itself, either directly or transitively.

### View Expansion Mechanism
When a user queries a view, the query processor substitutes the view name with its stored subquery:

```sql
CREATE VIEW ece_courses AS
SELECT course_id, title, credits FROM course WHERE dept_name = 'ECE';

CREATE VIEW ece_3credit_courses AS
SELECT course_id, title FROM ece_courses WHERE credits = 3;
```

When a user executes `SELECT * FROM ece_3credit_courses;`, the engine expands `ece_courses`:

```sql
SELECT course_id, title
FROM (
    SELECT course_id, title, credits
    FROM course
    WHERE dept_name = 'ECE'
) AS ece_courses
WHERE credits = 3;
```

The optimizer then flattens this subquery into a single scan on base relation `course` with `WHERE dept_name = 'ECE' AND credits = 3`.

## Updatable Views: Rules, Ambiguities, and Constraints

**Updatable View:** An updatable view is a view that allows `INSERT`, `UPDATE`, and `DELETE` operations to translate directly and unambiguously into modifications on an underlying base table.

### 1. Update Ambiguity and Insertion Anomalies
Modifying a view requires mapping changes back to base tables. Consider a view joining `instructor` and `department`:

```sql
CREATE VIEW instructor_info AS
SELECT ID, name, building
FROM instructor, department
WHERE instructor.dept_name = department.dept_name;
```

Attempting an insert through this view causes ambiguity:

```sql
INSERT INTO instructor_info
VALUES ('69987', 'White', 'Taylor');
```

Roadblocks:
1. The DBMS cannot determine White's `dept_name` if multiple departments occupy the `'Taylor'` building.
2. If no department exists in `'Taylor'`, inserting into `department` requires inventing primary keys.
3. If base tuples are inserted with nulls, the join predicate `instructor.dept_name = department.dept_name` evaluates to unknown on `NULL = NULL`. The inserted record fails to appear in the view!

### 2. The 4 SQL Standard Conditions for Updatable Views
Under standard SQL, a view permits `INSERT`, `UPDATE`, and `DELETE` only when every view tuple maps to exactly one base relation tuple. All four conditions must hold:
1. **Single Table in FROM:** The `FROM` clause contains only one base relation (no joins, unions, or subqueries).
2. **Simple Attributes in SELECT:** The `SELECT` list contains only column names (no expressions, calculations, aggregate functions, or `DISTINCT`).
3. **Nullable Missing Columns:** Any column of the base table omitted from the `SELECT` list permits `NULL` values or has a defined `DEFAULT`.
4. **No Grouping:** The query contains no `GROUP BY` or `HAVING` clause.

### 3. The WITH CHECK OPTION Clause
By default, SQL permits updates through an updatable view that cause the updated row to violate the view's `WHERE` predicate, making the row vanish from subsequent view queries.

To prevent rows from vanishing, append `WITH CHECK OPTION`:
```sql
CREATE VIEW history_instructors AS
SELECT *
FROM instructor
WHERE dept_name = 'History'
WITH CHECK OPTION;
```
With this option enabled, the DBMS tests every inserted or updated tuple against `dept_name = 'History'`. If the test fails, the DBMS rejects the operation with an error.

### 4. INSTEAD OF Triggers
For complex views that join multiple tables, database systems provide `INSTEAD OF` triggers. The trigger intercepts `INSERT`, `UPDATE`, or `DELETE` statements on the view and executes custom SQL statements to modify underlying base tables cleanly.

## Materialized Views vs. Standard Virtual Views

**Materialized View:** A materialized view is a view whose query result is precomputed and physically stored on disk like an actual table. The DBMS refreshes stored rows when base tables change.

### 1. View Maintenance Strategies
Keeping materialized view rows synchronized with base tables is called view maintenance:
1. **Immediate (Eager) Maintenance:** The DBMS updates the materialized view within the same transaction that modifies base relations. Read queries always see fresh data, but write operations on base tables become slower.
2. **Deferred (Lazy) Maintenance:** The view is marked stale when base tables change, and recomputed when a user queries it.
3. **Periodic (Snapshot) Maintenance:** The view refreshes on a fixed timer schedule (such as hourly or nightly). This suits OLAP and data warehousing where minor data staleness is acceptable.

### 2. Comparison Matrix

| Architectural Feature | Standard Virtual View | Materialized View |
| :--- | :--- | :--- |
| **Physical Storage** | None (stores only query text in catalog) | Stored physically on disk as a table |
| **Query Performance** | Slower (evaluates query on demand) | Very fast (reads precomputed data) |
| **Data Freshness** | Always 100% current and fresh | May be stale depending on refresh policy |
| **Write Overhead** | Zero overhead on base table updates | High overhead (triggers view maintenance) |
| **Ideal Use Case** | Security masking, query abstraction | OLAP, analytics, data warehousing |

## 🔮 Likely Questions (High-Probability RUET Exam Blueprint)

### 🎯 LQ1 · Conditions for Updatable Views in SQL · 04 Marks

> *Section B · Likely Question · Estimated Marks: 4 Marks*

**Question.** Under what conditions is an SQL view updatable? Explain why updates cannot be performed on views defined with aggregations or multi-table joins.

**Answer.**

#### 1. SQL Standard Conditions for an Updatable View
In SQL, an `INSERT`, `UPDATE`, or `DELETE` operation can be performed through a view only if all four conditions are satisfied:
1. The `FROM` clause references only one base table.
2. The `SELECT` clause contains only column names without expressions, calculated fields, aggregate functions, or the `DISTINCT` keyword.
3. Any base table column omitted from the `SELECT` clause permits `NULL` values (i.e., it is not defined as `NOT NULL` or `PRIMARY KEY` without a default).
4. The query does not contain a `GROUP BY` or `HAVING` clause.

#### 2. Why Updates Fail on Aggregated Views
Consider a view defined as:
```sql
CREATE VIEW dept_avg AS
SELECT dept_name, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name;
```
If a user updates `avg_salary` to 85,000 for the `'Comp. Sci.'` department, the DBMS cannot determine how to adjust individual instructor salaries. Many different combinations of individual salary changes produce an average of 85,000. Because no unique inverse mapping exists, the operation is prohibited.

#### 3. Why Updates Fail on Multi-Table Join Views
In a join view combining `instructor` and `department`, inserting a record with a new department building requires inserting `NULL` values into unspecified base columns. The resulting base tuples fail to satisfy the join predicate, preventing the inserted row from appearing in the view.

### 🎯 LQ2 · Virtual Views vs. Materialized Views and View Maintenance · 04 Marks

> *Section B · Likely Question · Estimated Marks: 4 Marks*

**Question.** Distinguish between a standard virtual view and a materialized view. Discuss the trade-offs involved in maintaining a materialized view.

**Answer.**

#### 1. Comparison
- **Standard Virtual View:** A virtual relation defined by an SQL query. The DBMS stores only the query specification in the data dictionary. Every time the view is referenced, the query processor substitutes the stored definition and computes the result dynamically. It consumes no disk space for data.
- **Materialized View:** A view whose query result is computed and physically stored on disk like an actual table. Queries against a materialized view execute rapidly because the DBMS reads precomputed rows directly without re-evaluating joins or aggregations.

#### 2. Trade-Offs and Maintenance Strategies
Materializing a view trades database write performance and storage space for query read speed:
- **Query Acceleration:** Accelerates complex decision-support and data warehousing queries that aggregate large volumes of rows.
- **Storage Cost:** Consumes physical disk storage for tuples and indexes.
- **Update Overhead:** When base relations are modified, the materialized view must be refreshed:
  - *Immediate Maintenance:* Updates the view immediately upon base table modification. This keeps data strictly consistent but increases write latency.
  - *Lazy / Periodic Maintenance:* Refreshes the view on access or at scheduled intervals. This reduces write overhead but leaves data temporarily stale.

### 🎯 LQ3 · View Expansion and Nested View Resolution · 03 Marks

> *Section B · Likely Question · Estimated Marks: 3 Marks*

**Question.** What is view expansion? Show how the DBMS expands a query on a view defined over another view using an example.

**Answer.**

#### 1. Concept of View Expansion
**View expansion** is a query rewriting transformation performed by the DBMS query processor. It replaces view references in a user query with their underlying SQL query definitions. This process recurses until the entire query is expressed purely in terms of physical base relations.

#### 2. Concrete Example
Assume a base view `physics_fall_2017`:
```sql
CREATE VIEW physics_fall_2017 AS
SELECT course.course_id, sec_id, building, room_number
FROM course, section
WHERE course.course_id = section.course_id
  AND course.dept_name = 'Physics'
  AND section.semester = 'Fall'
  AND section.year = 2017;
```

A second view `physics_watson` is defined over `physics_fall_2017`:
```sql
CREATE VIEW physics_watson AS
SELECT course_id, room_number
FROM physics_fall_2017
WHERE building = 'Watson';
```

When a user executes `SELECT * FROM physics_watson;`, the query processor expands the view definition:

```sql
SELECT course_id, room_number
FROM (
    SELECT course.course_id, sec_id, building, room_number
    FROM course, section
    WHERE course.course_id = section.course_id
      AND course.dept_name = 'Physics'
      AND section.semester = 'Fall'
      AND section.year = 2017
) AS physics_fall_2017
WHERE building = 'Watson';
```
The query optimizer flattens this subquery, producing an execution plan that scans `course` and `section` directly.

## ⚡ Exam Tips & Common Mistakes

- **The Four Updatable View Rules:** Memorize the 4 conditions: single table in `FROM`, simple attributes in `SELECT`, nullable missing columns, no `GROUP BY` or `HAVING`.
- **WITH CHECK OPTION Purpose:** It ensures that updates or inserts through a view satisfy the view's `WHERE` clause, preventing tuples from silently disappearing.
- **MySQL Limitation:** Standard MySQL does not natively support automated materialized views. Developers simulate them using scheduled tables and triggers.
- **View Expansion Timing:** View expansion is a compile-time syntactic rewrite that happens before query optimization and execution.
