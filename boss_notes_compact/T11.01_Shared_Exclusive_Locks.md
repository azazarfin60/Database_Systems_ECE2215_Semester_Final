# T11.01: Shared and Exclusive Locks & Compatibility Matrix

> **Topic:** T11 · Concurrency Control Protocols | **Priority:** 🟠 | **Exam Frequency:** 0/7 finals (0 marks; Starvation tested in 2017 Q.7(a))
> **Sources:** Silberschatz 7e Ch. 18 (§18.1.1–18.1.2, pp. 835–841) · Lecture Deck 08 (Slides 9–12) · Raidah Notes (p. 28, 30)

---

## Lock Modes: Shared (S) and Exclusive (X)

**Shared-Mode Lock (`lock-S`):** A lock requested with `lock-S(Q)` that gives a transaction read-only access to data item $Q$. Multiple transactions can hold shared locks on $Q$ at the same time because reading never alters data.

**Exclusive-Mode Lock (`lock-X`):** A lock requested with `lock-X(Q)` that gives a transaction both read and write access to data item $Q$. Only one transaction can hold an exclusive lock on $Q$ at any time. No other transaction can hold any lock on $Q$ while an exclusive lock is active.

A transaction releases a held lock using the `unlock(Q)` instruction.

---

## The Lock-Compatibility Matrix

**Lock-Compatibility Function:** A rule that decides if transaction $T_i$ can obtain a mode $A$ lock on item $Q$ while transaction $T_j$ holds a mode $B$ lock on $Q$. Mode $A$ is compatible with mode $B$ only when both modes are Shared ($S$). Any combination involving an Exclusive ($X$) lock conflicts and forces the requesting transaction to wait.

| Requested Mode $\downarrow$ \ Held Mode $\to$ | Shared ($S$) | Exclusive ($X$) |
| :---: | :---: | :---: |
| **Shared ($S$)** | **True** (Compatible) | **False** (Conflict) |
| **Exclusive ($X$)** | **False** (Conflict) | **False** (Conflict) |

### Why Each Cell Operates This Way

- **$S$ requested while $S$ is held (`True`):** Readers never modify values. Letting multiple readers share the item maximizes concurrency safely.
- **$S$ requested while $X$ is held (`False`):** An active writer is modifying $Q$. Blocking the reader until the writer finishes prevents dirty reads.
- **$X$ requested while $S$ is held (`False`):** Other transactions are reading $Q$. Blocking the writer until active readers finish prevents unrepeatable reads.
- **$X$ requested while $X$ is held (`False`):** Two simultaneous writers would overwrite each other's data. Blocking the second writer prevents lost updates.

---

## Pitfalls of Simple Locking Protocols

In a simple (naive) locking protocol, a transaction acquires a lock right before accessing an item and unlocks it immediately after that single operation finishes.

Releasing locks early causes four major hazards (Lecture Deck 08, Slide 11):

1. **Serializability is not guaranteed:** Unlocking an item early allows other transactions to observe intermediate states.
2. **Irrecoverable schedules can occur:** Unlocking a modified item before committing lets other transactions read uncommitted values and commit first.
3. **Starvation can occur:** A transaction waiting for an $X$ lock can be bypassed endlessly by incoming $S$ lock requests.
4. **Deadlocks can occur:** Two transactions can each hold a lock that the other needs, causing a circular wait.

### Why Early Unlocking Breaks Serializability

If a transaction releases a lock on item $B$ before acquiring a lock on item $A$, concurrent transactions can interleave between the unlock and subsequent lock requests. An audit transaction can read the newly committed value of $B$ alongside the un-updated value of $A$, observing an inconsistent intermediate database state (such as seeing \$250 instead of \$300). Because naive locking allows locks to be released before all required locks are acquired, it fails to guarantee conflict serializability. Databases solve this by enforcing **Two-Phase Locking (2PL)**.

## Starvation and Fair Lock Scheduling

**Starvation:** A condition where a transaction waits indefinitely for a lock because the system repeatedly grants compatible locks to newer incoming transactions.

Writers are especially vulnerable to starvation by readers:

1. Transaction $T_2$ holds `lock-S(A)`.
2. Transaction $T_1$ arrives and requests `lock-X(A)`. Because $X$ conflicts with $S$, $T_1$ waits.
3. Transaction $T_3$ arrives and requests `lock-S(A)`. Because $S$ is compatible with $T_2$'s held $S$ lock, a naive manager grants `lock-S(A)` to $T_3$.
4. $T_2$ finishes and unlocks $A$, but $T_1$ still waits because $T_3$ holds $A$.
5. Before $T_3$ finishes, $T_4$ arrives and receives `lock-S(A)`.
6. As long as new readers overlap, $T_1$ waits forever and starves.

### Starvation Schedule Matrix (Lecture Deck 08, Slide 12)

| Time | $T_1$ (Needs $X$) | $T_2$ | $T_3$ | $T_4$ | Lock State of $A$ |
| :--: | :--- | :--- | :--- | :--- | :--- |
| 1 | | $\text{lock-S}(A)$ | | | Held by $T_2$ ($S$) |
| 2 | $\text{lock-X}(A)$ **[WAIT]** | | | | $T_1$ waits for $T_2$ |
| 3 | | | $\text{lock-S}(A)$ | | Granted to $T_3$ ($S$) |
| 4 | | $\text{unlock}(A)$ | | | Still held by $T_3$ ($S$) |
| 5 | | | | $\text{lock-S}(A)$ | Granted to $T_4$ ($S$) |
| 6 | | | $\text{unlock}(A)$ | | Still held by $T_4$ ($S$) |
| 7 | | | | $\text{unlock}(A)$ | Lock becomes free |
| 8 | $\text{Grant}(\text{lock-X}(A))$ | | | | Granted to $T_1$ |

If new readers keep arriving before Step 7, Step 8 never happens.

### How the Lock Manager Prevents Starvation

The lock manager eliminates starvation using a **First-Come, First-Served (FIFO) queue** with two granting conditions:

When transaction $T_i$ requests a mode $A$ lock on item $Q$, the manager grants the lock if and only if:
1. No other transaction holds a lock on $Q$ that conflicts with mode $A$.
2. **No other transaction is already waiting in the queue for $Q$ with a conflicting request that arrived before $T_i$.**

Under Rule 2, once $T_1$ queues its request for `lock-X(A)`, later readers like $T_3$ and $T_4$ must wait behind $T_1$. Once $T_2$ unlocks $A$, $T_1$ gets its exclusive lock immediately.

## 🔮 Likely Questions

### 🎯 LQ1 · Shared and Exclusive Locks with the Lock-Compatibility Matrix · [04 Marks]

> *Expected Exam Format · 4 Marks*

**Question.** Explain the difference between shared-mode and exclusive-mode locks in database systems. Draw the lock-compatibility matrix and state the conditions under which a lock request is granted or made to wait.

**Answer.**

**1. Difference Between Lock Modes:**
- **Shared-Mode Lock (`lock-S`):** Grants read-only access to data item $Q$. Multiple transactions can hold shared locks on the same item concurrently.
- **Exclusive-Mode Lock (`lock-X`):** Grants both read and write access to data item $Q$. Only one transaction can hold an exclusive lock on $Q$ at a time. No other transaction may hold any lock on $Q$ while an exclusive lock is active.

**2. Lock-Compatibility Matrix:**

| Requested Mode $\downarrow$ \ Held Mode $\to$ | Shared ($S$) | Exclusive ($X$) |
| :---: | :---: | :---: |
| **Shared ($S$)** | **True** (Compatible) | **False** (Conflict) |
| **Exclusive ($X$)** | **False** (Conflict) | **False** (Conflict) |

**3. Granting and Waiting Conditions:**
- **Grant Condition:** A request for mode $A$ on item $Q$ is granted if mode $A$ is compatible with all locks currently held on $Q$, and no earlier conflicting request is waiting in the queue.
- **Wait Condition:** If another transaction holds a conflicting lock on $Q$, or an earlier conflicting request is waiting in the queue, the requesting transaction must wait until conflicting locks are released.

### 🎯 LQ2 · Starvation in Locking Protocols and Prevention · [04 Marks]

> *Expected Exam Format · 4 Marks (Cross-ref: 2017 Q.7(a))*

**Question.** What is starvation in database concurrency control? Illustrate how a transaction requesting an exclusive lock can suffer from starvation. How does the concurrency control manager prevent starvation?

**Answer.**

**1. Definition of Starvation:**
Starvation (indefinite blocking) occurs when a waiting transaction never acquires its requested lock because the lock manager repeatedly grants locks to other concurrent transactions first.

**2. Illustration of Starvation:**
Suppose transaction $T_1$ requests `lock-X(A)` while transaction $T_2$ holds `lock-S(A)`:
- Because $X$ conflicts with $S$, $T_1$ must wait for $T_2$ to release $A$.
- While $T_1$ is waiting, transaction $T_3$ arrives and requests `lock-S(A)`. Because $S$ is compatible with $T_2$'s shared lock, a naive manager grants `lock-S(A)` to $T_3$.
- When $T_2$ executes `unlock(A)`, $T_1$ still cannot proceed because $T_3$ holds a shared lock.
- If new transactions $T_4, T_5, \dots$ continuously arrive and acquire shared locks before earlier readers release theirs, $T_1$ waits forever and starves.

**3. Prevention Mechanism:**
The lock manager prevents starvation by using a **FIFO wait queue**:
- A lock request is granted only if it is compatible with currently held locks AND no transaction is already waiting ahead of it in the queue with a conflicting request.
- Under this policy, once $T_1$ queues `lock-X(A)`, subsequent requests for `lock-S(A)` must wait behind $T_1$. As soon as $T_2$ unlocks $A$, $T_1$ receives the lock.

### 🎯 LQ3 · How Simple Locking Leads to Inconsistent Analysis · [04 Marks]

> *Expected Exam Format · 4 Marks*

**Question.** Using an example of two transactions accessing bank accounts $A$ and $B$, show how a simple locking protocol where locks are released immediately after access can result in a non-serializable schedule.

**Answer.**

**1. Setup:**
Let accounts have initial balances $A = 100$ and $B = 200$ (true sum = \$300).
- $T_1$: Transfers \$50 from $B$ to $A$.
- $T_2$: Reads $A$ and $B$ and displays their sum.

**2. Interleaved Execution Schedule:**

| Step | Transaction $T_1$ | Transaction $T_2$ | State of Accounts |
| :---: | :--- | :--- | :--- |
| 1 | `lock-X(B); read(B);` | | $B = 200$ |
| 2 | `B := B - 50; write(B);` | | $B = 150$ |
| 3 | `unlock(B);` | | *Lock on $B$ released early* |
| 4 | | `lock-S(A); read(A); unlock(A);` | $A = 100$ read by $T_2$ |
| 5 | | `lock-S(B); read(B); unlock(B);` | $B = 150$ read by $T_2$ |
| 6 | | `display(A + B);` | **Displays \$250** |
| 7 | `lock-X(A); read(A);` | | $A = 100$ |
| 8 | `A := A + 50; write(A); unlock(A);` | | $A = 150$ |

**3. Analysis:**
- In serial schedule $\langle T_1, T_2 \rangle$, $T_2$ displays \$300 ($150 + 150$).
- In serial schedule $\langle T_2, T_1 \rangle$, $T_2$ displays \$300 ($100 + 200$).
- In the concurrent execution above, $T_2$ displays \$250. This does not match any serial execution, so the schedule is not serializable.
- **Root Cause:** $T_1$ released its lock on $B$ at Step 3 before obtaining its lock on $A$ at Step 7. This allowed $T_2$ to read inconsistent intermediate data.

## ⚡ Exam Tips & Common Mistakes

- **Compatibility Matrix Pattern:** In the $2 \times 2$ compatibility matrix, only `(S, S)` is `True`. Every combination involving an `X` lock is `False`.
- **Four Simple Locking Pitfalls:** Always list all four flaws: (1) non-serializable schedules, (2) irrecoverable schedules, (3) starvation, and (4) deadlocks.
- **Starvation vs. Deadlock:** In a deadlock, transactions wait on each other in a closed cycle and none can make progress. In starvation, the system continues running new transactions normally while one waiting transaction is continuously bypassed.
- **FIFO Queue Condition 2:** In starvation questions, explicitly state that incoming shared locks must NOT be granted if a conflicting exclusive lock request is already waiting in the queue.
