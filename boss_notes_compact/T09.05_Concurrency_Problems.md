# T09.5: Concurrency Problems (Anomalies)

> **Topic:** T09 · Transactions, ACID & Anomalies | **Priority:** 🟡 Medium Priority | **Exam Frequency:** 2/7 finals + CT-04 Q03 (7 final marks + 4 CT marks = 11 marks total)  
> **Sources:** Silberschatz 7e Ch. 17 (§17.5) · Lecture Deck 07 (Slides 28–33) · Classnote by Raidah (T09, pp. 26, 28)

---

## Core Concept: The Five Concurrency Anomalies

**Concurrency-Control Component:** The concurrency-control component is the DBMS subsystem that coordinates concurrent transactions to execute without interference and enforce the ACID property of Isolation.

When concurrency control is omitted or improperly implemented, uncoordinated interleaving violates transaction isolation. Five major concurrency anomalies can corrupt the database:

1. **Lost Update:** Two transactions access and update the same data item concurrently. The second transaction overwrites the value written by the first transaction without incorporating its changes, causing the first update to vanish.
2. **Dirty Read (Temporary Update):** A transaction reads a data item modified by another transaction that has not yet committed. When the modifying transaction later fails and rolls back, the second transaction is left having used data that never officially existed.
3. **Unrepeatable Read:** A transaction reads the same data item twice during its execution and receives two different values because another transaction modified and committed that item in between the two reads.
4. **Phantom Read:** In the RUET course slides (Deck 07, Slide 32), a transaction reads an item once, another transaction deletes that item, and the second read fails with a "variable does not exist" error. (In textbook SQL terminology, it also refers to range queries seeing new matching rows inserted by another committed transaction).
5. **Incorrect Summary (Inconsistent Analysis):** An aggregate transaction calculates a summary (`SUM` or `AVG`) across multiple records while another transaction transfers values between those records. The summary transaction reads some records before the transfer and others after, yielding an inaccurate total.

### Concurrency Anomalies Summary

| Anomaly | Alternative Name | Immediate Cause | Resulting Impact |
| :--- | :--- | :--- | :--- |
| **Lost Update** | Overwrite Problem | Second write overwrites first write | First update is completely lost |
| **Dirty Read** | Temporary Update | Read uncommitted data before rollback | Computation based on phantom rolled-back data |
| **Unrepeatable Read** | Fuzzy Read | Interleaved update commits between two reads | Reading same variable yields different values |
| **Phantom Read** | Missing Item Problem | Variable deleted between two reads | Second read fails because item no longer exists |
| **Incorrect Summary** | Inconsistent Analysis | Aggregate scans items during active transfer | Summary misses funds or calculates invalid total |

## Detailed Schedules for Supporting Anomalies

### Unrepeatable Read Schedule ($A = 500$ initially)

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Description |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | | $\text{read}(A)$ | $T_2$ reads $A = 500$ |
| $t_3$ | | $A := A + 100$ | $T_2$ computes local $A = 600$ |
| $t_4$ | | $\text{write}(A)$ | Database updated to $A = 600$ |
| $t_5$ | | $\text{commit}$ | $T_2$ commits its modification |
| $t_6$ | $\text{read}(A)$ | | $T_1$ reads $A = 600$ (contradicts first read of 500) |

### Phantom Read Schedule (RUET Slide 32 Deletion Format)

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Description |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | $\text{read}(A)$ | Both transactions read data item $A$ successfully |
| $t_2$ | $\text{delete}(A)$<br>$\text{commit}$ | | $T_1$ deletes data item $A$ and commits |
| $t_3$ | | $\text{read}(A)$ | $T_2$ attempts to read $A$ again; item no longer exists |

### Incorrect Summary Schedule ($A = 1000, B = 1000, C = 1000$ initially)

| Time | Transaction $T_1$ (Transfer 50 from $A$ to $B$) | Transaction $T_2$ (Calculate Average of $A, B, C$) | State / Running Total |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A);\; A := A - 50;\; \text{write}(A);$ | | $T_1$ writes $A = 950$ to disk |
| $t_2$ | | $\text{sum} := 0;\; \text{read}(C);\; \text{sum} := \text{sum} + C;$ | $T_2$ reads $C = 1000 \implies \text{sum} = 1000$ |
| $t_3$ | | $\text{read}(A);\; \text{sum} := \text{sum} + A;$ | $T_2$ reads updated $A = 950 \implies \text{sum} = 1950$ |
| $t_4$ | | $\text{read}(B);\; \text{sum} := \text{sum} + B;$ | $T_2$ reads old $B = 1000 \implies \text{sum} = 2950$ |
| $t_5$ | | $\text{avg} := \text{sum} / 3;\; \text{commit};$ | $T_2$ reports $\text{avg} = 2950 / 3 \approx 983.33$ |
| $t_6$ | $\text{read}(B);\; B := B + 50;\; \text{write}(B);\; \text{commit};$ | | $T_1$ writes $B = 1050$ and commits |

$T_2$ reported an average of 983.33 instead of the true average 1000 because it observed $T_1$ halfway through execution.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.5(a) / 2024 Q.8(a) · Concurrency Problems & Detailed Schedules · 04 / 03 Marks

> *Section B · Asked in: 2018 Q.5(a) [4m], 2024 Q.8(a) (CO3) [3m] · L2 merge*

**Question (2018 Q.5(a)).** If concurrency-control management is not implemented properly what problem may occur? Explain with example.

**Question (2024 Q.8(a)).** If concurrency-control management is not implemented properly what problem may occur? Explain with example.

**Answer.**

If concurrency-control management is not implemented properly, uncoordinated interleaving violates transaction isolation. This causes five major anomalies:
1. **Lost Update Problem**
2. **Dirty Read Problem (Temporary Update Problem)**
3. **Unrepeatable Read Problem**
4. **Phantom Read Problem**
5. **Incorrect Summary Problem (Inconsistent Analysis)**

#### 1. Lost Update Problem
- **Concept:** An update done by one transaction is overwritten and lost because another concurrent transaction writes to the same item without incorporating the first update.
- **Schedule ($A = 500$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Note |
| :--- | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | $A := A - 50$ | | $T_1$ computes local $A = 450$ |
| $t_3$ | $\text{write}(A)$ | | Database updated to $A = 450$ |
| $t_4$ | | $\text{write}(A)$ | $T_2$ performs blind write: $A = 25$ |
| $t_5$ | $\text{commit}$ | | $T_1$ commits |
| $t_6$ | | $\text{commit}$ | Final $A = 25$ (update by $T_1$ of $-50$ is lost!) |

#### 2. Dirty Read Problem (Temporary Update Problem)
- **Concept:** Occurs when a transaction reads a data item updated by another transaction that has not yet committed and later fails and rolls back.
- **Schedule ($A = 100$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Database State / Note |
| :--- | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads initial balance $A = 100$ |
| $t_2$ | $A := A + 100$ | | $T_1$ computes local $A = 200$ |
| $t_3$ | $\text{write}(A)$ | | Database $A = 200$ (uncommitted) |
| $t_4$ | | $\text{read}(A)$ | $T_2$ reads dirty value $A = 200$ |
| $t_5$ | | $A := A - 50$ | $T_2$ computes local $A = 150$ |
| $t_6$ | | $\text{write}(A)$ | Database updated to $A = 150$ |
| $t_7$ | | $\text{commit}$ | $T_2$ commits with invalid data |
| $t_8$ | $\text{abort}$ (Rollback) | | $T_1$ fails and aborts; recovery restores $A = 100$ |

$T_2$ based its calculation on an uncommitted value that was rolled back, leaving the database inconsistent.

*Variant for 2024 Q.8(a) (3 marks):* List the five anomalies, then provide the full schedule tables for Lost Update and Dirty Read.

### 🎯 GQ2 · CT-04 Q.03 · Two Problems Caused by Concurrent Execution · 04 Marks

> *Asked in: CT-04 (CO3) · L1 (asked once)*

**Question.** Explains any two problems caused by concurrent execution. *(Note: Printed verbatim in original script)*.

**Answer.**

Two major problems caused by uncontrolled concurrent execution are the **Lost Update Problem** and the **Dirty Read Problem**:

#### 1. Lost Update Problem
- **Definition:** Occurs when two concurrent transactions update the same data item and the second transaction overwrites the value written by the first transaction without including its update.
- **Example Schedule ($A = 500$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Action / Impact |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 500$ |
| $t_2$ | $A := A - 50;\; \text{write}(A)$ | | $T_1$ updates $A$ to $450$ |
| $t_3$ | | $\text{write}(A)$ | $T_2$ overwrites $A$ with blind write $A = 25$ |
| $t_4$ | $\text{commit}$ | | $T_1$ commits |
| $t_5$ | | $\text{commit}$ | $T_2$ commits, leaving $A = 25$ (the $-50$ update is lost) |

#### 2. Dirty Read Problem (Temporary Update Problem)
- **Definition:** Occurs when a transaction reads an uncommitted modification made by another transaction, and that modifying transaction subsequently aborts and rolls back.
- **Example Schedule ($A = 100$ initially):**

| Time | Transaction $T_1$ | Transaction $T_2$ | Action / Impact |
| :---: | :--- | :--- | :--- |
| $t_1$ | $\text{read}(A)$ | | $T_1$ reads $A = 100$ |
| $t_2$ | $A := A + 100;\; \text{write}(A)$ | | $T_1$ writes uncommitted $A = 200$ |
| $t_3$ | | $\text{read}(A)$ | $T_2$ reads dirty value $A = 200$ |
| $t_4$ | | $A := A - 50;\; \text{write}(A)$ | $T_2$ writes $A = 150$ |
| $t_5$ | | $\text{commit}$ | $T_2$ commits permanently |
| $t_6$ | $\text{abort}$ (Rollback) | | $T_1$ aborts; recovery restores $A = 100$ |

$T_2$ committed based on an uncommitted temporary value that never legally existed, corrupting the database.

## ⚡ Exam Tips & Common Mistakes

- **Always Draw Schedule Tables:** Never explain concurrency anomalies with plain paragraphs alone. Draw a two-column schedule table ($T_1$ and $T_2$) with numbered time steps ($t_1, t_2, \dots$).
- **State Clear Initial and Final Values:** Start with concrete numbers like $A = 500$ or $A = 100$. Show the exact arithmetic at each step and explain why the final database value is wrong.
- **Dirty Read vs Unrepeatable Read:** In a **Dirty Read**, $T_2$ reads an *uncommitted* write from $T_1$ before $T_1$ aborts. In an **Unrepeatable Read**, $T_1$ reads $A$ twice and gets two different values because $T_2$ updated and *committed* $A$ in between.
- **Best Two to Pick on Exams:** When a question asks for "any two problems" or "an example", always select **Lost Update** and **Dirty Read**. Their schedules are concise and directly match RUET Lecture Deck 07 (Slides 29 and 31).
