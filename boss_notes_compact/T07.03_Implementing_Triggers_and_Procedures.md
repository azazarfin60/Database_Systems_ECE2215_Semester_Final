# T07.3: Implementing Triggers and Stored Procedures

> **Topic:** T07 · Triggers and Stored Procedures | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals · 10 marks  
> **Sources:** Silberschatz 7e Ch. 5 (§5.2–5.3) · Fahim Handnote (pp. 59, 60) · (No lecture slides for Unit 4 advanced SQL)

## Stored Procedures vs. Triggers

**Stored Procedure:** A named program of SQL statements saved inside the database. Applications run it explicitly using `CALL procedure_name(...)` and pass `IN`, `OUT`, or `INOUT` parameters.

**Stored Procedure vs Trigger:** A stored procedure takes parameters and runs only when invoked explicitly. A trigger accepts no arguments and fires automatically when a DML modification (`INSERT`, `UPDATE`, or `DELETE`) occurs on its target table.

| Dimension | Stored Procedure | Database Trigger |
| :--- | :--- | :--- |
| **Invocation** | Explicitly called by an application (`CALL proc()`) | Automatically invoked by the DBMS on table events |
| **Parameters** | Accepts `IN`, `OUT`, and `INOUT` parameters | Takes no parameters (reads row data via `OLD` and `NEW`) |
| **Transaction Control** | Can start, commit, or roll back transactions | Runs inside the transaction of the activating DML |
| **Return Data** | Returns query result sets or `OUT` parameters | Cannot return query result sets to the caller |
| **Primary Role** | Multi-step business workflows (such as placing orders) | Integrity enforcement, sync, and audit logging |

## Implementing Stored Procedures for Business Workflows

When implementing business logic that checks data before updating multiple tables, follow three core practices:

**Pessimistic Concurrency Control (`FOR UPDATE`):** A locking clause added to a `SELECT` statement inside a transaction. It places an exclusive lock on selected rows until commit or rollback. This prevents concurrent transactions from modifying the same record simultaneously.

1. **Prefix Parameters and Variables:** Prefix parameters with `p_` (such as `p_product_id`) and local variables with `v_` (such as `v_stock`). This prevents SQL engines from mistaking variable names for table column names.
2. **Lock Rows During Validation:** Running a plain `SELECT` allows race conditions where two concurrent sessions read the same stock and sell the same item twice. Adding `FOR UPDATE` forces concurrent sessions to wait until the current transaction commits.
3. **Control Transaction Boundaries:** Begin with `START TRANSACTION;`. If validations fail, execute `ROLLBACK;` and raise an error with `SIGNAL SQLSTATE '45000'`. If validations pass, execute `COMMIT;`.

## Implementing Automated Audit and Sync Triggers

While stored procedures handle explicit user actions, triggers ensure secondary tables stay synchronized automatically:

- **Timing Selection:** Use `AFTER` timing for audit and sync tasks. The trigger runs only after the main row change passes all constraints and writes to the table.
- **Table Placement:** Attach the trigger directly to the table holding the monitored attribute. When tracking inventory, attach the trigger to `Products` (on `AFTER UPDATE`), rather than `Orders`. This captures changes from sales, cancellations, and restocks equally.
- **Change Detection:** Always wrap audit inserts in an `IF OLD.col <> NEW.col` check to prevent logging updates that did not modify the monitored column.

## Asynchronous Decoupling: Handling External Actions (Emails)

Exam questions often ask to implement a trigger that updates stock and sends an email.

**Out-of-Process Task Queue (Asynchronous Decoupling):** A pattern where a database trigger inserts job records into a queue table (`email_queue`) instead of calling external network services directly. A background worker reads the queue and performs the external task after commit.

### Why Triggers Cannot Send Emails Directly

1. **Transaction Blocking:** Network calls take hundreds of milliseconds. Because triggers run inside the active transaction, database row locks remain held while waiting for network responses.
2. **Un-Rollbackable Actions:** An email sent over SMTP cannot be undone. If the database transaction later aborts, the customer receives a confirmation email for an order that was rolled back.
3. **Security Boundaries:** Granting a database engine direct access to outbound network sockets creates unnecessary security exposure.

Instead, the trigger inserts an email job into an `email_queue` table within the same transaction. If the transaction rolls back, the queue insert rolls back too. Once committed, an external mailer service dispatches the email.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2023 Q.6(b) · Stored Procedure for Order Placement and Audit Log Trigger · 06 Marks

> *Section B · CLO2 · Asked in: 2023 · L1 (asked once)*

**Question (2023 Q.6(b)).** Considering the tables (Products, Orders, and Auditlog) answer (i) and (ii).  
(i) Create a stored procedure to place an order consider stock availability, updates the stock.  
(ii) Create a trigger to log every stock update in the Auditlog table automatically.

**Answer.**

*Assumption: The table schemas are `Products(product_id, name, stock, price)`, `Orders(order_id, product_id, quantity, order_date)`, and `Auditlog(log_id, product_id, old_stock, new_stock, changed_at)`.*

#### (i) Stored Procedure to Place an Order

The stored procedure verifies available stock using row-level locking (`FOR UPDATE`), places the order, and reduces the inventory within a transaction:

```sql
DELIMITER //

CREATE PROCEDURE PlaceOrder (
    IN p_product_id INT,
    IN p_quantity INT
)
BEGIN
    DECLARE v_stock INT;

    START TRANSACTION;

    -- Lock the target product row to prevent concurrent race conditions
    SELECT stock INTO v_stock
    FROM Products
    WHERE product_id = p_product_id
    FOR UPDATE;

    -- Validate product existence and stock sufficiency
    IF v_stock IS NULL THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Product does not exist';
    ELSEIF v_stock < p_quantity THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Error: Insufficient stock available';
    ELSE
        -- Record the new order
        INSERT INTO Orders (product_id, quantity, order_date)
        VALUES (p_product_id, p_quantity, NOW());

        -- Deduct ordered quantity from stock
        UPDATE Products
        SET stock = stock - p_quantity
        WHERE product_id = p_product_id;

        COMMIT;
    END IF;
END //

DELIMITER ;
```

#### (ii) Trigger to Log Stock Updates Automatically

An `AFTER UPDATE` trigger detects when the `stock` column changes and writes an audit record to `Auditlog`:

```sql
DELIMITER //

CREATE TRIGGER trg_log_stock_update
AFTER UPDATE ON Products
FOR EACH ROW
BEGIN
    -- Log only when the stock quantity actually changes
    IF OLD.stock <> NEW.stock THEN
        INSERT INTO Auditlog (product_id, old_stock, new_stock, changed_at)
        VALUES (OLD.product_id, OLD.stock, NEW.stock, NOW());
    END IF;
END //

DELIMITER ;
```

### 🎯 GQ2 · 2024 Q.6(b) · Trigger for Stock Update and Email Dispatch · 04 Marks

> *Section B · CO3 · Asked in: 2024 · L1 (asked once)*

**Question (2024 Q.6(b)).** An e-commerce system wants to automate actions when a new order is inserted such as updating stock and sending email. Implement a database trigger that handles this workflow.

**Answer.**

*Assumption: The tables are `orders(order_id, product_id, quantity, customer_email)`, `products(product_id, stock)`, and `email_queue(queue_id, recipient, subject, body, queued_at)`.*

A trigger runs inside the database engine and cannot send external emails directly. Instead, the trigger updates product stock and inserts a row into an `email_queue` table. An external mailer application reads this queue and sends the email after the transaction commits.

```sql
DELIMITER //

CREATE TRIGGER trg_after_order_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    -- 1. Deduct ordered quantity from product stock
    UPDATE products
    SET stock = stock - NEW.quantity
    WHERE product_id = NEW.product_id;

    -- 2. Enqueue email notification for external mailer service
    INSERT INTO email_queue (recipient, subject, body, queued_at)
    VALUES (
        NEW.customer_email,
        'Order Confirmation',
        CONCAT('Your order #', NEW.order_id, ' for product #', NEW.product_id, ' (Qty: ', NEW.quantity, ') has been placed successfully.'),
        NOW()
    );
END //

DELIMITER ;
```

## ⚡ Exam Tips & Common Mistakes

- **Race Conditions Without FOR UPDATE:** Always use `SELECT ... FOR UPDATE` when checking balances or inventory inside a stored procedure. Omitting it allows concurrent requests to oversell items.
- **The Direct Email Trap:** Never write fake functions like `SEND_EMAIL()`. Explain that databases cannot safely call SMTP servers directly and use an `email_queue` table.
- **State Assumptions:** If an exam question omits column types or table schemas, write a 1-line schema assumption before the code.
- **Audit Trigger Placement:** Attach stock audit triggers to `Products`, not `Orders`. Stock can change via restocks or inventory adjustments, not only new orders.
- **Variable Collisions:** Prefix procedure parameters with `p_` and local variables with `v_` to avoid conflicts with column names.
