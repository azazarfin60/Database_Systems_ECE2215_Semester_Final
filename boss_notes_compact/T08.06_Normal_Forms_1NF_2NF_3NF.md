# T08.6: Normal Forms: 1NF, 2NF, and 3NF

> **Topic:** T08 · Normalization & Functional Dependencies | **Priority:** 🟠 High Priority | **Exam Frequency:** 3/7 finals · 14 marks (+ CT-03 Q03, 3 marks)
> **Sources:** Silberschatz 7e Ch. 7 (§7.3, §7.7, §7.8) · Lecture Deck 06 (Slides 3–4, 30–40) · Raidah Class Notes (pp. 22–23)

## Foundations of Normalization

**Normalization:** A formal, systematic technique for designing relational database schemas. It decomposes relations with anomalies into smaller, well-structured relations to reduce data redundancy and ensure data integrity.

### Objectives of Normalization

1. **Eliminate Redundancy:** Avoid storing duplicate copies of the same real-world fact.
2. **Prevent Modification Anomalies:** Remove insertion, deletion, and update anomalies.
3. **Ensure Data Consistency:** Guarantee that updates keep records synchronized.
4. **Preserve Dependencies:** Ensure business constraints can be enforced without expensive cross-table joins.

### The Cumulative Hierarchy

Normal forms build cumulatively. Each level requires satisfying all previous levels:

$$
\text{UNF} \xrightarrow{\text{Atomic values}} \text{1NF} \xrightarrow{\text{No partial FDs}} \text{2NF} \xrightarrow{\text{No transitive FDs}} \text{3NF} \xrightarrow{\text{Determinants are superkeys}} \text{BCNF}
$$

Every relation in 3NF is automatically in 2NF, and every relation in 2NF is automatically in 1NF.

## The Three Classical Normal Forms

### 1. First Normal Form (1NF)

**First Normal Form (1NF):** A relation schema $R$ is in 1NF if and only if every attribute domain contains only **atomic (indivisible) values**, and each cell holds exactly one value.

**Atomic Domain:** A domain is atomic if elements of the domain are considered to be indivisible units.

**Rules:**
- No multi-valued attributes (lists, arrays, or comma-separated strings).
- No composite attributes or nested tables.
- No repeating groups of columns.
- Each tuple must be uniquely identifiable by a primary key.

*Example:* An unnormalized student record `(S01, Fahim, "01711, 01822")` violates 1NF. To convert to 1NF, split the phone numbers into separate rows: `(S01, Fahim, 01711)` and `(S01, Fahim, 01822)`, with primary key `(Student_ID, Phone)`.

### 2. Second Normal Form (2NF)

**Second Normal Form (2NF):** A relation schema $R$ is in 2NF if and only if it is in 1NF and contains **no partial functional dependencies**. Every non-prime attribute must be fully functionally dependent on every candidate key.

**Rules:**
- The relation must be in 1NF.
- No non-prime attribute may depend on a proper subset of any candidate key.
- If all candidate keys are single attributes, the relation is **automatically in 2NF**.

*Example:* In `ENROLL(StudentID, CourseID, StudentName, Grade)` with primary key `(StudentID, CourseID)`:
- `(StudentID, CourseID) -> Grade` is a full dependency.
- `StudentID -> StudentName` is a partial dependency because `StudentName` depends only on `StudentID`.
- To fix, decompose into `STUDENT(StudentID, StudentName)` and `ENROLLMENT(StudentID, CourseID, Grade)`.

### 3. Third Normal Form (3NF)

**Third Normal Form (3NF):** A relation schema $R$ is in 3NF if and only if it is in 2NF and contains **no transitive dependencies**. A non-prime attribute must not depend on another non-prime attribute.

**Formal Condition:** For every non-trivial functional dependency $\alpha \rightarrow \beta$ in $F^+$, at least one of the following must hold:
1. $\alpha$ is a **superkey** of $R$, **OR**
2. Each attribute $A \in (\beta - \alpha)$ is a **prime attribute** (member of some candidate key).

*Example:* In `STUDENT(StudentID, StudentName, DeptID, DeptName)` with primary key `StudentID`:
- `StudentID -> DeptID` and `DeptID -> DeptName`.
- `DeptName` transitively depends on `StudentID` through non-prime attribute `DeptID`.
- To fix, decompose into `STUDENT(StudentID, StudentName, DeptID)` and `DEPARTMENT(DeptID, DeptName)`.

### Summary Comparison

| Normal Form | Core Requirement | Anomaly / Flaw Eliminated |
| :--- | :--- | :--- |
| **1NF** | Attribute values must be atomic | Multi-valued lists, composite attributes, repeating groups |
| **2NF** | In 1NF + No partial dependencies | Redundancy from non-prime attributes depending on part of a key |
| **3NF** | In 2NF + No transitive dependencies | Redundancy from non-prime attributes depending on non-prime attributes |

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.3(a) / CT-03 Q.03 · Normalization and Its Importance · 03 Marks

> *Section A · Asked in: 2017 (3 marks), CT-03 Q.03 (3 marks) · L2 merge*

**Question (2017 Q.3(a)).** What do you mean by normalization? Why normalization is important for database?

**Question (CT-03 Q.03).** Define normalization and state its main objective.

**Answer.**

#### 1. What is Normalization?

**Normalization** is a formal, systematic technique for designing relational database schemas. It decomposes relations with anomalies into smaller, well-structured relations to reduce data redundancy and ensure data integrity.

#### 2. Importance of Normalization (Main Objectives)

Normalization is essential for relational databases because it:

1. **Eliminates Unnecessary Data Redundancy:** Prevents storing the same facts repeatedly across multiple records, which conserves physical storage.
2. **Prevents Database Anomalies:** Completely removes insertion, deletion, and update anomalies that corrupt data during modifications.
3. **Ensures Data Consistency and Integrity:** Guarantees that an update applied to one record keeps all related facts accurate and consistent.
4. **Preserves Data Dependencies:** Ensures all real-world business constraints and functional dependencies can be enforced efficiently without complex cross-table joins.

*Variant for CT-03 Q.03 (3 marks):* Define normalization as the systematic decomposition of relations to minimize redundancy and eliminate anomalies. State the main objective: to produce well-structured tables free of insertion, update, and deletion anomalies while maintaining data consistency.

### 🎯 GQ2 · 2017 Q.8(c) · 1NF, 2NF, and 3NF Definitions · 03 Marks

> *Section B · Asked in: 2017*

**Question.** What is 1NF, 2NF and 3NF?

**Answer.**

1. **First Normal Form (1NF):**  
   A relation is in 1NF if and only if every attribute domain contains only **atomic (indivisible) values**, and each cell contains exactly one value. It strictly disallows multi-valued attributes, composite attributes, and repeating groups.

2. **Second Normal Form (2NF):**  
   A relation is in 2NF if and only if:
   - It is already in 1NF.
   - It contains **no partial functional dependencies**. Every non-prime attribute must be fully functionally dependent on the entire candidate key, rather than on a proper subset of it.

3. **Third Normal Form (3NF):**  
   A relation is in 3NF if and only if:
   - It is already in 2NF.
   - It contains **no transitive dependencies**. A non-prime attribute must not depend on another non-prime attribute. Formally, for every non-trivial functional dependency $X \rightarrow Y$, either $X$ is a superkey, or $Y$ consists entirely of prime attributes.

### 🎯 GQ3 · 2019 Q.3(a) / 2018 Q.4(c) · Normalization, 1NF, and 2NF with Examples · 04 Marks

> *Section A · Asked in: 2019 Q.3(a) (4 marks), 2018 Q.4(c) (4 marks) · L2 merge*

**Question (2019 Q.3(a)).** What is normalization? Discuss 1NF and 2NF.

**Question (2018 Q.4(c)).** Explain the rules of 1NF and 2NF with a proper example.

**Answer.**

#### 1. What is Normalization?

**Normalization** is the process of decomposing a relation schema into smaller schemas to minimize data redundancy and prevent insertion, deletion, and update anomalies.

#### 2. First Normal Form (1NF)

**Rules:**
- Every attribute must hold only atomic (single, indivisible) values.
- No multi-valued attributes or repeating groups are permitted.
- Each column must contain values of the same domain, and each row must be uniquely identifiable.

**Example:**

*Violating 1NF:*

| Student_ID | Name | Phone |
| :--- | :--- | :--- |
| S01 | Fahim | 01711, 01822 |
| S02 | Noor | 01933 |

*Converted to 1NF (atomic rows):*

| Student_ID | Name | Phone |
| :--- | :--- | :--- |
| S01 | Fahim | 01711 |
| S01 | Fahim | 01822 |
| S02 | Noor | 01933 |

PK: `(Student_ID, Phone)`

#### 3. Second Normal Form (2NF)

**Rules:**
- The relation must be in 1NF.
- There must be **no partial dependency**. No non-prime attribute can depend on a proper subset of any candidate key.

**Example:**

Consider relation `ENROLL(StudentID, CourseID, StudentName, Grade)`:
- Candidate Key: `(StudentID, CourseID)`
- Dependencies:
  - `(StudentID, CourseID) -> Grade` (Full dependency)
  - `StudentID -> StudentName` (Partial dependency on proper subset `StudentID`)

*Converted to 2NF (decompose to remove partial dependency):*
1. `STUDENT(StudentID, StudentName)` with PK `StudentID`
2. `ENROLLMENT(StudentID, CourseID, Grade)` with PK `(StudentID, CourseID)`

*Variant for 2018 Q.4(c) (4 marks):* State the rules for 1NF (atomicity, no multi-valued attributes) with the phone number example. State the rules for 2NF (in 1NF, no partial dependencies) with the student course example.

## ⚡ Exam Tips & Common Mistakes

- **3NF condition has two options:** Always state both conditions for 3NF: $\alpha$ is a superkey OR $\beta - \alpha$ contains only prime attributes. Forgetting the second option gives the definition of BCNF instead of 3NF.
- **Partial dependency only applies to non-prime attributes:** If an attribute depending on a subset of a candidate key is itself prime, it does not violate 2NF!
- **Atomic domain definition:** Always use the keyword "indivisible" or "atomic" when defining 1NF.
