# T11.05: Wait-Die vs. Wound-Wait Deadlock Prevention

> **Topic:** T11 · Concurrency Control Protocols | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (0 marks; Foundation for 2017 Q.7(b))
> **Sources:** Silberschatz 7e Ch. 18 (§18.2.1, p. 850) · Lecture Deck 08 (Slide 23) · Raidah Notes (p. 29)

---

## Timestamp Principles in Deadlock Prevention

**Wait-Die Scheme:** A non-preemptive deadlock prevention protocol using transaction startup timestamps $\text{TS}(T)$. When transaction $T_i$ requests a lock held by $T_j$, $T_i$ waits only if it is older than $T_j$ ($\text{TS}(T_i) < \text{TS}(T_j)$). If $T_i$ is younger ($\text{TS}(T_i) > \text{TS}(T_j)$), $T_i$ dies (rolls back and restarts with its original timestamp).

**Wound-Wait Scheme:** A preemptive deadlock prevention protocol using transaction startup timestamps $\text{TS}(T)$. When transaction $T_i$ requests a lock held by $T_j$, an older $T_i$ ($\text{TS}(T_i) < \text{TS}(T_j)$) wounds $T_j$, forcing $T_j$ to roll back and release the lock. If $T_i$ is younger ($\text{TS}(T_i) > \text{TS}(T_j)$), $T_i$ waits for $T_j$ to finish.

**Timestamp Retention Rule:** When a transaction rolls back under wait-die or wound-wait, it restarts with its **original timestamp** instead of receiving a new one. Keeping the original timestamp increases its seniority over time, preventing starvation.

Timestamps represent seniority:
- Smaller timestamp = Older (earlier) transaction with higher seniority.
- Larger timestamp = Younger (later) transaction.

---

## The Critical Timestamp Trap: Deadlock Prevention vs. TSO

> [!IMPORTANT]
> - **In Deadlock Prevention (Wait-Die and Wound-Wait):** A rolled-back transaction **KEEPS ITS ORIGINAL (OLD) TIMESTAMP** upon restart. Its seniority increases over time until it becomes the oldest transaction in the system, guaranteeing freedom from starvation.
> - **In Concurrency Control (Timestamp Ordering / TSO):** A rolled-back transaction **RECEIVES A NEW, LARGER TIMESTAMP** upon restart. If it kept its old timestamp, it would trigger the exact same conflict condition on disk immediately.

---

## The Wait-Die Scheme (Non-Preemptive)

Wait-die is **non-preemptive**. A requesting transaction never revokes locks from an active transaction.

### Wait-Die Decision Rules

When transaction $T_i$ requests an item held by transaction $T_j$:

1. **Older requests Younger ($\text{TS}(T_i) < \text{TS}(T_j)$):**
   - $T_i$ is older and has seniority, so $T_i$ is allowed to **WAIT** until $T_j$ releases the lock.
2. **Younger requests Older ($\text{TS}(T_i) > \text{TS}(T_j)$):**
   - $T_i$ is younger, so $T_i$ **DIES** (aborts, rolls back, and restarts with its original timestamp).

*Mnemonic:* "Old can wait, Young must die." Only older transactions are ever permitted to wait.

---

## The Wound-Wait Scheme (Preemptive)

Wound-wait is **preemptive**. An older transaction can forcibly take locks away from younger transactions.

### Wound-Wait Decision Rules

When transaction $T_i$ requests an item held by transaction $T_j$:

1. **Older requests Younger ($\text{TS}(T_i) < \text{TS}(T_j)$):**
   - $T_i$ is older, so $T_i$ **WOUNDS** $T_j$. The system rolls $T_j$ back and grants the lock immediately to $T_i$.
2. **Younger requests Older ($\text{TS}(T_i) > \text{TS}(T_j)$):**
   - $T_i$ is younger, so $T_i$ is allowed to **WAIT** until $T_j$ finishes.

*Mnemonic:* "Old wounds young, Young must wait." Only younger transactions are ever permitted to wait.

---

## Side-by-Side Comparison: Wait-Die vs. Wound-Wait

| Feature / Metric | Wait-Die Scheme | Wound-Wait Scheme |
| :--- | :--- | :--- |
| **Preemption Style** | Non-preemptive | Preemptive |
| **Older requests Younger** | Older **waits** | Older **wounds younger** ($T_j$ rolls back) |
| **Younger requests Older** | Younger **dies** ($T_i$ rolls back) | Younger **waits** |
| **Who is allowed to wait?** | **Only older transactions** | **Only younger transactions** |
| **Who is rolled back?** | Requesting transaction (younger) | Holding transaction (younger) |
| **Rollback Frequency** | **Higher** (young transaction may die repeatedly) | **Lower** (young transaction waits once wounded) |
| **Wasted Work** | Low (aborted transactions are young) | Moderate (holding transaction may be partway through) |
| **Restart Timestamp** | **Original timestamp** retained | **Original timestamp** retained |
| **Starvation Freedom** | Guaranteed (aging guarantees completion) | Guaranteed (aging guarantees completion) |
| **Deadlock Freedom** | Guaranteed (cycles impossible) | Guaranteed (cycles impossible) |

---

## Proof of Deadlock Impossibility

A deadlock requires a closed directed cycle of waiting transactions: $T_1 \to T_2 \to \dots \to T_k \to T_1$.

1. **In Wait-Die:** An edge $T_i \to T_j$ exists only if $\text{TS}(T_i) < \text{TS}(T_j)$. A cycle would require:
   $$
   \text{TS}(T_1) < \text{TS}(T_2) < \dots < \text{TS}(T_k) < \text{TS}(T_1) \implies \text{TS}(T_1) < \text{TS}(T_1)
   $$
   This is a contradiction. No cycle can form.
2. **In Wound-Wait:** An edge $T_i \to T_j$ exists only if $\text{TS}(T_i) > \text{TS}(T_j)$. A cycle would require:
   $$
   \text{TS}(T_1) > \text{TS}(T_2) > \dots > \text{TS}(T_k) > \text{TS}(T_1) \implies \text{TS}(T_1) > \text{TS}(T_1)
   $$
   This is a contradiction. No cycle can form.

## 🔮 Likely Questions

### 🎯 LQ1 · Wait-Die and Wound-Wait Schemes with Examples · [04 Marks]

> *Expected Exam Format · 4 Marks (Cross-ref: 2017 Q.7(b))*

**Question.** Explain the wait-die and wound-wait deadlock prevention schemes with clear examples. How do they differ in terms of preemption?

**Answer.**

**1. Wait-Die Scheme (Non-Preemptive):**
Wait-die uses transaction timestamps $\text{TS}(T)$. When transaction $T_i$ requests a lock held by $T_j$:
- If $\text{TS}(T_i) < \text{TS}(T_j)$ ($T_i$ is older), $T_i$ **waits**.
- If $\text{TS}(T_i) > \text{TS}(T_j)$ ($T_i$ is younger), $T_i$ **dies** (rolls back and restarts with its original timestamp).
- *Example:* Let $\text{TS}(T_1) = 100$ and $\text{TS}(T_2) = 200$. If $T_1$ requests an item held by $T_2$, $T_1$ waits ($100 < 200$). If $T_2$ requests an item held by $T_1$, $T_2$ dies ($200 > 100$).

**2. Wound-Wait Scheme (Preemptive):**
Wound-wait uses transaction timestamps $\text{TS}(T)$. When transaction $T_i$ requests a lock held by $T_j$:
- If $\text{TS}(T_i) < \text{TS}(T_j)$ ($T_i$ is older), $T_i$ **wounds** $T_j$ ($T_j$ rolls back and yields the lock to $T_i$).
- If $\text{TS}(T_i) > \text{TS}(T_j)$ ($T_i$ is younger), $T_i$ **waits**.
- *Example:* With the same timestamps, if $T_1$ requests an item held by $T_2$, $T_1$ wounds $T_2$ ($T_2$ rolls back). If $T_2$ requests an item held by $T_1$, $T_2$ waits.

**3. Difference in Preemption:**
- **Wait-Die is Non-Preemptive:** Locks are never taken away from an active holder. Only the requesting transaction is ever aborted.
- **Wound-Wait is Preemptive:** An older requesting transaction forcefully revokes locks from a younger holder by aborting the younger transaction.

### 🎯 LQ2 · Why Rolled-Back Transactions Retain Original Timestamps · [04 Marks]

> *Expected Exam Format · 4 Marks*

**Question.** Why does a rolled-back transaction retain its original timestamp in the wait-die and wound-wait schemes? What would happen if it were assigned a new timestamp?

**Answer.**

**1. Reason for Retaining the Original Timestamp:**
In both wait-die and wound-wait, rolled-back transactions keep their original timestamps to **prevent starvation (livelock)**:
- New transactions enter the system with larger (younger) timestamps.
- Because the rolled-back transaction keeps its old timestamp, its relative seniority increases over time.
- In Wait-Die, an older transaction is allowed to wait and never dies.
- In Wound-Wait, an older transaction wounds younger holders and is never forced to wait.
- Eventually, the transaction becomes the oldest in the system. At that point, it can never be aborted or wounded again, guaranteeing it will finish in finite time.

**2. What Happens if Assigned a New Timestamp:**
If the database assigned a new timestamp on restart:
- The transaction would become younger than other active transactions.
- In Wait-Die, it would repeatedly request items from older holders and die again.
- In Wound-Wait, older transactions would repeatedly preempt it.
- The transaction could be aborted indefinitely, resulting in **infinite starvation**.

### 🎯 LQ3 · Algorithmic Trace of Three Transactions under Wait-Die and Wound-Wait · [04 Marks]

> *Expected Exam Format · 4 Marks*

**Question.** Three transactions $T_1, T_2, T_3$ enter a database system with timestamps $\text{TS}(T_1) = 10, \text{TS}(T_2) = 20, \text{TS}(T_3) = 30$. Data item $Q$ is held under an exclusive lock by transaction $T_2$. Determine the system action when:
1. **Request A:** $T_1$ requests an exclusive lock on $Q$.
2. **Request B:** $T_3$ requests an exclusive lock on $Q$.
Evaluate both requests separately under (i) Wait-Die and (ii) Wound-Wait.

**Answer.**

**1. Evaluation under Wait-Die Scheme (Non-Preemptive):**
- **Request A ($T_1$ requests $Q$ held by $T_2$):**
  - Requester: $T_1$ ($\text{TS}=10$); Holder: $T_2$ ($\text{TS}=20$).
  - $\text{TS}(T_1) < \text{TS}(T_2) \implies 10 < 20$ (Older requests Younger).
  - **Action:** $T_1$ is **allowed to WAIT**. $T_2$ continues execution.
- **Request B ($T_3$ requests $Q$ held by $T_2$):**
  - Requester: $T_3$ ($\text{TS}=30$); Holder: $T_2$ ($\text{TS}=20$).
  - $\text{TS}(T_3) > \text{TS}(T_2) \implies 30 > 20$ (Younger requests Older).
  - **Action:** $T_3$ **DIES** (rolls back, retaining original timestamp $\text{TS}=30$).

**2. Evaluation under Wound-Wait Scheme (Preemptive):**
- **Request A ($T_1$ requests $Q$ held by $T_2$):**
  - Requester: $T_1$ ($\text{TS}=10$); Holder: $T_2$ ($\text{TS}=20$).
  - $\text{TS}(T_1) < \text{TS}(T_2) \implies 10 < 20$ (Older requests Younger).
  - **Action:** $T_1$ **WOUNDS $T_2$**. The DBMS preempts the lock on $Q$, rolls $T_2$ back (retaining $\text{TS}=20$), and grants the lock immediately to $T_1$.
- **Request B ($T_3$ requests $Q$ held by $T_2$):**
  - Requester: $T_3$ ($\text{TS}=30$); Holder: $T_2$ ($\text{TS}=20$).
  - $\text{TS}(T_3) > \text{TS}(T_2) \implies 30 > 20$ (Younger requests Older).
  - **Action:** $T_3$ is **allowed to WAIT** until $T_2$ releases $Q$.

**Summary Table:**

| Scenario | Requester vs. Holder | Wait-Die Action | Wound-Wait Action |
| :--- | :---: | :---: | :---: |
| **Request A ($T_1 \to T_2$)** | Older requests Younger ($10 < 20$) | $T_1$ **waits** | $T_1$ **wounds $T_2$** ($T_2$ rolls back) |
| **Request B ($T_3 \to T_2$)** | Younger requests Older ($30 > 20$) | $T_3$ **dies** ($T_3$ rolls back) | $T_3$ **waits** |

## ⚡ Exam Tips & Common Mistakes

- **Who Waits Rule:** Remember: In wait-die, **only the older transaction waits**. In wound-wait, **only the younger transaction waits**.
- **Who Is Rolled Back:** In wait-die, the requesting transaction dies. In wound-wait, the holding transaction is wounded and rolled back.
- **The Timestamp Trap:** Do not state that rolled-back transactions get new timestamps here. They keep their **original** timestamps to prevent starvation.
- **Locking Is Still Used:** Both schemes use standard locks. Timestamps are consulted only to resolve lock contention without forming deadlock cycles.
