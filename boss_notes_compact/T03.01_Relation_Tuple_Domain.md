# T03.1: Relation, Tuple, Attribute, and Domain

> **Sources:** Silberschatz 7e Ch. 2 (§2.1–2.2) · Lecture Deck 02 (Slides 2–5) · Lecture Deck 03 (Slide 6) · Class Notes (Raidah p. 12; Fahim p. 18, 26)

## Structure of the Relational Model

The relational model stores data in two-dimensional tables called relations.

**Relation:** A relation is a two-dimensional table made of rows and columns. Mathematically, a relation $r$ on schema $R(A_1, A_2, \dots, A_n)$ is a subset of the Cartesian product of its attribute domains:

$$
r(R) \subseteq \text{dom}(A_1) \times \text{dom}(A_2) \times \dots \times \text{dom}(A_n)
$$

Because a relation is a mathematical set of tuples, duplicate rows are forbidden in relational theory.

**Tuple:** A tuple is a single row or record in a relation. Mathematically, an $n$-tuple is an ordered list of $n$ values $\langle v_1, v_2, \dots, v_n \rangle$ where each value $v_i \in \text{dom}(A_i)$.

**Attribute:** An attribute is a named column of a relation. It represents a specific property or field describing the entity.

**Domain:** A domain is the set of all permitted and meaningful values that an attribute can take.

**Relation Schema:** The logical blueprint of a relation, written as $R(A_1, A_2, \dots, A_n)$. It specifies the table name, columns, and integrity rules. It is static and changes rarely.

**Relation Instance:** The specific set of rows populated in a table at a given point in time. It is dynamic and changes whenever rows are inserted, updated, or deleted.

## Core Relational Invariants

The relational model follows four fundamental rules:

1. **Cartesian Product Subset:**  
   If attributes have domains $\text{dom}(A_1), \dots, \text{dom}(A_n)$, the Cartesian product $\text{dom}(A_1) \times \dots \times \text{dom}(A_n)$ contains all possible value combinations. A table instance $r(R)$ stores only the combinations that exist in the real world. Thus, $r(R)$ is a formal mathematical subset of that product.

2. **Tuples are Unordered:**  
   In set theory, element order does not change set identity. Swapping rows does not create a new relation. The database table represents the same relation instance regardless of row display order.

3. **Domains Must Be Atomic (Indivisible):**  
   **Atomic Domain:** An attribute domain is atomic if its values are considered indivisible units.  
   - Composite values are not allowed in one cell. For example, an address must be split into `street`, `city`, and `zip_code` if parts are queried separately.
   - Multivalued lists or sets are not allowed in one cell. Multiple phone numbers must be placed in separate rows or in a child table.
   - Requiring atomic domains is the exact definition of First Normal Form (1NF).

4. **The Special `null` Value:**  
   The marker `null` signifies an unknown, unrecorded, or inapplicable value. It belongs to every domain. Because equality between unknown values cannot be determined, `null` introduces three-valued logic (`TRUE`, `FALSE`, `UNKNOWN`) into SQL conditions.

## Domain vs. Data Type

Students often confuse domain and data type. They operate at two different abstraction levels:

- A **data type** is a physical, machine-level storage specification. It tells the DBMS how many bytes to allocate and how to format bits in memory (such as `INT`, `VARCHAR(30)`, or `FLOAT`).
- A **domain** is a conceptual, real-world constraint set. It defines what values make semantic sense for that column in business logic.

### Distinction Table

| Comparison Point | Domain (Logical Level) | Data Type (Physical Level) |
| :--- | :--- | :--- |
| **Concept Level** | Conceptual and semantic level. Reflects real-world business meaning. | Physical implementation level. Specifies computer memory format. |
| **Values Allowed** | Strict subset of meaningful values (e.g., letter grades `{'A', 'B', 'C', 'F'}`). | Broad machine-level range (e.g., `CHAR(1)` accepts 256 ASCII symbols). |
| **Validation** | Enforces logical rules and business checks (such as `student_age BETWEEN 16 AND 40`). | Restricts storage width and category (such as 4-byte `INTEGER`). |
| **Compatibility** | Two attributes with the same data type can have completely different domains. | Two attributes share a data type if their physical storage matches. |

### Concrete Example

Consider two attributes: `student_age` and `monthly_salary`.  
Both columns can use the `INT` data type in SQL. But they belong to different domains:
- $\text{dom}(\text{student\_age}) = \{x \in \mathbb{Z} \mid 16 \le x \le 100\}$ (measured in years).
- $\text{dom}(\text{monthly\_salary}) = \{x \in \mathbb{Z} \mid x \ge 0\}$ (measured in currency units).

Adding them (`student_age + monthly_salary`) or comparing them is accepted by the CPU, but makes no sense logically. The relational model treats them as distinct domains.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.3(b) · Differentiate Between Domain and Data Type · 02 Marks

> *Section A · Asked in: 2018 Q.3(b) (2 marks) · L1*

**Question (2018 Q.3(b)).** Differentiate between domain and data type.

**Answer.**

A **domain** is the logical set of all valid values that an attribute can take. It defines real-world meaning and business constraints.  
A **data type** is a physical storage format recognized by the computer hardware and DBMS. It defines memory layout and low-level bit representation.

| Comparison Point | Domain | Data Type |
| :--- | :--- | :--- |
| **Concept Level** | Conceptual and semantic level. It reflects business meaning. | Physical implementation level. It specifies storage layout. |
| **Values Allowed** | Strict set of valid real-world values (for example, letter grades `{'A', 'B', 'C', 'F'}`). | Broad machine-level value range (for example, `CHAR(2)` accepts any two characters). |
| **Constraints** | Carries logical rules and business checks (such as `age >= 18`). | Only restricts memory size and storage category (such as `INT`). |
| **Equivalence** | Two attributes with the same data type can have different domains. | Two attributes share the same data type if their storage format matches. |

*Example:* `student_age` and `monthly_salary` can both use the `INT` data type. But they belong to different domains. Adding an age to a salary makes no logical sense.

## ⚡ Exam Tips & Common Mistakes

- **Use the Age vs. Salary Example:** In any question contrasting domain and data type, use two integer columns like `age` and `salary`. It shows why identical data types can have incompatible domains.
- **Connect Atomicity to 1NF:** When defining atomic domains, mention that indivisible values form the core condition of First Normal Form (1NF).
- **Use Tables for Distinctions:** For 2-mark comparison questions, write a 4-row markdown table for faster scoring and full marks.
