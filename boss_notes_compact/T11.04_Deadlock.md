# T11.04: Deadlock Handling: Prevention, Detection, and Wait-For Graph

> **Topic:** T11 · Concurrency Control Protocols | **Priority:** 🟠 | **Exam Frequency:** 4/7 finals (17 marks)
> **Sources:** Silberschatz 7e Ch. 18 (§18.2, pp. 849–853) · Lecture Deck 08 (Slides 20–25) · Raidah Notes (pp. 28–29)

---

## Deadlock and the Coffman Conditions

**Deadlock:** A state where two or more transactions are waiting indefinitely for locks held by each other in a circular chain. None of the transactions can continue without external intervention.

A deadlock can occur if and only if four conditions hold simultaneously:

1. **Mutual Exclusion:** At least one resource is held in an exclusive (non-shareable) mode.
2. **Hold and Wait:** A transaction holds at least one lock while waiting for another lock held by another transaction.
3. **No Preemption:** The system cannot forcibly seize locks from a holding transaction.
4. **Circular Wait:** A closed chain of transactions exists such that $T_0$ waits for $T_1$, $T_1$ waits for $T_2$, ..., and $T_n$ waits for $T_0$.

Deadlock prevention works by breaking at least one of these four conditions.

---

## Deadlock Prevention Protocols

**Deadlock Prevention:** A set of locking rules that ensures the system never enters a deadlock state. Four standard schemes exist (Lecture Deck 08, Slides 22–23):

### 1. Pre-declaration (Locking All Items Upfront)
- Each transaction must request and acquire all required locks at once before execution begins. If any item is unavailable, no locks are granted and the transaction waits.
- **Why it works:** Breaks the *Hold and Wait* condition.
- **Drawbacks:** Predicting all needed records in advance is difficult. Locking unused records lowers concurrency.

### 2. Lock Ordering (Total / Graph-Based Ordering)
- Impose a strict global order on all data items ($d_1 < d_2 < \dots < d_n$).
- A transaction can only request a lock on item $d_j$ if it already holds locks on items that precede $d_j$.
- **Why it works:** Breaks the *Circular Wait* condition because wait chains only move in one direction.

### 3. Timestamp-Based Schemes (`Wait-Die` and `Wound-Wait`)
- Each transaction $T_i$ is assigned a unique startup timestamp $\text{TS}(T_i)$ upon arrival.
- When $T_i$ requests a lock held by $T_j$, the manager compares timestamps:

| Scheme | When $T_i$ requests item held by $T_j$ | Type |
| :--- | :--- | :--- |
| **Wait-Die** | If $T_i$ is older ($\text{TS}(T_i) < \text{TS}(T_j)$), $T_i$ **waits**.<br>If $T_i$ is younger ($\text{TS}(T_i) > \text{TS}(T_j)$), $T_i$ **dies** (rolls back). | Non-preemptive |
| **Wound-Wait** | If $T_i$ is older ($\text{TS}(T_i) < \text{TS}(T_j)$), $T_i$ **wounds** $T_j$ ($T_j$ rolls back).<br>If $T_i$ is younger, $T_i$ **waits**. | Preemptive |

- **Starvation Rule:** A rolled-back transaction restarts with its **original timestamp** so its seniority increases over time until it cannot be aborted. *(Detailed trace in T11.05).*

### 4. Timeout-Based Scheme
- A transaction waits for a lock for only a set amount of time. If the lock is not granted within the interval, the transaction times out and rolls back.
- **Trade-off:** Easy to implement, but hard to tune: short timeouts abort innocent transactions, while long timeouts waste time during real deadlocks.

---

## Deadlock Detection and the Wait-For Graph

When prevention is not used, the DBMS allows locks freely and monitors dependencies using a **wait-for graph**.

**Wait-For Graph:** A directed graph $G = (V, E)$ where vertices $V$ represent active transactions, and directed edges $E$ represent lock wait dependencies:
- **Vertices ($V$):** Active transactions $\{T_1, T_2, \dots, T_n\}$.
- **Directed Edge ($T_i \to T_j$):** Transaction $T_i$ is waiting for transaction $T_j$ to release a conflicting lock. The edge is removed once $T_j$ releases the lock.

> **Cycle Detection Theorem:** The database system is in a deadlock state **if and only if** the wait-for graph contains a **directed cycle**.

![Wait-for graph showing deadlock cycle T1 to T2 to T1](diagrams/T11_2017_Q7a_deadlock_wait_for_graph.jpg)  
*Figure: Wait-for graph with a cycle indicating deadlock (Source: Course Archive)*

### Deadlock Recovery: Breaking the Cycle

Once a cycle is detected, the DBMS breaks the deadlock in three steps:

1. **Victim Selection:** Choose one transaction in the cycle to roll back based on minimum cost:
   - How long the transaction has run.
   - How many data items it has modified.
   - How many locks it currently holds.
   - How many transactions will be affected by its rollback.
2. **Rollback:**
   - **Total Rollback:** Abort the transaction completely and restart it.
   - **Partial Rollback:** Roll back only to the savepoint before the conflicting lock was requested.
3. **Starvation Prevention:** Track the number of times a transaction has been aborted. Include this count in victim selection so an unlucky transaction is not repeatedly chosen.

## Prevention vs. Detection: Cost Trade-offs

Deadlock prevention and deadlock detection offer different engineering trade-offs (Textbook Exercise 18.20, tested in 2018 Q.5(b)):

### Prevention / Avoidance Is Less Expensive When:
1. **High Lock Contention:** Many transactions access the same records, making deadlocks frequent. Detection would waste substantial CPU time on repeated cycle searches and rollbacks.
2. **Long or Resource-Heavy Transactions:** Aborting long transactions near completion wastes large amounts of processing and disk I/O.
3. **High Cycle Detection Overhead:** Updating and scanning the wait-for graph for thousands of concurrent transactions creates a CPU bottleneck.

### Detection and Recovery Is Less Expensive When:
1. **Deadlocks Are Rare:** Transactions access disjoint data items, so wait cycles almost never form.
2. **Short Transactions:** Quick queries finish in milliseconds, so an occasional abort costs very little. Transactions run without upfront locking delays.

**Question (2017 Q.7(b)).** Define deadlock. Explain how deadlock is prevented?

**Answer.**

**1. Deadlock Definition:**  
A deadlock is a condition in which two or more transactions are waiting indefinitely for locks held by each other. None of the transactions can continue without external intervention.

**2. Deadlock Prevention Methods:**  
Deadlock prevention protocols ensure that the system never enters a deadlock state. Four standard schemes are:

1. **Pre-declaration (Pre-claiming All Locks):**  
   Each transaction must lock all required data items at once before execution begins. If any item is unavailable, no locks are granted and the transaction waits.

3. **Timestamp-Based Schemes (Preemption and Rollback):**  
   Each transaction $T_i$ is assigned a unique timestamp $\text{TS}(T_i)$ when it begins. The system compares timestamps to decide whether to wait or roll back:

   | Scheme | When $T_i$ requests item held by $T_j$ | Type |

   | **Wait-Die** | If $T_i$ is older ($\text{TS}(T_i) < \text{TS}(T_j)$), $T_i$ **waits**.<br>If $T_i$ is younger ($\text{TS}(T_i) > \text{TS}(T_j)$), $T_i$ **dies** (rolls back). | Non-preemptive |
   | **Wound-Wait** | If $T_i$ is older ($\text{TS}(T_i) < \text{TS}(T_j)$), $T_i$ **wounds** $T_j$ ($T_j$ rolls back).<br>If $T_i$ is younger, $T_i$ **waits**. | Preemptive |

4. **Timeout-Based Scheme:**  
   A transaction waits for a lock for only a set amount of time. If the lock is not granted within the interval, the transaction times out and rolls back.

### 🎯 GQ2 · 2018 Q.5(b) · Deadlock in Transaction Management and Cost Trade-offs · [04 Marks]

> *Section B · Asked in: 2018 · L1 (asked once)*

**Question (2018 Q.5(b)).** What do you know about deadlock in transaction management? Under what conditions it is less expensive to avoid deadlock than to allow deadlocks to occur and then to detect them?

**Answer.**

**Deadlock in Transaction Management:**  
A deadlock is an execution state where a set of transactions $\{T_1, T_2, \dots, T_n\}$ cannot proceed because each transaction waits for a lock held by another transaction in the set. A circular wait forms in the wait-for graph. The DBMS must intervene, select a victim transaction, and roll it back to break the cycle.

**When Avoidance / Prevention is Less Expensive Than Detection:**  
Deadlock avoidance or prevention is less expensive than detection and recovery under the following conditions:

1. **High Lock Contention (High Conflict Probability):**  
   When many concurrent transactions compete for the same data items, deadlocks occur frequently. Deadlock detection would repeatedly discover cycles, causing frequent, costly rollbacks. Prevention stops deadlocks before they happen.
2. **Long-Running or Resource-Intensive Transactions:**  
   Rolling back a transaction that has performed extensive computation or heavy disk writes wastes substantial system work. Prevention avoids deep rollbacks.
3. **High Overhead of Cycle Detection:**  
   Continuously maintaining wait-for graphs and running cycle-detection searches under heavy workloads adds CPU overhead. Prevention avoids this monitoring burden.

**When Detection is Less Expensive:**  
When deadlocks are **rare** (short transactions, low concurrency, mostly disjoint data items), detection is cheaper. Prevention mechanisms reduce concurrency or cause false-positive aborts. Detection allows transactions to run freely and resolves only the rare deadlock that occurs.

### 🎯 GQ3 · 2020 Q.7(a) · Deadlock Definition and Two-Phase Locking Protocol · [04 Marks]

> *Section B · Asked in: 2020 · L1 (asked once)*

**Question (2020 Q.7(a)).** What is deadlock? Describe the time-shared locking protocol with example.

**Answer.**

*Assumption: "Time-shared locking protocol" is an exam misprint for the Two-Phase Locking (2PL) protocol.*

**Deadlock:**  
A deadlock is a situation where two or more transactions are in a mutual wait condition, each waiting for a data lock held by the other. Neither transaction can make progress.

**Two-Phase Locking (2PL) Protocol:**  
The Two-Phase Locking protocol ensures conflict serializability by requiring that each transaction acquires and releases locks in two distinct phases:

1. **Growing Phase:** A transaction may acquire locks (shared or exclusive) and upgrade locks ($S \to X$). It cannot release any locks.
2. **Shrinking Phase:** A transaction may release held locks and downgrade locks ($X \to S$). It cannot acquire any new locks.

**Lock Point:**  
The point where a transaction acquires its final lock is its **lock point**. Serializability is guaranteed in the order of transaction lock points.

**Example:**  
Consider transaction $T_1$ modifying accounts $A$ and $B$:

| Step | Action | Phase |
| :---: | :--- | :--- |
| 1 | $\text{lock-S}(A)$; $\text{read}(A)$ | Growing |
| 2 | $\text{lock-X}(B)$; $\text{read}(B)$; $\text{write}(B)$ | Growing (**Lock Point**) |
| 3 | $\text{unlock}(A)$ | Shrinking begins |
| 4 | $\text{unlock}(B)$ | Shrinking |

$T_1$ obtains all locks before releasing any lock. This satisfies 2PL and guarantees serializability.

### 🎯 GQ4 · 2021 Q.8(a) · Deadlock Detection on Wait-For Graph · [05 Marks]

> *Section B · CLO1 · Asked in: 2021 · L1 (asked once)*

**Question (2021 Q.8(a)).** What is deadlock? Consider the following wait-for-graph:

![Wait-for-graph for Q.8(a)](diagrams/T11_2021_Q8a_wait_for_graph_pyq.jpg)  
*Figure 2021_Q8.a: Wait-for-graph for deadlock detection (Source: Page 2, Q.8(a))*

Determine whether the schedule contains any deadlock or not.

**Answer.**

**Deadlock:**  
A deadlock is a state where each transaction in a set is waiting for a resource or data lock held by another transaction in that set. None of the transactions can continue execution.

**Analysis of the Wait-For Graph:**  
The given wait-for graph has:
- **Vertices (Transactions):** $V = \{T_1, T_2, T_3, T_4, T_5\}$
- **Directed Edges:** $E = \{(T_1, T_4), (T_1, T_2), (T_1, T_3), (T_4, T_5), (T_5, T_2), (T_2, T_4)\}$

A directed edge $T_i \to T_j$ means transaction $T_i$ is waiting for transaction $T_j$ to release a required lock.

**Cycle Detection:**  
We trace the directed edges among transactions $T_2, T_4,$ and $T_5$:

$$
T_4 \to T_5 \to T_2 \to T_4
$$

1. $T_4$ is waiting for $T_5$.
2. $T_5$ is waiting for $T_2$.
3. $T_2$ is waiting for $T_4$.

This forms a closed directed cycle.

**Verdict:**  
**Yes, the schedule contains a deadlock.**

**Transactions in Deadlock:**  
Transactions $\mathbf{T_2, T_4, \text{ and } T_5}$ are deadlocked. (Note: $T_1$ is waiting on $T_2, T_3, T_4$, but is not part of the cycle. $T_3$ has no outgoing edges and is not blocked).

**Breaking the Deadlock:**  
The DBMS must select one transaction in the cycle ($T_2, T_4$, or $T_5$) as a **victim** based on minimum abort cost, roll it back, and release its locks. This breaks the cycle and allows the remaining transactions to complete.

## ⚡ Exam Tips & Common Mistakes

- **Write Out the Cycle Fully:** On graph questions like 2021 Q.8(a), write the complete loop ($T_4 \to T_5 \to T_2 \to T_4$) including the repeated node so the grader sees the closed cycle instantly.
- **Do Not Include Blocked Nodes in Deadlock Set:** In 2021 Q.8(a), $T_1$ has arrows into the cycle ($T_1 \to T_2, T_1 \to T_4$). $T_1$ is blocked, but it is NOT part of the deadlock cycle because no edges lead back to $T_1$. Only list cycle nodes as deadlocked.
- **Recognize the 2020 Q.7(a) Typo:** "Time-shared locking protocol" is a printing typo for Two-Phase Locking (2PL). Mention the typo in one line and write the full 2PL answer.
- **Wait-For Graph vs. Precedence Graph:** A cycle in a **Precedence Graph** (`T10`) means the schedule is **not conflict serializable**. A cycle in a **Wait-For Graph** (`T11`) means active transactions are in a **deadlock**.
