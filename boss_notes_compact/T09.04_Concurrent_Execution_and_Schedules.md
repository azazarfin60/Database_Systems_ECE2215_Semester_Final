## Core Concepts: Schedules and Concurrency

**Transaction:** A transaction is a logical unit of program execution that accesses and updates data items in a database.

**Schedule:** A schedule is a sequence of instructions specifying the chronological execution order of concurrent transactions. A valid schedule must contain all operations of its participating transactions, preserve the internal order within each transaction, and end with an explicit `commit` or `abort`.

**Throughput and Resource Utilization:** System throughput is the average number of transactions completed per unit time. Resource utilization is the fraction of time CPU and disk subsystems are actively processing. Concurrent execution maximizes both.

Modern database systems run multiple transactions concurrently for two primary reasons:

1. **Higher Processor and Disk Utilization (Better Throughput):**  
   Transactions mix CPU operations (calculations, comparisons) and disk I/O operations (reading and writing data pages). Because the CPU and disk controllers are independent hardware devices, they operate in parallel. While one transaction waits for a disk read to complete, the CPU executes calculations for another transaction. Keeping hardware busy increases system **throughput** (transactions completed per second).

2. **Reduced Average Response Time (Lower Waiting Time):**  
   Workloads mix short queries (such as a 5-millisecond balance check) with long batch transactions (such as a 2-hour payroll job). In a serial schedule, a short transaction queued behind a long one must wait hours. Interleaving operations allows short transactions to run in between and complete quickly, cutting the average response time.

## Comparing Schedule Classes

**Serial Schedule:** An execution sequence where transactions run strictly one after another without interleaving. Each transaction finishes completely before the next begins. For $n$ transactions, there are $n!$ possible serial schedules.

**Concurrent Schedule:** An interleaved execution sequence where operations of multiple transactions overlap in time.

**Serializable Schedule:** A concurrent, interleaved schedule whose final database state is identical to the outcome produced by some serial schedule.

### Serial vs. Concurrent Schedule

| Feature | Serial Schedule | Concurrent Schedule |
| :--- | :--- | :--- |
| **Execution Pattern** | Non-interleaved. One transaction finishes completely before the next starts. | Interleaved. Operations from different transactions overlap in time. |
| **Resource Use** | Low. CPU sits idle while the transaction waits for disk I/O. | High. CPU runs calculations for one transaction while disk serves another. |
| **Response Time** | High average response time; short transactions wait behind long ones. | Low average response time; short transactions finish quickly. |
| **Concurrency Control** | None needed. Execution is safe from interference by default. | Essential. Requires protocols (locks or timestamps) to prevent data corruption. |
| **Total Possible Orders** | Exactly $n!$ possible serial schedules for $n$ transactions. | Vastly greater than $n!$ due to all possible operation interleavings. |

### Serial vs. Serializable Schedule

| Feature | Serial Schedule | Serializable Schedule |
| :--- | :--- | :--- |
| **Instruction Interleaving** | No interleaving. Transactions run strictly one after another. | Interleaved. Operations from multiple transactions interleave over time. |
| **System Concurrency** | Zero concurrency. No hardware parallelism. | High concurrency. CPU and disk work in parallel across transactions. |
| **Throughput & Latency** | Low throughput. Long queue delays for short transactions. | High throughput. Short transactions complete with low average response time. |
| **Correctness** | Always correct and consistent by default. | Correct only if its final effect matches some serial execution. |
| **Verification** | No testing required. | Must be verified (e.g., cycle check on a precedence graph). |
| **Relationship** | Every serial schedule is trivially serializable. | Most serializable schedules are concurrent and non-serial. |

**Question.** Define transaction and schedule. What is the difference between serial schedule and serializable schedule?

**Answer.**

#### 1. Definitions
- **Transaction:** A logical unit of program execution that accesses and possibly updates various data items in a database.
- **Schedule:** A sequence of instructions that specifies the chronological order in which instructions of concurrent transactions are executed. A schedule must contain all operations of its constituent transactions and preserve the internal operation order within each transaction.

#### 2. Difference Between Serial Schedule and Serializable Schedule

| Feature | Serial Schedule | Serializable Schedule |
| :--- | :--- | :--- |
| **Instruction Interleaving** | No interleaving. Transactions run strictly one after another; each finishes before the next begins. | Instructions of multiple transactions are interleaved concurrently. |
| **System Concurrency** | Zero concurrency. Hardware sits idle during disk I/O waits. | High concurrency. CPU and disk operate in parallel across transactions. |
| **Throughput & Latency** | Low throughput. Short transactions suffer long queue delays. | High throughput. Short transactions complete with low average response time. |
| **Correctness** | Always correct and consistent by default. | Correct only if it produces the same final state as some serial execution. |
| **Verification** | No verification needed. | Requires testing (e.g., precedence graph cycle check for conflict serializability). |

### 🎯 GQ2 · CT-04 Q.02 · Serial vs. Concurrent Schedule & Advantages of Concurrency · 04 Marks

> *Asked in: CT-04 (CO3) · L1 (asked once)*

**Question.** Differentiate between a serial schedule and a concurrent schedule. Mention two advantages of concurrent execution of transactions.

**Answer.**

#### 1. Difference Between Serial Schedule and Concurrent Schedule

| Feature | Serial Schedule | Concurrent Schedule |
| :--- | :--- | :--- |
| **Execution Pattern** | Non-interleaved. One transaction runs to completion before another begins. | Interleaved. Operations from different transactions overlap in time. |
| **Resource Use** | Low. CPU remains idle while a transaction waits for disk I/O. | High. CPU processes one transaction while disk serves another. |
| **Response Time** | High average response time; short transactions wait behind long ones. | Low average response time; short transactions finish quickly. |
| **Need for Concurrency Control** | None. Execution is safe without concurrency control protocols. | Essential. Needs protocols (locks/timestamps) to avoid anomalies. |

#### 2. Two Advantages of Concurrent Execution of Transactions
1. **Increased Processor and Disk Use (Better Throughput):**  
   A transaction consists of both CPU and disk I/O operations. The CPU and disk subsystems can operate in parallel. While one transaction performs disk reads or writes, the CPU can execute calculations for another transaction. This parallel operation keeps hardware busy and increases transaction throughput.
2. **Reduced Average Response Time (Lower Waiting Time):**  
   In a serial schedule, a short transaction must wait for preceding long-running transactions to finish. Concurrent execution allows transactions to share CPU cycles and disk accesses. Short transactions complete without unpredictable delays, reducing average response time.

## ⚡ Exam Tips & Common Mistakes

- **Do Not Conflate Concurrent and Serializable:** A concurrent schedule is *any* interleaved schedule, including bad ones that corrupt data. A serializable schedule is a *safe* concurrent schedule whose outcome matches a serial run.
- **State Both CPU and Disk:** When explaining throughput gains, explicitly state that the CPU runs calculations for one transaction while the disk handles I/O for another.
- **State the $n!$ Formula:** For $n$ transactions, there are exactly $n!$ valid serial schedules, whereas concurrent interleavings are vastly more numerous.
- **Use Comparison Tables:** In "differentiate" questions, organize answers into a clean comparison table with explicit evaluation criteria in the left column.
