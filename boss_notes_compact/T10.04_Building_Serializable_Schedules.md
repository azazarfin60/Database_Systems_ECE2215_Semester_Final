# T10.4: Building Serializable and Non-Serializable Schedules

> **Topic:** T10 · Serializability | **Priority:** 🟡 | **Exam Frequency:** 2/7 finals (13 marks)
> **Sources:** Silberschatz 7e Ch. 17 (§17.1, §17.6, Exercise 17.15) · Lecture Deck 07 (Slides 10–21) · Raidah Notes (T10)

---

## 1. The Cross-Reading Problem Setup

**Consistency Requirement (Database Invariant):** A condition that the database state must satisfy before and after any isolated transaction execution, such as $A = 0 \lor B = 0$.

**Serializable Schedule:** A concurrent schedule whose outcome and final database state are identical to some serial execution ($\langle T_1, T_2 \rangle$ or $\langle T_2, T_1 \rangle$), preserving database consistency.

**Concurrency Control:** The DBMS mechanism coordinating simultaneous transactions to ensure Consistency and Isolation without sacrificing throughput.

Consider the classic two transactions from Silberschatz Exercise 17.15 (asked in 2017 Q.5(c)):

```text
T1:                              T2:
  read(A);                         read(B);
  read(B);                         read(A);
  if A = 0 then B := B + 1;        if B = 0 then A := A + 1;
  write(B);                        write(A);
```

- Initial values: $A = 0, B = 0$.
- Consistency requirement: $A = 0 \lor B = 0$.

### Serial Baselines Preserving Consistency

- **Serial schedule $\langle T_1, T_2 \rangle$:** $T_1$ reads $A=0, B=0$, sets $B := 1$, and writes $B = 1$. Next, $T_2$ reads $B=1, A=0$. Because $B = 0$ is false ($1 \neq 0$), $T_2$ does not change $A$. Final state: $A = 0, B = 1$ (consistent).
- **Serial schedule $\langle T_2, T_1 \rangle$:** $T_2$ reads $B=0, A=0$, sets $A := 1$, and writes $A = 1$. Next, $T_1$ reads $A=1, B=0$. Because $A = 0$ is false ($1 \neq 0$), $T_1$ does not change $B$. Final state: $A = 1, B = 0$ (consistent).

Every serial schedule produces either $(0, 1)$ or $(1, 0)$. Neither produces $(1, 1)$.

---

## 2. The Read-First Recipe for Non-Serializable Schedules

To construct an interleaved non-serializable schedule, let both transactions complete their `read` operations before either executes its `write` operation:
1. $T_1$ and $T_2$ both read initial values $A = 0$ and $B = 0$.
2. Both `if` conditions evaluate to true.
3. $T_1$ writes $B = 1$ and $T_2$ writes $A = 1$.
4. Final state is $A = 1, B = 1$, violating $A = 0 \lor B = 0$.

### Why No Genuinely Interleaved Schedule Can Be Serializable

For an execution to be interleaved, both transactions must start before either finishes:
1. **On item $A$:** $T_1$'s first step is `read(A)` and $T_2$'s last step is `write(A)`. In an interleaved run, $T_1$ must read $A$ before $T_2$ writes $A$. If $T_2$ wrote $A$ first, $T_2$ would have already completed all its steps, making it the serial schedule $\langle T_2, T_1 \rangle$. Thus, $T_1 \to T_2$.
2. **On item $B$:** Symmetrically, $T_2$'s first step is `read(B)` and $T_1$'s last step is `write(B)`. In an interleaved run, $T_2$ must read $B$ before $T_1$ writes $B \implies T_2 \to T_1$.

Every genuinely interleaved execution forces both $T_1 \to T_2$ and $T_2 \to T_1$, creating cycle $T_1 \longleftrightarrow T_2$. Thus, **no concurrent execution of $T_1$ and $T_2$ can produce a serializable schedule**.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.5(c) · 06 Marks

> *Section B · Asked in: 2017 · L1 (asked once)*

**Question (2017 Q.5(c)).** Consider the following two transactions.

**T1:**  
  `read(A);`  
  `read(B);`  
  `if A = 0 then B:=B+1;`  
  `write(B);`

**T2:**  
  `read(B);`  
  `read(A);`  
  `if B = 0 then A:=A+1;`  
  `write(A);`

Let the consistency requirement be $A = 0$ or $B = 0$ with $A=B=0$ the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a nonserializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

**Answer.**

Initial state: $A = 0, B = 0$. Consistency requirement: $A = 0 \lor B = 0$.

In any serial execution, the database remains consistent:
- Serial order $\langle T_1, T_2 \rangle$: $T_1$ reads $A=0$, sets $B=1$, writes $B=1$. Then $T_2$ reads $B=1$. The condition $B=0$ fails, so $T_2$ does not change $A$. Final state: $A=0, B=1$ (consistent).
- Serial order $\langle T_2, T_1 \rangle$: $T_2$ reads $B=0$, sets $A=1$, writes $A=1$. Then $T_1$ reads $A=1$. The condition $A=0$ fails, so $T_1$ does not change $B$. Final state: $A=1, B=0$ (consistent).

---

#### (i) Concurrent Execution Producing a Nonserializable Schedule

Consider the following interleaved execution where both transactions read the initial values before either writes:

| Step | $T_1$ | $T_2$ | Local state |
| :--: | :-- | :-- | :-- |
| 1 | `read(A);` | | $T_1$ reads $A = 0$ |
| 2 | | `read(B);` | $T_2$ reads $B = 0$ |
| 3 | `read(B);` | | $T_1$ reads $B = 0$ |
| 4 | | `read(A);` | $T_2$ reads $A = 0$ |
| 5 | `if A = 0 then B:=B+1;`<br>`write(B);` | | $T_1$ evaluates $0 = 0$ (true), sets $B = 1$, writes $B = 1$ |
| 6 | | `if B = 0 then A:=A+1;`<br>`write(A);` | $T_2$ evaluates $0 = 0$ (true), sets $A = 1$, writes $A = 1$ |

**Final state:** $A = 1$ and $B = 1$.  
The consistency rule requires $A = 0$ or $B = 0$. Here both are 1. The database is in an **inconsistent state**.

![2017 Q.5(c) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2017_Q5c_precedence_graph.jpg)
*Figure 1: Precedence graph for 2017 Q.5(c) showing cycle between T1 and T2.*

**Proof of nonserializability:**
- $T_1$ reads $A$ (step 1) before $T_2$ writes $A$ (step 6) $\implies T_1 \to T_2$.
- $T_2$ reads $B$ (step 2) before $T_1$ writes $B$ (step 5) $\implies T_2 \to T_1$.
- The precedence graph has a cycle: $T_1 \longleftrightarrow T_2$.

Because it creates a cycle and ends in an inconsistent state that no serial schedule can produce, this schedule is **non-serializable**.

---

#### (ii) Can a Concurrent Execution Produce a Serializable Schedule?

**No.**

**Proof:**
For an execution to be genuinely concurrent (interleaved), both transactions must start before either finishes:
- $T_1$ must read $A$ before $T_2$ writes $A$. If $T_2$ wrote $A$ first, $T_2$ would have already completed its read and write, meaning $T_2$ ran serially before $T_1$. Therefore, in an interleaved run, $T_1$ reads $A$ first $\implies T_1 \to T_2$.
- Similarly, $T_2$ must read $B$ before $T_1$ writes $B$. Otherwise, $T_1$ ran serially before $T_2$. Therefore, $T_2$ reads $B$ first $\implies T_2 \to T_1$.

Any interleaved execution forces both edges $T_1 \to T_2$ and $T_2 \to T_1$. This always creates a directed cycle. Therefore, **no concurrent execution of $T_1$ and $T_2$ can produce a serializable schedule**. Only strictly serial executions ($\langle T_1, T_2 \rangle$ or $\langle T_2, T_1 \rangle$) are serializable.

### 🎯 GQ2 · 2019 Q.4(a) · 07 Marks

> *Section A · Asked in: 2019 · L1 (asked once)*

**Question (2019 Q.4(a)).** What is concurrency control? Consider the following two transactions.

**T1:**  
`read (P);`  
`read (Q);`  
`if P=10 then Q:=Q-5;`  
`write (Q);`

**T2:**  
`read (Q);`  
`read (P);`  
`if Q=10 then P:=P+5;`  
`write (P);`

Let the consistency requirement be P=5 or Q=5 with P=Q=5 the initial values.  
(i) Show a concurrent execution of T1 and T2 that produces a serializable schedule.  
(ii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

*(Note: In the printed question paper, sub-question (ii) is printed identically to (i) as "Is there a concurrent execution of T1 and T2 that produces a serializable schedule?")*

**Answer.**

*Paper Typo Clarification: Sub-question (i) misprinted "non-serializable" as "serializable", and the IF conditions test P = 10 / Q = 10 while initial values are P = Q = 5. Below we address both the intended Silberschatz Exercise 17.15 reading and the literal printed text.*

#### 1. What is Concurrency Control?

**Concurrency control** is the DBMS mechanism that coordinates the simultaneous execution of transactions. It prevents anomalies like lost updates, dirty reads, and unrepeatable reads. It ensures transactions maintain the **Isolation** and **Consistency** ACID properties while maximizing transaction throughput.

---

#### 2. Analysis of the Given Transactions

Initial values: $P = 5, Q = 5$. Consistency condition: $P = 5 \lor Q = 5$.

- **As printed (`if P=10` and `if Q=10`):** Since $P$ and $Q$ start at $5$, both `P = 10` in $T_1$ and `Q = 10` in $T_2$ evaluate to **false**. Neither variable changes, so $T_1$ writes $Q = 5$ and $T_2$ writes $P = 5$.
- **Intended textbook guards (`if P=5` and `if Q=5`):**
  - Serial $\langle T_1, T_2 \rangle$: $T_1$ sees $P=5$, sets $Q := 5 - 5 = 0$, writes $Q=0$. $T_2$ then sees $Q=0 \neq 5$, leaves $P=5$. Final state: $P=5, Q=0$ (consistent).
  - Serial $\langle T_2, T_1 \rangle$: $T_2$ sees $Q=5$, sets $P := 5 + 5 = 10$, writes $P=10$. $T_1$ then sees $P=10 \neq 5$, leaves $Q=5$. Final state: $P=10, Q=5$ (consistent).

---

#### 3. Part (i): Concurrent Execution

##### (a) Intended Reading: Interleaved Execution Producing a Non-Serializable Schedule

Interleave $T_1$ and $T_2$ so both read before either writes:

| Step | $T_1$ | $T_2$ | Action (Intended `if P=5` / `if Q=5`) | Action (As-Printed `if P=10` / `if Q=10`) |
| :--: | :-- | :-- | :-- | :-- |
| 1 | `read(P);` | | $T_1$ reads $P = 5$ | $T_1$ reads $P = 5$ |
| 2 | | `read(Q);` | $T_2$ reads $Q = 5$ | $T_2$ reads $Q = 5$ |
| 3 | `read(Q);` | | $T_1$ reads $Q = 5$ | $T_1$ reads $Q = 5$ |
| 4 | | `read(P);` | $T_2$ reads $P = 5$ | $T_2$ reads $P = 5$ |
| 5 | `write(Q);` | | $P=5$ is true $\implies$ writes $Q = 0$ | $P=10$ is false $\implies$ writes $Q = 5$ |
| 6 | | `write(P);` | $Q=5$ is true $\implies$ writes $P = 10$ | $Q=10$ is false $\implies$ writes $P = 5$ |

![2019 Q.4(a) Precedence Graph showing cycle between T1 and T2](diagrams/T10_2019_Q4a_precedence_graph.jpg)
*Figure 2: Precedence graph for 2019 Q.4(a) interleaved execution showing cycle between T1 and T2.*

- $T_1$ reads $P$ (step 1) before $T_2$ writes $P$ (step 6) $\implies T_1 \to T_2$.
- $T_2$ reads $Q$ (step 2) before $T_1$ writes $Q$ (step 5) $\implies T_2 \to T_1$.
- Cycle: $T_1 \longleftrightarrow T_2$. Thus, this schedule is **NOT conflict serializable** (and under intended guards produces $P = 10, Q = 0$, violating $P = 5 \lor Q = 5$).

##### (b) Literal Reading: Serial Schedule $\langle T_1, T_2 \rangle$

No genuinely interleaved schedule of $T_1$ and $T_2$ can be conflict-serializable. Only a non-interleaved **serial** schedule where $T_1$ finishes completely before $T_2$ begins has an acyclic precedence graph ($T_1 \to T_2$, order $\boxed{\langle T_1, T_2 \rangle}$):

| Step | $T_1$ | $T_2$ | Local Actions (As Printed) |
| :--: | :-- | :-- | :-- |
| 1 | `read(P);` | | $T_1$ reads $P = 5$ |
| 2 | `read(Q);` | | $T_1$ reads $Q = 5$ |
| 3 | `if P=10 then Q:=Q-5;`<br>`write(Q);` | | Condition false; writes $Q = 5$ |
| 4 | | `read(Q);` | $T_2$ reads $Q = 5$ |
| 5 | | `read(P);` | $T_2$ reads $P = 5$ |
| 6 | | `if Q=10 then P:=P+5;`<br>`write(P);` | Condition false; writes $P = 5$ |

---

#### 4. Part (ii): Can a Concurrent Execution Produce a Serializable Schedule?

**No** (not for conflict serializability).

**Proof:**
For an execution to be genuinely concurrent (interleaved), both transactions must start before either finishes:
- **Conflict on $P$:** $T_1$'s first instruction is `read(P)` and $T_2$'s last instruction is `write(P)`. In any interleaved run, $T_1$ reads $P$ before $T_2$ writes $P \implies T_1 \to T_2$.
- **Conflict on $Q$:** Symmetrically, $T_2$'s first instruction is `read(Q)` and $T_1$'s last instruction is `write(Q)`. In any interleaved run, $T_2$ reads $Q$ before $T_1$ writes $Q \implies T_2 \to T_1$.

Every genuinely interleaved execution forces both $T_1 \to T_2$ and $T_2 \to T_1$, creating the cycle $T_1 \longleftrightarrow T_2$. Therefore, **no concurrent execution of $T_1$ and $T_2$ is conflict-serializable**; only the strictly serial schedules $\langle T_1, T_2 \rangle$ and $\langle T_2, T_1 \rangle$ are conflict-serializable.

## ⚡ Exam Tips & Common Mistakes

- **Remember the Read-First Recipe:** To build a non-serializable schedule, place all `read` operations before any `write` operation.
- **Never answer "Yes" to Part (ii):** A serial schedule is not an interleaved concurrent execution. Any interleaved execution creates cycle $T_1 \longleftrightarrow T_2$.
- **Mention both typo interpretations in 2019 Q.4(a):** Explain the intended problem (from Silberschatz Ex. 17.15) and provide both the non-serializable interleaved trace and the serial baseline.
- **Always define concurrency control:** In 2019 Q.4(a), defining concurrency control carries 2 of the 7 marks.
