## Systematic Reduction Rules: E-R Constructs to Relational Tables

**Reduction to Relation Schemas:** The systematic process of translating an E-R diagram (entities, relationships, attributes) into relational tables (`CREATE TABLE` definitions) with well-defined primary keys, foreign keys, and integrity constraints.

Because relational tables must satisfy First Normal Form (1NF), each table cell must store a single atomic value. The conversion follows nine rules:

### Rule 1: Strong Entity Sets with Simple Attributes
**Strong Entity Set Reduction:** Reduces directly to a table whose columns are all simple attributes of the entity set. The primary key of the entity set becomes the primary key of the table.
$$
\text{student}(\underline{\text{ID}}, \text{name}, \text{tot\_cred})
$$

### Rule 2: Composite Attributes (Flattening)
Flattened by creating a separate column for each leaf sub-attribute and omitting the composite parent name.
$$
\text{instructor}(\underline{\text{ID}}, \text{first\_name}, \text{last\_name}, \text{street}, \text{city}, \text{zip})
$$

### Rule 3: Multivalued Attributes (Separate Table)
Spun off into a separate table combining the parent entity's primary key (as a foreign key) and the multivalued attribute. Both columns together form the composite primary key.
$$
\text{inst\_phone}(\underline{\text{ID}}, \underline{\text{phone\_number}})
$$
`FK: ID references instructor(ID)`

### Rule 4: Weak Entity Sets
**Weak Entity Set Reduction:** Reduces to a table containing all weak entity attributes plus the primary key of the identifying strong entity set. The table's composite primary key combines the owner's primary key with the weak entity's discriminator.
$$
\text{section}(\underline{\text{course\_id}}, \underline{\text{sec\_id}}, \underline{\text{semester}}, \underline{\text{year}})
$$
`FK: course_id references course(course_id) ON DELETE CASCADE`

### Rule 5: Many-to-Many ($M:N$) Relationship Sets
**Relationship Set Reduction:** Always requires a dedicated junction table. The primary keys of both participating entity sets become foreign key columns, and together form the composite primary key. Any descriptive attributes on the diamond are included as columns.
$$
\text{takes}(\underline{\text{student\_id}}, \underline{\text{course\_id}}, \text{grade})
$$
`FK: student_id references student(student_id), course_id references course(course_id)`

### Rule 6: Many-to-One and One-to-Many ($N:1$ / $1:N$) Relationships
Merged into the table on the "Many" ($N$) side by adding the primary key of the "One" side as a foreign key column. This avoids creating an unnecessary junction table.
$$
\text{course}(\underline{\text{course\_id}}, \text{title}, \text{credits}, \text{teacher\_id})
$$
`FK: teacher_id references teacher(teacher_id)`
*(Note: If participation on the "Many" side is partial, a separate table may be used to avoid storing NULL foreign key values).*

### Rule 7: One-to-One ($1:1$) Relationship Sets
Merged into either entity table by adding the other table's primary key as a foreign key. To prevent `NULL` values, place the foreign key inside the table that has **total participation**.

### Rule 8: Identifying Relationship Diamonds (Omitted)
Never create a separate table for the double diamond. The weak entity table (Rule 4) already contains the owner's foreign key and existence constraint.

### Rule 9: Non-Binary (Ternary / $n$-ary) Relationship Sets
Requires a dedicated table whose columns include the primary keys of all participating entity sets plus any descriptive attributes on the diamond. The composite primary key is usually the union of all participating primary keys.
$$
\text{scores}(\underline{\text{student\_id}}, \underline{\text{offering\_id}}, \underline{\text{exam\_id}}, \text{marks})
$$

## Comprehensive Reduction Summary Table

| E-R Construct | Relational Table Generated | Primary Key | Foreign Key Constraints |
| :--- | :--- | :--- | :--- |
| **Strong Entity Set $E$** | Table $E(\underline{K}, A_1, A_2, \dots)$ | $K$ (PK of $E$) | None (unless recursive) |
| **Composite Attribute** | Component columns flattened into table $E$ | $K$ | None |
| **Multivalued Attribute $M$ of $E$** | Table $E_M(\underline{K}, \underline{M})$ | $(K, M)$ | $K \to E(K)$ |
| **Weak Entity Set $W$ (Owner $S$)** | Table $W(\underline{K_S}, \underline{D_W}, A_1, \dots)$ | $(K_S, D_W)$ | $K_S \to S(K_S)$ |
| **$M:N$ Relationship Set $R(A, B)$** | Junction table $R(\underline{K_A}, \underline{K_B}, \text{attrs})$ | $(K_A, K_B)$ | $K_A \to A(K_A)$, $K_B \to B(K_B)$ |
| **$1:N$ Relationship Set (Total on $N$)** | Merged into table on "Many" side: $N(\underline{K_N}, \dots, K_1)$ | $K_N$ | $K_1 \to \text{One}(K_1)$ |
| **$1:1$ Relationship Set** | Merged into either table (preferred on total side) | Existing PK | References the other table |
| **Identifying Relationship** | Redundant (Omitted) | N/A | Handled inside weak entity table |
| **Ternary Relationship $R(A, B, C)$** | Table $R(\underline{K_A}, \underline{K_B}, \underline{K_C}, \text{attrs})$ | $(K_A, K_B, K_C)$ | $K_A \to A, K_B \to B, K_C \to C$ |

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2018 Q.2(c) · Ternary Examination Marks E-R Diagram & Relational Data Model · [05 Marks]

> *Section A · Asked in: 2018 · L1 (asked once)*

**Question (2018 Q.2(c)).** Consider a database used to record the marks that students get in different examinations of different course offerings. (i) Construct an E-R diagram that models examinations as entities, and uses a ternary relationship for the above database; (ii) Draw a relational data model for the above corresponding E-R diagram.

**Answer.**

#### (i) E-R Diagram with Ternary Relationship (2.5 Marks)
- Participating Entity Sets: `STUDENT`, `COURSE_OFFERING`, `EXAM`.
- Ternary Relationship: `Scores` connecting all three entity sets.
- Relationship Attribute: `marks` (descriptive attribute placed on `Scores`).

![Ternary relationship diagram for student marks in examinations of course offerings](diagrams/T02_2018_Q2c_ternary_exam_er.jpg)
*Figure 1: Ternary Relationship Model for Student Exam Marks.*

#### (ii) Relational Data Model (Relational Schemas) (2.5 Marks)

**student**(**student_id**, name, dept_name)  
`PK: student_id`

**course_offering**(**offering_id**, semester, year)  
`PK: offering_id`

**exam**(**exam_id**, exam_type, max_marks)  
`PK: exam_id`

**scores**(**student_id**, **offering_id**, **exam_id**, marks)  
`PK: (student_id, offering_id, exam_id)`  
`FK: student_id references student(student_id), offering_id references course_offering(offering_id), exam_id references exam(exam_id)`

## ⚡ Exam Tips & Common Mistakes

- **Placement of Marks Attribute:** Never place `marks` inside `EXAM` or `STUDENT`. Exam entities hold only exam metadata (type, max marks). Obtained marks depend on student, offering, and exam combined, so `marks` must be on the ternary relationship.
- **Do Not Split Ternary into Binary Diamonds:** When a prompt specifies a ternary relationship, draw a single diamond linked to three entity rectangles.
- **Underline All Composite Key Parts:** In relational schemas for junction tables or ternary relationships, clearly underline all composite primary key components.
- **Omit Identifying Diamonds:** Never create an extra table for an identifying relationship diamond. The weak entity table already holds the foreign key.
