# T02.5a: E-R Design: Student and Teacher-Course DBs

> **Topic:** T02 · E-R & EER Modeling | **Priority:** 🔴 High | **Exam Frequency:** 5/7 finals (+ CT-02 Q2) (24 marks)  
> **Sources:** Silberschatz 7e Ch. 6 (§6.1–6.4, §6.9) · Lecture Deck 05 (Slides 7–39) · Class Notes (Raidah pp. 18–19; Fahim pp. 20–30)

---

## The 5-Step E-R Design Recipe

**Entity-Relationship (E-R) Data Model:** A high-level conceptual data model that represents real-world enterprise data using entities, attributes, relationship sets, and integrity constraints.

**Entity:** A distinct real-world object or thing that can be distinguished from other objects.

**Entity Set:** A collection of entities of the same type that share the same attributes, drawn as a **rectangle**.

**Relationship Set:** An association among several entity sets, drawn as a **diamond**.

**Total Participation:** A constraint where every entity in the entity set must participate in at least one relationship instance, drawn as a **double line**.

When translating an exam prompt into an E-R diagram, follow this 5-step recipe:

1. **Step 1: Spot Entity Sets from Key Nouns:** Identify major people, physical objects, or core transaction records (such as `STUDENT`, `ADVISOR`, `COURSE`, `RESULT`). Draw each as a rectangle.
2. **Step 2: Attach Attributes and Underline Primary Keys:** Assign realistic attributes as ovals. Underline the primary key with a solid line. Branch composite attributes and use double ovals for multivalued attributes.
3. **Step 3: Turn Connecting Verbs into Relationship Diamonds:** Action verbs linking nouns (such as *advises*, *registers*, *teaches*, *obtains*) become diamonds. Put descriptive attributes (such as `grade`, `session`) directly on the diamond.
4. **Step 4: Mark Cardinality and Participation Constraints:**
   - Label mapping cardinalities ($1, N, M$) on edges.
   - Use **double lines** for total participation when the prompt says *"must"*, *"at least one"*, or *"every"*. Use **single lines** for optional participation.
5. **Step 5: Notation Check:** Confirm primary keys are underlined, diamonds connect rectangles, and no foreign key attributes are placed inside entity ovals.

---

## Common Design Pitfalls and Silberschatz Rules

- **The Foreign Key Oval Trap:** Never draw a foreign key attribute (like `advisor_id` on `STUDENT`) as an attribute oval on an entity. The relationship diamond itself models the connection. Foreign keys appear only after table reduction.
- **Misplacing Relationship Attributes:** If an attribute depends on both participating entities (such as `marks` or `semester` of registration), place it on the relationship diamond. Putting it on the entity makes it inaccurate across semesters.
- **Overusing Weak Entity Sets:** If an entity has its own unique ID (like `result_id`), model it as a strong entity with total participation, not as a weak entity.

### 🎯 GQ1 · 2017 Q.1(b) / 2024 Q.1(b) · RUET Student Database · [06 Marks / 02 Marks]

> *Section A · Asked in: 2017 (06 Marks), 2024 (02 Marks, CO3) · L2 merge*

**Question (2017 Q.1(b)).** Draw an E-R diagram for RUET student database which can be used to store student's basic information, course advisor's information, subject registration, result information.

**Question (2024 Q.1(b)).** Draw an E-R diagram for RUET student database which can be used to store student’s basic information, course advisor’s information, subject registration, result information.

**Answer.**

#### 1. Entity Sets and Attributes
1. **STUDENT:** Basic information entity.
   - Primary Key: `roll_no` (underlined)
   - Attributes: `name`, `dept_name`, `series`
2. **ADVISOR:** Faculty advisor entity.
   - Primary Key: `advisor_id` (underlined)
   - Attributes: `name`, `designation`, `department`
3. **COURSE (SUBJECT):** Academic course entity.
   - Primary Key: `course_code` (underlined)
   - Attributes: `course_title`, `credits`
4. **RESULT:** Semester examination outcome entity.
   - Primary Key: `result_id` (underlined)
   - Attributes: `semester`, `gpa`, `cgpa`

#### 2. Relationship Sets and Cardinalities
- **`Advises` (1:N):** Connects `ADVISOR` and `STUDENT`. One advisor counsels many students; each student has one advisor. Total participation on `STUDENT` (double line).
- **`Registers` (M:N):** Connects `STUDENT` and `COURSE`. Students register for multiple courses; courses have many students. Total participation on `STUDENT` (double line). Descriptive attributes on diamond: `session`, `semester`.
- **`Obtains` (1:N):** Connects `STUDENT` and `RESULT`. Each student obtains multiple semester results; each result belongs to one student. Total participation on `RESULT` (double line).

### 🎯 GQ2 · 2018 Q.1(c) · Teacher-Student-Course with Participation Constraints · [05 Marks]

> *Section A · Asked in: 2018 · L1 (asked once)*

**Question (2018 Q.1(c)).** What is E-R model? Draw an E-R diagram that includes teacher, student and course entities with following constraints: (i) Each teacher must take at least one course; (ii) A student can register one or more courses; (iii) A course may have teacher or not.

**Answer.**

#### 1. E-R Model Definition
The Entity-Relationship (E-R) model is a high-level conceptual data model. It views the real-world enterprise as a collection of basic objects called entities and relationships among these objects.

#### 2. Constraint Analysis and Line-Style Mapping
- *(i) Each teacher must take at least one course:*  
  **Total participation** of `TEACHER` in relationship `Teaches`. Drawn as a **double line** from `TEACHER` to `Teaches` (cardinality $1..\text{*}$).
- *(ii) A student can register one or more courses:*  
  **Total participation** of `STUDENT` in relationship `Registers`. Drawn as a **double line** from `STUDENT` to `Registers` (cardinality $1..\text{*}$, M:N relationship).
- *(iii) A course may have teacher or not:*  
  **Partial participation** of `COURSE` in relationship `Teaches`. Drawn as a **single line** from `COURSE` to `Teaches` (cardinality $0..1$ or $0..\text{*}$).

#### 3. Entity Sets and Attributes
- **`TEACHER`:** `teacher_id` (PK, underlined), `name`, `dept_name`
- **`STUDENT`:** `student_id` (PK, underlined), `name`, `tot_cred`
- **`COURSE`:** `course_id` (PK, underlined), `title`, `credits`

## ⚡ Exam Tips & Common Mistakes

- **Firm Double Lines:** Trace double lines clearly in exam scripts. Faint double lines risk being misgraded as single lines.
- **Label Every Branch:** Always write $1$, $N$, or $M$ on each line entering a relationship diamond.
- **Foreign Keys Do Not Belong in Entities:** In 2017 Q.1(b), never put `advisor_id` inside `STUDENT`. Let the `Advises` diamond represent the relationship.
- **Mark Calibration:** For 2-mark questions (2024 Q.1(b)), draw rectangles, diamonds, and underlined primary keys. Skip non-essential attribute ovals to save time.
