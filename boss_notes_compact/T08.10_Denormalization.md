# T08.10: Pros and Cons of Normalization and Denormalization

> **Topic:** T08 · Normalization & Functional Dependencies | **Priority:** 🟡 Practical Design | **Exam Frequency:** 0/7 finals · 0 marks [Cross-ref: 2017 Q.3(a) in T08.06]
> **Sources:** Silberschatz 7e Ch. 7 (§7.9.3, §7.1.3) · Lecture Deck 06 (Slides 47–51) · Raidah Class Notes (p. 23)

## Trade-offs in Relational Schema Design

Relational database design balances data consistency against query retrieval speed.

**Normalization:** The formal database design process of splitting relations into smaller, well-structured tables (such as 3NF or BCNF) to eliminate redundant data and prevent modification anomalies.

**Denormalization:** The deliberate process of adding controlled redundancy into a previously normalized database schema. Designers merge relations or replicate columns to eliminate expensive `JOIN` operations and accelerate read queries.

**Materialized View:** A physical database table that stores the precomputed result of a complex query. The DBMS updates it automatically when underlying base tables change, achieving read acceleration while leaving base tables normalized.

### Advantages of Normalization (Deck 06 Slide 47)

1. **Elimination of Data Redundancy:** Each fact is recorded in exactly one location, saving storage and preventing contradictory copies.
2. **Prevention of Modification Anomalies:** Fully protects the database from update, insertion, and deletion anomalies.
3. **Data Integrity and Consistency:** Relationships are enforced cleanly through primary and foreign keys.
4. **Faster Write Operations:** Updates, inserts, and deletes touch narrow tables without locking unrelated columns.
5. **Simpler Table Maintenance:** Narrow tables are cheaper to reorganize, re-index, and back up.

### Disadvantages of Normalization (Deck 06 Slide 48)

1. **Table Proliferation:** High-level normal forms split enterprise data into dozens of narrow tables.
2. **Heavy JOIN Overhead:** Reconstructing full records requires multi-table `JOIN` operations, consuming CPU cycles and memory buffers.
3. **Degraded Read Performance:** Complex queries across millions of rows suffer from slow response times.
4. **Complex SQL:** Application developers must write multi-table joins for everyday queries.
5. **Index Overhead:** Each decomposed table requires primary and foreign key indexes, consuming disk space.

## Denormalization Concepts and Techniques

Denormalization is applied **after** a schema is normalized to 3NF or BCNF. It is not equivalent to leaving a table unnormalized.

### When to Denormalize (Deck 06 Slide 50)

- **Read-Intensive Workloads:** Applications where `SELECT` queries account for over 90% of database operations.
- **High-Frequency Critical Queries:** Core user interactions requiring sub-millisecond response times.
- **Reporting and Data Warehousing (OLAP):** Analytical systems scanning large historical datasets (e.g. Star and Snowflake schemas).
- **Frequent Aggregations:** Eliminating repetitive `SUM()`, `AVG()`, or `COUNT()` calculations on large child tables.

### Common Denormalization Techniques

1. **Pre-Joining Relations (Flattening):** Merging a parent and child table into one.  
   *Example:* Merging `CUSTOMER` and `ORDERS` into a single table eliminates `JOIN` overhead on order lookups.
2. **Replicating Frequently Queried Columns:** Copying a single frequently requested attribute into a child table.  
   *Example:* Adding `CourseTitle` directly into `ENROLLMENT(StudentID, CourseID, CourseTitle, Grade)` avoids joining `COURSE`.
3. **Storing Derived or Summary Attributes:** Storing calculated counts or totals in parent rows.  
   *Example:* Storing `TotalBalance` in `ACCOUNT` rather than summing child `TRANSACTION` rows.
4. **Table Partitioning:** Splitting tables horizontally (by date range) or vertically (separating text blobs from primary columns).

## 🔮 Likely Questions

### 🎯 LQ1 · Pros and Cons of Normalization · 04 Marks

> *Section A / B · Probability: High*

**Question.** Discuss the advantages and disadvantages of database normalization. Why might a database designer deliberately choose to denormalize a database?

**Answer.**

#### 1. Advantages of Normalization
1. **Redundancy Elimination:** Storing each fact in one place saves physical storage space.
2. **Anomaly Elimination:** Completely prevents insertion, update, and deletion anomalies.
3. **Data Integrity:** Simplifies the enforcement of relational constraints and business rules.
4. **Faster Writes:** Narrow tables allow fast `INSERT`, `UPDATE`, and `DELETE` operations.

#### 2. Disadvantages of Normalization
1. **JOIN Performance Penalty:** Querying full entity profiles requires joining multiple tables, which consumes CPU, disk I/O, and buffer memory.
2. **Slower Read Performance:** High-traffic read queries experience latency due to table proliferation.
3. **SQL Query Complexity:** Demands intricate queries with multiple join conditions.

#### 3. Reason for Denormalization
A designer denormalizes a database when read performance becomes a critical bottleneck. In read-heavy systems (such as reporting systems, search engines, and data warehouses), the cost of repeated joins outweighs the cost of managing controlled redundancy.

### 🎯 LQ2 · Denormalization Techniques and Trade-offs · 04 Marks

> *Section A / B · Probability: High*

**Question.** Define denormalization. Describe two common denormalization techniques with examples and discuss their trade-offs.

**Answer.**

#### 1. Definition of Denormalization
**Denormalization** is the deliberate process of introducing controlled data redundancy into an already normalized schema (3NF or BCNF). It minimizes expensive `JOIN` operations and accelerates read-intensive query performance.

#### 2. Two Common Techniques

1. **Replicating Attributes in Child Tables:**
   - *Description:* Duplicating a heavily accessed non-key column from a parent table into a child table.
   - *Example:* In `STUDENT_ENROLLMENT(StudentID, CourseID, Grade)`, adding `CourseName` directly into the table avoids joining `COURSE(CourseID, CourseName)`.
   - *Trade-off:* Read queries run with zero joins. However, if a course name changes, multiple enrollment records must be updated, reintroducing update anomaly risks.

2. **Storing Derived / Pre-Aggregated Values:**
   - *Description:* Storing precalculated summaries directly inside parent records instead of computing them dynamically on demand.
   - *Example:* In `CUSTOMER(CustomerID, CustomerName, TotalOrderAmount)`, storing the sum of all orders avoids scanning thousands of child rows in `ORDERS`.
   - *Trade-off:* Drastically accelerates analytical reporting queries. However, application logic or database triggers must update `TotalOrderAmount` whenever an order is inserted or modified.

## ⚡ Exam Tips & Common Mistakes

- **Denormalized vs. Unnormalized distinction:** Never call an unnormalized table "denormalized." Denormalization is a conscious optimization applied to a schema that has already been normalized.
- **Always mention Materialized Views:** Citing materialized views as an alternative to manual denormalization shows advanced database knowledge.
- **Write penalty:** Whenever you explain the read performance benefits of denormalization, always state the trade-off: slower writes and the risk of update anomalies.
