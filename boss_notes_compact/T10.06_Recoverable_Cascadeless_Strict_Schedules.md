# T10.6: Recoverable, Cascadeless, and Strict Schedules

> **Topic:** T10 · Serializability | **Priority:** ⭐ | **Exam Frequency:** 0/7 finals (High-Yield Candidate)
> **Sources:** Silberschatz 7e Ch. 17 (§17.7, pp. 819–821) · Lecture Deck 08 (Slides 3–8) · Raidah Notes (Suggestions)

---

## 1. Safety Levels of Concurrent Schedules

Serializability ensures consistency when all transactions complete normally. But when a transaction aborts or crashes, the DBMS must undo its changes cleanly. Recoverable, cascadeless, and strict schedules establish this crash recovery safety:

1. **Recoverable:** $T_2$ may read uncommitted data from $T_1$, but $T_2$ cannot commit until $T_1$ commits.
2. **Cascadeless:** $T_2$ cannot read data written by $T_1$ until $T_1$ commits. Cascading rollbacks are eliminated.
3. **Strict:** No transaction can read **or overwrite** data written by $T_1$ until $T_1$ commits or aborts. Rollbacks restore before-images directly without affecting other transactions.

---

## 2. Classification and Containment Hierarchy

![Hierarchy of schedules based on recoverability](diagrams/T10.06_schedule_recoverability_hierarchy__L08_p08_fig01.jpg)
*Figure 1: Classification hierarchy showing nested containment: All Schedules $\supset$ Recoverable $\supset$ Cascadeless $\supset$ Strict (Source: Lecture Deck 08, Slide 8).*

$$
\text{Strict Schedules} \subset \text{Cascadeless Schedules} \subset \text{Recoverable Schedules} \subset \text{All Possible Schedules}
$$

- Every strict schedule is cascadeless and recoverable.
- Every cascadeless schedule is recoverable.
- Non-recoverable schedules are strictly disallowed in ACID databases.

---

## 3. Non-Recoverable Schedules: Dirty Read Hazard

**Non-Recoverable Schedule:** A schedule where transaction $T_j$ reads uncommitted data written by $T_i$ and commits before $T_i$ commits.

| Step | Transaction $T_1$ | Transaction $T_2$ | Database State | Event |
| :--: | :--- | :--- | :---: | :--- |
| 1 | $\text{read}(A)$ | | $A = 100$ | $T_1$ reads balance |
| 2 | $\text{write}(A)$ | | $A = 150$ | Uncommitted dirty write |
| 3 | | $\text{read}(A)$ | $A = 150$ | $T_2$ reads uncommitted dirty data |
| 4 | | $\text{commit}$ | $A = 150$ | **Fatal:** $T_2$ commits permanently |
| 5 | $\text{abort}$ | | | $T_1$ crashes |

- **Atomicity** requires undoing all of $T_1$'s changes, reverting $A$ to \$100.
- **Durability** forbids undoing committed transaction $T_2$.
- The DBMS cannot satisfy both properties. Recovery is impossible.

---

## 4. Recoverable Schedules: Commit Order Rule

**Recoverable Schedule:** A schedule where, whenever transaction $T_j$ reads a data item previously written by $T_i$, $T_i$ commits before $T_j$ commits:
$$
\text{Commit}(T_i) < \text{Commit}(T_j)
$$

| Step | Transaction $T_1$ | Transaction $T_2$ | Note |
| :--: | :--- | :--- | :--- |
| 1 | $\text{read}(A)$ | | |
| 2 | $\text{write}(A)$ | | Uncommitted write by $T_1$ |
| 3 | | $\text{read}(A)$ | $T_2$ reads uncommitted value |
| 4 | $\text{commit}$ | | $T_1$ commits first |
| 5 | | $\text{commit}$ | $T_2$ commits safely |

If $T_1$ aborts at Step 4, $T_2$ has not committed yet, so $T_2$ rolls back safely alongside $T_1$.

---

## 5. Cascading Rollbacks vs. Cascadeless Schedules

**Cascading Rollback:** A failure phenomenon where aborting a single transaction triggers a domino effect of rollbacks across active dependent transactions that read uncommitted data.

**Cascadeless Schedule:** A schedule where, whenever $T_j$ reads a data item written by $T_i$, $T_i$ commits before $T_j$ executes the read:
$$
\text{Commit}(T_i) < \text{Read}_j(Q)
$$

By enforcing read-after-commit, transactions only read committed data. If $T_1$ aborts, no other transaction has seen its changes, eliminating cascading rollbacks.

---

## 6. Strict Schedules: Preventing Dirty Writes

**Strict Schedule:** A schedule where no transaction reads or overwrites a data item $Q$ written by $T_i$ until $T_i$ commits or aborts:
$$
\text{Commit}(T_i) < \text{Read}_j(Q) \quad \text{and} \quad \text{Commit}(T_i) < \text{Write}_j(Q)
$$

- Cascadeless schedules block dirty reads, but still permit dirty writes ($T_2$ overwriting uncommitted $A$ from $T_1$). If $T_1$ aborts, restoring $A$'s before-image destroys $T_2$'s write.
- Strict schedules disallow dirty writes entirely. Undoing an aborted transaction requires only restoring the before-image of each modified data item. Strict Two-Phase Locking (Strict 2PL) automatically enforces strict schedules.

---

## 7. Comparison Summary

| Feature | Recoverable Schedule | Cascadeless Schedule | Strict Schedule |
| :--- | :--- | :--- | :--- |
| **Rule for Reads** | $\text{Commit}(T_i) < \text{Commit}(T_j)$ | $\text{Commit}(T_i) < \text{Read}_j(Q)$ | $\text{Commit}(T_i) < \text{Read}_j(Q)$ |
| **Rule for Writes** | Uncommitted writes can be overwritten | Uncommitted writes can be overwritten | $\text{Commit}(T_i) < \text{Write}_j(Q)$ |
| **Cascading Rollback?** | Yes, if an early writer aborts | No, eliminated | No, eliminated |
| **Dirty Read Allowed?** | Yes (delayed commit) | No | No |
| **Dirty Write Allowed?** | Yes | Yes | No |
| **Undo Mechanism** | Complex, multi-transaction aborts | Simple, single transaction abort | Trivial, restore before-images |
| **Enforcing Protocol** | Commit dependency tracking | Read-committed isolation | Strict 2PL / Rigorous 2PL |

## 🔮 Likely Questions

### 🎯 LQ1 · Distinguish Between Recoverable and Cascadeless Schedules with Examples · 04 Marks

**Question.** Define recoverable and cascadeless schedules. Provide example schedules to show why every cascadeless schedule is recoverable, but not every recoverable schedule is cascadeless.

**Answer.**

#### 1. Definitions
- **Recoverable Schedule:** A schedule where, whenever transaction $T_j$ reads a data item written by $T_i$, $T_i$ commits before $T_j$ commits ($\text{commit}(T_i) < \text{commit}(T_j)$).
- **Cascadeless Schedule:** A schedule where, whenever transaction $T_j$ reads a data item written by $T_i$, $T_i$ commits before $T_j$ reads that item ($\text{commit}(T_i) < \text{read}_j(Q)$).

#### 2. Example 1: Recoverable but NOT Cascadeless

| Step | Transaction $T_1$ | Transaction $T_2$ |
| :--: | :--- | :--- |
| 1 | $\text{write}(A)$ | |
| 2 | | $\text{read}(A)$ |
| 3 | $\text{commit}$ | |
| 4 | | $\text{commit}$ |

$T_2$ reads uncommitted $A$ at Step 2. Because $T_1$ commits at Step 3 before $T_2$ commits at Step 4 ($\text{commit}(T_1) < \text{commit}(T_2)$), the schedule is **recoverable**. But if $T_1$ aborts at Step 3, $T_2$ must abort too. Thus, it is **not cascadeless**.

#### 3. Example 2: Cascadeless (and Therefore Recoverable)

| Step | Transaction $T_1$ | Transaction $T_2$ |
| :--: | :--- | :--- |
| 1 | $\text{write}(A)$ | |
| 2 | $\text{commit}$ | |
| 3 | | $\text{read}(A)$ |
| 4 | | $\text{commit}$ |

$T_1$ commits at Step 2 before $T_2$ reads $A$ at Step 3. No dirty read occurs, so cascading rollbacks cannot happen. Since $T_2$ reads $A$ before committing, we get $\text{commit}(T_1) < \text{read}_2(A) < \text{commit}(T_2)$. Every cascadeless schedule is automatically recoverable.

---

### 🎯 LQ2 · Explain Cascading Rollback with a Timeline Schedule and State How to Prevent It · 04 Marks

**Question.** What is cascading rollback? Illustrate how cascading rollback occurs using an interleaved schedule of three transactions. How can a database system prevent cascading rollback?

**Answer.**

#### 1. Definition
**Cascading rollback** is a failure event where the abort of one transaction forces a chain reaction of rollbacks across active transactions that read uncommitted data written directly or indirectly by the failed transaction.

#### 2. Timeline Schedule

| Step | Transaction $T_1$ | Transaction $T_2$ | Transaction $T_3$ | Explanation |
| :--: | :--- | :--- | :--- | :--- |
| 1 | $\text{read}(A)$ | | | $T_1$ reads $A = 100$ |
| 2 | $\text{write}(A)$ | | | $T_1$ writes $A = 80$ (uncommitted) |
| 3 | | $\text{read}(A)$ | | $T_2$ reads dirty value $A = 80$ |
| 4 | | $\text{write}(A)$ | | $T_2$ writes $A = 130$ (uncommitted) |
| 5 | | | $\text{read}(A)$ | $T_3$ reads dirty value $A = 130$ |
| 6 | **$\text{abort}$** | | | **$T_1$ crashes and aborts** |
| 7 | | **$\text{abort}$** | | **$T_2$ forced to roll back** (read dirty $A$ from $T_1$) |
| 8 | | | **$\text{abort}$** | **$T_3$ forced to roll back** (read dirty $A$ from $T_2$) |

$T_1$'s failure at Step 6 forces $T_2$ to abort at Step 7, which in turn forces $T_3$ to abort at Step 8, wasting substantial CPU and I/O work.

#### 3. Prevention
The database prevents cascading rollbacks by enforcing **cascadeless schedules** (via Strict 2PL):
- Prohibit reading uncommitted data: $\text{commit}(T_i) < \text{read}_j(A)$.
- Hold exclusive write locks until commit or abort. Readers must wait until the writer completes, so failures remain localized to the single failing transaction.

---

### 🎯 LQ3 · Define Strict Schedules and Explain the Containment Hierarchy · 04 Marks

**Question.** Define a strict schedule. Why is a strict schedule stronger than a cascadeless schedule? Draw and explain the containment hierarchy of schedules based on recoverability.

**Answer.**

#### 1. Definition
A schedule is **strict** if no transaction can read or overwrite a data item $Q$ written by $T_i$ until $T_i$ has committed or aborted:
1. $\text{Commit}(T_i) < \text{Read}_j(Q)$ (blocks dirty reads).
2. $\text{Commit}(T_i) < \text{Write}_j(Q)$ (blocks dirty writes).

#### 2. Why Strict Is Stronger than Cascadeless
A cascadeless schedule only blocks dirty reads. It still permits concurrent writes to uncommitted items. If $T_1$ writes $A$, $T_2$ writes $A$, and $T_1$ aborts, restoring $A$'s pre-image overwrites $T_2$'s valid write. A strict schedule blocks uncommitted writes, allowing crash recovery to simply restore the log before-image.

#### 3. Containment Hierarchy
$$
\text{Strict} \subset \text{Cascadeless} \subset \text{Recoverable} \subset \text{All Schedules}
$$
- **All Schedules:** All concurrent interleaved operation sequences.
- **Recoverable:** Enforces $\text{commit}_i < \text{commit}_j$ so committed transactions never depend on aborted ones.
- **Cascadeless:** Enforces $\text{commit}_i < \text{read}_j$ to eliminate cascading rollbacks.
- **Strict:** Enforces $\text{commit}_i < \text{read}_j$ and $\text{commit}_i < \text{write}_j$ for direct before-image recovery.

## ⚡ Exam Tips & Common Mistakes

- **Commit order vs. Read order:** Recoverable compares commits ($\text{commit}(T_i) < \text{commit}(T_j)$). Cascadeless requires commit before read ($\text{commit}(T_i) < \text{read}_j(Q)$).
- **Serializability vs. Recoverability:** These are independent properties. A schedule can be conflict serializable but non-recoverable, or recoverable but non-serializable.
- **State the dirty write hazard:** When explaining why strict schedules are necessary, describe how uncommitted writes ruin before-image log restoration.
- **Sketch the 4-layer hierarchy:** Drawing $\text{Strict} \subset \text{Cascadeless} \subset \text{Recoverable} \subset \text{All Schedules}$ secures quick visual marks.
