# T12.1: Failure Classification and Recovery Precautions

> **Topic:** T12 · Recovery System & RAID | **Priority:** 🔴 High | **Exam Frequency:** 5/7 finals · 17 marks
> **Sources:** Silberschatz 7e Ch. 19 (§19.1–19.2) · Lecture Deck 01 (Slides 23, 26) · Lecture Deck 07 (Slide 8)

---

## Core Failure Concepts & Storage Hierarchy

**Recovery Scheme:** A recovery scheme is a DBMS subsystem that restores the database to a consistent state after a failure. It enforces atomicity by undoing unfinished transactions and durability by preserving committed updates.

**Fail-Stop Assumption:** The fail-stop assumption states that hardware faults or operating system crashes halt the CPU and clear volatile memory without corrupting non-volatile disk storage. Because disk blocks survive intact, the recovery manager can read disk logs on reboot to rebuild lost state.

A database uses three storage tiers with different survival properties:

| Storage Type | Speed & Cost | Persistence Across Crashes | Vulnerability | Hardware Media | Role in Recovery |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Volatile Storage** | Very fast, high cost | Wiped on power cut or crash | Lost completely on CPU halt | Main memory (RAM), CPU cache | In-memory log buffer, shared buffer pool |
| **Non-Volatile Storage** | Moderate, medium cost | Survives system crashes | Vulnerable to disk head crashes and bad sectors | Magnetic hard disks, SSDs | Permanent database tables, indexes |
| **Stable Storage** | Slower (requires multi-writes) | Survives all hardware faults and local crashes | Theoretical concept; approximated via redundancy | Mirrored RAID disks with battery NVRAM, remote replicas | Write-Ahead Log records, checkpoints |

**Stable Storage:** Stable storage is an idealized storage medium whose contents are never lost. In practice, database systems approximate stable storage using mirrored RAID arrays, battery-backed NVRAM, and off-site replicas.

## The Three Fundamental Classes of DBMS Failure

A database management system groups failures into three main classes based on the affected component:

### 1. Transaction Failure
A single transaction cannot complete its execution, but the database engine continues running:
- **Logical Errors:** The transaction halts because of an internal error condition or invalid input. Examples include division by zero, arithmetic overflow, invalid data formats, or data records not found.
- **System Errors:** The DBMS terminates the transaction because the system entered an undesirable state. Examples include deadlock victim selection by the concurrency controller or transaction timeouts. The transaction can abort and restart later.

### 2. System Crash
A hardware malfunction, power blackout, or operating system kernel panic brings the server to a sudden halt:
- **Volatile Storage Loss:** All contents of main memory (RAM), including active transaction workspaces and database buffer pools, are lost.
- **Survival of Disk Storage:** Non-volatile disk blocks remain intact and uncorrupted under the **fail-stop assumption**. The recovery manager reads disk logs on reboot to restore a consistent database state.

### 3. Disk Failure
Physical damage destroys data blocks on non-volatile storage:
- **Causes:** Disk head crashes, surface defects, bad sectors, or drive controller failures.
- **Recovery Requirement:** Because data blocks on the disk are destroyed, recovery requires redundant copies such as RAID arrays or off-site archival backups plus log archives.

*(Disaster / Site Failure: A catastrophic event like a fire, flood, or earthquake destroys the entire facility. Recovery requires geographically remote off-site backups or remote standby replicas).*

## Buffer Blocks vs. Physical Blocks

Transactions do not modify data directly on physical disk drives. The DBMS reads blocks into main memory buffer pools, updates them in RAM, and flushes them to disk later.

![Block storage operations between main memory buffer blocks and disk storage via input and output](diagrams/T12.01_block_storage_operations__TB_fig_19_01.jpg)
*Figure 12.1: Block storage operations between main memory buffers and physical disk (Silberschatz Figure 19.1).*

Data moves between disk and memory using two operations:
- $\text{input}(B)$: Transfers physical block $B$ from disk into a main memory buffer block.
- $\text{output}(B)$: Writes the modified buffer block $B$ back to non-volatile disk storage.

If power fails before $\text{output}(B)$ runs, committed changes in RAM are lost (requiring redo). If $\text{output}(B)$ writes an uncommitted change to disk before a crash, the disk holds dirty data (requiring undo).

## Runtime Precautions vs. Post-Crash Recovery Methods

**Recovery Algorithms:** Recovery algorithms are procedures that guarantee database consistency, transaction atomicity, and durability across crashes. Every recovery algorithm consists of two complementary parts: proactive precautions taken during normal operation (such as write-ahead logging and checkpoints) and repair actions taken after a crash (such as log undo and redo scans).

Exam questions often require separating proactive precautions taken during normal operation from reactive recovery methods executed after a crash:

### 1. Precautions Taken During Normal Operation
- **Write-Ahead Logging (WAL):** Force every update log record to stable storage before writing the modified data block to disk.
- **Uninterruptible Power Supply (UPS) & NVRAM:** Use battery-backed caches to prevent incomplete writes during sudden power cuts.
- **Disk Redundancy (RAID):** Use mirroring (RAID 1) or distributed parity (RAID 5/6) to survive drive failures without downtime.
- **Periodic Checkpointing:** Flush dirty buffer blocks to disk and record active transaction lists to bound post-crash restart time.
- **Archival Off-Site Backups:** Periodically copy full database dumps and log files to remote media or cloud storage.

### 2. Post-Failure Recovery Methods
- **Log-Based Undo:** Scans log records backward to reverse modifications made by uncommitted transactions, restoring original values ($V_1$) to enforce atomicity.
- **Log-Based Redo:** Scans log records forward to reapply modifications made by committed transactions, applying new values ($V_2$) to enforce durability.
- **Checkpoint-Guided Restart:** Uses the checkpoint record to limit log scans, avoiding redoing transactions that committed before the checkpoint.
- **Shadow Paging:** Flipped pointers between shadow and current page tables to recover without log undo passes.
- **Archival Restore & Roll-Forward:** Restores the last offline backup and replays subsequent archived log records to reconstruct lost disk volumes.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.6(c) & 2023 Q.7(a) · Classification of DBMS Failures · [03 Marks]

> *Section B · Asked in: 2017 Q.6(c) (3 marks), 2023 Q.7(a) (3 marks, CLO2) · L2 merge*

**Question (2017 Q.6(c)).** Classify and discuss the failures in DBMS.

**Question (2023 Q.7(a)).** Explain the different types of failures that can occur in a database system.

**Answer.**

A database management system experiences three main classes of failure based on the affected storage component:

1. **Transaction Failure:** An individual transaction aborts before completing.
   - *Logical Error:* Caused by internal transaction logic or bad data (such as division by zero, arithmetic overflow, or data not found).
   - *System Error:* The system enters an undesirable state (such as a deadlock or timeout) and terminates the transaction.
2. **System Crash:** A hardware failure, power outage, or operating system bug halts the database server.
   - The contents of **volatile storage** (main memory buffers) are lost.
   - The contents of **non-volatile storage** (disk drives) remain uncorrupted (*fail-stop assumption*).
3. **Disk Failure:** Physical damage destroys data blocks on non-volatile media.
   - Causes include head crashes, magnetic surface defects, or transfer errors.
   - Recovery requires redundancy such as RAID arrays or archival backups.

### 🎯 GQ2 · 2018 Q.5(c) [Part 1] · Failure Types in DBMS · [02 Marks]

> *Section B · Asked in: 2018 Q.5(c) [Part 1] (2 of 4 marks)*

**Question.** Discuss each type of failure that can happen in DBMS. How does RAID model help to recover a system?

*(Note: 4-mark question split 2 + 2 with T12.4. This is Part 1 covering failure types for 2 marks. Part 2 covering RAID recovery is in T12.4).*

**Answer.**

A DBMS is subject to three primary failure types:

1. **Transaction Failure:** A transaction cannot continue due to internal logical errors (invalid inputs, overflow) or system-induced conditions (deadlocks).
2. **System Crash:** Hardware faults or power cuts wipe volatile RAM. Disk storage remains intact under the fail-stop assumption.
3. **Disk Failure:** Head crashes or unreadable physical sectors destroy non-volatile disk blocks.

### 🎯 GQ3 · 2019 Q.4(b) & 2024 Q.3(b) · Failure Modes, Precautions, and Recovery Methods · [05 Marks]

> *Section A · Asked in: 2019 Q.4(b) (5 marks), 2024 Q.3(b) (4 marks, CO1) · L2 merge*

**Question (2019 Q.4(b)).** How many ways a DBMS could be failed? What precautions should be taken considering the failure of DBMS and point out the recovery methods.

**Question (2024 Q.3(b)).** Discuss the ways of DBMS can be failed. Also, mention the precautions should be taken considering the failure of DBMS and point out the recovery methods.

**Answer.**

#### 1. Ways a DBMS Can Fail
A DBMS can fail in three primary ways:
- **Transaction Failure:** Caused by logical errors (overflow, invalid input) or system errors (deadlock aborts).
- **System Crash:** Loss of volatile main memory from power loss, CPU faults, or operating system crashes.
- **Disk Failure:** Loss of non-volatile disk storage caused by head crashes or bad sectors.
- *(Site / Disaster Failure):* Physical destruction of an entire data center caused by fire, flood, or earthquake.

#### 2. Precautions Against DBMS Failures
- **Write-Ahead Logging (WAL):** Force log records to stable storage before writing modified data pages to disk.
- **Uninterruptible Power Supply (UPS) & NVRAM:** Use battery-backed caches to prevent incomplete writes during sudden power loss.
- **Disk Redundancy (RAID):** Use mirroring (RAID 1) or parity (RAID 5/6) to survive single or double disk failures.
- **Archival Off-Site Backups:** Periodically copy full database dumps and log files to remote tape or cloud storage.

#### 3. Recovery Methods
- **Log-Based Recovery:**
  - *Undo:* Reverses uncommitted updates using old values from the log.
  - *Redo:* Re-applies committed updates using new values from the log.
- **Checkpoints:** Periodically flushes dirty buffer blocks and logs active transactions, bounding the restart log scan.
- **Shadow Paging:** Writes updates to a separate page copy and switches pointers atomically, avoiding undo/redo logs.
- **Archival Restore and Roll-Forward:** Restores the last offline backup and replays subsequent archived log records.

## ⚡ Exam Tips & Common Mistakes

- **System Crash vs. Disk Failure:** A system crash wipes volatile RAM only. Disk blocks survive uncorrupted under the fail-stop assumption. Never say a system crash destroys disk data.
- **Precautions vs. Recovery Methods:** Precautions operate *before* a crash during normal processing (WAL, RAID, UPS, checkpoints). Recovery methods run *after* a crash on restart (undo, redo, roll-forward).
- **Always State the Fail-Stop Assumption:** When describing system crashes, mention the fail-stop assumption. It shows examiners you know foundational recovery theory.
- **Logical vs. System Transaction Errors:** Logical errors are internal bugs (such as division by zero). System errors are external aborts (such as deadlock victim selection).
