# T08.11: Lossless-Join Decomposition and Dependency Preservation

> **Topic:** T08 · Normalization & Functional Dependencies | **Priority:** 🟡 Theoretical Core | **Exam Frequency:** 0/7 finals · 0 marks
> **Sources:** Silberschatz 7e Ch. 7 (§7.1.2, §7.2.3, §7.4.4, §7.5) · Lecture Deck 06 (Slides 52–62) · Raidah Class Notes (pp. 24–25)

## Safety Properties of Decompositions

Decomposing a relation schema $R$ splits its attributes across smaller relations $R_1, R_2, \dots, R_k$ such that $R = \bigcup R_i$. Every valid decomposition must satisfy two formal properties.

**Lossless-Join Decomposition:** A decomposition of relation $R$ into $R_1, R_2, \dots, R_k$ is lossless if joining the decomposed tables back together with a natural join restores the exact original relation without producing fake rows:

$$
\Pi_{R_1}(r) \bowtie \Pi_{R_2}(r) \bowtie \dots \bowtie \Pi_{R_k}(r) = r
$$

**Spurious Tuples:** Invalid, erroneous tuples generated when an improperly decomposed (lossy) relation is joined back together. Spurious tuples represent false combinations of data not present in the original relation.

**Dependency-Preserving Decomposition:** A decomposition where the union of the functional dependencies enforceable on individual sub-relations implies all dependencies in the original set $F$:

$$
(F_1 \cup F_2 \cup \dots \cup F_k)^+ = F^+
$$

---

## Lossless-Join Decomposition Condition

### The Superkey Rule for Binary Decomposition

**Lossless-Join Condition:** A binary decomposition of relation schema $R$ into $R_1$ and $R_2$ is a lossless-join decomposition with respect to functional dependency set $F$ if and only if the intersection of their attributes forms a superkey of at least one of the decomposed schemas:

$$
(R_1 \cap R_2) \rightarrow R_1 \in F^+ \quad \text{OR} \quad (R_1 \cap R_2) \rightarrow R_2 \in F^+
$$

If the common attribute set is a superkey of neither $R_1$ nor $R_2$, joining them produces duplicate matches and creates spurious tuples, resulting in a **lossy decomposition**.

### 3-Step Verification Recipe

1. Find the intersection of the two relations: $K = R_1 \cap R_2$.
2. Compute the attribute closure $K^+$ under the original functional dependency set $F$.
3. Check whether $R_1 \subseteq K^+$ (meaning $K \rightarrow R_1$) or $R_2 \subseteq K^+$ (meaning $K \rightarrow R_2$). If at least one condition holds, the decomposition is **lossless**.

### Worked Example: Lossless Verification

Let $R(A, B, C)$ with $F = \{A \rightarrow B\}$. Decompose $R$ into $R_1(A, B)$ and $R_2(A, C)$.

1. Common attributes: $R_1 \cap R_2 = \{A\}$.
2. Compute closure: $A^+ = \{A, B\}$.
3. Compare: $R_1 = \{A, B\} \subseteq A^+$.  
   Since $A \rightarrow R_1$ holds, the common attribute $A$ is a superkey of $R_1$.
4. **Conclusion:** The decomposition is **lossless**.

## Dependency Preservation

### Practical Significance

Enforcing functional dependencies is essential to guarantee data consistency.
- In a **dependency-preserving** decomposition, each dependency $\alpha \rightarrow \beta$ can be verified locally on a single relation using a simple primary key or `UNIQUE` constraint.
- In a **non-dependency-preserving** decomposition, verifying $\alpha \rightarrow \beta$ requires executing an expensive natural join across multiple tables on every `INSERT` or `UPDATE`.

### 3NF vs. BCNF on Dependency Preservation

- **Third Normal Form (3NF):** There is always a decomposition that is **both** lossless-join and dependency-preserving (synthesized using canonical covers).
- **Boyce-Codd Normal Form (BCNF):** A lossless-join BCNF decomposition is always achievable, but it is **not always possible** to preserve dependencies in BCNF.

## 🔮 Likely Questions

### 🎯 LQ1 · Lossless-Join Condition and Spurious Tuples · 04 Marks

> *Section A / B · Probability: High*

**Question.** What is a lossless-join decomposition? State the necessary and sufficient condition for a binary decomposition to be lossless-join, and explain what spurious tuples are.

**Answer.**

#### 1. Definition of Lossless-Join Decomposition
A decomposition of a relation schema $R$ into relations $R_1$ and $R_2$ is a **lossless-join decomposition** if for every legal relation instance $r(R)$:
$$
\Pi_{R_1}(r) \bowtie \Pi_{R_2}(r) = r
$$
The natural join of the projections reproduces the exact original relation without data loss or extra tuples.

#### 2. Necessary and Sufficient Condition
A binary decomposition of $R$ into $R_1$ and $R_2$ is lossless-join with respect to functional dependency set $F$ if and only if at least one of the following dependencies belongs to $F^+$:
1. $(R_1 \cap R_2) \rightarrow R_1$
2. $(R_1 \cap R_2) \rightarrow R_2$

In plain terms, the attributes common to both tables must form a superkey of at least one of the tables.

#### 3. Spurious Tuples
**Spurious tuples** are fake, invalid tuples generated when a lossy decomposition is joined back together. When tables are split on a non-key attribute, multiple rows share identical join values, producing a Cartesian-like combination of unrelated data. These fake tuples make it impossible to determine the true original facts.

### 🎯 LQ2 · Dependency Preservation and Normal Form Trade-offs · 04 Marks

> *Section A / B · Probability: High*

**Question.** What is dependency preservation in relational database decomposition? Explain why dependency preservation is desirable and compare 3NF and BCNF regarding this property.

**Answer.**

#### 1. Definition of Dependency Preservation
A decomposition of schema $R$ into $D = \{R_1, R_2, \dots, R_k\}$ is **dependency-preserving** if:
$$
(F_1 \cup F_2 \cup \dots \cup F_k)^+ = F^+
$$
where each $F_i$ is the projection of $F$ onto schema $R_i$. Every functional dependency in $F$ must be logically implied by the dependencies that apply locally to individual tables.

#### 2. Why Dependency Preservation is Desirable
If a decomposition is dependency-preserving, the DBMS can verify every integrity constraint by inspecting a single table during an `INSERT` or `UPDATE`. If a dependency is not preserved, enforcing that constraint requires joining multiple tables on every database modification, introducing severe performance overhead.

#### 3. 3NF vs. BCNF Comparison
- **3NF Guarantee:** It is always possible to find a decomposition for any relation schema that is simultaneously **lossless-join** and **dependency-preserving**.
- **BCNF Limitation:** While every schema can be decomposed losslessly into BCNF, it is **not always possible** to achieve BCNF while preserving all functional dependencies. When a choice must be made, designers frequently choose 3NF to avoid expensive cross-table integrity joins.

## ⚡ Exam Tips & Common Mistakes

- **Intersection superkey test:** Always check $R_1 \cap R_2$. If the intersection does not functionally determine all attributes of at least one of the sub-relations, the decomposition is lossy.
- **Why "more rows" means "lossy":** Generating spurious tuples increases row count, but it is called "lossy" because you lose the ability to distinguish valid historical facts from false combinations.
- **3NF vs BCNF trade-off:** If asked to compare 3NF and BCNF, always highlight that 3NF guarantees dependency preservation while BCNF guarantees zero redundancy.
