# T07.2: Triggers for Database Security

> **Topic:** T07 · Triggers and Stored Procedures | **Priority:** 🟡 Medium | **Exam Frequency:** 2/7 finals · 8 marks  
> **Sources:** Silberschatz 7e Ch. 5 (§5.3), Ch. 9 (§9.8) · Fahim Handnote (p. 59)

---

## Dual-Phase Database Security Model

**Database Security:** The protection of database systems and data against unauthorized access, malicious modifications, or accidental loss.

**Preventive Trigger:** A `BEFORE` trigger that inspects incoming data modifications before they reach the table. It halts unauthorized operations by raising an error with `SIGNAL`.

**Audit Trail:** A time-ordered log table populated automatically by `AFTER` triggers. It records the responsible user (`USER()`), timestamp (`NOW()`), and before-and-after values (`OLD` and `NEW`).

**Security Breach:** An incident where an unauthorized user bypasses access controls to read, modify, or delete protected database records.

Triggers strengthen database security across two distinct phases:

| Dimension | Before a Breach (`BEFORE`) | After a Breach (`AFTER`) |
| :--- | :--- | :--- |
| **Trigger Timing** | `BEFORE INSERT / UPDATE / DELETE` | `AFTER INSERT / UPDATE / DELETE` |
| **Primary Goal** | Prevent unauthorized changes | Capture forensic evidence and assist recovery |
| **Operating Role** | Security gatekeeper and policy inspector | Tamper-evident audit recorder |
| **Primary Mechanism** | Policy validation and `SIGNAL SQLSTATE '45000'` | Row capture into an independent audit table |
| **Table State** | Unchanged (transaction rolls back on violation) | Modified (changes written and recorded) |
| **Captured Data** | None retained on disk (operation is aborted) | `USER()`, `NOW()`, `OLD`, and `NEW` values |
| **Recovery Role** | None needed (the damage was blocked) | High (allows restoring corrupted records from `OLD`) |

---

## Phase 1: Security Before a Breach (Prevention via BEFORE Triggers)

`BEFORE` triggers inspect data modifications before the DBMS writes them to disk. If a change violates a security policy, the trigger aborts the transaction immediately.

### Prevention Mechanisms

- **Temporal Access Controls:** Block sensitive updates outside approved business hours.
- **Sanity and Threshold Checks:** Restrict extreme updates, such as transfers exceeding a single-transaction limit.
- **Privilege Enforcement:** Prevent non-administrative users from altering restricted security columns.
- **Transaction Abort:** Executing `SIGNAL SQLSTATE '45000'` cancels the statement and rolls back uncommitted changes, keeping the database intact.

### Prevention Example: Blocking Changes Outside Office Hours

```sql
DELIMITER //

CREATE TRIGGER trg_guard_employee_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Security Alert: Edits outside office hours are blocked';
    END IF;
END //

DELIMITER ;
```

## Phase 2: Security After a Breach (Forensics and Auditing via AFTER Triggers)

When an attacker uses valid credentials to perform unauthorized actions, `AFTER` triggers run immediately after the change succeeds on the target table.

### Forensic and Recovery Mechanisms

- **Database-Level Auditing:** The trigger fires inside the DBMS engine. Even if an attacker bypasses application-level logging, the database trigger still records the event.
- **User and Session Identification:** Functions like `USER()` and `NOW()` record the database account, client IP, and exact timestamp.
- **Before-and-After Values:** Storing both `OLD` and `NEW` column states preserves a complete record of what was altered.
- **Incident Recovery:** Administrators use the recorded `OLD` values to restore corrupted records to their pre-breach state.

### Forensics Example: Logging Role Privilege Changes

```sql
DELIMITER //

CREATE TRIGGER trg_audit_user_role_change
AFTER UPDATE ON user_roles
FOR EACH ROW
BEGIN
    IF OLD.role <> NEW.role THEN
        INSERT INTO security_audit_log (
            user_id, old_role, new_role, changed_by, changed_at
        ) VALUES (
            OLD.user_id, OLD.role, NEW.role, USER(), NOW()
        );
    END IF;
END //

DELIMITER ;
```

## Security Scope and Limitations of Triggers

While triggers provide powerful write-side protection, keep these limits in mind:

- **No Triggers on `SELECT`:** Triggers only respond to `INSERT`, `UPDATE`, and `DELETE`. They cannot detect or block unauthorized data reading. Use SQL views, column authorization (`GRANT SELECT`), or encryption to protect confidential reads.
- **Privileged Account Bypass:** Users with `SUPER` or `TRIGGER` privileges can alter or drop triggers. Triggers protect against compromised client accounts, not rogue administrators.
- **Defense in Depth:** Triggers work alongside prepared statements (to prevent SQL injection), strict user roles, and network security.
- **Recursive Trigger Prevention:** Always write audit logs to an independent audit table. Writing to the source table can cause infinite recursive trigger calls.

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2017 Q.8(b) / 2024 Q.2(a) · Database Security Before and After a Breach · 05 Marks

> *Section B / Section A · Asked in: 2017 (5 marks), 2024 (3 marks, CO2) · L2 repeat merge*

**Question (2017 Q.8(b)).** Using examples, discuss how Trigger can contribute to the security of database, before and after a security breach.

**Question (2024 Q.2(a)).** Discuss how trigger can contribute to the security of database before and after a security breach. Explain with example.

**Answer.**

Triggers protect database security at two stages: proactive prevention before a breach and forensic auditing after a breach.

#### 1. Before a Security Breach: Prevention via BEFORE Triggers

`BEFORE` triggers act as real-time security gatekeepers. They evaluate incoming data modifications before changes reach the database.

- **Security Role:** They validate user identity, verify business timing, and inspect the values being written. If a policy violation appears, the trigger halts the transaction using `SIGNAL SQLSTATE '45000'`.
- **Key Contributions:**
  - Blocks unauthorized operations outside working hours.
  - Prevents illegal privilege escalation or unauthorized salary updates.
  - Validates and sanitizes input data to stop malicious updates.

**Example (Blocking salary changes outside working hours):**

```sql
DELIMITER //

CREATE TRIGGER trg_prevent_unauthorized_salary_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        IF CURRENT_TIME() NOT BETWEEN '09:00:00' AND '17:00:00' THEN
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT = 'Security Alert: Salary edits outside office hours are blocked';
        END IF;
    END IF;
END //

DELIMITER ;
```

#### 2. After a Security Breach: Auditing and Forensics via AFTER Triggers

`AFTER` triggers execute immediately after a modification succeeds on a table.

- **Security Role:** If an attacker bypasses application checks, `AFTER` triggers write the unauthorized changes into an independent audit log table.
- **Key Contributions:**
  - Creates a tamper-evident audit trail capturing `USER()`, `NOW()`, the modified table, and both `OLD` and `NEW` column values.
  - Supplies forensic evidence to pinpoint how and when the attacker breached the system.
  - Helps administrators trace unauthorized modifications and restore corrupted data to its original state.

**Example (Logging security role modifications):**

```sql
DELIMITER //

CREATE TRIGGER trg_audit_role_change
AFTER UPDATE ON user_roles
FOR EACH ROW
BEGIN
    IF OLD.role <> NEW.role THEN
        INSERT INTO security_audit_log (
            user_id, old_role, new_role, changed_by, changed_at
        ) VALUES (
            OLD.user_id, OLD.role, NEW.role, USER(), NOW()
        );
    END IF;
END //

DELIMITER ;
```

## ⚡ Exam Tips & Common Mistakes

- **Timing Distinction:** Never use `AFTER` for prevention. `AFTER` triggers run after changes reach the table, making prevention impossible.
- **Log Both States:** In forensic audit triggers, always record both `OLD` and `NEW` values. Storing only `NEW` leaves administrators unable to restore original records during recovery.
- **The SELECT Blindspot:** Remember that triggers do not fire on `SELECT` queries. They protect data modification, not data reading.
- **Audit Table Separation:** Always insert audit logs into a dedicated audit table rather than modifying the monitored table. This prevents trigger recursion limits from halting transactions.
