## Core Concept: The Five Transaction States

**Transaction:** A transaction is a logical unit of program execution that accesses and updates various data items in a database. It begins with `begin transaction` and ends with `commit` or `abort`.

During its lifecycle, a transaction moves through five distinct states:

1. **Active State:**
   - The initial state upon transaction creation.
   - The transaction stays in this state while executing its read, write, and calculation instructions.
2. **Partially Committed State:**
   - Entered immediately after the final statement has executed.
   - Calculations are finished in memory, but updates may still sit in volatile RAM buffers and are not yet fully written to disk.
3. **Failed State:**
   - Entered the moment the DBMS detects that normal execution cannot proceed.
   - Caused by hardware failures, runtime software bugs (division by zero), constraint violations, or concurrency aborts (deadlock victim).
4. **Aborted State:**
   - Entered after the recovery system finishes rolling back all partial updates, restoring data items to their pre-transaction values.
   - Guarantees **Atomicity** and marks the transaction as terminated.
5. **Committed State:**
   - Entered after all modifications and commit log records are safely flushed to non-volatile stable storage.
   - Guarantees **Durability**. The transaction is terminated and its updates cannot be rolled back.

**Terminated Transaction:** A transaction has terminated when it reaches either the **Committed** state (successful termination) or the **Aborted** state (unsuccessful termination). A terminated transaction cannot perform any further operations.

**Compensating Transaction:** Once a transaction enters the Committed state, the DBMS cannot roll it back. The only way to undo its effect is to run a separate compensating transaction (such as issuing a refund to reverse an earlier payment).

### Actions After an Abort

Once a transaction enters the Aborted state, the DBMS takes one of two actions:
- **Restart the Transaction:** The system automatically reruns the transaction as a new transaction. Used only when failure was caused by external transient factors (such as a deadlock abort or temporary network glitch).
- **Kill the Transaction:** The system cancels the transaction permanently and alerts the user. Used when failure was caused by an internal logic error (bad input data, division by zero, syntax errors) where rerunning would fail again.

### Observable External Writes

Actions with real-world physical side effects (such as dispensing cash from an ATM or printing a ticket) cannot be reversed by log rollback. The DBMS must delay observable external writes until **after** the transaction enters the **Committed** state.

## State Transition Summary Table

| Transition | Trigger Event | Resulting Database State |
| :--- | :--- | :--- |
| **Active $\to$ Partially Committed** | Final program statement executes | Execution done in RAM; disk writes still in flight |
| **Partially Committed $\to$ Committed** | Updates and log flush to stable storage | Changes are permanent; transaction terminates |
| **Active $\to$ Failed** | Hardware crash, logic bug, or deadlock abort | Execution halted; rollback initiated |
| **Partially Committed $\to$ Failed** | System crash before disk flush completes | Commit interrupted; rollback initiated |
| **Failed $\to$ Aborted** | Recovery system finishes undoing partial writes | Database restored to initial pre-transaction state |
| **Aborted $\to$ Active (Restart)** | Abort caused by external transient factor | Re-executed as a new transaction |
| **Aborted $\to$ Terminated (Kill)** | Abort caused by internal program logic error | Transaction permanently discarded |

## 🏆 Golden Questions (Past Exam Archive)

### 🎯 GQ1 · 2020 Q.5(b) · Transaction Definition and Life Cycle · 04 Marks

> *Section B · Asked in: 2020 · L1 (asked once)*

**Question.** What is a transaction? Describe the life cycle of a transaction.

**Answer.**

#### 1. Definition
A **transaction** is a logical unit of program execution that accesses and possibly updates various data items in a database. Delimited by `begin transaction` and `commit` or `abort` statements, it transforms the database from one consistent state to another.

#### 2. Life Cycle of a Transaction
A transaction moves through five distinct states during its execution:

![Transaction state transition diagram showing states: active, partially committed, committed, failed, and aborted with transition arrows](diagrams/T09.03_transaction_state_diagram__L07_L07_p08_fig01.jpg)
*Figure 9.4: Transaction Lifecycle State Diagram (Source: Lecture Deck 07, Slide 8).*

1. **Active:**  
   The starting state. The transaction enters this state upon creation and remains here while executing its read, write, and computational operations.
2. **Partially Committed:**  
   Entered immediately after the final statement has executed. Calculations are complete, but updates may still reside in volatile main-memory buffers and are not yet fully written to disk.
3. **Failed:**  
   Entered when normal execution can no longer proceed due to hardware faults, logical bugs (e.g., division by zero), constraint violations, or concurrency conflicts.
4. **Aborted:**  
   Entered after the recovery system has undone all partial writes, restoring the database to its pre-transaction state. After an abort, the system can:
   - **Restart** the transaction if aborted by transient factors like deadlocks.
   - **Kill** the transaction if aborted by internal logical errors or bad input data.
5. **Committed:**  
   Entered after successful completion, once all updates and commit log records are safely written to non-volatile stable storage.

**Committed** and **Aborted** are the only two terminal states.

#### State Transitions
- **Active $\to$ Partially Committed:** When the transaction executes its final statement.
- **Partially Committed $\to$ Committed:** When updates are safely flushed to stable storage.
- **Active $\to$ Failed:** When a system error, constraint violation, or deadlock abort occurs.
- **Partially Committed $\to$ Failed:** When a crash interrupts writing data to disk before commit finishes.
- **Failed $\to$ Aborted:** When the recovery manager restores the database to its pre-transaction state.

## ⚡ Exam Tips & Common Mistakes

- **Do Not Skip "Partially Committed":** Never draw an arrow directly from Active to Committed. The Partially Committed state represents the window where statements finished in RAM but disk writes are still pending.
- **Include Partially Committed $\to$ Failed:** System crashes can occur while flushing buffers to disk. You must include the arrow pointing from Partially Committed to Failed.
- **Never Draw Outgoing Arrows from Committed:** Once a transaction commits, its updates are permanent. It can never transition to Failed or Aborted.
- **State Restart vs Kill Clearly:** In descriptive questions, always state that the DBMS restarts transactions aborted by deadlocks and kills transactions aborted by logic bugs.
