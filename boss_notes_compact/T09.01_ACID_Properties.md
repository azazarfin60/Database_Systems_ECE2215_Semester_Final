## Core Concepts: Transaction and ACID Guarantees

**Transaction:** A transaction is a logical unit of program execution that accesses and updates various data items in a database. It is bounded by `begin transaction` and `end transaction` (`commit` or `abort`). To the user, it acts as a single indivisible operation that transforms the database from one consistent state to another.

**ACID Properties:** The four guarantees (Atomicity, Consistency, Isolation, Durability) that every relational DBMS enforces to keep data reliable across system crashes and concurrent execution:

1. **Atomicity ("All-or-None"):**
   - **Guarantee:** Either all operations of the transaction take effect in the database, or none do.
   - **Failure Handled:** System crashes, power loss, or aborts halfway through execution.
   - **Enforcing Subsystem:** The **Recovery System** (using write-ahead undo logs to reverse partial writes).

2. **Consistency (Preserving Invariants):**
   - **Guarantee:** Executing a transaction in isolation preserves database validity and all domain rules.
   - **Failure Handled:** Flawed application logic or illegal data updates (like creating or losing money).
   - **Enforcing Subsystem:** The **Application Programmer** (writing correct business logic) and the DBMS **Integrity Constraint Subsystem** (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`).

3. **Isolation (Shielding Concurrent Access):**
   - **Guarantee:** Each transaction executes unaware of other concurrent transactions. Uncommitted intermediate updates remain hidden until commit.
   - **Failure Handled:** Interleaved access conflicts like dirty reads, lost updates, and temporary anomalies.
   - **Enforcing Subsystem:** The **Concurrency-Control System** (using Two-Phase Locking or Timestamp Ordering).

4. **Durability (Persistence):**
   - **Guarantee:** Once a transaction commits, its updates persist permanently on non-volatile storage and survive any later system crashes.
   - **Failure Handled:** Power outages or server reboots immediately after a commit confirmation.
   - **Enforcing Subsystem:** The **Recovery System** (using write-ahead redo logs on stable storage).

### ACID Subsystem Summary

| Property | Core Guarantee | Threat Mitigated | Enforcing Component |
| :--- | :--- | :--- | :--- |
| **Atomicity** | All operations take effect or none do | Crash during execution | Recovery System (Undo Log) |
| **Consistency** | Invariants and schema constraints hold | Bad logic or invalid inputs | Application Programmer + DBMS Constraints |
| **Isolation** | Intermediate uncommitted updates remain hidden | Interleaved concurrent access | Concurrency-Control System (2PL / TSO) |
| **Durability** | Committed data survives power failure | Crash right after commit | Recovery System (Redo Log on Stable Storage) |

## Fund Transfer State Evolution

Consider a transaction $T_1$ transferring \$50 from account $A$ (initially \$1000) to account $B$ (initially \$2000). The invariant is $A + B = 3000$.

$$
\begin{aligned}
1.&\quad \text{read}(A) \\
2.&\quad A := A - 50 \\
3.&\quad \text{write}(A) \quad [A \text{ becomes } 950] \\
4.&\quad \text{read}(B) \\
5.&\quad B := B + 50 \\
6.&\quad \text{write}(B) \quad [B \text{ becomes } 2050] \\
7.&\quad \text{commit}
\end{aligned}
$$

![ACID properties illustrated on a \$50 fund transfer transaction showing database state evolution and the four ACID guarantees](diagrams/T09_2018_Q4b_acid_transfer.jpg)
*Figure 9.1: State evolution of a \$50 fund transfer under ACID guarantees.*

1. **Atomicity:** If a crash happens after step 3, the recovery system reads undo logs and resets $A$ to 1000.
2. **Consistency:** Total money $A + B = 3000$ holds before step 1 ($1000 + 2000$) and after step 6 ($950 + 2050$).
3. **Isolation:** Between steps 3 and 6, the temporary sum is 2950. Concurrency control stops other queries from reading this intermediate state.
4. **Durability:** After step 7 commits, balances $A = 950$ and $B = 2050$ are safe on stable storage.

### 🎯 GQ1 · CT-04 Q.01 / 2017 Q.5(a) / 2021 Q.7(a) / 2024 Q.6(c) · ACID Properties Discussion & Examples · 06 / 04 / 02 Marks

> *Section B / Section A · Asked in: CT-04 (CO3) [6m], 2017 Q.5(a) [4m], 2021 Q.7(a) (CLO1) [4m], 2024 Q.6(c) (CO3) [2m] · L2 merge*

**Question (CT-04 Q.01).** Define a transaction? Explain the four ACID properties of a transaction with suitable examples.

**Question (2017 Q.5(a)).** Briefly discuss the ACID properties of transaction.

**Question (2021 Q.7(a)).** Explain the ACID properties of transaction.

**Question (2024 Q.6(c)).** Briefly discuss the ACID properties of transaction.

**Answer.**

#### 1. Definition of a Transaction
A **transaction** is a logical unit of program execution that accesses and updates various data items in a database. It is bounded by `begin transaction` and `end transaction` (`commit` or `abort`) statements.

#### 2. The Four ACID Properties with Examples
Consider transaction $T_1$ transferring \$50 from account $A$ (initially \$1000) to account $B$ (initially \$2000):

$$
T_1: \text{read}(A) \to A := A - 50 \to \text{write}(A) \to \text{read}(B) \to B := B + 50 \to \text{write}(B) \to \text{commit}
$$

1. **Atomicity ("All-or-None"):**
   - **Explanation:** Either all operations of the transaction take effect in the database, or none do.
   - **Example:** If a crash happens right after $\text{write}(A)$, account $A$ is 950 while account $B$ is still 2000. Atomicity requires the recovery system to undo the update on $A$ using log records, restoring $A$ to 1000.
   - **Enforced by:** Recovery system using undo logs.

2. **Consistency (Invariant Preservation):**
   - **Explanation:** Running a transaction in isolation preserves database consistency. It moves the database from one valid state to another.
   - **Example:** The business invariant requires total funds $A + B = 3000$. Before $T_1$, $1000 + 2000 = 3000$. After $T_1$, $950 + 2050 = 3000$.
   - **Enforced by:** Application programmer logic and DBMS integrity constraints.

3. **Isolation (Shielding Concurrent Execution):**
   - **Explanation:** Each transaction executes unaware of other concurrent transactions. Uncommitted intermediate states remain hidden.
   - **Example:** After step 3, $A = 950$ and $B = 2000$ (sum is 2950). If transaction $T_2$ runs concurrently to calculate total assets, isolation blocks $T_2$ from reading the partial sum 2950. $T_2$ reads either 3000 before $T_1$ or 3000 after $T_1$.
   - **Enforced by:** Concurrency-control manager (2PL or timestamp ordering).

4. **Durability (Persistence):**
   - **Explanation:** Once a transaction commits, its updates persist permanently and survive future crashes.
   - **Example:** Once $T_1$ commits, balances $A = 950$ and $B = 2050$ are safe on stable storage. If power fails a second later, the balances survive upon reboot.
   - **Enforced by:** Recovery system using redo logs.

*Variant for 2017 Q.5(a) and 2021 Q.7(a) (4 marks):* Provide the transaction definition, the 4 property definitions, and state the enforcing subsystem for each.

*Short version for 2024 Q.6(c) (2 marks):* Write one concise bullet point per property naming its core guarantee and enforcing subsystem.

### 🎯 GQ2 · 2018 Q.4(b) · ACID Properties with Diagram · 04 Marks

> *Section A · Asked in: 2018 · L1 (asked once)*

**Question.** Describe the ACID-properties of database system with appropriate diagram.

**Answer.**

To maintain database integrity against failures and concurrent updates, every transaction must satisfy four **ACID** properties:

- **Atomicity:** All operations of the transaction take effect or none do.
- **Consistency:** Execution in isolation preserves all explicit constraints and implicit invariants.
- **Isolation:** Intermediate uncommitted states remain invisible to other concurrent transactions.
- **Durability:** Committed updates survive crashes permanently on stable storage.

#### Illustration with \$50 Fund Transfer ($T_1$)
Let account $A$ have initial balance \$1000 and account $B$ have initial balance \$2000. Transaction $T_1$ moves \$50 from $A$ to $B$.

$$
\begin{aligned}
1.&\quad \text{read}(A) \\
2.&\quad A := A - 50 \\
3.&\quad \text{write}(A) \quad [A \text{ becomes } 950] \\
4.&\quad \text{read}(B) \\
5.&\quad B := B + 50 \\
6.&\quad \text{write}(B) \quad [B \text{ becomes } 2050] \\
7.&\quad \text{commit}
\end{aligned}
$$

![ACID properties illustrated on a \$50 fund transfer transaction showing database state evolution and the four ACID guarantees](diagrams/T09_2018_Q4b_acid_transfer.jpg)
*Figure 9.2: ACID properties in fund transfer transaction.*

#### Mapping to the Diagram
1. **Atomicity:** If a crash occurs after step 3, account $A$ is 950 while account $B$ remains 2000. The recovery system uses log records to roll back $A$ to \$1000.
2. **Consistency:** The invariant $A + B = 3000$ holds in the initial state ($1000 + 2000 = 3000$) and in the final state ($950 + 2050 = 3000$). Money is neither created nor lost.
3. **Isolation:** Between steps 3 and 6, the sum is temporarily 2950. Concurrency control blocks concurrent transaction $T_2$ from reading this intermediate state.
4. **Durability:** After step 7 commits, balances $A = 950$ and $B = 2050$ survive power loss permanently.

### 🎯 GQ3 · 2023 Q.4(b) · Importance of ACID Properties with Example · 04 Marks

> *Section A · Asked in: 2023 (CLO3) · L1 (asked once)*

**Question.** Briefly explain the importance of ACID properties of transactions with suitable example.

**Answer.**

Databases must handle two critical challenges: system failures (crashes, power loss) and concurrent execution. The ACID properties are essential because without them, database data becomes corrupt and untrustworthy.

**Example:** Transaction $T_1$ transfers \$50 from account $A$ (initial balance \$1000) to account $B$ (initial balance \$2000). The invariant is $A + B = 3000$.

#### Importance of Each Property
1. **Importance of Atomicity:**
   - *Failure case without atomicity:* The system crashes after deducting 50 from $A$, before adding 50 to $B$. The bank loses \$50 of customer money.
   - *Protection:* Atomicity forces the recovery manager to undo the deduction, restoring $A = 1000$.

2. **Importance of Consistency:**
   - *Failure case without consistency:* A flawed program deducts 50 from $A$ but adds 100 to $B$.
   - *Protection:* Consistency ensures transaction logic preserves all domain rules. The total sum $A + B = 3000$ remains balanced.

3. **Importance of Isolation:**
   - *Failure case without isolation:* An audit transaction $T_2$ reads balances right after $T_1$ writes $A = 950$, before $T_1$ writes $B$. $T_2$ calculates total assets as $950 + 2000 = 2950$. It issues a false financial warning.
   - *Protection:* Isolation ensures $T_2$ sees either pre-transfer data ($A + B = 3000$) or post-transfer data ($A + B = 3000$).

4. **Importance of Durability:**
   - *Failure case without durability:* $T_1$ completes and confirms the transfer. Then a power outage occurs before updates reach disk. The transfer is lost upon reboot.
   - *Protection:* Durability guarantees that committed transactions are logged to stable storage and survive power loss.

## ⚡ Exam Tips & Common Mistakes

- **Name the Enforcing Component:** Always pair each property with its subsystem: Atomicity $\to$ Recovery System (undo log), Consistency $\to$ Programmer Logic + DBMS Constraints, Isolation $\to$ Concurrency-Control System, Durability $\to$ Recovery System (redo log on stable storage).
- **Atomicity vs Isolation:** Atomicity deals with failure and rollback midway through a transaction. Isolation deals with hiding intermediate states from other concurrent transactions.
- **Programmer Role in Consistency:** The DBMS cannot know the intended business logic. If application code adds \$100 instead of \$50, only the programmer can fix that error.
- **Use Clear Numbers in Examples:** Always state $A = 1000$, $B = 2000$, and invariant $A + B = 3000$. Show the intermediate sum 2950 to make your point undeniable.
