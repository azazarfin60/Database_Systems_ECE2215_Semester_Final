# T02.4: Weak vs. Strong Entity Sets

> **Topic:** T02 · E-R & EER Modeling | **Priority:** 🟠 High | **Exam Frequency:** 4/7 finals (11 marks)  
> **Sources:** Silberschatz 7e Ch. 6 (§6.2, §6.5.3, §6.7.3, pp. 245, 259–260, 267–268) · Lecture Deck 05 (Slides 34–37, 42, 48) · Classnote by Raidah (p. 19) · Handnote by Fahim (p. 21)

---

## 1. Core Concepts and Definitions

**Entity Set:** A collection of entities of the same type that share the same properties or attributes (such as the set of all students or all courses in a university).

**Strong Entity Set:** An entity set that has sufficient attributes to form a primary key of its own. It exists independently of other entity sets and is represented in an E-R diagram by a **single rectangle** with its primary key underlined with a **solid line**.
- *Example:* `course` with primary key `course_id` and attributes `title`, `credits`.

**Weak Entity Set:** An entity set that does not have sufficient attributes to form a primary key of its own. Its existence depends on an identifying (owner) strong entity set. It is drawn as a **double rectangle**.
- *Example:* `section` with attributes `sec_id`, `semester`, `year` owned by `course`.

**Identifying Relationship:** The relationship set linking a weak entity set to its identifying strong entity set. It is many-to-one ($N:1$) with total participation from the weak entity, drawn as a **double diamond**.

**Discriminator (Partial Key):** The set of attributes that distinguishes among all entities of a weak entity set that depend on the same strong entity. It is underlined with a **dashed line**.

---

## 2. Strong vs. Weak Entity Sets: Comparison Matrix

| Feature | Strong Entity Set | Weak Entity Set |
| :--- | :--- | :--- |
| **Primary Key** | Has sufficient attributes to form its own primary key. | Lacks a primary key of its own. Uses a partial key (discriminator). |
| **Existence Dependency** | Independent. Does not depend on another entity set. | Existence-dependent on an identifying (strong) entity set. |
| **E-R Notation** | Single rectangle. | Double rectangle. |
| **Relationship Set** | Connected via regular relationship (single diamond). | Connected via identifying relationship (double diamond). |
| **Key Underlining** | Primary key is underlined with a **solid line**. | Discriminator is underlined with a **dashed line**. |
| **Primary Key Formula** | Formed solely from its own candidate key attributes. | Formed by: $\text{PK}(\text{Identifying Entity}) \cup \text{Discriminator}$. |
| **Participation** | Can be partial or total. | Must have **total participation** (double line). |
| **Cardinality** | Typically the "One" side of the relationship. | Many-to-One ($N:1$) from weak entity to identifying entity. |
| **Deletion Rule** | Normal deletion rules apply. | Uses `ON DELETE CASCADE` to delete child rows if owner is deleted. |
| **Example** | `course` with primary key `course_id`. | `section` (`sec_id`, `semester`, `year`) identified by `course`. |

---

## 3. Visual E-R Notation for Weak Entity Sets

When drawing a weak entity set in an E-R diagram, include five visual elements:
1. **Double Rectangle:** The weak entity set.
2. **Double Diamond:** The identifying relationship set.
3. **Dashed Underline:** The discriminator (partial key).
4. **Double Line:** Total participation from the weak entity set to the identifying diamond.
5. **Directed Arrow ($\rightarrow$):** From the identifying diamond to the strong owner entity ($N:1$).

## 4. How a DBMS Handles Weak Entity Sets

A relational DBMS turns a weak entity set into a standard SQL table using three rules:

1. **Composite Primary Key Formation:**
   The DBMS combines the primary key of the identifying strong entity with the weak entity's discriminator:
   $$
   \text{PK}(\text{Weak}) = \text{PK}(\text{Identifying Entity}) \cup \text{Discriminator}
   $$

2. **Table Schema Reduction Without Extra Table:**
   A dedicated table is created for the weak entity. It includes the identifying entity's primary key as a foreign key along with all weak entity attributes. **No separate table is created for the identifying relationship diamond**, because the weak entity table already stores the owner's primary key and has total participation in an $N:1$ link.

3. **Foreign Key Integrity with Cascade:**
   The foreign key in the weak entity table is declared with `ON DELETE CASCADE`. If an owner tuple is deleted, all dependent weak entity tuples are automatically removed:
   ```sql
   CREATE TABLE section (
       course_id   VARCHAR(8),
       sec_id      VARCHAR(8),
       semester    VARCHAR(6),
       year        NUMERIC(4,0),
       PRIMARY KEY (course_id, sec_id, semester, year),
       FOREIGN KEY (course_id) REFERENCES course(course_id) ON DELETE CASCADE
   );
   ```

### 🎯 GQ1 · 2018 Q.1(b) / 2020 Q.2(c) / 2021 Q.8(c) · Strong vs. Weak Entity Sets · [04 Marks]

> *Section A · Asked in: 2018, 2020, 2021 (CLO1) · L2 merge*

**Question (2018 Q.1(b)).** Define entity set. Explain the following with suitable example: (i) strong entity set and (ii) weak entity set.

**Question (2020 Q.2(c)).** Explain the difference between a weak and a strong entity set with appropriate example.

**Question (2021 Q.8(c)).** Explain weak and strong entity set with appropriate example.

**Answer.**

#### 1. Entity Set Definition
An **entity set** is a collection of entities of the same type that share the same properties or attributes (e.g., the set of all students in a university).

#### 2. Comparison Matrix

| Feature | Strong Entity Set | Weak Entity Set |
| :--- | :--- | :--- |
| **Primary Key** | Has sufficient attributes to form its own primary key. | Lacks a primary key of its own. Uses a partial key (discriminator). |
| **Existence Dependency** | Independent. Does not depend on another entity set. | Existence-dependent on an identifying (strong) entity set. |
| **E-R Notation** | Single rectangle. | Double rectangle. |
| **Relationship Set** | Connected via regular relationship (single diamond). | Connected via identifying relationship (double diamond). |
| **Discriminator Key** | None (uses full primary key underlined with solid line). | Has a discriminator underlined with a dashed line. |
| **Composite PK** | Its own primary key. | Formed by (Owner Primary Key + Discriminator). |
| **Example** | `course` with primary key `course_id`. | `section` with discriminator `sec_id`, `semester`, `year`. |

![Weak entity set section connected to identifying strong entity set course via sec_course](diagrams/T02.04_weak_entity_section__L05_p37_fig01.jpg)

#### 3. Concrete Examples
- **Strong Entity Set Example:** `course` has attributes `course_id` (PK), `title`, `credits`. It exists independently.
- **Weak Entity Set Example:** `section` has attributes `sec_id`, `semester`, `year`. A section number like `Sec 1` is meaningless without knowing the course. Its full primary key is `(course_id, sec_id, semester, year)`.

### 🎯 GQ2 · 2019 Q.1(b) · Entity, Entity Set, and DBMS Handling of Weak Entity Sets · [03 Marks]

> *Section A · Asked in: 2019 · L1 (asked once)*

**Question (2019 Q.1(b)).** What are entity and entity set? How is a weak entity set handled in DBMS? Explain.

**Answer.**

#### 1. Definitions
- **Entity:** An object that exists in the real world and is distinguishable from other objects (such as a student or a course).
- **Entity Set:** A collection of entities of the same type sharing the same attributes (such as the set of all students).

#### 2. Handling a Weak Entity Set in DBMS
1. **Primary Key Formation:** The DBMS cannot identify weak entity tuples by local attributes alone. It combines the primary key of the identifying strong entity with the weak entity's discriminator (partial key):
   $$
   \text{PK}(\text{Weak}) = \text{PK}(\text{Identifying Entity}) \cup \text{Discriminator}
   $$
2. **Table Schema Reduction:** A dedicated table is created for the weak entity. It includes the identifying entity's primary key as a foreign key along with all weak entity attributes. The identifying relationship does not need a separate table.
3. **Foreign Key Integrity with Cascade:** The identifying foreign key is declared with `ON DELETE CASCADE`. If the owner entity tuple is deleted, all dependent weak entity tuples are automatically removed.

## ⚡ Exam Tips & Common Mistakes

- **"Weak Entities Have No Key" Trap:** Never write that weak entities have no keys. They lack an independent primary key, but they have a **discriminator (partial key)** and form a full **composite primary key** with their owner.
- **No Table for Identifying Diamond:** When reducing to relational tables, never create a separate table for the double diamond. The foreign key inside the weak entity table captures it completely.
- **Always Mention `ON DELETE CASCADE`:** When asked how a DBMS handles weak entity sets, write `ON DELETE CASCADE` to show how existence dependency is maintained in SQL.
- **Underlining Rule:** Solid line for strong entity primary keys; dashed line for weak entity discriminators.
