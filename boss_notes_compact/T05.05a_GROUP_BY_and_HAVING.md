# T05.05a: GROUP BY and HAVING Clauses

> **Topic:** T05 · SQL (DDL, DML, Aggregates, Subqueries) | **Priority:** 🟠 | **Exam Frequency:** 3/7 finals + CT-02 Q1(d) (24 marks total)
> **Sources:** Silberschatz 7e Ch. 3 (§3.7.2–3.7.3, pp. 92–96) · Lecture Deck 03 (Slides 32–34) · Classnote by Raidah (p. 15) · Handnote by Fahim (pp. 43–44)

## Mechanics of GROUP BY and HAVING

**GROUP BY Clause:** Partitions table tuples into subsets where all rows in a group share identical values in specified grouping columns. Aggregate functions then run on each group independently, producing one summary row per group.

**HAVING Clause:** Filters summary groups after they are formed by `GROUP BY`. Unlike `WHERE`, which filters individual rows prior to grouping, `HAVING` evaluates conditions containing aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`).

**Single Group Fallback:** When a query includes aggregate functions or a `HAVING` clause without an explicit `GROUP BY`, SQL treats all rows passing the `WHERE` filter as a single group.

## The Cardinal Rule of GROUP BY

Every `GROUP BY` query must satisfy this rule: **any attribute appearing in the `SELECT` list outside of an aggregate function must appear in the `GROUP BY` clause.**

```sql
/* ILLEGAL in standard SQL and MySQL ONLY_FULL_GROUP_BY */
SELECT dept_name, ID, AVG(salary)
FROM instructor
GROUP BY dept_name;
```

**Why this fails:** Each `dept_name` group collapses into a single output row showing one average salary. Since a department contains multiple instructors with distinct `ID`s, the database cannot determine which single `ID` to output.

---

## Evaluation Pipeline of a SQL Query

A query executes in a strict logical order:

| Step | Clause | Logical Operation | Status of Data |
| :---: | :--- | :--- | :--- |
| **1** | `FROM` | Identifies source tables and performs joins | Intermediate joined tuples |
| **2** | `WHERE` | Evaluates row predicates and drops non-matching tuples | Filtered individual tuples |
| **3** | `GROUP BY` | Partitions surviving tuples into groups | Group partitions |
| **4** | `HAVING` | Evaluates group predicates and drops non-matching groups | Filtered groups |
| **5** | `SELECT` | Computes aggregates and projects specified columns | Projected result relation |
| **6** | `ORDER BY` | Sorts final tuples ascending (`ASC`) or descending (`DESC`) | Sorted output tuples |

```sql
SELECT dept_name, AVG(salary) AS avg_sal
FROM instructor
WHERE salary > 50000
GROUP BY dept_name
HAVING AVG(salary) > 70000
ORDER BY avg_sal DESC;
```

1. `FROM instructor`: Reads all instructor rows.
2. `WHERE salary > 50000`: Discards any instructor earning \$50,000 or less before grouping.
3. `GROUP BY dept_name`: Buckets remaining instructors by department.
4. `HAVING AVG(salary) > 70000`: Drops departments whose filtered average salary is \$70,000 or less.
5. `SELECT dept_name, AVG(salary)`: Outputs department name and group average salary.
6. `ORDER BY avg_sal DESC`: Sorts the resulting summary rows from highest average to lowest.

---

## WHERE vs. HAVING Comparison

| Feature | `WHERE` Clause | `HAVING` Clause |
| :--- | :--- | :--- |
| **Filtering Target** | Individual rows (tuples) | Aggregated groups of tuples |
| **Execution Timing** | Before `GROUP BY` partitioning | After `GROUP BY` partitioning |
| **Aggregate Functions** | Forbidden (`WHERE SUM(qty) > 10` is illegal) | Allowed and expected (`HAVING SUM(qty) > 10`) |
| **Operation on Rows** | Discards individual rows | Discards entire group summaries |
| **Usage Without GROUP BY** | Filters rows from entire table | Treats the entire table as one single group |

### NULL Values in Grouping
When grouping by an attribute, SQL assigns all rows with `NULL` in that attribute to a single combined `NULL` group.

### 🎯 GQ1 · 2018 Q.7(b) · E-Commerce Multi-Table Business Reporting · 08 Marks

> *Section B · Asked in: 2018 · L1 (asked once)*

**Question.** Consider the following data tables:

`Product (p_id, p_name, quantity, unit_price)`  
`Customer (c_id, c_name, contact)`  
`Sales (c_id, p_id, quantity)`

Write down SQL expressions for following queries.  
(i) Show the information of those customers who have bought more than five different products.  
(ii) Show the information of those products that were sold more than ten pieces.  
(iii) Show the information of the product with maximum sale (maximum sold amount of money or bought by the maximum customer).  
(iv) Show the product id and corresponding remaining quantity of that product.

**Answer.**

*(i) Customers who bought more than five different products:*

```sql
SELECT c.c_id, c.c_name, c.contact
FROM Customer c
JOIN Sales s ON c.c_id = s.c_id
GROUP BY c.c_id, c.c_name, c.contact
HAVING COUNT(DISTINCT s.p_id) > 5;
```

*(ii) Products sold more than ten pieces:*

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
HAVING SUM(s.quantity) > 10;
```

*(iii) Product with maximum sale:*

*Primary interpretation: Maximum sold amount of money ($\sum (\text{quantity} \times \text{unit\_price})$):*

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price,
       SUM(s.quantity * p.unit_price) AS total_sales_value
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
ORDER BY total_sales_value DESC
LIMIT 1;
```

*(Alternative subquery without `LIMIT` to return all tied products on top revenue):*

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
HAVING SUM(s.quantity * p.unit_price) = (
    SELECT MAX(prod_rev)
    FROM (
        SELECT SUM(s2.quantity * p2.unit_price) AS prod_rev
        FROM Sales s2
        JOIN Product p2 ON s2.p_id = p2.p_id
        GROUP BY s2.p_id
    ) AS sub
);
```

*Alternative interpretation: Bought by the maximum number of distinct customers:*

```sql
SELECT p.p_id, p.p_name, p.quantity, p.unit_price,
       COUNT(DISTINCT s.c_id) AS customer_count
FROM Product p
JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.p_name, p.quantity, p.unit_price
ORDER BY customer_count DESC
LIMIT 1;
```

*(iv) Product ID and corresponding remaining quantity:*

```sql
SELECT p.p_id,
       p.quantity - COALESCE(SUM(s.quantity), 0) AS remaining_quantity
FROM Product p
LEFT JOIN Sales s ON p.p_id = s.p_id
GROUP BY p.p_id, p.quantity;
```

*Note on unsold products:* Using `LEFT JOIN` and `COALESCE(SUM(s.quantity), 0)` guarantees that products with zero sales are preserved with their original stock rather than dropped.

### 🎯 GQ2 · CT-02 Q.01(d) · Second-Highest CGPA Without LIMIT · 03 Marks

> *CO2 · Asked in: CT-02 · L1 (asked once)*

**Question.** Given $\text{STUDENT}(\text{StudentID}, \text{Name}, \text{Department}, \text{Semester}, \text{CGPA})$, write SQL query:  
**(d)** Display the students having the second-highest CGPA without using LIMIT.

**Answer.**

```sql
SELECT *
FROM STUDENT
WHERE CGPA = (
    SELECT MAX(CGPA)
    FROM STUDENT
    WHERE CGPA < (
        SELECT MAX(CGPA)
        FROM STUDENT
    )
);
```

*Logic:*
1. The innermost subquery finds the maximum CGPA across all students.
2. The outer subquery finds the maximum CGPA among students strictly below the top grade.
3. The main query displays all students matching that calculated second-highest score, correctly preserving ties.

## ⚡ Exam Tips & Common Mistakes

- **Never Put Aggregates in WHERE:** Conditions like `WHERE SUM(quantity) > 10` are invalid. Use `HAVING SUM(quantity) > 10`.
- **Include All Non-Aggregated Columns:** Every column in `SELECT` outside aggregate functions must appear in `GROUP BY`.
- **Distinct Products in HAVING:** When counting "different products", write `COUNT(DISTINCT s.p_id)`.
- **Use LEFT JOIN for Inventory Balances:** An `INNER JOIN` drops unsold products completely. Use `LEFT JOIN` with `COALESCE(SUM(s.quantity), 0)`.
- **Preserve Ties Without LIMIT:** When `LIMIT` is forbidden, use scalar subqueries with `MAX` or `MIN`.
